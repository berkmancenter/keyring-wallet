# ref-07b-statement-shape

What does [cred-spec #45](https://github.com/trustoverip/dtgwg-cred-spec/issues/45)
cost an implementer who already has WD02-shaped VWCs in the field?

#45 proposes folding the VWC into a generic `StatementCredential` with a
`dtg:witnessed` **profile** — predicate, object, and per-profile constraints,
with `"WitnessCredential"` retained as a registered type alias. This rung measures
the migration against Keyring's real artifacts and real code rather than reasoning
about it.

```sh
npm install && node run.mjs        # acts 1-3 need nothing; act 4 needs cargo
npm run regen                      # rebuild the fixture from the shipped builder
```

## The fixtures are real

- **`../ref-07-dtg-edge-semantics/fixtures/edge-witnessed-captured.json`** — a full
  witnessed exchange run by the reference implementation over real Credo agents,
  each half verified at capture by Keyring's own verifier.
- **`fixtures/vwc-trust-tasks-path.json`** — generated by `build-fixture.mjs`,
  which calls the **shipped production builder**
  (`witness-server/dist` → `buildWitnessCredentialJson`, `WitnessService.ts:231`)
  and then applies the four binding lines from `WitnessTaskSessions.ts:258-262`
  verbatim. It is not a hand-written approximation of what we emit; it is what we
  emit. The captured legacy VWC predates Trust Task Context Binding and carries no
  `taskContext`, which is why this second fixture exists.

Act 2 loads the **real** `@bifold/core` credential predicates from the package's
compiled output — the same module every screen, hook and display handler
dispatches through.

## What it proves

**Act 0.** The VWC validity window is **7.00 days**, computed from the fixture the
shipped builder produced. The claim "our installed base ages out inside a week, so
a shape migration never has to verify both forms side by side" is a measurement,
not a recollection.

**Act 1 — the profile changes no check.** The four things a VWC verifier actually
does — decode-and-compare the witnessed digest, confirm the subject is the issuer
of the referenced VRC, match `taskContext` to the session document, recognise the
credential as a witness attestation — give **identical verdicts on both shapes**.
Only the accessor path differs (`credentialSubject.digest` →
`credentialSubject.object.digestMultibase`). Six subject members before, six after:
the re-expression invents nothing and drops nothing.

Shape **B** — the explicit RDF reification `talltree` and `martipos` favour on the
issue, where the subject DID moves out of `credentialSubject.id` into a `subject`
member — answers **all four checks too**, with one accessor changed per check. B's
cost is not in verification either; it is in everything else that reads
`credentialSubject.id`: holder binding, correlation scope, and the "two credentials
share a subject" ZK predicate. Keyring reads it in the display layer and in contact
matching, so B is a wider change for us than C — the same conclusion #45 reaches
from the spec side.

**Act 2 — the aliases hold, and underneath them we have a latent bug.**

| Credential | `isWitnessCredential` | `isPeerVrcCredential` | lands in |
|---|---|---|---|
| WD02 VWC | true | false | witness display handler |
| statement VWC, alias kept | true | false | witness display handler |
| statement VWC, alias dropped | false | **true** | **Contacts** |
| endorsement statement (a VEC as a profile) | false | **true** | **Contacts** |

The registered-alias mechanism #45 originally proposed does exactly what it
claims: with `"WitnessCredential"` retained, our dispatch is untouched. Since the
thread has now agreed to **delete** the aliases, the act also implements and tests
the replacement — dispatch on `predicate`, falling back to the type list when
there isn't one:

| credential | type dispatch | predicate dispatch |
|---|---|---|
| WD02 VWC | witness handler | witness handler |
| statement VWC, alias kept | witness handler | witness handler |
| statement VWC, alias dropped | **Contacts** | witness handler |
| endorsement statement | **Contacts** | endorsement handler |
| unrecognised predicate | — | `"statement from X"` |

So the alias removal is safe for a wallet that makes this change, and the graceful
degradation Glenn described is real but is not automatic — it is this function. The last two rows are
ours, not the issue's. `isPeerVrcCredential` is defined as *"`DTGCredential` and
not `WitnessCredential`"* (`credentialTypes.ts:81`) — safe only while the VWC is
the sole non-relationship DTG credential a wallet can hold. One type / N profiles
ends that, and any statement credential without the witness alias is filed as a
relationship. This is a small fix (an allowlist rather than a negation) that we
should make before the first non-witness statement credential exists, and it is a
concrete instance of the display-dispatch gap #45's open questions do not cover.

**Act 3 — the Trust Task layer barely notices.** `@bifold/trust-tasks` — the
platform-neutral package carrying document proofs, the binding-0.2 carriage
message and the payload validator — reads `credentialSubject` **zero times**. The
Trust Task model does not see credential shape at all. Three read sites hard-code
`taskContext`'s position inside `credentialSubject`
(`outcomeEvidence.ts:71`, `:227`, `witnessCeremony.ts:169`), and since **WD02
already places `taskContext` at the credential top level**, those three are a
WD02-alignment fix we owe regardless of #45 — not a cost of the profile.

**Act 4 — cross-implementation, and this is where it gets interesting.**

`conformance-rs/` feeds our artifacts to **`dtg-credentials` 0.7.0** (Glenn Gore /
OpenVTC — the catalogue the VTC mints from, published the same day #45 was filed).
Starting from the one shape the reference implementation accepts and re-adding each
Keyring member **in isolation**, so every verdict has exactly one cause:

| Variant | Verdict | Reason |
|---|---|---|
| reference-accepted form | **ACCEPTED** | `type=Witness` |
| `issuer` as `{id, name}` | REJECTED | `invalid type: map, expected a string` |
| `witnessContext.hardwareAttestationIncluded` | REJECTED | unknown member |
| `witnessContext.localityVerification` | REJECTED | unknown member |
| `credentialSubject.parties` | REJECTED | unknown member |
| `credentialSubject.taskDigestMultibase` | REJECTED | unknown member |
| `taskContext` inside `credentialSubject` | REJECTED | unknown member |
| `taskContext` absent | REJECTED | `missing the required taskContext property` |
| `Ed25519Signature2018` proof | REJECTED | `missing field cryptosuite` |
| the #45 statement shape | REJECTED | unknown member |

Nine independently fatal divergences. Three readings, and they point different
ways:

1. **One is ours to fix.** WD02 §VWC says `issuer` **(string, REQUIRED)**. We emit
   `{id, name}` — legal W3C VC 2.0, off-spec DTG. That is a Keyring bug, found by
   running someone else's implementation against our output.
2. **Several are unspecified, not wrong.** WD02 says **nothing** about how a
   verifier should treat members it does not recognise — `grep` for extensibility
   language in `spec/body.md` returns nothing. The Rust catalogue models each
   `credentialSubject` as a closed schema (serde `deny_unknown_fields`); Keyring
   adds members freely. Neither is violating the spec, because the spec has no
   opinion. Every additional member we carry — `parties`, `taskDigestMultibase`,
   `localityVerification`, `hardwareAttestationIncluded` — is independently fatal
   to the other implementation.
3. **This is #45's problem in miniature.** The issue says a profile fixes
   *"required and optional additional members and their schema"*. Act 4 is what
   happens when two implementations disagree about that set: not a warning, not a
   degraded read, a hard parse failure. A statement type with N profiles multiplies
   the number of member sets any given verifier has never heard of, so
   unknown-member handling stops being an editorial detail and becomes the
   mechanism that decides whether profiles interoperate at all.

The last row also prices the other side of the migration: the reference
implementation would need a new `CredentialSubject` variant. #45 is not free for
the Rust catalogue either, and that cost is worth naming in the thread rather than
discovering later.

## What it does NOT prove

- **No proof verification.** Act 1 compares field values and Act 4 tests
  deserialization; neither checks a signature. The captured fixture's
  `Ed25519Signature2018` proofs were verified by Credo at capture time and that
  receipt is frozen in `captureMeta`. Signature coverage is `ref-07c`'s subject.
- **Nothing about display rendering.** Act 2 tests the dispatch predicates, not the
  handler output or any screen. Whether a wallet renders an unknown predicate
  usefully is untested and, as the rung notes, unspecified.
- **The reference implementation's strictness is a choice, not a verdict.** Act 4
  reports what `dtg-credentials` 0.7.0 does. It does not claim the crate is wrong
  — on `issuer` it is right and we are not — nor that WD02 requires strictness.
- **Not a live statement-shaped exchange.** No witness minted a `StatementCredential`
  over DIDComm; Act 1 re-expresses a captured one. Running the live leg would need
  a flag in `witness-server` and rung-local context terms, deliberately not done.
- **Nothing about VEC, VAC, VDC, VIC or VPC.** Only the VWC's fold is measured.
