## The change as built (Option A — chosen)

`packages/tsp-js/src/crypto/hpke.ts` bound directly to hpke-js, which needs
`crypto.subtle`. The patch:

| File | Change |
|---|---|
| `src/crypto/hpke-noble.ts` | **new**, ~150 lines — RFC 9180 HPKE-Auth (AuthEncap/AuthDecap, key schedule, single-shot seal/open) on `@noble/{curves,hashes,ciphers}`; exports mirror `hpke.ts`'s contract |
| `src/crypto/hpke.ts` | +34 lines — runtime backend detection (`crypto.subtle` present → hpke-js, else noble), plus `activeBackend()` / `setBackend()` and a `TSP_HPKE_BACKEND=noble\|webcrypto` override so the suite runs against both |
| `package.json` | +1 dependency: `@noble/ciphers` (`@noble/curves` and `@noble/hashes` were already dependencies) |

`seal`/`open` signatures are untouched, nothing is removed from the public API,
and `pack`/`unpack` are not modified at all. `package-lock.json` is deliberately
left out of the branch for maintainers to regenerate.

*Alternative considered — **B, an injected backend**: export a `CryptoBackend`
interface and let hosts supply one. More explicit and flexible, but a larger
public API for a case the runtime can detect itself. Raised as an open question
below rather than assumed away.*

## Why this serves the community, not just our use case

- **It unblocks every runtime without WebCrypto — mobile is only the loudest
  case.** Hermes (React Native) has no `crypto.subtle`, so today `vti-tsp-js`
  cannot run in *any* React Native wallet. The same gap affects older Node
  targets, some embedded/edge runtimes, and test environments that stub
  WebCrypto. The package's README already advertises "runs anywhere WebCrypto
  does" — this changes that to "runs anywhere," which is a stronger claim for
  a spanning-layer library whose entire premise is universality.
- **It matches where the ecosystem is heading.** The VTA, the mobile core, and
  the browser plugin all treat TSP as the preferred envelope; a JS wire layer
  that cannot run on phones is a structural gap in that story, and mobile is
  where the remaining unimplemented client surface lives.
- **It reduces the dependency surface rather than growing it.** The noble
  primitives are audited, dependency-free, and already transitively present
  (hpke-js's own ChaCha20Poly1305 vendors noble-ciphers code).
- **No behavioural fork.** The suite IDs, key schedule, and wire output are
  identical by construction and proven so below — this is an implementation
  choice, never a protocol variant.

## Why it doesn't break anything (evidence)

| Claim | Evidence |
|---|---|
| Correct per the standard, independent of any implementation | The **official CFRG test vector** for `mode_auth` + our exact suite is reproduced byte-exact: `AuthEncap` `enc` and `shared_secret`, `AuthDecap` shared secret, and the sealed ciphertext (`vectors/cfrg-auth-x25519-chacha.json`, extracted from cfrg/draft-irtf-cfrg-hpke) |
| Interoperable with the current implementation | Two-way: noble opens hpke-js output and vice versa |
| Compatible with real TSP wire bytes | Frozen wire fixtures from ref-01 (direct, nested, two routed legs) are opened by the noble backend using the library's own CESR framing and `-E` envelope as HPKE `info` |
| **The package's own suite passes on both backends** | `npm test` → **42/42 pass** with the default backend and again with `TSP_HPKE_BACKEND=noble` |
| Byte-compatible with the Rust lineage | That run includes `tests/interop.rust-vector.mjs` — the fixed-key `affinidi-tsp` vector — so the noble path satisfies the same Rust-generated bytes the WebCrypto path does |
| No API change for existing consumers | `seal`/`open` signatures untouched; `pack`/`unpack` unmodified; additions are two small helpers |

## Open questions for the maintainer

1. Preference between A (auto-select) and B (injected backend)? A is less API;
   B is more explicit.
2. Should the noble backend become the *default* everywhere (fewer code paths,
   no WebCrypto dependency at all) with hpke-js kept as an option — or stay
   the fallback? Performance data on the target runtimes would decide it.
3. Interest in an upstream React-Native smoke test, given we'll have one?
