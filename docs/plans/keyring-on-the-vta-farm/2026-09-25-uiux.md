# 2026-09-25 — UI/UX: the screens for owning an agent from the phone

**Plan:** [`own_agent_subtask.md`](./own_agent_subtask.md) §7. **Author:** the UI/UX lane.

## What was concluded

1. **The flow starts from My Agent's empty state**, which gains **Create my agent** as its primary button. Today's **Link your agent** stays as the secondary **I already have one — link it**. There's no new tab or menu entry: a person with no agent already lands on this screen.
2. **The address comes before the owner code.** The first draft asked for the owner code first. It was reordered because the phone's key is a `did:peer:2` that names the agent's mediator, resolved from the agent's DID before the key is made (`vtaEnrolment.ts` `resolveVtaMediator`, then `createVtiClientDid`). The Farm's wizard also shows the address first (Create session), then asks for the Admin DID. So: explain → address → owner code → connect → backup → ready.
3. **The screens say "protected by your Face ID", never "stored in secure hardware"**, because Phase 1 keeps a software key behind a fresh confirmation (§3, D1). A screen that claimed hardware custody would be wrong on every phone that runs Phase 1.
4. **Face ID is never a step of its own.** It appears as the system prompt when the phone acts as owner: making the code, connecting, and granting a backup. Cancelling it isn't an error and shows no message.
5. **The browser plugin isn't offered as a backup** until D4 is decided. It keeps a VTA-minted key, so offering it would make a custody choice on the person's behalf.

## Superseded

- **Owner code first, address second.** This was the first draft's order. It fails because the key can't be made without the agent's mediator (point 2).
