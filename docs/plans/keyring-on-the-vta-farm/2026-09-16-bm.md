## F2 — Adopt "the agent is the state" for agent-owned state; reject its no-offline corollary

*Framing amended by F8, which rebased this document onto two days of execution. The reasoning below is preserved as written.*

**Evidence.** [[AGENT-STATE]]'s rule for a client author is *"do not build a second copy of anything the agent already is"*, with authority taken from a who-am-I task and *"never inferred from anything stored locally"*. Its stated costs are equally explicit: *"no cache to invalidate because there is no cache"*, and *"no optimistic rendering and no offline mode, because there is nothing to render from when the agent is unreachable."*

The first half fits this subtask; the second does not, on three measured counts:

1. **The in-person path has no VTA in it.** The VRC/witness exchange is peer-to-peer, and the argument for `eddsa-jcs-2022` there is that a credential formed in person verifies with no `@context` resolution ([`openvtc-integration-plan.md`](../openvtc-integration-plan.md) §4.5). A wallet that cannot render its own credentials without a reachable agent fails precisely where that path is meant to work.
2. **Not persisting inbound documents loses them.** The sibling records an open upstream defect: `@openvtc/vti-didcomm-js` acks an inbound frame before dispatching it, and the ack tells the mediator to delete its copy ([`pnm_cnm_subtask.md`](../openvtc-integration-plan/pnm_cnm_subtask.md) §4.3). A browser worker's teardown is occasional; a mobile OS backgrounds and kills apps as routine.
3. **Idempotence is local state.** The wire invariant is that a retry re-sends the document unchanged, only a genuinely new request mints a new id, and a `duplicate` refusal is answered by reading the prior outcome ([`pnm_cnm_subtask.md`](../openvtc-integration-plan/pnm_cnm_subtask.md) §2.2). None of that is satisfiable without recording the id durably *before* the send.

**Position adopted.** New §2.6, stating the boundary once: no local mirror of anything the agent owns; durable local state only for what Keyring owns — its keys and credentials, inbound documents persisted before acknowledgement, and the in-flight task-id ledger. §7 gains the rendering rule that follows — agent-owned state renders from the current session's replies or as a stated unreachable state, never as a last-known value — and §8 gains `e2e:agent:unreachable` as P7 stretch (F7).

**Supersedes.** Nothing stated — the subtask had no boundary, and §7's rule that the legal name lives on the VTA and is *"not duplicated in Keyring"* was its only instance. That sentence is now a case of a stated rule rather than a one-off, which is the difference between a convention an implementer can apply to the next screen and one they cannot.

## F3 — The ceremony's preview is already a task, so §7's S10 can be made checkable

*Framing amended by F8, which rebased this document onto two days of execution. The reasoning below is preserved as written.*

**Evidence.** [[AGENT-STATE]]'s preview pattern is the real task reporting rather than acting, so the UI *"never disagrees with the agent's logic."* At the baseline, `vta-sdk/src/trust_tasks.rs` registers `persona/disclosure/preview/1.0` beside `persona/disclosure/present/1.0`, and the published `@openvtc/pnm-core` 0.9.1 tarball implements both (`dist/persona/disclosure.js`; the two URIs appear as string literals). `vta/contexts/preview-delete/1.0` is the same pattern for a destructive operation.

Reproduce:

```sh
gh api repos/OpenVTC/verifiable-trust-infrastructure/contents/vta-sdk/src/trust_tasks.rs?ref=53a7cde4 \
  --jq .content | tr -d '\n' | base64 -d | grep -oE '"https://trusttasks.org/spec/(persona/disclosure|vta/contexts)/[a-z/.0-9-]+"' | sort -u
curl -sL "$(npm view @openvtc/pnm-core@0.9.1 dist.tarball | tr -d "'")" | tar xz -O package/dist/persona/disclosure.js \
  | grep -oE 'persona/disclosure/[a-z-]+/[0-9.]+' | sort -u
```

**Position adopted.** New §3.9. §3.3's *"disclosure preview, then presentation"* is two tasks; S10 renders the response to the first rather than a locally composed rendering of the face. Two corollaries land with it: the S9 match code is displayed rather than derived (and if ever derived, from the **decoded** digest bytes — the encoded-string slice upstream's mobile core takes leaves ~17.6 bits where the operator believes ~35, [`pnm_cnm_subtask.md`](../openvtc-integration-plan/pnm_cnm_subtask.md) §4.2), and the app never predicts a verdict, because whether requirements are met is `submit/0.2`'s answer. P6's acceptance criteria gain the S10 rule; the resumption rule is stated in §2.6 and §7 and proven by `e2e:vetting:resume` as P7 stretch (F7).

**Supersedes.** Nothing stated. S10's *"exactly what the vetter will see"* was a claim with no named source; it now has one, and a failing test if it drifts.

## F4 — `vta/app-state/*` is the mechanism the doctrine needs, and it is already in the client

*Framing amended by F8, which rebased this document onto two days of execution. The reasoning below is preserved as written.*

**Evidence.** The baseline registers a third store beside the vault and agent memory: *"versioned, namespaced, per-context JSON an application owns and the VTA does not interpret"*, addressed `(contextId, namespace, key)` and gated on context access. `pnm-core` 0.9.1 ships the client (`dist/app-state/`, six URIs `get`, `get-many`, `put`, `put-many`, `list`, `delete`), with `expectedVersion` preconditions (`0` = create-only), an RFC 7386 `mergePatch` path for concurrent writers, `list` with `sinceVersion` as a change feed that always includes tombstones, and — the detail that matters for a phone on a conference network — a failed precondition that returns the VTA's current version *and value*, so a conflict resolves without a re-read.

Upstream also records why this is not `vta/memory/*`: `MemoryItem` has nothing to hang a precondition on, and *"'forget everything' has to stay a safe thing to ask an agent, which it cannot be if account state lives there."*

**Position adopted.** A §5 bullet naming the three stores and what belongs in each, and a P4 criterion that an `app-state` record round-trips and a deliberately stale conditional write is answered with the current version and value rather than an overwrite. Deliberately **not** adopted for anything that must render before the first successful session — putting first-run UI state behind a round trip buys nothing and costs a reachability dependency.

## F8 — Rebased onto two days of execution: the boundary is conditional, and the article is the case for B

**Evidence.** This document was drafted against the subtask as proposed in #53 (`b602f43`) and landed on `6fcc280`, after `3f5afeb` and `6fcc280` recorded what P0–P5 actually measured (`[2026-09-16-al.md](./2026-09-16-al.md)`). Three of its premises moved:

1. **`pnm-core` is no longer a dependency.** §2.1 now reads *"upstream's TypeScript client is a reference, not a dependency"* — the community leg is Keyring's own Credo transport (`VtiMediatorTransport.ts`, `vtiAgent.ts`), because those agents publish an Affinidi-style mediator `DidCommV2Carriage` cannot reach.
2. **§2.4 is an open decision.** A — the phone is the agent, its own `did:peer:2` is the member, no VTA — or B — Keyring drives the user's VTA (`[2026-09-16-al.md](./2026-09-16-al.md)` F14). P4 shipped as A.
3. **The identity bug is evidence for this document's own divergence.** F14 measured both credentials sitting at the mediator *"for a DID the app no longer remembers because it mints a new `did:peer:2` on every connect"*, and P5's first rung is now one identity kept across restarts. F2 argued for durable local state on principle; execution hit it as the first bug.

**Positions adopted, each superseding a framing above:**

- **F1's framing.** [[AGENT-STATE]] is not the design rationale of a package we embed; it is the ecosystem's design intent for a VTA client, and — the more useful reading — **the written case for §2.4's option B**, from the people who built the stack. The reference entry says so.
- **F2's boundary.** §2.6 no longer asserts the doctrine unconditionally. It splits: under B the full no-mirror rule binds and carries the who-am-I and `app-state` criteria the doctrine implies; under A the doctrine's subject does not exist, because the phone *is* the agent. The architecture-neutral half — the community owns membership, requirements and the verdict under either option, and Keyring owns its credentials, a restart-surviving identity, persisted inbound documents and the task-id ledger — binds either way.
- **F3's preview rule.** Generalised from *"the agent's answer"* to *"produced by the code that will act"*, which is what the rule was always for. Under B that is `persona/disclosure/preview/1.0`; under A it is an implementation rule with no task behind it — one function builds the card, the screen shows its output.
- **F4's `app-state`.** Not a shipped surface any more. Its six operations are upstream's and still worth knowing, but adopting them under B is a port onto our own transport; under A it is not needed.
- **P4's criteria, withdrawn.** F2 and F4 put a who-am-I criterion and an `app-state` round-trip in P4's gate. P4 is now recorded as done under A, and neither criterion has meaning there, so both move into §2.6 as what B carries rather than into a phase that has shipped.
- **The second runner is renamed** `e2e:counterparty:unreachable`, since under A the unreachable party is the community, not an agent.

**Supersedes.** The four framings named above, preserved in full in F1–F4, and the P4 criteria as F2 and F4 first proposed them.

**What it does not change.** Every architecture-neutral rule: the match code displayed rather than derived, no locally predicted verdict, persist-before-ack, the task-id ledger, and the resilience runners as P7 stretch (F7).
