## F1. Approval rules are one policy row, not a task family

- The rules are the reserved policy row `approvals` (`vta-sdk/src/approvals/mod.rs:50`), read and written with `policy/get/0.1` and `policy/upsert/0.2` (`vta-sdk/src/client/policy.rs:29-88`; server dispatch `vta-service/src/trust_tasks/mod.rs:1747-1754`). The rules sit in `ext["openvtc.approvals"]`, the approver sets in `ext["openvtc.approver-sets"]` (`approvals/mod.rs:72-75`).
- The client synthesizes the Rego (`synthesize_rego`) and the VTA rebuilds it and compares bytes (`approvals/mod.rs:22-30`; `vta-cli-common/src/commands/approvals.rs:88-108`; the reserved-row check in `vta-service/src/operations/policy.rs` ~`:154-178`). **Position:** Keyring ports the synthesis and proves it with two-way vectors, or does not write rules.
- A rule (`ApprovalRule`, `approvals/mod.rs:96-127`): `taskType`, `requires: reauth|consent`, `approverSet`, `minApprovals` (≥1), `excludeRequester`, `contexts`. Per task type and context; no per-key or per-caller rule. **Position:** the groups a person sees are Keyring's (subtask §2.4).
- pnm's `approvals list|require|remove|approvers add|remove|explain` (`pnm-cli/src/cli.rs:2463-2531`) are client-side edits of that row; `explain` is computed locally because `policy/evaluate/0.3` is not served (`vta-sdk/src/trust_tasks.rs:1967`). pnm has no approve/deny or pending-list command (`docs/05-design-notes/approvals-convergence.md:250-253`).
- **Enforcement is off by default** and is a config flag with a restart (`docs/02-vta/approvals.md:13-16, 131-150`); no config task reports it. **Position:** the screen never claims a rule is in force; VTI-Q33.
- **Authorization:** read needs Admin or Initiator (`operations/policy.rs:72,121`); write needs an unrestricted Admin (`:142,246`; `vti-common/src/auth/extractor.rs:329-331,487-492`). ACL `kind` and `label` are consulted nowhere, so a phone entry is judged by role and scope only. Own-agent owner phones are unrestricted admins (the Farm's grant, measured 2026-09-25; the twin's `import-did --role admin`), so they can write.
- **Approving:** a DI-proved `task-consent/decision/0.1` by a member of the named approver set; the bearer token is ignored (`vta-service/src/trust_tasks/task_consent.rs:111-130,205-231`). Approver sets name DIDs; no ACL entry is needed (ceremony allowance, `vta-service/src/messaging/auth.rs:92-104`). Self-approval is allowed unless `excludeRequester` (`task_consent.rs:233-253`).
- **Lifecycle:** pending record 900 s (`vta-service/src/policy_gate.rs:44`), grant 600 s (`task_consent.rs:23`); the request is pushed once, when newly raised (`policy_gate.rs:621-634`), over TSP when the device was last seen on TSP, else DIDComm at its mediator (`consent_request.rs:160-303`); no push without a route (`:190-209`). No pending-list or status task (`vta-cli-common/src/consent.rs:11-13`). **Position:** pending is the phone's own inbox; VTI-Q34.
- `approve_scope` matters only for cross-context consent (`task_consent.rs:61-108`); `step_up_*` are legacy (`approvals-convergence.md:140-144`). `acl/swap-key` rebuilds the entry dropping `allowed_keys`, `approve_scope`, `step_up_*` (`vta-service/src/operations/acl.rs:904-910` ✔; VTI-46), and approver sets name DIDs, so a swap leaves the set naming the old DID (inferred from the storage shape, not run). **Position:** Keyring rewrites `owners` after every swap.
- **Prior art.** The browser plugin's "Approvals" pane manages *messaging* consent (`consent/*/1.0`), not this row (`packages/extension/src/manager/panes/approvals.tsx:1-20`); its approver side is complete — verifies the signed request, keeps a durable pending inbox, biometric confirm with a digest comparison (`packages/core/src/inbound/task-consent.ts:1-40`, `inbound/pending.ts:1-22`, `packages/extension/src/confirm.tsx:41-52,159-188`). openvtc has no approvals implementation. **Position:** follow the plugin's approver side; do not copy its conflation of the two consent systems.

## F2. The vault is written by whoever holds the credential, and the phone holds it

- Eight verbs, each a Trust Task `https://trusttasks.org/spec/vault/credentials/{receive,query,get,archive,unarchive,delete,restore,purge}/0.1` (`vta-sdk/src/trust_tasks.rs:776-822`; handlers `vta-service/src/trust_tasks/cred_vault.rs`), over the same spine as every task — DIDComm, TSP or `POST /trust-tasks`. Specs for all eight exist at the trust-tasks-tf pin.
- **Capabilities:** receive needs `VaultWrite` (`cred_vault.rs:131` ✔), query/get `VaultRead` (`:365,:425`), the lifecycle verbs `CredentialWrite`. Admin and Initiator derive all three (`vti-common/src/acl/mod.rs:343-379`). `persona-holder` gates `persona/*` only and does not affect the vault.
- **Custody:** without `contextId`, a caller with exactly one context binds the record to it; anyone else — an unrestricted admin — stores it **unscoped** (`cred_vault.rs:396-417` ✔), and an unscoped record is readable by every vault reader of the agent (`vta-vault/src/query.rs:367-372`). The spec says an absent `contextId` means the consumer's own context (`specs/vault/credentials/receive/0.1/spec.md:81`). **Position:** Keyring always sends the persona's `contextId`; VTI-Q36. The Rust SDK and pnm cannot send `contextId` (`vta-sdk/src/client/vault.rs:297-313`); the wire and the plugin can (`packages/core/src/vault/credentials.ts:223-243`).
- **Idempotence:** the storage id is the given `id`, else the VC's `id`, else a fresh uuid (`cred_vault.rs:385-394`); a put on an existing id replaces it (`vta-vault/src/storage.rs:40-56`), with no custody check, and resets the lifecycle to Active (`vta-vault/src/receive.rs:432`). **Position:** send the VC's `id`; VTI-Q36 for the cross-context overwrite.
- **Verification on receive:** eddsa-jcs-2022 over a single `proof` whose `verificationMethod` sits under the issuer (`vta-vault/src/di_verify.rs:41-63`, `receive.rs:360-391`). A proof set is refused (`di_verify.rs:48-54` ✔; VTI-44 (e)); the VTC signs with a set when it holds several keys (`vtc-service/src/credentials/signer.rs:139-150`).
- **Indexing:** type, `community_did`, `issuer_did`, `purpose`, `status` (`vta-vault/src/model.rs:320-336`). `subject_did` is stored but neither indexed nor returned; `community_did` is never populated (`receive.rs:235,420,538`). `purpose` is derived from the type names: membership, endorsement (`receive.rs:712-733` ✔) — roles and vetter grants both land under `endorsement`. **Position:** read back by purpose, then filter bodies by subject.
- **Delivery:** the VTC sends each credential as its own `credential-exchange/issue/0.1` to the member's (persona's) DID through a 24-hour outbox (`vtc-service/src/credentials/delivery.rs:33-109,154-176`; `docs/03-vtc/credential-delivery.md:17-33`). The VTA stores an `issue` itself only when it is addressed to the VTA (`vta-service/src/messaging/router.rs:448-449` → `operations/credential_exchange.rs:71-108`, which uses a fresh uuid and no context), and it listens only as its own DID (`vta-service/src/messaging/service.rs:143-163` ✔). So persona-addressed credentials reach the phone, not the vault. **Position:** write-through by the phone; VTI-Q35 asks whether the VTA should receive for the personas it holds.
- **Read-back** by a second or restored device: query by purpose, get each id, filter by subject — what openvtc's recovery does (`openvtc-core/src/rebuild.rs:297-333,352-354`). openvtc's sync pushes memberships only (`openvtc-core/src/credential_sync.rs:74-132`). **Position:** Keyring pushes roles and grants too.
- **Revocation** is refreshed only when a credential is presented (`vta-vault/src/status.rs`; callers in `operations/credential_exchange.rs:636,769,984,1248`). **Position:** the phone checks status itself before showing a card as current.
- **VTI-Q27** (a lost membership credential cannot be fetched again): the vault closes the device-loss half only for credentials the phone already stored; nothing covers a delivery the phone never received.

## F3. The real credentials, and what the Wallet needs

Read from keyring-test-vtc's admin record of a member (`vtc/members/credentials/0.1`, 2026-09-26 ~02:10Z):

- membership: `type ["VerifiableCredential","DTGCredential","MembershipCredential"]`, no `name`, `issuer` a bare DID string, `validFrom` only, `credentialSubject {id}`;
- role: `type ["VerifiableCredential","DTGCredential","EndorsementCredential"]`, the same issuer, `validFrom` only, `credentialSubject {endorsement, id}`.

The VTC builds them with `dtg_credentials::DTGCredential::new_vmc` (`vtc-service/src/members/inbound_vmc.rs:444`). The UI/UX lane's reading of the Wallet (`ListCredentials.tsx`, `OpenIDCredentialRecordProvider.tsx`, the relationship-family hide rule, `display.tsx:422`'s `issuanceDate`) is theirs; the constraints it produced are the subtask's §6.

## F4. Positions taken

1. The phone writes through; no community-to-vault path is assumed.
2. Every vault write carries the persona's context and the VC's id.
3. Roles and vetter grants are kept, not only memberships.
4. Rules are written only by a byte-exact synthesis proved against vta-sdk.
5. The owner devices' approver set is Keyring's to keep current, including after swaps.
6. No screen claims enforcement.
7. Phases V1 (write-through), V2 (read-back), A1 (read rules, answer), A2 (write rules), gated on the lab twin with enforcement on and on the Farm runner.

New upstream questions VTI-Q33–Q36 go into `docs/VTI_UPSTREAM_FINDINGS.md`, not sent.
