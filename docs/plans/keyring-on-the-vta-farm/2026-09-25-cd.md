## F1 — What the plugin does to own an agent (R)

- **Taking ownership.** The plugin mints a temporary Ed25519 `did:key` and prints a `pnm acl create … --role admin --expires 1h` line for an operator. It never grants anything itself (`extension/src/grant-command.ts:52-73`, `extension/src/offscreen.ts:1739-1757`).
- **The long-term key comes from the VTA.** Connected as that temporary key, it runs `provision/integration/0.3` with `ask.type: "adminRotation"` (`core/src/provision/request.ts:91-125`, `run.ts:123-231`). The VTA mints the long-term Ed25519 admin key and returns its private key sealed to the temporary key (`run.ts:186-230`). The plugin's comment says the VTA mints it "under its own custody" (`offscreen.ts:1719-1723`).
- **The swap is unused.** `acl/swap-key` is present but marked "currently unused" (`core/src/onboarding/swap.ts:15-17`).
- **No backup-owner flow.** The ACL tasks exist (`core/src/admin/acl.ts:19-116`), and backup export/import is deliberately withheld from the browser (`core/src/admin/backup.ts:1-43`).
- **Portability to React Native.** The core is mostly portable: noble, scure, cbor-x, and HPKE in pure TypeScript, _"a React Native host does not"_ have `crypto.subtle` (`provision/hpke.ts:14-19`). What remains is browser-only (IndexedDB, `chrome.*`, WebAuthn, `crypto.subtle.digest`), and signing is hard-wired to an in-memory Ed25519 key (`trust-tasks/sign.ts:70, 89`).

**Position.** Keyring does not adopt the plugin's onboarding. It yields a VTA-minted, VTA-retained key, which the parent's F2 rules out. The plugin is used as a reference for the ACL task shapes and for the backup direction (the owner grants the plugin's temporary key).

## F2 — What "owner" means on a VTA (R)

- **No owner tier.** "Super-admin" is `admin` with no context restriction (`vti-common/src/acl/mod.rs:492-513`, `:868-870`); there is nothing above it. Rows are permanent by default (`:752-769`).
- **Delegation.** Only a super-admin may create another unrestricted admin (`acl/mod.rs:1081-1112`, used at `operations/acl.rs:361-363`). Any sufficiently privileged admin may delete another admin, but not itself (`operations/acl.rs:783-813`).
- **The swap.**
  - `acl/swap-key` moves the caller's own row, keeps its role and contexts, drops the expiry, and writes the new row before deleting the old (`operations/acl.rs:836-930`).
  - It does not carry `step_up_approver`, `approve_scope` or `allowed_keys` (`:913-919`).
  - Its link proof must be EdDSA (`vta-sdk/src/protocols/acl_management/swap.rs:171, 208`).
- **What the Farm grants is unknown.** The guide pairs the Admin DID paste with `vta import-did --role admin`, which writes an unrestricted, permanent admin (`vta-service/src/import_did.rs:57-71`; `vti-setup/developer/01-personal-vta.md:64-79`). Whether the Farm does exactly that is not documented. **I → measure M2.**
- **No recovery mechanism upstream** beyond several admins and a password `vta/backup` export (super-admin only; `trust_tasks/backup.rs`).

## F3 — Keys on the phone, and why the owner key stays software for now

- **Today's manager key (R).** It is a software Ed25519 key in Askar (`core/src/utils/agent.ts:82-87`), wrapped as `did:peer:2` naming the agent's mediator (`VtiMediatorTransport.ts:242-272`). It is minted only after the agent's DID is known (`vtaEnrolment.ts:58-59`).
- **Keyring's signatures are Ed25519 only (R).** Its Trust Task proofs and JWS are `eddsa-jcs-2022` / `EdDSA`, and its verifier rejects other suites (`packages/trust-tasks/src/documentProof.ts:218, 242, 326, 494`).
- **A secure-hardware key is registered but unused for this (R).** Credo's `SecureEnvironmentKeyManagementService` (`@animo-id/expo-secure-environment`) is already registered, with `biometricsBacked: false` (`utils/agent.ts:85`).
  - It supports **P-256 signing only**, with no key agreement (the patch and its build).
  - iOS: Secure Enclave with `.biometryCurrentSet` when biometric-backed.
  - Android: StrongBox, sign-only, biometric per use.
- **So a hardware key cannot carry Keyring's agent session (I).** DIDComm authcrypt and TSP both need key agreement on the phone's key. The swap's new key must be Ed25519 (F2).
- **A hardware owner could sign over REST instead (I, unmeasured).** The VTA's `/auth` accepts a DI-signed `auth/authenticate/0.1` from any resolvable DID (`vta-service/src/routes/auth.rs:152-164`). The proof library lists P-256 with `ecdsa-jcs-2019` (`affinidi-data-integrity` 0.7.11 `crypto_suites.rs:37-39, 71, 168`). The module comment still says eddsa, so this needs a measurement: M4.
- **The attestation key cannot be a DID key (R).** `react-native-attestation`'s iOS key is an App Attest key; its assertion signs authenticator data, not the message (`ios/Attestation.mm:395-496`).
- **Consequence (I).** Re-enrolling Face ID destroys a `biometryCurrentSet` key, and StrongBox-only generation fails on phones without StrongBox. Both argue for a backup owner before a hardware owner.

**Position.** Phase 1's owner key is Ed25519 inside the encrypted wallet. Owner acts require a fresh biometric or passcode confirmation. A hardware P-256 owner, signing over REST, is Phase 3, conditional on M3 and M4. This supersedes the parent §3.2 reading that the pasted key would be hardware-held on this path. That reading holds only once M3 and M4 do; until then the pasted key is software, as it is for every link today.

## F4 — The Farm wizard

- **No Farm code is public (R).** Not in any pin, nor in `scripts/openvtc/`.
- **The only description is the guide:** create an account with a passkey → Create VTA → Create session (the VTA DID is shown) → paste the Admin DID → Provision agent → "Agent is online" (`vti-setup/developer/01-personal-vta.md:38-80`).
- **Input and output.** The input example is an Ed25519 `did:key:z6Mk…`, and no redirect or callback is documented.
- **Ordering (R).** The VTA DID appears before the Admin DID is asked for. That fits Keyring, which needs the agent's DID before it can mint its key.

**Position.** The flow runs address first, owner code second. The QR ask (U1) reuses Keyring's existing `keyring://vta/enrol` exchange (`packages/trust-tasks/src/enrolment/offer.ts`, `vtaEnrolment.ts`) rather than inventing a new one: the Farm would host the page our lab already implements.

## F7 — M1 measured: the Admin DID field takes a did:key only, so the temporary key is one

**Measured.** On Alberto's own agent at the VTA Farm portal (`vtafarm.ic3.dev`), 2026-09-25, Keyring's manual-link code (a `did:peer:2`) was pasted into an existing agent's **Link another PNM → Admin DID**. The portal refused it: _"Paste only the did:key value (e.g. did:key:z6Mk…) with no surrounding text, labels, quotes, or whitespace."_ The new-agent wizard's Admin DID field carries the same placeholder. The VTA itself would have accepted it (`vta import-did` checks only `starts_with("did:")`, `vta-service/src/import_did.rs:22-24`), so the limit is the portal's form. M2 is still open: the ACL showed "Not synced yet" and no grant was made.

**Design adopted.** A link without a QR shows a temporary Ed25519 `did:key` (the pnm and plugin pattern), and the first connect swaps it onto Keyring's `did:peer:2`. Evidence that this works, read at the pins:

- **The swap checks no DID method (R).** `operations/acl.rs:849-944` checks only that the new DID differs from the caller, that the caller's entry exists, and that the new DID has none. The ACL is keyed by the DID string (`:881-887`). The swap's verifier accepts a `did:peer:2` key as a multibase key or a JWK (`vta-sdk/src/protocols/acl_management/swap.rs:400-433`).
- **Replies reach a did:key (R).**
  - The VTA replies to the authenticated sender and forwards through its own mediator (`messaging/service.rs:535-600`; `affinidi-messaging-sdk transport_adapter.rs:99-145`).
  - The mediator treats a recipient with no DIDComm service as local and queues the message for it (`routing.rs:382-405`).
  - Upstream states this design for did:key approvers (`trust_tasks/step_up.rs:782-784`).
- **This rests on one assumption (INFERRED).** The Farm VTA's configured mediator is the one its DID document advertises, which is the mediator the phone signs in to.
- **No REST is needed.** REST sign-in exists (`routes/auth.rs:152-306`), but it would add a whole transport to Keyring.

**Superseded.** Before this, §1 said the owner code was the phone's `did:peer:2`, and that the address came first because that key names the mediator. The address still comes first, now because the phone signs in through the agent's mediator. The QR path keeps `did:peer:2`, because the lab enrol page requires it (`scripts/openvtc/local-vti-stack/enrol-page/server.mjs:176`).

**Found on the way, recorded upstream as VTI-46 (not sent).** `acl/swap-key` carries only role, label, contexts, kind, capabilities and device (`operations/acl.rs:902-908`). It resets `allowed_keys` to none, which means all keys in scope and so **widens** a key-restricted grant. It also drops `approve_scope` and the step-up settings. A portal grant that sets any of these changes when the phone swaps.

**Applied:** the plan's §1, §2, §5 (U2) and §6 (M1).

## F8 — Provider-neutral wording (Alberto, 2026-09-25)

**Decision (Alberto).** The own-my-agent screens are generic about where the agent is hosted, like email: a person can self-host, or use a service. The Farm is one provider.

- **What the app says.** The app never says "Farm". The steps say "the service that hosts your agent", or, for a self-hosted agent, "whoever runs your agent".
- **Where the Farm specifics live.** Its `did:key`-only Admin DID field and the QR handoff (U1) stay in the plan as the first provider we support and test. They are not app wording.
- **Design consequence.** Nothing in the flow assumes the Farm. The owner code is an Ed25519 `did:key`, which any host that admits a `did:key` admin accepts. For a self-hosted VTA, the person gives the code to whoever runs it, for example through `pnm acl create`.

**Superseded.** §0 and §7 named the Farm and its website in the person's steps.

**Applied:** §0 (the plain version) and §7 (the screens' rules). UI/UX is sweeping the strings.
