So §5 requests 2 and 3 are answered by upstream's own work, request 1 (publish) is still open, and the finding of §3.3 was independently reached and fixed upstream on 2026-09-15 — the same day the subtask measured it.

The mediator side matters for how a frame travels. Mediator 0.26 accepts a TSP message as a **binary** WebSocket frame on an authenticated socket, binds the cleartext sender VID to the session DID (`force_session_did_match`), and stores it base64url-encoded for the receiver, who gets it as a **text** frame on a DIDComm-mode socket — or as binary if the socket was opened with the `tsp`/`tsp-ack` subprotocol. Direct TSP delivery is gated by `local_direct_delivery_allowed`, which a deployment has to turn on. The acknowledgement id is SHA-256 of the delivered text, the same contract as a queued DIDComm message. This is what `VtiMediatorSession` now implements, and it is the same shape `vti-didcomm-js` 0.10 uses.

## Part 2 — Adopt or port, and what landed

### The decision

The subtask's R2 assumed the wallet would build against 0.3.0 and its §3.1 table marked five items "theirs — arrives with the package". Measured against the actual 0.3.0 API, the package cannot serve as the codec on its own for a wallet whose keys never leave Askar:

1. `pack`/`unpack` take raw private keys (`PackKeys.senderSigningKey`, `UnpackKeys.receiverDecryptionKey`).
2. The capability seam it does have (`sealWithKeyAgreement`/`openWithKeyAgreement`, `signWithSigningKey`) covers HPKE-**Auth**. Its changelog says base mode "has no local key to hold and so needs no variant" — which is true of the sender and false of the recipient, whose static X25519 key is the decap. A base-mode `open` behind a `KeyAgreement` is exactly what our Rev 3 read path needs and it is not there (now §5 request 6).
3. The Rev 3 envelope, field, payload and control codecs (`encodeFields`, `finalizeFrame`, `encodePayloadFrame`, `decodePayloadFrame`, `control.ts`) are internal modules; `exports` names `.`, `./hpke` and `./unsafe-testing` only.
4. Five modules construct `new TextDecoder("utf-8", { fatal: true })` at import time, which throws on Hermes — the same defect we patched in 0.1.0, now in five places.
5. It is not on npm.

Against that, what the package *does* give byte-exactly and would be pure duplication to port: the CESR wire table with Rev 3's long count codes, `peekRevision`, the §7.2/§7.3 relationship state machine, the frozen Rev 2 reader, and a raw-key packer/unpacker every one of our frames can be tested against inside the same jest run.

**Decision:** the package is the wire authority and the tests' oracle; the orchestration over the custody ports stays ours (now §2.5). Concretely: vendor 0.3.0 at `bfdb0dc` as a prebuilt tarball under `bifold/packages/trust-tasks/vendor/` with the Hermes fix applied at source and a script that rebuilds it from the pinned clone; rebuild `direct.ts`'s Rev 3 framing on the package's exported `cesr` table over `SigningKey`/`KeyAgreement`/`VidResolver`, the way the Rev 2 port already did; hold it to the package in both directions and to the specification's Appendix A vectors.

Rejected: a yarn git dependency on the monorepo (`workspace=` on a Node-24 workspace that installs six packages to build one `tsc` package, on every install); waiting for npm (no date); porting the wire table too (drift with nothing to catch it).

### What R2–R6 landed as

- **R2** — the vendored 0.3.0. `yarn typecheck` named every invalidated call site as the plan said it would: `encodeEnvelope` (gone), `TSP_HPKEAUTH_CIPHERTEXT` (still exported, read-only), `senderEncryptionKey` (Rev 2 `UnpackKeys` only). The old 0.1.0 `.yarn/patches` entry and root resolution are gone.
- **R3** — `hpke.ts` gains base mode beside auth: `encapBase` (ephemeral only, no port), `decapBase` (one `agree(enc)`), `sealBase`/`openBase`, `deriveKeyPair`. The known answer is stronger than the RFC's A.2 table: the specification's `direct-hpke-base` message re-packs byte for byte from its `ikmE`, which exercises `DeriveKeyPair`, the base key schedule, the `YTSP-` info and the AAD boundary in one assertion. A `KeyAgreement` double that throws proves the send path never reaches it.
- **R4** — `rev3.ts`: envelope fields as AAD, `-E` finalized after sealing, `F` ciphertext `enc ‖ ct`, indexed signature under `-C23 -K22`, the ESSR sender field always written and checked against the envelope, empty padding, `-A` generic stream with exactly one Bytes primitive, Nested and Routed with the byte-length `-J`. The thread digest is SHA-256 over the `-Z` frame for application messages; the self-addressing `TSP_Digest` belongs to the control layouts and lands with R5.
- **R6** — `direct.ts` is the dispatcher: `pack` packs Rev 3, `unpack` peeks and dispatches, `createTspCodec({ packs })` is the build-time choice, `PackedMessage`/`UnpackedMessage` carry `revision`. `rev2.ts` is the previous port, frozen, with its own envelope encoder and hop codec because the package no longer exports Rev 2 writers. The per-peer record is `GenericRecordsTspPeerRevisionStore` in `@bifold/core`, written on every inbound TSP frame and shown on the agent card.
- **R1 (partly)** — the 4095/4096-quadlet boundary is asserted in `tspRev3.test.ts` with frames the packer produces; `VtiMediatorSession` classifies with both prefixes. The ladder rung and the live run against a mediator are still open.
- **R5** — open. Neither end of the peer leg enforces §7.2.2 today (both are Keyring), so the leg does not need it; a control frame that arrives is refused by name rather than misread.

Not in the plan, done because the peer leg is the only place a frame could go: TSP on the VTI mediator socket. `VtiMediatorSession.sendTspFrame` (binary), the text-frame demux before any JSON is parsed, the ack by `sha256(text)` after the consumer has taken the frame (a throwing consumer withholds it); `vtiAgent.connect({ persona })` derives both the DIDComm identity and the TSP identity from the persona's borrowed keys; `vtiAgent.send` packs the Trust Tasks TSP binding envelope when the build says `VTI_PEER_LEG=tsp`, and an inbound TSP frame reaches the same inbox a DIDComm plaintext does, presented as one (`id`/`type`/`thid`/`from`/`body`), so `vtiVetting.ts` did not change. The binding's identity rule (in-band `issuer` must be the TSP sender) is enforced at unwrap.

### What is tested and what is not

Tested, in jest, without an Agent: 15 assertions in `tspRev3.test.ts`, 14 in `vtiTsp.test.ts`, the 5 revised in `tspEnvelope.test.ts`, and the 19 existing trust-tasks suites (186 tests) still green — including `tspCarriage.test.ts`, whose wallet-to-wallet envelope now goes Rev 3 over DIDComm v1 without a change to the carriage.

Not tested: anything with a real mediator, a real `did:webvh` resolution, or Askar. Specifically unproven until a device run: that mediator 0.26 as deployed in the local stack has `local_direct_delivery_allowed` on; that a `did:webvh` persona document dereferences to Ed25519/X25519 keys the way `createVtiVidResolver` expects (it follows referenced verification methods, which the adapter's resolver does not); that React Native's WebSocket delivers a binary send intact; and the whole applicant ↔ vetter ceremony with `VTI_PEER_LEG=tsp` on both phones — the R7 gate.

## Part 3 — My Agent: connect first, then what the agent holds

### What changed

`community_vetting_subtask.md` §7.1 already describes S1 as a screen with one action, *Connect my agent*, and S4 as the home once connected. The screen as built showed every section in both states and left "connect and mint a persona on my VTA" in Developer options, where the two-device runners drive it. The rework:

- **S1** shows the sentence, the manager identity to enrol (full DID, selectable, with the enrolment hint), one button, and one line saying what connecting does. Nothing else.
- **Connect** does the three things in order and names each: sign in to the VTA (`vtaAgent.connect`), get the persona for the configured community (`ensurePersonaFor` — mint and borrow when needed, with the consent wait shown when an approver is in the loop), open the community session as that persona (`vtiAgent.connect({ persona })`). A build without a VTA keeps the old phone-minted path.
- **S4** is gated on the VTA session and led by the vetting entry: a hero card that names the seat — *You are the vetter* when a vetter grant for this persona is held, *You are being vetted* otherwise — with the seat's own sentence and its own call to action. Identity, approvals, invitations and communities follow. The agent card shows host, manager identity, persona and which carriage the peer leg is on.
- **Vetting** opens with the same seat banner on both screens, and the desk and the application each carry numbered step labels (hand out a ticket → requests; your face → ask a vetter → apply).
- The Developer probe stays as it was, log lines included. `vtaAgent.connect` now marks the state connected when the probe already opened the session, or a screen gated on that state would never see it.

Every testID the runners use is kept; `MyAgentVettingSeat`, `MyAgentVettingOpen`, `MyAgentEnrolCard`, `MyAgentManagerDid`, `MyAgentPeerLeg`, `ConnectCommunityButton`, `VettingSeatBanner`, `VettingRoleBadge` are new. `run-vti-vetting.js` now waits for the vetting entry before scrolling to it, since it appears only once the phone's VTA session has reconnected.

### The UX position

Moving connect-and-mint into My Agent with a connected gate is right, for two reasons the plan already gives: an agent is the precondition for everything else on the tab (§7's "a community is reached through an agent"), and state a counterparty owns must never be shown stale (§2.6) — a screen that lists approvals and invitations while not connected is showing exactly that. The gate makes the empty states honest.

Two things I would change with more time, recorded as positions rather than done:

1. **The gate should be per section, not per screen.** Memberships and the persona are the wallet's own records and render with no agent at all (§2.6's architecture-neutral half); only approvals and anything that asks the community should wait for the session. As built, everything waits, which is simpler to test and slightly too strict — a member with a card in the wallet should see it offline.
2. **The seat should be decided by the community's record, not the phone's.** The banner reads the vetter grant this phone holds, which is right under §2.4 B until the grant is revoked — a revoked vetter still sees the desk until the next refresh. §3.4's "revoked when checked on…" wording belongs next to the badge, with the date of the last check.

And one thing I would not change: the seat banner's colour and copy are the same on both phones on purpose. Two people at a table each looking at a blue card that says who they are is the whole point; making the vetter's screen visually different from the applicant's would invite the question "which one am I?" that the badge already answers.
