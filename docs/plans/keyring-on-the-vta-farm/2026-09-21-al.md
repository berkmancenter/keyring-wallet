The reasoning and the order the blockers were found in are in
[`2026-09-20-al.md`](./2026-09-20-al.md) §12–§16. What that companion does not

  minted in the wallet's own KMS, so one Ed25519 key backs both TSP ports
  (converted to X25519 at use, as `did:peer:2` derives its agreement key). No new

  greeting to the VTA, then six tasks over Rev 3, each depending on the last.

  refusal skipped the acknowledgement and the accept stayed queued at the

  reporting a control frame as "no Trust Task here" rather than by acknowledging
  everything, since a failed persist must still withhold its ack.

## 3. Era H, on devices (evening)

The lab moved to upstream main (era H in the findings document) and every rung
was re-run on two devices: enrol (a freshly installed iPhone), invite (a new
Android vetter), the two-phone approval, and the vetting ceremony. All green.
What the run turned up, in the order it did:

- **#1579 works with a phone approver, once the phone is routable.** The VTA
  resolves an approver's `DIDCommMessaging` service and pushes to the mediator
  it names — by DID. Keyring's client DID carried a DIDComm v1
  `did-communication` service holding the socket URL, which reads as "no
  route"; approvals arrived only because My Agent fetched them. Minted with the
  v2 service, the push arrived and the iPhone approved in about three seconds.
  A phone enrolled before the fix keeps the old DID and is reached by relay.
- **The approver rung needs enforcement on** (VTI-22, known since era A, and
  re-met because a fresh `setup` writes it off). `up.sh` now sets it for alice.
- **A consent refusal can arrive without its challenge** (VTI-37): at three
  approvers the signed requests pass the VTA's 4 KB bound on `details`, which is
  dropped whole. The client now reads the bare code as held; the relay it would
  have carried is lost upstream.
- **Refusals, staged:** a vetter grant revoked before the applicant applies
  leaves the request *deferred* (`requestMore`, "vetting:statements:1"), and
  withdrawing it works live — the first live run of the applicant's way out
  (VTI-03's client half). A tampered ticket is refused by the vetter
  (`invalidTicket`). The runner stages both (`E2E_REFUSAL`). *Supplement* is
  built and unit-tested and has not run live: it needs a second vetting round
  inside one run, and the runner is about to be rewritten by the UI/UX plan's
  UT phase.
- **TSP Rev 3's remaining lab items:** long-form frames through the mediator
  (`ref-04r`), and XRFI → XRFA → XRFD against the VTA's own state machine
  (`ref-04s`), which found VTI-38 — the §7.3 answer to a mutual cancel is
  refused because the transport forgets the relationship first. Sending XRFD
  from the app belongs with *Leave community* (UI/UX plan U1).
- **The ngrok refusal that stopped the afternoon** (`ERR_NGROK_4026` on one
  hostname) was an error on ngrok's side — a limit set during a subscription
  change — not credit. A VTA that boots while its own DID is refused skips
  DIDComm for the whole boot; `stack-health.sh --heal` now catches that.
