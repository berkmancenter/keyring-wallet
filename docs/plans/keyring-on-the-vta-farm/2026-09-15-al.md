Findings behind the new [`community_vetting_subtask.md`](./community_vetting_subtask.md), and the positions of [`keyring-on-the-vta-farm.md`](../keyring-on-the-vta-farm.md) they supersede. Measured against public upstream sources on the day; commands are given where a reader can reproduce them.

## F1 — A Farm session cannot run peer identity vetting yet

**Evidence.** Anonymous GHCR tag lists (`https://ghcr.io/v2/ic3software/<image>/tags/list` with a pull token from `https://ghcr.io/token?scope=repository:ic3software/<image>:pull`): the newest `vta` and `vtc` tags are `0.24.1-0af2cce7`. In a VTI clone, `git merge-base --is-ancestor 5a6d4923 0af2cce7` (vetting wire types, #1425) fails, as do `14ef89a6` (#1430) and `7a5d8aa0` (#1439). All three are ancestors of `vta-service-v0.27.0` (2026-09-12).

**Position adopted.** The development environment for vetting is a local VTI stack built from VTI `origin/main`; the Farm stays the production target and is used for enrolment and plain membership until vetting-capable images are selectable.

**Supersedes.** The parent's standing rationale that `ref-05-local-vta` is the offline twin (§8) — for this path the twin is the four-service local stack, because a single VTA cannot host a community.

## F3 — For a vetting community, L3 is Vetting Statements, not two VRCs

**Evidence.** VTI @ 53a7cde4 `docs/03-vtc/vetting.md` ("What the community checks at submit"): admission counts `EndorsementCredential` statements of the registered identity-vetting type against `minStatements`, `acceptedMethods`, `requiredClaims`, `maxStatementAge` and independence rules. The parent's two-VRC policy was already quoted as not active.

**Position adopted.** In a community that vets, what qualifies an applicant is statements from named vetters. Keyring's L3 contribution is restated rather than dropped: the Vetting Card is a `RelationshipCard` profile, and an `inPerson` method with liveness is what Keyring's witnessed, locality-proven, attested exchange evidences — the basis for Keyring as a **vetter**, which is later work.

**Supersedes.** Parent §2's L3 row as the qualifying mechanism for vetting communities. VRCs remain the member-to-member edge.

## F5 — TSP Rev 3 is a hard, wire-level cutover

**Evidence.** `docs.fpp.storm.ws/tsp-rev3-migration.html`: HPKE-Auth removed, HPKE-Base mandatory; CESR table and count codes, ciphertext code and layout, AEAD `info`/`aad`, thread digest and routed exit VIDs all change; *"a message is either wholly Rev 2 or wholly Rev 3"*; upstream `main` stays on Rev 2 until the reference SDK releases Rev 3; spec review open, test vectors deferred.

**Position adopted.** The vetting path does not depend on TSP; fixtures record the TSP revision that produced them; migrating Keyring's Rev 2 TSP work (`ref-00…04` fixtures, the HPKE-Auth crypto of `ref-03-noble-crypto`, the TSP carriage) belongs to `openvtc-integration-plan.md` on upstream's release. Rev 3 moves sender authentication to a signature, which removes the static X25519 key a device could not hold in hardware from the send path.

## F7 — Upstream's client-side vetting is still in progress

## F9 — The vetting dry-run runbook is the acceptance script

**Evidence.** *Vetting Dry Run* (OpenVTC · Peer Identity Vetting · V0, revision of 2026-09-14) pins the versions (vtc-service 0.11.58, vta-service 0.27.0, vta-sdk 0.38 with `vetting`), the topology (two VTAs, one shared mediator, a `name.legal` face), twelve steps with an observable outcome each, and nine negative cases. Every route, command and field it uses is also in public upstream sources: VTI `docs/03-vtc/vetting.md` (`/v1/endorsement-types`, `/v1/schemas/accepts`, `cnm vetting vetters grant|resend|revoke`, `cnm vetting revocations`, `requirementsDigest`, `needsReview`, `vetting-review`), `vtc-service/tests/vetting_journey.rs` and `join_requests.rs`.

**Position adopted.** The subtask carries the runbook's steps, assertion table and negative cases as §3.8, and P2's and P6's acceptance criteria are its *Expect* rows rather than a paraphrase of the operator docs. Where the runbook and the running services disagree, the services are the authority and the disagreement is a request (§9).

## F10 — The local stack needs six stable public hostnames per developer

**Evidence.** Six public services (three VTAs, VTC, mediator, DID hosting); §3.7's non-public-host refusal rules out `localhost` and emulator loopback; a `did:webvh` DID embeds its host, so a hostname change is a new DID.

**Position adopted.** One reserved tunnel dev domain per service, configured per developer and never shared between machines; quick tunnels only for throwaway runs. Subtask §4.
