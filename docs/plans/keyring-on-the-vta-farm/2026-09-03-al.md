# 2026-09-03 — AL: the Farm as target environment, the packaging chain that blocks it, and what that decides

Companion to [`keyring-on-the-vta-farm.md`](../keyring-on-the-vta-farm.md), written
with the plan it explains. Two bodies of measurement: upstream's own developer
guides read from the pinned `vti-setup` clone, and the published npm artifacts of
the ecosystem's TypeScript libraries read on 2026-09-03. Everything in the second
half is reproducible from the registry alone — no clone, no account — because a
portability claim nobody else can check is not evidence.

## What this document settles

1. The VTA Farm is the target environment for Keyring's VTA work, and self-hosting
   becomes the offline CI twin rather than the default path.
2. Enrolment on the Farm path keeps the private key on the device, which decides a
   question the PNM/CNM subtask left open.
3. A React Native wallet needs no WebAuthn to reach a Farm-hosted VTA, which
   closes an open question in the SDK companion.
4. `did:webvh` resolution is on the critical path from level zero, and the only
   TypeScript route to it is packaged in a way Metro cannot resolve — with four
   measured findings that become the contribution track.

---

## 1. Method, and why the guides are the primary source

The plan's level structure is not ours. It is upstream's own developer path,
read verbatim from the pinned `vti-setup` clone at **22f712f** (2026-08-17):
`developer/README.md` states the three steps, and each tutorial states what it
was verified against — **VTA 0.17.0, Mediator 0.18.19, DID Hosting Daemon 0.8.3**.

Taking the structure from the guides rather than inventing one is deliberate.
Every level then has an external definition of done — the tutorial's own
verification step — instead of one we wrote for ourselves, and "Keyring at every
level" becomes checkable rather than rhetorical.

## 2. What the Farm changes

**Path A removes exactly the infrastructure a phone cannot supply.** Quoted in
the plan §3.1. Path B's three prerequisites — a host, a public HTTPS origin for
`did.jsonl`, a mediator DID obtained from its operator — are each individually
disqualifying for a mobile developer, which is why the recommendation is not
merely upstream's preference but our constraint too.

**Enrolment collapses rather than disappears.** The PNM/CNM subtask established
that no self-service enrolment exists anywhere in the stack, `/auth/challenge`
being ACL-gated before a nonce is minted. That is still true on the Farm. What
changes is who the operator is and how far away they are: the client generates a
temp `did:key`, the human pastes it into the Farm console, and the grant is
issued. The out-of-band step is a paste into a tab already open.

**Position adopted — hardware custody, and the reasoning that gets there.** The
subtask's §9 Q2 asked whether Keyring keeps a Secure-Enclave-generated key or
adopts a VTA-minted one, and named the tension: `pnm-core`'s live onboarding path
(`provision-integration`) hands the wallet a private key generated off-device,
which is irreconcilable with hardware attestation being our differentiator. The
Farm path does not ask for that. It asks for a client-generated `did:key`, and
nothing about the Admin DID input constrains where the private half lives. So on
this path the question does not need trading off — take the enclave key.

I want to be precise about the scope of that: this settles Q2 **for the Farm
path**, not universally. A deployment that provisions through `provision-integration`
still faces the original tension, and if we ever support one we face it again.

**Position adopted — no WebAuthn on the wallet, and the correction it embodies.**
The SDK companion of 2026-09-01 (§4) recorded this as an open question gating the
Agent Leash: *"Whether a mobile wallet can authenticate to a Farm-hosted VTA is
unanswered."* It is answered, and the answer is that the question conflated two
surfaces. The Farm's Path A prerequisites list *"a computer with passkey support"*,
which is the **console's** requirement. The VTA session is DID-based: upstream's
own client obtains its REST bearer by `/auth/challenge` → DIDComm authcrypt →
`/auth/`, and its module docstring states that TSP and DIDComm carry no bearer at
all because they are sender-authenticated by their envelope. Passkeys live in a
separate task family (`auth/passkey/login/{start,finish}/0.2`).

That supersedes the SDK companion's §4 open question and, with it, the framing
that the Agent Leash is blocked on an authentication unknown. It is not.

**What the Farm makes mandatory: `did:webvh`.** On Path A the client is given a
DID and nothing else. `ref-06x` already measured Credo 0.6.3 answering
`unsupportedDidMethod` and proved a ~20-line adapter sufficient — but that
measurement was taken where resolution was one capability among several. Under
the Farm it is the first thing that must work, at level zero, before anything is
authenticated. The finding did not change; its position in the ordering did.

## 3. The packaging chain, measured from the registry

Reproduction, in a scratch directory, on 2026-09-03:

```sh
npm view @openvtc/pnm-core version dependencies --json
npm view @openvtc/vti-didcomm-js version dependencies --json
npm pack didwebvh-ts@2.8.0 && tar xzf didwebvh-ts-2.8.0.tgz
node -e 'console.log(JSON.stringify(require("./package/package.json").exports,null,1))'
grep -n 'require("node:fs")\|require("fs")' package/dist/cjs/index.cjs
npm pack @openvtc/pnm-core@0.7.0 && tar xzf openvtc-pnm-core-0.7.0.tgz
node -e 'const e=require("./package/package.json").exports;const k=Object.keys(e);
         console.log(k.length, k.some(x=>x.includes("*")), k.join(" "))'
grep -rln 'from "@openvtc/vti-didcomm-js"' package/dist | wc -l
grep -rho '@openvtc/vti-didcomm-js/[a-z0-9-]*' package/dist | sort | uniq -c
```

Results, and what each one means:

| Measured | Value |
|---|---|
| Dependency chain | `pnm-core` 0.7.0 → `vti-didcomm-js` 0.7.0 → `didwebvh-ts` ^2.7.4 → **2.8.0** |
| `didwebvh-ts` export conditions | `react-native` → `./dist/cjs/index.cjs`; `browser`, `import`, `require`, `types` |
| Node built-ins referenced | `node:fs` in the browser, ESM **and** CJS builds; `node:module` additionally in ESM. In CJS: `require("node:fs")` line 3075, `require("fs")` line 3080 |
| How fs is reached | A lazy guarded loader trying several specifiers in sequence, throwing only if called: *"Filesystem access is not available in this environment (unable to load fs)"* |
| `pnm-core` exports | **23** subpaths, all directory-level, **no wildcard**; no deep file import reachable |
| Reach of the chain inside `pnm-core` | `dist/vta/index.js:6` re-exports `./didcomm.js`; 18 of 116 files under `dist/vta/` import `../didcomm`; `dist/trust-tasks/verify.js` imports the `vti-didcomm-js` barrel |
| Barrel vs subpath usage | **12** files import the barrel; **0** import any subpath. Imports taken: `base64url` ×6, `multibase` ×5, `resolve` ×3, `didKey` ×2, the rest ×1 |
| `vti-didcomm-js` packaging | **24** fine-grained subpaths; `./base64url`, `./multibase`, `./did-key` are clean of `didwebvh-ts` |
| Its resolver | `src/resolver.js` documents itself as *"Pluggable: callers can pass their own map of `{ method: resolver }`"* via `createResolver(overrides)` — and statically imports `./did-webvh.js` at line 18 |

**The finding that reframes all of it: this is a bundler problem, not a runtime
problem.** Nothing on the resolution path needs a filesystem, and the loader is
written to survive its absence. Metro resolves specifiers statically, so the
build fails on code that would never have run. I initially read the chain as a
portability defect in the library's design; it is a packaging defect over a
design that is already right — a pluggable resolver, fine-grained subpaths, and a
declared `react-native` condition, each undercut by one static import or one
missing export. That supersedes the harsher reading, and it matters for how the
contributions are framed: these are not requests to redesign anything.

**The corollary that kills the obvious workaround.** "Use REST on the phone and
skip DIDComm" does not avoid the chain: there is no published route to the
transport-agnostic core, and `trust-tasks/verify.js` reaches the barrel anyway.
Worth recording because it is the first thing anyone will propose.

**The cheapest fix is measured, not guessed.** Of the 12 barrel imports, the
dominant three names — `base64url`, `multibase`, `didKey` — all have clean
dedicated subpaths that exist today. Only the three resolution sites genuinely
need `did:webvh`, and even those need not be static, because the resolver already
advertises an override map that its own static import defeats. Two mechanical
changes therefore remove most of the coupling with no API change and no design
argument, which is why they lead the contribution track.

## 4. The pin state, and why F0 starts with an advance

All four npm tripwires in `PINS.json` have tripped: `@openvtc/trust-tasks`
0.9.0 → 0.16.8, `pnm-core` 0.4.0 → 0.7.0, `vti-didcomm-js` 0.6.2 → 0.7.0
(`vti-tsp-js` holds at 0.2.0). The `dtgwg-trust-tasks-tf` clone is **68 commits
behind `origin/main`**.

One of those movements is directly load-bearing here. At the pin, the HTTPS
binding is **0.1**, and its §6 "Discovery wiring" defines only Type-URI discovery
over the same `POST /trust-tasks` endpoint — **no DID-document service type**.
The `TrustTaskHTTPS` type, and the rule that the advertised `serviceEndpoint` is
the Trust-Task base with `<base> + "/trust-tasks"` as the request URL, are
post-pin: they appear in the current upstream TypeScript client, attributed there
to binding 0.2 §6, and I have not verified them against the registry itself.

So the plan's §3.5 is stated as a gate rather than a fact, and F0 advances the
pins before measuring anything. Writing the Farm measurements against a
two-release-old view of endpoint discovery would produce numbers we would have to
take again.

## 6. What I did not settle

- **Whether a Farm VTA advertises an HTTPS Trust-Task base at all.** Everything
  about transport selection waits on it, and it needs an account to answer.
- **Whether the two-VRC join policy is live.** Upstream's guide says it is the
  target and explicitly not current. The plan's L3 argument depends on it and its
  L2 implementation does not, which is the only reason this is not blocking.
- **Which authority the join task uses.** The guide gives
  `trusttasks.org/openvtc/vtc/join-requests/submit/1.0`; the PNM catalogue treats
  that authority as retired. One sentence from upstream resolves it; a day of
  implementation discovers it.
- **Port `pnm-core` or write our own client.** Deliberately left to
  `pnm_cnm_subtask.md` §3, which owns the decision, and to the measurement F0 and
  F1 produce. This plan's silence is not a preference.
