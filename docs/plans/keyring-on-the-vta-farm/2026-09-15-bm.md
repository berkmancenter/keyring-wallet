# Part 2 — TSP Rev 3

Opened in response to the question of whether Rev 3 is handled automatically on the wire or needs a setting. It is neither — see T1. [`community_vetting_subtask.md`](./community_vetting_subtask.md) §3.6 defers this work out of the vetting path, and [`openvtc-integration-plan.md`](../openvtc-integration-plan.md) keeps ownership of TSP as a transport; the subtask this part opens owns only the cutover.

## T1 — Upstream already answered the revision question, and the answer is asymmetric

**Evidence.** `OpenVTC/vta-browser-plugin` carries a branch `feat/tsp-rev2-rev3-dual-handler` @ **78cfbf96** (2026-09-15), two commits ahead of `main`: *"feat(tsp-js): pack TSP Rev 3, read Rev 3 and Rev 2"* and *"feat(tsp): form relationships with XRFI/XRFA, which Rev 3 requires"*. It adds `packages/tsp-js/src/revision.ts`, a frozen `src/rev2/reader.ts`, a full `src/rev3/`, and `tests/revision.dispatch.mjs`.

`packages/tsp-js/CHANGELOG.md` states it: *"This package now packs Rev 3, and a Rev 2 peer cannot read what it sends. There is no negotiation and no fallback. … Reading is dual."* And the reason the asymmetry is not a compromise: *"an inbound message says what it is, an outbound one has nothing to read, and a dual **packer** could only be a guess dressed as a protocol."*

Detection is keyless — `revision.ts`: *"the revision is readable without any keys, at a fixed offset, before anything else is parsed"*, at most nine bytes, dispatching on MAJOR with MINOR never refusing a message.

**Position adopted.** Adopt upstream's shape unchanged (subtask §2.1–§2.2). Keyring stores the observed revision **per VID as a diagnostic** — which the changelog explicitly leaves to us (*"persisting it per peer belongs above this package"*) — and never feeds it back into what we pack.

**Supersedes** a position I proposed in review before this branch was found: a per-VID revision setting on send, opportunistically upgraded on first Rev 3 receive. It is wrong for the reason the changelog gives. Recording it because the instinct — "a wallet's peers upgrade at different times, so the wallet should adapt per peer" — is the obvious one, and the next person will have it too. The answer is that adapting per peer on *send* requires knowing something no wire bit carries; reading both on *receive* gets the benefit without the guess.

## T2 — Rev 3 breaks the mediator's TSP demux above 12,285 bytes

**Evidence.** Rev 2's `-E` count covered only the envelope header, so a TSP frame always began `0xF8` / base64url `"-E"`. Rev 3 widens that count to cover the ciphertext (`CHANGELOG.md`: *"The `-E` count covers all signable content"*), so a message past the 12-bit count limit is framed long — `0xFB`, text `"--"`. `packages/tsp-js/src/cesr/wire.ts` @ `78cfbf96` names the consequence: *"An ingress classifier that knows only `0xF8` starts dropping large messages the moment Rev 3 is switched on."*

`tsp-js` fixed its own `isTsp` to accept both bytes. The classifier Keyring rides is in a **different package** and was not fixed — `external/vti-didcomm-js/src/mediator-transport.js:536`:

```js
if (text.startsWith("-E")) {   // → onTspFrame
  ...
}
// otherwise falls through to unpackInbound() — the DIDComm unpacker
```

Reproducing the count-code encoding from `wire.ts` (`DASH = 62`, `LONG_COUNT_REV2 = D0`, `LONG_COUNT_REV3 = DASH`, short form when `count < 4096`) and running that predicate over it:

```
short-form -E count holds 4095 quadlets = 12285 bytes

demuxed as TSP   text="-EBk…" byte0=0xf8    300 bytes — Rev 2, any size
demuxed as TSP   text="-EPo…" byte0=0xf8   3000 bytes — Rev 3, small message
demuxed as TSP   text="-E__…" byte0=0xf8  12285 bytes — Rev 3, at the limit
MISROUTED        text="--EA…" byte0=0xfb  15000 bytes — Rev 3, long form
MISROUTED        text="-0EA…" byte0=0xfb  15000 bytes — Rev 2 long form (never emitted)
```

The threshold is inside our range: `ref-06p5-attestation-binding/fixtures/attestation-production.json` is 7,346 bytes and `ref-07-dtg-edge-semantics/fixtures/edge-witnessed-captured.json` is 6,623 — a witnessed exchange carrying both parties' attestation chains plus the task envelope crosses 12,285. The failure is silent at the protocol layer and surfaces as a DIDComm decode error, so it would be chased as a message-format bug rather than a size threshold.

**Position adopted.** Subtask §3.3, and R1 proves it against a running mediator before any crypto work. Filed as request 2, with request 3 asking whether the mediator *server* classifies the same way — this measurement covers the JS client transport only.

**Supersedes** nothing. It is not in *TSP Rev 3 Migration*, which is written against the Rust `tsp-sdk` and does not cover intermediaries — it is explicitly silent on how they handle mixed-revision flows.

## T3 — Relationship gating stops being optional

**Evidence.** `CHANGELOG.md`: *"Rev 3 gates application messages on a relationship, so without these a peer enforcing §7.2.2 drops everything a client sends — silently, since a dropped message answers nothing."* 0.3.0 adds `packInvite`/`packAccept`/`packCancel` and a pure §7.2/§7.3 state machine (`relationship.ts`).

**Supersedes** [`pnm_cnm_subtask.md`](../openvtc-integration-plan/pnm_cnm_subtask.md) §6 item 5, which records the FSM as *"declared-but-dead (`XRFI`/`XRFA`/`XRFD` markers exist in `packages/tsp-js/src/cesr/wire.ts:105-107` with no reader or writer)"*. True at that pin; under Rev 3 they are load-bearing, and a client that ignores them is mute without being told. Subtask R5.

## T4 — Rev 3 removes the static X25519 DH from the send path, confirmed in our own code

**Evidence.** `CHANGELOG.md`: *"HPKE-Auth → HPKE-Base. The sender's key leaves the KEM."* In our stack `bifold/packages/trust-tasks/src/tsp/hpke.ts:110` (`authEncap`) is the **only** place the send path calls `senderKeyAgreement.agree()`; the module's own comment already identifies it as *"the one call an Askar-backed implementation satisfies via `Key.fromKeyExchange`"*. Under Base the sender performs no static DH, so a sending device needs only an Ed25519 signing key — which the Secure Enclave and StrongBox can hold and X25519 cannot.

**Position adopted.** Recorded as a consequence (subtask §2.4), not a reason to accelerate.

**Supersedes** the sequencing in [`community_vetting_subtask.md`](./community_vetting_subtask.md) §2.4, which picks a hardware-custody target by measurement in its P4 among three options shaped by the Rev 2 send path. The claim in its §3.6 that Rev 3 eases hardware custody is correct; what it does not draw is that a P4 measurement made under Rev 2 may be answering a question Rev 3 retires. The choice belongs here.

## T5 — No Rev 3 release exists, and the two release trains are not the same

**Evidence.** `npm view @openvtc/vti-tsp-js versions` → `0.1.0`, `0.2.0`; `time.modified` 2026-08-17. Both Rev 2. 0.3.0 exists only on the branch above. Our stack pins **0.1.0 plus** `.yarn/patches/@openvtc-vti-tsp-js-npm-0.1.0-e571a35ca1.patch`, which works around Hermes throwing on `TextDecoder`'s `fatal` option.

*TSP Rev 3 Migration* tracks the Rust `tsp-sdk` (`rev3` branch, PRs #332/#333/#335/#336; *"Latest release `v0.9.0-alpha2` is still Rev 2"*). Our framing comes from the JS package, which that document does not cover.

**Position adopted.** Subtask §3.6 and requests 1 and 5.

## T6 — The version marker's MINOR encoding is contested between three implementations

**Evidence.** `wire.ts`: `tsp-js` packs `YTSP-AAC` (MAJOR.MINOR, MINOR = 2); *"The published §9.1 text reads the three characters as MAJOR, MINOR, PATCH and gives `YTSP-ABA`; affinidi-tsp deliberately does not follow that reading, and neither do we."* `revision.ts` resolves it by reading everything at MAJOR 0 that is not Rev 2's MINOR as Rev 3, and treating `KNOWN_MINORS` as diagnostics only.

**Position adopted.** Follow the same rule; flagged as conditional design at subtask §3.5 rather than in an open-questions list, because the dispatcher and §3.2 change together if it resolves. Request 4.

## T7 — The migration document's loudest breaking change is cheap for us

**Evidence.** *TSP Rev 3 Migration* warns that the thread digest *"is a public field on `PackedMessage` and `UnpackedMessage` and is what the relationship FSM correlates on"*, making it a source-visible break. In our tree `threadDigest` has no consumers outside `direct.ts` itself (grep across `bifold/packages/*/src`, `app/src`, `e2e/`): it is produced at `direct.ts:225` and `:287` and returned, and nothing correlates on it.

**Position adopted.** R4 treats the digest as implementation cost in one file. Worth recording because the warning is prominent and would otherwise be read as a refactor we owe.

## T8 — One conflict between the two upstream accounts, unresolved

*TSP Rev 3 Migration*, as I read it, describes the version field as `"YTSP <ver>"` becoming `"YTSP-AAB"` under Rev 3. `revision.ts` and `wire.ts` say `YTSP-AAB` is **Rev 2** (`REV2_MINOR = 1`, *"Read, never written"*) and Rev 3 is `AAC`. Both cannot be right.

I read the migration document through a page summariser rather than byte by byte, so the discrepancy may be mine. **Not acted on**: §3.2 and §3.5 follow the implementation, which is the thing our code links against. Worth confirming with the author before it reaches a request.

## Appendix — the T2 check, reproducible

Constants from `packages/tsp-js/src/cesr/wire.ts` @ `78cfbf96`; the predicate is `mediator-transport.js:536`'s, unchanged. Node, no dependencies.

```js
const B64U = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_'
const DASH = 62                          // '-'
const LONG_COUNT_REV2 = B64U.indexOf('0') // D0, a superseded CESR draft
const LONG_COUNT_REV3 = DASH              // the double-dash form
const E = B64U.indexOf('E')               // the `-E` group identifier
const bits = (n, w) => n & ((1 << w) - 1)
const toBytes = (w, n) => Uint8Array.from(
  Array.from({ length: n }, (_, i) => (w >>> (8 * (n - 1 - i))) & 0xff))

// wire.ts:240-247
function encodeCount(id, count, longForm) {
  if (count < 4096) return toBytes(((DASH << 18) | (bits(id, 6) << 12) | bits(count, 12)) >>> 0, 3)
  const hi = ((DASH << 18) | (longForm << 12) | (bits(id, 6) << 6) | bits(count >>> 24, 6)) >>> 0
  return new Uint8Array([...toBytes(hi, 3), ...toBytes(bits(count, 24), 3)])
}

// mediator-transport.js:536
const demuxedAsTsp = (frame) => Buffer.from(frame).toString('base64url').startsWith('-E')

for (const [label, quadlets, longForm] of [
  ['Rev 2, any size',            100, LONG_COUNT_REV2],
  ['Rev 3, small',              1000, LONG_COUNT_REV3],
  ['Rev 3, at the limit',       4095, LONG_COUNT_REV3],
  ['Rev 3, long form',          5000, LONG_COUNT_REV3],
  ['Rev 2 long form (unused)',  5000, LONG_COUNT_REV2],
]) {
  const frame = encodeCount(E, quadlets, longForm)
  console.log(`${demuxedAsTsp(frame) ? 'demuxed as TSP' : 'MISROUTED     '}` +
    ` byte0=0x${frame[0].toString(16)} ${quadlets * 3} bytes — ${label}`)
}
```

The short-form `-E` count holds 4,095 quadlets, so the boundary is **12,285 bytes**. This proves the classifier's behaviour over synthesised framing bytes only; the subtask's R1 turns it into `tsp-reference/ref-2x-rev3-demux/` with the ladder's usual `start`/`check` scripts — a snippet in a dated document is the wrong home for something that must be re-run after every upstream bump — and adds an opt-in live mode against a real mediator. Request 3 asks whether the mediator server classifies the same way.
