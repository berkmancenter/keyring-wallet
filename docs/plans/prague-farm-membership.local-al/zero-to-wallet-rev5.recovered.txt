    The farm is the finish line, not the on-ramp

    The VTA Farm is a managed Dogwood-R1 agent with a Community Mediator already wired — "no server, no public domain, no DID hosting, no mediator wiring on your side," treated as production and kept upgraded. It's tempting to start there. Don't.

    What this settles about the extension

    The extension never needs to meet the farm, which resolves a finding cleanly rather than leaving it as a blocker. For the record, since it cost a probe and is worth knowing: a request to vtafarm.firstperson.dev carrying Origin: chrome-extension://… returns 200 with no Access-Control-Allow-Origin header at all.     That would have been a genuinely nasty afternoon — inside the extension it surfaces as a bare TypeError: Failed to fetch, indistinguishable from a dead host, with the real reason visible only in a devtools console.     The naming layer, and where your DNS analogy breaks

    You called it "what IP is to DNS." The layer is exactly right. The direction of trust is inverted, and that inversion is the whole design.

    An agent name is example.com/@alice. Three details are load-bearing and all three are easy to get wrong:

      The marker is the two-character sequence /@, never a bare @ — so alice@example.com is deliberately not an agent name.

      Trailing path segments are part of the identity: …/@drummond/h2hsummit is a different name from …/@drummond.

      Case is preserved in the local part. @Alice and @alice are different names, because folding could silently merge two distinct identities — a strictly worse failure than one that occasionally fails to match.

    Now the inversion. In DNS the zone owner is authoritative: whatever the name says, is. Here, name → DID proves nothing. It's an HTTP redirect served by the name's own web server, and anyone who controls a domain can point a name at somebody else's DID. Authority runs the other way:

      DID → name is authoritative only via alsoKnownAs. Only the DID's controller can make a name true.

    So the closer analogy is rel="me" / IndieAuth, or ACME's DNS-01 challenge: the pointer only counts because the target claims it back. That's why resolution has three stages and why stage 3 is mandatory — and why the hosting server itself refuses a binding whose document doesn't already carry the claim.

    The wallet enforces this structurally rather than by convention. agent-name.ts exports extractAgentNames(doc) and deliberately offers no helper that guesses a name from a DID's host or path — an earlier version derived a handle from the DID's trailing segment, and that was a spoofing bug, not a shortcut. did-display.ts has no name display role for the same reason. And useAgentNames treats "claims no name", "didn't resolve" and "still loading" as indistinguishable, because none of the three licenses showing a name.

    What you can build on it

    Core already ships six Trust Tasks under vta/webvh/agent-name/* — set, remove, list, check, enable, disable. (check is a point-in-time availability answer, explicitly not a reservation.) That's more surface than any UI currently uses, and four things fall straight out of it:

      Names in every consent prompt. The prompt's central question is "do I recognise who is asking," and today the answer is fifty characters of monospace in which the host — the only part a human can check — carries the same visual weight as the SCID. A verified name is the answer to that question. This is the highest-value use of the naming layer in the entire wallet.

      Claim your name during onboarding. check then set. It converts the most alienating moment in the flow — "here is your did:key:z6Mk…" — into the most rewarding one: "you're keyring.app/@alberto." Your own plan already frames this as the agent-as-concierge beat.

      Find-by-handle for the peer-to-peer exchange, so two people trade names rather than DIDs.

      Rename without breaking anything. The DID is what gets stored; names are re-claimable. A user changing their handle doesn't sever a single relationship — which is a real product property, and worth saying out loud in the UI.

    The wall, and three ladders — two of which are already built

    The ACL grant is genuinely two-party: the ephemeral did:key is minted per installation, so it cannot be granted in advance. But two-party does not imply type a command, and that conflation is the accidental half.

    Here's the finding that fell out of reading the farm's own setup guides, and it's much stronger than a recommendation: the stack has already solved this twice, in two other places, and wallet onboarding has inherited neither.

        Ladder 1 · nobody has built this
        QR in both directions

        The wallet renders its ephemeral DID as a QR; an operator's already-onboarded wallet scans it and grants. Needs nothing new upstream — acl/grant is already a Trust Task and the operator's device already holds admin. Not one QR code exists anywhere in this stack today, which makes this the cheapest visible win available.

        Ladder 2 · shipped, on the farm
        Paste a DID into a web UI

        The farm's "Admin DID → Provision agent" form is this. The same grant that reads as acl create --role admin on your own agent is a text field and a button on the farm — so the security model plainly permits a GUI here, because it is already permitting one. What remains is a human ferrying a did:key:z6Mk… between two windows. You'll do it both ways, in Phases 2 and 7.

        Ladder 3 · shipped, one layer up
        Request, then human approval

        03-joining-a-community.md: "submit a join request under your persona, and get approved by a community admin." That is exactly self-service-under-policy — at the community layer. The same shape aimed at agent enrolment turns "run this command" into "tap Approve." Nothing needs inventing; it needs pointing one level down.

      Why this reframes the contribution
      "Make onboarding friendlier" is a taste argument, and taste arguments lose to shipping deadlines. "The grant already has a GUI on the farm and an approval ceremony at the community layer — wallet enrolment is the one place that inherited neither" is a consistency argument with two working precedents inside the same stack. That version is much harder to wave away, and it's the one worth taking to Prague.

    The thing worth taking away

    The techiness is not evenly distributed, and it isn't where it looks. Nearly every genuinely technical step is operator work — provisioning an agent, granting ACLs, configuring a mediator, pinning an extension key. Nearly every user step is already simple, or could be. What the stack lacks isn't simplicity; it's a seam.

      One surface currently does both jobs, which is why a person meets a --role admin --expires 1h flag. Drawing that line may be the reference app's most valuable contribution.

    The phone shows only what a person owns and decides. Everything else belongs to a console that person never opens. Hold that rule while you build Phases 5–6 and the answer to "where should this be normie-friendly" stops being a judgement call each time.

        RN transport

        REST first, TSP second, DIDComm never.

        The farm ships a managed Community Mediator — "no mediator wiring on your side." So this is precisely the phase you'd skip by starting there, and precisely the one worth not skipping: the mediator is where every hard property in this stack lives. Persist-before-ack, the per-agent inbox, transport health, the CORS trap. Build it once and Phase 7 tells you something; skip it and Phase 7 is just a green checkmark.

      Keyring's ref-05 named this exact gap and left it open — the production mediator can't mint its own DID, so it isn't a drop-in container. The tractable path that README identified is the harness crate the VTI's own e2e tests use, and it's already in your cargo cache.

        Wrap the test mediator in a binary. A tiny crate outside both repos. TestMediatorHandle gives you did() and ws_endpoint(); print both and park.

        Advertise it. Daemon stopped. Watch the new log entry land with byte-identical verification methods — a capability change with no key rotation.

        Let the wallet find it. The inbox is adopted from the agent's DID document with source: "agent". Confirm Setup says the relay came from your agent — because that sentence was once a lie the wallet told while routing through a stranger's demo host.

        Raise a consent prompt. Then read the ordering that makes it survivable: onInboundMessage awaits putPendingInbound as its first action, and only then does the transport ack — the ack is what tells the mediator to delete its copy.

        Kill the offscreen document mid-decision. Reload the extension with a prompt open. It should come back: both offscreen.ts and background.ts drain listPendingInbound on boot.

        The one that will actually bite you
        I checked the crate: the test mediator has no CORS layer at all. The wallet POSTs to {authEndpoint}/challenge before any socket exists, so with no Access-Control-Allow-Origin that handshake fails — and it takes TSP and DIDComm down together, since they share it. REST keeps working, so the wallet looks fine while the inbox is dark.

        Chrome hands JavaScript a bare TypeError: Failed to fetch for this, identical to a dead host. Don't debug it by hand and don't reach for curl — a terminal sends no Origin, so the endpoint answers perfectly and you conclude nothing is wrong. Run the wallet's own self-test: transport-diagnosis.ts infers the refusal structurally by re-probing the same host in no-cors mode. That panel exists for precisely the hour you're about to spend.

        Skip the doorbell, but notice its absence
        Push wake needs vti-push-gateway stood up; leave it. Without it a request sits in the mediator until the worker next happens to run. Time that delay once — it's the entire argument for the doorbell, and it lands better felt than read. It's also the strongest case for the phone: a notification is native there.

          A consent prompt renders, you approve it, and the agent records the decision.

          A prompt interrupted by a worker teardown is re-driven rather than lost.

          You can explain why sessions are keyed on the (agent, relay) pair.

    What this hands back to keyring

    Nothing in this plan modifies that repo. But five of its open threads get evidence they don't currently have.

        The enrolment rung nobody ran

        ref-06x declared enrolment out of scope. Phase 2 runs it against a Dogwood agent — the missing joint between the ladder and a real wallet.

        ref-05's named mediator gap

        "The mediator is not in the compose file yet." Phase 4 builds the harness-crate path that README already identified as tractable.

        A second upstream candidate

        The test mediator has no CORS layer, so no browser client can use it. A cors_origins builder option is a small PR with an obvious community rationale.

        P0's portability proof, measured

        The plan estimates ref-10-pnm-core-hermes. Phase 5 turns the estimate into a count: one shim on the Trust-Task path, one adapter, and a list of what to keep off the phone.

        The operator / user seam

        Not currently on any plan. The Class A/B/C map argues it's the highest-leverage product contribution available — and the reference app is where it gets drawn.

        No browser wallet reaches the farm

        Probed and confirmed: no Access-Control-Allow-Origin for an extension origin. The farm is the ecosystem's shared test environment and the ecosystem's own browser wallet can't use it. Two config entries fix it. Nothing here waits on that, but it's worth reporting.

        A local-dev path that actually exists

        The farm answers "give me an agent." It doesn't answer "let me run the stack." Phases 1 and 4 produce that recipe — setup TOML, a mediator binary, the CORS proxy — which is the local-dev.md upstream still has as a stub.
