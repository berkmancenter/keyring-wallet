Why the mismatch would cost you a week

Dogwood's conformance pass carried 57 breaking changes. The ones that would hit you: Trust Task payloads now emit canonical lowerCamelCase; generated payload types closed to hand-construction, with string members becoming validated newtypes; response envelopes stopped approximating schemas and now match published structures with real nesting; error codes re-cased against the registry; and consumers must declare their freshness and replay posture rather than inherit a default.

Every one of those produces a refusal that reads like your bug. Build the agent at Dogwood and the whole class disappears.

There's also a free diff waiting for you. This repo's task-surface.json snapshot records vta-sdk 0.30.0; Dogwood ships 0.31/0.32. The farm is the finish line, not the on-ramp

The VTA Farm is a managed Dogwood-R1 agent with a Community Mediator already wired — "no server, no public domain, no DID hosting, no mediator wiring on your side," treated as production and kept upgraded. It's tempting to start there. Don't.

Everything the farm does for you is something this journey exists to teach you. Provisioning an agent, hosting a did:webvh, wiring a mediator, granting an admin DID — start on the farm and those four become a web form you clicked through once. Build them yourself first and the farm stops being magic; it becomes a second implementation you can check your understanding against.

So the farm arrives as Phase 7, and it earns its place by answering a question nothing before it can: does what I built work against an agent I don't control? That's not a formality. It's the difference between a demo and a client.

Local proves you understand it. The farm proves you built it right. Only the second one transfers to Keyring.

What this settles about the extension

The extension never needs to meet the farm, which resolves a finding cleanly rather than leaving it as a blocker. For the record, since it cost a probe and is worth knowing: a request to vtafarm.firstperson.dev carrying Origin: chrome-extension://… returns 200 with no Access-Control-Allow-Origin header at all. Nothing there is configured for a browser-wallet origin.

That would have been a genuinely nasty afternoon — inside the extension it surfaces as a bare TypeError: Failed to fetch, indistinguishable from a dead host, with the real reason visible only in a devtools console. Since the extension stays on your own agent where you own cors_origins, the question simply doesn't arise. Still worth mentioning to Geoff as ecosystem feedback rather than as a request — "the browser wallet can't reach the shared test environment" is true and cheap to fix, but nothing in this plan waits on it.

The naming layer, and where your DNS analogy breaks

You called it "what IP is to DNS." The layer is exactly right. The direction of trust is inverted, and that inversion is the whole design.

An agent name is example.com/@alice. Three details are load-bearing and all three are easy to get wrong:

  • The marker is the two-character sequence /@, never a bare @ — so alice@example.com is deliberately not an agent name.
  • Trailing path segments are part of the identity: …/@drummond/h2hsummit is a different name from …/@drummond.
  • Case is preserved in the local part. @Alice and @alice are different names, because folding could silently merge two distinct identities — a strictly worse failure than one that occasionally fails to match.

Now the inversion. In DNS the zone owner is authoritative: whatever the name says, is. Here, name → DID proves nothing. It's an HTTP redirect served by the name's own web server, and anyone who controls a domain can point a name at somebody else's DID. Authority runs the other way:

DID → name is authoritative only via alsoKnownAs. Only the DID's controller can make a name true.

So the closer analogy is rel="me" / IndieAuth, or ACME's DNS-01 challenge: the pointer only counts because the target claims it back. That's why resolution has three stages and why stage 3 is mandatory — and why the hosting server itself refuses a binding whose document doesn't already carry the claim.

The wallet enforces this structurally rather than by convention. agent-name.ts exports extractAgentNames(doc) and deliberately offers no helper that guesses a name from a DID's host or path — an earlier version derived a handle from the DID's trailing segment, and that was a spoofing bug, not a shortcut. did-display.ts has no name display role for the same reason. And useAgentNames treats "claims no name", "didn't resolve" and "still loading" as indistinguishable, because none of the three licenses showing a name.

What you can build on it

Core already ships six Trust Tasks under vta/webvh/agent-name/* — set, remove, list, check, enable, disable. (check is a point-in-time availability answer, explicitly not a reservation.) That's more surface than any UI currently uses, and four things fall straight out of it:

  • Names in every consent prompt. The prompt's central question is "do I recognise who is asking," and today the answer is fifty characters of monospace in which the host — the only part a human can check — carries the same visual weight as the SCID. A verified name is the answer to that question. This is the highest-value use of the naming layer in the entire wallet.
  • Claim your name during onboarding. check then set. It converts the most alienating moment in the flow — "here is your did:key:z6Mk…" — into the most rewarding one: "you're keyring.app/@alberto." Your own plan already frames this as the agent-as-concierge beat.
  • Find-by-handle for the peer-to-peer exchange, so two people trade names rather than DIDs.
  • Rename without breaking anything. The DID is what gets stored; names are re-claimable. A user changing their handle doesn't sever a single relationship — which is a real product property, and worth saying out loud in the UI.

Where it's techy — and which kind of techy

This is the question you're actually trying to answer, so here's the map. Every moment in setup falls into one of three classes, and the classes matter more than the list.

Class A

Accidental

A UI gap. The security model doesn't require a human to do this by hand; nobody has built the alternative. Fixable now.

Class B

Essential but movable

Real security work that genuinely must happen — but not necessarily by this person, on this device, at this moment.

Class C

Irreducible

The friction is the feature. A human check that becomes frictionless has stopped being a check.

Setup today is four steps in forced dependency order — the agent's address first, because everything else is derived from resolving it. That ordering is already good design; the README used to have to warn "set your mediator DID before doing anything else" as install step 5, and the reordering deleted that whole class of confusion.

The wall, and three ladders — two of which are already built

The ACL grant is genuinely two-party: the ephemeral did:key is minted per installation, so it cannot be granted in advance. But two-party does not imply type a command, and that conflation is the accidental half.

Here's the finding that fell out of reading the farm's own setup guides, and it's much stronger than a recommendation: the stack has already solved this twice, in two other places, and wallet onboarding has inherited neither.

Ladder 1 · nobody has built this

QR in both directions

The wallet renders its ephemeral DID as a QR; an operator's already-onboarded wallet scans it and grants. Needs nothing new upstream — acl/grant is already a Trust Task and the operator's device already holds admin. Not one QR code exists anywhere in this stack today, which makes this the cheapest visible win available.

Ladder 2 · shipped, on the farm

Paste a DID into a web UI

The farm's "Admin DID → Provision agent" form is this. The same grant that reads as acl create --role admin on your own agent is a text field and a button on the farm — so the security model plainly permits a GUI here, because it is already permitting one. What remains is a human ferrying a did:key:z6Mk… between two windows. You'll do it both ways, in Phases 2 and 7.

Ladder 3 · shipped, one layer up

Request, then human approval

03-joining-a-community.md: "submit a join request under your persona, and get approved by a community admin." That is exactly self-service-under-policy — at the community layer. The same shape aimed at agent enrolment turns "run this command" into "tap Approve." Nothing needs inventing; it needs pointing one level down.

Why this reframes the contribution

"Make onboarding friendlier" is a taste argument, and taste arguments lose to shipping deadlines. "The grant already has a GUI on the farm and an approval ceremony at the community layer — wallet enrolment is the one place that inherited neither" is a consistency argument with two working precedents inside the same stack. That version is much harder to wave away, and it's the one worth taking to Prague.

The thing worth taking away

The techiness is not evenly distributed, and it isn't where it looks. Nearly every genuinely technical step is operator work — provisioning an agent, granting ACLs, configuring a mediator, pinning an extension key. Nearly every user step is already simple, or could be. What the stack lacks isn't simplicity; it's a seam.

One surface currently does both jobs, which is why a person meets a --role admin --expires 1h flag. Drawing that line may be the reference app's most valuable contribution.

The phone shows only what a person owns and decides. Everything else belongs to a console that person never opens. Hold that rule while you build Phases 5–6 and the answer to "where should this be normie-friendly" stops being a judgement call each time.

Extension or React Native first

Extension, and it isn't close.

The plugin is the only client where this flow works end to end, which makes it your oracle: when the RN app misbehaves against the same agent, you need a known-good second client to tell you whose bug it is. Its diagnostics panel is also the only instrument that distinguishes a CORS refusal from a dead host.

Where the agent lives

A sibling clone at the Dogwood tag.

~/Documents/verifiable-trust-infrastructure — exactly where this repo's npm run tasks:sync already looks for vta-sdk. Built fresh at Dogwood, never copied from keyring's Cypress clone. Keyring stays untouched throughout.

RN transport

The measured porting surface for a REST Trust-Task client on Hermes is one shim. vti-tsp-js is noble-only and explicitly RN-safe — your own team's HPKE work — and Dogwood makes TSP receive a first-class path. vti-didcomm-js is the WebCrypto-backed piece that would fight you.

Onboard the wallet, as both parties

half a day

Onboarding is a two-party handshake and locally you play both — which is the best possible way to feel where the wall is. The wallet mints an ephemeral did:key and asks an operator to grant it; you are that operator. Then provision/integration returns your long-term holder identity in an HPKE-sealed bundle.

  1. Build and side-load. Then confirm at chrome://extensions that the id matches what Phase 1 printed. If it doesn't, manifest assembly didn't pick up the key and your CORS entry points at nothing. 
    npm run build -w @openvtc/pnm-extension
# chrome://extensions → Developer mode → Load unpacked
#   → packages/extension/dist/
  2. In Setup, paste the full did:webvh:… — not a name. Name resolution's third stage requires the document to claim the name back via alsoKnownAs, and your local agent publishes no name server. A correct refusal, not a bug — and a good moment to re-read the naming section above.
  3. Press Prepare. Read provision/request.ts while it waits: the ephemeral's Ed25519 seed is also the secret that will open the sealed bundle.
  4. Grant it, as the operator. The offline CLI needs the fjall lock, so stop the daemon first. 
    # stop the daemon, then:
vta --config config.toml acl create \
  --did did:key:z…  --role admin --expires 1h
# restart the daemon
  5. Press Connect. Four round trips. The VTA mints a did:key holder, seals the keys to your ephemeral, and the wallet cross-checks the bundle id against its own request nonce before adopting anything.
  6. Then write down what you just did by hand. This is the Class-A/Class-B moment from the map. Note every place you typed or pasted something a QR could have carried — that list is Phase 6's design brief.
Where the gestures go

Onboarding runs in a tab, not the toolbar popup, because Chrome tears the popup down whenever a native dialog takes focus — and this flow raises two. Separately, chrome.permissions.request needs a live user gesture and must be the first await in the click handler or the gesture is already spent. Both constraints vanish on RN.

The mediator, and the approval ceremony

a week — the risky one

The part you said you care about. A consent prompt is a security control: one silently lost prompt is a gated action that never got its human check. Everything strange about the inbox design is downstream of that sentence.

The farm would hand you this, and that's the reason to build it

The farm ships a managed Community Mediator — "no mediator wiring on your side." So this is precisely the phase you'd skip by starting there, and precisely the one worth not skipping: the mediator is where every hard property in this stack lives. Persist-before-ack, the per-agent inbox, transport health, the CORS trap. Build it once and Phase 7 tells you something; skip it and Phase 7 is just a green checkmark.

Keyring's ref-05 named this exact gap and left it open — the production mediator can't mint its own DID, so it isn't a drop-in container. The tractable path that README identified is the harness crate the VTI's own e2e tests use, and it's already in your cargo cache.

    // two builder settings are load-bearing:
.enable_forwarding(true)   // routing/2.0 forward — defaults FALSE
.local_dids(vec![holder_did, vta_did])
// the WS upgrade handler refuses any session
// whose DID lacks the LOCAL ACL bit
  2. Put a CORS proxy in front of it. ~40 lines of Node: add Access-Control-Allow-Origin for your extension origin, pass the WebSocket upgrade straight through, point the wallet at the proxy.
  3. Advertise it. Daemon stopped. Watch the new log entry land with byte-identical verification methods — a capability change with no key rotation. 
    vta --config config.toml services didcomm enable \
  --mediator-did <the mediator's did>
  4. Let the wallet find it. The inbox is adopted from the agent's DID document with source: "agent". Confirm Setup says the relay came from your agent — because that sentence was once a lie the wallet told while routing through a stranger's demo host.
  5. Raise a consent prompt. Then read the ordering that makes it survivable: onInboundMessage awaits putPendingInbound as its first action, and only then does the transport ack — the ack is what tells the mediator to delete its copy.
  6. Kill the offscreen document mid-decision. Reload the extension with a prompt open. It should come back: both offscreen.ts and background.ts drain listPendingInbound on boot.
The one that will actually bite you

I checked the crate: the test mediator has no CORS layer at all. The wallet POSTs to {authEndpoint}/challenge before any socket exists, so with no Access-Control-Allow-Origin that handshake fails — and it takes TSP and DIDComm down together, since they share it. REST keeps working, so the wallet looks fine while the inbox is dark.

Chrome hands JavaScript a bare TypeError: Failed to fetch for this, identical to a dead host. Don't debug it by hand and don't reach for curl — a terminal sends no Origin, so the endpoint answers perfectly and you conclude nothing is wrong. Run the wallet's own self-test: transport-diagnosis.ts infers the refusal structurally by re-probing the same host in no-cors mode. That panel exists for precisely the hour you're about to spend.

Skip the doorbell, but notice its absence

Push wake needs vti-push-gateway stood up; leave it. Without it a request sits in the mediator until the worker next happens to run. Time that delay once — it's the entire argument for the doorbell, and it lands better felt than read. It's also the strongest case for the phone: a notification is native there.

Done when
  • Diagnostics shows DIDComm up with a completed handshake and an open socket.
  • A consent prompt renders, you approve it, and the agent records the decision.
  • A prompt interrupted by a worker teardown is re-driven rather than lost.
  • You can explain why sessions are keyed on the (agent, relay) pair.

Hermes portability probe

two or three days

No UI. Prove the library runs on the phone's engine before building anything on top of it — the same discipline as keyring's ref-03b, for the same reason: a byte difference found now is an afternoon, found later a week.

I measured the porting surface rather than guessing. It's much smaller than the file count suggests, because most apparent hits are comments and a parameter that happens to be named document.

  3. Assert byte-exact, not "looks right." Same signature, same digest, or the probe fails.

The reference wallet

two to four weeks

A Keyring-shaped RN app on the iOS simulator, against the agent you've run since Phase 1. Built to be lifted into keyring later — so it matches keyring's versions, theme and module shape from the first commit — and every technical moment from the Phase 2 list gets a QR or a tap.

Make the agent a config value, not a constant

You're building against localhost now and against the farm in Phase 7, so the agent's address is a runtime setting from the first commit. That isn't just plumbing for Phase 7 — a reference app that can only reach one agent teaches implementors less than one that demonstrably works against any, and swapping targets is also how you'll test what the UI does when a transport goes down.

Match keyring exactly

Same versions means the port is a folder move, not a negotiation. All read from app/package.json:

That vision-camera line matters more than it looks: keyring already ships and has shipped a working camera stack, so every QR idea in this document is a known quantity rather than a new native dependency.

Mimic the module shape, not just the look

Keyring consumes @bifold/* packages through portal: resolutions behind a tsyringe DI container. So put all pnm-core wiring behind one module with a DI token and RN shims — which is exactly the bifold/packages/vti-client shape your PNM/CNM plan already names. Do that from commit one and the eventual port is "move the folder, register the token." Do it later and it's a rewrite.

Five screens, each answering a question from the map

  • Agent — scan a QR to add an agent, with paste as the fallback. Show the capability ladder you first read in Phase 1, and render the DID with the host lifted, the way did-display.ts does.
  • Onboard — render the ephemeral DID as a QR for the operator to scan (Ladder 1), rather than a did:key:z6Mk… to copy between windows. You will have just done it by hand twice, on both tracks, so you'll know exactly what you're deleting. Biggest normie win available today, and it needs nothing upstream.
  • Name — check then set. Turn "here is your did:key:z6Mk…" into "you're …/@alberto." The screen that makes the whole thing feel like a product.
  • Persona — the farm's 02-openvtc-tui guide creates a persona DID for daily use, kept separate from the VTA's master keys. This wallet already implements the same idea — commits #144–#146 bind a persona to a site on first sign-in and sign in as it. Two independent arrivals at the same shape is a strong signal it belongs on the phone.
  • Approvals — the Phase 4 ceremony, and where a phone genuinely beats an extension. Dogwood guarantees the prompt is signed; show the requester by verified name, never by a name derived from the DID. Spend your design effort here.
Two simulator honesties

No hardware attestation on a simulator — keyring learned this the expensive way, and only attended device runs prove those paths. And leave encryptHolderSecret off, which is already the default, for the reason the extension documents at length: the WebAuthn ceremony needs a visible, user-focused context.

Done when
  • Someone who has never seen a DID onboards the app against your local agent by scanning two codes.
  • An approval raised from the extension can be decided on the phone.
  • The agent's address is a setting, and the pnm-core wiring is one folder behind one DI token.

Point it at the farm

an afternoon, if the rest was right

The graduation. Every earlier phase ran against an agent you configured, which means every earlier phase could have been passing for the wrong reason. The farm is a Dogwood-R1 agent you don't control, with a mediator you didn't wire, run by someone who didn't build your client — the first honest test in the whole journey.

Why this is the phase that transfers to Keyring

Keyring will eventually talk to the farm directly, and this is the rehearsal — done in a small app where a wrong turn costs a day instead of a sprint. What you carry over isn't code so much as a settled list: which shims were actually needed, which assumptions about the agent were yours rather than the protocol's, and what breaks when the endpoint isn't localhost.

  1. Get the pnm binary and check it runs native. The macOS build was refreshed 09-03; you're on an M5 and only x86/Linux and macOS are published. 
    curl -LO https://download.firstperson.dev/releases/dogwood/macOS/pnm
chmod +x pnm
file ./pnm     # arm64? or x86_64 under Rosetta 2?
./pnm --version
  2. Create the VTA in the web UI. vtafarm.firstperson.dev → Create account (any email; the passkey is the real credential) → Create VTA → name it → Create session. Copy the Personal VTA DID.
  3. Point pnm at it. Choose "Connect to an existing non-TEE VTA", give the same name, paste the VTA DID. pnm mints a temporary did:key:z6Mk… and prints an import-did command you don't run on this path. 
    ./pnm setup
  4. Grant it in the web UI. Paste that did:key into Admin DID → Provision agent → wait for "Agent is online."
    You will recognise this moment

    That paste is the ACL grant — the same act you performed with acl create --role admin in Phase 2, wearing a web form instead of a shell. Having done it both ways is what makes the Ladder 2 argument yours rather than borrowed. And it's still a human ferrying a did:key:z6Mk… between two windows, which is still exactly the QR-shaped hole.

  5. Verify, and read what it verifies. pnm health checks the VTA, the Mediator, and DIDComm/TSP trust pings. You built that mediator leg yourself in Phase 4, so you know what each line is actually asserting. 
    ./pnm health
  6. Switch the RN app's agent setting to the farm VTA and run the same five screens. Onboard, claim a name, list the vault, approve something. Note every difference from localhost — each one is a hidden assumption you can now name.
  7. Then go one layer up. 02-openvtc-tui for a persona DID, 03-joining-a-community for a join request approved by a community admin. That's the VTC layer, and it's where keyring's VRC work eventually meets this stack.
Done when
  • The RN app completes onboarding, a vault list and an approval against a farm VTA, with no code change beyond the address.
  • You can list every difference between the farm and your local agent, and say which were your assumptions rather than the protocol's.
  • You've joined a community under a persona, so the VTC layer is no longer hearsay.
  • The hand-off note for keyring is written: the shim list, the assumption list, and what you'd do differently.
