# 2026-09-21 — BM: confirmations follow the app's existing modal convention, not a new screen

**Plan:** [`../ui-ux-improvements-plan.md`](../ui-ux-improvements-plan.md). This document records what was measured and concluded on 2026-09-21; it is not revised afterwards.

**Read at:** `bifold/packages/core/src` on the submodule checkout in this worktree (`archive/trust-tasks-over-didcomm-v1`).

## S. What the app already does for a confirmation

[`2026-09-21-al.md`](./2026-09-21-al.md) measured what upstream offers for linking and sign-in. This part measures something closer to home: what Keyring itself already does, today, when it asks a person to confirm an action — because the plan's journeys (§5) and button rules (§4.3) were written without checking.

**A reusable bottom-sheet modal is the established pattern.** `CommonRemoveModal` (`bifold/packages/core/src/components/modals/CommonRemoveModal.tsx`) is a slide-up `SafeAreaView` with rounded top corners, built on the shared `SafeAreaModal` wrapper, driven by a `ModalUsage` enum (`types/remove.ts`): `ContactRemove`, `ContactRemoveWithCredentials`, `CredentialRemove`, `CredentialOfferDecline`, `ProofRequestDecline`, `CustomNotificationDecline`, `ProfileDeleteWithContacts`. Each usage supplies its own title, body and bullet content; the modal always renders a critical confirm `Button` (`ButtonType.ModalCritical`) and a `Cancel` `Button`. It is used from `screens/CredentialDetails.tsx:493`, `modules/vrc/screens/ContactDetails.tsx:581`, `screens/CredentialOffer.tsx`, `screens/ProofRequest.tsx` and `modules/vrc/screens/MyProfiles.tsx` (`ProfileDeleteWithContacts`). Sibling components on the same `SafeAreaModal` base — `ProofCancelModal.tsx`, `AlertModal.tsx`, `DismissiblePopupModal.tsx`, `ErrorModal.tsx`, `VerifyPINModal.tsx`, `BiometricConfirmationModal.tsx` — show this is a family, not a one-off.

**A lighter, ad hoc alternative also exists:** native `Alert.alert`, used directly in `modules/vrc/screens/WitnessConnections.tsx:267` ("Remove Witness") and `screens/Developer.tsx:172` ("Clear Test Contacts"). It is not the polished path — it has no themed styling and no bullet content — and both of its call sites are lower-stakes or dev-only.

**No dedicated full-screen "confirm" route exists anywhere in the app.** There is no screen file named, e.g., `ConfirmScreen`. Every confirmation today is a modal overlay on the screen the person was already on, not a navigation to a new one.

**The design guidelines say nothing on this.** `docs/design-guidelines/design guidelines.md` covers screen anatomy (app bar / body / navigation) and touch targets; it gives no criterion for modal-vs-screen. The convention here is established by usage, not documentation — which is exactly why a plan proposing new confirmation UI has to check the code, not the doc.

**The trust-task screens have no confirmation UI to inherit from.** `MyAgent.tsx`, `VtiCommunity.tsx` and `VtiVetting.tsx` reference no `Modal`, `Sheet` or `Alert` today — none of their actions are currently confirmed at all. So aligning them to `CommonRemoveModal`/`ModalUsage` breaks no local pattern; there isn't one yet.

## T. Position

**Every plain yes/no confirmation in this plan's journeys uses the app's existing bottom-sheet modal, extending `ModalUsage` with a case per action** (e.g. a case for joining a community, one for leaving it, one for unlinking a phone), rather than a new "confirm screen" route or a new component. One confirmation mechanism in the app, not two.

**Supersedes:**

- Plan §5.2 step 3, `"Confirm screen: 'Join Community name as a member?'"` — this is a `ModalUsage` case, shown over the community list the person was already looking at, not a screen transition.
- Plan §4.3's destructive-action bullet, which named the outcome-labelled confirm ("Leave *Community*" / "Stay", "Unlink this phone" / "Keep linked") without saying what UI carries it. It is the same modal family as every other destructive confirm in the app.

## U. The one deliberate exception, and why it survives this position

The full-screen match-code step in §5.3/§5.4 ("Does the vetter's screen show the same code? Codes match / Codes differ") stays full-screen, not a modal. This is not an oversight the position above corrects — it is a different kind of interaction. A `ModalUsage` confirm asks a person to affirm a decision they already made ("yes, leave"); the match code *is* the verification act itself, the one determinative check the whole in-person ceremony depends on, done by a person looking between their screen and a partner's screen with a face or a document in the room. It needs to be the only thing on screen, for the same reason Signal's safety-number view and the Bluetooth numeric-comparison prompt are both full-screen rather than a dialog over a chat view (plan principle 8, companion §C, "In-person verification"). A modal here would visually demote the one check the session's integrity rests on to the same weight as "leave this community."

## V. Applied

The plan (§4.3, §5.2) is edited in the same change as this document, per this directory's [`CLAUDE.md`](../CLAUDE.md): confirmations name `CommonRemoveModal`/`ModalUsage` as the mechanism, §5.2 step 3 is reworded from "screen" to the shared modal, and §4.3 gains one sentence recording the match-code exception and why it is not covered by the same rule.
