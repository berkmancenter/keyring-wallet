## A. The UI as it stands

### A1. Taps to get vetted, today

Applicant, from a linked phone: *Connect my agent* → *Reach the community* → *Create my identity* → open Vetting → type legal name → *Save* → *Start my application* → paste the ticket link → *Request vetting* → wait → *Send my card* → *Apply*. Eleven actions, three of which (*Connect*, *Reach*, *Create*) are plumbing the person cannot make a decision about.

Vetter: open the desk → *Publish my profile* (optional) → *New ticket* → *Open session* → compare the code → *Attest*.

### A2. What the user path depends on outside the app

| Dependency | Where | Why it is there |
|---|---|---|
| The agent's DID, the community's DID, the mediator's DID | `app/.env` (`VTI_VTA_DID`, `VTI_COMMUNITY_DID`, `VTI_MEDIATOR_DID`), baked at build time | No runtime choice of agent was built; switching lab ↔ Farm is `use-stack.sh` plus a native rebuild |
| Admitting the phone to the agent | `scripts/openvtc/local-vti-stack/enrol-manager.sh` — stops the VTA, writes the ACL entry offline, restarts it | Stand-in for the enrolment contract in the vetting subtask §9 request 2 |
| Invitations | `invite-persona.sh` prints a `keyring://vti/invitation?c=…` link; the runner opens it with `adb am start` | No portal step in the harness; the link does not fit a QR (VTI-32) |
| The vetter grant | `vtc-admin.mjs … vetter-grant <did>` | Admin action, correctly off-app |
| Resetting an applicant | Developer screen → *Forget this community* (`app/src/screens/Developer.tsx`, `handleForgetCommunity`) — the vetting runner opens the Developer screen to do it | No in-app leave |
| The VTA probe | Developer screen, auto-run with `VTI_PROBE_ON_START=1` | Dev convenience; it reports with an alert that the runners dismiss |

### A3. What the main-path screens show that a person cannot use

`MyAgent.tsx` (613 lines): agent host, manager DID, persona DID, and "Peer messages: TSP (Rev 3)" / "DIDComm v2". `VtiVetting.tsx` (790 lines) switches between the vetter desk and the applicant view on whether a vetter grant is held; the ticket is shown as a text link under "…let them scan or paste this link", with no QR rendered and no scanner route for `vetting-ticket:`. `TabStack.tsx` routes only `keyring://vti/invitation` deep links.

**Conclusion:** the flows are complete and correct, but three layers are interleaved on the same screens — decisions the person makes, plumbing the app should do, and diagnostics for us. The plan separates them (principles 3–5).

## B. What upstream supports for linking and sign-in

### B1. Admitting a manager DID to a VTA

- **Offline:** `vta import-did --did --role [--context]` and `vta acl …`, labelled "offline, no server required"; the store's exclusive lock is why the daemon must be stopped (`vta-service/src/main.rs:250-269`, `:319-321`; `vta-service/src/import_did.rs:17-40`).
- **Online:** `POST /acl` for Admin or Initiator (`vta-service/src/routes/acl.rs:78-90`), the same check as the `acl/grant/0.1` Trust Task with the policy step-up gate (`vta-service/src/trust_tasks/acl.rs:56-82`), and `pnm acl create --did --role [--contexts] [--expires 1h]` (`pnm-cli/src/cli.rs:2185-2230`; omitting `--contexts` with `--role admin` makes a super-admin, `:2198-2202`).
- **No self-enrolment for a non-TEE VTA.** `docs/05-design-notes/sealed-bootstrap.md` still describes a token-gated "Mode A" (`:45`, `:232-272`) and its header says "Implemented", but the code says it was removed: "non-TEE clients now use `pnm setup`'s … flow (client mints locally, admin grants via `vta acl create`…)" (`vta-service/src/routes/bootstrap.rs:10-13`). The only unauthenticated first-admin path is attestation-gated and TEE-only (`routes/bootstrap.rs:190-199`, `:356-367`).
- **Mobile:** upstream's iOS agent puts enrolment out of scope — "The device `did:key` must be in the VTA's ACL (`pnm acl create --did <did:key> …`) before *any* message from it is accepted" (`vta-mobile-agent-ios/README.md:75-77`); its pairing QR carries only where to connect (`Sources/VtaMobileAgent/PairingPayload.swift:3-16`). The mobile design note's PNM surface is "largely *not yet*" built (`docs/05-design-notes/mobile-agent-architecture.md:754-760`).

**Conclusion:** the phone cannot enrol itself from nothing; an authorised admin must act. But our lab script takes the offline path when an online one exists. **Supersedes** the assumption, implicit in `enrol-manager.sh` and the vetting subtask's P4, that granting a phone requires stopping the VTA.

### B2. How a person manages their VTA from a laptop

- `pnm setup` → "Connect to an existing non-TEE VTA" mints a temporary `did:key`, prints it, and asks the operator to admit it (`pnm-cli/src/setup.rs:43-52`, `:81-96`); it "never ingests a credential file: PNM always self-mints" (`:12-17`). On the first authenticated connect it rotates to a long-lived key and removes the temporary DID from the ACL (`setup.rs:430-434`; `vta-sdk/src/session.rs:305-326`, `:459-486`). Keys live in the OS keyring (`vta-sdk/src/session/backends/mod.rs:1-20`).
- `pnm auth` is only `logout | status | sign-challenge | show-token` (`pnm-cli/src/cli.rs:1681-1706`) — there is no "log in"; being admitted *is* the login.
- The Farm path in upstream's guide: create the VTA on the Farm, run `pnm setup` with its DID, paste the temporary DID into the Farm, `pnm health` (`vti-setup/developer/01-personal-vta.md:36-83`).
- The browser extension mints an ephemeral key and shows the command an operator runs — `pnm acl create --did <eph> --role admin … --expires 1h` (`vta-browser-plugin/packages/extension/src/grant-command.ts:1-70`) — then adopts a VTA-minted admin DID through a sealed reply (`packages/core/src/provision/run.ts:1-14`). It uses WebAuthn twice: a PRF passkey encrypts the stored secret at rest (`packages/extension/src/encrypt-holder.ts:1-40`), and a passkey can be enrolled as a DID verification method for relying-party login.

**Conclusion:** "logging in to your VTA from a computer" means `pnm setup` once (temporary key, admin grant, rotation), then the key in the OS keyring. The phone should follow the same pattern (plan §5.1).

### B3. Passkeys on the VTA

Enrolling a passkey verification method on a DID requires an admin session (`vta-service/src/routes/passkey_vms.rs:10`, `:58-161`). Login is `POST /auth/passkey-login/start` (unauthenticated, checks only that the DID is in the ACL — `routes/auth.rs:586-616`) and `…/finish`, which verifies against the DID-resolved method (`operations/passkey_login.rs:1-10`) and mints ordinary tokens with `amr=["did","passkey"]`, `acr="aal2"`; the session carries the DID's role. A cross-origin popup exists at `GET /auth/portal` (`routes/auth_portal/mod.rs:1-37`). The mobile design note names `ASAuthorization` / Credential Manager (`mobile-agent-architecture.md:505-507`), but no upstream component publishes `apple-app-site-association` or `assetlinks.json`, which a native passkey on the VTA's domain requires.

**Conclusion (inference, to be measured in U7):** a phone could sign in *as the person's admin DID* with a passkey through the VTA's portal in a system browser session, then grant its own manager key with `acl/grant`. It needs a `did:webvh` admin DID with a passkey method, and nothing upstream provides that hand-back today.

### B4. The Farm

The Farm account is a passkey (`vtafarm-api/internal/handler/passkey.go:116-309`). Creating a VTA provisions it and parks at "awaiting admin DID"; the console says "Run `pnm setup` locally and paste the admin DID it outputs" (`vtafarm/src/pages/portal/CreateVTAView.tsx:910`); the API accepts it once, in that state (`vtafarm-api/internal/handler/setup.go:1129-1174`), and "never runs `pnm setup`" (`vtafarm-api/docs/vta-setup-design.md:79-84`). No QR, deep link or phone hand-off exists in the console.

**Conclusion:** the Farm passkey authenticates the Farm account, not the VTA. A phone can take part only by producing the DID the person pastes — which the plan makes a QR plus Copy/Share, and which VTI-Q10 asks the Farm to make scannable.

### B5. The community admin portal

First sign-in is an **install URL** (a one-shot JWT, 15 minutes) plus a separate **claim code** from `vtc setup` (`vtc-service/src/install/mod.rs:1-24`; `install/claim_secret.rs:1-21`). Entering the code runs `POST /v1/install/claim/start|finish` and registers a passkey (`routes/install.rs:1-48`; `docs/03-vtc/getting-started.md:203-222`). Further admins come from `vtc admin invite --did <did>` on a stopped daemon, which mints a new install URL (`vtc-service/src/main.rs:160-180`, `:444-558`). After that, sign-in is by passkey or by DID auth (`docs/03-vtc/website-and-admin.md:349-364`). The VTC's ACL and token audience are separate from the VTA's, so a portal passkey cannot act on a VTA.

**Conclusion:** the lab portal shows no passkey prompt because no admin passkey has been claimed on it; the portal is passkey-based only after the install-URL claim. **Supersedes** our own earlier working note that the lab portal "signs in with a passkey" as though that were its first screen.

### B6. The identity document

The vetting session specification: the vetter "MUST NOT capture or store any detail of the documentation it inspects" and the applicant "MUST NOT put a document number, a document image, a portrait…on the card"; "a vetter looks at a passport; the passport does not travel" (`dtgwg-trust-tasks-tf/specs/vetting/session/0.1/spec.md:167`, `:179`, `:310-314`). The statement records a document *class* label (`documentClasses: ["passport"]`), the claims verified, liveness and a commitment (`vta-sdk/src/protocols/vetting.rs:671-696`); a portrait is refused (`:964-976`). Upstream's persona model keeps faces and the attribute pool on the VTA (`vta-persona/README.md:1-25`); its design note `persona-context-first.md` is "Status: proposed". A passport number can be a *typed* attribute (`vta-persona/src/claim_types.rs:329-336`), never read from the document.

**Conclusion:** reading the document is out of scope by specification (plan §5.6). Where the typed legal name is stored depends on the profile–persona reconciliation (plan §7).

## Part 2 — decisions and additions, later the same day

### E. Decided

1. **The phone's key stays device-bound.** No synced passkey carries it. Reason: it keeps hardware attestation available to the key and keeps "this phone" meaningful to the agent's access list. Cost accepted: a lost phone is re-linked, not restored. **Supersedes** Part 1's open decision 1, which only *assumed* device-bound.
2. **Face ID or a fingerprint is the only sign-in a person sees** — it unlocks the device key and confirms every signing act (plan principle 9). **Supersedes** Part 1's position D2 in wording only: the passkey remains a sign-in route to *measure* (U7), and is no longer described as a possible replacement.
3. **Leave community is in the app**, not only a lab script (plan U1). **Supersedes** Part 1's open decision 3.
4. **The approver stays out of the demo** (plan §8). **Supersedes** Part 1's open decision 4.

### F. Granting the phone: automate now, a web page next, the Farm later

The admin role in enrolment stands: an agent accepts a device only when someone authorised says yes (§B1). What was wrong was that saying yes meant stopping the agent at a terminal. Position: stage it (plan §5.1, *Granting the phone*):

- **Now:** the online grant, called by the runner with the key it reads off the phone. It makes the harness unattended and needs no upstream change (§B1–B2).
- **Next:** a lab enrolment page — the laptop camera reads the phone's QR, both screens show the key's fingerprint, the admin clicks Grant — tested with browser UI tests using a fake camera stream and a virtual authenticator (plan U8). It is also the working prototype of the enrolment contract the vetting subtask asks the Farm for, which makes that request concrete rather than descriptive.
- **Later:** the Farm console, when it accepts a device by QR (VTI-Q10).

Rejected: having the phone grant itself with a secret it was handed. Upstream removed that path for non-TEE agents (§B1), and reinstating it locally would test a flow no real agent host offers.

### G. What "signed in to your agent" should look like

Measured: the VTA has no login session to enter or leave (§B2) — being admitted is the login, and each request is authenticated by the key. Upstream's own client, once connected, shows the operator's view: "Connected ✓", "Your wallet is authorized at this VTA", the VTA's DID and the wallet's DID each with a copy button, "Role … · Transports …", and a "Manage this agent" button that opens a console of "contexts, keys, credentials, access and audit" (`vta-browser-plugin` `d045a7a`, `packages/extension/src/popup.tsx:415-458`).

Position: a person needs presence, contents, history and possibility, not identifiers. The plan's agent screen (§4.1) leads with a status line (Online / Reconnecting / Offline since …), what the agent holds, what it did, and what the person can do next, with upstream's operator view kept behind Details. The first-link introduction presents the agent as the person's stand-in online — the "digital twin" framing — once, in three panels, recallable from the agent screen. Grounds: EUDI's "visibility of system status" and its rule against rarely needed information (§C identity wallets); NN/g's contextual introductions over tours (§C roles).

"Linked" and "Online" are kept apart on purpose: linking happens once and lasts (like a paired device); being online changes minute to minute. Using one word for both is what makes "am I signed in?" unanswerable.

### H. The harness is part of every phase

Every flow change breaks the runners that drive it, and several changes add things a simulator cannot do unaided — a camera scan on iOS, Face ID, a two-sided confirmation. Position: runners change in the same commit as the screens, and one cross-cutting phase (plan UT) owns the shared needs: scanning by handing the scanner its text in dev builds, simulator biometrics, resets without the Developer screen, unattended enrolment, a documented test-ID map. **Supersedes** Part 1's per-phase note that runners are "renamed in the same change", which covered test IDs but not new capabilities the harness must gain.

### I. Still open

1. Whether the demo starts linked or shows linking live (plan §8).
2. Whether the lab enrolment page (U8) is built before Prague.

## Part 3 — the direction of the enrolment QR, a live demo, and the agent screen's state

### J. The phone scans; the laptop does not

Part 2 (§F) had the laptop's camera read a QR shown on the phone. That works in a browser (camera access plus a QR decoder), and it is not only a test device — but it points the camera the wrong way. A laptop camera is poor at reading a phone screen, and the phone already carries the app's one scanner. The position now: the **enrolment page shows the QR and the phone scans it**. The page's QR is a short-lived, single-use link bound to the page session; the phone submits its temporary key to that link signed with the key, and both screens show the key's fingerprint before the admin grants. This is the shape the vetting subtask already asks the Farm for (its §9 request 2), and it keeps the confirmation on the side that holds the authority — the IETF cross-device draft's "context on the approving device". **Supersedes** §F's "next" stage and plan principle 6 as first written ("the device being linked shows the QR; the trusted side scans").

It also changes the tests: the page is ours, so a browser test reads the enrolment link from the page itself and hands it to the simulator the way every other simulator "scan" works (plan UT). The fake camera stream §F planned for is not needed.

### K. A web page for granting already exists upstream

Measured at `vta-browser-plugin` `d045a7a`: the extension's management console has an **Access** pane — "who may act at this agent, in which contexts, until when" (`packages/extension/src/manager/panes/access.tsx:1`) — with a *Grant access* form (`:380-500`) that takes a pasted `did:key` (`:455`), a role and an optional expiry (`:394`, `:413`) and calls `aclGrant` (`:417`), the `acl/grant/0.1` Trust Task (`packages/core/src/admin/acl.ts:96-113`). No QR or camera code exists anywhere in the extension or the PWA.

**Conclusion:** the manual web path exists; what is missing is only the QR half. So the stages become: automated (runner), upstream's page (measure, no code), the lab page adding the QR (local experiment), and indications to upstream for the Access pane and the Farm console. **Supersedes** §F's three stages, which assumed no web page existed.

### L. The demo links live

Decided: linking is a step the person takes, by QR, and the demo shows it — the first thing the audience sees. **Supersedes** Part 1's assumption and Part 2's open question (§I.1). Consequence: the lab enrolment page is built before Prague (§I.2 closed). A second pair of phones, linked beforehand and kept off stage, covers a venue network that fails.

### M. The agent screen's state, and its buttons

Measured in `vtaAgent.ts` and `MyAgent.tsx` on the feature branch: the agent's status is `disconnected | connecting | connected | failed`, and each screen adds its own `useState` booleans and step strings, then combines them to decide what to render (`MyAgent.tsx`, the S1/S3/S4 branches). The screens use hand-rolled `Pressable` buttons, not bifold's themed `Button` / `ButtonType`.

Position (plan §4.2–§4.3): one state machine owned by the module — NotLinked, AwaitingGrant, Linking, Linked (Online / Reconnecting / Offline), Revoked — read through the existing `useSyncExternalStore` subscription; persisted and live state kept apart; each section with its own loading, empty, error and content states; an in-flight action owned by the machine rather than the button. Buttons use the existing theme and follow:

- Apple HIG, buttons: a 44 × 44 pt minimum hit region, one prominent button per view, verb labels, progress shown in the button — https://developer.apple.com/design/human-interface-guidelines/buttons
- WCAG 2.2 SC 2.5.8: "The size of the target for pointer inputs is at least 24 by 24 CSS pixels" — https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html
- NN/g, confirmation dialogs: "Use a confirmation dialog before committing to actions with serious consequences", and "Instead of Yes/No answers, provide response options that summarize what will happen" — https://www.nngroup.com/articles/confirmation-dialog/

The last one also changes the match-code screens: "Codes match" / "Codes differ" replace Yes / No (plan §5.3, §5.4). **Supersedes** the Yes / No wording in Part 1's journeys.

### N. Still open

1. How the indications from the lab page reach upstream — issue, pull request against the Access pane, or a note with the next report. Public, so it needs a go.
2. Whether the lab enrolment page is guarded by a passkey or runs as the lab admin with no sign-in.

## Part 4 — every QR has a link twin, scanning goes first, and a running list of upstream asks

### O. Reuse the VRC exchange's hand-over

Measured on the feature branch: the peer-to-peer VRC exchange already hands an invitation between two phones in a way that serves both people and the harness. The sharing phone shows a QR, and in dev builds also the link as hidden text (test ID `InvitationUrl`); the receiving phone opens the **Scan** screen, whose header has a *paste URL* button (`PasteUrlButton`); the runner reads the link off one phone, sets the other phone's clipboard and pastes it for real (`e2e/lib/flows.js`, the relationship-QR and scan-and-paste helpers). A person does the same with a camera, or with a copied link.

Position: agent enrolment, vetting tickets and invitations use that exact hand-over — a QR with a link twin, received through the same Scan screen — rather than a new test hook. **Supersedes** Part 3 §J's "hands it to the simulator the way every other simulator scan works" and plan UT's dev-build dispatch hook: the harness now pastes, as the VRC runners do, which also exercises a path a real person uses when their camera cannot scan.

### P. Scanning goes first

The person wants to start with scanning or pasting a link. Position: U4 (one scanner and paste) and enrolment by QR (U6, then U8) are the first phases; the rest follow (plan §6, *Order of work*). Every other flow hands something over through the scanner, so building it first unblocks them.

### Q. A running list of upstream asks

Position: the plan carries every ask of upstream in one table (plan §9), with the code each points at and a status, updated as the work finds them. It is the source for the next report to the maintainers and for the upstream findings document, which assigns the permanent `VTI-` numbers — never this plan, so numbers cannot collide between branches. Eight asks are recorded today: enrolment by QR in the extension's Access pane (U-1) and the Farm console (U-2, already VTI-Q10); whether the enrolment offer should live in the agent (U-3); the design note that still says a removed flow is implemented (U-4); one QR for upstream's mobile agent (U-5); invitations by reference (U-6, already VTI-32); native-app passkey sign-in (U-7, conditional on U7); where a client writes the typed legal name (U-8, conditional on the persona reconciliation).

### R. Still open, in plain words

1. How the asks reach upstream: with the next report, as an issue, or as a pull request. Public, so it waits for a go.
2. Whether the lab enrolment page needs a login. It never leaves our laptop; the plan assumes not.
