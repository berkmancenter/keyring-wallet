## A. What the first TestFlight build with the Prague work showed (0.2.0, build 206)

A tester linked a phone to the lab agent by QR — that part worked end to end — and then could not go further:

| # | What happened | Cause | Where it was fixed |
|---|---|---|---|
| A1 | **Get vetted** stopped at "No agent is configured for this build" | The vetting screen read only the build's `VTI_VTA_DID`; store builds leave it unset so testers link their own agent | keyring-bifold#57: every screen resolves the linked agent first (`resolveVtaDid`) |
| A2 | The **"Linked ✓"** screen came back on every return to the tab | Continue pushed the agent screen on top of it; and links reach My Agent as the tab's `{ screen }` param, which React Navigation replays on the next tab press | keyring-bifold#57: Continue sets the stack; `MyAgentStack` drops the param once acted on |
| A3 | Someone **invited** could not hand the admin their identity | An invitation is issued to a DID named in advance; the redesigned agent screen had dropped the only way to share one | keyring-bifold#58: "I was invited" |
| A4 | After linking, **what next** was unclear | Three equal buttons (Join a community, Get vetted, a locked Vet someone), no sense of where the person was, and "Create my identity" behind Get vetted | `feat/ui-ux-u3`: this document, §B |

**Why the runs had missed A1 and A2:** every automated run tested a configuration testers never get. The vetting runs baked `VTI_VTA_DID`; the Release check stopped at linking; nothing navigated away and back. From here on each PR is checked on a store-configuration Release build (no `VTI_VTA_DID`, no probe, `@bifold/core` `lib/` rebuilt at the head) along the whole tester journey — `run-vta-link.js JOURNEY=1` — which caught A2's second cause on its first run.

## B. The journey after linking — decided

Four directions for the redesign, from the TestFlight session:

1. Start from what the person wants — *I was invited*, *I want to join* — not from technical steps.
2. The community identity is made as part of joining, not as a button to find.
3. The identity a person joins with comes from one of their profiles, filled in rather than retyped.
4. Being a vetter is news when an admin grants it, not a locked step up front.

They became the plan's §4.1 table, §5.2, §5.3, §5.7 and §5.8. A mock of the screens was reviewed before any of it was built; the review accepted it with three decisions:

| Decision | Chosen | Alternative, and why not |
|---|---|---|
| How a profile relates to a community identity | **Seed by copy**: the profile fills in the new identity's name once; no live link | The editable multi-profile plan's enforced 1:1 link. Upstream's persona model reuses a face only as a deliberate, warned choice and protects by keeping faces local; a live link would carry a profile edit into every community. Changing that plan needs its author's agreement |
| What Join as selects by default | **A new identity starting from the active profile** | The profile's existing identity — faster only if reuse were the default, which upstream advises against |
| What Door 1 sends the admin | **The community identity made at Join as** | Another DID the phone already holds, linked at join through upstream's `subjectLinkage` (`vtc-service/src/credentials/invitation_verify.rs:197-200`). It would let Join as wait until the invitation arrives, but tells the community the two DIDs are one person, and Keyring would need new code to send the linkage |

## C. When the identity must exist — the protocol constraint behind the order

| Moment | Needs the community identity? | Evidence |
|---|---|---|
| The admin issues an invitation | A DID, yes | `vtc-service/src/routes/invitations.rs:43-44`: `subject_did`, "the DID to invite", required; the credential is holder-bound and single-use |
| A vetter's ticket is redeemed | Yes | `vetting/request/0.1` carries `joinDid`; the desk binds the ticket to it, and the statement names it as subject |
| The join request is submitted | Yes | The presentation's holder is the identity; a statement whose subject differs is not counted (`subject-not-applicant`) |

So the identity is made at **Join as**, before the admin invites (Door 1) and before the ticket (Door 2). The person never sees it made: they choose a profile and confirm once with Face ID.

The order of concepts is the TUI's. The one change of order — Door 1 makes the identity before the invitation exists — is forced by §C.

## E. Findings on the way

- **Which community is not the build's to decide.** A hosted community is joined from its DID, and everything else (mediator, manifest) is resolved from there. `VTI_COMMUNITY_DID` becomes a suggestion; a community link, a vetter's ticket or an invitation chooses the community (plan §5.7).
- **Registry consent.** Keyring's join request sends `registryConsent: false` (bifold `modules/trust-tasks/module/vtiAgent.ts:717`), as the TUI does (`openvtc-core/src/join.rs:248`). The service stores it (`vtc-service/src/join/mod.rs:111`, `src/join/orchestrate.rs:277`); its doc comment says it is consent to publication in the community's trust-registry record, deferred to a later phase, and nothing acts on it yet. Door 2 keeps sending false and does not ask; recorded upstream as VTI-Q14.
- **Where an admin pastes a phone's code.** The VTA browser extension already has a paste-only *Grant access* form (Manage this agent → Access), so linking to an agent an admin runs needs no upstream change; the no-QR link screen now names it beside `pnm acl create`. A "Link a phone" QR in the extension stays upstream ask U-1.

## F. Upstream's remediation plan, read against this plan

Read in full: *Keyring Remediation Plan* (`docs.fpp.storm.ws/keyring-remediation-plan.html`, state as of VTI `3dcbfe98`, TDK `1eeebba1`, webvh `88fc6464`, 22 September). Findings for this plan's asks and screens (the plan's §9 and §9.1 hold the resulting status; this section records why):

- **U-6 is answered; U-9 is not.** `vtc/invitations/deliver/0.1` solves delivery (a `message` channel pushes an offer to the invited DID) and size (an `offer` channel returns a QR-sized offer that names the credential rather than containing it). Both are redeemed "by proving a key of the invited DID", so an invitation is still made out to a DID in advance. Door 1's "send who you are" step stands; only its last step changes, from pasting a link to receiving or scanning the offer.
- **Linking a phone to a maintainer's VTA needs the admin role today.** Since VTI #1619, minting a persona needs `KeyMint` (initiator), but exporting a key is admin-only. Keyring borrows persona keys (`VtaClient.ensurePersona` → `borrowKey`), so a phone linked as initiator could mint but not use its identities. The link screen now says to choose admin in the extension's Grant access. Upstream's answer to Q4 — sign through `keys/sign` — is the path to linking as initiator, and is protocol work.
- **Door 2 took "not vetting" for "invitation only".** Found while checking KR-13 (a community cannot express "no requirements"): `asksFrom` treated any community without a vetting criterion as invitation-only. It now reads an invitation criterion, other criteria, and none as different answers.
- **Withdraw, supplement and `requestAlreadyOpen` (KR-03, KR-04)** give Door 2 its missing states. They need the lab on a VTI that carries VTI #1591–#1593, which is the Prague session's pin work.
- **Q10 is useful for U-1 and U-2 but does not close them.** The paste-free admin paths (`vta setup --from`, `pnm setup --name`/`continue`, `vta import-did --role admin`) are provisioning-time; a phone linking to a running agent still needs a paste or a QR.
