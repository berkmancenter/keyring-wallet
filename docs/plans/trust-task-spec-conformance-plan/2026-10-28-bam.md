## 2. Spec text relied on

Quoted at `bdf2cdd`, `spec/body.md`; line numbers are for the reader's convenience only, per `docs/plans/CLAUDE.md` citations go by section name.

- **Declared extension** (Compatibility Rules, ~l.648–650): a version that declares `extends` "keeps every member, type, required member, enumerated value, constraint and definition of the named version, and only adds to them … with the same proof requirement and every task-specific error code the named version declares." "A *consumer* implementing a version **SHOULD** accept a document of any later version whose `extends` chain reaches it … without the declaration a *consumer* **SHOULD NOT** apply forward [processing]". This is why `propose/0.2` cannot declare `extends: 0.1`: dropping `propose:declined` removes a task-specific error code the named version declares.
- **Behaviour at Each Status** (~l.682–683) and **Superseded and Withdrawn Versions** (~l.692): as quoted in the plan §2.
- **Extension by Individual Trust Task Specifications** (~l.1245–1247), rules 1 and 3: as quoted in the plan §2.
- **What a consumer verifies** (~l.197): "It **MUST NOT** verify over a re-serialization of a typed representation of the document, or of any value derived from one."
- **A hold is a next step** (~l.1296–1301), in full for the two cases: "**The *producer*.** Where the *producer* can perform the act itself — a step-up it can complete, a consent it is the party to give — `expects` names the *Trust Task* that performs it." "**A third party.** Where the act belongs to someone else … `expects` names a *Trust Task* by which the *producer* can learn the outcome or resume. Where the *consumer* offers no such task, `expects` names the originating *Type URI* with `continuation: resubmit`, and the *consumer* answers a resubmission in the same thread with the outcome once it is known, or with a further *next step* while the act is still awaited." And: "A hold that ends because the act is declined … is a refusal to run the task, and is answered as one (`permissionDenied`) when the *producer* next asks".
- **A decision is not a failure** (~l.1087–1089): "For such a task every decision it can produce, a negative one included, is the task's **outcome**, and is reported in the success response. … a *producer* never has to read a decision out of an error code it may not recognize." "A *recipient party* reports a decision in the form its specification defines."
- **`indeterminate`** (Standard Error Codes, ~l.1194, 1199): "`proofInvalid` says verification ran and the proof did not hold. `unavailable` says the *recipient party* itself is not able to process the task now … `indeterminate` says the *recipient party* could not reach a determination because a reference published by someone else could not be obtained or checked." Retryable: `true`.
- **Consumer Requirements item 11** (~l.903) and **Bounding the record** (~l.917): duplicate-execution protection keyed on `id`, bounded by `expiresAt` or the consumer's own window; "A *consumer* that can establish neither … **MUST NOT** execute a *consequential Trust Task* on it."
- **Shared Schema Components rule 5** (~l.850): as quoted in the plan.
- Library `trust-task-next-step/0.1` `continuation`: "`resubmit` (the default) means the expected task is a PREREQUISITE and the producer re-issues the originating request … `proceed` means the expected task IS the continuation and the originating request is not re-issued, as in an offer answered by a request."

## 3. Positions taken, with alternatives considered

**P1. Read by `extends` (plan position 1).** Alternative: `['0.5','0.6'].includes(version)` — the review's "simplest and good enough today". Rejected as standing design because it encodes today's registry in a list that goes stale at the next extension, which is exactly the failure that produced the bug (a reader written for "the version VTI emits" in September). `extendsChain` is the library's, already shipped. *(Corrected 2026-10-29, see [`2026-10-29-bam.md`](./2026-10-29-bam.md): "costs one import" was wrong; the chain must also be registered.)*

**P2. Emit 0.6 (plan position 2), conditional.** The `vtiVetting.ts:111–116` comment justifies 0.5 as "the version VTI emits and the only one trust-tasks-rs 0.22 models". That was a statement about a reader that does not do forward processing. 0.6 declares `extends: 0.5` (as the constant `EXTENDS` in its module, not in the library's index; see the 10-29 correction), so any reader that follows the framework's SHOULD reads it, but whether trust-tasks-rs at the current VTI pin does was not checked. Keeping 0.5 indefinitely conflicts with #33's producer SHOULD and leaves Keyring emitting two versions (vtiVetting 0.5, `rejectWith` 0.6). Hence: decide on evidence (W10 step 3a), with Q1 as the fallback.

**P3. The 0.3 sunset.** `LEGACY_ERROR_03_UNTIL = '2026-11-01'` is four days away. It is time-based by design and needs no code change; after it, a Keyring vetter older than "PR E" that still emits 0.3 has its refusal dropped. No such vetter is known in the field. The plan leaves the sunset as designed rather than extending it.

**P4. Next step for the consent hold (plan position 5).** Who acts: the wallet is the consumer and its person decides, so this reads as either "the producer" case (no — the proposer cannot give the recipient's consent) or the "third party" case. The consent is not the producer's to give, so the third-party branch governs; Keyring offers no task by which the proposer can learn the outcome other than the propose itself, so `expects` names the propose Type URI with `continuation: 'resubmit'`. Alternative: `continuation: 'proceed'` naming `propose#response` — rejected: `#response` is not a Trust Task the producer issues, and the next-step module says `proceed` is for "an offer answered by a request". The wallet continues to push the outcome unasked; the spec's resubmission rule is satisfied as well, so a proposer that does resubmit gets the outcome or a further next step.

**P5. The decline of a held propose: #45 vs #46.** #45 says a declined hold is answered `permissionDenied`; #46 says a decision the task exists to produce is its success outcome. For propose the consent *is* the decision the task produces, so #46 governs the answer and #45 governs only the interim next step. For `propose/0.1`, whose spec defines `propose:declined`, the decline stays in that form: "A *recipient party* reports a decision in the form its specification defines." Alternative: answer a 0.1 decline with `permissionDenied` to satisfy #45 literally — rejected: it would break every deployed Keyring proposer, which reads `…declined` and would show an error instead of "declined", and it reports the decision as a refusal to run the task, which #46 says it is not.

**P6. `propose/0.2` as a new version, not an extension (plan position 6).** Alternative: `propose/0.1` amended in place — rejected: 0.1 is published in the library and deployed, and changing a published version's error codes breaks the extension promise for every reader. Alternative: `0.2` with `extends: 0.1` and `decision` added — rejected: the declared-extension rule requires keeping "every task-specific error code the named version declares", so 0.2 would have to keep `propose:declined`, which is the SHOULD NOT #46 is about. Wire-compat comes from the existing `supportedTypes` discovery gate: deployed builds do not list 0.2, so they are never sent it.

**P7. `witness-share` (staging).** The review called this a judgment call. Position: the task's purpose includes verifying the pairing (the description says the receiver "ran the pairing algorithm"), so a negative verdict is a decision and goes in the receipt; an error stays for "not performed". If any distributed build emits the current shape, the change is staged as 0.2 rather than in place.

**P8. `indeterminate` via a pre-check now, the library later (W2).** Alternative: throw a typed error from our verifier and rely on `consumeInbound` — rejected for now: 0.28.1 catches every throw and maps it to `proofInvalid` (`consume.ts:441–444`), so the code never reaches the wire. The pre-check resolves the expected controller before `consumeInbound` and answers `indeterminate` itself, which is the review's interim fix. It costs one extra resolution on the happy path (resolver caches make it cheap), and it is removed when the library takes a tri-state verifier. The wire `message` must not name the DID or the resolver's answer, for the reason the library gives at `PROOF_INVALID_WIRE_MESSAGE` (a resolver-reachability oracle for an unauthenticated sender).

**P9. Witness submit is consequential (plan position 8), conditional on Q3.** The single-use, session-bound challenge already prevents a second VWC from a replayed submit in practice (the session is deleted at `:682`), so this is formal conformance more than a live hole. Taking it is cheap with the library's `consequentialChecks` and `replay.ts`, and makes the MUST checkable by a test rather than by an argument about session lifetimes.

**P10. #47 `alreadyIssued`.** Optional. It needs a registry change to `witness/session/submit`; the tombstone can ship first with `challengeMismatch` as the code.

**P11. #48.** `approvalsPolicy.ts` must stay a byte-exact port of vta-sdk (the VTA refuses a module that differs), so the fix in Keyring is upstream of the defaults: never build a consent rule that relies on them. The default itself is VTI's.

## 4. Upstream drafts (Q4)

**Issue on `trustoverip/dtgwg-trust-tasks-tf` (TS library), citing spec #50.** Title: "consumeInbound reports an unresolvable verification method as proofInvalid; #50 requires indeterminate". Body: `_runtime/consume.ts` (0.28.1, the `verify` case of the proof policy) maps a verifier's `false` or throw to `proofInvalid`, and `ProofVerifier.verify` returns `boolean`, so a consumer cannot report that the verification method's DID could not be resolved. Spec *Standard Error Codes*, `indeterminate`: the recipient "**MUST NOT** return `proofInvalid` or `permissionDenied` in its place." Proposal: let `verify` return `true | false | 'indeterminate'` (or throw an exported `IndeterminateProofError` carrying `reference: 'verificationMethod' | 'schema' | 'statusList' | 'document'`), and map it to `{ code: 'indeterminate', retryable: true, details: { reference } }` with a constant message; apply the same to an unobtainable schema in payload validation. Keep the constant-message rule for both codes. Offer the PR.

**Issue on VTI (`vta-sdk`), citing spec #48.** Title: "approvals Rego synthesis supplies governance defaults (minApprovals = 1, excludeRequester = false)". Body: `approvals/mod.rs` fills both when a rule omits them; `policy/_shared/0.4` dropped those defaults (`@openvtc/trust-tasks` 0.28.0, #960) and spec *Shared Schema Components* rule 5 says a component "**MUST NOT** supply a `default` for a governance value". Ask: require both, or reject a rule that omits them. Record as a `VTI-NN` finding after reproducing on the local stack.

## 5. Caveats and what was not verified

- Whether the DIDComm v1 class-transformer round trip and the retained-record path are byte-faithful in every case (W7 tests it).
- Whether VTA, VTC and openvtc accept the successor versions, and whether VTI's trust-tasks-rs does forward processing over `extends` (W10 step 3).
- How each VTA approval and step-up hold reaches the wallet: `VtaClient.ts` (~2580 lines) was not audited end to end (W10 step 4). `vtaClaim.ts` already reads the Farm's signed `trust-task-next-step/0.1` and follows `expects`.
- Whether `…:tickNotYet` in the hidden-vetting rounds means "held" (a #45 note for VTC) or "not yet eligible" (a refusal), W10 step 3c.
- The ceremony's credential digest comparisons re-serialize a typed VC (`JsonTransformer.toJSON(record.firstCredential)`), the pattern #44 warns about, though #44's letter covers Trust Task document proofs only. W7 step 3 is optional for that reason.
- The registry view used was the library's bundled modules (0.28.1), not a registry clone, because both local clones predate the library.
