# 2026-10-21 — al — the first OTA trial on an iPhone, and what keeps OTA off

Companion to `ota_updates_subtask.md` (a local export, not yet in this
repository; parent: `../release-cadence-and-testing-strategy.md`, also a local
export). Written by the
OTA lane on 21 October 2026, from the first over-the-air trial on a physical
iPhone. The trial used the quick-install test app: bundle id
`asml.bkc.harvard.wallet.ota`, channel `device-test`, and its own throwaway
key. No tester build was involved.

## Decision

**Store builds carry OTA from build 267 on; no update goes past ring 0 until
a bad update recovers without a force-quit.** `OTA_UPDATE_URL` is set for store
builds, so they check for updates. A production or preview bundle is published
to ring 0 only: installs that deliberately joined it from the Developer
screen. Every other install defaults to ring 2 (`app/src/ota/rings.ts`).
Widening it to ring 1 or ring 2 waits for three results on a device:
- the watchdog closes a crashing update by itself;
- it doesn't fire on a normal update's first launch on the slowest phone we
  have (an iPhone 11). That run is a measurement, not only a pass: the time to
  the first screen is recorded here. If it comes near the watchdog's 20
  seconds, the threshold changes before anything is widened;
- an OTA-off build installed over a phone holding an update runs its own
  bundle (the gap test, below). **Passed on 22 October.**

Separately, **no store build is cut after a production update until the
isolation key includes the build number** (see "A stored update can outlive a
store upgrade", below). The build that carries the fix starts clean whatever
its predecessor stored, since its key differs. So 267 can take ring-0 updates,
and the fix must land in the next store build cut after one. A version bump
would also change the key, but patch builds within a version wouldn't.

The gate is about what testers see. On iOS, an update that crashes while its
JavaScript loads currently leaves the app on a black screen. Only a force-quit
and reopen brings back the previous bundle. A tester who doesn't think to
force-quit is stuck. Ring 0 is people who joined it on purpose and know to. An update reaches
anyone else only once a crashing update returns the app to a working screen by
itself, either in place or by closing so that the next tap opens the previous
bundle.

Shipping the setting before the proofs is safe because nothing reaches a store
phone unless a bundle is published for its build, and a publish targets ring 0
only (`ota-deploy.mjs`). Widening is a separate command, run by hand with the
server's management token; no workflow widens.

Where the conditions for widening stand:

| Condition | Status |
| --- | --- |
| A store build records a fingerprint that a publish matches | Fixed and guarded in CI (#552, #554, #555). In trial step 7 the guard refused a publish for the wrong fingerprint. |
| A crashing update closes by itself | Cause found on the phone. A mitigation is merged (#562, a watchdog). Owed: the crash run on a device. |
| A normal update's first launch doesn't trip the watchdog | Owed: the iPhone 11 run, with its time to first screen recorded against the 20-second threshold. |
| An OTA-off build over an update runs its own bundle | Passed on the test app (below). The test had more margin than production has. |

## What the trial showed

On an iPhone 16, quick-install build 2610211645 (wallet `b4c59430`,
fingerprint `0dfd0297…`):

1. **The embedded bundle loads.** The app joined ring 0 from the Developer
   screen.
2. **An update loads.** Bundle `01a15fef-3ebf-7c53-…` (ota-publish run
   39657974819) downloaded during one session and ran on the next cold start.
3. **A tampered update is refused.** Bundle `01a1601d-…` (run 39666708827),
   signed with a key the app does not carry, was offered and downloaded. The
   phone's console shows the signature check refusing it twice, on its
   manifest and then on its archive (`RSA signature verification failed, no
   match`). The app stayed on `01a15fef`.
4. **A crashing update rolls back, but not cleanly.** Bundle `01a1605f-…` (run
   39674805929) throws on the first line of `index.js`. After a force-quit the
   app came back on `01a15fef`, and the phone's `crashed-history.json` records
   `01a1605f` with one crash. **On the crashing launch itself the app neither
   closed nor recovered: it stayed on a black screen.**
5. **A problem report names the running update.** The report saved from the
   test app's Settings has `· update 01a15fef` in its header.
6. **Withdrawing updates sends the phone back to its own bundle.** The
   device-test cleanup (run 39690524392) deleted every bundle on that channel.
   On the next launches the phone ran `embedded (01a1587f-…)`.

   A plain `bundle disable` of the running bundle would not have shown this.
   The server offers the newest enabled bundle above the phone's current one
   (`fingerprintStrategy` in `@hot-updater/js`), so it would have offered a
   newer crash bundle instead. The phone would refuse that from crash history
   and stay where it was.
7. **A bundle for another fingerprint never reaches the server.** Run
   39693932415 built a bundle on a native edit (fingerprint `f9650090…`) and
   asked to publish it for the test app's `0dfd0297…`. `ota-deploy` refused
   before uploading: "no phone on that build would be offered this bundle.
   Refusing".

**The gap test: an update installed, then OTA turned off. Passed.** This is
the case of a store build without `OTA_UPDATE_URL` installed over a phone
holding an update. On 22 October the iPhone 16 was running update
`01a160e9-…` (ota-publish run 39694039134). The same test app was then
reinstalled as a true OTA-off build (2610212348: no `HOT_UPDATER_*` keys in
Info.plist, no URL). It opened normally on two launches. Its OTA screen read
State off, Running embedded (`01a15a02-…`), Native fingerprint none. The
console shows why:

```
[BundleMetadata] Isolation key mismatch: expected=hotupdater_0.1.0_production_, got=hotupdater_0dfd0297…_0.1.0_device-test_
```

hot-updater files a phone's stored update under an isolation key
`hotupdater_{fingerprint}_{appVersion}_{channel}_` (`getIsolationKey` in
`HotUpdaterImpl.swift`). A build that doesn't find its own key ignores the
stored update. With no `HOT_UPDATER_*` keys the fingerprint is empty and the
channel falls back to `production`.

**Production has less margin than this test.** Here two parts of the key
differed: the fingerprint (empty against `0dfd0297…`) and the channel
(`production` against `device-test`). Between an OTA-on and an OTA-off store
build, both channels are `production` and the version is the same, so only the
fingerprint differs, and only because the OTA-off build has none. An OTA-off
build is therefore safe only while its Info.plist and manifest carry no
`HOT_UPDATER_*` keys. If one ever did, the keys would match and it would run
the stored update.

**A stored update can outlive a store upgrade (from source; not yet tested on
a device).** Every store build has version `0.2.0` (tags `staging-v0.2.0-NNN`),
and the build number isn't part of the key. Take a store build with only JS
changes since the last one. It has the same fingerprint, version and channel,
so the same key, and it finds the previous build's stored update:
- the native launch selects that stored bundle (`selectLaunch` in
  `BundleFileStorageService.swift`), with no comparison against the newer
  built-in one;
- the update check then reports that older bundle id with the new build's
  `minBundleId`;
- the server drops bundles older than `minBundleId`. Its empty-candidate branch
  returns no update and no rollback when `bundleId <= minBundleId`
  (`fingerprintStrategy` in `@hot-updater/js`).

That phone keeps the old JavaScript on the new binary until a newer bundle is
published. The planned fix is to include the build number in the isolation key,
using hot-updater's override (`HotUpdaterConfig.isolationKey`) on iOS and its
Android equivalent. The device test: build A, take an update, then install
build B from the same commit with a new build number. B must run its own
bundle.

## Why the black screen happens (0.36.18; confirmed on the phone)

- **hot-updater's recovery path.** During a monitored launch,
  `HotUpdaterRecoveryManager` (iOS, `HotUpdaterImpl.swift`) catches React
  Native's fatal-error handlers and `RCTJavaScriptDidFailToLoad`. Instead of
  letting the app crash, it asks for a recovery reload into the previous
  bundle.
- **What the reload does under the New Architecture.**
  `HotUpdaterPerformRecoveryReload` (`HotUpdater.mm:176`) does select the
  previous bundle: it calls `resetLaunchPreparation`, resolves the bundle URL,
  and passes it to `RCTReloadCommandSetBundleURL`. Only the final trigger,
  `HotUpdaterTriggerReloadCommand` (`HotUpdater.mm:33`), differs by
  architecture. Under `RCT_NEW_ARCH_ENABLED`, which this app uses, it is just
  `RCTTriggerReloadCommandListeners`; the old architecture first waits for its
  bridge to invalidate. So the rollback intent is expressed, and the black
  screen fits that bridgeless broadcast not taking effect.
- **No watchdog.** Nothing in hot-updater catches a screen that never
  appears. Its only timer starts after content appears.

**Confirmed on the phone.** A second crash bundle (`01a16084-…`, run
39682456319) was launched with the Mac's console attached. All of the
following happened within about 70 ms:

```
[BundleStorage] Setting bundle URL to: …/bundle-store/01a15fef-…/index.ios.bundle
[HotUpdaterRecovery] Triggered recovery reload for bundleId=01a16084-…
Scheduler::~Scheduler() was called · UIManager::~UIManager() was called
Non-js exception: AppRegistryBinding::startSurface failed. Global was not installed.
```

After that came nothing for 60 seconds: the black screen. The previous bundle
is chosen, and the old React instance is torn down. The new surface is then
started before the runtime it needs exists. On the next cold start
`01a15fef` reached its first screen, and the crash bundle was offered again
and refused: `Bundle '01a16084-…' is in crashed history, rejecting update`.

- **The cure is a fix to the bridgeless reload,** upstream, leading with that
  error. The previous bundle is already chosen; only the reload has to wait
  for its runtime.
- **The mitigation is a native watchdog** (wallet PR #562). When the first
  launch of a downloaded update, in the foreground, shows nothing within 20
  seconds, the app closes itself, so the next tap opens the previous bundle.
  The threshold errs long on purpose: firing late costs seconds of black
  screen after a rare bad update, while firing early would close healthy slow
  launches every time. It still needs two device runs:
  - the crash proof should close by itself;
  - a normal update's first launch on the iPhone 11 must not trip it, which
    also measures the real threshold.

## Also settled today, recorded elsewhere

The native fingerprint differed between where store builds are made and where
updates were published. That is fixed and guarded in wallet PRs #552, #554 and
#555:
- iOS updates are published on macOS after `pod install`;
- every store build records its fingerprint;
- a publish refuses on a mismatch.

The causes are in #554's description. Builds cut before #554, 241 to 265,
recorded no fingerprint, so OTA cannot target them.
