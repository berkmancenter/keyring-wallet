### 1.3 What the record says

1. Every long-lived integration branch this team has had decayed into the
   real trunk while `main` stopped being true. That is the single strongest
   fact in the history and it rules out a permanent `development` branch.
2. "Put unfinished work on a phone" was the need the epic branches and the
   deploy PR served. It is a build-trigger problem, not a branching problem.
3. Every code change is two branches (wallet + bifold). Branch topology costs
   double here.
4. `main` is already the centre of gravity again, with PRs and reviews
   happening; the flow should harden what is already working, not introduce
   a new tier.

## 3. Positions rejected, with the reason each fails

**`main` → `staging` → `development` (git-flow-shaped), as first proposed.**
Rejected, see 1.3(1) and plan §8. What the proposal wanted — a place for work
not yet fit for `main`, and a way to get it onto devices — is delivered by the
PR gate on `main` plus the dev channel building any `ref`. A short-lived
`release/x.y` stabilisation branch remains allowed for the rare case; it is
tagged and deleted, never kept.

**Keep building on `pull_request` to `staging`.** Rejected: it is how #146
stayed open three months; it lets an unmerged branch reach internal testers;
on a public repository it is a secrets surface. Replaced by a
`workflow_dispatch` of the staging channel with a `ref`, with the branch name
stamped into the build's release notes.

**Separate workflows per channel.** Rejected: each workflow has its own
`run_number`, so build numbers collide across channels. One workflow, one
counter (plan §4).

**`git rev-list --count` as the build number.** Considered because it is
deterministic and rebuildable; rejected because a preview build from a branch
with fewer commits than `main` produces a *lower* number, which the stores
refuse. Kept as a note so it is not re-proposed.

**A bifold-side `staging`/release branch.** Rejected: the submodule pointer
already pins bifold exactly; a second pointer is a second thing to keep
consistent with no extra guarantee. The one rule needed is that the pointer
is reachable from bifold `main`, which CI can check (plan §5).
