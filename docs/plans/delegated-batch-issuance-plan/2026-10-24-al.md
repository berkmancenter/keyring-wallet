### N2. The VTA's generic signing frames the payload, so its output is not a plain ES256 signature

**What the code does.** At pin `49f5f1be`, a signature made through the Trust Task `keys/sign` path is computed over a framed input, not over the caller's payload:

- `vta-sdk/src/protocols/key_management/sign.rs` defines `OPAQUE_SIGNING_DOMAIN_V1 = b"vti.vta.opaque-signing.v1"`;
- `opaque_signing_input(payload)` returns `TAG ‖ 0x00 ‖ payload`;
- the doc comment says: "A verifier of a signature produced by the VTA's generic signing operation checks it over **this**, not over the payload it supplied."

**Why it matters.** Any signature the plan expects the VTA to produce over a standard structure would fail a standard verifier unless the circuit or the verifier knows the frame. That includes the key-binding JWT, mdoc `DeviceAuth`, or a hash the circuit treats as plain ES256.

**Proposed changes.**
- Record this in §5.2 and §9.
- Add an upstream ask for a protocol-defined signing operation, one that signs without the frame for a named purpose. The alternative is to state that the circuit accounts for the frame.
- Rung D2 (Part 3) makes the mismatch concrete.

### N3. The phone-to-VTA presentation path needs a name, a time budget and an offline answer

**What B-direct implies.** B-direct binds each proof to the verifier's session transcript (§7.1), so the VTA must be online for every presentation.

**What the plan leaves open:**
- **No transport.** The plan does not name the Trust Task or carriage message that asks for the proof and returns it. Q26 covers delivery of the credential, not presentation.
- **No time budget.** The plan's own estimates are 2.7–7.7 s to prove (C++, one thread) and 1.5–4.2 s to verify (BAM-07 XIII.3), before the phone↔mediator↔VTA round trips. Wallet flows over OpenID4VP or the Digital Credentials API have their own timeouts, and nothing checks them against these numbers.
- **No unreachable-VTA case.** The plan does not say what the user sees when the VTA cannot be reached. Offline use exists only in B-batch, whose freshness (Q15) is open.

**Proposed change.** Add these three items to §5.5 as named open questions, each with an owner.

### N4. A proving VTA observes every presentation, and that interacts with #114

**What the VTA would see.** A VTA that proves for the holder sees the whole credential and every verifier transcript. It also records sign operations in its audit log (`vta-service/src/operations/keys.rs`, audit on sign). A per-presentation log kept on the VTA is a linkage record, which works against the plan's own goal of "no correlation".

The plan's requirement that the VTA be holder-controlled (Q12) is the only mitigation, and it is undecided.

**The conflict with #114.** The zero-knowledge plan (#114) says Keyring "runs no prover", and its 10-14 decision moved hidden-vetting proving to the VTA. It also quotes the DTG ZKP specification: "Mediated proving … MUST NOT be the only path available to a holder". Until Phase 4, a VTA-only prover is exactly that.

**Proposed changes.**
- Reconcile Phase 3 and Phase 4 with #114 in a cross-reference, since this plan does not cite #114 at all.
- State whether Phase 4 (proving on the phone) is what satisfies that MUST.

### N5. Proving on the phone is more feasible than the plan's numbers suggest, for the standard circuit

**The plan's numbers are not phone numbers.** Every proving figure in the plan is from a desktop host (BAM-07 XIII). The custom-circuit range (0.7–2.1 GiB per proof) is an estimate, and it would not fit a React Native app on most phones. Published phone measurements of the **stock** mdoc circuit tell a different story:

- **Yivi, October 2026, on a MediaTek Dimensity 8100 (Android 15):** about 1.1 s to prove in the wallet, about 1.0 s to verify, 360–365 KB per proof, 140–165 MB peak memory. Efficiency cores were about 3× slower than performance cores. <https://docs.yivi.app/blog/zkp-age-verification-mobile/>
- **Multipaz (OpenWallet Foundation) packages the upstream Rust prover:**
  - a C-ABI shim (JNA on Android, cinterop on iOS);
  - a stripped arm64 `libzkp.so` of 2.09 MB;
  - bundled circuits of about 280–336 KB each.

  <https://github.com/openwallet-foundation/multipaz/tree/main/multipaz-longfellow>
- **Other mobile packaging:** the EUDI project ships an iOS Swift package of the prover (`eu-digital-identity-wallet/av-lib-ios-longfellow-zkp`), and ISRG's Rust implementation (`abetterinternet/zk-cred-longfellow`) has uniffi Kotlin/Swift bindings.
- **Not measured anywhere:** low-end Android and iPhone figures are unpublished.

**What a Keyring native module would need** (all of these are to be measured, not assumed):
- an asynchronous TurboModule or JSI method that runs on a background executor, never the JavaScript thread;
- circuit loading and hashing done off the UI thread and cached. Yivi reported a launch freeze before it did this;
- a single-threaded prover, so battery cost per proof is about one core for one to two seconds.

Hermes has no WebAssembly, so the WASM builds are not an option on React Native 0.81.

**Precedents in this repo.** `askar-react-native` and `anoncreds-react-native` (dependencies) are Rust behind a C++ JSI host object. Our own TurboModules (`react-native-attestation`, `react-native-locality-peripheral`) have no Rust or C++ core. The parked native bridge mentioned in `hiddenVetting.ts` is not on any remote branch.

**Proposed changes.**
- Replace "sub-second proving on phones … [unverified]" (Part III) with the figures above.
- Make Phase 4's start condition a measurement: rung D0.
- Note that the cost question is mostly about the **custom** circuit, not about where it runs.

### N6. Longfellow's status has moved since the plan was written

- **New home.** Google donated the code to the PQCA (Linux Foundation Europe) on 2026-09-02, and the repository now lives in the `longfellow-zk` organisation. <https://blog.google/products-and-platforms/platforms/google-pay/zero-knowledge-proof-library-linux-foundation/>
- **Adopted at the IETF.** CFRG adopted the draft as `draft-irtf-cfrg-longfellow-00` on 2026-10-22. <https://datatracker.ietf.org/doc/draft-irtf-cfrg-longfellow/>
- **Releases.** The last tag is v0.9 (2026-03-31), and main is active.
  - Rust **v1** is bit-compatible with C++ and uses the frozen mdoc circuits (versions 5–7).
  - Rust **v2** is in development and has no frozen circuits.
  - The Rust circuit format is about 1 MB, against about 100 MB for the C++ format.
- **Both external audits found under-constrained checks in the production mdoc circuit,** which have been fixed:
  - Trail of Bits, 2025-08-18;
  - ISRG-01, patched in v0.8.4.

  This supports the plan's audit gate for any custom circuit. <https://longfellow-zk.github.io/longfellow-zk/docs/reviews/>
- **Limits of the stock circuit that matter here:**
  - equality checks only, with no range predicates;
  - the MSO must fit in about 2.5 KB (40 SHA blocks);
  - the issuer key is a public input;
  - there is no revocation check inside the circuit.
- **The EU age-verification profile allow-lists `longfellow-libzk-v1` only.** It carries proofs over the Digital Credentials API, and states that "ZKPs are not supported over OpenID4VP in this version". <https://ageverification.dev/av-doc-technical-specification/docs/annexes/annex-A/annex-A-av-profile/>

**Proposed change.** Update §7.4 and the Phase 0 pins to the new repository, the CFRG draft and Rust v1. Record whether the custom circuit targets v1 or v2.

### N7. The verifier side: Keyring cannot present to a standard verifier today

- **Keyring's agent does not register OpenID4VC.** `app/src/utils/bc-agent-modules.ts` on `main` registers askar, anoncreds, indyVdr, didcomm, dids, relationshipDid, attestationStorage and dataIntegritySuite, and no `openid4vc` module. Bifold carries OpenID4VP holder code (`modules/openid/resolverProof.tsx`, routed from the scanner), but in Keyring it has no module to call. The pilot verifier's flow (Phase 1) needs that path first.
- **Becoming a Digital Credentials API wallet is native work outside React Native:**
  - Android needs the Credential Manager holder API (`androidx.credentials.registry`, alpha), with a sandboxed matcher;
  - iOS 26 needs an Identity Document Provider extension, and supports `org-iso-mdoc` only.
- **In-person presentation is not addressed.** ISO 18013-5 over BLE or NFC is not in the plan.
- **Standard verifiers will not accept the custom proofs** (Q18). Only the plan's pilot verifier would. The test verifiers that exist upstream are:
  - Longfellow's `reference/verifier-service` (Go, Docker);
  - Multipaz's verifier server.

  The OIDF OpenID4VP conformance suite has no ZK tests.

**Proposed changes.** Name the presentation channel for Phase 1 (OpenID4VP over QR, or the DC API). Add "Keyring registers OpenID4VC and completes one plain OpenID4VP presentation" as a Phase 1 prerequisite.

### N8. User experience: the same flow, plus two additions

**Receiving and sharing keep today's flow:**
- receive: scan a QR, see the offer screen, find it in the Wallet tab (#419 §7, §9);
- share: scan the verifier's QR, see a consent screen listing exactly what will be shared, done.

The consent design lives in #419 (KH-P5), and this plan should reference it rather than define its own.

**B-batch adds a counter and a refill.** Existing wallets show it like this:
- the EU age-verification app: "N proofs of age left" and "No proofs of age left. Add more";
- the EUDI reference wallet: "Instances remaining n/m".

The EUDI ARF asks that refill need no user action, that the wallet warn when it is offline and running low, and that it fall back to reuse when empty (ARF 3.0.0 Annex 2, ISSU_42, ISSU_45, ISSU_46, ISSU_47). The plan should adopt those rules if B-batch ships.

**The user must be told when a derived fact cannot be proved.** Predicates such as "over 21" are not supported unless the primary credential carries them as claims (§7). A request for "over 21" may therefore force the full birth date, and the consent screen must say so before the user agrees.

### N9. Storage and its costs

- **On the phone** (#419 §4):
  - the credential, its blinded blocks and salts, and the DBI credential;
  - the status index, and **the whole status list** (§5.3);
  - the issuer's key log, which grows by one event per credential the state issues (§5.1).
- **Status list size.** With 2^24 entries, the list is 2 MiB raw per epoch, downloaded whole by every holder and every VTA. The plan does not discuss compression. For comparison, the IETF Token Status List draft reports about 13.7 KB compressed for 1 M entries at 1% revoked. <https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/>
- **B-batch size.** With the plan's estimated proof sizes (0.7–1.3 MB), a batch of 50 is about 35–65 MB. The plan should state a batch size, a purge rule for spent items, and the backup decision (KH-P7).
- **Known batch downsides:**
  - refill timing reveals usage to whoever serves the refill;
  - unspent copies stay valid until `validUntil` after a revocation;
  - reusing a copy links the two presentations;
  - per the Token Status List draft (§13.2), revoking a whole batch can reveal that its members belong together.

### N10. An inconsistency to resolve

§3's table says the state "Signs after issuance: nothing". §5.3 has the state anchor each epoch's status root in its key log, and that anchor is a signed event. The table should say "signs nothing per credential; signs a status-root anchor per epoch".

## Part 3 — A short proving ladder, verifier side included

Each rung is a small experiment under `tsp-reference/`, numbered when added. Each one's result is recorded in a dated companion before the phase it de-risks starts. Each takes days, not weeks.

| Rung | Proves | Done when | De-risks |
|---|---|---|---|
| **D0 Stock prover on phones** (`ref-dbi-phone-prove`) | The stock mdoc circuit runs inside a React Native app | A minimal native module, built from the Multipaz shim or ISRG's crate, proves a test mdoc on a mid-range Android, a low-end Android (under 4 GB RAM) and an iPhone, off the JS thread. Time, peak memory, binary size, circuit load time and repeated-run thermal behaviour are recorded per device | Phase 4's start condition (N5) |
| **D1 Server prove and round trip** (`ref-dbi-vta-prove`) | A VTA-class host proves within a wallet's time budget | The same proof on a 2-vCPU VM. Time, memory, two concurrent proofs, and the full phone → mediator → VM → phone round trip are recorded, and compared with OpenID4VP and DC API timeouts | Phase 3 sizing, N3 |
| **D2 VTA signing frame** (`ref-dbi-vta-sign`) | Whether VTA-made signatures verify as plain ES256 | A `keys/sign` P-256 signature over a test payload fails a plain ES256 check and passes over `opaque_signing_input(payload)`. The upstream ask is drafted from the result | N2 |
| **D3 Present to a verifier** (`ref-dbi-present`) | Keyring can present by QR to a real verifier, and the verifier refuses what it should | With OpenID4VC registered in a test build: a QR request from Longfellow's `verifier-service` is answered with a stock-circuit proof and **accepted**. The verifier **refuses** each of: a replayed session transcript, a circuit hash outside its list, an issuer key outside its trust configuration, a tampered proof, and an expired or stale status | Phase 1's pilot verifier, N7 |
| **D4 Custom circuit time-box** (`ref-dbi-circuit`) | The custom circuit's real cost against the estimate | One disclosed attribute from a keripy-generated, Utah-style fixture, proved and verified on the Phase 0 host. Time, memory and proof size are recorded against BAM-07 XIII.3's estimate. A fixed time-box is set in advance, and stopping at it is a valid result | G0 |
| **D5 Status list cost** (`ref-dbi-status`) | The whole-list download is affordable on a phone | A 2^24-entry list at a realistic revocation rate is built, compressed and timed for download and leaf lookup on a phone over cellular, per epoch | §5.3, N9 |

D0 and D3 are the two rungs that touch devices or a live verifier. D2 needs only the local VTI stack. D4 and D5 run on a workstation.

## Part 4 — What fits this repo's environment

1. **Measure before choosing where to prove.** The industry model is proving on the phone (Google Wallet, the EU age-verification app). The stock circuit is shown feasible on mid-range Android (N5). Run D0 and D1, then decide. A reasonable outcome is "phone by default, VTA opt-in for weak devices, with the device key always on the phone".
2. **Package an existing prover; don't write a prover binding of our own.** Multipaz's shim and ISRG's uniffi bindings are the shortest paths. A JSI wrapper follows the `askar-react-native` precedent already in the dependency tree.
3. **Treat the custom circuit as the main risk.** It, not the prover's location, drives cost (N5, N6). Keep D4 time-boxed, and keep the audit gate.
4. **Fix the presentation channel first.** Registering OpenID4VC and completing a plain presentation (N7) is needed whatever happens to the circuit, and it is testable now.
5. **Keep the VTA's role explicit.** If the VTA proves, the holder-controlled requirement (Q12), the audit-log linkage (N4) and the signing frame (N2) are blockers, not details.
