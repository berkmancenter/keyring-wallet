## Part I — Context: KERI on Keyring

*This part is background, not a decision. It is the survey that preceded the DBI discussion.*

**What the repo had.** No KERI, ACDC, did:webs, keripy or signify code or docs anywhere in the repo or in the pinned `external/` OpenVTC and VTI docs. The only "CESR" in the tree is TSP wire framing from `@openvtc/vti-tsp-js`, which is not a general KERI or ACDC parser. Blake3 is absent. Ed25519 is available through Askar and `@noble/curves`.

**Resolver seams.** DID resolvers are registered in two lists (`app/src/utils/bc-agent-modules.ts`, `bifold/packages/core/src/utils/agent.ts`); a did:webs resolver would be appended to both. `createVrcDocumentLoader` hand-resolves DIDs for JSON-LD and would need handling too. The Trust Tasks did-management conventions already name did:webs as a planned hosted method.

**Hermes constraints.** Fatal `TextDecoder`, `String.prototype.isWellFormed`, Node `fs`/`Buffer` assumptions, and ESM-only `exports` have each broken a library in this tree before (`vendor/README.md`, the `@scure/base` patch). Any KERI library has to clear them.

**What KERI would add to the VTA/VTC work.** The vetting and community work has no organization identity (communities are bare DIDs; the only identity evidence is a person's `name.legal` claim), only an ACL admin grant for delegation, and vetting revocation by notifying the VTC. vLEI-style legal-entity and role credentials, KERI delegation, and registry-anchored revocation fit those gaps. The plan calls this a later layer over the same did:webs verifier, not part of DBI.

**Research limits.** The did:webs specification site, the WebOfTrust `did-webs-resolver` repository, and weboftrust.org returned 404 or 403. The brief on did:webs resolution (fetch `did.json` and `keri.cesr`, replay the key log, regenerate the DID document, compare) is **[unverified]**, from memory. The December 2025 ToIP meeting notes did confirm the did:webs semantics are still moving (for example, when a did:web may appear in `alsoKnownAs`), so did:webs and ACDC are treated as active drafts. No verified production TypeScript or Rust did:webs resolver was found. Whether signify-ts runs under Hermes is **[unverified]**.

## Part II — Decisions

### D1. The VTA is the holder's agent, not a KERI delegate — **adopted**

*Rejected:* the state delegates issuance to the VTA through a KERI delegation event.

A KERI delegation is anchored in the delegator's key log. The state would see every delegate, which defeats the proposal's stated benefit that "the issuer has no knowledge of re-issuance, preventing collusion with verifiers."

*Also rejected:* the holder's identifier delegates to the VTA. It is a real delegation, but it puts an event in the holder's key log that a verifier following the chain would see, and it adds a KERI identifier lifecycle for the VTA with no benefit the plan needs.

*Adopted:* the DBI credential's rules bind re-issuance to the holder's key; the VTA is that key's custodian. This is how Keyring's VTA already behaves for persona keys, and how the Signify/KERIA model works (an agent holds keys, the controller remains the holder). The cost is that the proposal's wording ("delegates to the holder's VTA") has to be adjusted for the working group. The user confirmed that the VTA should be under each individual holder's control.

> **Superseded in part (Part VIII, M5).** The rejection of KERI delegation and the holder-controlled VTA stand. The two precedents cited for VTA custody of the holder key do not. (1) Signify/KERIA is the opposite model: Signify signs at the edge, the hosted KERIA agent never holds the controller's keys, and the KERIA agent's own AID is *delegated from the client AID*, which is the "holder's identifier delegates to the VTA" option rejected above. (2) Keyring's `vtaKeys.ts` *exports* VTA-held Ed25519 and X25519 keys to the phone (`keys/export-secret/0.1`, `type Curve = 'Ed25519' | 'X25519'`); it is not VTA-side custody or signing of a P-256 holder key. VTA-side P-256 holder-key signing is a new seam, and whether the VTA should hold that key at all is plan §11 Q15. The reasoning above is kept as written because the next reader will reach for the same two precedents.

### D2. ACDC bulk issuance is a fallback, not the answer — **adopted**

Verified against the ACDC specification's bulk-issuance section (tswg-acdc-specification f0bd097, about lines 2765–2835; Part IV above): unique blinding values give each copy a unique SAID, and the registry commits only to blinded digests `b_k = H(v_k + d_k)` aggregated as `B = H(C(b_k))`. An earlier version of this section described that mechanism from memory; the verified reading agrees with it on the mechanism and corrects its limits:

- It hides linkage between copies from third parties, with no zero-knowledge proof. It does **not** make colluding verifiers unable to correlate: they can still match on disclosed field values (the specification relies on contractual chain-link confidentiality, about line 2781), and a top-level registry identifier is a correlation point unless the nested option is used (about line 2779).
- It does **not** address issuer-verifier collusion, and the specification makes that structural: issuer and issuee share one salt, and every blinding value is derived from it by path (about lines 2789–2815), so the issuer sees all copies.
- Salt delivery is defined only for Ed25519 and X25519 identifiers (about line 2791); nothing covers P-256 identifiers.
- It requires one hash algorithm for every member and defaults to Blake3-256 unless negotiated out of band (about line 2818).
- It does **not** relieve the issuer. The state still issues the whole batch, and again when it runs out. DBI's stated benefits include reduced load on primary issuers and multi-device issuance without the issuer.

Kept as a comparison point and as an open question (plan §11 Q5): whether the state could bulk-issue blinded DBI credentials.

### D3. The primary is signed with P-256 — **decided by the user; CESR and keripy support verified, did:webs representation a gap**

The user decided to assume that the state's primary credential is signed with ECDSA P-256 and uses a SHA-256-family digest code. The plan states that as current design; the reasoning is here.

Longfellow's shipped circuit verifies ECDSA P-256 signatures and SHA-256 hashing; its field is the P-256 scalar field (or GF(2^128)), so P-256 arithmetic is native and cheap. An Ed25519 circuit needs 2^255-19 arithmetic emulated in a different field plus SHA-512, which is 64-bit-word work that is costly in this system. The research found no Ed25519 circuit. The cost comparison is the research's inference **[unverified]**: several times P-256, with no benchmark.

KERI's default is Ed25519, but CESR defines P-256 codes and keripy signs and verifies on P-256 (verified; Part IV). Government HSMs commonly support P-256 **[unverified]**. The verification also found what stands in the way: the did:webs reference resolver cannot represent a P-256 key, signify-ts cannot sign P-256, and P-256 with witnesses or delegation is unproven. The plan carries those as Phase 2 work and open questions.

Keyring's own credentials stay Ed25519; DBI touches none of them. The VTA's secondary-signing keys and holder-binding keys are P-256 (the hardware keys in `bifold/packages/core/src/hardware-signing/key.ts` are EC P-256), which is also what mdoc and ES256 verifiers expect.

**Contingency, non-default: a custom Ed25519 circuit.** If P-256 turns out unavailable in the state's signing infrastructure or in the verification stack (the did:webs resolver gap, if upstream refuses it, does not trigger this: it is solvable in our own resolver), the fallback is a custom circuit for the DBI statement with in-circuit Ed25519 verification (emulated field arithmetic, SHA-512). The circuit compiler means this is possible but real engineering, not configuration; it is unbenchmarked and expected to be several times the stock circuit's cost **[unverified]**. It is not planned work. It is recorded here so that the next implementer who hits an Ed25519-only issuer knows the option exists and what it costs. If it is ever started it needs its own plan section and a dated companion.

> **Superseded (D13; reconciled in Part VIII).** The custom Ed25519 circuit is no longer *the* fallback: D13 ranks a zkVM guest first and the custom Longfellow circuit second, and the plan's §3 carries that order. The parenthetical above ("the did:webs resolver gap, if upstream refuses it, does not trigger this") and the earlier kill criterion that listed a did:webs rejection as a trigger disagreed. The reconciled position, now in the plan's kill criteria: a did:webs rejection alone does not trigger a revisit, because the EC representation lives in our verifier; it triggers one only if verifiers the pilot needs also refuse our representation.

> **Correction (Part XII, 2026-10-08).** "The plan's §3 carries that order" used the pre-restructure numbering. After Part IX's cleanup the order lived in §5.1 (the kill criteria and fallbacks; the Part IX numbering map sends old §3 to §5.1), not in the plan's §3, which holds the architecture. It no longer lives anywhere in the plan: D15 (Part XI) replaced it, and §5.1 now states the zkVM measurement. The text above is kept as written.

### D4. SHA-256-family digest codes, not Blake3 — **adopted**

KERI's SAIDs commonly use Blake3, which is absent from the repo, and a hash inside a zero-knowledge circuit is the expensive part. SHA-256 is native to Longfellow's circuit and is what SD-JWT and mdoc already use. The ask to the state is SHA2-256 (`I`) for every SAID digest. keripy supports it (DigDex.SHA2_256; `test_coring.py` about line 6087), and the ACDC specification requires only a digest of at least 128 bits whose code identifies the algorithm. It is off-default, though: Blake3-256 is the ACDC default, the specification's own examples use it, and stock tooling expects `E`. The SHA2-256 choice is therefore a negotiated, governed profile for Utah, not something the ecosystem gives us. A general did:webs verifier still needs Blake3 for other issuers' logs (Phase 2); the state's own log and credentials do not.

> **Corrected (Part VIII, evidence).** "The ACDC specification requires only a digest of at least 128 bits" overstates the source: ACDC v1.1 states the 128-bit requirement for *Schema* SAIDs. The adopted SHA2-256 profile is unaffected (SHA2-256 meets it either way). The plan now quotes the sentence as written, and Phase 0 checks whether it covers every SAID kind. The same correction applies to the Part IV table row that repeats it.

### D5. BBS cannot link to a KERI-signed primary — **adopted**

BBS gives tiny, fast proofs and an unlinkable signature, but the *issuer* must sign with BBS (pairings, BLS12-381). A KERI-signed primary is not a BBS signature. BBS is therefore kept for credentials the VTA itself issues, which matches the repo's existing decision (`docs/CRYPTO_SUITE_FOLLOWUP.md` Decisions 10–13: `eddsa-jcs-2022` plus `bbs-2023`). The research also notes the Longfellow authors rule out the BBS family where device binding and legacy support matter (IETF 126 slides). BBS# has a device-binding variant **[unverified, secondary source]**. It is not post-quantum.

### D6. Alternatives considered for the linkage proof

| Option | Disposition | Reason |
|---|---|---|
| **Longfellow (mdoc-zk)** | Adopted as target | Transparent (no trusted setup); relies only on SHA-256 collision resistance; post-quantum; shipped circuit already covers the P-256 + SHA-256 + device-binding shape; Apache-2.0 with Android and iOS builds; deployed in Google Wallet age proofs |
| **Vega** (Berkeley / Microsoft Research, May 2026) | Tracked, not adopted | Transparent, and the paper reports 92 ms proving and 108 kB proofs (16 threads, Azure VM) against Longfellow's larger proofs, but it is not post-quantum, its code is research-grade, and the Longfellow authors dispute its extraction soundness for P-256 (the sources conflict; neither claim was independently checked) |
| **Crescent / Groth16-style SNARKs** | Rejected | Per-circuit trusted setup |
| **SD-JWT alone** | Rejected | Salted-hash digests link secondaries unless each is freshly issued; the EU ARF itself says salted-hash linkability is only mitigable with zero-knowledge proofs |
| **BBS / BBS#** | See D5 | |
| **WASM or JavaScript prover** | Rejected | Memory, SIMD and threading make a pure-JS or WASM prover unlikely to be viable on Hermes; a C++ library with a C ABI (`mdoc_zk.h`) and Android and iOS builds fits a JSI or TurboModule wrapper. No React Native wrapper exists, and the cost is the native build toolchain, a circuit of about 1 MB, and proving memory of 100–200 MB (secondary sources, **[unverified]**) |

### D7. Short validity by default, stapled status optional — **adopted**

Per-secondary status checks against the primary would correlate secondaries. Three options were weighed:

- **Short validity.** Secondaries live hours to days; revoking the DBI credential stops renewal. Fits DBI's ephemeral-credential benefit and upstream DTG's preference for expiry over revocation (delegation note). Cost: a window in which a revoked primary still backs live secondaries. A KERI purist may find that window uncomfortable, so the plan states it as a trade-off.
- **Stapled status.** The holder presents a recent signed "not revoked at time t" receipt, in KERI terms a registry entry with witness receipts. To be unlinkable it needs its own zero-knowledge proof; otherwise it identifies the credential. Kept as optional for high-assurance verifiers.
- **Tiers by use.** An age check tolerates a long window; a high-assurance action can require a staple. The tiers per Utah use class are not decided and are Utah's to answer (plan §11 Q2).

> **Superseded in part (Part VIII, R).** Short validity stays as the base mechanism. Stapled status is dropped in favour of an in-proof status epoch, and the plan's §7 "Revocation and freshness" replaces the old §7 "Freshness". The upstream-delegation agreement cited above is withdrawn as worded (Part VIII, M8).

### D8. Resolving verifiable-chain versus unlinkability — **adopted**

KERI's value is a visible chain of authority; DBI's goal is that verifiers cannot correlate secondaries. These conflict if every secondary shows the same chain, digest or salt. The resolution (plan §6) is **provable, not shown**: fresh salts and keys per secondary, and a zero-knowledge proof of the derivation. A verifier may ask for the full chain; the holder may decline. The weak point is that the proof for this exact statement is not an existing circuit, which the plan carries as Q3.

A related alignment trap was weighed: if the state used SHA-256 digests for its SAIDs, the secondary's SD-JWT digests could literally equal the primary's blinded attribute digests. That would be tidy and would link every secondary to the primary. It is the thing to avoid; the proof must relate re-salted commitments instead.

### D9. DBI is a compartmentalized interface with injected key state — **adopted**

The interface is `derive` and `verifyLinkage`; backends plug in behind it; a did:webs verifier supplies key state. Reasons: the phases can ship in order (Phase 1 needs no KERI code at all), the proof system can change without touching callers, and the KERI-specific machinery stays in one module a KERI reviewer can audit. The alternative of building DBI inside the VRC module was rejected because DBI is not a relationship credential, and the platform-neutral pattern of `@bifold/trust-tasks` is the better precedent.

### D10. The primary need not be an ACDC — **adopted, as a constraint on Utah**

"KERI-rooted but format-pluggable": the state's did:webs publishes the issuer key, and the credential could be an ACDC, an SD-JWT VC or an mdoc. Requiring ACDC would add a format Keyring cannot yet verify and that no mobile verifier consumes. The primary's signature (P-256, D3) is fixed independently of its format.

### D11. The proof takes blinded blocks as private witness — **adopted, correcting an earlier sketch**

The first sketch of the DBI circuit recomputed the per-attribute digests "from the SAID". The verification showed that cannot work: each block SAID is a digest over that block together with its own salt, the top-level SAID does not decompose into per-block digests, and no salt `u` is recoverable from a SAID. The circuit therefore takes the blinded blocks and their salts as private witness and recomputes each block SAID and the top-level digest from them. The consequence is that the proof's subset check is block-granular, so the state's schema must make each separately-disclosable claim its own blinded block (plan §11 Q8).

> **Refined (Part VIII, M1).** The block-granular witness stands. The rest of the sketch understated the statement: an ACDC is not signed directly. The state signs a KEL event that anchors the ACDC (or a TEL event naming it), and every SAID is a digest over a serialization with the `d` field filled with `#` placeholders. So the circuit parses three to four serializations and recomputes placeholder SAIDs; it does not check "a signature over the top-level digest". The plan's §8 states the exact chain.

### D12. Is P-256 still the best option? — **refines D3; supersedes nothing**

The user asked whether P-256 is still the best option after the verification in Part IV found the did:webs resolver gap and the unproven witness and delegation behaviour. The conclusion is that it is, as a default with explicit gates, not as an assumption. The plan now carries gates G1 and G2 and the kill criteria (plan §11, §12 Phase 0).

**The asymmetry.**

| | P-256 primary | Ed25519 primary |
|---|---|---|
| What it costs | Bounded ecosystem friction, concentrated in components we write or control: a did:webs resolver extension (our verifier emits `EC`/`P-256` verification methods), a keripy or HSM signer, a negotiated SHA2-256 SAID profile, and fixtures for witnesses and delegation that are unproven today | An unbenchmarked custom circuit with emulated 2^255-19 field arithmetic and SHA-512 in the hardest part of the design (the zero-knowledge proof) |
| Who carries the risk | Our verifier and Utah's governance; failures show up in fixtures and at gates | The proof system, on a codebase whose August 2025 Trail of Bits review found 13 issues, 2 of them high, in the *shipped* circuits; a new circuit would be unaudited |
| Reversibility | High: each cost is a test or a negotiation, and the interface (plan §5) is unaffected | Low: a new circuit is a large engineering and review commitment |

The P-256 costs are known, bounded, and mostly solvable by us. The Ed25519 cost is unknown and sits where a mistake is a soundness failure, not an interoperability annoyance.

**The unchecked assumption.** Utah's signing infrastructure. Government HSMs and the mdoc ecosystem generally use P-256, but that is **[unverified]** for Utah specifically. G1 exists to check exactly this.

**What would flip the decision.** The kill criteria, now in plan §11: Utah cannot sign P-256; the did:webs authors reject P-256 verification methods; P-256 fails with witnesses or delegation in G2; a benchmarked cheaper Ed25519 circuit appears upstream. Any one reopens the choice between the custom Ed25519 circuit (D3's contingency) and the variant below.

**The speculative variant: an anchored credential key.** The state's identifier keeps Ed25519 control keys, and a separate P-256 key signs credentials, with the key log anchoring that key by a seal. It is attractive because it would keep the log on KERI's default curve and confine P-256 to credential signing. It is not adopted because: it is **not verified** that KERI or did:webs defines such an arrangement; it adds a verification step (check the anchor, then the credential signature); and it departs from standard ACDC practice, where the issuer's key state signs the credential. It also does not remove the circuit question, since the proof still verifies a P-256 signature. It goes to the did:webs and KERI authors as plan §11 Q9, marked not decided.

### D13. Ed25519 zero-knowledge landscape and server-side proving — **refines D12; supersedes the earlier "custom Ed25519 circuit" fallback ordering**

The user approved a Phase 0 benchmark and asked that the Ed25519-in-zero-knowledge research and a server-side proving analysis be folded in. The research was partial: several primary sources returned 403 or 404, and the unverified items are listed below.

**Ed25519 in zero knowledge.** Longfellow has ECDSA P-256 and SHA-256 only. `draft-google-cfrg-libzk-03` has no Ed25519 or SHA-512 in the first 100k of its 167k characters (the rest unread); no roadmap or fork was found, but the repository's issues and pull requests and the CFRG list were not read, so "no plan" is **[unverified]**.

| System | What the research found | Status |
|---|---|---|
| Vega | P-256 only; code release unconfirmed; Hyrax-based, not post-quantum | no Ed25519 |
| Crescent | Groth16, per-circuit trusted setup; Ed25519 unconfirmed | trusted setup |
| OpenAC / zkID (PSE) | targets EU formats, probably ECDSA; signature support unconfirmed | **[unverified]** |
| Plonky2 (`plonky2-ed25519`) | about 171k gates, about 31 s CPU (search snippets) | **[unverified]** |
| Halo2 (Axiom) | EdDSA about 6.4–9.9 s to prove; KZG setup | trusted setup |
| Noir (`noir-ed25519`) | "fairly expensive"; trusted SRS; unaudited | trusted setup |
| SP1 / RISC Zero | SP1 has an Ed25519 precompile and RISC Zero a patched `curve25519-dalek`; **no published Ed25519 cycle counts found** | witness zero-knowledge **[unverified]**: a hard blocker to check |

Zero-knowledge virtual machine proofs are large (hundreds of kilobytes to megabytes; a Groth16 wrap is about 260 bytes but needs a trusted setup) and proving needs several gigabytes of memory. No ACDC or KERI zero-knowledge circuit work, and no SAID circuit, was found. No transparent, zero-knowledge, production-grade, off-the-shelf Ed25519 option is confirmed. The most pragmatic Ed25519 fallback is a zkVM guest (`ed25519-dalek` and `sha2`), contingent on confirming that the prover hides the witness (SP1's zero-knowledge property is unconfirmed; RISC Zero's STARK is zero-knowledge but unconfirmed here). The verifier ecosystem favors Longfellow (Google Wallet, the EU age-verification blueprint, Multipaz); that last point is my reasoning, not a finding from the sources.

**Why a zkVM guest outranks a custom Longfellow circuit as the fallback.** A custom Ed25519 circuit is hand-built arithmetic with emulated field operations and SHA-512 inside a proof system that, in its shipped circuits, had 13 review findings (D12). A zkVM guest is ordinary Rust running an audited-in-the-wild Ed25519 library, so authoring risk is far lower; its costs are operational (proof size, memory) and the unconfirmed zero-knowledge property, and verifiers would need to accept a proof system they do not use today. The ordering is conditional on confirming witness zero-knowledge and verifier support (plan §3).

**Server-side proving (VTA).** The only measured data point is the Vega paper's baseline of the Longfellow reference implementation on an Azure F16as v7 (16 vCPU, 64 GB): for a 1920-byte mDL MSO with an age check and a device signature, single-thread prove 501 ms, verify 244 ms, proof 325 kB, and a one-time circuit load of 5.59 s. Multi-thread scaling is unclear, there is no precompute phase, and a Rust prover under 100 MB is claimed but **[unverified]**.

> **Correction (Part XIII, 2026-10-08).** Both are now answered for the pinned builds. Neither prover is multi-threaded (process CPU 99% in every unpinned run), so "multi-thread scaling is unclear" becomes "there is none": a second core runs a second proof, not a faster one. The Rust prover under 100 MB is not supported by ISRG's `zk-cred-longfellow` `59709c4`: 555 to 1009 MiB measured (verifier alone 555, prover alone 757, prove and verify in one process 1009; XIII.2). The 0.5 to 1 s mdoc-sized figure was close for C++ (0.71 s, XIII.2); the Rust crate took 1.50 s. The text above is kept as written.

Estimates for a 2-vCPU container, all **inference, unmeasured**: about 0.5–1 s for an mdoc-sized statement and low single-digit seconds for ours, since the DBI statement hashes every blinded block with its salt and cost scales with block count; about 2 concurrent proofs; a 50-proof batch in about 1–3 minutes; verify about 0.25 s; memory budgeted at 2–3 times the claimed figure. Caveats: a vCPU may be a hyperthread or a burstable allocation subject to throttling; the build's CPU-feature requirements are unknown; the block count of a real Utah credential is unknown; and batch proving is background work that does not block the holder.

Bindings are a C interface (`mdoc_zk.h`), a Rust crate and a Python binding. For a Node VTA the options are a Rust or C++ sidecar, a subprocess, or an N-API addon; WASM is **[unverified]**. Offline pre-generation of a batch is possible only if the statement binds no verifier nonce, which is a design question (plan §11 Q10). On privacy, the VTA sees the primary credential, its salts and the holder key while proving. That is acceptable because the VTA is holder-controlled; a provider-hosted VTA would see the full primary credential. Trusted execution environments were not researched and matter only for the hosted case.

**Why server-side first.** The only measured number is on a server; the phone-side prover carries Hermes and React Native memory risk and has no existing wrapper; and the VTA already custodies the holder's keys. Phone-side becomes Phase 3b, optional and later.

> **Corrected (Part VIII, M5).** "The VTA already custodies the holder's keys" is not true of a P-256 holder key: Keyring's VTA path exports Ed25519 and X25519 keys to the phone and holds no P-256 holder key. Server-side-first still stands on the other two reasons, and on the holder key reaching the prover as signatures rather than as a private key if plan §11 Q15 picks device-side custody.

## Part III — What the research verified, and what it did not

**Longfellow, verified against sources read.** Per the repo README, `draft-google-cfrg-libzk-03` (IETF CFRG Informational, September 2026), the IETF 126 slides (July 2026), a W3C community list post by Frigo, and the Vega paper:

- Transparent argument system (sumcheck plus Ligero); hardness assumption SHA-256 collision resistance; at least 115-bit security; proofs are post-quantum.
- Shipped circuit is mdoc-zk: issuer P-256 signature over the MSO hash, SHA-256 (about 36 permutations), device P-256 signature (device binding), attribute equality. Parameters: about 2 KB MSO, up to 3 attributes in that configuration, roughly 30 ms per extra attribute.
- IETF 126 slides: ECDSA proof-of-possession proves in 16.7–38 ms and verifies in 10–23 ms on an M4 Mac, "close to BBS."
- Apache-2.0; C++ core with Rust bindings and a Rust rewrite; builds for Linux, macOS, Android and iOS; C interface; compact circuit format about 1 MB against about 100 MB for the first format.
- Independent review: Trail of Bits, August 2025, 13 issues, 2 high (circuit ID not checked at deserialization; an mdoc attribute check bypass). Panel reviews are mentioned in the README; the reports were not read.
- Deployment: Google Wallet age proofs on ISO 18013-7 mdocs; the EU age-verification blueprint lists it as experimental; Multipaz and wwWallet use it; ISRG has a second bit-compatible implementation.

**Not verified:**

- Proof size and mobile timings. The Vega comparison table cell is garbled in text extraction (about 200 kB **[unverified]**); mdoc-zk proofs of 250–350 kB and sub-second proving on phones are from memory **[unverified]**. - The did:webs resolution flow: the specification text is still unread (Part IV).

- Utah's actual constraints. The proposal was read through a condensed summary only.

- Per-attribute digests cannot be reproduced from a SAID (D11).

## Part VI — The organizational use case (notes, not part of the DBI plan)

*Context from the same session, kept here and deliberately out of the plan. The DBI plan does not depend on any of it. It records how KERI and vLEI-style organization identity could layer on the VTA, VTC and vetting work, so the analysis is not lost.*

**Gaps today.** From the survey of `docs/plans/keyring-on-the-vta-farm/` and the pinned upstream docs:

- No organization legal identity. Communities are bare DIDs, and the only identity evidence is a person's self-asserted `name.legal` claim inside a vetting card. The Farm console's passkey login is the real operator authority and sits outside the DID model.
- Delegation is only the ACL admin grant. No scoped, revocable delegation credential exists yet.
- Vetting statements are revoked by notifying the VTC only. Status lists for statements usable beyond their own community are V1 upstream (`external/openvtc/docs/design/vetting-process.md`).
- One persona per community by design, so there is no cross-community recognition.
- Key recovery after a lost phone has no backup-owner design; persona-key rotation through the VTA exists (`vtaRotation.ts`).

**Layering, in order of cost.**

1. **Verified community and operator identity.** The join manifest or community card shows "operated by [legal entity], vLEI-verified." The VTC's did:webvh links to an organization's did:webs, either by alias or by an ACDC the controller signs, and the wallet verifies the chain before the user submits anything. This is display and trust, not protocol, so it needs no upstream schema change.
2. **KERI evidence as a vetting method.** A community requirement carries `acceptedMethods`, `requiredClaims`, `eligibleVetters` and `independence`. "Holds an LEI or vLEI credential" could be a new accepted method, with the presentation riding in `join-requests/submit`, and the VTC's `join.rego` policy deciding. `vettingShape.ts` and `vettingSchemas.ts` validate against bundled schemas, so this needs upstream schema changes.
3. **Organization members.** Legal entity, then role, then person, as a checkable chain, in place of the self-asserted `name.legal`.
4. **Delegation.** A community appoints its VTA, or an organization appoints a witness or vetter. The design note `external/dtgwg-cred-spec/design-notes/delegation-design-time-window.md` has a worked example of the community appointing its VTA. Upstream prefers short-lived, single-hop delegation with non-renewal as revocation; vLEI chains lean on registries and status. This is a real design conflict.
5. **TRQP trust registry.** The VTC mirrors its roster to a TRQP registry (`registry/record/put`), but nothing in Keyring queries one. A verified organization is a natural thing for a registry query to return.

**Conflicts with upstream.** Upstream churns weekly. Trust Tasks use a clean cutover with no dual-accept, where Keyring's policy is to accept versions N and N-1. Vetting revocation is moving to VTA-hosted status lists, which an ACDC registry would duplicate unless Keyring only verifies KERI credentials issued by others. The selective-disclosure direction is `bbs-2023` with JCS; SAID-based blinding is an acknowledged alternative upstream has not adopted. Upstream has no KERI work today: the only mentions are the cred-spec intro (future versions "may generalize to other VID types (such as X.509 certificates or KERI AIDs)") and the did-management conventions' planned did:webs.

**Recommendation.**

- **Verify-only first:** verified operators (item 1) and organization roles (item 3). Neither needs an upstream change.
- **Raise upstream before any code:** the vetting-method extension (item 2) and delegation (item 4), because they touch schemas and delegation semantics upstream owns.
- **Record it as an open question** in `docs/VTI_UPSTREAM_FINDINGS.md`, following the `vti-lab-and-field` skill's rules for what earns a finding. That file was not edited in this session.
- All of this shares one dependency with DBI: a did:webs verifier module (DBI plan Phase 2).

### Revocation design rationale (plan §7)

**The constraint.** Secondaries are unlinkable and ephemeral, so anything a verifier does per secondary that reaches a third party is a correlation channel. The DTG Credentials Specification Working Draft 0.6 states the same cost for its own delegation credential: "a status check is a live lookup that reveals the verification event to whoever hosts the status list" (VDC, `credentialStatus`), and "Herd privacy over the list's contents does not touch the fetch itself" (Privacy Considerations, status lookups). That is evidence that the ecosystem recognizes the cost, not a requirement on DBI.

**Adopted.** No per-secondary revocation. Revocation is refusal to renew, enforced at an honest VTA by a derivation-time status check and, against a dishonest one, by a status epoch the proof must carry. Validity is bounded inside the proof, so a revoked holder's last secondaries die within `maxWindow`. The status structure is fetched whole. Assurance tiers set how recent an epoch a verifier demands.

**Rejected alternatives, with the reason each fails:**

- **Per-secondary status checks** (a status-list index or identifier in each secondary). Each secondary would need its own index, or would share one. A shared index links all secondaries. Distinct indices tell the list host, who is the state, which verifier checked when; and the state would have to allocate an index per secondary, which reveals re-issuance volume to it.
- **Stapled per-credential receipts** (D7's optional tier, now superseded). A receipt needs its own zero-knowledge proof to avoid identifying the credential, and fetching it tells the receipt's issuer when each holder refreshes: a timing channel per holder. The status epoch gives the same guarantee with a whole-structure fetch and no per-holder request.
- **OCSP-style online checks by the verifier.** A live lookup per verification, which is the correlation the constraint rules out. It also couples every verification to the state's availability: a verifier that fails open accepts revoked credentials during an outage, and one that fails closed turns the outage into a denial of service. The DTG text's revocation-latency consideration names the same trade for its own delegations.
- **Short validity alone.** Kept as the low-assurance tier and as Q17's fallback. It is rejected as the sole mechanism because it is enforceable only against an honest VTA: a compromised VTA, or a holder running modified software, keeps deriving after revocation. Even with C2's bound, that runs until the DBI credential expires, which is weeks.
- **A per-credential blinded TEL as the proof's status source.** ACDC's blinded state registry is per credential, is unblinded interactively by the discloser, and advances its blind with every event (evidence above). Proving in zero knowledge that a given TEL event is the *latest* one needs the TEL head, which is per credential, so learning or fetching it is a correlation point. The state's TEL can still be the authoritative record from which it builds the published structure; Q18 asks whether ACDC offers anything better.
- **An allow-list (membership in a set of valid credentials) instead of a deny-list.** It was considered as the epoch structure, because membership proofs are simpler than non-membership proofs. It was set aside as the candidate because an allow-list covers every credential, so a holder must either fetch its own path (a per-holder query) or download a structure sized to the population. A deny-list of revoked credentials is expected to be small enough to download whole. The sizes are an estimate **[unverified]**, and Q18 may reverse this.

> **Superseded (Part IX, IX.4).** The candidate structure is no longer a sorted Merkle deny-list over revocation tags. The plan adopts a Merkleized bitstring indexed by a `statusIdx` the primary carries, pending the Phase 0 benchmark, with signed spans as the benchmarked alternative. The rejection of per-secondary checks, stapled receipts, OCSP-style checks, short validity alone and a per-credential TEL stands; the allow-list versus deny-list reasoning above is moot because a bitstring covers every index at a fixed size the holder downloads whole.

**Trade-offs accepted.** The status epoch is a public input, so it partitions holders by when they derived (M10). Coarse epochs bound that, at the cost of revocation latency. A high-assurance verifier's epoch window also limits how far ahead a batch can be proved, which pulls against offline batch pre-generation (Q10). The forgery window after a state key compromise remains unless Q19 picks the key-state commitment.

### IX.1 The architectural gate — Path A or Path B — **applied as an undecided gate (plan §3, Q1, G0); superseded by D14 (Part X)**

> **Superseded (Part X, D14).** The gate is closed: the state's primary is an ACDC, so Path A ("preferred if Utah accepts it" below) and the "Path A first" recommendation are rejected and B-direct is the target. The analysis below is kept as written; Part X.4 restates it with the KERI-principle table.

**Finding.** Longfellow's mdoc verifier takes the issuer public key as a *public* input checked against a trusted-issuer list, and hides the issuer signature, the MSO and the device key: `run_mdoc_verifier(circuit, pkx, pky, transcript, attrs, now, zkproof, docType, zk_spec)`. Its documentation says the issuer key is "currently provided as input, later one among a list of issuers" and that issuer lists are "trusted inputs". A fresh proof per presentation is therefore already unlinkable, and the VTA-signed ephemeral-key secondary is largely a carrier: verifier trust comes from the proof, while the signed secondary adds batch-timing and reuse linkage.

**Evidence on the format verifiers.** Standard ISO 18013-5 readers need a DS certificate chaining to an IACA (VICAL or a trust list) and reject ephemeral keys. SD-JWT VC verifiers accept an issuer only through an `x5c` chain or https `jwt-vc-issuer` metadata (draft-ietf-oauth-sd-jwt-vc); HAIP 1.0 requires the issuer certificate and chain in `x5c`, not self-signed. Ephemeral issuer keys are accepted nowhere. did:web/did:webs issuers are accepted only in DID-aware stacks (Credo, walt.id; per library **[unverified]**); the EUDI stack is `x5c`-centric. These are paraphrases; the plan marks them (X5) and Phase 0 quotes the texts. Stock proofs bind the session transcript, so pre-generated nonce-free batches work only with a custom decomposition.

**Correction.** mdoc already has a zero-knowledge carriage for *registered* circuits: ISO 18013-5 second edition and the Digital Credentials API's `ZkDocument`, with verifiers pinning circuits by `ZkSpec` `circuit_hash`. Multipaz ships `multipaz-longfellow`; Google Wallet runs ZKP over mdoc; the EU age-verification blueprint publishes `zk-age-verifier` on PyPI. The earlier plan's "neither SD-JWT VC nor mdoc has a defined slot" (old §8 *Outside the proof*, old Q4) was wrong for mdoc and is **superseded**; what lacks a slot is a *custom* circuit (current Q18).

**The two paths.**

- *Path A* (preferred if Utah accepts it): the primary is a P-256 mdoc whose DS certificate chains to an IACA; the state publishes DS/IACA keys anchored in its KEL or did:webs as a KERI-rooted trust-list feed; DBI shrinks to a holder-side ZK-presentation module on the stock Longfellow circuit, run in the VTA or on the phone; works with Multipaz and Google verifiers. Estimated 6–10 person-weeks, plus a pilot verifier.
- *Path B* (only if the primary must be an ACDC): keep the custom linkage circuit and proof, drop the VTA-signed secondary, emit a Longfellow-style response under a custom `ZkSpec`; verifiers must be Keyring-aware (Google Wallet will not accept a custom circuit).
- *Format-only verifiers*: a separate linkable tier of state-issued, single-use, stable-issuer batches.

**Which benefits survive.** Unlinkability across verifiers is redundant for an mdoc primary; format conversion matters only if the primary is an ACDC; multi-device presentation only weakly (it needs a VTA- or cloud-held holder key, tying it to custody); offline batches only through a custom decomposition; revocation is not provided by stock mdoc-zk (short MSO validity and re-issue instead).

**The KERI story.** Path A changes it: the primary is no longer an ACDC, and KERI becomes the trust root for signing keys. Whether the working group and the KERI community find that harmonious is a decision for Brendan and the working group, not a technical one. The plan says so at §3.

**Phase 0 and Phase 1 additions.** A stock-circuit direct-presentation prototype against Multipaz (3–5 person-weeks, estimate) to anchor the comparison; confirming how Multipaz and Google verifiers validate the DS chain against a ZK-proven issuer key **[unverified]**; quoting the ISO 18013-5 and SD-JWT VC/HAIP texts in place of the old "not read" caveats; an interop check of plain secondaries against Credo, an EUDI verifier and walt.id (1 person-week, estimate). Phase 1 gains a pilot verifier (a verifier service holding trust configuration, triggered over the W3C Digital Credentials API or OpenID4VP; 4–8 person-weeks, estimate) naming the stock-circuit target and trust configuration; a custom circuit requires a patched verifier.

**Superseded.** The plan's former single design — every secondary VTA-signed under an ephemeral key, with the linkage proof attached — is now the *B-batch* variant of Path B, kept for offline batches and format conversion; B-direct is Path B's default.

### IX.2 Custom linkage circuit scope (Path B) — **applied (plan §3 table, §7.3, §7.4, Phase 3 Path B, audit gate)**

**Estimate and its derivation.** 40–66 person-weeks of ZK engineering: circuit and witness 25–40; fixtures and negative suite 6–10; prover/verifier sidecar and carriage 6–10; Longfellow ramp-up 3–6. Plus 6–10 weeks of external audit and about 4–6 engineer-weeks of remediation. If the primary were an SD-JWT VC or an mdoc rather than an ACDC, perhaps 25–40 person-weeks **[unverified]**. A second, independent figure for Path B was 20–40 person-weeks plus audit, not broken down.

**Inconsistency recorded.** The same scoping also said "12–18 calendar months with 3–4 people". Its own effort numbers do not support that: 40–66 person-weeks across 3–4 people is roughly 3–5 months of engineering, plus the audit. The plan therefore makes no calendar claim beyond "to be re-estimated after the Phase 0 benchmark".

**The device-signature pattern is reusable for the fresh holder key (C1).** `lib/circuits/mdoc/mdoc_signature.h` and `mdoc_zk.h`: public inputs are the issuer key (`pkx`, `pky`), `hash_tr`, `now`, attribute ids and values, and `docType`; hidden are the MSO, the issuer signature (`r`, `s`) and the device public key (`dpkx`, `dpky`), committed with MACs and extracted from the MSO by approximate CBOR parsing (`mdoc_hash.h`). Signature 2 is an ECDSA signature by the hidden device key over a public hash, `verify_signature3(dpkx, dpky, hash_tr, sig)`. So the primary's holder key stays hidden while the fresh secondary holder key is public, with `e = SHA256(fresh holder key || signing key || context)` as the signed hash. This resolves Part VIII's open doubt about the check's shape.

**What must change.** Replace the MSO CBOR hash circuit with a parser for the primary's format (no JSON parser exists in the repository); add `#`-placeholder SAID recomputation and version-string size checks; seal containment across three or four serializations; a second state signature for the DBI credential; equality of each secondary disclosure digest to the primary block value. Present already: SHA-256, P-256 ECDSA, `memcmp`, routing, CBOR parsing, comparisons (`leq`), MAC glue between GF(2^128) and Fp256, issuer-list membership up to 50 keys. Code sizes for orientation: `logic.h` 1,234 lines; ECDSA `verify_circuit.h` 371; `flatsha256_circuit.h` 330; `cbor.h` 675; `mdoc_hash.h` 554; `mdoc_zk.cc` 712.

**Formats and IDs.** A Rust rewrite exists (LFC2 format, about 1 MB circuits against about 100 MB for LFC1); its README calls it the intended production path and says "we do not ship a C++ runtime for now". `circuit_id` is the SHA-256 of the compressed circuit bytes, listed in `zk_spec.cc` `kZkSpecs` (12 entries); any gate or witness change means a new spec and hash.

> **Correction (Part XIII, 2026-10-08).** The ID is not the SHA-256 of the compressed circuit bytes. Measured against the pinned generator: `circuit_hash` is SHA-256 of the signature circuit's id concatenated with the hash circuit's id (in that order; the reverse does not match), which equals `kZkSpecs[0].circuit_hash` for spec 0. The compressed file hashes to a different value. A gate or witness change still means a new hash. Plan X3 states the correct form. The sentence above is kept as written.

**Soundness bug class.** Trail of Bits found 13 issues, 2 high, including under-constrained witness variables (a witness length used where the public length belonged) and a deserializer that did not check the circuit hash; ISRG found under-constrained CBOR indices, fixed in v0.8.4. Disposition: negative tests per *witness variable* as well as per public input, and circuit hashes verified at startup (`verify`). Both are Phase 3 acceptance criteria.

**Bindings.** A C interface exists only for mdoc-zk; a custom circuit needs a new Rust or C entry point. Google's repository has no Node binding (`pylongfellow` is a thin Python binding, depth **[unverified]**). ISRG's `abetterinternet/zk-cred-longfellow` (MPL-2.0, Rust, WASM via wasm-pack, UniFFI Kotlin/Swift) is the best lead for Node, WASM and React Native; whether it supports custom circuits or is audited is **[unverified]**. Android and iOS build scripts exist; the C++ path needs cmake, clang, openssl, zstd and gtest. Upstream documents no stable third-party circuit-authoring API.

**Fixed-size circuits.** Padding is native (`kMaxSHABlocks` 7 with `nb_` a witness index; separate circuits per attribute count). So there is one circuit ID per (schema, number of disclosed attributes, maximum block count); verifiers hold a manifest of all of them; the attribute count and circuit ID partition the anonymity set; and a larger fixed maximum always costs prover time. This refines the old "one circuit per (primary schema, secondary format)" in old §6, which is **superseded**.

### IX.3 Rate limiting — **decided: deferred (plan §5.4, Q16, §8)**

Nothing in the Longfellow repository implements PRF-nullifier or k-times-anonymous schemes. A public nullifier `H(secret, epoch)` costs about one SHA-256 block (about 5 ms by `BM_ShaZK_fp2_128/1`), but a verifier-visible nullifier links one holder's presentations within an epoch, and a shared nullifier set is a registry. Decision: defer. The cap is enforced by the VTA only, and therefore only against honest VTAs, until a stateful minting party exists; a nullifier is an opt-in tier for high-assurance verifiers that share a set. Under Path A there is no DBI credential and so no cap in its rules; the cap is Path B design. This supersedes old Q20's open framing (k-times anonymous credentials or nullifiers "not researched").

### IX.4 Revocation and status mechanism — **applied: Merkleized bitstring, pending benchmark (plan §5.3, Q6)**

**ACDC-native TEL status cannot be shown privately.** TEL status events (`rip`/`bup`/`upd`; v1 tooling `vcp`/`iss`/`rev`): a blinded `bup` carries a blinded block SAID that "the Discloser" unblinds with a salt shared with the issuer (ACDC v1.1, about lines 2127–2135: "Only the Discloser can unblind the state"; "MUST increment the sequence number and hence the blinding factor"), so re-blinding shows the issuer's refresh timing; the registry id `rd`, event SAIDs and the ACDC SAID `td` are verifier-visible. The specification's herd-privacy option, a sparse Merkle tree root over TEL events anchored periodically (about lines 2916–2935), proves inclusion of an event, not that it is the latest, and is heavy in SHA-256. This answers old Q18 in the negative.

**Standard lists cannot be proven as published.** W3C Bitstring Status List (Recommendation, 2025-05-15): minimum length 131,072 bits; "statusListIndex is the only link between the verifiable credential and its status". IETF Token Status List (draft 21) is zlib-compressed; in-circuit inflate is infeasible.

**Recommendation adopted as current design, pending the Phase 0 benchmark.** A Merkleized bitstring: each primary carries a `statusIdx` in a signed block; the state publishes a SHA-256 Merkle tree of the list in 512-bit leaves, depth about 15 for 2^24 entries, and anchors the root with a `SealRoot` seal (keripy `structing.py:38`); the verifier checks the anchored root outside the proof (no extra in-circuit ECDSA); the circuit proves one leaf plus a depth-15 path (about 31 compressions per credential, about 60 for primary plus DBI credential); holders and VTAs fetch the whole list, so lookups are private; the fixed depth keeps the circuit ID stable. Preferred over a sorted deny-list, whose path is deeper. Under Path A the stock circuit has no status input, so revocation there is short MSO validity and refusal to re-issue.

**Alternative, to benchmark.** The experimental `mdoc_revocation.h` signed-span scheme: the state signs `epoch||l||r` spans and the circuit proves `l < id < r` with SHA-256 and one ECDSA verification. Cheaper than the Merkle path and it carries an epoch, but the state must sign and anchor spans. Recorded as a considered alternative (plan §5.3).

**Estimates.** Status profile 1–1.5 person-weeks; state publisher (builder, anchor, static hosting) 2–3 person-weeks; circuit component and benchmark 0.5–1 person-week. Decided by Utah (epoch cadence), the working group and Brendan. The holder must retain, for any TEL-based flow: the ACDC, `rd`, the salt, the latest sequence number and the KEL seal reference.

**Superseded.** Old Q17 (status epoch in the proof versus fallback) and old Q18 merge into current Q6; Part VIII's sorted Merkle deny-list over revocation tags is replaced (marked there).

### IX.5 Exact signed bytes and anchoring — **applied (plan §5.1 terms, §7.2, Q7, Q8)**

**"Direct" has two senses.** ACDC v1.1 says ACDCs are "not directly signed by the Issuer" (lines 1663–1673) and also speaks of "an Issuer commitment via a signature (direct) or KEL anchored seal (indirect)" (line 1822). The plan now defines *signed*, *direct anchoring* and *indirect anchoring* in §5.1 and uses only those.

**SAID digest.** keripy `serdering.py` `_compute()` builds the serialization with the real size in `v` and each SAID field replaced by `#` repeated to the field's qb64 length, then `Diger(ser=raw)`; the CESR specification: "replace the SAID field value ... with a dummy string of the same length. The dummy character is `#`".

**Signed bytes.** keripy `habbing.py` does `sigers = self.sign(ser=serder.raw)`, signing the KEL event's raw JSON. P-256 is ECDSA over SHA-256 with raw `r||s` (`signing.py:262–267`) under a 33-byte compressed key, so the circuit needs point decompression and `kt` must be 1. The TEL seal in the `ixn` is `{"i":regk,"s":"0","d":<iss SAID>}`. Signature attachments are not signed.

**Version drift.** ACDC's document status says v1.1, but its examples use protocol-2.0 strings (`ACDCCAACAAJSONAAFE.`, `rd`, `acm`) and it says "Compliant ACDC version 2.XX implementations MUST support the old ... 1.x Version String"; the did:webs example uses `ACDC10JSON000574_` with `ri`. The state must pin one protocol version because the circuit layout depends on it (Q8).

**Fixed layout.** keripy JSON has no whitespace and a fixed field order, so a fixed-layout profile is feasible (44-character SAIDs, 24-character `u`, 32-character `dt`). The variable pieces are the hex `s` (1–3 digits, so 3–4 layout variants, splitting circuit IDs) and claim strings. CESR-native uses fixed-size primitives (`-F##`) and is the most circuit-friendly; its tooling maturity is **[unverified]**.

**SHA-256 compression-block estimates** (arithmetic from the scoping, parsing excluded):

| Component | n = 5 blinded blocks | n = 20 |
|---|---|---|
| Primary | ~25 | ~75 |
| DBI credential | ~20 | ~30 |
| Anchoring | 24–34 | 24–34 |
| Disclosure digests | ~10 | ~40 |
| Merkle bitstring, depth 15, two credentials | ~64 | ~64 (a sorted-list Merkle at depth 20–30 would add 160–240 instead) |
| **Total** | **~145** | **~420** |

That is 4–12 times mdoc-zk's about 36 permutations. The ECDSA count goes from 2 to 3, or stays at 2 if both credentials are sealed in one `ixn`. Parsing with a fixed layout is nearly free (constant offsets); with witness offsets it adds a multiplexer of O(bytes × fields), guessed at 10–50 block-equivalents **[unverified]**. The Phase 0 benchmark therefore includes parsing and placeholder-SAID recomputation as separate components.

**Anchoring stays in the circuit.** Taking it out leaks: revealing the `ixn` or its SAID reveals the issuance bucket and links secondaries.

**New scale issue: KEL growth.** One `ixn` per credential grows the state's KEL per holder; did:webs resolution processes `keri.cesr` and fails on any problem, so the whole stream must be replayed. Options: batch `SealRoot` seals (leaks an issuance-batch partition) or a separate issuing AID. Whether stock verifiers accept a root seal for issuance is **[unverified]**.

**Anchoring form recommendation.** Direct anchoring with the primary and DBI credential sealed in *one* `ixn` (one ECDSA, no TEL parse). The primary is never shown to verifiers and status comes from IX.4, so a per-credential TEL adds nothing for them. But the did:webs designated-aliases ACDC needs a registry ("MUST NOT successfully resolve unless the resolved DID appears in a valid, unrevoked designated aliases ACDC"), so the state needs a minimal TEL anyway. If the primary is an SD-JWT VC or mdoc signed by the did:webs key (Path A), the TEL, the KEL growth and most of the parsing disappear. Q2 (primary format) is decided first; Q7 and Q2 sit with Utah and Brendan. This supersedes old Q16's neutral "direct or indirect" framing with a recommendation.

### IX.6 did:webs specification found — **applied (plan X13, §5.1, Q9, Phase 2)**

### X.5 Dual issuance, and where the complexity goes

**The option.** The state issues the ACDC as the authoritative credential and also an mdoc projection of it (Path A's mdoc, with the ACDC alongside), so verifiers get the mdoc path while KERI principles hold.

**Why rejected.** It doubles Utah's operational burden — two issuance stacks, two records, and two revocation paths kept consistent — and it duplicates what DBI is meant to avoid, per-format issuance by the state.

**Utah-burden comparison** (as in the plan, §3):

| Issuance stacks | 1 | 2 | 1 | 1 |

| Signs after issuance | mdoc re-issue per short validity | mdoc re-issue | nothing | nothing |
| Complexity carried by us | low | low | circuit, audit | circuit, audit |

**The insight.** Path B moves complexity onto us (the circuit and its audit) while keeping the state at one issuance. A plus ACDC dual moves it onto Utah's operations and their consistency. ### X.9 How the custom linkage circuit could fail

Added after the user asked why the circuit could fail when Longfellow already has P-256. The primitives are reused (SHA-256, P-256 ECDSA, `memcmp`, routing, comparisons; IX.2). What does not exist is the circuit for our statement: the state's KEL-anchored key signs an ACDC, the credential is unrevoked at the status epoch, and it is bound to a fresh holder key. Stock mdoc-zk proves a different statement (an issuer signed an MSO and attributes satisfy a predicate), so ours is a new circuit, not a parameter change (plan §4, X4: upstream's experimental circuits are not production-vetted). "Fail" here almost never means "cannot be built"; it means one of the following, listed most likely first.

1. **Cost.** The circuit hashes the ACDC, the KEL event data and Merkle paths, and checks more signatures than mdoc-zk: about 4 to 12 times its permutation count (IX.5). Circuits are fixed-size, so every maximum is paid on every proof. If proving time, memory on the VTA, or proof size exceeds the budget, the design is unusable as specified. The Phase 0 benchmark measures this; whether the result is acceptable is Brendan's judgment at G0 (X.6 item 2).
2. **A rigid in-circuit layout.** The circuit recomputes SAIDs and reads fields from serialized ACDC and KEL data, with no JSON parser upstream. That needs a pinned layout. If ACDC versions or field order vary (Q8), either many circuits (and a larger manifest) or a profile Utah may not accept is needed.
3. **Soundness bugs.** Longfellow's reviews found under-constrained witness variables (Trail of Bits, 13 issues, 2 high) and under-constrained CBOR indices (ISRG). A custom circuit can accept a false statement with no visible symptom. This is why the plan budgets an external audit and negative tests per witness variable, and why audit findings are a schedule risk.
4. **Upstream instability.** No stable third-party circuit-authoring API is documented, there is no Node binding, and the C interface exists only for mdoc-zk. Upstream changes, or the move to the Rust LFC2 format, can force a rebuild. Any gate or witness change also changes the circuit ID.
5. **Verifier acceptance.** A sound circuit achieves nothing if verifiers will not accept our proof format or circuit IDs. The circuit-ID manifest (Q17) and the interoperability check address it.

**Not the same as P-256 failing.** If P-256 fails in the state's signing infrastructure or in keripy with witnesses or delegation (G2), the plan's kill criteria and fallbacks apply. *Part XII note:* when X.9 was written they were "zkVM guest first, then a custom Ed25519 circuit" (D13); D15 replaced that order, and no fallback is viable on a 2-CPU VTA, only a custom Ed25519 Longfellow circuit, unbenchmarked. Those fallbacks do not answer a custom-circuit failure, which has no named fallback (X.6 item 1; Q25). The benchmark is the cheapest way to learn which of the five applies.


### X.10 Draft question for Utah: TEL status versus direct anchoring (plan Q7)

*Drafted 2026-10-08 for Brendan to send. It has not been sent, and Utah has not been contacted. The wording keeps X14's provenance: "TEL status" is the principle as Brendan reported it from ongoing communication, not a Utah document and not confirmed in writing, so the message asks Utah what its principle requires and does not assert it. A copy sits at `/srv/dev/scratch/2026-10-08-bam-q7-utah-question.md`.*

**Why it is needed.** Two separate things are tangled in "TEL status". (1) *Issuance anchoring*: the plan recommends one KEL interaction event sealing the primary and the DBI credential directly, with no per-credential TEL (IX.5). (2) *Status at presentation*: the plan proves, in zero knowledge, that the primary's bit is clear in a Merkleized list whose root the state anchors each epoch, because TEL status cannot be shown privately (X11: the registry id, event SAIDs and the ACDC SAID are verifier-visible, and re-blinding reveals refresh timing). The plan keeps the state's TEL as the authoritative status record from which the list is built (plan §5.3). If Utah means only the second, the plan already conforms. If Utah means a per-credential TEL registry with issuance and revocation events, the recommended anchoring changes.

**The message (ready to send).**

> We are designing how a holder presents the state's ACDC to verifiers without revealing the credential, so that presentations cannot be linked to each other or to the original. We understand the state's principle to include TEL-backed status. Please tell us what that requires, because two designs differ on it.
>
> 1. **Is a per-credential TEL entry (a registry, an issuance event and, on revocation, a revocation event) required for each credential, or is the requirement that the state's registry is the authoritative record of status?**
> 2. **If the state's TEL stays the authoritative record, may we rely on a status list derived from it?** Each epoch the state would publish a list built from the TEL and anchor its root in the state's key event log. Holders would fetch the whole list and prove, privately, that their credential is not revoked under an anchored root. A revocation would still be a TEL event first; the list would follow it at the next epoch. The TEL would not be consulted at presentation, because a lookup there identifies the credential.
> 3. **If the answer to 1 is "a per-credential TEL entry", is a single anchoring event per credential, or batch anchoring under one root, acceptable for the growth of the state's key event log?** And who would run the list publisher?
> 4. **What epoch cadence is acceptable for the derived list, and for emergency revocation?** (This overlaps with the freshness question already open.)
>
> A one-line answer to 1 and 2 is enough to proceed; the rest can follow.

**Tradeoffs of the answers.** Figures are plan estimates or inferences; none is measured, and the Phase 0 benchmark prices the indirect form separately if it is required.

| | Direct anchoring, state TEL authoritative, derived list | Indirect anchoring (per-credential TEL entry), derived list | Direct anchoring, list authoritative, no per-credential TEL |
|---|---|---|---|
| What anchors issuance | one `ixn` sealing the primary and DBI credential SAIDs | an `ixn` sealing a TEL issuance event that names the credential | as the first column |
| Where authoritative status lives | the state's TEL (a registry kept for status), list derived from it | the state's TEL | the list itself |
| Fits "TEL status" literally | partly: needs Utah to accept that the list is derived | yes for the record; the presentation list is still derived (X11) | no |
| In-circuit work (inference) | one ECDSA, no TEL parse; fewest serializations | one more serialization and one more seal-containment check; layout variants multiply with TEL event fields | as the first column |
| Consistency burden on Utah | list must be rebuilt from the TEL each epoch | same | none, but no TEL record |
| KEL growth | one `ixn` per credential unless batched (plan Q7) | one `ixn` per credential plus TEL growth | as the first column |
| Verifier trust | trusts the list matches the TEL; not provable in the circuit (inference) | same | the list is the record |

Utah accepts a derived list but requires per-credential TEL entries: Q7 closes on indirect anchoring, §7.2 item 3 states that form, and Phase 0 benchmarks the extra serialization. ### XI.3 Interpretation

On the benchmark's own bands for a zero-knowledge mode on `c2` (10 s or less and 8 GiB or less: viable; 10 to 120 s or 8 to 16 GiB: background batch only; above 120 s, above 16 GiB, out of memory or no working zero-knowledge mode: not viable as specified), RISC Zero's succinct receipt is far above the 120 s line (808 s for T2, 1349 s for T3), so it is not viable as a per-presentation prover on a 2-CPU VTA. A 50-proof batch of T3 is 50 x 1349 s = 67,450 s, about 18.7 hours of two dedicated cores. SP1 has no measured zero-knowledge mode at all. Verification is cheap everywhere (12 ms on RISC Zero succinct), so the cost is entirely on the prover. RISC Zero's succinct mode is the one the vendor claims is zero-knowledge, and it says plainly that it has not written the argument; composite receipts leak the execution length. D13's "witness zero-knowledge" contingency is therefore still not met by any measured route. Prove time on RISC Zero is a step function of the padded segment count (T0 to T2 share two segments, T3 has three), so a real ACDC with variable-length claims, which costs more than the fixed layout, would pay in steps.

For scale only: D13's Longfellow estimates (0.5 to 3 s) are inferences and were not measured here. They remain Phase 0's job. *Part XIII note:* the stock baseline is now measured (XIII.2); the custom circuit's cost is still an estimate.

### XI.4 Limits

The statement is simplified (one credential, one anchoring event, fixed offsets, no key-state replay, no selective disclosure); the guests are unaudited and use vendor forks of the crypto crates; one shared host, with nice 19 and an idle I/O class, so absolute values would differ on a dedicated machine; the SAIDs were not cross-checked against keripy; verifier acceptance of a zkVM proof for an Ed25519 check was not tested; phone-side proving was not tested; the zero-knowledge claims are vendor statements; Longfellow's numbers were not measured.

### XIII.3 Custom-circuit cost: an estimate, not a measurement

The estimate applies IX.5's model: the hash part scaled by 4 to 12 (145 to 420 SHA-256 compression blocks against about 36 permutations for mdoc-zk, a figure not re-derived here), the signature part by 1.5 (a third ECDSA; no scaling if both credentials are sealed in one `ixn`). The stock C++ time is split using upstream's own phase log: prove about 0.62 s hash side (including the 0.12 s circuit decompress and parse, assumed to scale) and 0.12 s signature side; verify about 0.34 s and 0.08 s.

| C++ implementation, one uncontended thread | Stock (measured) | Custom (estimate) |
|---|---|---|
| Prove | 0.71 s | about 2.7 to 7.7 s (all-scaled bound 2.8 to 8.5 s) |
| Verify | 0.40 s | about 1.5 to 4.2 s (bound 1.6 to 4.8 s) |
| Peak memory | 0.22 GiB | about 0.7 to 2.1 GiB (assumes memory follows the hash circuit, 94% of circuit bytes) |
| Proof size | 360 KB | about 0.7 to 1.3 MB (weakest estimate; assumes Ligero growth of 2 to 3.5x) |
| 50 proofs, two separate cores, prove only | about 18 s | about 1.1 to 3.2 min |

For the Rust implementation, multiplying by the measured ratios (about 2.1x time, 4.6x memory, **assuming the ratios hold on a different circuit**) gives about 5.7 to 16 s to prove and, by my arithmetic, about 3 to 10 GiB, which fits an 8 GiB container only at the low end. **Excluded:** witness-offset parser cost (IX.5 guesses 10 to 50 block-equivalents, unverified), soundness work, the memory behaviour of a circuit 4 to 12 times larger (the stock circuit is 99 MB uncompressed, so 0.4 to 1.2 GB of circuit data), and any verifier acceptance. ### XIII.4 Corrections to this document and the plan

1. **`circuit_hash`** (plan X3, IX.2). Verified from `results/raw/circuit-identity.txt`: the generated v7 circuit's log ids were `sig=2845210a...df2d` and `hash=58248d20...d106`; SHA-256 of their concatenation (signature id first) is `8d079211...2121`, equal to `kZkSpecs[0].circuit_hash`; the reverse order does not match; the compressed circuit file hashes to `9016d173...2769`, a different value. So the hash is the bundle id of the two circuits' ids, not a hash of the compressed bytes. The plan's X3 now states the correct form; IX.2 carries a dated correction with the original text kept. The practical consequence stands: any gate change is a new hash.
2. **D13, "a Rust prover under 100 MB"** is unsupported by the pinned crate (555 to 1009 MiB measured), and **"multi-thread scaling is unclear"** is answered (none). D13 carries a dated correction; its text is kept.

Proof sizes differ (360 against 832 KB), so proofs are not assumed interchangeable.
