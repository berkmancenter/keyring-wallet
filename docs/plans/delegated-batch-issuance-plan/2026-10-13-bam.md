## Part B. The keripy pin

Three commits appear: `25f06d2` (this companion's Part IV read), `7143832` (the holder plan's research) and `927c0cb` (the reference field of the keri-ts vectors that plan reuses). `gh api repos/WebOfTrust/keripy/compare` shows one line of history: `927c0cb` is 24 commits ahead of `25f06d2`, and `7143832` is 3 ahead of `927c0cb`. `PINS.json` in this checkout has no keripy entry (its note says to advance pins only with `tools/sync-external.mjs --advance`).

**Proposal (Brendan to confirm): pin `7143832`.** It contains the other two, so one clone serves the Utah generator, the vector provenance and this plan's Phase 0 re-quote. The cost is real and stated in the plan: 25 files differ between `25f06d2` and `7143832`, including `src/keri/core/coring.py`, `indexing.py` and `serdering.py`, where Part IV's P-256 code, indexed-code and SAID claims were read. Those quotes are therefore re-read at the pin before anything relies on them. Which files carry the changes' content was not read here. The alternative, `25f06d2`, keeps Part IV valid as read and moves the cost to the holder plan, which would regenerate its generator output.

**Who owns the entry.** The holder plan's default is that this plan owns the pin file. The plan states it more narrowly: this plan's Phase 0 Pins task adds the keripy entry through the pin tooling; the file itself belongs to the repo's shared pin tooling; the holder plan adds its own entries (a cesr-ts and keri-ts commit) through the same tooling. Whether that split is acceptable is Brendan's.
