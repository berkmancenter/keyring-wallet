## A2 — The plan's highest-stated risk is already measured, and the measurement is worse than §3.7 says

**Evidence.** §3.7 states that under our RDF-canonicalized suites *"a VSC member
with no JSON-LD term is not merely unsigned, it does not exist in the signed
graph"*, and calls it the highest-risk part of the migration. `ref-07c` measured
exactly this against the real shipped `@bifold/vrc-contexts` bytes, and found
three things, of which only the first is in the plan:

1. **An untermed member contributes zero quads.** Confirmed — `ref-07c` Check 4:
   `witnessContext.localityVerification.challenge` and a profile-added
   `observationContext.documentType` are both unsigned.
2. **`object.digestMultibase` is already safe and cannot be redefined.** The
   `credentials/v2` base context defines `digestMultibase` as
   `security#digestMultibase` and `@protected`s it. Attempting to redefine it is a
   fatal JSON-LD error. So the plan's V2 term list needs *fewer* terms than it
   states, and must not define that one.
3. **The zero-quad case is not the dangerous one.** An unresolved CURIE does not
   drop to zero quads — `example:observedDocument` is a syntactically valid
   absolute IRI whose scheme is `example`, so it is signed verbatim and is
   tamper-evident **over an IRI its author did not mean**. A verifier holding a
   context that maps `example:` expands the same bytes to a different IRI. Two
   meanings, both signatures valid. JSON-LD safe mode, which our DI signing path
   uses, catches the zero-quad case and **does not catch this one**.

**Position adopted.** V2's guard (the generalized `localityVocabulary.test.ts`)
must assert two properties per member, not one: that it contributes a quad, and
that the quad's predicate IRI is the one we intended — i.e. the guard compares
expanded IRIs, not counts. A quad count alone passes finding 3.

**What it supersedes.** Nothing in the plan; it sharpens §3.7's rule 2, whose
stated defence (*"counting quads per member"*) is necessary and not sufficient.

## A3 — A Keyring-namespaced context is a network dependency inside someone else's trust boundary

**Evidence.** `ref-07d` drives the **real shipped** `createVrcDocumentLoader` and
counts requests. Five contexts are bundled and resolve with zero network. Every
other context is fetched over HTTP, unauthenticated, uncached, with no allowlist.
Measured consequences: one unbundled community context produces one outbound
request *at verification time* (the vocabulary host learns which verifier reads
which credential kind, and when); offline, that credential cannot be verified at
all; and serving a second version of the context that withdraws a term
invalidates the original signature without the credential, the key or the issuer
changing.

**Why this lands on §3.5.** The plan moves `locality*`,
`hardwareAttestationIncluded`, `parties` and `taskDigestMultibase` under a
Keyring-controlled namespace. For *our* wallet that is free — we bundle it. For a
third party verifying a Keyring VWC it is `ref-07d` Check 1 and Check 2 pointed
at us: they fetch our host at verification time, or they fail offline. And it
makes Keyring the party who can retroactively change what its own issued
credentials signed over.

**Position adopted.** Three constraints on §3.5, none of which changes the
decision:

1. The Keyring namespace document ships **bundled in `@bifold/vrc-contexts`** in
   the same phase that first emits a member under it (V2 before V4, which the
   plan's ordering already gives).
2. The namespace document is **immutable once published** — new terms only, never
   a withdrawal or a redefinition. Stated in the file, beside the terms.
3. §10 gains a line: a third-party verifier's offline path is the argument for
   getting these members into the registry's `witness-context.schema.json`
   eventually (the plan's Q4), rather than a purely editorial preference.

## A4 — Nothing in the ladder puts a VSC through Credo 0.7, and this plan is stacked on the Credo 0.7 branch

**Evidence.** `ref-21`'s own *Does not prove* line says *"anything about Credo,
signing on device, or the DIDComm path. No agents run."* `ref-22` is pure string
work by design. `ref-23` transforms captured artifacts. So under the plan as
written, the first time a VSC meets Credo's real sign-and-verify path is **V4's
`yarn e2e:vrc`** — after issuance has already changed.

This branch forks from `feat/credo-0.7` (PR #54), where the credential path is
not the one the rungs were written against. Four measured tripwires from that
work bear directly on a credential-shape change:

- **The witness ceremony depends on a core patch.** Credo 0.7's
  `verifyPresentation` holder-binding rule (*"does not authenticate the
  credentialSubject"*) breaks the witness ceremony on v1 **and** v2; we carry
  `verifyCredentialSubjectAuthentication: false` at three call sites. A plan whose
  D6 adds a *new* subject-binding check must state its relationship to the check
  we just switched off.
- **The PR #2704 snapshot carries main's in-progress `w3c-di` restructure**,
  which rejects eddsa suites in the legacy JSON-LD models; we map non-anoncreds
  `DataIntegrityProof` to the generic class in a core overlay hunk. That is the
  code path a VSC signed `eddsa-rdfc-2022` travels.
- **`json-canonicalize@2.0.1` is a broken publish** (pinned to 2.0.0) — and JCS
  is the canonicalization under every digest this plan moves.
- **`class-transformer` metadata is module-local**, so it must stay a Metro
  singleton and a jest `moduleNameMapper` entry.

A fifth, from `ref-07e` Act 1: our rung-local `eddsa-jcs-2022` helper attached
`@context` to the proof configuration, which vc-di-eddsa does not do. Both
directions of a cross-implementation check failed until it was deleted. The bug
was invisible for as long as the same helper both signed and verified — which is
precisely the shape of `ref-21` as specified (*"sign `eddsa-jcs-2022` over
deterministic test keys"*, verified by an implementation written from the
constraints file).

**Position adopted.** A new rung before V3 — working title
`ref-07h-vsc-credo-suites` — that signs and verifies a VSC through **Credo 0.7
with our patch set**, under both suites we actually ship (`Ed25519Signature2018`
and `eddsa-rdfc-2022`), and asserts the D6 check against a credential Credo
verified rather than one the rung signed itself. `ref-21`'s JCS work stays, as
the cross-implementation leg it already is in `ref-07e`, but it is not the
evidence that V4 is safe.

**Acceptance criteria to add.** V3: the D6 check passes through Credo's verify
path, not only over fixtures. V4: the `yarn e2e:vrc:witnessed:didcomm-v2:tsp`
suite is green, not only `yarn e2e:vrc`.

## A5 — The Trust Task layer's exposure is four read sites, and three of them are a debt we already owe

**Evidence.** `ref-07b` Act 3 measured that `@bifold/trust-tasks` reads
`credentialSubject` **zero times** — the Trust Task model does not see credential
shape at all, which is what makes the plan's §3.1 reuse clean. What does read it:

| Site | Reads | Status |
|---|---|---|
| `outcomeEvidence.ts:71` | `credentialSubject.taskContext` | WD02 already puts `taskContext` at the top level, so this is a fix we owe **regardless of this plan** |
| `outcomeEvidence.ts:227` | same | same |
| `witnessCeremony.ts:169` | same | same |
| `WitnessService.ts:2545` | `credentialSubject.digest` | D3 |

`ref-07e` Act 3 measured the consequence from the other side: of Keyring's four
VWC checks run against a VWC minted by `dtg-credentials` 0.7.0, **two fail**, both
because of these placements, and both pass once WD02 placement is used.

**Position adopted.** §3's D4 is described as *"breaking, trivial"*. It is
trivial to emit and it is four read sites to fix, three of which are a standing
WD02-conformance bug that has been costing us cross-implementation compatibility
since before this migration. Name them in V4's scope so they are not discovered
at fixture-regeneration time.

**Two self-findings from the #18 split that land in the same files**, recorded
here so they are not re-derived: `outcomeEvidence.ts` accepts any `#response`
(a control response passes), and never checks that the terminal message's signer
is the initiating document's recipient. `ref-07g` is the rung that covers the
pairing rule; the fixes are not this plan's, but V4 touches the file.

**A rung the ladder does not have.** No rung runs a *witnessed exchange* with a
VSC over a carriage. Proposed as `ref-07i-vsc-over-carriages`: the ceremony end to
end with a VSC over DIDComm v1, DIDComm v2 and the TSP envelope, with outcome
evidence retained and verified. Both v2 and TSP carriages landed after every rung
cited in this plan was written.

## A8 — A second shipped implementation rejects our extension members outright

**Evidence.** `ref-07b` Act 4 fed Keyring's real artifacts to
**`dtg-credentials` 0.7.0** — the Rust catalogue the VTC mints from — re-adding
each Keyring member in isolation so each verdict has one cause. Nine
independently fatal divergences, among them:

| Variant | Verdict |
|---|---|
| `issuer` as `{id, name}` | REJECTED — `invalid type: map, expected a string` |
| `witnessContext.hardwareAttestationIncluded` | REJECTED — unknown member |
| `witnessContext.localityVerification` | REJECTED — unknown member |
| `credentialSubject.parties` | REJECTED — unknown member |
| `credentialSubject.taskDigestMultibase` | REJECTED — unknown member |
| `taskContext` inside `credentialSubject` | REJECTED — unknown member |
| `Ed25519Signature2018` proof | REJECTED — `missing field cryptosuite` |

The crate models each `credentialSubject` as a closed schema (serde
`deny_unknown_fields`).

**Why this matters to §3.5.** The plan's argument for carrying extension members
is C10 — *"a verifier MUST ignore additional members a profile does not
define"* — and it is correct about WD 0.4.0. It is not correct about the
implementation the ecosystem actually runs. This is the same class of finding as
§7.1's `personhood.rego`, from a different component, and it is stronger: the
policy is documented as replaceable, whereas `deny_unknown_fields` is a
compiled-in choice.

**Two consequences.**

1. **One of the nine is our bug**, and it is unrelated to the VSC: WD02 and
   WD 0.4.0 both make `issuer` a string, and we emit `{id, name}`. V4 touches the
   builder; fix it there.
2. **§10's upstream table gains a fourth row** — `dtg-credentials`'s
   unknown-member handling — with the same *"confirm against current upstream
   before proposing"* caveat §7.1 carries, since Act 4 is pinned to 0.7.0.

**What it does not change.** The decision to carry the members. C10 is the
normative text and we are conforming; the finding is about what will actually
interoperate, which is worth knowing before a Farm demo, not a reason to move
them.

## A9 — Two different placeholder namespaces are in play, and the mirror can only generate one

**Evidence.** The plan (§2.2, §2.4) issues under
`https://firstperson.network/credentials/dtg/v1#witnessed`, citing C12's note
that this is the specification's placeholder. `ref-07f` built #52's registry from
the issue body (fetched 2026-09-14, body sha256 `38f6f37b…`) and its worked
entries place the predicates under **`https://trustoverip.org/dtg/vocab#`**.

§2.2's acceptance criterion for the mirror is that the generated
`accept-list.json` is *"byte-equal to #52's quoted example modulo the namespace
constant"*. With two candidate namespaces that criterion is ambiguous: byte-equal
to the issue's example means `trustoverip.org`; issuing what the plan says means
`firstperson.network`.

**Position adopted.** State in §2.2 which of the two the mirror generates and
which the wallet issues, and make the difference the *only* thing `DTG_NS`
controls. The plan's own rolling-cutover mechanism (§2.3) makes this survivable;
what is not survivable is discovering at V4 that the accept-list and the issuer
disagree. This is one line in §2.2, not a design change.

## A10 — Narrowing the accept-list is the deprecation hazard, measured

**Evidence.** `ref-07f` Act 6: #52 keeps deprecated terms *"forever"* but puts
only **active** IRIs in the generated accept-list. So a deprecation retroactively
invalidates every credential already issued under the term — a verifier
configured from the new accept-list rejects a statement that was conforming when
issued.

§2.3's step 4 is exactly this operation: *"accept `{B}` and delete `A`"*.

**Position adopted.** The step is safe **because of the seven-day expiry**, not
because the accept-list format makes it safe — and the plan should say so at the
step, since the mechanism is the ladder's, not the spec's. In the mirror, keep
deprecated entries present and marked rather than dropped; that is also the
concrete proposal for #52, and it is `ref-07f`'s finding to contribute.

## A11 — With the type string gone, a VSC files itself under Contacts

**Evidence.** `credentialTypes.ts:81` defines `isPeerVrcCredential` as
*"`DTGCredential` and not `WitnessCredential`"*. `ref-07b` Act 2 and `ref-07f`
Act 3 both measured the consequence against the **real compiled** module: a
statement credential without the type alias is rejected by `isWitnessCredential`
and **claimed by `isPeerVrcCredential`**, so today's wallet files a witness
attestation under Contacts. An endorsement statement does the same.

`ref-07f` Act 3 also measured the fix in place: dispatching on the accept-list
routes both correctly — *"for a wallet, the accept-list is the dispatch table, not
only an allowlist"* — with an unrecognised predicate rendering as a generic
statement rather than as a relationship.

**Position adopted.** V3's bullet on `credentialTypes.ts` names this as the
defect it is: the negation must become an allowlist, and that fix is owed before
the first non-witness statement credential exists, independently of when V4
flips. The plan's §1 already calls this the one place where the migration is a
design change; this is the specific failure mode, already reproduced.
