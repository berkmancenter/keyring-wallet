## 1. Internal findings

- **VRCs Keyring emits lack `issuerScope`.** The VRC section (`spec/body.md`, lines 302-330) lists `issuerScope` as *"(string, REQUIRED): `pairwise`, `directed` or `public`"*. The witness credential emits it (plan §3.6); a search of the VRC module's non-test source (`bifold/packages/core/src/modules/vrc`) finds no `issuerScope`. G32.
- **Peers that only speak v2 receive `Ed25519Signature2018`.** `vrc-manager.ts` (line ~489-503) offers `DataIntegrityProof`/`eddsa-rdfc-2022` only to a peer that announced it can verify it, and `Ed25519Signature2018` to everyone else (`docs/CRYPTO_SUITE_FOLLOWUP.md`, Decision 6). The spec's `proof.type` MUST (line 199) permits neither. G32.
- **iOS-origin evidence verification trusts the embedded hash.** `AttestationModule.kt` lines 1516-1530 and `Attestation.mm` lines 1437-1455 use the evidence's embedded `signedContentHash` as the App Attest `clientDataHash` when one is present, and only log a warning (`⚠ Embedded hash differs from SHA256(signedContent) — expected for cross-device VRC`) when it differs from `SHA256(signedContent)`. The assertion is therefore verified against a hash the evidence itself supplies, and is **not bound to the credential bytes the verifier holds**. G33. Staged fix: `hardware_evidence_binding_subtask.md`. History and measurement: the embedded hash dates from `081c6d7e3`, when both native verifiers skipped the App Attest nonce hash and `@context` was not restored; `007788b28` fixed both but kept the hash substitution; and Credo 0.7 preserves today's VRC signed bytes but moves `credentialSubject.id` last on a round trip, so Stage 2 must land before any `credentialSubject` member is added.
- **`docs/HARDWARE_ATTESTATION_FLOW.md` is stale**: proof suite, preference default, emulator behaviour, sample chain length and iOS hash trust. The five items are as reported by the coordinator's investigation; **the document was not re-read line by line in this pass**. G34.
- **`WITNESSED_EXCHANGE_CONTEXT_DOCUMENT` still redefines terms the real registry context owns.** This is G26, still open (plan Q9); nothing in this part changes it.

## 3. G32 implemented: `issuerScope` and Data Integrity on every VC 2.0 VRC

Same author, same day.

### 3.1 What was decided

- **`issuerScope` is `pairwise`.** Checked in code rather than assumed: `getOrCreateRelationshipDid` (`vrc-manager.ts`) creates a new `did:peer:0` with a fresh Ed25519 key per counterparty connection DID, stores the mapping, and returns the same DID only for the same counterparty (concurrent callers share one creation). Nothing passes that DID to a second counterparty, so the identifier in `issuer` is pairwise. The specification recommends `pairwise` for a VRC. Q8's `directed` (plan §3.6) concerns the witness's single identifier across all sessions and is unchanged. One caveat: the relationship DID is also shown to the witness during a witnessed exchange as presenter; that is the same relationship's counterparty ceremony, not a second correlation context for the VRC.
- **The VC 2.0 path gets it; VCDM 1.1 does not.** The 1.1 path has no registry context, so the term would not be signable; it is untouched.
- **RCE v2-only peers fall to the VCDM 1.1 path.** The smallest change that leaves no VC 2.0 VRC with a non-DI proof was to raise the VC 2.0 gate (`counterpartySpeaksVc20`) from RCE v2 to RCE v3; since v3 implies DI, `useDi` is now always true inside the VC 2.0 branch. The Ed25519 suite context is no longer appended for any VRC the wallet builds (`selectCredentialContexts` keeps the branch for direct callers and tests). `RCE_PROTOCOL_VERSION` stays 5. **Wire behaviour an old peer sees:** a peer announcing exactly RCE v2 now receives a VCDM 1.1 VRC instead of a VC 2.0 one, and no RCard (the RCard gate uses the same function). Every build at v2 or below already reads the 1.1 VRC (it is what v1 peers receive) and can do without an RCard. No build is known to announce v2 without v3 (pre-production, all apps assumed current), so this is expected to affect no real peer. The rejected alternative was keeping v2 peers on VC 2.0 with `Ed25519Signature2018`, which is the non-conformant emission G32 names.
- **Left alone on purpose:** the challenge-bound VP that wraps a VRC for the witness is still `Ed25519Signature2018` (a presentation, not a VRC; the witness dual-verifies); the `vrc-reference` demo `Participant.ts` still issues VC 2.0 VRCs with `Ed25519Signature2018` and no `issuerScope`; `docs/CRYPTO_SUITE_FOLLOWUP.md` Decision 6 text describes the old gate and was not edited.

### 3.2 Consumers checked

- **Witness (`witness-server`, `@bifold/vrc-shared` loader).** `credentialBuilder.ts` reads `issuer`, `validFrom`/`issuanceDate`, `proof` and `evidence[*].hardwareBinding.publicKey`; it validates no VRC shape strictly and the digest is JCS, so an added member neither breaks nor reorders anything, and changing `issuerScope` changes the digest. Identity Check is `verifyCredential` with `demoDocumentLoader`, which resolves the registry and evidence contexts (`vrc-shared/src/documentLoader.ts`).
- **VWC digest edge** (`object.digestMultibase` over `taskDigestMultibase(vrcJson)`, RFC 8785): key-order independent, covers `issuerScope`. The Trust Task payload schemas (`additionalProperties: false`) sit on the delivery envelopes, not on the VRC.
- **Hardware-signed bytes.** The wallet signs `JSON.stringify(credential)` after `issuerScope` is set and before `evidence`/`proof`; `extractSignedContent` strips those two and restores `@context` first. A test runs the real builder output through Credo's `JsonTransformer` round trip and asserts the verifier is handed byte-identical content, `issuerScope` included.

### 3.3 Verification

Device-free only. `hardwareEvidenceVocabulary.test.ts`: safe-mode URDNA2015 expansion of `issuerScope` to `https://registry.trustoverip.org/dtg/credentials#issuerScope` with every evidence variant, and no stray namespace. `vrcIssuerScopeAndProofGate.test.ts`: v3/v4/v5 peers get `pairwise` and DI options; v1/v2/unknown get a 1.1 VRC and `Ed25519Signature2018`; across versions VC 2.0 implies DI. `diConformance.test.ts`: eddsa-rdfc sign and verify with and without evidence, tampering with `issuerScope` fails, `issuerScope` without the registry context refuses to sign, the witness VP wrapping the new VRC verifies, an old `Ed25519Signature2018` VRC still verifies. **Not verified:** a real-device hardware-signed exchange; a witness process built from this tree handling a v5 peer end to end (the witness is covered by unit and `vrc-reference` tests only); an old-peer simulation for the v2 fall-back beyond the gate tests.

## 4. Real-device runs 2026-09-30
Same author, same day. Device runs on two Android phones (Android-only, real hardware).
### 4.1 What ran

- **Witnessed exchange** (Android-only): passed. The harness asserted the exchange completed and the Verified (Witnessed) badge on the contact ("Secure Exchange" and "In-Person" were not required on this run).
- **Attested exchange** (Android-only): passed. The harness asserted the hardware-evidence marker and the Secure Exchange badge; on one phone the badge was absent and the assertion continued because the log showed verification had been attempted (the lenient branch of the badge assertion).
- **Hardware verification failed on both phones**: `Certificate chain validation failed: timestamp check failed ... Root certificate expires in -129 days` (an expired Google attestation root). The runs passed despite it because the harness tolerates an attempted-but-failed verification by default. The cause is diagnosed in §4.4.
### 4.2 No VRC JSON had been captured, and why

Neither run logged a single issued-credential line, so the credential checker proved nothing about `@context`, `issuerScope` or the Data Integrity proof on hardware. The cause was in the app, not in the capture: the marker was logged only when a DIDComm credential exchange reached `done` (`vrc-manager.ts`, credential state handler). Between v4+ peers the VRC is delivered and stored by the Trust Task ceremony (`trust-tasks/ceremony.ts`), which never drives a credential exchange; the witnessed log shows "v4 pair — witness ceremony rides the trust-task session; legacy witness flow stands down".

Fix: the same single-line, PEM-elided log is now written by the ceremony when the VRC is sent (`side=ISSUER`) and when it is stored (`side=RECEIVER`); the redaction helper moved to `vrc-credential-log.ts` and wire bytes are unchanged. The harness was also changed to keep the continuation lines of a payload Android splits at about 4 KB, and to run the credential checker when a run finishes (a missing credential or a wrong shape fails the run; hardware-verify failures stay warnings unless strict markers are requested). An opt-in `E2E_REQUIRE_HW_VERIFIED=1` makes the badge assertion require an actual native-verification-passed marker. The checker was not yet proven on a device when this was written.

### 4.3 Swapped-phone run: wrong evidence context, and its cause

The swapped-phone witnessed run (15:28-15:34) captured the issued VRCs for the first time. `issuerScope` was `pairwise` and the proof was `DataIntegrityProof`/`eddsa-rdfc-2022`, but `@context` was `[credentials/v2, registry v1, https://www.firstperson.network/dtg/v1]`, the legacy entry, although both wallets logged `Received relationshipDid via message ... (RCE v5)` and stored it.

Cause: `handleInboundPropose` and `handleInboundProposeResponse` in `trust-tasks/ceremony.ts` call `updateCounterpartyRelationshipDid(..., TRUST_TASKS_MIN_RCE_VERSION)`, and the repository assigned that value unconditionally. `TRUST_TASKS_MIN_RCE_VERSION` is 4, the floor for speaking the dialect, not what the peer announced. The ceremony therefore overwrote the stored 5 with 4 before the VRC was built, so `counterpartyRceVersionAtLeast(..., 5)` was false while the `>= 3` VC 2.0 and DI checks still passed. The gate itself, the lookup timing and the catch-returns-false path were not at fault; the existing gate tests passed because they seed the version directly.

Fix (bifold 66c67d40f): `RelationshipDidRepository.updateCounterpartyRelationshipDid` only raises `counterpartyRceVersion`, never lowers it; regression tests in `RelationshipDidRepository.test.ts`. This is inference from code and the run's logs; it is not yet proven on a device.

Next device run must show, for every issued VRC between two v5 phones: `@context` is `[credentials/v2, registry v1, https://www.firstperson.network/hardware-evidence/v1]` with no `dtg/v1` entry (`check:vrc:witnessed --expect v5`), plus the unchanged `issuerScope`, proof type and StrongBox evidence. It also has to sign and verify under the new context on device, which has not been exercised yet.

### 4.4 G39: the Android verifier no longer rejects factory chains whose root has lapsed

Both phones attest with a factory-provisioned chain (StrongBox, 4 certificates). Across the real-device runs the S25 reported `timestamp check failed ... Google attestation root expires in -129 days ... Attestation extension not found in leaf` for the S20+'s evidence, while the S20+ verified the S25's evidence as `valid=true`, in both role assignments (§4.3), so the swap did not separate evidence from verifier. Two defects in `react-native-attestation`, found by code analysis and not yet seen on a device:

1. `GoogleAttestationChainValidator` ran PKIX at the current time over the whole chain, leaf included. The S20+ chain ends in the legacy factory root (`SERIALNUMBER=f92009e853b6b045`), which expired 2026-05-24, so it fails on any device whose chain reaches that root. Google's guidance (security key attestation page, updated 2026-07-09) and its `android/keyattestation` verifier keep trusting chains to that root regardless of validity.
2. `parseAttestationExtension` read `attestationSecurityLevel` and `keymasterSecurityLevel` with an INTEGER-only reader. The `KeyDescription` schema types them ENUMERATED (tag `0x0A`), so the read threw and the caller reported "Attestation extension not found in leaf". It now accepts both tags.

Fix (bifold `45818a042`), following Google's rules: the root is matched by subject and public key, not by serial number or by trusting the last certificate; signatures, issuer names and CA flags are checked; the leaf's validity is not checked; on a factory chain (root subject `SERIALNUMBER=f92009e853b6b045`) expiry is ignored for the rest of the chain; a certificate that is not yet valid fails on any chain; on every other Google root (RKP) the intermediates and root must be within their validity period. The `validateChain` signature gains optional `anchors` and `now` parameters so the rules are testable.

Tests: `GoogleAttestationChainValidatorTest` adds 13 cases over openssl-generated chains (`src/test/resources/gen-chains.sh`): expired factory chain, valid factory chain, not-yet-valid intermediate, RKP with an expired leaf, RKP with an expired intermediate and with an expired root, tampered leaf, foreign leaf, imposter root (same subject, different key), non-CA intermediate. Gate: `cd app/android && ./gradlew :bifold_react-native-attestation:testDebugUnitTest --offline` (the package has no `test` script; this is its Gradle JUnit gate), 23 tests, all green. The ENUMERATED parse is covered only indirectly: `Asn1Parser` is private to `AttestationModule`, so it is exercised on a device, not in JUnit.

The harness's logcat dump filters now include `HW:`, so the `[HW:Verify]`, `[HW:Evidence]` and `[HW:Sign]` lines reach the saved device logs.

**Unverified, and what the next 2-phone run must show** (needs an APK rebuilt from the bumped submodule, since this is native code): both phones log `valid=true` for each other's evidence, in both role assignments; no `timestamp check failed` or `Attestation extension not found in leaf`; `[HW:Verify]` lines are present in the saved logs. The iOS verifier (`Attestation.mm`) is untouched and unverifiable on this host. G33 Stage 1 touches the same native verifier files and lands after this.

### 4.5 G33 Stage 1: the verifier always recomputes the signed content hash

Implemented as specified in `hardware_evidence_binding_subtask.md` §4.3 (options D + E), in three bifold commits (`470239ed5` JS, `21b1bc505` Kotlin, `981dd0444` Obj-C++) and a superproject bump (the same change was later replayed onto bifold `main` as `34d22d31b`/`e95a7dc3a` for the JS gate, `05644e05f` for Kotlin and `b56782647` for Obj-C++, with the pinning test `13f35ec22`). Signed bytes, the signer and the wire format are unchanged; no RCE bump; Stage 2 (JCS bytes) and the evidence-context gate are untouched.

- **JS** (`core/src/hardware-signing/binding.ts`, `verify.ts`): `verifyEvidence` requires `signedContent` (empty is `valid: false`, native not called); compares a present `signature.signedContentHash` with `base64(SHA-256(UTF-8(signedContent)))` and returns `contentBindingMismatch` without calling native; passes the recomputed hash, never the embedded one, as the sixth native argument; maps a native `contentBindingMismatch` error to `signatureValid: false`. SHA-256 is `@noble/hashes/sha2.js`. This adds a fourth permitted dependency to the `hardware-signing` directory, so `credo-free-boundary.test.ts`'s allowlist and the `index.ts` header were updated with it.
- **Kotlin** (`ContentBinding.kt`, `AttestationModule.kt`): `clientDataHash` is always the recomputed SHA-256. A non-empty supplied hash that is undecodable, not 32 bytes, or different fails with the `contentBindingMismatch` prefix, on the Apple CBOR path and the raw DER path; empty content is an error; the two "cross-device" log lines are gone. `ContentBinding` uses `java.util.Base64`, so it runs under plain JUnit.
- **Obj-C++** (`Attestation.mm`): the same rules through a static helper `checkSuppliedClientDataHash`, on both paths; a wrong-length or undecodable value is an error, no longer a silent fallback. **Unverified: not compiled, not run, not reviewed on a host with Xcode.** Kept minimal; no TurboModule spec change.
- **Tests:** `content-binding.test.ts` (U1-U8 plus the native-error mapping and a SHA-256 cross-check against Node); `vrcSignedContentKeyOrder.test.ts` now embeds the genuine hash, so the Credo round trip must reproduce the signed bytes for native to be called (U9 for the legacy scheme). Existing fixtures that carried an unrelated placeholder `signedContentHash` were corrected, since the gate rightly rejects them. Kotlin: `ContentBindingTest` (8 cases). Gates run: `core` `yarn test` (325 suites green after the fixture fixes), root `yarn typecheck`, and `cd app/android && ./gradlew :bifold_react-native-attestation:testDebugUnitTest --offline` (31 tests green).
- **Not done in Stage 1:** S1.4's new log assertions (`contentBindingMismatch` absent, the per-platform "signature valid" lines); `E2E_REQUIRE_HW_VERIFIED` already exists (§4.2). The Node real-signature negatives (U2/U3/U7 against a captured App Attest assertion) need a captured iOS fixture that does not exist yet. U10-U13 belong to Stage 2. `docs/HARDWARE_ATTESTATION_FLOW.md` "iOS hash trust" (G34) is not yet corrected.

**Unverified, and what a device run must show** (Android APK rebuilt from the bumped submodule, iOS device app rebuilt with `FORCE_BUNDLING=1`, Metro `--reset-cache`): every genuine direction still verifies (iOS to Android, Android to iOS, iOS to iOS, Android to Android), with the "Secure Exchange" badge on each receiver; zero `contentBindingMismatch` in any log (a hit means some path re-serializes the VRC between signer and verifier, and the path must be found before shipping); no `Embedded hash differs` line (it no longer exists, so a hit means a stale binary); Android logcat shows `✓ Apple CBOR assertion signature valid` for iOS-origin evidence and iOS shows `3/3 Assertion signature: VALID`. On the two Android-only phones, Android to Android must stay `valid=true` (G39 also applies).

### 4.6 G36 reversed: the evidence-context swap deploys now

**What changed.** §3.5 recorded "hold back" (commit `b58dbc6e`, plan Q10): keep the legacy `@vocab` context on the wire through the next live demo and deploy the swap afterwards, witness first. Later on 2026-09-30 Brendan reversed it: the swap deploys now. Plan decision Q10 on the stack and the G36 row in §2 say so.

**Why.** The deployment is beta and pre-production. Brendan controls the phones and can update the witness before any wallet sends the new context, which removes the ordering risk that made holding back attractive (§3.5: the RCE v5 gate protects wallets only, and an un-upgraded witness cannot canonicalize a VRC carrying the new IRI). What he gains is that the first hardware run under the new context happens a week before the demo, not after it. The cost, accepted by him, is a shorter window to fix any surprise from that run; the legacy context is retained in code for peers below RCE v5, so reverting the APK restores the old behaviour with no witness change.

**Rollout constraint.** (1) Rebuild the witness from a tree containing `45e02d5b3` and the later fixes and deploy it first. It needs no code change, because `@bifold/vrc-shared`'s loader serves the context from the bundle with no network fetch, and it keeps serving the legacy context to v4 peers. (2) Only then rebuild the APK from the same bifold commit. (3) Run the two-phone device proof (`yarn e2e:vrc:witnessed:devices`, then the credential check): every issued VRC's `@context` is `[credentials/v2, registry v1, https://www.firstperson.network/hardware-evidence/v1]` with no `dtg/v1`, `issuerScope` and proof type unchanged, and the exchange shows the Witnessed badge.

**Not yet true.** Nothing is deployed. The v5 gate fix (bifold `66c67d40f`), the G39 root-validation fix and G33 Stage 1 are all unproven on devices, and the witness has never run end to end against a v5 peer (unit and `vrc-reference` tests only).

- The credential checker, run by hand with no path after a run finishes, reads the run transcript too, and that transcript holds the harness's own echo of the issued-credential lines cut to about 50 characters, so it reports five truncated or unparsable FAILs on a run that is good (the in-run check, which does not read the transcript, passes). Pointing it at the explicit device-log and credential-dump files gives the true verdict.
- `Credential verification failed: Verification error(s).` appears once per phone per run in the React Native log. It is the `[DI self-test]` tamper case (`tamper rejected`, PASS on the next line) and also appears in the 2026-09-30 runs; it reads like a real failure and is not one.
