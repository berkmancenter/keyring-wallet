# 2026-09-30 (bam) — the evidence block's context, and the byte-exact registry context

Decisions recorded with the change (see `vsc-migration-plan.md` §2.6 for the resulting design).

## G29 — the legacy `@vocab` was the only thing making evidence signable

**Finding.** `buildVrcCredential` listed `[credentials/v2, registry v1, DTG_CONTEXT_URL]`. The registry context defines no term of the hardware-attestation `evidence` block; `DTG_CONTEXT_URL`'s `@vocab` (`https://www.firstperson.network/dtg#`) was the only reason JSON-LD safe-mode signing accepted it. A `@vocab` also signs any misspelled member silently (demonstrated: `hardwareBindng` canonicalizes to a quad under the legacy context, throws under the new one), and the VCDM says `@vocab` SHOULD NOT be used in production.

**Adopted.** A dedicated `@protected`, `@vocab`-free context (`HARDWARE_EVIDENCE_CONTEXT_*` in `@bifold/vrc-contexts`). Types `BiometricAttestation`, `DeviceAuthentication` (the two authentication types `HardwareEvidenceBuilder` emits) and `HardwareKeyAttestation` (always emitted alongside one of them). The member terms sit in a type-scoped context on `HardwareKeyAttestation`. `created` is `dcterms:created` as `xsd:dateTime`. `authenticationMethod`, `biometricMethod`, `hardwareBinding`, `attestation`, `signature` are `@type: @json`: the certificate chain is an ordered array, and plain JSON-LD arrays are sets, so only a JSON literal (JCS-canonicalized) makes the chain order part of the signature. Verified: canonical output is identical under the real registry `v1` and the earlier two-term stand-in, and reversing the chain breaks a Data Integrity signature.

**Namespace.** Provisional: `https://www.firstperson.network/hardware-evidence/v1` / `#`, following the `<base>/<name>/v1` convention of the other Keyring contexts. Keyring does not control that host. One constant pair, commented as provisional. Not decided: whether upstream publishes such a vocabulary and where.

## G30 — rollout gate

**Finding.** A wallet without the new context cannot resolve its IRI offline, so an older peer would reject the VRC.

**Adopted (most conservative option).** `RCE_PROTOCOL_VERSION` 4 to 5; the new context is listed only when the peer announced v5 or higher, otherwise the legacy context is kept. The legacy document stays in every loader (dual-read).

**Alternative not taken.** Negotiate by `supportedTypes`-style capability discovery (as the Trust Task ceremony does for `vrc/relationships/propose`) instead of an ordinal version. It would avoid spending a protocol number on one context, but it needs a discovery round trip before the VRC is built and the legacy basic-message dialect has no channel for it. A product decision if a finer-grained capability is wanted.

**Open risk.** The witness is not a peer with an RCE version. A witness server that predates the context cannot canonicalize a v5 peer's VRC carrying it; the witness must be upgraded before (or with) wallets that announce v5.

## G31 — the registry context is bundled verbatim

The previous `REGISTRY_DTG_CONTEXT_DOCUMENT` defined 2 of the 18 terms of the real `v1`. It is now the real document's bytes (kept as a string, parsed), pinned by test to SHA-256 `3e1376ac...0bb448` (multibase `zQmSWyCagdx8...`), and compared byte-for-byte to `external/dtgwg-vsc-registry/contexts/v1.jsonld` when that clone is present. No existing expected output changed: the VRC never used the other terms. This does not execute D7 for the witness credential (G26 still stands): `WITNESSED_EXCHANGE_CONTEXT_DOCUMENT` and the `vsc` `@context` order are untouched.

**Not verified:** a real-device hardware-signed exchange on the new context.

## 3. The evidence/`@context` investigation

### 3.1 VCDM and Data Integrity facts, with corrected citations

Earlier working notes mis-cited these; the section numbers below are the corrected ones.

- *"Optional properties MAY be ignored"* is in **VCDM 1.3 Conformance**, not in the extensibility sections.
- `@vocab`: **5.2 Semantic Interoperability** says it SHOULD NOT be used in production, and carries a conditional MUST that a context defining undefined terms, or the `v2` context, comes last. The `credentials/v2` context itself has no `@vocab`.
- `evidence` is defined in **5.6 Evidence**.
- **Data Integrity 2.4.3**: data loss during canonicalization MUST throw. **2.4.1 / 4.6**: context validation.

### 3.2 What the DTG specification says, and does not say (pin `94af2d8`, `spec/body.md`)

- `@context` rule, line 188: first `https://www.w3.org/ns/credentials/v2`, second the registry `v1` IRI, *"followed by any contexts a proof type, a predicate profile or a community vocabulary requires"*.
- `proof.type`, line 199: *"`proof.type` MUST be `DataIntegrityProof`, with the cryptographic suite named in `proof.cryptosuite`"*.
- Context Versions, lines 228-236, including the pre-v1 sentence at 236: *"Credentials issued before the Implementers Draft of this specification are not conformant to it, whatever context IRI they list. Contexts published before `v1` under other IRIs are not recognized, and a verifier is not required to process a credential that lists one."*
- Predicate Profiles item 5, line 805: *"A verifier MUST ignore additional members a profile does not define"*. Scoped to `credentialSubject` members of a profile.
- Security Considerations item 8, line 1330 (*Context integrity*): verifiers should bundle the context and check it against the published digest.

The specification has **no rule on `evidence`, on extension members outside a profile, or on `@vocab`** (a search of `spec/body.md` for `@vocab` finds nothing; its uses of "evidence" are the ordinary-English sense).

### 3.3 The emitted evidence block, and what it means for the signature

`HardwareEvidenceBuilder.buildEvidenceBlock` (`bifold/packages/core/src/hardware-signing/evidence.ts`, line 338) emits:

```
id: urn:uuid:<uuid>
type: ['BiometricAttestation' | 'DeviceAuthentication', 'HardwareKeyAttestation']   // DeviceAuthentication when authenticationMethodType is DevicePasscode
created: <ISO string>
authenticationMethod: { type, authenticatorType: 'platform', userVerification: 'required' }
hardwareBinding: { keyStorage, platform, keyType: 'EC-P256', algorithm: 'ECDSA-SHA256', publicKey }
attestation: { format, certificateChain: string[] }
signature: { value, algorithm: 'ECDSA-SHA256', signedContentHash? }
biometricMethod: { type, authenticatorType, userVerification }                    // only when not passcode (backward compatibility)
```

The credential's `@context` is inside the bytes the hardware key signs, so the context list is part of what a verifier must reproduce. Under the **legacy** `@vocab` path (`DTG_CONTEXT_URL`): `certificateChain` order is unprotected (a JSON-LD array is a set), `created` is an untyped plain string, and a misspelled member is signed silently. `credentials/v2` has no `@vocab` to fall back on, which is why G29 needed a context at all.

# Part 3 — G32 implemented: `issuerScope` and Data Integrity on every VC 2.0 VRC

Same author, same day; extends this file. Present-tense design is in `vsc-migration-plan.md` §2.6.

## 7.1 What was decided

- **`issuerScope` is `pairwise`.** Checked in code rather than assumed: `getOrCreateRelationshipDid` (`vrc-manager.ts`) creates a new `did:peer:0` with a fresh Ed25519 key per counterparty connection DID, stores the mapping, and returns the same DID only for the same counterparty (concurrent callers share one creation). Nothing passes that DID to a second counterparty, so the identifier in `issuer` is pairwise. The specification recommends `pairwise` for a VRC. Q8's `directed` (plan §3.6) concerns the witness's single identifier across all sessions and is unchanged. One caveat: the relationship DID is also shown to the witness during a witnessed exchange as presenter; that is the same relationship's counterparty ceremony, not a second correlation context for the VRC.
- **The VC 2.0 path gets it; VCDM 1.1 does not.** The 1.1 path has no registry context, so the term would not be signable; it is untouched.
- **RCE v2-only peers fall to the VCDM 1.1 path.** The smallest change that leaves no VC 2.0 VRC with a non-DI proof was to raise the VC 2.0 gate (`counterpartySpeaksVc20`) from RCE v2 to RCE v3; since v3 implies DI, `useDi` is now always true inside the VC 2.0 branch. The Ed25519 suite context is no longer appended for any VRC the wallet builds (`selectCredentialContexts` keeps the branch for direct callers and tests). `RCE_PROTOCOL_VERSION` stays 5. **Wire behaviour an old peer sees:** a peer announcing exactly RCE v2 now receives a VCDM 1.1 VRC instead of a VC 2.0 one, and no RCard (the RCard gate uses the same function). Every build at v2 or below already reads the 1.1 VRC (it is what v1 peers receive) and can do without an RCard. No build is known to announce v2 without v3 (pre-production, all apps assumed current), so this is expected to affect no real peer. The rejected alternative was keeping v2 peers on VC 2.0 with `Ed25519Signature2018`, which is the non-conformant emission G32 names.
- **Left alone on purpose:** the challenge-bound VP that wraps a VRC for the witness is still `Ed25519Signature2018` (a presentation, not a VRC; the witness dual-verifies); the `vrc-reference` demo `Participant.ts` still issues VC 2.0 VRCs with `Ed25519Signature2018` and no `issuerScope`; `docs/CRYPTO_SUITE_FOLLOWUP.md` Decision 6 text describes the old gate and was not edited.

## 7.2 Consumers checked

- **Witness (`witness-server`, `@bifold/vrc-shared` loader).** `credentialBuilder.ts` reads `issuer`, `validFrom`/`issuanceDate`, `proof` and `evidence[*].hardwareBinding.publicKey`; it validates no VRC shape strictly and the digest is JCS, so an added member neither breaks nor reorders anything, and changing `issuerScope` changes the digest. Identity Check is `verifyCredential` with `demoDocumentLoader`, which resolves the registry and evidence contexts (`vrc-shared/src/documentLoader.ts`).
- **VWC digest edge** (`object.digestMultibase` over `taskDigestMultibase(vrcJson)`, RFC 8785): key-order independent, covers `issuerScope`. The Trust Task payload schemas (`additionalProperties: false`) sit on the delivery envelopes, not on the VRC.
- **Hardware-signed bytes.** The wallet signs `JSON.stringify(credential)` after `issuerScope` is set and before `evidence`/`proof`; `extractSignedContent` strips those two and restores `@context` first. ## 8.5 G39: the Android verifier no longer rejects factory chains whose root has lapsed

Both phones attest with a factory-provisioned chain (StrongBox, 4 certificates). Across the real-device runs the S25 reported `timestamp check failed ... Google attestation root expires in -129 days ... Attestation extension not found in leaf` for the S20+'s evidence, while the S20+ verified the S25's evidence as `valid=true`, in both role assignments (§8.4), so the swap did not separate evidence from verifier. Two defects in `react-native-attestation`, found by code analysis and not yet seen on a device:

1. `GoogleAttestationChainValidator` ran PKIX at the current time over the whole chain, leaf included. The S20+ chain ends in the legacy factory root (`SERIALNUMBER=f92009e853b6b045`), which expired 2026-05-24, so it fails on any device whose chain reaches that root. Google's guidance (security key attestation page, updated 2026-07-09) and its `android/keyattestation` verifier keep trusting chains to that root regardless of validity.
2. `parseAttestationExtension` read `attestationSecurityLevel` and `keymasterSecurityLevel` with an INTEGER-only reader. The `KeyDescription` schema types them ENUMERATED (tag `0x0A`), so the read threw and the caller reported "Attestation extension not found in leaf". It now accepts both tags.

Fix (bifold `45818a042`), following Google's rules: the root is matched by subject and public key, not by serial number or by trusting the last certificate; signatures, issuer names and CA flags are checked; the leaf's validity is not checked; on a factory chain (root subject `SERIALNUMBER=f92009e853b6b045`) expiry is ignored for the rest of the chain; a certificate that is not yet valid fails on any chain; on every other Google root (RKP) the intermediates and root must be within their validity period. The `validateChain` signature gains optional `anchors` and `now` parameters so the rules are testable.

Tests: `GoogleAttestationChainValidatorTest` adds 13 cases over openssl-generated chains (`src/test/resources/gen-chains.sh`): expired factory chain, valid factory chain, not-yet-valid intermediate, RKP with an expired leaf, RKP with an expired intermediate and with an expired root, tampered leaf, foreign leaf, imposter root (same subject, different key), non-CA intermediate. Gate: `cd app/android && ./gradlew :bifold_react-native-attestation:testDebugUnitTest --offline` (the package has no `test` script; this is its Gradle JUnit gate), 23 tests, all green. The ENUMERATED parse is covered only indirectly: `Asn1Parser` is private to `AttestationModule`, so it is exercised on a device, not in JUnit.

E2E dump filters now include `HW:`, so the `[HW:Verify]`, `[HW:Evidence]` and `[HW:Sign]` lines reach the saved logcat artifacts (`witnessedExchangeFlow.js`, `run-vrc-exchange-devices-android-only.js`).
