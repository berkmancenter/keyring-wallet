## G10 — The witness display-name regression (flagged at V4, §3 D1) is fixed: `witnessName`, a new D5 extension member

**Evidence.** V4's `issuer` string fix (both WD02 and WD 0.4.0 require a bare
string) removed the only place a witness's human-readable name lived
(`issuer.name`), leaving `witnessCredentialUtils.ts`'s `extractWitnessInfo`
with no way to resolve anything but the generic `"Witness"` fallback for any
credential minted after that fix. Checked directly: `credentialSubject.id`
is the *observed VRC's issuer* (D6), not the witness — so reusing the
generic `schema:name` term there, as a shortcut, would assert the wrong RDF
subject's name.

**Position adopted.** `witnessName` is a new D5-pattern extension member —
sibling of `witnessContext`, Keyring-namespaced, ignorable by any verifier
that does not define it (C10) — exactly the same shape as `locality*` and
`hardwareAttestationIncluded`, not a special case. `extractWitnessInfo` reads
it first, falls back to the legacy `issuer.name` object form (harmless
insurance for any pre-V4-fix credential still in existence), then
`"Witness"`. Committed `bifold` `83a5af0e7` on new branch
`feat/vsc-witness-name-and-shape-default` (based on `feat/vsc-issuer-scope`),
outer pointer bump `896c28cd`. Verified: `witness-server` 20/21 · 735/735
(+5 new tests), `core` 315/315 · 3182/3184 (+5 new tests), no regressions.
Plan text updated: §3.5 (new member), §8 note near "Touch the VRC's shape."

## G12 — Q8 decided: `issuerScope` stays `directed`

**Evidence.** §9 Q8 asked whether `directed` or `public` is the truthful
value for Keyring's actual witness deployment — explicitly a deployment
fact, not a technical question. Brendan confirmed: *"we have no permanent
witness — we have just demo/test witnesses right now."* `public` asserts a
witness DID is durably, broadly discoverable by anyone, not just the two
parties and the governing community (per the spec's own worked-example
convention for "a party that must be findable" generally) — untrue of a
disposable test identity by construction, so declaring it would be the less
truthful claim, not the more conservative one.

**Position adopted.** No code change — `directed` was already what
`WitnessService.ts:377` emits. §9 Q8 marked decided rather than open, with
an explicit revisit trigger: a permanent witness with a durably-published
DID (e.g. a stable `did:webvh`), at which point flipping to `public` is a
one-line change, not a redesign.

## G13 — `taskDigestMultibase` is REQUIRED as of the advanced pin (G9's sibling, G15 below); a placement bug found and fixed; one gap found and left open

**Evidence.** The `dtgwg-cred-spec` pin advance (G15) surfaced a requirement
invisible at the plan's original `994a3d63`/`b89f389` baseline:
`taskDigestMultibase` is now normatively REQUIRED wherever `taskContext` is
required, at the same top level, sibling of `credentialSubject` — not
nested inside it. Checked directly: `@bifold/trust-tasks`'s
`taskDigestMultibase`/`digestBytesEqual` (§3.1, built independently
2026-08-20) already implement the correct encoding (base58btc multibase over
a sha-256 multihash of the JCS form, compared as decoded bytes) — the
Trust-Tasks session-ceremony path's bug was placement, not encoding: it
nested the value inside `credentialSubject` unconditionally, and the
wallet's read side (`witnessCeremony.ts`) had no top-level fallback the way
`taskContext`'s own read sites already did (§3, D4's four-site table).

**A separate, real gap found and correctly left open, not fixed.** The
*legacy basicmessage-dialect* witnessed-exchange path — `WitnessService.ts`'s
`buildWitnessCredentialJson`, the code `vrc-reference`'s `witnessedFlow.test.ts`
exercises, distinct from the Trust-Tasks session-ceremony path this fix
touched — emits neither `taskContext` nor `taskDigestMultibase` at all for
`vsc` shape. That dialect predates the Trust Tasks framework and may have
nothing to cite as a task context; deciding what it should cite, if
anything, is a real design question this session did not resolve.

**Position adopted.** Fixed the placement bug: `WitnessTaskSessions.ts`
(issuance) and `witnessCeremony.ts` (verification, dual-read: top-level with
a fallback, matching `taskContext`'s own pattern). `wd02`'s pre-existing
non-conformance here (nested placement) is untouched — it was never meant to
track current spec text (§6 V4's own framing for `wd02` generally). Committed
`bifold` `be8dd6044` on new branch `feat/vsc-task-digest-multibase` (based on
`feat/vrc-namespace-registry-alignment`, G14), outer pointer bump `615dc09c`.
Verified: `witness-server` 21/22 · 738/743 (+3 new tests, 0 failed), `core`
315/315 · 3183/3185, root `yarn typecheck` clean, `ref-07-dtg-edge-semantics`
re-run green. Plan text updated: §3 (new paragraph after D4's read-site
table).

## G14 — VRC's own namespace migrated to the real registry, dual-read — adjacent to this plan, not part of its design

**Evidence.** `DTGCredential`/`RelationshipCredential`'s own vocabulary
(`bifold/packages/vrc-contexts/src/relationshipContext.ts`) still targeted
the old placeholder namespace this plan itself moved off of for the witness
credential (§2.5). Given Brendan's "align everything possible" instruction
and confirmation that a real, current, normative standard now exists for
this too (cred-spec `spec/body.md` at `94af2d8`: `@context` MUST list
`https://registry.trustoverip.org/dtg/context/v1` — the same registry V1/V2
already target — `type` MUST include `DTGCredential` plus exactly one
concrete subtype), this was migrated too.

**Why dual-read, not a hard cutover, and why this matters more here than it
did for the witness server.** The witness server is a stateless deployed
service (§7's framing) — flipping its default has no persistent-state risk.
VRC is the client-side peer-to-peer feature, and whether real VRCs already
exist between real devices from internal dogfooding is not a fact
recoverable from the repository. Rather than betting on "probably not," new
VC 2.0 issuance was moved to the registry namespace while every existing
document loader keeps resolving the old self-hosted context documents
unchanged, so any already-issued or legacy VRC keeps verifying exactly as
before — the "does dogfooding data exist" question is made moot rather than
answered. Proven with a real Credo sign/verify round trip
(`vc20Conformance.test.ts`), not only a JSON-LD shape assertion.

**`RCard` deliberately left on the old namespace — no real target exists.**
Cred-spec `spec/body.md:21` (at `94af2d8`) states RCard is *"not a
`DTGCredential` subtype"* and *"will be defined in the planned DTG
Verifiable Data Structures specification"* — an intention, not a published
document with a real IRI. Same situation as `createVrcDocumentLoader.ts`'s
VTI/trust-tasks placeholder context (confirmed 404 as of 2026-09-27, no
change here) — nothing to migrate to yet.

**Why this is recorded here but is not a phase of this plan.** §8 states
this plan does not touch the VRC's *shape*, and that remains true — nothing
about VRC's fields or structure changed, only which `@context` new issuance
targets. But it is adjacent enough to this plan's own namespace work (§2,
§2.5) that a reader could reasonably wonder whether §8's exclusion still
holds; it does, and this finding exists so that isn't ambiguous.

**Position adopted.** Committed `bifold` `0dafd72b3` on new branch
`feat/vrc-namespace-registry-alignment` (based on
`feat/vsc-witness-name-and-shape-default`, G10/G11), outer pointer bump
`7dd4494d`. Verified: real sign/verify round trip green (4/4 legacy round
trips unchanged, +1 new registry-namespace round trip), `core` 315/315 ·
3183/3185 (+1 net), `witness-server` 21/22 · 738/743, root `yarn typecheck`
clean, relevant `tsp-reference` ladder rungs (`ref-07`, `-07c`, `-07e`,
`-07h`, `-07i`) all green. Plan text updated: §8's "Touch the VRC's shape"
bullet, with a pointer here.

## G16 — Capture-harness rebuild: the tool now exists and is committed; a fresh `vsc`-shaped capture does not, and is blocked on a real architectural gap

**Evidence.** §6 V5 named rebuilding the capture harness as its own,
separate, unstarted task — the original tool that produced
`edge-witnessed-captured.json` was never committed (`captureEdge.local-al.test.ts`,
confirmed absent from git history), a deliberate convention, not an
oversight (a sibling fixture, `edge-pairwise-captured.json`, has the exact
same story). Rebuilt: `captureWitnessedEdge.test.ts`, entirely in-process
(real Askar-backed Credo agents, no live mediator/witness-server needed),
reproducing the existing frozen fixture's exact shape as a regression guard,
with a `CAPTURE_OUTPUT=1` mode to write a fresh (gitignored, throwaway)
sample.

**Why no fresh `vsc`-shaped capture, checked directly rather than assumed
feasible.** `vrc-reference`'s own credential builder
(`Witness.buildWitnessCredential`) is a separate, hardcoded legacy builder —
it never reads `WITNESS_CREDENTIAL_SHAPE` and structurally cannot emit `vsc`
shape. The real `vsc` builder is `witness-server`'s
`buildWitnessCredentialJson`, but that package has no library entrypoint —
its `package.json` `main` is a CLI entry pulling in server-only dependencies
(`langchain`, `node-ble`, `three`, `ws`), not meant for reuse from a test.
Producing a genuine `vsc`-shaped capture needs either a live witness-server
process (the same live-infra requirement the e2e proof is already blocked
on, §9) or a real library-export refactor of `witness-server` — both
independently bigger than "rebuild the capture tool," and neither attempted
here rather than faked.

**Position adopted.** Committed `bifold` `afa81d753` on new branch
`feat/vsc-capture-harness` (based on `feat/vsc-task-digest-multibase`, G13),
outer pointer bump `17b3ffe6`. Verified: `captureWitnessedEdge.test.ts` 1/1
pass (with and without `CAPTURE_OUTPUT`), root `yarn typecheck` clean. §6
V5's text updated to state the tool exists and the `vsc`-capture gap
precisely, rather than "not started."
