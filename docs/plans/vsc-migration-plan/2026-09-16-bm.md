## F1 — The deprecation is a collapse of types into a vocabulary, not a rename

**Evidence.** `spec/body.md` at `994a3d63` carries a new *VSC (Verifiable
Statement Credential)* section whose editor's note states: *"The VSC replaces the
concrete `EndorsementCredential` and `WitnessCredential` subtypes of Working
Draft 02, which are now the `dtg:endorses` and `dtg:witnessed` profiles below.
The names VEC and VWC are retained for those profiles. The type strings
`EndorsementCredential` and `WitnessCredential` are not retained."* The commit is
`5a660ea` *"Add the verifiable statement credential (VSC)"*; the glossary entry
`spec/terms-definitions/verifiable_witness_credential.md` now opens *"A VSC under
the `dtg:witnessed` predicate profile…"*.

**Position adopted.** The migration is scoped to the **wire shape**, not to
vocabulary in prose or code identifiers. The plan says so in §1 and the file
survey in §4 is built on it.

**What it supersedes.** The framing this investigation started from — "convert
from the deprecated VWCs to VSC credentials" read as a find-and-replace across
~2,200 occurrences. A naive grep-and-replace of "VWC" would be **wrong**: the
specification retains the name and only drops the type string. Sizing the work
by the word inflates it by two orders of magnitude and, worse, produces a diff
that renames correct prose while missing the digest coverage change of F4.

## F2 — The vocabulary repository does not exist, and this was checkable

**Evidence.** `gh repo list trustoverip --limit 100` on 2026-09-16 returns
sixteen `dtgwg-*` repositories — `dtgwg-cred-spec`, `dtgwg-trust-tasks-tf`,
`dtgwg-zkp-spec`, `dtgwg-vti-spec`, `dtgwg-trust-tasks-spec`, `dtgwg-zkp-tf`,
`dtgwg-vds-spec`, `dtgwg-agent-names-spec`, `dtgwg-htx-tf`, `dtgwg-cred-tf`,
`dtgwg-rahp-tf`, `dtgwg-rcards-tf`, `dtgwg-vds-tf`, `dtgwg-ux-tf`,
`dtgwg-general`, `dtgwg-agent-names-tf`. **`dtgwg-predicate-vocab` is not among
them.** The spec's *Related Specifications* section says of the DTG Predicate
Vocabulary and its siblings: *"None has been published yet."*

**But it is fully specified.** cred-spec [#52](https://github.com/trustoverip/dtgwg-cred-spec/issues/52)
(OPEN) gives the repository layout, the per-predicate definition format, the
generated artifacts, and — decisively — **a verbatim `witnessed.jsonld` and a
verbatim `accept-list.json` entry**. Both are quoted into the constraints
companion as C13.

**Position adopted.** Build a **mirror** of the registry in the shape #52
specifies, not an invention of our own. The plan's §2.2 splits it into a
deletable mirror and a permanent consumer, and `ref-22`'s acceptance criterion
(a) is that our generated `accept-list.json` is byte-equal to #52's example
modulo the namespace constant.

**Why that framing and not a simpler one.** The obvious cheap move is a hardcoded
`const WITNESSED = 'https://…#witnessed'` and an `if`. It works, and it leaves
nothing to delete when upstream publishes — the seam disappears into the
codebase and the migration becomes archaeology. Mirroring an artifact format
someone else has already specified costs one generator script and buys a
deletion that is a single directory.

## F3 — The namespace is guaranteed to change, and that is survivable by design

**Evidence.** The spec's own notation note: *"The namespace shown is a
placeholder: its home is decided in [#48], and the final form carries no version
segment."* The current value `https://firstperson.network/credentials/dtg/v1#`
**has** a version segment, so it cannot be the final form under either option in
#48. #48 itself: *"Changing the namespace later is a find-and-replace in the spec
but a migration for every credential issued under it… That cost is zero today
and grows with every issued credential."*

**The mechanism that makes it cheap is in the spec, not invented here.**
*Predicate Handling* step 2: *"The set of accepted vocabularies is the verifier's
configuration… It is never derived from the credential."* A verifier's accepted
set is therefore **ours to choose**, and accepting two IRIs for one predicate
while issuing under one is conforming. That yields the four-state rolling cutover
in plan §2.3, which `ref-22` criterion (f) is written to prove.

**Position adopted.** Issue under the spec's placeholder verbatim; put it behind
one exported constant; treat #48 as a rolling cutover.

**Rejected: issue under a Keyring-controlled namespace.** #52 permits it —
*"a community that publishes a predicate under a namespace it controls can issue
under it… without waiting on or ever seeking admission"* — and it would make us
immune to #48. **The constraint that rules it out** is that `dtg:witnessed` is a
core profile the specification itself defines, under a namespace the
specification itself names (*"Predicates defined by this specification live in the
DTG namespace"*), and #52's admission criterion 5 is *"has no existing term with
the same meaning — one identifier per concept"*. Minting a Keyring `witnessed`
forks the core vocabulary to dodge a rename we have already made cheap. Recorded
in plan §2.4 as standing rationale, because it is exactly the option a future
reader re-proposes on finding the placeholder still placeholding.

Note the asymmetry with F6: the same argument **does not** apply to our locality
and hardware-attestation members, which have no DTG equivalent and belong in a
namespace we control. One rule, two answers, because the inputs differ.

## F4 — The digest change is three breaks, and `ref-07` records one of them as stale

**Evidence, at the pin.** `git show b89f389:spec/body.md` line 382:
*"`digest` (string, REQUIRED): … MUST be computed as the SHA-256 hash of the
credential's JSON representation canonicalized with JCS … and MUST be encoded as
the string `sha256:` followed by the lowercase hexadecimal digest."* **The whole
credential.**

**Evidence, at `994a3d63`.** *Digest Encoding*: *"Take the referenced
credential's JSON representation **excluding its top-level `proof` member**, and
canonicalize it with JCS … Form a Multihash value … Encode … with the
base-58-btc alphabet and prefix the Multibase header `z`."* Plus: *"Verifiers
MUST NOT rely on string comparison."*

**Evidence, in our code.** `bifold/packages/witness-server/src/WitnessService.ts:215`:

```ts
export function computeVrcDigest(vrcJson: unknown): string {
  return 'sha256:' + createHash('sha256').update(jcsCanonicalize(vrcJson)).digest('hex')
}
```

Its caller at `:264` passes `credentials[0]` straight off the observed
presentation — **a signed VRC, proof included**. The two `delete …proof` calls at
`:2427`/`:2447` are inside a `if (this.config.verbose)` canonicalization-debug
block and do not touch the digest.

**The stale claim.** `tsp-reference/ref-07-dtg-edge-semantics/run.mjs:348-349`
reports the gap and characterises it: *"KNOWN GAP: this VWC digest is legacy
`sha256:`+hex, not the multibase multihash of #17 / PR #18"* … *"the rename is
exactly PR #18's `digestMultibase` change, **already specified as
encoding-only**"*. That was accurate against the pin and is **no longer
accurate**: the WD 0.4.0 rule hashes a different document. A transcoder that
re-encodes the existing hash would pass `ref-07`'s check and fail the
specification.

**Position adopted.** Plan §3.1 splits D3 into three named breaks and gives
`ref-21` a negative case whose entire purpose is the third one. Plan §6 V5
corrects `ref-07`'s check text **while keeping the check running against the
legacy fixture** — the ladder records superseded claims rather than deleting
them.

**This is the finding that justifies the constraints companion.** A claim true at
a pin and wrong four weeks later, sitting inside a green test, is precisely the
failure `docs/plans/README.md` rule 5 and the `openvtc-workspace` skill's
verify-against-the-pin rule exist to catch. It was caught here only because the
digest section was re-read rather than trusted.

## F5 — The primitive the migration needs is already written and already tested

**Evidence.** `bifold/packages/trust-tasks/src/documentProof.ts:49-83` exports
`digestMultibase` (JCS → sha-256 → multihash → base58btc),
`taskDigestMultibase` (the same, minus the document's top-level `proof`), and
`digestBytesEqual` (decoded-multihash-byte comparison). `taskDigestMultibase`'s
doc comment already cites *"cred-spec, Trust Task Context Binding"*.

Line for line, that **is** *Digest Encoding*. `object.digestMultibase` over a VRC
is `taskDigestMultibase(vrcJson)`; C6's decoded-byte comparison is
`digestBytesEqual`.

The root `CLAUDE.md` declares `trust-tasks` platform-neutral — *"no Node-only or
RN-only imports allowed"* — so the witness server and the wallet can both call
it. That is exactly the property D3 and D6 need, and it is already guaranteed by
a rule with a reason.

**Position adopted.** V4 **deletes** `computeVrcDigest` rather than porting it.
`ref-21` verifies the shape with an implementation written from the constraints
file, so the rung is an independent check rather than a tautology against the
library it is testing.

## F6 — Hoisting the extension members out of `witnessContext` is a locality-plan win, not a migration cost

**Evidence, the profile.** The `dtg:witnessed` profile defines `witnessContext`
with exactly three OPTIONAL members: `event`, `sessionId`, `method`.

**Evidence, what we put there.** `buildWitnessCredentialJson` adds
`hardwareAttestationIncluded`, optionally `localityVerification` (the deprecated
nested shape), and then `Object.assign(witnessContext, localityAssertion)` — the
fourteen flat `locality*` terms.
`witness-server/src/trustTasks/WitnessTaskSessions.ts:591-593` adds `parties` and
`taskDigestMultibase` to `credentialSubject`.

**Evidence, that carrying them is conforming.** *Predicate Profiles* point 5:
*"A verifier MUST ignore additional members a profile does not define… strictness
lives in the predicate, not in the payload."*

**Evidence, that `witnessContext` is about to get a schema.** #52's
`witnessed.jsonld` sets
`additionalMembers.witnessContext.schema` to
`https://trustoverip.org/dtg/vocab/schemas/witness-context.schema.json`.

**The finding that decided it.** `locality-plan.md` requires flat `locality*`
members because *"bbs-2023 discloses at the RDF-quad level, and a nested object
is a blank node whose path must be revealed before disclosing anything under
it."* Today they are flat **inside `witnessContext`** — which is itself a nested
object. The blank-node problem was moved up one level, not solved. Hoisting to
`credentialSubject`, which the VSC's *"further members as the profile defines"*
mechanism invites, is the first arrangement that delivers what the locality plan
actually asked for.

**Position adopted.** Plan §3.5: `witnessContext` keeps the profile's three
members and nothing else; everything else becomes a sibling under a
Keyring-controlled namespace.

**Rejected: a second VSC under a Keyring `coPresent` predicate.** Cleaner on
paper — locality is a distinct statement with distinct evidentiary weight — and
rejected on a constraint rather than on taste: the profile says *"the meaning of
a witness attestation depends on the conditions under which the witnessing
occurred"*, so those conditions are part of what `dtg:witnessed` means. Split
into a separate credential, a party could present the witnessing **without** its
conditions, which is a weaker artifact than the one we ship today. The practical
cost — doubled artifacts, a second taskContext binding, a changed ceremony reply
shape that four `ref-06p*` rungs are built around — is real but secondary.
Preserved in plan §3.5 with the condition under which it should be revisited.

## F7 — Two of the eight deltas are verifier obligations we do not implement at all

**Evidence.** Grepping `bifold/packages/core/src/modules/vrc` and
`.../modules/trust-tasks` for digest recomputation against the VWC's
`credentialSubject.digest` returns **nothing outside tests**. The only
implementation of that check in the repository is
`tsp-reference/ref-07-dtg-edge-semantics/run.mjs:327-338`, out of band. Nothing
anywhere checks that `credentialSubject.id` equals the referenced VRC's `issuer`;
the witness sets it correctly at `WitnessService.ts:268` (`vrcIssuer`) and no
consumer verifies it.

**What we do check** is at the Trust Task layer:
`core/src/modules/trust-tasks/witnessCeremony.ts:221-232` verifies
`vwcDigestMultibase` against `digestMultibase(vwc)` and the §4.9.3 task digest
against `taskDigestMultibase(sessionDoc)`, both with `digestBytesEqual`. The
right shape, on a different edge of the triangle: it binds the VWC to its
session, never to the VRC it attests.

**Why this matters beyond conformance.** The profile says a VWC's subject and
`taskContext` *"identify only the observed party and the trust task exchange, not
the edge being witnessed"*. A Keyring contact's witness badge today is drawn from
a credential whose binding to the VRC on the same screen is asserted by the
witness and verified by nobody. D6 is not a box-tick; it lets the wallet make a
stronger claim than it currently makes, from artifacts it already holds.

**Position adopted.** Plan §6 V3 implements D6 and D8 **before** V4 changes
issuance, and §3.3 states the user-visible gain so the work is not read as pure
compliance.

**Second-order note, not yet a position.** WD 0.4.0 makes the subject–issuer
binding **unconditional**, where WD02 required it only for bidirectional
exchanges. The editor's note gives the reason — *"a verifier holding a VWC and
the credential it names cannot tell whether that credential was one half of a
reciprocal pair, so a rule that depends on it cannot be checked"*. Our issuance
already satisfies it in both cases, so this costs us nothing; it is recorded
because it means a **third-party** verifier can now run the check, which is what
`ref-06p3-third-party-verify` exists to do.

## F9 — Seven-day expiry is the reason this migration is cheap, and it has three qualifications

**Evidence.** `DEFAULT_CREDENTIAL_EXPIRATION_DAYS = 7` in both
`witness-server/src/WitnessService.ts:111` and
`core/src/modules/vrc/vrc-manager.ts:164`. Seven days after the witness cuts
over, every **valid** VWC in existence is a VSC.

**The three qualifications, which are the actual content of the finding.**

1. **Expiry governs validity, not storage.** Contacts render witness badges from
   stored `W3cCredentialRecord`s and nothing prunes expired ones, so the
   **display** path must read both shapes for longer than seven days. Plan §7
   therefore gives the dual-read a **stated deletion date** — one release after
   V4 ships to the last channel, recorded beside the code. A tolerance without a
   date becomes permanent.
2. **The witness is a deployed service; the wallet is an installed app.** We
   control the rollout of one and not the other. This dictates V3-before-V4, and
   it is the reason the plan's phases are ordered verification-then-issuance
   rather than the other way round.
3. **Structural distinguishability is load-bearing.** `WitnessCredential` and
   `StatementCredential` differ in the `type` array, so a dual-reader never
   guesses. The spec's *Compatibility Rules* make this explicit for MAJOR
   revisions. Had the WG kept the type string and changed only the subject, no
   safe dual-read would exist — worth recording as a piece of luck we should not
   count on next time.

## F12 — Every shipped proof suite is RDF-canonicalized, which makes the vocabulary mandatory

**Evidence.** `core/src/modules/vrc/vrc-manager.ts:438-446` negotiates exactly
two proof suites by RCE version: `DataIntegrityProof` with
**`eddsa-rdfc-2022`** for v3+ peers, and **`Ed25519Signature2018`** otherwise —
the file's own comment says *"RCE v3+ … DataIntegrityProof/eddsa-rdfc-2022, older
peers keep Ed25519Signature2018 (docs/CRYPTO_SUITE_FOLLOWUP.md, Decision 6)"*.
Both canonicalize with URDNA2015.

**What this corrects.** The parent plans discuss `eddsa-jcs-2022`, and F1–F10
inherited that framing. `eddsa-jcs-2022` is the **recommendation** of
`docs/CRYPTO_SUITE_FOLLOWUP.md` and cred-spec #18; it is **not what we ship**.
The difference is load-bearing: JCS hashes the JSON, so an untermed member is
still signed, whereas under RDF canonicalization **an untermed member does not
exist in the signed graph at all**. Reading this migration as "JCS, so the
vocabulary is optional" would have been a silent-failure-shaped mistake.

**Position adopted.** New plan §3.7 states the constraint and derives V2's
ordering from it: terms land in V2, members in V4, one change at a time, and the
`localityVocabulary.test.ts` quad-counting guard generalised to every VSC member.
This is now the plan's stated highest-risk item — the one most likely to present
as an inexplicable verification failure rather than a clean error.

**Explicitly not claimed.** This is true **at our pin**, not necessarily at

`verifiable-trust-infrastructure: FETCH FAILED`, so the clone cannot presently be

## F14 — The predicate-awareness tail is two call sites, not thirty

**Evidence.** The `credentialTypes.ts` predicates have **30** non-test call sites
across `bifold/packages/core/src` and `app/src`. Of those, exactly **two** pass a
bare type array rather than a credential object — both `isWitnessCredential(types)`
in `core/src/modules/vrc/vrc-manager.ts`. Every other site passes `raw`,
`credJson`, `credentialData` or an equivalent whole-credential value.

**Why it was worth measuring.** Plan §1 calls the predicate-aware split *"the one
place where the migration is a design change rather than a substitution"*, and
the file's tolerant-input contract (*"a credential JSON, a `type` array, or a
single type string"*) reads like a warning that call sites everywhere hold only a
string. They do not. Both exceptions are in the file that builds VRCs, which has
the full credential in scope and can simply pass it.

**Position adopted.** Plan §4 records the measurement. The design change stands —
it is real, and `isWitnessCredential` genuinely cannot answer the new question
from a type array — but it is a small change, and the plan should not have let a
reader budget for an audit of thirty sites.

## F15 — The fixture we most need to regenerate has no committed tool

**Evidence.** `tsp-reference/ref-07-dtg-edge-semantics/README.md` credits
`edge-witnessed-captured.json` to
`bifold/packages/vrc-reference/__tests__/integration/captureEdge.local-al.test.ts`,
calling it an *"untracked local capture tool"*. That file is **not** in that
directory — eleven integration tests are, and it is not among them — and
`git log -- '…/captureEdge*'` returns nothing. It was never committed.

**Why it matters.** `edge-witnessed-captured.json` is the highest-value fixture
in the repository: a real five-phase witnessed exchange over real Credo agents,
and the input to `ref-23`'s entire premise (plan §5). Regenerating it after the
wire change means **rebuilding the capture harness first**.

**Position adopted.** Plan §6 V5 names it as a task to budget for rather than a
discovery to make at the end, and requires the rebuilt harness to be
**committed** — so the next wire change does not pay this cost a second time.

**Not resolved here:** whether the original tool still exists on someone's
machine. If Alberto has it (the `local-al` suffix suggests so), recovering it is
cheaper than rebuilding it. Worth one question before anyone starts.
