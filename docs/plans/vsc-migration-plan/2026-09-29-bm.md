## G19 — `@openvtc/vti-tsp-js`'s pure-ESM package broke witness-server's process startup entirely; never caught because nothing had launched the real process

**Evidence.** `witness-server`'s tsconfig targets `"module": "commonjs"`, so
both `ts-node` (dev) and the compiled `node dist/index.js` (production)
compile every `import` from `@bifold/trust-tasks`'s TSP codecs down to a
`require('@openvtc/vti-tsp-js')` call. The vendored tarball ships
`"type": "module"` with an `exports` map offering only an `"import"`
condition — no `"require"` condition for CJS to resolve against. Result:
`ERR_PACKAGE_PATH_NOT_EXPORTED`, thrown before the witness-server binds a
single port, on **every** invocation. Reproduced directly:
`node -e "require('@openvtc/vti-tsp-js')"` fails against the original
tarball, succeeds once a `"require"` condition (pointing at the identical
file the `"import"` condition already uses) is added — Node 20.19+/22+ can
`require()` a genuine ES module natively once the package's own exports map
offers a path to it.

Never caught before today because every prior verification of this
migration's own phases was Jest-based (which papers over ESM/CJS interop via
its own transform config), and the one CI path that actually builds and runs
a real container (`staging-witness.yaml`) only triggers on a PR into
`staging` — no branch carrying this code has ever opened one.

**Position adopted.** Patched the vendored tarball's `package.json#exports`
(three entries, each gains a `"require"` key equal to its existing
`"import"` value — no source or `dist/` output changed, confirmed by
`diff -r` against the pre-patch tarball extraction). Baked into
`build-vti-tsp-js.mjs` as a post-build, pre-pack step, documented in the
vendor `README.md`, so a future pin bump doesn't silently lose it. Flagged
as a good candidate to send upstream (any CJS/`ts-node`/non-bundler consumer
on a modern-enough Node hits the identical crash; the fix is
backward-compatible and costs ESM consumers nothing) — not done, needs
Brendan's decision on drafting and sending it, per this repo's own
upstream-contribution convention (`openvtc-workspace` skill).

`bifold` `75b574773` on `feat/vsc-real-device-fixes` (based on
`feat/vsc-capture-harness`).

## G20 — `dtg-vocab`'s accept-list loaded via `fs`/`path`, breaking Metro bundling; never caught because nothing had bundled this code path for a real device

**Evidence.** `acceptList.ts`'s `loadAcceptList()` used
`readFileSync(join(__dirname, ...))` to read `accept-list.json` at runtime —
fine under Node (Jest, `ts-node`, the compiled server), but this module is
also reachable from the **wallet app's own bundle**
(`@bifold/core`'s `credentialTypes.ts`/`witnessCeremony.ts` call
`loadAcceptList()` directly), and Metro has no `fs`/`path` polyfill:
`Unable to resolve module path from .../dtg-vocab/src/acceptList.ts`.

**Position adopted.** Same fix as this migration's own V1 precedent for
exactly this class of problem: `resolveJsonModule` was already on in this
package's `tsconfig.json`, so a static `import acceptListJson from
'../vocab/dist/accept-list.json'` resolves identically from `src/` and from
compiled `build/` output — `tsc` inlines the parsed JSON directly into the
emitted `.js` (confirmed by inspecting `build/index.js` after rebuilding),
so this is if anything a stronger guarantee than the old runtime read, not a
weaker one.

## G21 — `configure(loadAcceptList())` never loaded `witnessContext`'s named schema at either app call site; every witnessed credential failed verification, unconditionally, from the moment V1 shipped

**Evidence.** `predicateHandling.ts`'s `verify()` (cred-spec C4, step 3):
for any `additionalMembers` entry that names a schema but whose `validate`
function is `null` (i.e. no schema was ever loaded into the `schemaStore` at
`configure()` time) — `if (m.schemaUrl && !m.validate) return
reject('schema for ${name} named but not loaded at configuration time')` —
an **unconditional** rejection whenever that member is present in the
credential, regardless of the credential's actual validity. The accept-list
names a real schema for `witnessContext`
(`https://registry.trustoverip.org/dtg/vsc/witnessed/1/witness-context.schema.json`),
and both app call sites — `witnessCeremony.ts:60`, `credentialTypes.ts:99` —
called `configure(loadAcceptList())` with no second argument, defaulting to
`{}`. The package's own schema file was already bundled
(`dtg-vocab/vocab/schemas/witness-context.schema.json`) and already used
correctly by the package's own test suite (`predicateHandling.test.ts`
builds a real `schemaStore` and passes it) — only the app's own two call
sites missed it.

This means: from the moment V1 shipped the accept-list with a schema
reference for `witnessContext`, **no witnessed credential could ever pass
this specific check in the live app**, on either the wallet or witness-server
side. Never caught because nothing had previously exercised the live app's
own predicate verification against a real witness ceremony, end to end, on
either shape — every earlier verification (V1–V5, `issuerScope`) checked the
codec/vocabulary layer directly, not this call path.

**Position adopted.** New export `loadSchemaStore()` (`schemaStore.ts`,
mirroring `loadAcceptList()`'s own static-JSON-import pattern), wired into
both call sites. No design change to `predicateHandling.ts` itself — its
behavior is correct and already tested; the app just never gave it what it
asked for.

## G22 — The VC 2.0 VRC's `@context` dropped `DTG_CONTEXT_URL`'s `@vocab`, silently rejecting any credential with real hardware-attestation evidence

**Evidence.** G14 (2026-09-28) migrated the VC 2.0 VRC's `@context` to
`[credentials/v2, REGISTRY_DTG_CONTEXT_URL]` — the real registry namespace,
correctly ordered per cred-spec. The registry context defines only
`DTGCredential`/`RelationshipCredential`, with **no top-level `@vocab`**; the
legacy `DTG_CONTEXT_URL`'s `@vocab` is what covers the hardware-attestation
`evidence` block's own terms (`attestation`, `hardwareBinding`, ...). Without
it, JSON-LD safe-mode signing rejects any VC 2.0 VRC carrying real
attestation evidence: `Error issuing W3C JSON-LD VC. Safe mode validation
error`, caught generically as `[TrustTasks:Ceremony] VRC delivery after
acceptance failed`, with no further detail reaching the log (a separate,
noted gap — see G24). Reproduced and isolated directly with
`jsonld.expand(..., {safe: true})` against the app's real bundled contexts:
registry-context-only + an evidence block fails with this exact error,
property `attestation`; registry + `DTG_CONTEXT_URL` + evidence passes.

Silent on emulators (which skip hardware attestation entirely and fall back
to a plain, unattested exchange — root `CLAUDE.md`) and in every existing
test (`vc20Conformance.test.ts` never builds a credential with an evidence
block); only surfaced on a real, attended, hardware-attested exchange
between two real devices — this is very likely why G14 itself never caught
it, verified as it was against Jest-only conformance tests.

**Position adopted.** `DTG_CONTEXT_URL` appended alongside
`REGISTRY_DTG_CONTEXT_URL`, not instead of it — cred-spec's ordering
requirement (registry IRI second, after `credentials/v2`) is preserved; the
legacy context lands third. Every document loader already resolves both
IRIs (G14's dual-read), so already-issued and legacy credentials keep
verifying unchanged either way. Must be set before hardware signing:
`BiometricSignatureVerifier.extractSignedContent` only strips
`evidence`/`proof`, so the context can't be appended after signing without
invalidating the hardware signature — this rules out a lazier "detect and
patch" fix at the signing boundary.

`bifold` `b8325c1f8` on `feat/vsc-real-device-fixes`.

## G23 — The outcome-evidence self-check still read `taskDigestMultibase` from the pre-migration nested location, after G13 moved its emission to the top level

**Evidence.** G13 (2026-09-28) fixed `taskDigestMultibase`'s *emission* to
sit at the top level, a sibling of `credentialSubject`, per the spec's Base
Structure requirement for `vsc` shape. `outcomeEvidence.ts`'s self-check
(the last step before a witness-share is sent) still read it only from the
old location: `const taskDigest = String(subject?.taskDigestMultibase ??
'')`, where `subject` is `credentialSubject`. Since the field no longer
lives there, this read always returned empty, and the self-check
unconditionally failed: `outcome-evidence self-check failed — witness-share
withheld: credential carries no taskDigestMultibase` — on the one path G13
had actually fixed correctly. `readTaskContext()`, immediately above this
line, already had the correct dual-read pattern (top-level first, nested as
fallback) for the sibling field `taskContext`; `taskDigestMultibase` was
simply never given the matching update when G13 landed.

Found on the same run that finally exercised this exact check end to end
for the first time — every earlier failure this session (G19–G22) was
upstream of ever reaching it.

**Position adopted.** New `readTaskDigestMultibase()`, mirroring
`readTaskContext()`'s dual-read exactly. The now-unused `subject` local
(nothing else in the function used it) removed.

`bifold` `9a008d7b5` on `feat/vsc-real-device-fixes`, final tip.

## G24 — The e2e harness itself hardened: four real bugs in the tooling, one environmental surprise, and a new preflight script

**Evidence, tooling bugs, each independent of G19–G23:**

- `flows.js`: `RCardLastNameInput`/`RCardSubmit` used a bare `byTestId(...).
  setValue(...)` with no wait or scroll. On a shorter physical viewport
  (`1080x2340` vs. a working device's `1080x2400` at the same density),
  `RCardLastNameInput` renders just past the ScrollView's visible bottom
  edge, and UiAutomator2 omits off-screen nodes from the accessibility tree
  entirely — no amount of waiting ever made it appear, only scrolling does.
  An initial fix (adding `waitForTestId`, believing the cause was a
  `SiblingNoticeDismiss` overlay race) did not resolve it; the real cause
  was found by cross-referencing a failure screenshot against the actual
  device serial in the Appium session log (see the next bullet for why that
  cross-referencing was harder than it should have been). Fixed with
  `scrollToTestId` (already a no-op if the element is already visible).
- `driver.js`: `screenshot()`/`dumpSource()` named failure artifacts only
  `<label>-<platform>-<timestamp>` — indistinguishable between two Android
  devices except by which log lines happened to be nearby. This mismatch
  sent one investigation the wrong direction for the better part of an hour
  (a screenshot showing a fully-onboarded device was mistaken for the
  *failing* device's state, when it was actually the other one) before an
  independent review caught it by cross-referencing Appium session IDs
  against the tap-event log. Fixed: filenames now include a filename-safe
  device tag.
- `witness.js`: the spawned witness-server process silently inherited
  `WITNESS_LLM_ENABLED=true` from a developer's local, gitignored
  `witness-server/.env` — `dotenv` never overrides a variable already
  present in the environment, the identical class of bug the harness had
  already handled for `MEDIATOR_INVITATION_URL` (see that override's own
  comment). A real Anthropic API call per witness message adds
  unpredictable latency no fixed-timeout assertion can account for. Forced
  to `"false"` by default; explicit opt-in via `WITNESS_LLM_ENABLED=true` to
  deliberately test the LLM path. (Turned out not to be the actual cause of
  that day's specific failure — G22 was — but is a real, independent
  correctness fix for harness determinism regardless.)
- `witnessedExchangeFlow.js`: `dumpAndroidWitnessLogs`'s filter regex
  dropped `[TrustTasks:Ceremony]` and `[VRC Flow]` — exactly the tags
  carrying the real error messages that explained G22 and G23 ("Safe mode
  validation error", "credential carries no taskDigestMultibase"). Every
  artifact captured before this fix hid the actual cause, forcing a fresh
  `adb logcat -d` pull mid-investigation instead. Broadened to include
  `TrustTasks`, `VRC Flow`, and both known failure-dialog strings verbatim.

**Evidence, environmental:** one device's screen locked mid-run (a
Samsung "start dream immediately on dock" setting — the charging animation
takes over the instant the phone is plugged in, independent of the
screen-off timeout), which Appium cannot see past or interact through.
Diagnosed from a failure screenshot showing only a charging percentage on a
black screen. A fix that disabled the screensaver via `adb shell settings
put` was initially added to the preflight script unconditionally, then
**reverted at Brendan's explicit direction**: real, persistent, user-visible
device settings — one of these two phones is a daily driver — are not this
harness's business to change without being asked, unlike the disposable
test app it fully owns. Re-added as an opt-in check
(`--manage-device-settings` / `E2E_MANAGE_DEVICE_SETTINGS=1`, off by
default, nothing reverted automatically) rather than removed outright, so
the diagnosis and fix are still available on request.

**Position adopted.** All four tooling fixes plus a new
`e2e/preflight-real-devices.mjs` — checks (in order): exactly two physical
devices; a clean app install on both (auto-fixed, not just checked — the
disposable test app is this harness's own, unlike device settings); Metro
serving this worktree; `app/.env`'s `MEDIATOR_URL` actually reachable (a
dead cloudflared tunnel from a past session, and no mediator running at
all, separately cost a full attended run before being found); the built APK
newer than `app/.env`'s last change (`react-native-config` bakes `.env` at
compile time, not JS runtime — a stale bake is silent); witness-server's
ports free; witness-server's compiled build actually booting without
crashing (a cheap, generic smoke check that would have caught G19 and G20
without needing to know either one specifically); `cloudflared` installed.
Device settings deliberately excluded from the default checks, per the
paragraph above.

## G27 — the legacy-dialect gap made explicit in code; `proofExchange.test.ts` genuinely fixed, not just documented

Two more items closed the same day, in a later working session on top of G26
(`bifold` `e764baa80`, `6aa398d3c`; outer `f19af993`, `2c49972c`).

**The legacy basicmessage-dialect `taskContext` gap (§3 D4, §9's cred-spec `#58`
neighbor) is confirmed structural, not accidental, and now says so in code.**
Traced `WitnessService.ts`'s `buildWitnessCredential` (the private wrapper
around `credentialBuilder.ts`'s `buildWitnessCredentialJson` that the legacy
basicmessage dialect actually calls): its session (`SessionData`) is a purely
in-memory bookkeeping record — a `sessionId`, a `challenge`, `Map`s of received
presentations — never exchanged with either party as a real, content-bearing
document, unlike the Trust-Task dialect's real `witness/session` document that
gets JCS-canonicalized and digested for `taskDigestMultibase`. Per
`dtgwg-cred-spec`, `taskContext` "holds the originating Trust Task `threadId`"
and outcome interpretability requires "the matching outcome artifact
[to be] reachable" — neither exists for this dialect, so emitting a fabricated
`taskContext` would assert a citable Trust Task document that doesn't exist,
which is actively wrong, not merely incomplete. **No code change was the
correct answer here**, confirming what G25 already flagged as a real design
question rather than a mechanical fix. What *did* change: a related, previously
undocumented fact found while tracing this — `buildWitnessCredential`'s call
to `buildWitnessCredentialJson` (`WitnessService.ts:2594` at the time) never
passes `shape` at all, so this dialect silently always emits `wd02` regardless
of `WITNESS_CREDENTIAL_SHAPE`'s now-`vsc` default, indistinguishable from an
oversight. Added a doc comment at the call site (`bifold` `e764baa80`) stating
explicitly that this is deliberate and permanent — the dialect predates the
Trust Tasks framework and structurally cannot supply a conformant `taskContext`
for `vsc` shape — so a future contributor doesn't "fix" it into emitting a
fabricated task citation.

**`proofExchange.test.ts`'s two remaining failures (of the original 5 — see
G25's "now 1, not 5") are genuinely fixed, not a documented limitation.**
Investigation found the earlier root-cause attribution was half right:
Keyring's shipped app *does* reach this code path for real — `bc-agent-modules.ts`
registers `DidCommDifPresentationExchangeProofFormatService` as a live proof
format, and `ProofRequest.tsx`'s real "accept incoming proof request" screen
has a generic branch that routes any DIF-Presentation-Exchange request,
including a VRC, through `agent.modules.didcomm.proofs.acceptRequest()`. So
this was live product exposure, not a reference-tool-only concern — any
relying party requesting a VRC via the standard protocol would have hit this
crash on a real device. The actual hardcode, traced to source, is **not**
`@credo-ts/core`'s `W3cCredentialService.createPresentation()` (never called
in this chain) but `@animo-id/pex@6.1.1`'s `constructPresentations()`
(`app/node_modules/@animo-id/pex/dist/*/lib/PEX.js`), which unconditionally
force-appends `CREDENTIALS_CONTEXT_V1_URL` to the VP's base context regardless
of what the caller supplies, combined with `DifPresentationExchangeService.createPresentation()`
never supplying a v2 alternative in the first place. Fixed with two coordinated
patches, verified together (fixing either alone left a mismatched or empty
context that still failed): pex's `constructPresentations()` changed to only
default to v1 when the caller supplies no base context at all
(`if (context.length === 0)` instead of `if (!context.includes(v1))`), and a
new hunk added to the existing `@credo-ts/core` patch giving
`DifPresentationExchangeService.createPresentation()` a new
`getVc2BasePresentationPayload()` helper that supplies
`basePresentationPayload: { '@context': [CREDENTIALS_CONTEXT_V2_URL] }` when
every credential being wrapped is VC2.0-shaped `LdpVc` — mirroring the file's
own existing `shouldSignWithAnonCredsW3cService` pattern.

**Non-obvious discovery mid-fix: `bifold` is a fully separate yarn workspace
from the outer `keyring-wallet` app, with its own `node_modules`/`.yarn/patches`/
`package.json` resolutions, independent of the outer repo's.** The first pass
at this fix patched only the outer repo's dependency tree and appeared to work
(`yarn install`/`typecheck` clean there) — but `vrc-reference`'s own tests
resolve `@credo-ts/core`/`@animo-id/pex` from `bifold/node_modules`, which never
received the patch, so re-running `proofExchange.test.ts` still failed
identically. Confirmed by checking the actually-resolved package version in
each tree, and by grepping the installed `node_modules` copies directly for
the new function name rather than trusting `yarn install`'s exit code. Both
patches were applied a second time, independently, inside `bifold`'s own
`.yarn/patches/`/`package.json` (bifold's own pex resolution was previously
absent entirely — it resolved `6.1.1` transitively with no patch at all).
After that: `proofExchange.test.ts` **7/7 passing** (both previously-broken
tests, run directly), full `vrc-reference` and `witness-server` suites
confirmed green with no regressions. `vrc-reference` now shows **0 of 12
integration suites failing**, down from the original 5 — the last one closed
for real, not deferred.
