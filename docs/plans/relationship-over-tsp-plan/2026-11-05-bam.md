## 2. Registry binding facts

Read from trust-tasks-tf `origin/main` (status of every binding: draft; framework `SPEC.md` is Working Draft 0.7.0).

- **`bindings/tsp/0.1` targets TSP "Implementers Draft (Rev 2)"** (`spec.md` lines 22 and 235, §10 references), while the TSP specification is now Release 1.0. The binding targets framework `0.5.0`. It says a TSP message carrying a Trust Task "MUST be sealed and signed by TSP's authenticated encryption". The binding defines no DID service type; it "resolves a VID through TSP's own mechanism".
- **Binding proof rule.** In direct and nested TSP the proof MAY be omitted; in non-nested routed carriage it SHOULD be included, since only the last hop is authenticated. The framework's rule (§9.1.1, "Permitting proof to be Omitted") makes silence not permission. The shared-connect design asks for proofs on every step regardless, which is stricter than the binding needs.
- **Relationship prerequisite.** The binding's §5.4 leaves relationship forming to TSP. `affinidi-tsp` enforces it (`RelationshipPolicy::Gated` by default), so `XRFI` must precede `propose` against an affinidi-based reference.
- **Service types.** The framework defines no service-type-to-binding mapping. Only `https/0.2` and `0.3` (§6.2) name one, `TrustTaskHTTPS`, and say "the DIDComm binding resolves `DIDCommMessaging` … and the TSP binding resolves a VID through TSP's own mechanism". `TSPTransport` appears nowhere in trust-tasks-tf; it is the string the VTA and Keyring read.
- **Binding set.** `didcomm` (DIDComm v2.1) 0.1 and 0.2, `didcomm-v1` 0.1 and 0.2, `https` 0.1 to 0.3, `tsp` 0.1, and `push` 0.1 exist in the registry. DIDComm is therefore a registry binding, not only a Keyring one.

### 2.1 Resolvers and service spellings differ between stacks

As understood on 2026-11-05 and not re-measured here:

| Stack | `did:peer` numalgo | `TSP` service spelling read |
|---|---|---|
| VTA resolver library | 0 and 2 (the library parses 1 but does not resolve it); numalgo 4 not resolved | `TSPTransport`, delivering through a mediator DID |
| Keyring (Credo) | 2 and long-form 4, resolved locally | `TSPTransport` (reader in `tspCapability.ts`, `VtiMediatorTransport.ts`) |
| TSP reference implementation | numalgo 4 only | a service of type `tsp` with a `{uri}` object endpoint |

Consequences recorded in the plan: readers of the flow should resolve both numalgos; producers should use `did:peer:2` for codes shown in person because it is compact (about 450 characters or fewer for an in-person code, QR versions 14 to 16; a 1,000-character budget needs version 26 at level M, so a ceiling of 990 was suggested for links that travel); and no single `TSP` service spelling is read by all stacks. "`TSPTransport` plus a mediator DID" must therefore not be assumed as the one form: it breaks the TSP reference's `did:peer:4` parser. The plan's WP2 and Q3 ask the counterparts for a real vector for this reason. The offline path (the responder showing a signed `propose` as a code) was estimated at 1,200 to 1,400 characters with `did:peer:2`, from the thread's examples and not measured, which is over the code budget, so it stays cut.

## 3. Findings behind the plan's verdict

1. **Existing Keyring connections do not shorten the work.** The trigger link is not an out-of-band invitation, the counterparts run no Aries connection protocol, and the ceremony is keyed by Credo connection records (state, repositories, UI stores). Choosing DIDComm only swaps the carriage.
2. **The TSP carriage that exists is not a starting point.** `TspCarriage` wraps TSP in a DIDComm v1 message on an existing connection and is wallet-to-wallet by design. The connectionless pieces that matter are in the VTI module (`VtiMediatorSession`, `greetPeerOverTsp`, `unpackTrustTaskFromPeer`).
3. **The credential gate is the quiet blocker.** Because the RCE version defaults to 1 for a peer that never announces, a naive reuse of the VRC builder produces a VCDM 1.1 credential with `Ed25519Signature2018`. Proofs and key choice (decision 3) add a second late failure point.
4. **TSP failure is silent.** Missing relationship, wrong revision, crossing mediators and oversize frames all look like silence from the sender's side; cross-operator TSP completed nowhere in the 2026-09-22 measurements (same-mediator accept in 1.15 s; cross-operator DIDComm v2 about 1 s).
5. **Estimate basis.** Sizes are one developer who knows the codebase. The full scope (WP1 to WP13) sums to roughly 13 to 16 days; the thin demo to about 9; the DIDComm variant to about 8.
