# 2026-09-18 — bam

## Crop UX bug: the OS `allowsEditing` crop step returns a stale image

**Reported**: after picking a new photo for a profile, the app displays a
different, already-saved profile's photo instead of the one just picked and
cropped.

**Concluded**: the crop step (`ImagePicker.launchImageLibraryAsync({
allowsEditing: true, aspect: [1, 1] })` in what was `RCardForm.tsx`'s
`pickAndProcessRCardPhoto`) delegated cropping to the OS's own picker/editor
UI. On Android this is a known failure mode of `expo-image-picker`'s
`allowsEditing`: the crop activity can hand back a stale, previously-cropped
image instead of the one the user just selected, because the underlying
native crop implementation writes its output to a reused temp file/URI that
isn't reliably refreshed between invocations. The app had no way to detect
or correct this — whatever URI the OS handed back was trusted as the fresh
selection.

This also matches §3.4's original design, which already named
`expo-image-manipulator` as covering "resize/rotate/**crop**" — the
`allowsEditing: true` shortcut was an implementation deviation from that,
introduced without a plan update, that happened to reintroduce the native
crop step's instability.

**Superseded**: the plan's §6 open question "Crop/aspect-ratio UX ... is not
designed yet — needs a design pass" is resolved differently than that framing
suggested. No interactive crop/pan UI was designed or built. Instead, the
native OS crop step was removed outright: the picker now returns the raw
selected asset (with its own width/height), and this app's own
`processRCardPhoto` (`bifold/packages/core/src/modules/vrc/utils/rcardPhoto.ts`)
center-crops it to the largest square before the existing resize/compress
pipeline runs. This is deterministic and keyed only to the picker's own
just-returned asset URI, so there is no shared/reused output file for
staleness to hide in. A user-adjustable crop (pan/zoom to choose which part
of a non-square photo survives the center-crop) is still undesigned and
still needs a design pass if wanted later — this fix does not add one, it
only removes the buggy native delegate.

**Also fixed alongside**: `EditRCard.tsx` didn't key its `<RCardForm>` by
which profile (or "new") it's editing, so `RCardForm`'s
`useState(initialValues ?? EMPTY_RCARD_FORM)` — which only runs on first
mount — could carry a previous profile's `formState` (including its photo)
into a later render if the screen instance were ever reused for a different
`profileId` (e.g. via a stack navigator's default same-route param-merge
behavior) rather than fully unmounted. Added `key={profileId ?? 'new'}` so
switching what this screen edits always gets a fresh `RCardForm` and fresh
`formState`. Not confirmed as the trigger for the reported symptom (the user
confirmed the wrong photo appeared *after* picking a new one, which points
at the native crop step above), but it was a real, independently-reproducible
bug on its own, cheap to fix, and defends against the same symptom via a
different path.

**Evidence checked in code** (not yet re-run against a physical device to
confirm the native-crop staleness theory itself, only against the unit/jest
suite): `bifold/packages/core/__tests__/modules/vrc/utils/rcardPhoto.test.ts`
(`centeredSquareCrop`, crop-action-before-resize ordering),
`__tests__/modules/vrc/screens/RCardOnboarding.test.tsx` (asserts
`launchImageLibraryAsync` is called without `allowsEditing`, and that a
1200×800 picked asset is cropped to a centered 800×800 square before
storage), `__tests__/modules/vrc/screens/EditRCard.test.tsx` (new test:
switching which profile the same screen instance edits, via `rerender` with
the same outer `key`, no longer leaks the previous profile's photo preview).

## Follow-up, same day: a real crop step, not just a silent auto-crop

The fix above removed the buggy native crop screen but replaced it with a
silent, non-adjustable center-crop — no view the user could act on at all.
Reported back immediately: "that is progress, but not the full solution."

**Concluded**: added `RCardPhotoCropModal.tsx` — a square viewport the user
pinch-zooms and pans over the freshly-picked photo (never any other image;
it renders literally the URI `pickRCardPhoto` just returned, so this can't
reintroduce the original staleness bug), with Cancel/Use Photo actions.
`processRCardPhoto` now takes an explicit crop rect from this modal instead
of computing one itself; the pure geometry (cover-fit scale, pan clamping,
transform → source-image crop rect) lives in `rcardCropMath.ts`, unit-tested
independently of any rendering/gesture code.

This is still not the "design pass" the original open question asked for —
no design review happened, and choices like the circular viewport mask
(matching the round avatar preview elsewhere), max 4x zoom, and the modal's
visual style are engineering defaults, not designed ones. Worth a design
pass still if this needs to look considered rather than functional.

**Also concluded**: `react-native-reanimated` was in `bifold/packages/core`'s
`devDependencies` but not its `peerDependencies`, even though `@bifold/core`
now ships a component that imports it at runtime. Added it to
`peerDependencies` (it was already a real dependency of `app/`, so nothing
downstream needed to change) — a pre-existing metadata gap, not something
this feature caused, but one it now makes load-bearing.

## Follow-up, same day: on-device, the crop image moved wrong and threw

First on-device try after the modal shipped: "Showed wrong image in crop
view and got an error!" Device logcat showed the real cause immediately —
repeated `[ReanimatedError: [Reanimated] Tried to synchronously call a
non-worklet function 'clampTranslation' on the UI thread.` on every pan/pinch
update. `RCardPhotoCropModal`'s gesture callbacks (themselves marked
`'worklet'`, so Reanimated runs them on the UI thread) call
`rcardCropMath.ts`'s `clampTranslation` directly, but that function was
plain JS — callable fine from the modal's own JS-thread code (`handleConfirm`,
and every unit test), but not from a UI-thread worklet. Every gesture update
threw, so `translateX`/`translateY` never got a valid clamped value, which is
what looked like "wrong image" (the displayed transform was left stuck or
garbled) and "an error" (the thrown Reanimated exception, surfaced as a
red-box/error).

**Concluded**: added the `'worklet'` directive to `clampTranslation` itself
(`rcardCropMath.ts`) so Reanimated compiles it to run on the UI thread too.
`cropRectFromTransform` and `coverScale` didn't need it — they're only ever
called from plain JS-thread code (`handleConfirm`, the `useMemo` computing
`baseScale`), never from inside a gesture worklet. This is why the jest
suite didn't catch it: the tests call these functions directly as plain JS,
which worked before and after the fix either way — the only place the
distinction matters is a real Reanimated UI-thread call, which nothing in
this package's jest setup exercises (no jest environment stands in for the
UI-thread/worklet runtime). On-device manual verification remains the only
check for this class of bug here.
