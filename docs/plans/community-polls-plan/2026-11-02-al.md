# 2 November 2026: community polls, upstream research and a review response

Parent: [../community-polls-plan.md](../community-polls-plan.md).

Two parts from one working session. Part 1 is the upstream research behind the first draft. Part 2
responds to a maintainer's review of that draft on wallet #825, and records the decisions the
project lead took the same day.

## Part 1: upstream research

Read from upstream source and docs on 2 November, at
[VTI 3139e00e](https://github.com/OpenVTC/verifiable-trust-infrastructure/tree/3139e00ec202351dc253d89b5b4f9885d7ae071e)
and [vta-browser-plugin f89796b1](https://github.com/OpenVTC/vta-browser-plugin/commit/f89796b1).
Nothing was run, and no request was sent to any community.

### Findings

1. **Upstream has a complete voting system.** `vti-voting`, `vti-voting-service`, and the
   `vtc/elections/*` and `voting/*` tasks all exist. Upstream's guide says it runs end to end in
   tests but hasn't run on deployed infrastructure. An upstream maintainer has since offered First
   VTC for testing, so that line may be out of date.
2. **A voter needs VTA 0.69 or newer.** Files under `vta/pcs/voter` and `vta/pcs/vote`: 0 at tag
   `vta-service-v0.67.0`, 13 at `vta-service-v0.69.0`. So any agent on 0.67 can't vote today.
3. **VTC 0.17.0 lacks the newest voting work.** The guided poll builder (#2364), portal voting
   (#2367), the trusted ballot box list (#2370) and the voter tasks in JSON form (#2371) came after
   `vtc-service-v0.17.0` and are in `v0.17.1`.
4. **`voting` is an optional VTC build feature, off by default** (`vtc-service/Cargo.toml`). An
   Elections page in the console doesn't prove a VTC serves voting.
5. **A community needs a trusted ballot box in its host configuration**
   (`[[voting.trusted_ballot_boxes]]`), and the ballot box has to allow that community.
6. **The browser plugin shows the working client.** Its commits give the real order of tasks and
   rules worth keeping: a random pause of up to 20 seconds, a receipt check, a stored "you voted"
   with no choice, and asking before it reaches a new ballot box address.
7. **PCS isn't a secrecy level.** Blind tickets and one-time keys apply at `open`, `sealed` and
   `tallied-encrypted`. The levels decide who can read ballots.
8. **The member's agent sees the choice,** because `vta/pcs/vote/0.2` takes the ballot in its payload.
   It's the member's own agent, but if a provider hosts that agent, the provider is part of that
   trust. The app must not imply otherwise.
   *Applied in Part 2 (R2):* now a requirement on the ballot screen.
9. **Upstream calls the ballot cryptography unaudited:** "fine for polls and surveys; have it reviewed
   before a binding election" (`docs/07-voting/README.md`).

### Not checked

- Whether hosted VTC builds include the `voting` feature.
- Whether the app's community session can carry the signed reads.
- Which version First VTC runs today.

### Position it replaces

None. This is the first look at voting for Keyring.

## Part 2: response to the review

A maintainer reviewed the first draft on wallet #825. Every point is taken. Below, for each: what
the plan now says, the evidence, and what it replaces. Upstream sources are at 3139e00e unless
said otherwise, read from the pinned clone in `external/`.

### R1. Lab and field

**Concluded.** The plan gains *Where each claim is tested*, following the `vti-lab-and-field`
skill's table: unit tests for rules and the cast state machine; the lab for the happy path first
and for every refusal; the field for task versions and for the ballot box being run apart. The
skill's rule on fixture deviations is adopted as written: a change made to get a green run is said
in the same commit, and a finding measured across one names it in the findings doc's *Stack under
test* section. P1's and P2's "Done when" lines now say which environment each claim needs.

**Evidence.** The local stack (`scripts/openvtc/local-vti-stack/`) builds the VTA and mediator with
`--features tsp`, and builds no VTC with `voting` and no ballot box. So the lab can't support any
voting claim today; adding both is P0 work. Two claims are field-only by construction: on the lab
we run the community and the ballot box, so `same_operator` is a setting we chose, and we can't
show which task versions a real server serves.

**"Our findings list"** now points at `docs/VTI_UPSTREAM_FINDINGS.md`. Checking it showed that the
one-vote-per-membership limit isn't recorded there. The plan now says so, and that it goes in as a
question once P0 has measured it, per the skill's rule to try to disprove a finding before
recording it.

**Replaces.** Decision 5 named only First VTC, and no "Done when" line named an environment.

**Later the same day, the project lead decided P0's environment:** First VTC as the community,
conditional on its maintainer confirming that its build has `voting` and a ballot box that will
allow a test community; a Farm VTA, created by the project lead, as the agent; and a local VTC
0.17.1 built with `voting` plus a local `vti-voting-service` as the backup. Decision 5 moves from
open to decided, conditional on those answers. A VTA Farm community was the other option
considered; it drops out because whether a Farm VTC is built with `voting` is as unknown as First
VTC's, and First VTC's maintainer has offered it.

### R2. Who can see the choice

**Concluded.** Finding 8 is now a requirement on the ballot screen: it says that whoever hosts the
member's agent can see the choice, and never implies that no one else does. The "Who sees what"
row now says so too.

**Evidence.** `vta/pcs/vote/0.2` takes the ballot in its payload, and `pcs_voter.rs` `vote` runs
`check_ballot` on it before building the cast, so the agent reads the plaintext. The findings doc's
VTI-Q16 already asks upstream to make operators readable to a client, for hidden vetting; the same
gap applies here.

**Replaces.** The table cell "Nothing is hidden from it", which was true but read as reassurance.

### R3. P0 needs code

**Concluded.** P0's second half is a local probe: worktrees of bifold and wallet main, one
dev-only file that sends the two requests, run in a Debug simulator build. It is never pushed and
never becomes a Test build. P0 still ships no app code.

**Reasoning.** The room-files gate governs builds that reach testers. The probe builds nothing for
testers, so it sits outside that gate. If that reading proves too wide, the session proof moves to
ring 0 in P1's first update, where it rides an update the gate already covers.

**Replaces.** "P0, prove the route, no app code", which needed code it didn't name.

### R4. Coercion and vote-selling

**Concluded.** After a vote the phone keeps only "voted at": no receipt and no board entry, at every
secrecy level. Checking a vote on the board leaves P3 and is out of scope for now.

**Evidence.** On an `open` poll the board holds each ballot in the clear, and a receipt names its
board entry. A member holding both can prove how they voted to anyone, so they can be made to.
Upstream's threat model (`docs/05-design-notes/community-voting-threat-model.md`) doesn't mention
coercion or receipt-freeness.

**The limit, stated in the plan.** Upstream's VTA keeps the cast's board hash and the receipt,
wrapped, until `RECEIPT_RETENTION` after voting closes: `pub const RECEIPT_RETENTION:
chrono::TimeDelta = chrono::TimeDelta::days(30);` (`vta-service/src/operations/pcs_voter.rs`). Its
module header: "Once voting closes the ticket is discarded, and [`RECEIPT_RETENTION`] later
everything else". So anyone controlling the agent in that window holds the evidence the phone
dropped. Revoting, where a poll allows it, is the one mitigation a member has.

**Replaces.** Step 7 ("keeps that the member voted, when, and the board entry") and P3's "check
their vote is on the board, through the receipt".

### R5. Ticket and vote apart in time

**Concluded.** The plan now says what the pause does: it blurs the arrival order of votes sent
close together. And what it doesn't: it does nothing against pairing the ticket's issue time with
the vote's arrival time when few members vote in that window, and nothing against the ballot box
seeing the phone's IP address.

**Decision 6, decided for now by the project lead:** keep upstream's random 0–20 s pause and the
"can be paired" warning within the first hour after the ticket, and revisit it. The options for the
revisit are a minimum gap after the ticket, or "vote later" by default (send at a random time in a
window, with "Send now"). The cast's send-after time makes any of them a change of one number. Before
this decision the review response treated the default as open; the project lead settled it the same
day.

**Evidence.** The plugin's `MAX_CAST_DELAY_MS = 20_000`, commented as "the same bound `pnm elections
vote` uses". Upstream's elections guide states the pairing risk (quoted in the plan).

**Replaces.** "Keep the ticket and the vote apart in time" with the pause as its only answer.

### R6. Failure handling

**Concluded.** The cast is a state machine the phone persists in the wallet's encrypted store:
ticket held → cast built (with its send-after time) → sent → receipt kept → done. The built cast is
kept only between build and receipt, then deleted.

**Evidence.**

- `pcs_voter.rs` `vote` builds a fresh cast each call (`cast_wire(…, &mut rng)` with `OsRng`) and
  signs it with a new one-time key (`sign_as_one_time_key` fills a fresh seed). The tag comes from
  the ticket. So a rebuilt cast is a new document, and how the box treats it depends on the poll's
  revote rule.
- `vti-voting/src/service/mod.rs` `open_cast` answers an exact resend with its first receipt
  (VTI-VOT-042), matched by the digest of the cast. So resending the stored bytes is the safe retry
  after a kill, a background or a lost receipt.
- A crash between the poll record and the ticket is safe. `register` refuses with `TicketHeld`
  once the ticket is held (`pcs_voter.rs`), and until then returns the request document it kept.
  `vtc-service/src/elections/ops.rs` `issue_ticket` answers "a resend of the document already
  answered" from its record (item 1).

**Replaces.** Nothing; the draft had no failure handling.

### R7. The cross-agent poll record

**Concluded.** It lives in the wallet's encrypted store on the phone, is never logged, and stays
out of backups. Android: `android:allowBackup="false"` in `app/android/app/src/main/AndroidManifest.xml`.
iOS: not yet confirmed, so it's a P1 acceptance criterion rather than a stated fact.

### R8. Decisions

**Concluded.** Each decision now has a status, who decides, and the option not chosen. The project
lead decides product questions; upstream maintainers answer environment questions. Decisions 1, 2
and 4 were decided by the project lead with the design approval on 2026-11-02. Decision 5 is
decided conditionally (R1) and Decision 6 decided for now (R5).

**Decision 3's alternative.** A relay that forwards the cast: an anonymising relay, or the agent's
host. Not chosen for now: it adds a party that sees timing and needs infrastructure no community
runs. Forwarding through the agent's host is worse than it looks, because that host already knows
who the member is.

### R9. Smaller points

- **P3** now has a "Done when", for what remains in it: a notice of a new poll, and change my vote
  where the poll allows.
- **Citations.** VTI-VOT-004 and VTI-VOT-090 are quoted with their source. Upstream's register of
  VTI-VOT requirements is not in the repository at 3139e00e; the quotes are upstream's own
  statements of them, in docs and in a DID template:
  - VTI-VOT-004: `vta-sdk/templates/ballot-box.json`, the template description: "a cast MUST be
    accepted over a binding whose sender holds no persistent identifier and no session
    (VTI-VOT-004)"; and `docs/07-voting/README.md`, *What it is*: "This is the door a cast is
    always accepted on (VTI-VOT-004)."
  - VTI-VOT-090: `docs/03-vtc/elections.md`, *Turning it on*: "`operator` and `same_operator` are
    shown to every member before they take a ticket (`Disclosure`, VTI-VOT-090): the separation
    above is only as good as the two operators' independence, so members are told when one party
    runs both."
- **"Who sees what" prose.** The draft said the ballot wording follows the board's visibility, then
  "That is why upstream tells members who runs each one", which didn't follow. The disclosure
  follows from collusion, not from board visibility; the two are now separate paragraphs.
- **`admin` or `initiator`.** Now explained as the phone's access level on the member's agent. Both
  roles derive `PcsVoter` (`vti-common/src/acl/mod.rs`, `derived_capabilities_for_role`); its doc
  comment says it is "derived by the roles that act as the principal and never by
  [`Role::Application`]". The voter tasks check it (`vta-service/src/trust_tasks/pcs.rs`,
  `require_capability(… Capability::PcsVoter …)`). Hidden vetting applies the same rule to
  `pcs-applicant` (bifold `hiddenVetting.ts`, `APPLICANT_ROLES`).
- **Parent plan and carriage.** The plan links `openvtc-integration-plan.md`. Reads and the ticket
  request use the existing community session in bifold's `trust-tasks` module (`vtiAgent.ts`); the
  cast uses plain HTTPS to the ballot box's `TrustTaskHTTPS` door, found the way room files find a
  host's door (`modules/rooms/real/files/door.ts`). Polls add task types, not a carriage.
- **Mock link.** The project lead decided there will be no shareable copy. The link stays, described
  as shared with reviewers on request.
- **Testing.** P1 carries conformance tests (payloads against vendored upstream schemas; ballot
  rules against the browser plugin's and `check_ballot`'s cases), unit tests of the cast state
  machine, and a two-device e2e in the style of `e2e:vrc` once an environment exists.

### R10. Reads go over the session, not through the agent

Found while building P1, not raised in the review. Part 1 had the agent sign each read as the
member (`vta/pcs/voter/read/0.2`), as the browser plugin does. The plugin does that because a
browser holds no key of the member's identity. The phone's community session already signs as that
identity, and `vtc/elections/list/0.3` and `show/0.2` declare no required proof (their bundles at
3139e00e, `policy.proofRequired.request: false`). So a read is one hop over the session, as every
other community read in the app is. The ticket request still goes through the agent: the agent
holds the blinding state, and `vtc/elections/tickets/issue/0.1` requires a proof. This replaces
Part 1's two-hop reads.

The receipt is also held on the phone a little longer than Part 1 implied: after the cast is
dropped, until the agent has kept the receipt (`vta/pcs/voter/receipt/0.1`). If the agent can't be
reached, the phone hands it over next time, then drops it.
