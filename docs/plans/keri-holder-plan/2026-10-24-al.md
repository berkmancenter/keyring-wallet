## Part 1 — Review notes

### N1. A VTA-resident home for ACDCs, tracked as an upstream ask

**Position.** The wallet side would like ACDCs to be able to live on the holder's VTA as well as on the phone. The plan's §4 keeps the phone as the system of record, and sends the VTA only a per-session export.

**Why the VTA cannot hold them today.** At VTI pin `49f5f1be`:
- **The vault rejects them.** `vta-vault/src/model.rs` `CredentialFormat` lists `bbs-2023`, `zkp`, `eddsa-jcs-2022`, `sd-jwt-vc`, `mso_mdoc` and `Other`. `receive.rs` refuses `Other`: "there is no path that stores an unverified … credential".
- **App-state is not an alternative.** `docs/05-design-notes/appstate-store.md` describes it as schema-agnostic JSON, "Not for secrets", with no blobs in 1.0. `vta-service/src/operations/app_state.rs` caps a record at `MAX_VALUE_BYTES = 65_536`. That rules out an ACDC's salts and its retained secret material.
- **#202's proof-set objection is outdated.** `di_verify.rs` now accepts proof sets, but that does not change the ACDC conclusion.

**Proposed changes.**
- Keep §4's phone-as-system-of-record for v1. The storage adapter seam §4 already describes is enough to add a second home later.
- Add a KH-Q: "VTA-resident copy of a held ACDC". It is blocked on an upstream vault change, owned by the VTI maintainers.
- Record the upstream ask in that KH-Q. It is one of:
  - a `CredentialFormat::Acdc` whose receive path runs the KERI checks (SAID, KEL, TEL anchoring);
  - a sanctioned opaque, typed record class.

  Either needs indexing by issuer AID and schema SAID, and a status-refresh path.
- KH-Q1 (the VTA copy DBI's B-batch might need) and DBI-Q12 (what counts as holder-controlled) are the natural parents of this KH-Q.

### N2. The iPhone hardware key cannot sign KERI messages as built

**What the plan assumes.** §7 and §8 allow `HolderSigner` to be "P-256 (`1AAI`) from the device", citing `hardware-signing/key.ts`.

**What the code does.** On iOS the only device key is an App Attest key. `react-native-attestation/ios/Attestation.mm` signs with `DCAppAttestService generateAssertion`. That returns a CBOR assertion whose signature covers `SHA256(authenticatorData ‖ clientDataHash)`, not the payload. No `SecKeyCreateSignature` / `kSecAttrTokenIDSecureEnclave` signing key exists in bifold `main`. An App Attest assertion does not verify as a KERI signature over `exn` bytes.

**On Android it can work, with conversion.** `AttestationModule.kt` signs `SHA256withECDSA` over the payload with a StrongBox or TEE `secp256r1` key, which is usable. Two conversions are needed:
- the DER signature to raw 64-byte `r‖s`, for `0I` or the indexed `E`/`F` codes;
- the SPKI public key to the 33-byte compressed point, for `1AAI` / `1AAJ`.

High-S signatures need no normalising, since keripy and the plan's verifier accept both.

**Proposed changes.**
- In §8, state that the device P-256 path needs a new native signing method on iOS: a Secure Enclave key signed with `SecKeyCreateSignature`, ECDSA X9.62 SHA-256.
- That key must be separate from the VRC-evidence key. Reusing one key would let a verifier link the KERI identity to VRC evidence.
- Gate the device path on rung K4 (Part 3).
- The vLEI / stock profile (Ed25519 + Blake3) cannot use phone hardware at all, so it stays on the Askar Ed25519 signer.

### N3. A hardware-held key with a non-transferable AID has no recovery

A non-transferable AID cannot rotate. Phone hardware keys cannot be exported. Android keys created with `setInvalidatedByBiometricEnrollment(true)` die when the user re-enrolls a fingerprint.

So a credential bound to a hardware-held non-transferable AID is lost with the device, or after a biometric change, and has to be re-issued or re-bound (DBI-Q14).

**Prior art.** The only published hardware pattern for KERI keys is server-side: WebOfTrust `gcp-ksm-shim` creates the current and next keys in a cloud HSM at inception. Nobody has published phone-enclave KERI keys.

**Proposed change.** Add this as a risk in §10, with re-bind (DBI-Q14) as the mitigation. Note that pre-rotation does not help on a single device, because the next key would sit in the same enclave.

### N4. v1 cannot receive from today's vLEI issuers unless they push to us

**The limit.** Production vLEI issuers run KERIA, where the issuer's agent delivers the IPEX grant to the holder's KERIA mailbox. The plan already says the wallet is "neither a KERIA agent nor a mailbox poller" (§7, R3), so v1 reaches only an issuer willing to push the grant over our DIDComm or TSP carriage.

**Proposed change.** State this in §1's goals as a v1 limit. Also note that KH-Q10 (a mailbox-poll client) is what makes the "receive a vLEI credential" goal reachable outside our own test stack.

### N5. Test the non-transferable admit first, since it decides the identity model

The plan's §13 lists as unverified whether keripy accepts an `/ipex/admit` from an AID it holds no KEL for. Today's ecosystem always admits from a witnessed, transferable AID: vLEI credentials and signify-ts's `credentials.test.ts` bind `a.i` to one.

If the non-transferable admit is refused, the exchange-identity design (§7, §8) changes, so this deserves the earliest live check. That is rung K3 below.

### N6. Utah has not chosen KERI, and Utah-style ACDCs upstream are protocol v2

What is publicly confirmed, as of 2026-10-24:
- **The state guide names no technology.** Utah's SEDI implementation guide is `0.1.0-draft`: <https://sedi.utah.gov/implementation-guide/>.
- **Procurement is still open.** A vendor's SEDI page that argues for KERI also states the bills "do not mandate any specific technology", and says procurement is running under RFI AE26-1: <https://veridian.id/sedi>.
- **The upstream SEDI design is KERI/ACDC protocol v2.** It is keripy discussion #1515, "New Unary Edge Operators to Support SEDI" (<https://github.com/WebOfTrust/keripy/discussions/1515>), plus the `tests/sedi/` example suite merged 2026-09-18 to 10-06. It uses:
  - `KERICAACAAJSON` strings;
  - `rip` registries;
  - the E1E edge operator, added to the ACDC specification on 2026-08-11;
  - issuee presentation registries.
- **The production tools are v1 only.** KERIA (built on `keri` 1.2.14) and signify-ts speak only v1 (signify-ts has only `Vrsn_1_0`).

**Proposed changes.**
- A1–A4 remain assumptions, as §2 says. The plan should cite public sources for them, or mark them as unconfirmed, rather than rely on statements nobody can check.
- KH-Q8 (v1 or v2) becomes more pressing. The fixtures for the Utah profile should include protocol-v2 events, generated from keripy's 2.x line, beside the v1 vLEI set.
- S6 (edges) should list E1E. keripy implements I2I, NI2I and E1E, and fails closed on DI2I and NOT.

### 2.2 Life cycle, and who signs what

| Step | Event / message | Signed by |
|---|---|---|
| Issuer identity | `icp` starts the KEL, committing the digests of the *next* keys (pre-rotation) | Issuer's current keys |
| Key change | `rot` reveals the committed next keys; `ixn` anchors seals without changing keys | Newly revealed keys / current keys |
| Witnessing | `rct` receipts | Each witness's non-transferable key |
| Discovery | OOBI URL returns the KEL as CESR | Nobody: trust comes from verifying the KEL, not from the URL |
| Registry | `vcp` (v1) or `rip` (v2), anchored by a seal in an issuer `ixn` | Issuer, through the anchoring `ixn` |
| Issuance | `iss` TEL event anchored in the issuer KEL; the ACDC is authenticated by its SAID plus that anchor | Issuer, through the anchor; the ACDC is not signed separately |
| Delivery | IPEX `/ipex/grant` `exn` carrying the ACDC, `iss` and the anchor | Issuer's AID |
| Acceptance | `/ipex/admit` (or `/ipex/spurn`) | **Holder** |
| Presentation | IPEX `/ipex/grant` to the verifier, carrying the chain, KELs and TELs | **Holder** |
| Revocation | `rev` TEL event anchored in the issuer KEL | Issuer only |

**The holder signs twice:** on acceptance and on presentation. A *targeted* ACDC requires the issuee to be an AID.

**Key split in KERIA / Signify.** The client keeps every private key and signs everything on the device. KERIA holds public keys and next-key digests only (KERIA `docs/protocol.md`).

### 2.3 Crypto suites

These codes come from keripy `coring.py` / `indexing.py`; signify-ts uses the same ones.

| Suite | Public key (transferable / non-transferable) | Signature (non-indexed / indexed) |
|---|---|---|
| Ed25519 | `D` / `B` | `0B` / `A`, `B` |
| ECDSA P-256 | `1AAJ` / `1AAI` | `0I` / `E`, `F` (big: `2E`, `2F`) |
| secp256k1 | `1AAB` / `1AAA` | `0C` / `C`, `D` |

**Digests.** The default is Blake3-256 (`E`). Others are Blake2b-256 (`F`), SHA3-256 (`H`) and **SHA2-256 (`I`)**.

**Who can sign P-256.** keripy and keri-ts sign P-256. signify-ts only verifies it.

### 2.4 Specification status

- **KERI, ACDC and CESR are ratified ToIP specifications.** They were approved on 2026-01-21, with v1.0 tags in March 2026. The repositories are now `trustoverip/kswg-*`, the renamed `tswg-*`.
- **Two protocol versions.** The specifications define both protocol 1.x and 2.x.
- **The IETF drafts have lapsed.** The KERI-family IETF drafts expired in early 2024 without working-group adoption.
- **did:webs is still a draft.** The `kswg-did-method-webs-specification` is at v0.10.3, not ratified.

### 2.5 Offline verification

**What a cached copy can re-check.** With the issuer's KEL and TEL, the ACDC and the schema stored, all of these can be re-checked with no network:
- SAIDs and the schema;
- the issuer's KEL, including pre-rotation commitments and witness receipts;
- the issuance anchor;
- edges, where their targets are held;
- revocation, *as of the cached TEL*.

**What it cannot check.** A later revocation, a later rotation, or duplicity that only watchers would see. That is why §3's "status with the age of the check" is the right rule.

## Part 3 — A short proving ladder

Each rung lives under `tsp-reference/`. They are numbered when added, in that directory's `README.md` order, and each one's working name is shown below. Each rung is meant to take days, not weeks, and runs outside the app. **Its result is recorded in a dated companion before the KH phase it de-risks starts.**

| Rung | Proves | Done when | De-risks |
|---|---|---|---|
| **K1 Hermes primitives** (`ref-keri-hermes`) | The trimmed cesr-ts 1.0 subset parses CESR and checks signatures on Hermes. It follows the method of `ref-03b-hermes-identity` / `ref-03d` | On a Hermes release bundle: Blake3 and SHA2-256 SAIDs recompute; Ed25519 and P-256 (high-S and low-S) verify; bundle size and cold start are recorded; G-H1–G-H7 are each marked pass or fail | KH-P0 |
| **K2 Fixture verify** (`ref-keri-fixtures`) | A thin in-memory verifier accepts a real issuer chain: icp → ixn → vcp/rip → iss → ACDC | Pinned keripy generates two fixture sets, vLEI-like (Ed25519/Blake3, v1) and Utah-like (P-256/SHA2-256, v2). Both verify under Node. A one-byte mutation, a missing anchor and a wrong next-key digest each fail closed | KH-P1, KH-P2, N6 |
| **K3 Live grant and admit** (`ref-keri-ipex`) | KERIA and keripy accept an admit from the wallet's non-transferable AID | Against signify-ts's docker stack (KERIA, the keripy witness demo, the vLEI schema server): a keripy-driven grant reaches a test holder over a DIDComm stand-in; its admit is observed by the issuer; a revoked credential reads as revoked | KH-P4, N5 |
| **K4 Device signatures** (`ref-keri-device-sign`) | Phone hardware P-256 keys produce signatures keripy verifies | On physical devices: Android StrongBox / TEE P-256 and a new iOS Secure Enclave key (`SecKeyCreateSignature`) each sign an `exn`; after DER→raw and SPKI→compressed conversion, keripy verifies both; App Attest is shown not to verify | KH-P5, N2 |
| **K5 Presentation** (`ref-keri-present`) | A real verifier accepts a holder-signed presentation | GLEIF's `vlei-verifier` or `sally`, or a keripy verifier, accepts an IPEX grant from the K3 holder, and rejects the same grant after one byte changes | KH-P5 |

K1 and K2 need no network or devices. K3 needs Docker only. K4 is the only rung that needs phones, and simulators cannot stand in for it.

## Part 4 — What fits this repo's environment

1. **Verify first, with our own small verifier.** This agrees with §6 L2 and L3: take the cesr-ts 1.0 primitives and write the KEL/TEL/ACDC checks ourselves. Nothing upstream runs verification in memory on React Native.
2. **Do not adopt signify-ts and KERIA as the wallet's client.**
   - It means running or renting a KERIA cloud agent beside our mediator.
   - signify-ts depends on `libsodium-wrappers-sumo` (WebAssembly, which Hermes lacks).
   - It signs Ed25519 only and speaks protocol v1 only.
   - Use it, as §11 does, only as the issuer side of the test stack.
3. **Keep the THCLab Rust stack out of the app.** keriox and dkms-bindings are EUPL-1.2, a copyleft licence. Every other candidate is Apache-2.0.
4. **Hardware fits only the P-256 profile.** It needs a new iOS Secure Enclave signing key (N2) and a recovery story (N3). The vLEI profile stays on a software Ed25519 key in Askar.
5. **Track protocol v2.** Any Utah-style credential upstream is v2, while today's production tools are v1. Fixtures for both versions (K2) keep the verifier from being built for only one.
6. **Use Veridian as UX prior art, not as architecture.** It is the only shipped mobile KERI wallet, and its flows are worth studying. Its WebView-plus-cloud-agent design does not carry over to this app.
