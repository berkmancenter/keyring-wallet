# Encrypted Spaces: proposal vs. implementation

Date: 2026-10-06
Sources: https://encryptedspaces.org/, whitepaper v1.1 (Aug 2026, 42 pp), GitHub org
https://github.com/encrypted-spaces (`prototype`, `merk`).

Method and caveats: status comes from reading the site, the whitepaper, READMEs, file trees
and code, plus running the default-feature test suites. Cryptographic soundness was not
verified. Percentages are judgment calls, not measurements.

## The proposal

Encrypted Spaces is an "active research preview" for collaborative applications that run on
untrusted servers. The server stores and syncs data but cannot read it.

- Hash-chained change logs, with zero-knowledge "fast-forward" proofs so users can verify a
  data version without replaying history.
- Schema-driven selective encryption: the app schema decides what is encrypted and what the
  server can see.
- Membership, access control and key distribution handled by the system.
- Every change attributed to its author; access is visible.
- A Firebase/Supabase-style sync engine (Tables, Lists, TextAreas) with a Rust SDK offering
  table CRUD, verification running underneath.

The protocol is stated to be under design and review.

## What exists in the repos

`prototype` is about 4 MB of Rust, last pushed 2026-09-22, tagged 0.0.2. The README says
"DO NOT USE IN PRODUCTION". `merk` is a Merkle key-value store used as storage.

## Whitepaper vs. code

1. **Fast-forward proof.** It proves the change-log commitment (Merkle mountain range), the
   data-commitment transition including access-control checks, the timestamp high-water
   mark, the parent commitment and the per-author signature-reference chain. Signatures are
   not verified inside the proof: it outputs each author's latest change and the client
   checks one signature per user. No separate "reconciliation" step was found. Default
   builds set `RISC0_DEV_MODE=1`, so proofs are fake (documented in the README).
2. **Schema-driven encryption.** Every column not marked `plaintext` is encrypted, and
   inserts must supply all encrypted columns. Cipher is AES-256-CTR with no MAC; integrity
   relies on the Merkle commitment. All columns use the space's current key; the per-column
   key derivation the paper claims was not found. The server cannot verify that an
   "encrypted" column holds ciphertext (the paper lists this as future work).
3. **TextArea.** Not a CRDT, OT or the paper's piece table. It is text chunked into at most
   16 characters per node in a server-ordered doubly-linked list; concurrency comes from
   server ordering. Concurrent edits were not tested.
4. **Attribution.** Code does attribution only (Ed25519-signed entries). No deniable
   authentication exists, and the paper says so. The paper's argument that misbehavior is
   attributable depends on the non-deniable mode.
5. **In the paper, absent from code.** Transparency/consensus layer (so no fork
   resistance), pairwise deniable authentication, post-quantum change signatures, metadata
   hiding, the piece-table text design, per-column key derivation. The paper admits most of
   these.

Other gaps: the site says users can cryptographically verify server behavior, which
depends on fast-forward proofs that are not real by default. Rust is the only SDK. The
site does not mention the retention construction or the RISC Zero / STARK choices.

## Tests (default features, dev-mode proofs)

- `merk`: 733 passed, 4 ignored, 1 doctest, 0 failed.
- `prototype`: about 1,319 passed, 0 failed (crypto, key-manager, retention, acl-types,
  storage-encoding, backend, changelog-core, sdk, backend-server, zkp).
- Not run: the RISC Zero toolchain is not installed (`rzup install rust` downloads into the
  shared home directory), so the build used `RISC0_SKIP_BUILD=1` and the guest ELF was
  stubbed. Skipped: `ffproof` crate tests and `ffproof/integration_tests`, `methods_bench`,
  tauri demos, `sdk_fuzzer`, `sdk/codegen`, `spongefish-stark`, benches, real-proof and
  CUDA paths.
- The passing SDK and server tests do not show the fast-forward proof path working end to
  end.

## Overall

- Against the described architecture: roughly 70-80% exists as research-grade code (data
  model, change log, crypto, key management, retention, proofs).
- Against production readiness: roughly 40-50%. Blockers: fake proofs by default,
  placeholder authentication, incomplete DoS hardening, no security audit.
- The pieces that would make the server untrusted in practice (real proof path,
  transparency layer, deniability) are partly built or not built.

## Suggested follow-up

Install the RISC Zero toolchain (`rzup install rust`) and run the `ffproof` tests and
integration suite in dev mode; test concurrent TextArea edits.
