## 1. Availability comes from the person's agent at runtime, not from the pin

**Concluded.** Whether an operation is available is decided from what the person's own agent serves, asked at runtime through `trust-task-discovery/0.1`. It is not decided from the VTI commit Keyring reads upstream source at.

**Evidence.**

- The agent answers discovery with exactly the tasks it dispatches (READ: VTI `vta-service/src/trust_tasks/mod.rs`, `dispatched_uris()`: "a hand-maintained list of what we support … goes stale").
- `VtaClient` already uses it (READ: `servesPcs()` in bifold `VtaClient.ts`).
- The agents people run are newer than the source pin. The gate's nightly `4a0f1ff1` and tag `vta-service-v0.64.0` both contain community rooms and offers (`795fd2ae`), the owner's group add/remove (`196b26f6`), room files (`49d8fe3d`), revocation (`87a0ee64`) and `rooms/keys/act` (`ca7c8faa`). READ: `git merge-base --is-ancestor` for each.

**Supersedes.** §5a's framing of readiness "measured at the pin". The pin remains the source we cite; it is not the gate for what a user's agent can do. R0 encodes this: an operation is `available` only when the agent serves it and Keyring implements it. An unanswered discovery is `agentUnknown`, never "serves nothing".

## 2. A room's details come from the community, not from the agent

**Concluded.** "My rooms" is the community's record joined with the agent's key custody. The agent alone can only list room IDs.

**Evidence (READ).**

- `rooms/keys/list` returns custody only. At spec `7b6bb488` (0.1) each entry is `{ roomId, epoch, earliestReadableEpoch }`; 0.2 adds `member` and a personal label. It has no name, tier, rights, expiry, community or host (`specs/rooms/keys/list/0.1/payload.schema.json`, `$anchor: response`).
- `rooms/keys/browse` and `rooms/keys/read` both require the host's DID: "nothing maps a room to its host" (`specs/rooms/keys/read/0.1`, `host`).
- The community's `vtc/rooms/memberships/list/0.1` returns "room identifiers, labels, descriptions, tiers, actions, expiries, states" (spec main, `spec.md:35`). For a community-owned room the host is the community's VTC.

**Consequence for the interface.** A room known only through custody has `source: 'custody'`, `nameFrom: 'roomId'` (a short ID, shown as an ID), `tier: 'unknown'` and `verbs` undefined. Its operations report `detailsNotLoaded` (`RoomsService.roomCapabilities`). Agreed with the screens lane.

## 3. The community leg needs no new network leg: the persona signs over the existing DIDComm/TSP channel

**Concluded.** Keyring sends the community room tasks (`vtc/rooms/memberships/list`, `vtc/rooms/offers/list`, `vtc/rooms/offers/accept`) through `vtiAgent`, as the persona it already joins the community as. They travel over DIDComm or TSP, like join requests and self-remove today. No HTTPS leg is added.

**Evidence (READ).**

- Keyring joins "as a persona the wallet's VTA holds", and the persona's keys are lent to the phone. `vtiAgent` connects as the persona and signs every document with its lent signing key (bifold `vtiJoin.ts:1-10`; `vtiAgent.ts:91-108`, `:471`, `:871-876`).
- The community records the membership against that persona.
- These tasks require "being the member the offer names, and an active member now" (VTI main `vtc-service/src/trust_tasks/community_room_tasks.rs:9-12`).
- The VTC's DIDComm path calls the same dispatcher as its HTTPS route (`vtc-service/src/messaging.rs:1012`, `:1694` → `dispatch_trust_task_core`), and the room tasks are routed in it (`trust_tasks/mod.rs:1381`).
- Over DIDComm the caller is the authcrypt sender (`mod.rs:4613`). A document is accepted when its proof is by its `issuer` and that issuer is the transport's sender (`mod.rs:401-414`), which is what `vtiAgent` already does.

**Why the browser client uses HTTPS (INFERRED).** A browser has no DIDComm channel as the persona, so it delivers persona-signed documents to the VTC over HTTPS. Keyring has that channel already.

## 4. R2 (writes) is scoped to community-hosted rooms; a standalone host is a named gap

**Concluded.** Writes go through `rooms/keys/act`: the agent completes a persona-signed document, and someone delivers it to the host.

- **Community-hosted rooms:** the phone delivers it over the same DIDComm leg as the persona, because the VTC dispatches `rooms/*` through the same function (READ: VTI `vtc-service/src/trust_tasks/mod.rs:1151`).
- **Standalone `room-host`:** it speaks DIDComm only when its operator enables `--mediator-did`, which is off by default (READ: `room-host/src/didcomm.rs:21`). Otherwise it speaks HTTP.
- **So** a standalone host is the one place an HTTPS leg could come back. It is out of scope until a standalone host is a requirement, and then it goes to Alberto as a new network leg, with options.

**Supersedes.** The plan's R3 ("write to an open room by `rooms/records/put` … sealed room by `rooms/keys/seal` then `put`"). That assumed the wallet calls the host directly. With `rooms/keys/act` the agent signs as the persona and the phone only delivers.

## 5. Phases as they now stand

- **R0** (bifold #595): the interface, capability rules, inert text, and a sample service for development builds. No network.
- **R1:** "My rooms" = `vtc/rooms/memberships/list` (community, as the persona, over `vtiAgent`) joined with `rooms/keys/list` (agent, for custody and epochs). Room detail and host come from the membership. Notes come from `rooms/keys/browse` / `rooms/keys/read` naming that host. Leaving goes through the existing `vtc/members/self-remove`. Built on bifold `feat/rooms-r1-service`, stacked on #595. AI-agent access (`rooms/keys/present`, ACL grant) was planned for R1. It is not in this branch and reports `clientNotBuilt`, so it follows as its own change.
- **R2:** writes and curation on community-hosted rooms (`rooms/keys/act`, delivered over DIDComm), then offers (`vtc/rooms/offers/list`, `accept`) with renewals collected from `offers/list` 0.3 (§6).
- **R3:** files (`rooms/keys/file-key`). This needs a byte-exact JS port of upstream's file cipher with test vectors, and the file key never leaves trusted code.

## 6. Upstream's week-43 changes: groups, the directory, and rooms

**Baselines.** VTI main `c667554d` (2026-10-26). Eucalyptus was cut from `1a85c2f7` (2026-10-10, vta-service 0.56.0, `releases/eucalyptus.toml`), and main is 276 commits past it. The Trust Task specs are at main. READ.

**Release placement (READ, `git merge-base --is-ancestor` and `git tag --contains`).**

- **Not in Eucalyptus at all:** every room task R1 needs from a community. `vtc/rooms/memberships/list` first ships in `vta-service-v0.63.0`, and the member directory's `vtc/directory/entries/list` in `v0.64.0`.
- **Untagged main only (Fig):** community groups, groups bound to rooms, renewals, record provenance and retention.
- **Consequence:** R1's community leg works against an agent and VTC at `v0.63.0` or later, or at Fig. A VTC on Eucalyptus answers "My rooms" from custody only, with every room `detailsNotLoaded`. That is the behaviour R0 already specifies, so nothing breaks. This is the same constraint §3's lab call is waiting on.

**Room access through groups: it changes nothing in R1, and R2's offers matter more.**

- A group bound to a community room (`vtc/groups/bindings/add/0.1`, VTI `20e73c02`) gives its members access by offering them admission through the ordinary offer path, and removes them when they leave the group. Groups are not a new way into a room, so R1's join of memberships with custody is unchanged.
- What changes is volume. Joining a group can produce offers with no administrator involved, so R2's offers (`vtc/rooms/offers/list`, `accept`) become the normal way rooms arrive.

**New requirement: renewals (`vtc/rooms/offers/list/0.3`).**

- Before an admission expires, the community issues fresh membership and authority credentials, listed as `renewals`.
- The member's own client **MUST** store them with the member's key holder, in place of the ones they renew, and **MUST NOT** call `accept` for them (spec, Surface items 1–3).
- `memberships/list` shows the renewed `validUntil` as soon as the renewal is listed (Responder item 7). A member whose client never stores it would therefore see a later expiry than their key holder can act on, and reads would start failing at the old one.
- **Consequence:** for anyone whose only client is Keyring, collecting renewals is needed to keep rooms readable. It is a small task: `offers/list` 0.3, then a store, with no group or KeyPackage step. It goes with R2's offers, and moves ahead of writes if a lab member's admission is due to lapse first. The VTA task that does the store has not been confirmed yet.

**The member directory can feed a community-wide Members view, but not a room's member list.**

- A member may call `vtc/directory/entries/list` (role: member or administrator), served from `v0.64.0`.
- A room's own member list stays administrator-only (`vtc/rooms/community/members/list`, `vtc.rooms.manage`). `listCommunityMembers` therefore stays `adminOnly`.
- A Members tab can show the community's directory: the cards members chose to publish. It cannot say who is in a given room.

**Rooms changes that touch R1's reads (READ):**

- `rooms/keys/browse` is at 0.3 in the specs. 0.3 only renames `lastPrune.at` to `prunedAt`. R1 speaks 0.1, which stays published, and its parser drops unknown members, so nothing breaks.
- Record provenance (`basis`, `confidence`, `evidence`, `validFor`, `validUntil`, VTI `f0d0b48c`) is display-only by its own definition. R1 ignores it for now. A later screen could show "declared" or "expired" beside a note.
- Retention and pruning can remove records. A pruned record simply disappears from a listing.
- `rooms/keys/act` is specified up to 0.8. R2's write requirement names 0.5 and 0.6. The versions R2 targets are checked against the agent's discovery when R2 starts, not now.
