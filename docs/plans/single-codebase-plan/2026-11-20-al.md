## 1. Why now

The product owner decided on 2026-11-20 to stop maintaining two codebases and keep `keyring-wallet` only, with the bifold packages inside it. The stated reasons: a simpler and cleaner codebase, and less work per change in future. All other framework work was paused the same day; the DIDComm v2 migration continues in parallel with its own owner and worktrees.

### 2.3a Version drift between `app` and `core` (the hoisting risk in the plan's §5.4)

Comparing `app/package.json` with `core`'s peer and direct dependencies: 7 names differ, and only one is a real range difference: `react` (app `19.1.0`, core `~19.1.4`; the root resolution pins `19.1.0`). The other six are `*` in core (`react-native`, `react-native-orientation-locker`, `react-native-screenguard`, `react-native-vision-camera`) or `workspace:*` already (`@bifold/credo-tsp-adapter`, `@bifold/trust-tasks`). So the ~40 jest pins exist because of the second install, not because of range conflicts; after Phase 2 a `yarn dedupe` and `yarn why react` are the whole check. Both `app` and `core` set `installConfig.hoistingLimits: "workspaces"`; three `react` directories exist on disk today (root, `app/node_modules`, `bifold/node_modules`).

`@bifold/oca` has no `exports` field; the 5 app imports of `@bifold/oca/build/legacy` resolve to a built path and must become `@bifold/oca/legacy` once `main` is source.

### 2.4 Bifold's own CI (what has to move)

Read at bifold `origin/main` on 2026-11-21 (a first reading from the main checkout's `bifold/` working tree, which sits on an old branch with seven workflows, was wrong and is superseded): `quality.yaml` with jobs "Linting and formatter", "Testing part N/4" (four core jest parts), "Testing", "Testing scope · <scope>" (the scoped-subset logic) and "Type check (ratchet)"; `full-tests.yaml` ("Jest part (N)", "Full suite"; push to main, schedule, dispatch; the unscoped run review waits on); `targeted-jest.yaml` ("Targeted jest", dispatch); `vti-conformance.yaml` ("VTI SDK accepts Keyring's card and statement"); `commit-checks.yaml` ("DCO sign-off and commit signature"); `publish.yaml` ("Release", changesets); `maintenance.yaml`, `repolinter.yaml`, `scorecard.yaml`, `roadmap-pr-status.yaml`. Rulesets: "Main" requires "DCO sign-off and commit signature", "Linting and formatter", "Testing", "Type check (ratchet)"; "OTA pins" protects `refs/heads/ota/*` from deletion and force-push. The "SEDI/KERI switch guard" is the jest test `packages/core/src/modules/trust-tasks/__tests__/sediKeriSwitches.test.ts`, not a job. Secrets: `keyring-bifold` lists only `ROADMAP_TOKEN`; `CODECOV_TOKEN` is referenced by `quality.yaml` but is not a repository secret in either repo.

**Lesson, for every later reading in this plan:** the main checkout's `bifold/` directory is a working tree that can sit on any branch; read bifold facts from `git -C bifold show origin/main:<path>` or a fresh clone, never from the directory as checked out. The same trap as `external/` clones in the root `CLAUDE.md`.

## 3. Positions adopted, and what they supersede

**P1, revised. Preserve history in this repository; `main` gets one signed squash.** The first draft said "merge with history onto `main`, not squash", to keep `git blame` and the sign-off attribution in a 190,000-line package. That cannot land: wallet `main` requires every commit signed and GitHub-verified (the "Main" ruleset and `commit-checks.yml`, which lists every PR commit), `git filter-repo` produces new shas and so strips every signature, and the upstream OpenWallet-era history was never signed. Adopted instead (plan D1): one signed squash on `main`, the full history pushed once to an unprotected `history/bifold` ref in the same repository, an optional `refs/replace/` graft. Alternatives kept for the record: a protection change for a history-preserving merge; history only in the archived repository ("start clean" with copied files was rejected first, because it loses everything D1 protects). `git subtree add --squash` was rejected for the same reason as a plain squash without a history ref; subtree without squash keeps history but adds a merge commit per import and its own metadata; filter-repo gives a plain merge with prefixed paths and is what git's documentation points to instead of `filter-branch`.

**P2. Fold in place first (same `bifold/` paths), move second.** The alternative, moving to `packages/*` in the same PR, was the first draft. Dropped because (a) every open bifold PR's patch and every v2 replay applies unchanged while the paths are the same, (b) a Phase 1 failure can only be install wiring, and (c) review clears moves per file by hash and wants moves and edits in separate commits.

**P3. Bundle React Native packages from source (`main: src/index.ts`).** Today's split (source in dev through Metro's resolver, built `lib/` in release) is the reason `ensure-bifold-ready.js` runs `yarn build` on every install and why `tsconfig` redirects three packages. `react-native-locality-peripheral` already ships `main: src/index.ts` and works in release builds, which is the evidence it is safe for the others.

**P4. The fold is a store-build boundary.** Because `hot-updater` hashes `extraSources` by path, moving the native module folders may change the fingerprint without changing native code. Rather than engineer path stability, old lines keep the old structure and tooling, and the product owner chose to retire the 279/280 OTA lines at the first folded store build's publish rather than keep two toolchains alive ("we don't need to be as careful with the original migration plan"; the user base is small and active users can be asked to upgrade). The post-fold cut is a cherry-pick of real file changes, not a pin bump, so the OTA cut tooling needs a rework before the first post-fold OTA; made a Phase 2 exit criterion rather than Phase 3 work.

**P5. End the upstream "branch swap" strategy.** `UPGRADE_PROGRESS.md` §2 chose a same-repo fork so upstream commits could be cherry-picked with shared history. After the fold, upstream changes come in as patches (`git am --directory=packages`). The shared-history benefit has shrunk: we are on upstream's React 19 / RN 0.81 / expo 54 line already, and the remaining delta is ours. Superseded in part: `reference-app-sdk-packaging.md`'s assumption that `@bifold/*` are publishable from a separate repository.

**P6. Keep `@bifold/*` names.** A rename is one `sed` and one PR; bundling it in would double the diff of a PR that is already rename-heavy.

**P7. Both workstreams in their own worktrees, consolidation as a named step.** The product owner: "at least two worktrees going on so one does not interrupt the other, later we will consolidate." §7.1 of the plan is the replay and cut-over recipe. "Less careful" for v2 means no backwards-compatibility steps for old builds, only tests that prove the new path.

**P8. One integration branch, stacked PRs, one PR to `main`.** The first draft had each phase as its own merge to `main`. The product owner (2026-11-20, ~23:10Z): "I would prefer to make a new branch and then make the PR into that one branch of the multiple phases and then use GitHub's new stacked PRs somehow and then we will make one large PR to main." Adopted as D2. Consequences: `main` is never between phases, so OTA cuts, the nightly and anyone rebasing never meet a half-folded tree; the v2 cut-over moves to that single merge; the Phase 1 PR may merge into the integration branch with a merge commit (it is unprotected) while `main` still gets exactly one signed commit; the integration branch is kept so the phase boundaries stay reachable. Stacked PRs into `feat/one-codebase` get no CI unless the first PR in the stack adds that branch to `quality.yml` and `test-builds.yml` (their `pull_request` triggers filter on `branches: [main]`), and `commit-checks.yml` must not be widened to it.

**P9. The final PR is a one-commit branch.** `commit-checks.yml` iterates the PR's commits, so a PR opened from the integration branch fails on its first unsigned history commit regardless of the merge method. The PR to `main` is opened from a branch made with `git commit-tree -S` on the integration tip's tree; review clears it by tree equality plus the stacked PRs' clearances.

## 3a. The rehearsal (2026-11-20, 22:30Z to 23:35Z)

- `git filter-repo --to-subdirectory-filter bifold` on a fresh clone of bifold `main` a5bfcf3b2: 1 s for 4,341 commits; the filtered tree under `bifold/` is byte-identical to a5bfcf3b2's tree (`ffe2645d…`); every filtered commit is unsigned (`%G?` = N for all 4,341).
- A private throwaway repository under the product owner's login refused branch protection and rulesets (HTTP 403, free plan). With the product owner's agreement it was made public for the rehearsal (its content: bifold's public history and a README), given a copy of the wallet's "Main" ruleset and `commit-checks.yml`, and set back to private afterwards; its deletion needs a `gh` scope the Mac's token lacks and is the product owner's click.
- Outcomes, all as predicted: a direct push of a signed commit to `main` was refused by the ruleset ("Required status check … is expected"); a PR opened straight from the integration branch **failed** the commit check on the unsigned history; the one-commit `git commit-tree -S` PR **passed** and squash-merged with `--match-head-commit`; `main` then held one commit GitHub reports `verified: true (valid)` whose `bifold/` tree is a5bfcf3b2's; `history/bifold` (4,341 unsigned commits) was accepted on its unprotected ref; a local `git replace --graft` made `git log` of a core file from `main` reach 43 commits instead of 1.
- One recipe error caught: with the gitlink removal still staged, `git merge --no-commit` refused the dirty index and the first fold commit silently only deleted the gitlink; the one-commit PR built from it had the wrong tree. Caught by comparing `git rev-parse HEAD:bifold` against `ffe2645d…`. The plan's recipe now commits the removal first and makes that tree check a step.

## 4. Decisions taken by the product owner, 2026-11-20 (22:55Z to 23:20Z)

Asked as twelve questions during the draft; recorded here as decisions, with the alternative each one closed. The plan states them as design (D1 to D9 and §5.3) and no longer carries the question list.

- Cut now, at the shas current when Phase 1 starts; do not wait for in-flight work (alternative: wait for named PRs).
- Retire the 279/280 OTA lines at the first folded store build's publish and ask active users to update (alternative: keep them alive with the old tooling).
- Keep the `@bifold/*` names through Phase 3 (alternative: rename in the fold).
- Node services join the root workspace (alternative: a `services/` tree with its own install).
- Bifold's shared root files go to the repository root (alternative: inside `packages/core`).
- Drop upstream leftovers in Phase 2 (alternative: keep them until Phase 4).
- One commit convention for the whole repository, no separate DCO rule for `packages/` (alternative: keep DCO for the former bifold files).
- Keep the VTI conformance job and coverage upload; drop repolinter and scorecard.
- `keyring-bifold` stays writable until the first folded store build, then is archived (alternative: archive at once).
- Open bifold PRs: ready ones merge before the cut if reviewed; drafts older than 30 days close with a pointer; the rest re-land by `git am`.
- History lands as one signed squash with the full history on `history/bifold` in this repository, and the push of that ref is covered by this decision (alternatives: a protection change for a history merge; history only in the archive).
- The one PR to `main` needs the product owner's explicit word; the stacked phase PRs merge on review clearance (first answered as "his word for each of two merges to `main`" when the phases were separate merges; superseded by the integration-branch shape).
- Also that evening: the two Phase 1/2 merges were the structural ones he wanted his word on; with the integration branch there is one.
