## 3. Positions adopted, and what they supersede

**P1. Merge with history (`git filter-repo` + `--allow-unrelated-histories`), not `git subtree add --squash`.** Subtree with squash would make `git blame` in a 190,000-line package stop at one commit and discard the DCO sign-offs the bifold repository required. Subtree without squash keeps history but gives a merge commit per import and its own metadata lines; filter-repo gives a plain merge whose paths are already prefixed, and is the tool git's own documentation now points to instead of `filter-branch`. Rejected alternative, kept for the record: a fresh orphan branch with the files copied in ("start clean"). It is the fastest and loses everything D1 protects.

**P2. Fold in place first (same `bifold/` paths), move second.** The alternative, moving to `packages/*` in the same PR, was the first draft. It was dropped because (a) every open bifold PR's patch and every v2 replay applies unchanged while the paths are the same, (b) a Phase 1 failure can only be install wiring, and (c) the review lane clears moves per file by hash and wants moves and edits in separate commits.

**P3. Bundle React Native packages from source (`main: src/index.ts`).** Today's split (source in dev through Metro's resolver, built `lib/` in release) is the reason `ensure-bifold-ready.js` runs `yarn build` on every install and why `tsconfig` redirects three packages. `react-native-locality-peripheral` already ships `main: src/index.ts` and works in release builds, which is the evidence it is safe for the others. Risk noted: `@bifold/oca/build/legacy` is imported by path from 5 app files and must become `@bifold/oca/legacy` or a `src/legacy` export.

**P4. The fold is a store-build boundary (281).** Because `hot-updater` hashes `extraSources` by path, moving the native module folders may change the fingerprint without changing native code. Rather than engineer path stability, old lines keep the old structure and tooling. This matches the product owner's "we don't need to be as careful with the original migration plan"; Q2 asks whether the old lines are retired at 281.

**P5. End the upstream "branch swap" strategy.** `UPGRADE_PROGRESS.md` §2 chose a same-repo fork so upstream commits could be cherry-picked with shared history. After the fold, upstream changes come in as patches (`git am --directory=packages`). The shared-history benefit has shrunk: we are on upstream's React 19 / RN 0.81 / expo 54 line already, and the remaining delta is ours. Superseded in part: `reference-app-sdk-packaging.md`'s assumption that `@bifold/*` are publishable from a separate repository.

**P6. Keep `@bifold/*` names.** A rename is one `sed` and one PR; bundling it in would double the diff of a PR that is already rename-heavy.

**P7. Both workstreams in their own worktrees, consolidation as a named step.** The product owner: "at least two worktrees going on so one does not interrupt the other, later we will consolidate." The v2 lane keeps landing on today's layout; §8.1 of the plan is the replay and cut-over recipe.

## 3a. Revisions after the coordinator's read, same session (~23:50Z)

The coordinator session read the draft and returned ten points. What moved:

**P1 is superseded.** The first draft said "merge with history, not squash" and had the fold land on `main` as a merge commit of 3,756 rewritten bifold commits. That cannot land: wallet `main` requires every commit signed and GitHub-verified (branch protection and `commit-checks.yml`), `git filter-repo` produces new shas and so strips every signature, and the upstream OpenWallet-era history was never signed. The position adopted instead (plan D1, Q0 option a): one signed squash commit on `main`, the full history pushed once to an unprotected `history/bifold` ref in the same repository, and an optional `refs/replace/` graft for anyone who wants `git log --follow` to cross. Options kept for the product owner: a protection change for a history-preserving merge (b), or history only in the archived repository (c). Phase 0 gains a rehearsal on a throwaway repository with the same protection rules. The earlier argument for P1 (blame and sign-off attribution in a 190,000-line package) still holds and is why the history lives in this repository rather than only in the archive.
