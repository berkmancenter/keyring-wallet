# 2026-11-12: where the demo state's did:webs lives, and the evidence

Parent: [`../demo-state-hosting-plan.md`](../demo-state-hosting-plan.md). One session, written with the first draft of
the plan.

## Findings

### F1. The quick tunnel is not reliable enough for a demo

The temporary tunnel ran on 2026-11-12 for the owner's hand run of build 278.16. Cloudflare's free quick-tunnel endpoint
refused new tunnels with HTTP 429 / error 1015 (its rate limit) on two attempts. The tunnel came up on the fourth.

On top of that, each run has a new random hostname. All of the demo's `did.json` files name the host, so they had to be
regenerated, and every phone's "Demo state host" retyped, on every run. Those steps sit on the critical path of a live
demo.

**Concluded:** the quick tunnel stays for ad hoc tests, and a demo needs a host that is the same every time.

### F2. GitHub Pages fixes its own cache lifetime

`curl -sI https://trustoverip.github.io/kswg-did-method-webs-specification/` on 2026-11-12 answered
`server: GitHub.com` and `cache-control: max-age=600`. Pages sets that header and a site cannot change it. A revoked
card's issuer log could then be served stale for up to ten minutes, with nothing on the screen saying so. The phone's
own five-minute reuse (`sedi/webs/lastLive.ts`) applies only after a failed fetch and is labelled with its time; an
intermediate cache is neither.

**Concluded:** Pages is ruled out for the live-revocation demo, which needs `no-store` (plan §1.1). This supersedes an
earlier recommendation, made while the resolver was being planned, of "GitHub Pages under the organization". That
recommendation came before live revocation was in scope.

### F3. The wallet host is our Caddy, and the demo path is free

On 2026-11-12, `https://wallet.asml.berkmancenter.org/.well-known/assetlinks.json` answered 200, `server: Caddy`,
`content-type: application/json`, and `/keyring-demo-state/` answered 404. `deploy/keyring-ota/Caddyfile` describes
that site: "the static site that iOS and Android read for universal links (/.well-known), the install page (/invite),
and short invitation links (/i, /i/<id>)". The app claims only `/invite` and `/i/` there
(`app/ios/AriesBifold/AriesBifold.entitlements`, `app/android/app/src/main/AndroidManifest.xml`).

**Concluded:** the same Caddy can serve the demo state with no new server. Either a new site block on its own hostname
(the plan's recommendation) or a path on the wallet host (the fallback) works.

### F4. Why a separate hostname over the wallet host's path

A did:webs identifier carries its host, and the phone's list stores the root's did:webs. Publishing on the wallet host
would make `did:webs:wallet.asml.berkmancenter.org:…` the demo state's identifier. Retiring or moving the demo would then
mean changing the site the app's universal links depend on.

The trust anchor doesn't move with the host: it is the AID on the phone's list, and the Developer field can repoint a
demo root anyway. So this is about keeping two services apart, not about trust.

**Concluded:** use a separate hostname when a DNS record is cheap, and the wallet host's path only as the fallback.

### F5. Publishing must be atomic

The resolver fetches `keri.cesr`, then `did.json`, and refuses a pair that disagrees (`didDocMismatch`). If a rotation
were published file by file, a phone opening the screen between the two writes would see "Couldn't reach the state".

**Concluded:** publish by swapping a directory symlink (plan §3.2).

### F6. Making the empty field mean "the permanent host" is rejected

The alternative: give the demo root's own did:webs the permanent host, and fetch it whenever "Demo state host" is
empty. It is one line in `websDidToFetch`. It changes, though, what an empty field means. Today the empty field shows
"Demo: checked against a copy on this phone", and a phone fetches nothing unless someone set a host.

**Concluded:** the one-tap demo setup fills the field when it is empty (plan §5, A1). That keeps every existing meaning.

## Open with the SEDI lane (for the K1 design, plan §4)

The plan was drafted while the SEDI lane was busy with build 278.17. These are its questions. The plan's §4 is
conditional until they are answered.

1. K1's shape: is it the same three-level chain as K0 (root, org unit, issuing agent, then the Guardian card), and are
   all its keys P-256 with no witnesses and no delegation, as the resolver requires?
2. The issuance tool: keripy (as the K0 kit was made), or our own? Which of its outputs are the `kel-<name>.cesr` files
   the generator's `--kels` reads?
3. How a K1 card reaches the guardian's phone: the existing carriage, or a new step?
4. Live revocation: is the revocation an event in the issuing agent's log, as K0's G-revoked card has it, so that only
   that AID's `keri.cesr` is republished?
5. Does K1 replace K0 in the one-tap setup, or sit beside it, and which one does the Sunday-after demo use?
