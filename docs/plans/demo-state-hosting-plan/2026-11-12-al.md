# 2026-11-12: where the demo state's did:webs lives, and the evidence

Parent: [`../demo-state-hosting-plan.md`](../demo-state-hosting-plan.md). One session, written with the first draft of
the plan.

## Findings

### F1. The quick tunnel is not reliable enough for a demo

The temporary tunnel ran on 2026-11-12 for the owner's hand run of build 278.16. Cloudflare's free quick-tunnel endpoint
refused new tunnels with HTTP 429 / error 1015 (its rate limit) on two attempts. The tunnel came up on the fourth.

On top of that, each run has a new random hostname. All of the demo's `did.json` files name the host, so they had to be
regenerated, and every phone's "Demo state host" retyped, on every run. Those steps sit on the critical path of a live
demo.

**Concluded:** the quick tunnel stays for ad hoc tests, and a demo needs a host that is the same every time.

### F2. GitHub Pages fixes its own cache lifetime

`curl -sI https://trustoverip.github.io/kswg-did-method-webs-specification/` on 2026-11-12 answered
`server: GitHub.com` and `cache-control: max-age=600`. Pages sets that header and a site cannot change it. A revoked
card's issuer log could then be served stale for up to ten minutes, with nothing on the screen saying so. The phone's
own five-minute reuse (`sedi/webs/lastLive.ts`) applies only after a failed fetch and is labelled with its time; an
intermediate cache is neither.

**Concluded:** Pages is ruled out for the live-revocation demo, which needs `no-store` (plan §1.1). This supersedes an
earlier recommendation, made while the resolver was being planned, of "GitHub Pages under the organization". That
recommendation came before live revocation was in scope.

### F3. The wallet host is our Caddy, and the demo path is free

On 2026-11-12, `https://wallet.asml.berkmancenter.org/.well-known/assetlinks.json` answered 200, `server: Caddy`,
`content-type: application/json`, and `/keyring-demo-state/` answered 404. `deploy/keyring-ota/Caddyfile` describes
that site: "the static site that iOS and Android read for universal links (/.well-known), the install page (/invite),
and short invitation links (/i, /i/<id>)". The app claims only `/invite` and `/i/` there
(`app/ios/AriesBifold/AriesBifold.entitlements`, `app/android/app/src/main/AndroidManifest.xml`).

**Concluded:** the same Caddy can serve the demo state with no new server. Either a new site block on its own hostname
(the plan's recommendation) or a path on the wallet host (the fallback) works.

### F4. Why a separate hostname over the wallet host's path

A did:webs identifier carries its host, and the phone's list stores the root's did:webs. Publishing on the wallet host
would make `did:webs:wallet.asml.berkmancenter.org:…` the demo state's identifier. Retiring or moving the demo would then
mean changing the site the app's universal links depend on.

The trust anchor doesn't move with the host: it is the AID on the phone's list, and the Developer field can repoint a
demo root anyway. So this is about keeping two services apart, not about trust.

**Concluded:** use a separate hostname when a DNS record is cheap, and the wallet host's path only as the fallback.

### F5. Publishing must be atomic

The resolver fetches `keri.cesr`, then `did.json`, and refuses a pair that disagrees (`didDocMismatch`). If a rotation
were published file by file, a phone opening the screen between the two writes would see "Couldn't reach the state".

**Concluded:** publish by swapping a directory symlink (plan §3.2).

### F6. Making the empty field mean "the permanent host" is rejected

The alternative: give the demo root's own did:webs the permanent host, and fetch it whenever "Demo state host" is
empty. It is one line in `websDidToFetch`. It changes, though, what an empty field means. Today the empty field shows
"Demo: checked against a copy on this phone", and a phone fetches nothing unless someone set a host.

**Concluded (first draft):** the one-tap demo setup fills the field when it is empty. That keeps every existing
meaning. **Superseded the same day by F7.**

## SEDI lane answers (same session, later)

The draft's §4 was conditional on five questions to the SEDI lane. Its answers came from the K0 kit's `PROVENANCE.json`
(bifold `72db4ffe7`), and the lane marked what it inferred.

1. **Shape.** K1 is the same as K0:
   - the chain roy → (Unit) deb → (Agent) sue → (Guardian) jordan, naming sam as the ward, plus jordan → (Social) sam;
   - P-256, SHA2-256 prefixes and next-key digests, and Blake3 SAIDs;
   - no witnesses, one key, `kt` 1;
   - ACDC edges, not delegation.

   All the kit's declared deviations stay. In the lane's words: "Don't 'fix' Blake3 to SHA2-256 in K1."
2. **Tool.** keripy at the same pin (`7143832`), with `run_k0.sh` and a `gen_k1.py` copied from `gen_k0.py`. It writes
   `kel-<name>.cesr` beside the TEL, ACDC and schema files, so the generator's `--kels` reads the right files. The keys
   stay on the operator's machine. Only `did.json` and `keri.cesr` go to the host, and issuing and revoking never run
   there.
3. **Delivery to the guardian.** A new step. The existing carriage (keyring-bifold#1027) runs from the approver to the
   person, and K0's card is bundled in the build. The lane's options:
   - (a) bundle a K1 card, which isn't issuance;
   - (b) a Developer "Get the Guardian card from \<host\>" that fetches the card and its TEL and keeps it through
     `holdGuardianEvidence`. The lane recommended this one;
   - (c) a real IPEX grant, which needs a KERI agent on the phone.

   The ward stays a Developer setting.
4. **Live revocation.** A TEL `brv` in the card's own registry, anchored by an event in sue's log. Only sue's
   `keri.cesr` is republished. The phone catches it from the anchor alone. The card itself showing "revoked" would need
   the `brv` published and fetched too. The lane asked the plan to name which one it promises.
5. **K1 beside K0, never replacing it.** K1 gets its own entry with its own AID, name and `demo: true`, and its
   did:webs host fixed in that entry. The setups take a kit choice, K0 by default until K1 has been proven on both
   phones.

**Applied:**
- in plan §4, with the shape, the tool, the card-fetch step (b) and the ward;
- in plan §4, which promises only "The issuer's published record shows it was revoked";
- in plan §5, as A2–A4.

### F7. The one-tap fill collides with "cleared means the copy" (supersedes F6's conclusion)

The SEDI lane pointed out a collision. "Fill the field only when it is empty" and "a cleared field means the copy"
cannot both hold: a tester who clears the field to use the copy has it filled again on the next tap. Fixing that would
take three saved states: never set, set, and cleared on purpose.

The lane also pointed out a larger problem. Routing a state that issues and revokes through a free-text field lets a
typed host stand in for the state's own, and live revocation rests on that host's answer.

**Concluded:**
- K1's host is fixed in its entry on the phone's list, and the field never redirects it.
- The field applies only to K0, by an explicit mark on its entry.
- The one-tap fill is dropped.

This is plan §5 A1 and A2 and their "Why K1's host is fixed" note. F6's rejection of "empty means the permanent host"
stands.

## Later the same day: the bucket, and the card files

### F8. The host moves to a bucket in the infra repository (supersedes F3 and F4's recommendation)

The coordinator moved the hosting work to the infra repository, with the infra lane: "Don't push any Caddyfile,
script or deploy change to keyring-wallet for this." The infra lane's draft (Mickens-Lab/keyring-push-gateway-infra#23)
is a Cloud Storage bucket with one variable: the bucket's own URL, or a hostname we own behind a load balancer.

- The contract (§1.1) holds on both. GCS answers 200 or 404 with no redirect. Read is one object by name. The bucket
  keeps no log.
- `no-store` is per object, so the publish script sets it on every upload. Without it, a public object is served
  `public, max-age=3600`.
- A bucket has no atomic swap, so F5's symlink swap can't apply. The upload order keeps a revocation safe, and
  rotations are published outside demos (plan §3.2).

F4's reasoning still stands, in the new form. A separate hostname keeps the demo's DIDs off the wallet host.

**Concluded:** plan §2 and §3.2 describe the bucket. The Caddy site moves to "Ruled out", as superseded.

### F9. The card files

The SEDI lane's K1 issuer writes the cards; the infra lane's script publishes them. They are agreed between the two:

- **Where they sit.** `cards/` is beside `keyring-demo-state/`, not inside it, since that path is DID space.
- **The id.** The infra lane first proposed a 32-hex `pickupId`. The issuer's 22 base64url characters, from 16 random
  bytes, were taken, since the issuer makes the id.
- **The cache header.** The issuer asked for `no-cache`. `no-store` was kept: it is stricter and meets the same need.
- **A third file.** A `.status.json` beside the card and its page.
- **A revocation** republishes the card's three files along with the issuing agent's `keri.cesr`.
- **Removal** is never the script's job.

**Applied:** plan §1, §1.2, §3.2 and §4.

### F10. A dry run caught the script's DID check

Run with a stub `gcloud`, so nothing left the machine, over a tree from the K0 generator. The draft script refused all
three AIDs: it compared `did.json`'s `id` with the did:webs DID. The generator writes the did:web twin as `id`, as
did:webs specifies, and the phone accepts either form (`sedi/webs/document.ts`, `checkDocument`).

The fix, accepting either form, was sent to the infra lane. Plan §3.1 now states the form both writers use. A dry run
over each writer's tree is part of S2's done-when.

### F11. Local hosting first, and K1's host constant

The owner, relayed by the coordinator: "website should be done locally first and then moved into using the infra
later". The demo is served from a local server through a tunnel, and the bucket (F8) follows later.

- **The local server.** The SEDI lane's runbook served the tree with `python3 -m http.server`. That lists directories,
  so anyone reaching the tunnel could read every pickup id under `cards/`. It also sets neither header. It is replaced
  by a small server that serves only the exact paths in §1 and §1.2, with the headers. The live check passed against
  it, and a request for a directory answered 404.
- **A tunnel and K1's fixed host.** A quick tunnel's hostname changes every run, so a build can't name it. The SEDI
  lane's first design let the field reach K1 whenever no host was set. That reopened F7, on the branch every build
  gets by default.

**Concluded:** `K1_WEBS_HOST` defaults to `null`, and K1 then fetches nothing. The field reaches K1 only through an
explicit opt-in, labelled as a typed host (plan §5 A2).

**Later: the opt-in is declined.** The SEDI lane first read the owner's relayed words, "i mean running it locally
for testing only, we would move to prod later", as choosing `'developerField'`. That reading was put to the owner,
and he declined it in his own words, relayed by the coordinator: "no we should not type it on developer settings, it
should issued if needed somehow … I thought this was as simple as scanning".

**Concluded:** `K1_WEBS_HOST` stays `null`. The host comes with what is issued, the did:webs DID in the card or its QR
code. The designated-alias check is proposed to bind that host to the AID. Without the check, the host a card names is
as untrusted as a typed one (plan §5 A2).
