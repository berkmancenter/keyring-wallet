# iOS builds on Linux — the research re-checked against main (2026-10-13, BAM)

**Status: Draft.** Plan: [`../ios-builds-on-linux-plan.md`](../ios-builds-on-linux-plan.md).
Research it was built from: [`2026-10-05-bam.md`](./2026-10-05-bam.md).

The 2026-10-05 note was written outside the repository. This document records
what changed when its facts were checked against `main` at `0da7eead`.

## F1. Versions and the workspace — confirmed, with precision added

- React Native **0.81.5**, patched (`app/package.json`, `.yarn/patches/react-native-npm-0.81.5-*.patch`);
  React **19.1.0**; Expo **~54.0.31**. The note said "RN 0.81 + Expo modules";
  this is still correct.
- Workspace `app/ios/AriesBifold.xcworkspace`, scheme `AriesBifold` (the root
  `CLAUDE.md`). Unchanged.
- CI selects **Xcode 26.3** on `macos-26` (`test-builds.yml`, `gate-smoke.yml`).
  The note's "App Store uploads now need Xcode 26" is confirmed by
  `staging.yaml`: *"App Store Connect only accepts uploads built with Xcode 26 /
  the iOS 26 SDK since 2026-04-28"*.

## F2. Pod count — 144, and 15 Expo pods

`app/ios/Podfile.lock` lists **144** distinct pods (CocoaPods 1.15.2). The note
said "about 145", which is close enough. It also said "about 12 Expo modules";
the lock has **15** pods with Expo names (`Expo`, `ExpoModulesCore`,
`EXConstants`, `EXImageLoader`, and `ExpoAppIntegrity`, `ExpoAsset`,
`ExpoCrypto`, `ExpoFileSystem`, `ExpoFont`, `ExpoImageManipulator`,
`ExpoImagePicker`, `ExpoKeepAwake`, `ExpoSecureEnvironment`, `ExpoSecureStore`,
`ExpoSharing`). `react-native-attestation`, `react-native-locality-peripheral`,
`askar` and `hermes-engine` are present as the note said. None of this changes
the xtool verdict.

## F3. `yarn e2e:smoke` defaults to Android

`yarn e2e:smoke` runs `e2e/run-onboarding-smoke.js`, and
`const platform = process.env.PLATFORM || "android"`. The note's measurement,
*"`xcrun simctl boot` a device and run `yarn e2e:smoke`"*, would have tested
the Android emulator. **Supersedes** that command: the plan's step 3 uses
`PLATFORM=ios yarn e2e:smoke`. `yarn e2e:vrc` and `yarn e2e:vrc:devices`
exist as the note described, along with `ios-devices` variants of the
witnessed exchange.

## F4. Cloud Mac CI already exists

The note recommended cloud Mac CI (GitHub Actions or EAS Build) for builds and
TestFlight as if it were still to be set up. It is already in place on GitHub's
hosted `macos-26` runners:

- `staging.yaml` `build-ios-staging` builds and uploads to TestFlight;
- `test-builds.yml` `ios-simulator` builds the simulator app;
- `gate-smoke.yml` runs the gate's SMOKE rows on an iOS simulator with no Farm
  and no secrets.

**Concluded.** The second recommendation is done. EAS Build is not needed.
**Supersedes** the note's recommendation 2 as an open item.

## F5. The Mac mini has a concrete job: the release gate

`e2e/gate/README.md` ("Where a gate runs", agreed 10-10) runs the full gate on
"the Mac" only while it is stable. A laptop is stable only with the lid open or
a display attached. A machine with *"no lid at all and no battery is a desktop
and is always stable … so a headless mini still gates"*. Release 236's gate
took about 10 hours, of which about 2 were testing.

**Concluded.** The note's recommendation 1 (a used Apple Silicon Mac mini) was
argued for interactive work. It is stronger than that: it is the gate's natural
runner, and the attended iPhone legs need it too. The plan leads with this.

## F6. Relation to the release flow

`release-flow-plan.md` owns how a build reaches TestFlight, and its channels run
on hosted runners. Nothing here changes it. The gate is a check before release,
documented in `e2e/gate/`, not in that plan.
