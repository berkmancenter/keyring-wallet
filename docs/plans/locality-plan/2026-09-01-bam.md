# 2026-09-01 — Brendan. Item 12 run live: both witnessed e2e variants pass on real hardware, plus two bugs the run surfaced

Closes 2026-08-21-bam.md's "Not run" gap on item 12: two physical Galaxy
phones (`R5CN70Q6PDP`, `R5CY83SM4ST`) and a Linux host with a real
Bluetooth adapter were available today, so `yarn
e2e:vrc:witnessed:locality:android-only` — written 2026-08-21, never
executed — finally ran. It failed twice before passing, and both failures
were real bugs, not flakiness. This document is the reasoning behind the
two fixes and why item 8's own text is now wrong until this supersedes it.

## What passed

Both android-only witnessed variants, on the same two phones, in the same
session:

- `yarn e2e:vrc:witnessed:android-only` (no locality) — clean pass.
- `yarn e2e:vrc:witnessed:locality:android-only` — clean pass: both phones'

  witness-share verified, hardware-attestation evidence present on both,
  Witnessed + Secure Exchange shields shown.

## Bug 1: the witness-connect pre-flight sheet couldn't tell "offered" from "off"

The first `witnessed:android-only` run (no locality involved at all) failed
with "could not land on Contacts within 10 attempts" — a symptom several
steps downstream of the real cause. `LocalityPreflightModal` (item 8) was
showing on this run too, and nothing in this variant's e2e flow expects or
dismisses it, so the UI sat blocked under an unanswered sheet.

Item 8's text says the offer state is "always shown first, regardless of
whether this witness's policy is offered or required (the wallet can't
reliably tell those apart from discovery alone)" — true as written, but the
consequence wasn't fully reasoned through: it also can't tell `offered`
apart from **`off`**, i.e. a witness with no locality leg at all. Discovery
only ever set a `requiredExt` marker for `policy === 'required'`;
`'offered'` and `'off'` produced byte-identical `supportedTypes` rows.
`witness-server`'s own default policy is `'offered'` (config.ts), so *every*
witness — including e2e's, including a hypothetical witness that never
built the locality leg at all — discovery-declared enough to trigger the
sheet.

**Fix, superseding item 8's design as written:** discovery now emits an
`offeredExt` marker distinct from `requiredExt`
(`WitnessTaskSessions.ts`'s `handleDiscovery`), and a new
`getWitnessLocalitySupport` (`ceremony.ts`) reads the tri-state
(`required`/`offered`/`off`/`null`-not-yet-known) in place of the old
boolean `getWitnessLocalityRequirement` (kept as a thin projection for
compatibility). `WitnessConnectionProvider` now skips scheduling the sheet
entirely when support resolves to `off`, instead of showing it
unconditionally. Item 8's own text needs updating to read "shown for a
witness that discovery-declares `offered` or `required`" — not "always
shown first" — the next section below is what that rewrite should say.

On the e2e side: `startWitness` (`e2e/lib/witness.js`) now defaults spawned
witnesses to `WITNESS_LOCALITY_POLICY=off` — the opposite of
`witness-server`'s own default — because every witnessed-exchange variant
except the locality one has no code path that expects this sheet. The
locality runner explicitly sets it back to `required`.

Also fixed the sheet's own copy while touching it: "X can confirm in-person
meetings. Allow Bluetooth?" read as X being generically capable of
confirming meetings, not that Bluetooth on THIS phone confirms THIS
exchange. Now "Allow Bluetooth to confirm you're at X?", with a body that
states the Bluetooth mechanism explicitly.

Tests: `getWitnessLocalitySupport` tri-state coverage in `ceremony.test.ts`
(4 new cases), an `off`-skips-the-sheet case in
`witnessConnectionProvider.test.tsx`, updated copy assertions in
`LocalityPreflightModal.test.tsx`. `packages/core`'s full suite (178 suites)
and `witness-server`'s typecheck both clean.

## Bug 2: fixing bug 1 exposed a second one — nothing tells the operator to answer the sheet

With the sheet correctly gated to only the locality-required run, that run
then failed the same "could not land on Contacts" way on its own first
attempt: the sheet appeared on both phones as designed, but there is no
Appium automation for it (item 8 already documents this is a human step),
and — the actual gap — no loud signal telling the operator to look for it,
unlike the biometric step's own boxed `████ OPERATOR: authenticate NOW
████` banner. By the time the sheet was noticed, the run's own downstream
timeout had already elapsed.

**Fix:** `witnessedExchangeFlow.js` now prints the same boxed-banner
treatment right before either phone connects to the witness, gated on
`assertLocality`, so the operator is watching both phones before the sheet
can appear on either. Confirmed fixing a run that had just failed exactly
this way — second attempt passed clean.

## A local-environment red herring, worth naming so it isn't re-investigated

Both runs' witness announced `eventName: "Other event"` — this is
`bifold/packages/witness-server/.env`'s own `WITNESS_EVENT_NAME`, a
per-developer file `startWitness` does not override the way it already
does `MEDIATOR_INVITATION_URL` (for exactly the "works on my machine"
reason documented at that override's own comment). Not a bug in this
session's changes; flagged here only because it briefly looked like one
mid-run. Whether `startWitness` should pin `WITNESS_EVENT_NAME` the same
way is an open, small item — not done today.

## Open, not yet decided: no locality indicator on the Contacts list or detail screens

Raised after today's runs: `ContactDetails.tsx` already renders a Locality
Verification line per witness record (via `extractWitnessInfo`'s
flat-members-first, legacy-nested-fallback read — item 11's "three-state
reader" doing exactly what it was built for), but it is nested inside each
Witness Record entry, not a glanceable indicator, and `ListContacts.tsx`
has no locality signal at all next to its existing `shield-check` /
`check-decagram` badges. A proposal (badge icon, placement, data source)
is being drafted; nothing is decided or built yet. This paragraph exists so
the gap doesn't need re-discovering — the fix, once picked, updates this
same file, not a new one.
