## Finding 3 — ceremony-window edges: adopted, with `windowSeconds` narrowed

The reason-vocabulary gap and the permission-timing point were already closed
by §8.4 (same commit as the finding) and by the existing §8.1 language on a
single-source default — no further edit needed there beyond formalizing the
`windowLost` reason value in §7.1 rule 5, and correcting §8.4's own forward
reference to it (it had written `window-lost`, prose-cased, before the value
existed anywhere in §7.1).

The `windowSeconds` anchor is where this document's position differs in
substance from the review's framing, not in conclusion. The review discussed
anchoring "`windowSeconds`" as one parameter — radio-side vs. padded for
task-channel latency. Looking at the reference rung
(`tsp-reference/ref-06p-locality-binding/run.mjs`) before writing the edit
showed no code anywhere gives `windowSeconds` enforcement semantics yet: the
rung sets it as a literal in the directive and only asserts that `ext`
survives the pipeline byte-identically; the plan's own §5.3 says only that the
sensor "records... the wall-clock window," past tense, after the round trip
already completed. There was no stated design for what happens *at*
`windowSeconds`, on either side.

Once stated, it splits into two things with different owners:

- **The device's own advertise-patience** — how long the wallet keeps
  advertising before giving up and surfacing `windowLost`. This is a local UX
  timeout. It is not evidentiary, does not need a schema field, and is not
  specified by this plan.
- **The sensor's own trust bound** — how long after opening a session the
  witness will still credit a connection as belonging to it. This is the only
  half that is load-bearing, the only half that appears in the VWC
  (`localityWindowSeconds`), and the half `ref-06p2`/`ref-06p4` need to
  measure and enforce.

Only the second is `windowSeconds` as a protocol parameter — no schema split
needed, contrary to what I raised as an open question before looking at the
rung. It is anchored radio-side: at the sensor's own clock, from when it
starts scanning for the session's expected EID to when it first observes a
matching advert, not at directive-mint time. Both ends of that measurement are
the witness's own, so the bound never depends on the device's clock or on
task-channel delivery latency (mediator dial-out, pickup-poll cadence) — which
was the review's underlying concern, addressed without needing to budget or
measure that latency at all. Recorded in §5.5, alongside the existing RTT
bound it is a close cousin of but distinct from.
