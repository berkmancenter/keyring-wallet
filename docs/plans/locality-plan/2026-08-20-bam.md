# 2026-08-20 — Brendan. `ref-06p2` built and run against a real phone; the BLE library finding

`ref-06p2-ble-observation` (locality-plan.md §10.1) was designed, built, and
run for real: two independent radios (this box's `hci0`, a phone running nRF
Connect for Mobile's local GATT-server feature), a real advert, a real GATT
connection, a real write/read round trip. Two runs, 35 trials total, landed
consistently at median ≈180ms / p95 ≈224ms. Recorded in the rung's own
`fixtures/measured-rtt.jsonl` and its README; this document is about a
finding along the way, not the rung's result.

## The finding: raw HCI sockets are the wrong default on a box also running `bluetoothd`

`ref-06p2` was first built on `@abandonware/noble` — a raw `AF_BLUETOOTH` HCI
socket, matching how noble/bleno are normally described ("BlueZ gives a Node
process the scanning and GATT-central roles," locality-plan.md §5.6, as
originally written). With `cap_net_raw` granted to the `node` binary
(noble's own documented no-root setup) and the adapter confirmed
`poweredOn`, `startScanningAsync()` produced **zero discover events**,
indefinitely — not an error, just silence.

Diagnosis, in order, each ruling out one candidate cause:

1. **Not a permissions problem.** The identical script run as root (`sudo
   node ...`, pinned to the exact binary — `sudo` resets `PATH`, so a bare
   `sudo node` silently ran a different, older Node install with no
   `node_modules`) also saw nothing.
2. **Not a dead radio.** `bluetoothctl scan on` — BlueZ's own discovery, via
   D-Bus — found the room's real ambient BLE devices (solar/battery
   equipment, a smart light, several phones) in the same window noble found
   nothing.
3. **Not our script's bug.** noble's own bundled `examples/advertisement-discovery.js`,
   run unmodified, produced the same silence.
4. **A real, separate radio flakiness, on top.** Independently of the above,
   the adapter went through a period where *even* `bluetoothctl` found
   nothing — HCI event counters barely moved during an active scan. A
   `btusb` driver reload (`modprobe -r btusb && modprobe btusb`, then restart
   `bluetoothd`) fixed this, repeatedly, when it recurred. This is a real
   fact about the specific dev machine and adapter (Intel AC9260) and not
   a finding about the library choice — recorded in `ref-06p2`'s README as a
   troubleshooting step because it is cheap to hit and cheap to fix, not
   because it says anything about production hardware.

(1)–(3) together point at one thing: two independent processes opening the
same raw HCI channel — noble's socket, and `bluetoothd`'s own management of
the adapter's scan state — contend, and the failure mode is silent. noble's
own README says as much, in the "Running without root/sudo" section: *"You
will not get any errors if running without sudo, but nothing will happen."*
That sentence is usually read as being about the capability grant
specifically; empirically, on this box, the identical symptom also showed up
with the capability correctly granted and confirmed, simply because
`bluetoothd` was also holding the adapter.

## The fix, and why it generalizes

Switched to `node-ble`, a pure-JS BlueZ client over the same D-Bus interface
`bluetoothctl` uses. No native bindings, no raw socket, no contention with
`bluetoothd` — it *is* a client of `bluetoothd`, the same way `bluetoothctl`
is. Once a one-time D-Bus policy file was in place (`node-ble`'s own
documented setup — allow this user to `own`/talk to `org.bluez`), scanning,
discrimination against real ambient devices, connecting, and the GATT round
trip all worked, repeatedly, with `bluetoothd` running normally throughout.

This is not just a workaround for one rung. §5.6 already settled that the
production witness server runs *at the venue*, on a box the operator also
presumably wants to use its Bluetooth stack normally for. A production
`BleLocalityProvider` built on a raw HCI socket would need `bluetoothd`
stopped, or would be exposed to the same silent-contention failure mode this
rung hit — undetectable in a way that would look exactly like "no locality
today," which is precisely the failure §8.2's whole `offered`-not-`required`
argument assumes is rare and recoverable, not systemic. Going through D-Bus
costs nothing here (no root needed beyond the one-time policy file; no
native build step) and removes a whole class of "why is scanning silently
empty" incidents before they happen in the field.

**Supersedes:** the informal reading of §5.6's "BlueZ gives a Node process
the scanning and GATT-central roles" as implying a raw-socket library
(noble/bleno) was ever a decision — it wasn't; the plan simply hadn't named
BlueZ's two access paths as a choice. §10.2 item 2 is edited in place to name
the D-Bus path as the one to build, with this document as the evidence.

## Also recorded, smaller

- **`sudo` resets `PATH`.** `sudo node ...` finds `/usr/bin/node` (an old,
  system-package Node) rather than an nvm-managed one on `PATH` for the
  invoking user. Any future root-level Node invocation on a dev box using
  nvm needs the full `readlink -f $(which node)` path, not a bare `sudo
  node`.
- **BlueZ's `RSSI` device property is not reliable once connected**, and was
  `null` in both measured runs even captured just before `connect()`. The
  rung still tries and records it; the timing bound (§5.5) does not depend
  on it, so this did not block anything, but a future implementer should not
  expect `rssi` corroboration (§7.1's `localityRssiDbm`) to be populated from
  this code path without more work than "read the property."
