# 2026-08-21 — Brendan. `ref-06p3` and `ref-06p4` built and run

Two rungs finished today: `ref-06p3-third-party-verify` (no hardware,
16 checks) and `ref-06p4-relay-trial` (two real runs against a phone,
5 checks each). Both are marked done in locality-plan.md §10.1. This
document is the reasoning behind two decisions and one bug, not a
restatement of what the rungs' own READMEs already cover in full.

## `ref-06p3`: the plan already promised three-state coverage, and the first draft didn't have it

Locality-plan.md §8.2 states the "emit `confirmed: false`, never omit" rule
is "tested in `ref-06p3`" (written before this rung existed). The first
implementation only exercised the happy path — a genuine bundle passing all
seven steps — because building the seven forgeries turned out to be most of
the work, and it was easy to call the rung done once those passed. It
wasn't: the plan's own text already committed to something this build
hadn't done yet.

Fixed by adding `confirmed` / `declined` / `not-offered` as three
pairwise-distinguishable verifier outcomes: `declined` runs only the
document-level steps (1–3) since there's no transcript to check when the
device never answered, and — the check worth naming specifically — a
`declined` bundle is not exempt from proof tampering either; a corrupted
proof on a `declined` claim still fails at step 1. `not-offered` is
detected before any mechanical step runs at all, since its only signal is
the total absence of `locality*` members, matching the plan's own §7.1
rule 5 wording exactly.

**Lesson for next time, stated plainly:** when a plan document makes a
specific claim about what a not-yet-built rung will test, that claim is a
checklist item, not foreshadowing. Worth grep'ing the plan for the rung's
own name before calling it done.

## `ref-06p4`: one real leg, one simulated — a scope decision, not a compromise discovered late

The ladder table says `ref-06p4` needs "two BLE radios." This box plus one
phone IS two radios — but both are already spoken for as sensor↔device
directly (the `ref-06p2` topology). A genuine two-*hop* relay (device →
attacker-near-device → attacker-near-sensor → sensor) needs a *third* radio,
which wasn't available.

Decided up front, not discovered as a limitation partway through: build the
relay as the plan's own wording already describes it — "two processes
bridge the GATT exchange over a socket with injected latency" — and let one
of those two processes be the one that owns the real BLE connection, while
the other injects the delay a second physical hop would add. This is not
the same claim a three-radio relay would let us make (a genuinely staged
second link could show artifacts — jitter, occasional loss — a socket delay
doesn't), and the rung's README says so under "What it does NOT prove"
rather than leaving it implicit. What it DOES let us do is answer §5.5's
actual question — at what added latency does a bound derived from the
honest distribution start rejecting it, and what does that bound cost
honest devices — using a real round trip as the base measurement instead of
a synthetic one.

**Measured, both runs:** honest baseline median ≈180ms / p95 ≈224.7–224.9ms
(matching `ref-06p2`'s independent measurement of the same physical round
trip almost exactly — a good cross-check that both rungs are measuring the
same thing). 5–20ms of injected delay stayed indistinguishable from honest
(median 180.1ms at 20ms injected, vs. 179.9ms honest) — §5.5's "sub-10ms
local relays are achievable and indistinguishable" claim, checked rather
than assumed. The first delay whose *fastest* trial still exceeded the
bound was 100ms. A bound's false-rejection rate was checked against a
*second*, independent honest sample (224.9ms) rather than the sample the
bound was set from (224.7ms) — checking a bound against its own source
sample would trivially read "about 5%, as designed" and prove nothing; the
two independent samples landing within 0.2ms of each other is the actual
finding, and it says the p95 line is stable, not noise.

## The bug: stale `Device` object across reconnect retries

While making the real BLE leg reliable (the same class of flakiness
`ref-06p2` hit), a retry loop that reused the same `node-ble` `Device`
object across attempts started failing with `UnknownObject` on later
retries after the first attempt's `connect()` timed out. Two things
compound: a timed-out `connect()` promise doesn't cancel BlueZ's underlying
D-Bus call, and Android rotates the phone's random BLE address between
advertising sessions — so the D-Bus object path a stale `Device` handle
points at can simply stop existing by the next attempt.

Fixed by re-scanning from scratch on every retry (`connectFresh()` in
`device-leg.mjs`) rather than retrying against a cached object. Folded into
§10.2 item 2's acceptance text so the production `BleLocalityProvider`'s own
reconnect logic doesn't rediscover this the same way.

## `ref-06p5`: App Attest and Play Integrity are not symmetric, and the plan has been treating them as if they were

Locality-plan.md §7.1 carries `localityHardwareAttestation` as one field
with three states (`verified` / `present-unverified` / `absent`) regardless
of platform. Building `ref-06p5` — genuinely, against a real Apple-signed
attestation object, verified offline against Apple's real public root —
surfaced that the two platforms aren't interchangeable underneath that
shared field: App Attest's chain is checkable forever with nothing but the
object and Apple's public root; a Play Integrity token is **encrypted**,
and decoding one is *always* a live call to Google's backend. There is no
offline path for Play Integrity, now or later, with or without test data —
it needs a registered Play Console app, a Google Cloud service account, and
a network call, permanently. Recorded as **Q7** in §11 rather than resolved
here: is that online dependency acceptable for Android's half of locality,
or does Android's existing offline-verifiable Key Attestation (already used
for VRC hardware evidence per `docs/HARDWARE_ATTESTATION_FLOW.md`) belong
here instead? `ref-06p5` ships Play Integrity as shape-only pending that
call, with `live-play-integrity-optional.mjs` parked and ready to run the
real thing once Play Console/Google Cloud access exists — which is also
what was actually asked for when this rung was scoped: build the real App
Attest path now, and set up the Play Integrity live check as separate,
explicit future work rather than fake it or skip it silently.

## Also recorded: a summarizing web fetch is not safe for pinning cryptographic material

While pinning Apple's App Attest root CA (for `ref-06p5`'s act 0 — proving
the root this rung trusts is the one Apple actually publishes, not
node-app-attest's word for it), an initial fetch through a
summarization-mediated tool silently altered a handful of base64 characters
mid-certificate — invisible unless the fingerprint is checked, which is
exactly what makes it dangerous rather than merely wrong. A direct `curl`
fetch, with the SHA-256 fingerprint checked against the value both fetches
were supposed to agree on, caught it. **Any future pin of cryptographic
material — a root cert, a public key, a test vector — should be fetched raw
(curl/direct HTTP) and fingerprint-checked, never taken from a
summarizing/AI-mediated fetch tool's transcription.** This is a corpus-wide
lesson, not specific to App Attest.

## §10.2 (witness-server, items 1–6) built — and a real blocker found first

Asked to continue into §10.2/§10.3, the first thing that turned up was that
the ground didn't exist yet: `bifold/packages/witness-server/src/WitnessService.ts`
on this repo's pinned bifold commit (`7a42a7b0`, on `main`) still runs the
**legacy chat-message ceremony** (`session-request`/`submit-presentation` as
JSON over DIDComm basic messages) — not the Trust Tasks
(`witness/session`/`witness/session/submit`) ceremony §10.0 says has been
"Implemented and live-proved... since 2026-08-18." It has been, but on
bifold's `feat/trust-tasks-integration` branch — 2281 commits past `main`,
which is what `.gitmodules` and the submodule pin actually tracked. A
companion doc already on file (`2026-08-19-al.md`) said as much explicitly
("Written on `feat/trust-tasks-integration`; this folder unifies with the
plan's branch at merge") — that unification hadn't happened anywhere, not on
`main`, not on `plan/locality` (checked both, same stale pin on each).

Repointed the bifold submodule to `feat/trust-tasks-integration`'s tip
(`592af01e`) and updated `.gitmodules` — **with the user's explicit
sign-off**, asked for first, since silently repointing a submodule 2281
commits is exactly the kind of hard-to-reverse-feeling repo-wide change the
root CLAUDE.md's git-safety rule exists for. Getting back to a green
baseline after that took real repair, recorded here because each is a
trap the next branch-advance will hit again if unrecorded:

- **`app/tsconfig.json` had no `paths` mapping for `@openvtc/trust-tasks`'s
  subpath exports** (`@openvtc/trust-tasks/witness/session/0.1/payload`,
  etc.) — `tsconfig-base.json`'s `moduleResolution: "node"` (legacy) doesn't
  follow `package.json` `exports` maps at all. `bifold/packages/core`'s own
  tsconfig already had the fix; `app`'s didn't, because app's typecheck is
  what pulls bifold/core's source into one TS program via the `portal:`
  resolution, and nobody had needed it there before this branch. Fixed by
  mirroring core's exact `paths` entries into `app/tsconfig.json`.
- **`app/jest.config.js` had the same gap, one layer down**, for Jest's
  *runtime* resolution rather than the type-checker: no `moduleNameMapper`
  entry, and `@openvtc` missing from `transformIgnorePatterns`'s allowlist
  (the package is ESM-only with an import-only `exports` condition, so
  Jest's default CJS `require` can't resolve it, and even once resolved the
  raw ESM `export const` syntax needs Babel to run over it, which
  `transformIgnorePatterns` was skipping). Fixed by mirroring both settings
  from `bifold/packages/core/jest.config.js`.
- **`bifold/` is its own separate yarn workspace, with its own
  `node_modules` and `yarn.lock`** — and the root's `scripts/ensure-bifold-ready.js`
  preinstall hook only runs `yarn install` inside it when
  `bifold/node_modules` doesn't exist yet. It already existed (from the
  previous commit), so the hook skipped reinstalling even though the new
  commit's `package.json` files added a real dependency
  (`@openvtc/trust-tasks` in `bifold/packages/core/package.json`) that
  needed to land in bifold's own nested `node_modules`. A root-level `yarn
  install` alone never surfaces this — it has to be `cd bifold && yarn
  install` specifically. **Any future submodule commit advance should
  budget for this as a matter of course**, not rediscover it fresh.
- **`vrc-contexts` publishes from `build/`, not `src/`.** Editing
  `witnessedExchangeContext.ts`'s source and running a consuming test
  immediately produced `jsonld.ValidationError` for terms that were
  unmistakably right there in the file — because every consumer resolves
  the package via `main: "build/index.js"`, and nothing rebuilds that
  automatically on a source edit. `yarn build` inside `vrc-contexts` fixed
  it. Worth remembering for item 13's CI vocabulary guard too: that check
  needs to run against a *built* `vrc-contexts`, or it will pass locally
  against fresh source while CI (which does a clean install-then-build)
  would have caught a real staleness bug — or vice versa.

With that foundation solid (typecheck/lint/test green across witness-server,
bifold/core, and app before touching anything further), items 1–6 landed as
real, typechecked, unit-tested code — full status in the plan's §10.2 table
above. Two design calls worth recording beside the implementation:

- **The real transcript signs with P-256, not the reference ladder's
  Ed25519.** `ref-06p`/`ref-06p2`/`ref-06p3` all used Ed25519 for the
  transcript signature, reusing the corpus's one crypto primitive
  everywhere. The actual device signs the locality transcript with the
  *same* EC-P256 key it already uses for VRC hardware attestation
  (`docs/HARDWARE_ATTESTATION_FLOW.md` — Secure Enclave and StrongBox both
  speak P-256). `trustTasks/locality.ts` verifies P-256 ECDSA via
  `@noble/curves`'s NIST export, the same library `documentProof.ts`
  already uses for Ed25519, just a different curve. This is also what makes
  §7.3 step 6 (does the radio key match the credential signer?) a plain
  base64 comparison rather than a second signature check: both keys are
  already-verified P-256 points at that point.
- **`LocalityProvider`/`NullLocalityProvider` were left alone, on purpose,
  after a false start.** The obvious move — revise that shared interface in
  place for the new direction (§5.2's device-advertises flip) — would have
  broken the legacy basic-message ceremony's compile, because
  `LocalityService.ts` (explicitly *not* being reworked, per this plan's own
  §10.2 preamble) still implements the old shape and is still wired into
  that still-serving path's own gating logic. Reverted that edit and put the
  new port under its own name (`TaskLocalityProvider`/`BleLocalityProvider`,
  in `trustTasks/`) instead. The lesson: "revise the port" in a plan can mean
  "add a new one, distinctly named," when the old one is genuinely still
  load-bearing elsewhere — check call sites before assuming a rename is a
  clean in-place edit.

**Not done, and worth naming plainly rather than letting the ✅ marks above
imply otherwise:** no live end-to-end run has exercised any of this yet —
not the BLE observation against a real device, not the full DIDComm
session→submit round trip, not the discovery/required-policy refusal path.
Everything above is real code, typechecked, and unit-tested at the
crypto/decision-logic layer (`locality.test.ts`, 19 cases;
`localityVocabulary.test.ts`, 4 cases) — the same split this whole codebase
already uses (`WitnessService.test.ts`'s own header says integration is
proven by e2e, not by mocking a full Credo agent for a unit test). §10.3
still has the harder half ahead: the device-side native BLE peripheral
(item 9) is a different category of work entirely.

## Item 9, scoped: what the Android native work actually requires

Asked to scope item 9's Android half next. Read
`react-native-attestation/android/src/main/java/com/attestation/AttestationModule.kt`
(the only existing native-module pattern in this repo to mirror), the app's
`AndroidManifest.xml`, `app/android/build.gradle`, and `ref-06p2`'s README
(which documents exactly what a phone needs to do in the peripheral role,
since that rung stood a phone in via nRF Connect rather than building this).
Findings, in order of how much they change the design:

- **The hardware-attestation key cannot be signed with as currently
  configured, inside a live GATT round trip — this is a real conflict, not
  a detail.** `AttestationModule.kt:223-233` creates the key with
  `setUserAuthenticationRequired(true)` and, on API 30+,
  `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`
  — Android's per-operation auth model: every `Signature.sign()` against this
  key needs a fresh `BiometricPrompt` bound via `CryptoObject`, not a
  time-windowed unlock. §5.5's RTT bound (witness-server's
  `PROVISIONAL_RTT_BOUND_MS = 400`) cannot include a human looking at a
  fingerprint prompt mid-round-trip. The plan's own item 9 text — "sign with
  the existing hardware-attestation key" — reads as if this is a
  straightforward reuse of `signWithHardwareBiometricAuth`
  (`vrc-hardware-signing.ts`'s existing call site); it is not, and an
  implementer who tried that first would discover the conflict only after
  building the GATT server, not before.
  - The resolution follows directly from how Android's own `CryptoObject`
    API is shaped: authorization and use are already two separate steps in
    the platform API, just usually collapsed into one call in this codebase's
    existing usage. Present the prompt once, early (when the sensor
    directive arrives, before advertising even starts), keep the resulting
    authorized `Signature` object alive in native memory, and perform the
    real `sign()` call later, synchronously, inside the write callback. This
    is not a workaround bolted onto the platform's model — it is the
    intended use of per-operation `CryptoObject` auth, just not the shape
    `AttestationModule.kt` happens to use today (create-key/sign as two
    calls, each atomic prompt-then-immediately-use).
  - Recorded this in the plan itself (§10.3 item 9), not only here, because
    it is a standing design constraint an implementer needs before starting,
    not a story about how this session found it.
- **The RN bridge itself is a timing risk, not just the biometric prompt.**
  `ref-06p2` measured ~180 ms median / 224 ms p95 for a real connect +
  discover-services + write + read with *no* JS involved at all. Bouncing
  each GATT server callback (write received, read requested) across the RN
  bridge into JS and back adds indeterminate JS-thread scheduling delay on
  top of a budget that's already most of the way to witness-server's
  provisional 400 ms bound. The peripheral's advertise/GATT-server/sign/serve
  loop should be one native state machine, called from JS once and resolving
  once — matching `DeviceLocalityProvider.respondToSensor()`'s contract
  exactly, so nothing about the `witnessCeremony.ts` wiring done earlier
  today needs to change when this lands.
- **This wants its own package, not an addition to
  `@bifold/react-native-attestation`.** That package's own README/structure
  is entirely about attestation and hardware-key signing; BLE
  advertising/GATT-server APIs are a different Android surface with their
  own manifest permissions and lifecycle concerns. The monorepo already
  keeps concerns this separate (`witness-server`, `react-native-attestation`,
  `oca`, `verifier`, `vrc-contexts`, `vrc-reference`, `vrc-shared`,
  `remote-logs` are each their own package) — a new
  `@bifold/react-native-locality-peripheral`-shaped package follows that
  convention rather than breaking it. It does need read access to the same
  KeyStore alias `AttestationModule.kt` creates
  (`HARDWARE_SIGNING_KEY_ALIAS`), which currently lives as a private constant
  in that one file and will need to move somewhere shared.
- **No BLE code exists in the app at all today, in either direction.** Grepped
  for it before assuming otherwise: the two `BLUETOOTH*` manifest entries and
  the `NSBluetooth*UsageDescription` iOS strings are upstream bifold/BC Wallet
  boilerplate for call-audio routing, unrelated to VRC — confirmed by reading
  what they're attached to, not just by their presence. There is no
  `PermissionsAndroid` call for Bluetooth anywhere in `app/` or
  `bifold/packages/core`, because the legacy `LocalityService`'s scanning
  role has always lived in `witness-server` (a separate Node process), never
  in the wallet. So item 9 is greenfield on the permission-request UX too,
  not a rewire of an existing flow — worth knowing going in, since it's easy
  to assume "the app already asks for Bluetooth somewhere" and go looking for
  a flow to extend that doesn't exist.
- **Validation doesn't need a new idea — `ref-06p2` already named it.** Its
  own README states the nRF-Connect-as-peripheral stand-in "stays that way
  until the Keyring app's own peripheral role ships … and can be pointed at
  this same sensor script." So the acceptance path for this item, once
  built, is: point witness-server's real `BleLocalityProvider` (already
  built, §10.2 item 2 — not a reference-rung stand-in) at the native
  peripheral on the attached physical device (`R5CN70Q6PDP`), before
  reaching for the full `e2e:vrc:devices` suite (item 12).

**Not done in this pass, deliberately:** no Kotlin was written. This was a
scoping pass only, at the user's request, specifically because the biometric-
timing conflict above is exactly the kind of thing that should be surfaced
and, ideally, sanity-checked before code exists — not discovered by building
past it.

## Item 9, continued: the Spec/interface shapes, and the pure-TS half that could be built now

Asked to go ahead and sketch the actual interface shapes. Two things came
out of that beyond the sketch itself:

- **The EID/UUID/binding derivation (§5.3-5.4) is pure TS with no native
  dependency, so it didn't need to stay a sketch — it's real code now.**
  Added `deriveEid`, `serviceUuidFromEid`, `bindingFor`,
  `LOCALITY_CHARACTERISTIC_UUID`, `LOCALITY_BINDING_CONTEXT` to
  `deviceLocality.ts`, matching witness-server's `trustTasks/locality.ts`
  copy exactly. Cross-checked, not just eyeballed: ran witness-server's real
  functions via `ts-node` against a frozen set of inputs and pasted the
  output into `__tests__/deviceLocality.test.ts` as the expected values — 5
  cases, including one that composes the whole chain
  (challenge+taskDigest → EID → the exact service UUID a real sensor would
  scan for). This is the same fixture-parity pattern the reference ladder
  already uses, applied for the first time across the wallet/witness-server
  boundary specifically (previously each side's tests only checked
  themselves).
- **The native Spec itself (`@bifold/react-native-locality-peripheral`) is
  one bridge method, not several.** `NativeLocalityPeripheral.ts`'s
  `respondToSensor(params)` runs the *entire* advertise → GATT-serve →
  sign → resolve lifecycle natively and resolves once, mirroring
  `DeviceLocalityProvider.respondToSensor()`'s contract exactly (transcript,
  or `null` on window-lost) — not split into `advertise()`/`sign()`/`serve()`
  calls, for the RN-bridge-latency reason recorded above. One real
  consequence of that choice: because only the native side ever learns
  `sensorNonce` (the sensor writes it over BLE), and the binding can't be
  signed without it, native has to assemble the same JCS-canonicalized
  binding `bindingFor()` computes *itself*, in Kotlin — a **third** deliberate
  duplicate of that one algorithm, joining the wallet (Hermes) and
  witness-server (Node) copies. Extended the frozen fixture to include a
  known `sensorNonce`/`sensorDid` and the exact resulting `bindingUtf8`/
  `bindingHex`, specifically so a future Kotlin implementation has something
  to check itself against rather than relying on eyeballed agreement with
  two files it can't easily import.
  - `hardwareAttestation` state is a *parameter into* `respondToSensor`, not
    something native derives — it's already knowable before advertising
    starts, from the existing attestation flow. Deliberately did NOT thread
    this through `DeviceLocalityProvider`'s existing interface (which item
    10 already wired into the real `ceremony.ts` call site, tested, this
    session) — instead `AndroidBleDeviceLocalityProvider` (the sketch
    implementation) takes a `GetHardwareAttestationState` function
    injected in its constructor, so determining that state is a decision
    left to whoever wires this in for real, not baked into the interface
    boundary `witnessCeremony.ts` already depends on.
- **`AndroidBleDeviceLocalityProvider` exists, typechecks, and is
  unit-tested against a mocked bridge** (4 cases: param marshaling including
  the derived UUID, transcript reassembly, the null/window-lost pass-through,
  and that a genuine native rejection propagates rather than being
  swallowed) — but it is **not wired into `ceremony.ts`**, which still
  constructs `NullDeviceLocalityProvider()` at its one real call site. There
  is nothing to switch to yet.
- **The new package is deliberately not wired into the yarn workspace.**
  `bifold/packages/react-native-locality-peripheral/` has its own
  `package.json`/`tsconfig.json` and typechecks standalone (verified via a
  temporary `node_modules` symlink to `core`'s, removed immediately after —
  not left in place), but is not a dependency of `core` or `app`, and no
  `yarn install` was run against it. Its own README says so explicitly and
  lists what actually building the native side requires, in order (manifest
  permissions, the shared KeyStore alias, the biometric-authorization split,
  the GATT state machine, the binding-assembly duplicate, and the validation
  path via witness-server's real `BleLocalityProvider` against the attached
  physical device).

**Still not done, and still deliberately so:** no Kotlin, no Android
manifest changes, no workspace wiring. The pure-TS half of item 9 (EID/UUID/
binding derivation) is now real, tested code; the native half is a reviewed
interface with nothing behind it yet.
