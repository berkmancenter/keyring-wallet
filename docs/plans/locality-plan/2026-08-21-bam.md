# 2026-08-21 — Brendan. `ref-06p3` and `ref-06p4` built and run

Two rungs finished today: `ref-06p3-third-party-verify` (no hardware,
16 checks) and `ref-06p4-relay-trial` (two real runs against a phone,
5 checks each). Both are marked done in locality-plan.md §10.1. This
document is the reasoning behind two decisions and one bug, not a
restatement of what the rungs' own READMEs already cover in full.

## `ref-06p3`: the plan already promised three-state coverage, and the first draft didn't have it

Locality-plan.md §8.2 states the "emit `confirmed: false`, never omit" rule
is "tested in `ref-06p3`" (written before this rung existed). The first
implementation only exercised the happy path — a genuine bundle passing all
seven steps — because building the seven forgeries turned out to be most of
the work, and it was easy to call the rung done once those passed. It
wasn't: the plan's own text already committed to something this build
hadn't done yet.

Fixed by adding `confirmed` / `declined` / `not-offered` as three
pairwise-distinguishable verifier outcomes: `declined` runs only the
document-level steps (1–3) since there's no transcript to check when the
device never answered, and — the check worth naming specifically — a
`declined` bundle is not exempt from proof tampering either; a corrupted
proof on a `declined` claim still fails at step 1. `not-offered` is
detected before any mechanical step runs at all, since its only signal is
the total absence of `locality*` members, matching the plan's own §7.1
rule 5 wording exactly.

**Lesson for next time, stated plainly:** when a plan document makes a
specific claim about what a not-yet-built rung will test, that claim is a
checklist item, not foreshadowing. Worth grep'ing the plan for the rung's
own name before calling it done.

## `ref-06p4`: one real leg, one simulated — a scope decision, not a compromise discovered late

The ladder table says `ref-06p4` needs "two BLE radios." This box plus one
phone IS two radios — but both are already spoken for as sensor↔device
directly (the `ref-06p2` topology). A genuine two-*hop* relay (device →
attacker-near-device → attacker-near-sensor → sensor) needs a *third* radio,
which wasn't available.

Decided up front, not discovered as a limitation partway through: build the
relay as the plan's own wording already describes it — "two processes
bridge the GATT exchange over a socket with injected latency" — and let one
of those two processes be the one that owns the real BLE connection, while
the other injects the delay a second physical hop would add. This is not
the same claim a three-radio relay would let us make (a genuinely staged
second link could show artifacts — jitter, occasional loss — a socket delay
doesn't), and the rung's README says so under "What it does NOT prove"
rather than leaving it implicit. What it DOES let us do is answer §5.5's
actual question — at what added latency does a bound derived from the
honest distribution start rejecting it, and what does that bound cost
honest devices — using a real round trip as the base measurement instead of
a synthetic one.

**Measured, both runs:** honest baseline median ≈180ms / p95 ≈224.7–224.9ms
(matching `ref-06p2`'s independent measurement of the same physical round
trip almost exactly — a good cross-check that both rungs are measuring the
same thing). 5–20ms of injected delay stayed indistinguishable from honest
(median 180.1ms at 20ms injected, vs. 179.9ms honest) — §5.5's "sub-10ms
local relays are achievable and indistinguishable" claim, checked rather
than assumed. The first delay whose *fastest* trial still exceeded the
bound was 100ms. A bound's false-rejection rate was checked against a
*second*, independent honest sample (224.9ms) rather than the sample the
bound was set from (224.7ms) — checking a bound against its own source
sample would trivially read "about 5%, as designed" and prove nothing; the
two independent samples landing within 0.2ms of each other is the actual
finding, and it says the p95 line is stable, not noise.

## The bug: stale `Device` object across reconnect retries

While making the real BLE leg reliable (the same class of flakiness
`ref-06p2` hit), a retry loop that reused the same `node-ble` `Device`
object across attempts started failing with `UnknownObject` on later
retries after the first attempt's `connect()` timed out. Two things
compound: a timed-out `connect()` promise doesn't cancel BlueZ's underlying
D-Bus call, and Android rotates the phone's random BLE address between
advertising sessions — so the D-Bus object path a stale `Device` handle
points at can simply stop existing by the next attempt.

Fixed by re-scanning from scratch on every retry (`connectFresh()` in
`device-leg.mjs`) rather than retrying against a cached object. Folded into
§10.2 item 2's acceptance text so the production `BleLocalityProvider`'s own
reconnect logic doesn't rediscover this the same way.

## `ref-06p5`: App Attest and Play Integrity are not symmetric, and the plan has been treating them as if they were

Locality-plan.md §7.1 carries `localityHardwareAttestation` as one field
with three states (`verified` / `present-unverified` / `absent`) regardless
of platform. Building `ref-06p5` — genuinely, against a real Apple-signed
attestation object, verified offline against Apple's real public root —
surfaced that the two platforms aren't interchangeable underneath that
shared field: App Attest's chain is checkable forever with nothing but the
object and Apple's public root; a Play Integrity token is **encrypted**,
and decoding one is *always* a live call to Google's backend. There is no
offline path for Play Integrity, now or later, with or without test data —
it needs a registered Play Console app, a Google Cloud service account, and
a network call, permanently. Recorded as **Q7** in §11 rather than resolved
here: is that online dependency acceptable for Android's half of locality,
or does Android's existing offline-verifiable Key Attestation (already used
for VRC hardware evidence per `docs/HARDWARE_ATTESTATION_FLOW.md`) belong
here instead? `ref-06p5` ships Play Integrity as shape-only pending that
call, with `live-play-integrity-optional.mjs` parked and ready to run the
real thing once Play Console/Google Cloud access exists — which is also
what was actually asked for when this rung was scoped: build the real App
Attest path now, and set up the Play Integrity live check as separate,
explicit future work rather than fake it or skip it silently.

## Also recorded: a summarizing web fetch is not safe for pinning cryptographic material

While pinning Apple's App Attest root CA (for `ref-06p5`'s act 0 — proving
the root this rung trusts is the one Apple actually publishes, not
node-app-attest's word for it), an initial fetch through a
summarization-mediated tool silently altered a handful of base64 characters
mid-certificate — invisible unless the fingerprint is checked, which is
exactly what makes it dangerous rather than merely wrong. A direct `curl`
fetch, with the SHA-256 fingerprint checked against the value both fetches
were supposed to agree on, caught it. **Any future pin of cryptographic
material — a root cert, a public key, a test vector — should be fetched raw
(curl/direct HTTP) and fingerprint-checked, never taken from a
summarizing/AI-mediated fetch tool's transcription.** This is a corpus-wide
lesson, not specific to App Attest.

## Item 9, scoped: what the Android native work actually requires

Asked to scope item 9's Android half next. Read
`react-native-attestation/android/src/main/java/com/attestation/AttestationModule.kt`
(the only existing native-module pattern in this repo to mirror), the app's
`AndroidManifest.xml`, `app/android/build.gradle`, and `ref-06p2`'s README
(which documents exactly what a phone needs to do in the peripheral role,
since that rung stood a phone in via nRF Connect rather than building this).
Findings, in order of how much they change the design:

- **The hardware-attestation key cannot be signed with as currently
  configured, inside a live GATT round trip — this is a real conflict, not
  a detail.** `AttestationModule.kt:223-233` creates the key with
  `setUserAuthenticationRequired(true)` and, on API 30+,
  `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`
  — Android's per-operation auth model: every `Signature.sign()` against this
  key needs a fresh `BiometricPrompt` bound via `CryptoObject`, not a
  time-windowed unlock. §5.5's RTT bound (witness-server's
  `PROVISIONAL_RTT_BOUND_MS = 400`) cannot include a human looking at a
  fingerprint prompt mid-round-trip. The plan's own item 9 text — "sign with
  the existing hardware-attestation key" — reads as if this is a
  straightforward reuse of `signWithHardwareBiometricAuth`
  (`vrc-hardware-signing.ts`'s existing call site); it is not, and an
  implementer who tried that first would discover the conflict only after
  building the GATT server, not before.
  - The resolution follows directly from how Android's own `CryptoObject`
    API is shaped: authorization and use are already two separate steps in
    the platform API, just usually collapsed into one call in this codebase's
    existing usage. Present the prompt once, early (when the sensor
    directive arrives, before advertising even starts), keep the resulting
    authorized `Signature` object alive in native memory, and perform the
    real `sign()` call later, synchronously, inside the write callback. This
    is not a workaround bolted onto the platform's model — it is the
    intended use of per-operation `CryptoObject` auth, just not the shape
    `AttestationModule.kt` happens to use today (create-key/sign as two
    calls, each atomic prompt-then-immediately-use).
  - Recorded this in the plan itself (§10.3 item 9), not only here, because
    it is a standing design constraint an implementer needs before starting,
    not a story about how this session found it.
- **The RN bridge itself is a timing risk, not just the biometric prompt.**
  `ref-06p2` measured ~180 ms median / 224 ms p95 for a real connect +
  discover-services + write + read with *no* JS involved at all. Bouncing
  each GATT server callback (write received, read requested) across the RN
  bridge into JS and back adds indeterminate JS-thread scheduling delay on
  top of a budget that's already most of the way to witness-server's
  provisional 400 ms bound. The peripheral's advertise/GATT-server/sign/serve
  loop should be one native state machine, called from JS once and resolving
  once — matching `DeviceLocalityProvider.respondToSensor()`'s contract
  exactly, so nothing about the `witnessCeremony.ts` wiring done earlier
  today needs to change when this lands.
- **This wants its own package, not an addition to
  `@bifold/react-native-attestation`.** That package's own README/structure
  is entirely about attestation and hardware-key signing; BLE
  advertising/GATT-server APIs are a different Android surface with their
  own manifest permissions and lifecycle concerns. The monorepo already
  keeps concerns this separate (`witness-server`, `react-native-attestation`,
  `oca`, `verifier`, `vrc-contexts`, `vrc-reference`, `vrc-shared`,
  `remote-logs` are each their own package) — a new
  `@bifold/react-native-locality-peripheral`-shaped package follows that
  convention rather than breaking it. It does need read access to the same
  KeyStore alias `AttestationModule.kt` creates
  (`HARDWARE_SIGNING_KEY_ALIAS`), which currently lives as a private constant
  in that one file and will need to move somewhere shared.
- **No BLE code exists in the app at all today, in either direction.** Grepped
  for it before assuming otherwise: the two `BLUETOOTH*` manifest entries and
  the `NSBluetooth*UsageDescription` iOS strings are upstream bifold/BC Wallet
  boilerplate for call-audio routing, unrelated to VRC — confirmed by reading
  what they're attached to, not just by their presence. There is no
  `PermissionsAndroid` call for Bluetooth anywhere in `app/` or
  `bifold/packages/core`, because the legacy `LocalityService`'s scanning
  role has always lived in `witness-server` (a separate Node process), never
  in the wallet. So item 9 is greenfield on the permission-request UX too,
  not a rewire of an existing flow — worth knowing going in, since it's easy
  to assume "the app already asks for Bluetooth somewhere" and go looking for
  a flow to extend that doesn't exist.
- **Validation doesn't need a new idea — `ref-06p2` already named it.** Its
  own README states the nRF-Connect-as-peripheral stand-in "stays that way
  until the Keyring app's own peripheral role ships … and can be pointed at
  this same sensor script." So the acceptance path for this item, once
  built, is: point witness-server's real `BleLocalityProvider` (already
  built, §10.2 item 2 — not a reference-rung stand-in) at the native
  peripheral on the attached physical device (`R5CN70Q6PDP`), before
  reaching for the full `e2e:vrc:devices` suite (item 12).

**Not done in this pass, deliberately:** no Kotlin was written. This was a
scoping pass only, at the user's request, specifically because the biometric-
timing conflict above is exactly the kind of thing that should be surfaced
and, ideally, sanity-checked before code exists — not discovered by building
past it.

## Item 9, continued again: the Android native module, written and compiled for real

User picked "item 9 native Kotlin" explicitly when asked where to focus
next. Built the whole thing — manifest, Gradle, Kotlin, workspace wiring —
and, critically, actually compiled it against real codegen rather than
stopping at "this looks right." Findings, roughly in the order they
mattered:

- **The exact wire protocol had to be traced from witness-server's real
  code, not assumed from the reference ladder.** `ref-06p2`/`ref-06p4`'s
  device-leg/sensor-leg scripts do a bare nonce echo — no real transcript,
  no JSON. Read `BleLocalityProvider.runTranscriptExchange()` directly
  instead of assuming the echo test generalized, and it doesn't in two
  ways that would have produced a native module that compiled fine and
  then failed every real round trip: (1) the sensor's nonce travels as
  UTF-8 *text* of a hex string (`randomBytes(32).toString('hex')`,
  written as `Buffer.from(sensorNonce, 'utf8')`), not raw binary — so the
  native write callback decodes the write as a UTF-8 string directly, no
  hex-decoding step; (2) the GATT *read* response is the full
  `JSON.stringify`'d `LocalityTranscript` (`method` included), because
  witness-server does `JSON.parse(raw.toString('utf8')) as LocalityTranscript`
  and expects every field — not just the signature bytes, which is what a
  read of the ladder's echo test alone would suggest. Both corrections
  landed in `NativeLocalityPeripheral.ts`'s own doc comments before any
  Kotlin was written, and `method` had to be added as a native input
  parameter it didn't have in the first sketch pass, purely so the wire
  transcript can carry it.
- **The public-key encoding finding was the most consequential thing this
  pass surfaced, and it came from tracing `transcriptKeyMatchesVrcSigner`'s
  actual comparison, not from the locality design docs.** Both
  `locality.ts` (witness-server) and the original `deviceLocality.ts`
  comment called `devicePublicKey` "Base64, raw EC-P256 point." Before
  writing `Base64.encodeToString(publicKey.encoded, ...)` in Kotlin, checked
  what `AttestationModule.kt`'s own `getHardwarePublicKey()` — the function
  that fills the *existing* VRC evidence's public key field — actually
  returns: `publicKey.encoded`, which for an Android `ECPublicKey` is
  SPKI-wrapped DER, not a raw 65-byte point. `BiometricSignatureVerifier.ts`
  confirms this is deliberate and known: *"Public key encoding: iOS uses
  raw 65-byte EC point, Android uses SPKI-wrapped. Native
  verifyHardwareEvidence normalizes both formats."* Since
  `transcriptKeyMatchesVrcSigner` is a bare `===`, not a normalizing
  comparison, the locality transcript's `devicePublicKey` on Android MUST
  match the SPKI encoding the existing evidence already uses, or the
  match check would spuriously fail on every single Android device despite
  being the literal same key. So `LocalityPeripheralModule.kt` correctly
  uses `publicKey.encoded` as-is — the "raw EC-P256 point" comments were
  simply wrong for Android and are now corrected in both `deviceLocality.ts`
  and the native Spec to say "whatever this platform's `getHardwarePublicKey()`
  already returns," not a specific byte layout. Did not touch
  witness-server's own `locality.ts` comment in this pass (it's already
  committed); worth a small follow-up correction there too, though the
  naive `===` itself is not a bug — it only needs both sides to agree on
  ONE platform's own convention, which they now do.
- **The biometric-authorization split compiled exactly as scoped, as one
  bridge method, not two.** The original scoping note proposed
  `beginLocalityTranscriptSignature()`/`signLocalityTranscript()` as two
  JS-facing entry points. Building it, there was no reason to split them at
  the JS boundary — the ordering guarantee ("authorize before advertising,
  sign later inside the write callback") is just as easily a two-step
  sequence *inside* one Kotlin method (`respondToSensor`) as it is two
  separate bridge calls, and one call is simpler for the JS side
  (`AndroidBleDeviceLocalityProvider` stays a single pass-through, matching
  `DeviceLocalityProvider.respondToSensor()` 1:1). Recorded this correction
  in the plan.
- **It actually compiles, against real TurboModule codegen, not a
  hand-simulated check.** `cd app/android && ./gradlew
  ':bifold_react-native-locality-peripheral:compileDebugKotlin'` →
  `BUILD SUCCESSFUL`, only pre-existing-pattern deprecation warnings
  (`currentActivity`, `TurboReactPackage` — the same ones
  `AttestationModule.kt`/`AttestationPackage.kt` already produce). Read the
  actual generated `NativeLocalityPeripheralSpec.java` to confirm codegen
  parsed the TS `Spec` (including the object-typed `respondToSensor` param)
  into the exact `ReadableMap`/`Promise` signature the Kotlin implements.
  Then confirmed integration, not just isolated compilation: `npx
  react-native config` lists the module with the right `sourceDir`/
  `packageImportPath`, and running `:app:generateAutolinkingPackageList`
  produced a `PackageList.java` that actually instantiates
  `new LocalityPeripheralPackage()`. Getting a new RN native module to
  compile *and* autolink correctly on the first real attempt is not
  something to take for granted — this only happened because the Spec/
  wire-protocol work in the prior pass was accurate enough that the Kotlin
  writing itself had few surprises.
- **Wiring the workspace dependency needed one more link than expected.**
  Adding `@bifold/react-native-locality-peripheral` to `core`'s
  `package.json` (`workspace:*`) and the root's `portal:` resolutions
  wasn't enough for autolinking to find it — `npx react-native config`
  came back empty for it until it was *also* added as a **direct**
  dependency of `app/package.json` itself, matching
  `@bifold/react-native-attestation`'s own placement there. Autolinking
  scans the app's own direct dependency tree; a transitive dependency via
  `core`'s devDependencies doesn't reach it. Two `yarn install` runs
  needed: one in `bifold/` (to symlink the new package into `core`'s own
  `node_modules`), one at the repo root (to resolve the app-level `portal:`
  entry into `app/node_modules`).
- **What's still explicitly not verified, and shouldn't be assumed from a
  green compile:** whether the authorized `Signature`/`CryptoObject`
  genuinely survives being held in native memory across an entire
  `windowSeconds` advertising window (Android's per-operation auth model
  has no documented hard expiry, but "no documented expiry" is not the same
  claim as "verified to work for 30 seconds on a real device"), and a live
  round trip against witness-server's actual `BleLocalityProvider`. Neither
  requires more code — both require running the thing on the attached
  physical device (`R5CN70Q6PDP`), which is a deliberately separate next
  step, not folded into this pass. `ceremony.ts`'s real call site stays on
  `NullDeviceLocalityProvider` until they are.

## Item 9, verified live: three real bugs, in the order they were actually found

User asked directly to run the live verification the previous pass left as
the explicit next step. What follows is the honest trail — two dead ends
included, not smoothed over — because the dead ends are exactly what
distinguishes "eventually worked" from "worked because the fix was
understood," and a future reader debugging something similar in this same
BLE stack should see both.

**The harness.** A temporary debug button on `ToggleLocalityConfirmation`
(behind `__DEV__`, calling `AndroidBleDeviceLocalityProvider.respondToSensor()`
directly with fixed test values) plus a temporary script
(`witness-server/src/_liveVerificationSensor.ts`, reusing the real
`BleLocalityProvider`/`locality.ts` — no reference-ladder stand-in) as the
sensor side. Both deleted before committing; neither is production code,
and `ToggleLocalityConfirmation.tsx` diffs clean against its prior commit
after removal. `adb`/`uiautomator dump` stood in for a human's eyes on the
device (screenshots came back empty once the app reached a screen with
`FLAG_SECURE` — presumably the wallet's own screenshot-blocking on
sensitive screens — so the whole session after that point relied on the
accessibility-tree dump, not pixels).

**First real result, first surprise.** The very first live attempt hit
"no hardware signing key exists yet" — obvious once seen (a fresh wallet
that's never done a VRC exchange has no key), fixed by having the harness
call `ensureHardwareSigningKey(agent)` before `respondToSensor`. Not a bug
in the shipped design; a gap in the harness only, since the real ceremony
already has a key by the time locality would run.

**Bug 1 — `verifyTranscript()` rejects every real signature.** First
completed round trip: the app produced a full, real transcript (real
nonce, real SPKI key, real DER signature) — but `verifyTranscript()` said
`transcriptSignatureInvalid`. Verified independently with Node's own
`crypto.verify()` that the signature *was* mathematically valid, which
narrowed it to "this file's verify call is wrong," not "the device signed
wrong." Two stacked mismatches, found by testing every `{format, prehash,
lowS}` combination against the real captured bytes rather than guessing
one at a time:
- `devicePublicKey` is SPKI DER (91 bytes) on Android; `@noble/curves`'s
  `verify()` needs a raw point. Passing SPKI bytes through unchanged
  doesn't throw — it just silently fails validation, which is worth
  remembering next time a "valid-looking input, wrong answer" bug shows up
  in this codebase generally.
- The signature itself is DER and high-S; noble defaults to rejecting
  non-low-S signatures in compact form. `p256.verify(sig, msg, pub,
  {format:'der', prehash:true, lowS:false})` — the exact combination
  isn't discoverable from noble's types alone, it took a systematic sweep
  of the option space against the real bytes to find.
Fixed the verifier and, just as importantly, fixed *why the existing 19
unit tests never caught this*: they signed with `p256.sign()`'s own
convenient defaults (compact, low-S), which is exactly what a real device
never produces. Changed the test helper to sign DER/single-hash, matching
`java.security.Signature`'s real behavior — the tests were previously
agreeing with the (buggy) verifier while both disagreed with reality.

**Bug 2, believed fixed, wasn't (dead end #1).** Next symptom:
"Unterminated string in JSON at position 512" — read the exact same
symptom before and after a fix, which is the tell that the fix addressed
something real but not *the* thing. Diagnosed (correctly, as far as it
went) that `BluetoothGattCharacteristic.value` caps at 512 bytes
(`GATT_MAX_ATTR_LEN`) and switched to serving from the module's own
`ByteArray`. Compiled, reinstalled, reran — same "position 512" error,
unchanged. This fix was real (confirmed by the deprecation warning for
`char.value` disappearing from the compile log) but insufficient alone.

**Dead end #2 — chased MTU/pacing before finding the actual ceiling.**
Interpreted the persistent 512 truncation as a long-read chaining problem
next: added a pacing delay between reads (justified independently — a
real `le-connection-abort-by-local` did appear with no pacing at all,
so this wasn't wasted, just not sufficient) and raised the iteration cap
from 20 to 80 (also independently justified — 20 reads at the ATT default
MTU covers only 440 of ~630 bytes, a real latent bug in its own right).
Still "position 512" after both. At this point recognized the pattern —
the same number, regardless of what changed on either the pacing or
iteration-count axis — meant the bug wasn't in how patiently either side
read, and stopped guessing.

**The actual root cause, found via logcat, not more guessing.** Captured
`adb logcat` around one more live attempt. It showed `onMtuChanged() -
mtu=517` (a large, healthy negotiated MTU — ruling out "MTU never
negotiates" as the cause) and exactly two GATT read requests processed
before the server closed. BLE's GATT protocol caps a *single attribute
value* at 512 bytes (Bluetooth Core Spec, Vol 3, Part F, §3.2.9, "Long
Attribute Values") — independent of MTU, which governs per-packet size,
not per-attribute total size. The 630-byte transcript could never be
served as one characteristic's value, at any MTU, with any amount of
read-chunking patience. This is why dead end #2 felt so persuasive: the
symptom (a fixed 512-byte ceiling) looked exactly like a chunking/MTU bug
because it repeats regardless of chunking parameters — but the actual
mechanism is a protocol-level attribute-value limit, not a session-level
negotiation.

**The fix: two characteristics, not one.** Split the transcript's wire
representation across the existing characteristic (core fields) and a new
read-only one (`devicePublicKey`/`signature` only) — the two fields whose
size scales with the crypto primitives, and the only part likely to grow
if a curve or signature scheme ever changes. Comfortably under 512 bytes
each for any realistic field length, not just this test fixture's. Pulled
`runTranscriptExchange` out of the class as a standalone function
specifically so the merge logic — the one piece of this whole fix with no
prior test coverage — could get a real one, against a fake `BleDevice`.

**Result: full, live, end-to-end success on the next attempt.**
`RESULT: observed after 12555ms, rttMs=522` / `VERIFY: {"ok":true}` — a
freshly minted signature, not the frozen fixture used elsewhere. Ran it
once more (having already gotten a clean result, mostly to satisfy "did
that actually work or was it luck") — same result.

**What this pass leaves recorded, deliberately, that a green build alone
would not have shown:** the exact reasoning that ruled out MTU negotiation
and read-chunking patience as the cause, so nobody re-treads dead end #2 if
a superficially similar "stuck at some byte count" bug shows up again on a
different characteristic later — the diagnostic that actually works is
"capture logcat, look at `onMtuChanged` and how many read requests the
server actually processed," not "adjust chunking parameters and retry."

## Items 8 and 11: one sheet, not two — and why that isn't a shortcut

Continuing on `feat/locality-android-ble`. Both items were marked "no design
guidance available" — false by the time this ran: §8.4's UX table already
gives exact copy and sequencing for item 8's sheet, and re-reading it against
item 11's "what will be shared" requirement settled a question neither item's
own text had answered.

**The one-sheet decision.** §8.4's table names exactly one new prompt
surface at witness-connect, and its governing principle is explicit:
"Locality must not add a second question to the ceremony." Building item
11's disclosure sheet as a second, separate screen would itself be the
second question the plan rules out — both concerns are pre-ceremony, about
the same radio leg, at the same moment. `LocalityPreflightModal` covers
both: its offer body names what the assertion discloses (venue, a time
window, the witness) in the same sentence that primes the Bluetooth
permission. Recorded here because it's exactly the kind of design call that
looks obvious once made and isn't visible in the diff.

**Where the sheet mounts, and why.** `RelationshipProposalModal` was already
the precedent for "modal driven by a context, mounted once at
`RootStack.tsx`'s root, no per-screen wiring." Following it: a new
`localityPreflight`/`resolveLocalityPreflight` pair on
`WitnessConnectionProvider`'s context, set from `handleWitnessAnnouncement`
right after the discovery query fires, read by the new
`LocalityPreflightModal` mounted beside `RelationshipProposalModal`.
Considered and rejected: hooking into `WitnessConnections.tsx` (the
manage-witnesses settings screen) — that screen is for reviewing existing
connections after the fact, not the connect moment itself, and gating a
sheet there would miss the QR-scan-triggered connections §8.4 is actually
about.

**Required vs. offered, and why the sheet doesn't try to tell them apart
up front.** §8.2's own discovery mechanism can only distinguish `required`
(via `requiredExt`) from "not confirmed required" — a bare `witness/session`
listing means either `off` or `offered`, indistinguishable from the wallet's
side. Rather than treat this as a gap, the sheet always shows the generic
offer first (matching §8.4's literal sequencing: "the OS Bluetooth
permission request, primed by one app sheet first... If the event requires
it... and the user declines... say so now"), and only escalates to the
harder "this event requires in-person confirmation" copy if the user
declines AND `getWitnessLocalityRequirement` came back `true` in time.
`handleWitnessAnnouncement` polls that function for up to 5 seconds
(250ms interval) before scheduling the prompt, failing open to
`required: false` on timeout or a thrown error — the discovery round trip
is normally a fast in-memory DIDComm exchange, and failing open beats
blocking the sheet indefinitely on a slow or silent witness.

**No new gating flag.** The sheet's decision needed to reach wherever the
witnessed exchange decides whether to advertise. It already does:
`ceremony.ts`/`witnessCeremony.ts` read `isLocalityConfirmationPreferred()`
(§8.1's setting) to compute `localityOffered`. `resolveLocalityPreflight(false)`
dispatches the exact same `USE_LOCALITY_CONFIRMATION` action Settings →
Secure Exchanges uses — declining in the sheet just flips the one existing
setting rather than inventing a second, per-session one. A new
`hasSeenLocalityPreflight` preference (default `false` everywhere — no
split-default risk, unlike `useLocalityConfirmation`'s own keyring-bifold#38
history) makes the sheet one-shot per install regardless of how it's
answered.

**What's genuinely still a gap, stated rather than glossed over:**
pre-API-31 `ACCESS_FINE_LOCATION`. §9.1 names it as needed below API 31, but
`LocalityPeripheralModule`'s manifest doesn't declare it at all (item 9's own
finding) — requesting an undeclared permission via `react-native-permissions`
would silently no-op, so the sheet only requests `BLUETOOTH_ADVERTISE` and
`BLUETOOTH_SCAN` (API 31+, what the manifest actually has). Closing this is a
manifest change, not a sheet change, and whether it's even still required for
advertise-only (vs. scan) on pre-31 Android needs its own check against the
platform docs before adding it blind. Also out of scope, deliberately, per
§8.4's last table row: translating a `malformedRequest` refusal that arrives
mid-ceremony (the "gated event, refused entry" row) into the "event rule, not
a technical fault" language that row describes — that's a different UI
surface (wherever task errors already render) than this pre-flight sheet.

**Verification:** `yarn tsc --noEmit` clean; `eslint` clean on every changed
and new file; `packages/core`'s full suite — 175 suites, 1591 tests — passes
with no regressions (17 new: 8 in `witnessConnectionProvider.test.tsx`
covering the scheduling logic, 9 in a new `LocalityPreflightModal.test.tsx`
covering both sheet states and every button). Not run live on a device — no
physical Android phone was available this pass; the sheet's actual OS
permission-dialog behavior and the discovery-timing race are unverified
against real hardware, same caveat as everything in §10.2 items 1/3/4/5.

## Catching up with `feat/trust-tasks-integration` before going further — and a real bug found doing it

Asked directly: had this branch actually merged or rebased in the latest
`feat/trust-tasks-integration` from both repos? It had not — `feat/locality-android-ble`
(bifold) was still branched from that day's earlier tip, and `bam/locality`
(main repo) had diverged from the same branch's own 32-commit-ahead state on
the main-repo side. Asked to stash and catch up before continuing.

**Why rebase turned into merge.** Bifold's `feat/trust-tasks-integration` had
moved 3 commits ahead, one of which (`e3a756e7`) deletes
`witness-server/src/trustTasks/framework.ts` entirely — the exact local
consume/respond helpers `WitnessTaskSessions.ts` was built on, replaced with
the real `@openvtc/trust-tasks` `consumeInbound` pipeline (a new
`@bifold/trust-tasks` package now holds document proofs, the DIDComm
carriage, and the payload validator, shared by wallet and witness). A linear
rebase would have replayed all 8 of this branch's commits against that
missing foundation, hitting the same deep conflict at the very first one and
needing it re-resolved at every commit after. Asked which approach to take;
chose merge — one conflict resolution instead of nine, at the cost of a
merge commit instead of staying linear.

**Re-porting the locality logic onto `consumeInbound`.** The generic runtime
enforces SPEC.md §7.2 items 4–8 but has no notion of any one consumer's
LOCAL `ext`-namespace policy (§7.2's own words: a consumer "MAY require...
as a matter of local policy" — necessarily something the generic package
can't know). `handleSession`'s old `requiredExtNamespaces` check (via the
deleted `framework.ts`) had no upstream equivalent to inherit; re-added it
explicitly inside the handler. Same for `handleDiscovery` — it had nothing
upstream to conflict with or replace, since discovery-in-the-witness was
entirely this plan's own addition; ported it onto `consumeInbound` the same
way as `handleSession`/`handleSubmit`, adding a discovery spec loader to
`runtime.ts`.

**The real bug, found by re-reading the merged logic rather than assuming it
still worked:** `handleSubmit` never actually enforced `required`'s own
"refuse to issue without a confirmed observation" promise (§8.2). It only
checked, via `handleSession`'s ext-namespace gate, that the session request
had *populated* the namespace — `{offered: false}` satisfies that — never
that the radio phase that followed actually *succeeded*. A `required`
witness would issue a VWC carrying `localityConfirmed: false` on
`declinedByHolder`/`windowLost` exactly as if it were `offered`. Fixed by
adding an explicit check in `handleSubmit`, right before VWC assembly: if
`policy === 'required'` and the resolved observation isn't confirmed, refuse
with a new extended code (`localityRequired`) instead of proceeding. This is
the kind of gap that a "policy configuration" item marked ✅ can hide — the
enum and the discovery wiring were real, but the ONE enforcement path that
makes `required` mean anything at issuance time was missing, and nothing
caught it until this merge forced a re-read of the whole handler.

**Two mistakes worth recording, not just the fix.** First: staged the merge
resolution (`git add -A`) before fixing a second typecheck error
(`locality.ts`'s `./documentProof` import, also moved to `@bifold/trust-tasks`
by the same upstream commit) — the fix landed in the working tree but not in
the commit that got pushed, caught only by re-checking `git status` after
the push and noticing the file was still dirty. Second: `packages/core`'s
`types` field points at `lib/typescript/src/index.d.ts`, a build artifact
this checkout's `lib/` hadn't regenerated recently — `yarn typecheck` at the
main repo's root failed on a real, live export (`setupTrustTasksInbound`)
that TypeScript couldn't see because it was reading a stale prebuilt
declaration file, not the source. `cd bifold/packages/core && yarn build`
fixed it. Both are the same class of mistake — trusting an artifact (a git
index, a `lib/` build) instead of checking the thing itself — and the
second one is exactly `vrc-contexts`' own "publishes from `build/`, not
`src/`" gotcha (§10.2 item 6), just for `core` instead of `vrc-contexts`.

**Result:** both branches merged, pushed, and re-verified clean —
witness-server (645 tests), `packages/core` (1591 tests), the main repo's
`app/` suite (70 tests), `yarn typecheck`/`yarn lint` at the root — all

## The BLE-locality e2e flow (item 12), written against the now-merged e2e infrastructure

The merge itself turned out to matter here too: it brought in a new
upstream simulator/emulator witnessed-exchange e2e
(`run-vrc-exchange-witnessed.js`) with logcat-marker assertion helpers
(`assertTrustTaskExchangeMarkers`, `assertWitnessCeremonyMarkers`,
`assertWitnessShareMarkers`) that the existing attended device flow
(`runWitnessedExchange` in `witnessedExchangeFlow.js`) now also uses in
place of the older credential-offer-chat assertions. Building the locality
e2e on top of this — rather than the pre-merge version — meant less new
code and a flow that stays consistent with however the ceremony markers
evolve upstream.

**What was built:** a new logcat marker in `witnessCeremony.ts` itself
(`[TrustTasks:Witness] locality confirmed for session …` /
`locality not confirmed for session … (reason)`), distinct from the
existing "radio phase produced a transcript" line — that one only reports
what the DEVICE produced, not what the WITNESS ultimately confirmed, which
is the thing item 12 actually needs to assert. A new
`assertLocalityConfirmedMarker` in `e2e/lib/flows.js` reads it, failing
loudly on a "not confirmed" line rather than merely timing out on a missing
one. `runWitnessedExchange` gained an `assertLocality` option (default
off) that runs this assertion on both sessions after the witness-share
markers, plus a fail-fast check that `WITNESS_LOCALITY_REQUIRED` was
actually set to `"true"` before the witness started — asserting locality
against a witness that was never asked to enforce it would otherwise either
hang on the timeout or, worse, look like it passed for the wrong reason. A
new top-level script,
`run-vrc-exchange-witnessed-locality-android-only-devices.js`
(`yarn e2e:vrc:witnessed:locality:android-only`), mirrors the existing
android-only witnessed script exactly, setting `WITNESS_LOCALITY_REQUIRED=true`
itself and passing `assertLocality: true`.

**Why Android-only, and why this variant alone needs a Linux host.** Item
9 has no iOS peripheral, which already rules out the iPhone pairing other
witnessed variants use. Less obviously: the witness's own BLE SENSOR
(`witness-server`'s `BleLocalityProvider`, over BlueZ's D-Bus interface via
`node-ble`) only runs on Linux (`docs/plans/locality-plan/2026-08-20-bam.md`)
— so unlike every other witnessed-exchange variant, which needs macOS only
