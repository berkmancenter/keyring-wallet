# 2026-09-12 — Alberto

Scoping the iOS BLE peripheral (§10.3 item 9) turned up a blocker that is not
an implementation detail: **on iOS the device cannot sign the locality binding
at all**, because the platform's hardware key is an App Attest key and Apple
does not expose raw signing over it. This document records what was found, the
three ways out, and a correction to my own first framing of the trade-off.

No code was written. `ref-13-macos-ble-central` — the rung that started this —
stands on its own and is unaffected.

## What the Android peripheral does, and why iOS cannot mirror it

`LocalityPeripheralModule.kt` loads `vrc_hardware_signing_key` from the Android
Keystore and signs the §5.3 binding directly:

```kotlin
val signature = Signature.getInstance("SHA256withECDSA")
signature.initSign(privateKey)
…
authorizedSignature.update(bindingBytes)
val signatureBytes = authorizedSignature.sign()
```

The witness verifies exactly that, in `locality.ts`:

```ts
p256.verify(signatureBytes, message, publicKeyBytes, { format: 'der', prehash: true, lowS: false })
```

On iOS there is no equivalent key. `Attestation.mm`'s `createSecureEnclaveKey`
creates an **App Attest** key — its own log line says "App Attest single key" —
and the `HardwareSigningKeyTag` keychain query that looks like a Secure Enclave
key is only used to *delete* a legacy one. Signing goes through
`DCAppAttestService generateAssertion`, which returns a **CBOR assertion**
signing Apple's own `SHA256(authenticatorData ‖ clientDataHash)` construction,
never caller-supplied bytes.

So `p256.verify(sig, bindingBytes, …)` cannot succeed against an iOS device.
This is not an encoding mismatch that an adapter could bridge — it is a
different signing primitive.

**What already works on iOS**: the public key. `getHardwarePublicKey` returns
the raw 65-byte point extracted from the App Attest leaf certificate, and
`rawPointFromDevicePublicKey` already accepts both shapes ("a raw 65-byte point
on iOS, SPKI-wrapped DER on Android"). The verification side was written with
iOS in mind; only the signing side has no path.

## The three options

**1 — a separate Secure Enclave P-256 key, used only for locality.**
`SecKeyCreateRandomKey` with `kSecAttrTokenIDSecureEnclave`, signed via
`SecKeyCreateSignature` with `.ecdsaSignatureMessageX962SHA256`, which produces
the DER the witness already expects. Works with zero witness changes. The cost
is that it is **not** the key that signed the VRC's attestation evidence, so
§7.3 step 6's tier-3 check fails by construction on iOS:

```ts
transcript.devicePublicKey === vrcEvidencePublicKeyBase64
```

**2 — teach the witness to verify App Attest assertions.** Keeps one key on
both platforms, at the cost of a forked verification path. Scoped below.

**3 — option 1, plus honesty.** Ship the separate key, and make the evidence
state which tier iOS actually reached rather than reporting a bare "confirmed".

## What option 2 actually costs

Researched rather than estimated, and it is two jobs, not one.

**Job A — verify the assertion.** Add a CBOR decoder (there is none anywhere in
this monorepo today — a new dependency in a security-critical path), parse
`authenticatorData` and `signature`, recompute
`SHA256(authenticatorData ‖ SHA256(clientData))`, verify against the cached
public key. Apple also increments a **counter** per assertion which must
strictly increase, so the witness would need to remember per-key state across
ceremonies — persistence it does not currently have.

**Job B — the part that makes Job A worth doing.** For tier 3 to mean what it
sounds like, the witness must know the cached public key really is a Secure
Enclave key. It does not check that today; it believes what the device sent.
Establishing it means verifying Apple's attestation certificate chain — root,
nonce extension, app-ID hash — which would be the first Apple-specific
verification anywhere in this codebase.

Job A is days. Job A + B is materially more, plus a permanently forked
verification path.

## Correction: tier 3 is weaker than I first said

My first framing of this trade-off told Alberto that option 1 "silently weakens
a security property". That overstated the gap, and the overstatement was mine.

`transcriptKeyMatchesVrcSigner` is a base64 string comparison. **The witness
never verifies Android's attestation chain either** — nothing server-side
verifies hardware attestation on either platform. The type that carries this
says so out loud:

```ts
type HardwareAttestationState = 'verified' | 'present-unverified' | 'absent'
```

So tier 3 today means *the same unverified key appeared in both places*. That
is still worth having — it defeats a second device in the room answering on
behalf of the first — but it is a consistency check, not a hardware guarantee,
and option 1 gives up less than I implied.

## Recommendation

Option 1 or 3 now; option 2 only if iOS locality becomes important enough to
justify a forked verification path. Locality is not on the Prague path, and the
iOS peripheral is not a prerequisite for anything currently scheduled.

The larger question this surfaced, and the one worth answering first: **should
hardware attestation be verified server-side at all?** It currently is not, on
either platform. That is bigger than locality, affects Android equally, and is
what `present-unverified` has been quietly flagging since it was written. Job B
is a piece of that answer, not a locality-specific cost.

## Addendum, same day: option 2 was built

The recommendation above — option 1 or 3 now, option 2 only if iOS locality
became important enough — was overtaken within the day. Option 2 shipped on
`feat/locality-ios`, along with the iOS peripheral itself, which the
recommendation had treated as separately deferred.

What changed the arithmetic was answering the question the recommendation
raised. **Hardware attestation is verified today — on the device.**
`ContactDetails.tsx` and `ListContacts.tsx` call `verifyVrcHardwareEvidence`,
which reaches `verifyHardwareEvidence` in
`@bifold/react-native-attestation` and, on iOS, `Attestation.mm` — which has
had CBOR parsing for App Attest assertions since it was written. That file's
own header states the asymmetry plainly: *"iOS sends CBOR App Attest
assertions, Android sends DER ECDSA. Native `verifyHardwareEvidence`
normalizes both formats."*

So the puzzle "why does VRC signing work on iOS but locality cannot" has a
flat answer, and it is not about the signature, the key, or the byte length.
It is about **where the verification runs**. The wallet verifies on a phone
that has Apple's frameworks. The witness verifies in a Node service that has
none. Locality is simply the only place a hardware signature is checked
somewhere other than the device.

That reframes option 2 from "a forked verification path" to "the second
implementation of an unwrapping that already exists" — the same
cross-runtime duplication the binding algebra already carries four times over.
It came to about 300 lines of TypeScript and a strict CBOR subset, small
enough that deferring it cost more in explanation than in code.

Two things landed alongside it that were not on any option list:

- **Three witness-server test suites, 233 tests, had been silently
  unrunnable.** `@bifold/trust-tasks` re-exports an ESM-only package missing
  from `transformIgnorePatterns`, so anything importing it died at import.
  `locality.test.ts` was one of the three — the entire transcript-verification
  contract, including the on-device Android capture that exists precisely to
  catch silent verification regressions, had not run since that dependency
  arrived.
- **The cross-language binding parity assertion now exists.** Both native
  files claimed their hand-written canonical JSON was "checked against the
  frozen fixture, not just eyeballed". Nothing was checking it.

### What is still open

Option 2 is built and tested; it is not proven. Every fixture is constructed
with the algorithm under test, so they demonstrate self-consistency and
rejection of specific tampering, not agreement with Apple. There is a
`describe.skip` waiting for a real-device capture, exactly as the Android path
got one on 2026-08-21 — and that capture is what found two real bugs the
synthetic fixtures had not.

The iOS peripheral has the same status, plus one measurement it cannot make
for itself: iOS has no `CryptoObject` equivalent, so `generateAssertion` runs
*inside* the RTT-bound window rather than before it. The Swift logs
`signingElapsedMs` on every run. If that number does not fit under 400ms, the
provisional bound moves or the iOS design does, and no amount of reasoning
here settles which.

The larger question the recommendation raised stands unchanged: **hardware
attestation is still not verified server-side, on either platform.** Locality
now verifies the transcript signature on both, but `hardwareAttestation:
'present-unverified'` still means what it always meant, and that is not a
locality problem.
