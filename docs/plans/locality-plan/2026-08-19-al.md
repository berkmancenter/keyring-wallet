## Finding 2 — the §8 policy mechanism is already implementable: discovery shipped, `requiredExt` included

§8.2's publication mechanism ("consumers applying such a policy SHOULD
publish the requirement via discovery") is quoted from the framework as a
future facility. It is not future here: `trust-task-discovery` answering
shipped in the wallet on 2026-08-18 (bifold `97ae5a1c`) — the proposer
queries before proposing and any v4 wallet answers with its `supportedTypes`,
slug-glob filtered, e2e-gated since run 14.

The part the plan does not yet name: the discovery response schema's
`supportedTypes` entries admit an **expanded form carrying `requiredExt`** —
"reverse-DNS `ext` namespaces this responder requires on inbound documents of
this Type URI as a matter of local policy … a producer that does not populate
every listed namespace will receive a `malformed_request` rejection"
(`trust-task-discovery/0.1`, pinned schema). That is §8.2's `required` tier,
verbatim, in an already-running exchange:

- **`off`** — the witness's discovery response lists `witness/session` bare.
- **`offered`** — bare listing; the witness annotates when the wallet offers.
- **`required`** — the expanded entry:
  `{ "type": ".../witness/session/0.1", "requiredExt": ["edu.harvard.seas.atl.keyring"] }`,
  and the framework's own rejection rule enforces it.

The wallet side needs one addition: today it acts only on the propose row of
a discovery response; teaching it to read `requiredExt` on the witness rows
gives the §8.1 setting its counterpart signal (the wallet can warn *before*
opening a session at a gating event, instead of failing inside one).

**Plan edits implied:** §8.2 names the shipped mechanism and the expanded
`supportedTypes` form; §10.2 item 4's "published via discovery" becomes
concrete ("the witness's discovery responder lists the expanded entry");
§10.3 gains the wallet-side `requiredExt` read as a numbered item.

## Finding 3 — three ceremony-window edges, from a day of live runs

The plan's radio window sits inside the most failure-prone stretch we have
measured. On 2026-08-18 the exchange test machine ran twenty-one ceremonies;
the failures that were not code defects were all app-lifecycle and
channel-latency events landing mid-ceremony. Three design consequences, each
currently unstated:

1. **The mid-window app-death path needs a named evidence state.** The plan
   says foreground-only (§10.3 item 8) but not what the evidence records when
   the app backgrounds, is watchdog-killed, or locks *during* the advertising
   window — and that will be the common case at a real event, because people
   pocket their phones. We hit watchdog restarts landing on the unlock screen
   repeatedly in a single evening, on idle test hardware. §7.1's three-state
   design (confirmed / refused-with-reason / absent) already has the right
   shape; it needs a reason vocabulary entry (`window-lost` or similar) so a
   verifier can distinguish "declined", "never attempted", and "attempted and
   interrupted" — the third being the one that says *try again* rather than
   *suspicious*.

2. **The Bluetooth permission prompt must not fire mid-ceremony.** With
   §8.1's setting defaulting on, a fresh install's first witnessed exchange
   stacks three system interruptions into one social moment: the biometric
   prompt, the new relationship-consent sheet (the v4 UX as of 2026-08-18 —
   consent is accepting the proposal), and then the OS Bluetooth dialog,
   while the user stands in front of a stranger. Request the permission at
   witness-connect time — the natural "you are at an event" moment, and the
   same moment the wallet learns via Finding 2's `requiredExt` whether the
   event even gates. The plan's own neighbor bug
   ([keyring-bifold#38](https://github.com/berkmancenter/keyring-bifold/issues/38))
   is the cautionary tale for the setting itself: define the default in one
   place.

3. **Anchor `windowSeconds` radio-side, or size it from measured channel
   latency.** The sensor directive reaches the wallet inside
   `witness/session#response`, which travels witness → the wallet's mediator
   → the wallet's pickup poll. That channel's latency is not hypothetical to
   us: pickup polls at 10 s, and the same evening's runs measured the
   inbound-processing hazard the hard way (a ceremony awaited inside an
   inbound handler starved its own transport for exactly the 60 s timeout —
   bifold `5d45e76d`). If the window opens when the witness mints the
   directive, wallets routinely lose a third of it before hearing. Either
   the sensor starts the clock at first advert observed (the witness controls
   both ends of that measurement), or `windowSeconds` is sized against the
   published task-channel latency distribution — which the e2e logs from
   2026-08-18 can supply today.

**Plan edits implied:** §7.1 reason vocabulary gains the interrupted state;
§8.1 moves the permission request to witness-connect and names the
single-source default; §5.5/§6's directive gains the window-anchor decision
(radio-side recommended), with the task-channel latency numbers cited.
