## Findings and amendments

All applied in the plan unless marked otherwise.

### M1 — Issue creation is the publication event

- **Need.** The plan treated Step 4 (go public) as the moment content becomes public. Issues in `keyring-wallet` and `keyring-bifold` are public on creation, in Steps 2 and 3, whatever the project's visibility. A leak in Step 3 would already be indexable, with edit history, before Step 4.
- **Options.** (a) Keep the plan and warn. (b) Create issues in a private repository first. (c) Put a human gate and a rehearsal before the first create.
- **Choice.** (c). §7 states that creation is publication. Steps 2 and 3 require the product owner's sign-off on a scan dry run of every body before the first create; the Step 3 end-to-end test runs in a throwaway public test repository; §9 Step 4 states what it gates: project visibility, pins and the announcement.
- **Why.** (b) is the rejected private-intake design: private issues cannot be transferred to a public repo. A rehearsal in a throwaway repo costs one deletion and exercises the real code path.

### M2 — Closure and Status semantics

- **Need.** `Closes #N` closes at merge, before a fix reaches testers. Built-in workflows then set Done on close and on merge. A Shipped view defined as "closed items" would include declined items. And bifold merges land before the wallet release that moves the submodule pointer.
- **Options.** (a) Leave built-ins on and correct Status afterwards. (b) Disable them and key everything on Status.
- **Choice.** (b), as D16: disable *Item closed* and *Pull request merged*; PRs use `Refs`; only release automation sets Shipped and closes; closes use `state_reason` completed / not planned / duplicate; views filter on Status; a bifold item ships with the wallet release whose submodule pointer includes its merge. §4.3, §4.4, §5, §8 and D5 now agree.
- **Why.** (a) briefly shows false Done states publicly, and a race with automation is hard to test.

### M3 — Declined items were invisible

- **Need.** D5 listed Not planned and Duplicate, but §4.3's Status options omitted them and no view showed them.
- **Options.** Status values, or a view filtered on issue close reason.
- **Choice.** Status values (D12), a *Closed without shipping* view, a required one-line reason comment, and a link to the original for Duplicate.
- **Why.** Project filters work on fields; close reason is issue state. One field keeps every view and the sync on one mechanism.

### M4 — Screening was thin

- **Need.** The scan named patterns and one create path. A leak could arrive through a title, label, bot comment, branch text, sub-issue title or an attachment.
- **Choice.** §7.1 covers every field on every create, edit and comment path; sets an attachment policy (the sync never attaches Signal files, screenshots are described in words); makes a canary suite a Step 0/1 acceptance criterion; adds a hold-for-approval state for borderline results; §7.3 adds a leak-response procedure; forms carry a warning and link the Code of Conduct; a moderation owner is named by role (§8.1).
- **Why.** Edit history makes a post-hoc fix insufficient (the plan already says so), so every path to a public write needs the same gate, and the gate needs a test that proves it rejects what it should.
- **Not resolved.** Community-uploaded images cannot be scanned in advance. The plan has the moderation owner review them within the acknowledgement window and does not claim more.

### M5 — Reporter linkage

- **Need.** D3 published `IN-` numbers in a public field. A public `IN-` number, the issue's creation time and a summary of the report let anyone who knows when a person wrote to the bot link them to the issue. Device model, OS minor and exact times add to that.
- **Options.** (a) Public `IN-` as decided on 10-21. (b) `IN-` stays private, the public issue number is the receipt. (c) A separate public token per report.
- **Choice.** (b), proposed default (open item 1). D3 now reads this way, so this amends the 10-21 text. Also: per-report opt-in (D18), summaries drop device model, OS minor and exact timestamps, publication in daily batches (D13). The *Report IDs* field is removed. (c) is the alternative if the owner wants reporters to quote a stable ID that is not the issue number.
- **Why.** (b) removes the cross-reference at no cost to the reporter, who gets a link either way. A cost: dedupe looks up the ledger's `IN-` → issue map, not a project field.

### M6 — Security and embargo

- **Need.** The plan excluded items flagged security, which fails open when a flag is missing. It named no approver, said nothing of fix development, and `keyring-bifold` and the submodule pointer reveal a fix at merge.
- **Choice.** §7.2: default-deny with the security flag as a fail-closed exclusion; disclosure approver is the product owner (open item 5); fixes in the private advisory fork with no public branch or PR before release, and bifold merge and pointer bump timed to one release; a late discovery is deleted, not closed; Step 0 proves private reporting on both repositories including the fork.
- **Why.** Closing leaves content and history visible. The pointer bump is public in the wallet's git log.

### M7 — Keep-private items had no home

- **Need.** D1, D7 and the non-goal said there is no internal board, yet Step 1 has a "keep private" outcome. The rows had nowhere to go, so they would be lost or leak.
- **Options.** (a) Delete them. (b) Leave them in the Command Center backlog, which D1 says reads from GitHub. (c) A private holding project of draft items.
- **Choice.** (c), proposed default (open item 4). Draft items create no issue and no history. D1, D7, the non-goal and §4.1 now say it is a list, not a board. Embargoed security items live in private advisories, not here.
- **Why.** (a) loses work. (b) makes the Command Center a second backlog and breaks the zero-diff check.

### M8 — Verifiable acceptance criteria

- **Choice.** §5 specifies filter and grouping per view. "Command Center matches the board" is a scripted zero-diff on title, Status and Up next. Step 3 checks created bodies for `@` and each batch for 25 or fewer. Testing and Shipped automation, and *Shipped in*, are flagged conditional on the versioning-and-releases plan (not in this repository) at the approach in §8 and in the header, with a manual fallback by the triage owner. Step 3 requires a rollback test (project back to private, automation disabled).
- **Why.** The earlier criteria ("views render as in §5") could not be failed.

### S1 — Migration mapping

Added as a table in Step 1: `call = Drop` becomes Not planned; Not decided and Not scheduled become Under review with Up next blank; shipped rows without a release number become Shipped with `Shipped in` blank (*pre-versioning*); plan README statuses map to board Status; drafts stay off unless the plan owner opts in (open item 9); only plans on `main` become epics. *Choice of Under review* for undecided items: it is the honest public state, and Planned would promise work.

### S2 — Ownership and cadence

§8.1 defines a triage owner role and says "the coordinator" means it, a 3-working-day acknowledgement target (provisional), staleness rules that only report, a moderation owner with Code of Conduct and lock policy, and where the weekly job runs and with which credential. People are not named (open item 8).

### S3 — Cross-repository

Applied: the same-org assumption is stated and verified in Step 0; issues are never transferred, they are re-created, linked and closed as Duplicate; auto-add limits are verified against the org's plan; auto-add does not backfill, so existing wallet issues are added by hand in Step 1; Issues on `keyring-bifold` are confirmed and upstream Aries templates are replaced in Step 0 and §8.

### S4 — Credential

Applied as D10 and §8 (open item 6). A GitHub App is what the docs recommend for org projects, and it is not tied to a person's account. The bot identity is documented publicly so readers know whose comments they are.

### S5 — Sorting by 👍

§5 and Step 0: verify, with a fallback link to issue search sorted by `reactions-+1-desc` over a `community` label. The docs do not mention reaction sorting (see above).

### S6 — Card standard for community issues

One mechanism: the maintainer's first comment starting `**What this is:**`. The 10-21 text said the summary was added as the first comment *and* pinned in the body, which is two places. The staleness check inspects that comment for community issues and the body for the rest.
