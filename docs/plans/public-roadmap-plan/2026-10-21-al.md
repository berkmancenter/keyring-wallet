**Plan:** [`../public-roadmap-plan.md`](../public-roadmap-plan.md)
**Session:** first research pass. Internal sources were read on 2026-10-21. GitHub features were checked against GitHub's docs and changelog as of October 2026. Several of them are recent or in preview, and those are marked.

## 1. Internal sources

- **Command Center board and Backlog page.** Both are claude.ai artifacts backed by an artifact database. Collections: `release`, `testing`, `decisions`, `features`, `backlog`, `config/releases`, `builds`, `agents`, `items`.
  - Backlog rows: `title`, `what`/`plain` (1–3 sentences: symptom, cause, fix), `ref`, `lane`, `release` (only the product owner sets it), `reportedBy/Via/On`.
  - Backlog page items: `group` (feedback / p1 / p2 / p3 / shipped), `plain`, `state`, `call` (Next release / Later / Drop).
  - On 2026-10-08: 57 decisions, 100+ work items, 32 backlog rows and 11 session cards.
  - The plain-language writing is already close to what a public card needs.
  - **Gap:** the account used for this research could not open either artifact. Counts come from the 10-08 cadence report and an older snapshot, not from a live read.
- **Agents' work queue.** About 100 rows mixing `IN-` ids with ad-hoc ids. Technical text: file and line references, DIDs, hostnames.
- **Signal ledger.** An append-only event log with a regenerated summary.
  - **Every inbound message with text or an attachment gets the next `IN-` number,** including chatter and follow-ups. So 351 numbers have been issued, but about 155 were merged into another ticket, about 69 closed as noise, and 63 are open.
  - States: awaiting → claimed → answered → queued → fixed → told → notify/closed.
  - Each row holds the reporter's display name, Signal UUID and verbatim text.
  - **Conclusion:** an `IN-` number is a receipt for a message, not an identifier for a piece of work. The board has to map many receipts onto one issue, and it can never publish rows directly.
- **Existing public-writing rules.** The leadership-update procedure and the planned GitHub Release body already require plain words, verified claims, and no names, private quotes, DIDs, hostnames or report ids. The card standard reuses them, except that report ids become public once their issue is accepted (plan D3).
- **Plans.** 16 plans on `main`, with subtasks as `<plan>/<x>_subtask.md`. Some README statuses are stale, and plans rarely link PRs.
- **GitHub.**
  - Both repos are public, with issues on, Discussions off and no milestones.
  - The wallet has 13 issues, default labels and no issue templates. Bifold has upstream Aries templates that still say "Aries Bifold".
  - Org issue types Task, Bug and Feature are enabled.

## 2. GitHub capabilities that shape the design (October 2026)

- **Projects:**
  - Table, board and roadmap views.
  - 50 fields per project; 50,000 items including archived ones.
  - Public projects are visible to anyone. Project visibility never overrides repository permissions: private-repo items show to outsiders as redacted.
  - Built-in workflows: closed → Done and merged → Done are on by default. Auto-add works one repo per workflow (5 workflows on Team) and does not backfill existing items. Auto-archive immediately archives everything that already matches.
  - Projects have a README and status updates (health, dates, notes), and insights are visible to every viewer.
  - Docs: <https://docs.github.com/en/issues/planning-and-tracking-with-projects>
- **Issue hierarchy:**
  - Sub-issues: 100 per parent, 8 levels, across repos within the org.
  - Issue types: org-level, up to 25, and issue forms can set `type:`.
  - Dependencies (blocked by / blocking): GA 2025-08-21.
  - "Relates to" links: GA 2026-09-25.
- **Issue fields** (GA 2026-07-02, multi-select GA 2026-08-07):
  - Each field has a visibility, **Public** or **Organization only**. Organization-only fields are hidden from non-members in the sidebar, timeline and search, including on a public project.
  - They cannot be set from issue templates; only the sidebar, a project, the API or Actions can set them.
  - This is the only per-field privacy control. Project fields have none.
  - <https://github.blog/changelog/2026-07-02-issue-fields-are-now-generally-available>
- **Issue sidebar** shows the first release containing the linked PR (2026-04-09).
- **Previews to watch:** native issue status (Backlog / Todo / In progress), the Issues board view and the Planning tab (github/roadmap #1336, #1337, #1339, September 2026). Native status could replace the project Status field later.
- **Automation:**
  - `GITHUB_TOKEN` cannot write to projects, so automation needs a separate credential.
  - `addProjectV2ItemById` is idempotent.
  - Adding an item and setting its fields take separate calls.
  - Content creation is limited to about 80 a minute and 500 an hour, with secondary limits on concurrency.
- **Intake:**
  - Issue forms (`type:`, `labels:`).
  - `config.yml` with `blank_issues_enabled: false` and contact links.
  - A repo setting restricting issue creation to collaborators (2026-06-29).
  - Private vulnerability reporting with structured report forms and confidential comments (2026-10-01).
- **Pitfalls:**
  - Bulk-creating issues notifies everyone watching the repo, and @mentions in generated bodies notify those people.
  - Issue numbers cannot be chosen, so `IN-309` never equals `#309`.
  - Private-repo issues cannot be transferred to a public repo.
  - Edit history persists after a redaction.

## 3. How other open-source projects run public roadmaps

- **GitHub's own roadmap** (github/roadmap, org project 4247):
  - Plain "Value Prop" / "Expected Outcome" bodies, the phase in the title, and quarter columns plus an "Exploratory" column.
  - Issues are locked, and feedback goes to Discussions.
  - Shipped items are closed with a link to the changelog post.
  - An explicit "not a commitment" disclaimer.
- **Mastodon:** Released / Next release / Exploring, with one or two benefit-led sentences per item and no dates. The horizon is deliberately 3–6 months.
- **Zed:**
  - A public "Community Requests" project, with 👍 counts as interest.
  - Feature requests go to Discussions, and bug forms set `type: Bug` plus a `needs triage` state label.
  - Zed's contribution policy refuses contributions from autonomous agents. That is relevant optics for a team that works through agents, and why the plan's README says plainly how we work.
- **Bitwarden:** votes are "a barometer", not binding. In 2024 the public roadmap was cut back to items in active development.
- **Home Assistant:** a public, commentable roadmap framed as an open call to contribute.
- **Tauri:** several public org projects, each scoped to one initiative.
- **Logseq:** a public Trello roadmap went stale and drew lasting complaints. This is the failure the staleness check exists to prevent.
- **Common pattern:**
  - three to six plain statuses;
  - no dates;
  - a "not a commitment" line;
  - requests and voting kept apart from work items;
  - shipped items closed with a release link;
  - duplicates closed by pointing at the original.

## 4. Options considered and not taken

1. **Publish the Command Center artifact directly.** It mixes release, gate and session detail with the backlog, cannot be filtered per audience, and lives outside the repo, where neither contributors nor GitHub links can reach it.
2. **One issue per `IN-` number.** Most numbers are chatter or follow-ups. The board would fill with noise and duplicates.
3. **A private intake repo, with issues transferred to the public repo when accepted.** GitHub cannot transfer private-repo issues to a public repo, so this becomes re-create plus manual linking. The privacy screen before creation does the same job with less machinery.
4. **Issues in both `keyring-wallet` and `keyring-bifold`.** It splits the board's audience across two repos for a distinction (which submodule holds the code) that readers don't care about.
5. **A stale bot that auto-closes inactive issues.** Widely resented, and it would close real tester reports. The plan's staleness check reports to the coordinator instead.
6. **Dates or quarters on cards.** A small team's dates slip and turn into broken promises in public. Releases are the only time unit shown.

# Part 2 — Later the same session: decisions taken

## 5. Decisions and what they superseded

The product owner answered D1–D10 the same day. These first-pass positions are superseded:

- **A private "Keyring Internal" project, with organization-only fields (Priority, Lane, Next-release call).** Rejected (D7). The team coordinates in Signal and has no use for a second board. Without an internal view there is nothing to show organization-only fields in, so the plan uses none. The product owner's "Your call" moves onto the public board as a project field, *Up next* (Next release / Later), which carries no date.
- **Issues in `keyring-wallet` only.** Replaced by both repositories on one project (D2). To keep the reporter's experience in one place, epics and community reports still live in the wallet, and implementation issues go to the repository where the code changes. This relies on sub-issues working across repositories in one org.
- **GitHub Discussions for feature ideas.** Replaced by feature-request issues through a form (D8). 👍 on the issue shows interest. A community issue keeps the reporter's own words, and the plain summary is added at triage.
- **Credentials.** The first pass named a specific credential type. How automation authenticates is now kept out of the plan documents entirely (D10) and managed separately.

## 6. Findings after the decisions

- **Org project #9 "Keyring" exists.** It is private, was created in 2025 by another maintainer, and was last updated 2026-09-23. It holds 125 items: 61 from a private `AdvancedIdentity` repo, 31 from an older private `bifold` repo, and a few from three others. Making it public would show outsiders redacted rows, and it belongs to someone else. Decided: a new project, with #9 left alone (D11).
- **The org already has issue fields:** Priority, Effort, Start date and Target date. They are not used on this board. Priority is expressed by order and *Up next*, and dates are excluded by D9.
- **Page sources confirm the data model.** The product owner supplied the HTML of both pages. They match the schema in the plan's §3: the Command Center backlog has a per-row release picker (release numbers, "Later", "Not scheduled"), and the Backlog page has a per-item "Your call" (Not decided / Next release / Later / Drop). The pages load their rows from the database at runtime, so the sources carry no item data.
- **The Command Center and Backlog page databases cannot be read from the account used here.** Both artifacts belong to a claude.ai account outside this login's organization, so the database read was refused, and a page read returns only the loading shell. Step 1 therefore runs from a session signed in to the owning account, and the current-state counts stay those of 2026-10-08.
- **The stretch idea from the product owner:** a Keyring agent in the Signal channel that asks for and records decisions. It is recorded under *Later* in §10 and deferred until after Step 4.
