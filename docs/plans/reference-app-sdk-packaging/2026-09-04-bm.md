# 2026-09-04 — BM: R1–R4 built, and "no hand-configured .env" raised from convenience to acceptance criterion

Companion to [`reference-app-sdk-packaging.md`](../reference-app-sdk-packaging.md).
Records what implementation of sequencing items 1 and part of 2 settled, a
requirement that arrived during the work and changes what R1 has to deliver,
and several findings about the developer path that only building it could
produce — including two places where the plan asked for more than the codebase
actually needs.

## What this document settles

**R1 is built and confirmed on a device.** `bifold/packages/mediator-server` is
a Credo mediator; `scripts/mediator-lifecycle.js` is its spin-up; `yarn mediator`
and `yarn demo:android` / `yarn demo:ios` are the entry points.

**The bar moved: a basic demo must require no hand-configured `.env` at all.**
The plan's R1 asked for "a documented, one-command local stack". During the
work that was tightened: a developer trying a demo should not hand-edit
`app/.env` — not to paste a mediator URL, not for anything else. This is
stricter than what R1 said, and it is the standard the rest of the
reference-app track should be held to as well (R3's bundled OCA resolver
removes the `OCA_URL` reason to touch that file, which is the same objective
arriving from a different direction).

That is why there are two commands rather than one. `yarn mediator` is the
mediator alone. `yarn demo:<platform>` is the whole thing, and exists because
**`app/.env` is a build-time input**: react-native-config bakes `MEDIATOR_URL`
into the native build, so "start the mediator" and "build the app" are not two
independent steps a developer may interleave freely — the mediator must be up
and its invitation written before any build starts. Ordering that correctly is
not something a README can be relied on to enforce, so the demo runner enforces
it.

## Decision: mint a fresh invitation on every boot

The mediator does not cache its invitation across restarts. The invitation
carries the mediator's `serviceEndpoint`, and that endpoint changes whenever
the tunnel in front of it restarts; a cached invitation would still parse and
still connect, to an address that no longer answers.

This is the same failure `app/.env.sample` shipped: a captured ngrok
invitation, dead for a long time, whose symptom is not a startup error but
"There is no mediator to pickup messages from" much later (`e2e/README.md`).
That value is now empty rather than stale — **an empty value fails immediately
and legibly; a stale one fails late and misleadingly** — and is filled in by
tooling.

## Finding: the tunnel is not always needed, which narrows R1

R1 assumed the witness's tunnel arrangement carries over wholesale. It does
not, and the cheaper path is available for the common case. Debug builds permit
cleartext to a fixed set of hosts —
`app/android/app/src/debug/res/xml/network_security_config.xml` allows
`localhost`, `10.0.2.2` and `127.0.0.1`; `app/ios/AriesBifold/Info.plist`
carries an ATS exception for `localhost`:

| Target | Endpoint | Tunnel |
|---|---|---|
| Android emulator(s) | `http://10.0.2.2:<port>` | no |
| iOS simulator(s) | `http://localhost:<port>` | no |
| Android emulator **and** iOS simulator together | — | yes |
| Physical phones | — | yes |

So the default demo path needs **no `cloudflared`, no account, and no network
beyond the machine itself** — `cloudflared` becomes a dependency only for
physical devices and mixed pairs. A newcomer's first run has one fewer thing
to install and one fewer thing to fail.

## Findings: two ways the developer path lies about success

Both were found by running the thing, not by reading it, and both would have
been reported to a funder-facing developer as a working demo:

1. **`react-native run-android` starts Metro by opening a new terminal
   window.** Headless — over SSH, in CI — that silently does nothing: the
   build succeeds, the app installs and launches, and then waits forever for a
   bundle it cannot fetch. The only evidence is a `Couldn't connect… will
   silently retry` line in logcat. The demo runner therefore owns Metro and
   waits for it to listen before building.
2. **Asked to use an occupied Metro port, the CLI prompts — and with no
   terminal to answer, exits 0 without building anything.** A runner trusting
   that exit code announces success over an app that was never installed. A
   busy port is now refused up front, and the install is confirmed by asking
   the device what is installed rather than by trusting an exit code.

The general lesson for the remaining reference-app work: **verify against the
device, not against the exit code.** The toolchain has more than one way to
report success while having done nothing.

## Finding: R3 needs no new resolver — it was always supported

R3 asked for "a local/offline OCA resolver option… so a from-scratch PoC
doesn't have to reason about GitHub-raw hosting just to skin one credential",
and the walkthrough sized it as building one, noting the interface is small
enough that it would be easy (`resolve(params)`).

It did not need building. `DefaultOCABundleResolver` — the class
`RemoteOCABundleResolver` already extends — takes bundles as a
`Record<string, IOverlayBundleData>` keyed by credential definition id, schema
id or template id, and resolves them from memory with no network. Shipping
branding inside the app has always been one constructor argument.
`app/src/demo-profiles/starter/ocaBundles.ts` is the worked example, and
credentials with no bundle still render, because the resolver generates a
default one and derives a colour from the credential name.

So R3 is documentation and a worked example, not engineering. **Two of the five
reference-app requirements turned out smaller than the plan sized them once
checked against the code** (this and R1's tunnel). That is worth noting before
R5 is scoped: the plan's estimates were made from reading, and reading
overestimated twice.

## Decision: the starter container sits alongside `container-imp.ts`

R2's line-level analysis stands — of `container-imp.ts`'s 421 lines, roughly
fifteen are container mechanism and most of the rest is BC-Gov and Keyring
product detail. But the plan described producing the trimmed version as
*subtractive*, which reads as trimming the real file.

`app/src/demo-profiles/starter/StarterContainer.ts` is a separate ~60-line
container instead, and `container-imp.ts` is untouched. Two reasons. The
2026-09-03 caution — that some of what looks like BC-Gov cruft may still be
live in Keyring's own product, and must be proven dead before deletion — is
real work that gates nothing a demo needs. And the deliverable is *a file to
copy*: a trimmed `container-imp.ts` would still be Keyring's container, where
what a newcomer wants is the smallest thing that runs. Deleting the dead
BC-Gov registrations is still worth doing, on its own, as a change to Keyring
rather than as demo preparation.

The starter is tested for the one property that matters — that it is genuinely
swappable for `AppContainer`: it satisfies the `Container` contract, its
overrides resolve, core's registrations still resolve through it (it is a child
container, so a copy need not re-register the app), and its `LOAD_STATE`
example is safe on a first boot with nothing persisted.

## Note: `.gitignore`'s bare `lib` pattern

The shared spin-up module was first written to `scripts/lib/mediator.js` and
was invisible to git — root `.gitignore` line 24 is a bare `lib`, which
matches a directory of that name at any depth. It now lives at
`scripts/mediator-lifecycle.js`. Worth knowing before anyone puts shared code
under a `lib/` directory anywhere in this repo; not worth changing the ignore
rule for, since narrowing it risks un-ignoring build output elsewhere.

## Acceptance evidence

On a `-wipe-data` Pixel_8_API_33 emulator, from a checkout with no `app/.env`,
`yarn demo:android` alone produced a running, onboarded wallet:

- `yarn e2e:smoke` (install → onboarding → main tabs) passed against it.
- The device log shows `Mediation granted, setting as default mediator`,
  `Default mediator set`, and a Pickup v2 `status-request` / `status` exchange
  with the local mediator at `http://10.0.2.2:3010`.

The package also carries `yarn verify`, which stands the mediator up, points a
wallet-shaped Credo agent at the invitation it minted, and asserts mediation
reaches `granted` — a headless check that does not need a device. It is a
script rather than a jest test because `@credo-ts` ships ESM builds that
package's ts-jest setup cannot parse, and the root `CLAUDE.md` says not to bend
a package's jest config to match.
