# 2026-09-10 — BM: the Approver moves per-contact; `ACTIVE_DEMO_PROFILE=none` reaches the bundle; dev-mode module-resolution debt closed

Companion to [`reference-app-sdk-packaging.md`](../reference-app-sdk-packaging.md).
Records the Approver demo's UI recast off the Wallet tab and onto each
contact's own details screen, two new container extension points that
recast rode in on, `ACTIVE_DEMO_PROFILE=none` closing from runtime-inert to
build-time-excluded, and a round of dev-mode module-resolution fixes the
walkthrough kept tripping on.

## What this document settles

**The Approver's UI is no longer a Wallet-tab-wide banner.**
`2026-09-06-agent.md` and `2026-09-06-agent2.md` recorded `ApproverHomeBanner`
— a single footer slot on the credential list showing "whichever single
request was pending across ALL contacts at once." That doesn't generalize:
a real access request always comes from one specific contact, and a global
slot can only ever surface one of them, on a screen that has nothing to do
with contacts. It's replaced by `ApproverContactSection`, rendered per-contact
on `ContactDetails` and scoped to that contact's own connection, plus
`ApproverGlobalListener`, a toast that fires from anywhere in the app and
navigates to the sender's `ContactDetails` — the entry point the removed
banner used to be.

**Two new container tokens carried this, both general-purpose, not
Approver-specific:** `COMPONENT_CONTACT_DETAILS_FOOTER` (per-contact
injection point, mirroring `COMPONENT_CRED_LIST_FOOTER`'s no-op-default
pattern) and `COMPONENT_APP_GLOBAL_LISTENER` (mounted once in `TabStack`,
alongside `InAppMessageNotifier`, for a profile that needs to observe
app-wide events regardless of which screen is active). A third,
`COMPONENT_CONTACT_CARD`, shipped a few days earlier in the same vein —
`ListContacts`' hard-coded R-Card row is now a resolved token
(`modules/vrc/components/ContactCard.tsx`), so a demo profile can restyle
the contacts list itself (a trading card, say) with one `registerInstance`
and no fork. None of this is new mechanism: it's the same `container-api.ts`
DI pattern R2 already established, extended with three more example
registrations — exactly the shape R2's "trimmed starter container" argument
in `2026-09-04-bm.md` expects future work to take.

**`ACTIVE_DEMO_PROFILE=none` now excludes demo code from the JS bundle, not
just from the runtime registry.** `selectDemoProfiles` already returned `[]`
for `none` (built 2026-09-07); until now that only meant the code shipped
unregistered, not absent. Metro's `resolveRequest` swaps the `demo-profiles`
barrel import for a zero-dependency stub whenever the flag is set, so
Metro's dependency graph never reaches into `approver/`, `trading-card/`, or
`starter/` — true build-time exclusion. This is R4 closing a gap the plan
left open: a developer building *Keyring itself* from this scaffold, not a
demo, can now do so with zero demo-profile code in the artifact, which
matters for anyone shipping a production app from the same repo shape.

## Why the UI moved, and what broke while it did

Moving from "one slot, global" to "one slot per contact" surfaced three bugs,
each fixed and each with a regression test in `4b54aed`:

- **Late `connectionId`.** `ApproverContactSection` checked
  `trustTaskPromptStore` for a pending request only in its `useState`
  initializer, which runs once at mount — before `ContactDetails`' own
  async connection-id lookup resolves. A request that arrived *before* the
  screen opened (the exact case `ApproverGlobalListener`'s toast produces,
  since it navigates straight here) had already fired its one-shot `prompt`
  event and would never appear. Fixed by syncing against the store whenever
  `connectionId` changes, not just subscribing to future events.
- **Wrong counterparty name.** The pending-prompt label used
  `connection.theirLabel` — the DIDComm connection's own label, frequently
  not the name a person recognizes for that contact. `genericApproval.ts`
  now prefers the VRC/RCard issuer name (`getVrcNameForConnection`) when a
  relationship exists, falling back to `theirLabel` only when it doesn't.
- **Overflow on free-text fields.** A request's resource/reason fields are
  free text; laid out side-by-side with no wrap inside a card embedded in a
  details-screen footer, long values clipped. `TrustTaskFields` (label above
  value, `flexShrink`/`flexWrap` on the value) is now shared between the
  inline `TrustTaskApprovalCard` and the new `TrustTaskApprovalModal` — a
  scrollable bottom sheet used for the Approver's actual incoming-request
  presentation, since a card embedded in a footer doesn't have the room a
  modal does. `1dca0598` additionally made the requester's name the
  dominant heading in the modal (a bold name under a small "Request from"
  caption, demoting the task type's own generic title) — who is asking is
  what a person needs to notice before tapping Approve, a UI-copy decision
  worth recording since it isn't derivable from the diff alone.

## Dev-mode module-resolution debt, found and closed

Three unrelated failures surfaced while running the app and its test suites
during this work, all the same shape as `2026-09-04-bm.md`'s "two ways the
RN toolchain reports success having done nothing":

- `@hyperledger/anoncreds-react-native`'s Android `build.gradle` has no
  `namespace`, which AGP 8.x now hard-requires, and two native deps
  (`react-native-inappbrowser-reborn`, `react-native-splash-screen`)
  reference an `android/libs` `fileTree` npm never publishes — both patched
  via `patch-package`; the Android debug build was failing outright before
  this.
- `tsc` and Jest each independently resolve `@bifold/react-hooks` and
  `@bifold/credo-tsp-adapter` to their declared `build`/`lib` output, which
  doesn't exist in dev (Metro alone was taught to resolve these to source,
  via `BIFOLD_SOURCE_PACKAGES`). `tsconfig` paths and
  `jest.config.js`'s `moduleNameMapper` now mirror that, closing typecheck
  and test-suite gaps that had nothing to do with the code under test.
- Inside bifold itself, `react-hooks`' public entry point never re-exported
  `recordUtils`' `recordsAddedByType`/`recordsRemovedByType`/`RecordsState`,
  so a consumer (`OpenIDCredentialRecordProvider`) reached into a
  `build/recordUtils` subpath that only exists post-build — invisible in
  CI, which builds first, but broken for exactly the dev-mode,
  build-from-source workflow R1's "no hand-configured `.env`" bar is
  supposed to make painless.

None of these are packaging-plan scope changes; they're recorded because
each one silently blocked the walkthrough R1/R2 already promised works, and
the next person hitting the same error should find it here rather than
re-diagnosing it.
