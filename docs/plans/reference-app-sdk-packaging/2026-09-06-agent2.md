# 2026-09-06 — agent: the Approver on-device gap, resolved

Companion to [`reference-app-sdk-packaging.md`](../reference-app-sdk-packaging.md),
continuing [`2026-09-06-agent.md`](./2026-09-06-agent.md), which left one open
finding: the Approver demo's "Request access from a contact" button did not
respond to taps on-device, even though Appium confirmed the tap resolved to and
clicked the correct, unique accessibility node.

## What this document settles

The on-device round trip now passes, for a different reason than the first
hypothesis. Both causes are recorded here because each is real and each was
independently confirmed — the first fix did not turn out to be the answer to
the second problem, and a reader who only sees the final state would wrongly
conclude one bug, one fix.

## Cause 1, real but not sufficient: `ListFooterComponent` as an inline function

`bifold/packages/core/src/screens/ListCredentials.tsx`'s `FlatList` had
`ListFooterComponent={() => <CredentialListFooter credentialsCount={credentials.length} />}`
— an inline arrow function. `@react-native/virtualized-lists`' `VirtualizedList.js`
treats a non-element `ListFooterComponent` as a component *type* and
instantiates it fresh via `<ListFooterComponent />` on every render
(`isValidElement(ListFooterComponent) ? ListFooterComponent : <ListFooterComponent />`).
An inline arrow function is a new identity every time `ListCredentials`
re-renders — routine during an active DIDComm session — so React read it as a
changed element type and fully unmounted/remounted the whole footer subtree on
every such re-render. `TradingCard`, the only prior
`COMPONENT_CRED_LIST_FOOTER` registration, never surfaced this because it has
no `onPress` to lose; the Approver demo's buttons were the first interactive
consumer of that token.

**Fixed**: pass the element directly —
`ListFooterComponent={<CredentialListFooter credentialsCount={credentials.length} />}`
— so React reconciles by `CredentialListFooter`'s own stable type instead of a
fresh render-scoped closure. Confirmed against the existing
`ListCredentials.test.tsx` / `listCredentialsFilter.test.ts` (13/13 passing, no
regression).

**This alone did not resolve the symptom.** A second real on-device run, with
the fix applied and a diagnostic `console.log` as the literal first statement
of the button's `onPress`, still showed zero occurrences of that log in
logcat, on either device, across the run. The remount theory was real but
wrong for this case — recorded, not deleted, per this directory's own
convention, since the fix is independently correct and worth keeping regardless
of whether it explains this particular bug.

## Cause 2, the actual answer: a lingering onboarding-tour overlay

Diagnosis proceeded in two steps rather than guessing again:

1. **Ruled out a stale-bundle problem.** `app/metro.config.js` resolves
   `@bifold/core` to ESM source in dev, so edits should reach a running app
   with no build step — but "should" isn't "does." A unique marker string
   added to the `onPress` handler was confirmed present in the actual bundle
   Metro was serving (`curl` the bundle, grep for the marker) within seconds of
   the edit. Bundle freshness was not the problem.
2. **Isolated the failure to position, not component.** A bare RN `<Button>`
   planted alongside the real `TouchableOpacity`, in the same footer position,
   also never fired its `onPress` on a real run — even though a mount-log
   confirmed the component tree was present and stable (not remounting
   mid-gesture, so cause 1's fix was holding). Something was intercepting the
   tap before it reached either element.

The Appium view-hierarchy dump taken immediately after a failed tap showed the
answer directly: a full-screen `SpotlightOverlay`/`SpotTooltip` — bifold's
onboarding tour — layered over the entire window (`bounds [0,0][1080,2340]`).
`bifold/packages/core/src/components/tour/TourOverlay.tsx` renders this as an
absolutely-positioned view with no `pointerEvents="box-none"`, so while the
tour is up, every tap lands on its backdrop regardless of what the
accessibility tree reports underneath — which is also why Appium's
`elementClick` kept reporting clean success against the right node: the OS
correctly delivered a touch to that screen region, and the tour intercepted it
before React's responder chain saw it.

This tour auto-starts the first time the Wallet tab renders with zero
credentials, which is every run of the Approver demo, since it issues none.
The codebase already carries a guard for exactly this —
`e2e/lib/flows.js`'s `dismissTourIfPresent`, with its own comment ("a lingering
tour overlay can swallow the first tab tap") — called by several other flows
after switching tabs. `run-approver-exchange.js`'s own `goToWalletTab` simply
never called it.

**Fixed**: added `dismissTourIfPresent(driver)` after the Wallet-tab tap in
`goToWalletTab`. Not an app bug — the tour is intentional first-run UX; the
test needed to dismiss it like every other flow already does.

## Verification

A real, full two-emulator run (`ANDROID_AVD2=Pixel_8_API_33_b
PLATFORMS=android,android node run-approver-exchange.js`, local mediator,
existing debug APK) passed the complete round trip: access request sent by
wallet A, `TrustTaskApprovalCard` rendered on wallet B, approved, signed
decision received back on wallet A. All temporary diagnostics (the extra
`Button`, mount/unmount logs, the marker log, a throwaway diagnostic script)
were removed before this was recorded.
