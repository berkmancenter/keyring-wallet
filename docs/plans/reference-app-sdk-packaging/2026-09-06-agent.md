# 2026-09-06 — agent: R5 built — the open registry, the generic approve/deny screen, and the Approver demo

Companion to [`reference-app-sdk-packaging.md`](../reference-app-sdk-packaging.md).
Records what R5 (the open Trust Task type→handler registry + a UI-side
render/approve-deny registry, plus the Approver demo profile) settled on, why,
the concrete Type URI and scenario chosen, the DI-token-collision finding from
wiring two demo profiles together, and what is verified versus still
unverified.

## What this settles

R5's two halves — engine-side dispatch and UI-side rendering — are built and
exercised end to end by a new, third demo profile (`app/src/demo-profiles/approver/`),
alongside the existing `starter/` and `trading-card/` profiles. Nothing about
the existing VRC/witness/discovery exchange changed behaviourally: it is now
implemented as the first four registrations into the same open registry
rather than a separate if/else sitting beside it, and the full existing
`ceremony.test.ts` suite (unchanged) still passes against that refactor.

## The registry design, and why

Built precisely to 2026-09-01-al.md §2's specification —
`registerTrustTask({ spec, orchestration, renderer })`, not a bare dispatch
table — and to 2026-09-03-bm.md's Carriage-shaped constraint. Concretely,
two registries, kept apart on the same axis 2026-09-01-al.md §1 already
draws between the pure Trust Tasks layer and everything Credo/UI-specific:

- **`bifold/packages/core/src/modules/trust-tasks/registry.ts`** —
  `TrustTaskRegistry`, the engine-side, platform-neutral half. A
  `TrustTaskRegistration` carries `typeUri`, `spec` (the same
  `TrustTaskSpecPolicy` shape `TrustTasksService.consume` already takes),
  optional `responseSpec`, optional `orchestration`
  (`isDeterministicProposer`, `minRceVersion`, `requiresDiscovery` — the four
  things 2026-09-01-al.md §2 names: proposer selection, capability gating,
  version gating, and idempotence; idempotence itself is not a registry
  field because it is already structural — every registration's handler
  queries `{typeUri, connectionId}` through the same
  `TrustTaskDocumentRepository` the built-ins use, so a registration gets it
  by writing its handler the way the existing ones do, not by declaring a
  flag), and `handleRequest`/`handleResponse`.
  `resolveForDocumentType(documentType)` strips `#response` and returns the
  registration plus whether the inbound leg was the response — the one
  lookup `ceremony.ts`'s dispatch needs.

- **`bifold/packages/core/src/modules/trust-tasks/display/trustTaskDisplayRegistry.ts`**
  — the UI-side half, mirroring `ICredentialDisplayRegistry`
  (`modules/vrc/display/displayRegistry.ts`) exactly on purpose, per the
  plan's own instruction to reuse that pattern rather than invent a second
  one. It maps a `typeUri` to `Field[]` extraction (`ITrustTaskDisplayResult`
  — title, `Field[]`, approve/deny button label keys), not to a React
  component: the actual rendering is one generic component,
  `bifold/packages/core/src/screens/TrustTaskApprovalCard.tsx`, that lays out
  whatever `Field[]` a matching handler returns plus two buttons — the same
  relationship `ICredentialDisplayRegistry` has to
  `CredentialCard10`/`Card11Pure`. This is deliberately a **card component,
  not a navigator screen/route**: R5's own scope note
  (2026-09-03-bm.md: "a full picker UI is out of scope") argues against
  adding a new stack route, which would mean touching the app's shared
  navigator — exactly the kind of shared-code edit a demo profile shouldn't
  need. A profile embeds the card wherever it wants (the Approver profile
  embeds it in a `COMPONENT_HOME_HEADER` override); the component itself
  assumes nothing about where it's mounted.

- **`registerTrustTask({ spec, orchestration, renderer, ... })`**
  (`registerTrustTask.ts`) is the single call surface the plan asks for,
  registering into both registries in one call when a `renderer` is
  supplied.

**`ceremony.ts`'s dispatch itself** (`setupTrustTasksInbound`'s
`handleInboundDocument`) is now: strip `#response`, look up
`trustTaskRegistry.resolveForDocumentType(type)`, and call
`handleRequest`/`handleResponse`. The four existing branches — `propose`,
`discovery`, `issue`, `witness-share` (each with its own request/response
pair) — are registered into this exact registry at the bottom of `ceremony.ts`
(`registerBuiltinTrustTasks()`, called once at module load, guarded against a
duplicate call). This is the part the plan calls out as proving the registry
is real: **a demo profile's registration and the built-in VRC exchange now go
through the identical lookup**, not a privileged path beside an empty
registry. `handleInboundDiscovery`'s `supportedTypes` answer was changed to
merge the legacy `SUPPORTED_TASK_TYPES` constant with
`trustTaskRegistry.listTypeUris()`, so a demo profile's registered type is
discoverable the same way the built-ins are, with no second list to keep in
sync.

Every existing behaviour is preserved exactly, verified by the full existing
`ceremony.test.ts` suite passing unchanged (24 tests across
`registry.test.ts` + the new `ceremonyRegistry.test.ts` + the existing
`ceremony.test.ts`, run together) and by the full `bifold/packages/core`
suite (1667 passing, 2 skipped, 182 suites — see "Verified" below). The
existing "arrived without an authenticated connection" retain-and-warn path,
the witness-leg response handling, the `trust-task-error` handling, and the
"unhandled type" retain-and-log fallback all stay exactly where they were in
`handleInboundDocument`, unmodified — they were never branches *of* the
if/else this refactor replaced; they sit after the registry lookup as its
documented fallback for anything the registry doesn't resolve (a type with no
`handleResponse`, or a `document.type` nothing has registered).

### The generic approve/deny scaffold (`genericApproval.ts`)

R5 also needed the "there is no UI anywhere that renders an arbitrary
incoming Trust Task and lets a person approve/deny it" gap filled once, not
per-demo. `createApprovalRequestHandler({ spec, summarize, proofPolicy })`
builds a `handleRequest` that runs the framework pipeline
(`TrustTasksService.consume`) and, on acceptance, surfaces the document in a
new `trustTaskPromptStore` (an `EventEmitter`, the same shape
`witnessStatusStore.ts`'s `vrcFlowStore` already uses) instead of
auto-replying — mirroring how `handleInboundPropose` defers to
`pendingProposals`/`respondToRelationshipProposal` today, generalized across
any registered type. `respondToPendingTrustTask(agent, connectionId, typeUri,
decision, buildResponsePayload, signUnderRelationshipDid?)` is the answer
side: builds the `#response` via the same `respondWith` helper
`handleInboundIssue` etc. use, optionally signs it, retains it, and sends it.

One real design deviation surfaced building the Approver demo against this
scaffold: `proofPolicy` could not be a single static value, because "verify
under whichever identity this specific contact already established" (an
existing relationship DID) is inherently a per-sender lookup, not a value
known at registration time. `CreateApprovalRequestHandlerOptions.proofPolicy`
was widened to accept either a static policy or `(agent, context) =>
Promise<policy>` — a real, if small, extension the generic scaffold needed to
be honest, not a corner cut for the demo.

## The Approver scenario and Type URI

**Scenario:** two wallets already hold an established VRC relationship (the
existing exchange, unmodified). Either side can then ask the other, over that
same connection, for access to something concrete — the demo's own worked
example is *"may I see your event photo album ('Family 2026')?"* — and the
other side sees the request rendered (via the generic card) and taps Approve
or Deny. The decision travels back signed, and the requester's own UI shows
that the signed decision landed (`ApproverLastDecision`).

This picks the narrowest concrete instance of "The Approver" the plan's own
research scored — not the browser-login/`demo-rp` MVP from
`openvtc-integration-plan.md` §6 (there is no relying-party service in this
repo, and building a browser flow was explicitly out of scope for this work),
but the wallet-to-wallet shape 2026-09-03-bm.md's phasing already committed
to for this demo, riding the same two-device VRC exchange the trading-card
demo rides.

**Type URI:** `https://keyring.appliedtechnologylab.org/spec/approver/access-request/0.1`
(and its `#response`). Minted under a private authority per
`trust_tasks_subtask.md` §1 point 5 / §6.5 ("Publishing under an authority we
control is fully conforming... The only constraint is that we must not use
the `trust-task*` reserved slug prefix or the `trusttasks.org` authority") —
the host is the one 2026-09-01-al.md §6b's R13 already names as the lab's
documentation address, so it is a real authority the lab controls rather than
an invented placeholder domain. Checked against every existing Type URI in
the codebase before minting (`propose`, `issue`, `discovery`,
`witness/session{,/submit}`, `witness-share`, all under `trusttasks.org`, plus
upstream `@openvtc/trust-tasks`'s full registry, which — notably — already
ships a generic `confirm/request/0.1` type under `trusttasks.org` with a
similar "ask for confirmation, get a signed ack" shape. Recording this rather
than silently ignoring it, per `docs/plans/CLAUDE.md`'s instruction to keep
rejected alternatives as standing rationale: the Approver demo does not reuse
`confirm/request` because (a) it is scoped to the demo's own authority per the
task's explicit instruction to mint a new one, and (b) `confirm/request`'s
payload (`subject`, `challenge`, free-text `reason`/`actionDetails`) is a
generic RP-confirmation shape with a synchronous ack as its `#response` —
different from this demo's synchronous decision-carrying `#response` — so a
literal reuse would have been a bad fit even absent the authority
constraint. `payload.schema.json` is checked in at
`app/src/demo-profiles/approver/payload.schema.json`
(`trust_tasks_subtask.md` §1 point 4), and the app validates against
`SPEC.payloadSchema` in `accessRequestSpec.ts`, kept identical to the checked-in
file by hand — the same "LOCAL spec staging" convention
`witnessShareSpec.ts` already uses for a spec that hasn't gone through
codegen.

**Proof:** required on both legs, verified under the sender's already-established
VRC relationship DID — the exact policy `issueProofPolicy` in `ceremony.ts`
applies to the issue/witness-share legs, reused rather than reinvented. This
demo has no identity mechanism of its own; it deliberately rides the
relationship the two wallets already hold, which is also why it declares no
`isDeterministicProposer` (it is always user-initiated, never a
tie-broken auto-proposal) and `requiresDiscovery: false` (both wallets in
this demo run the same build, so peer support is known by construction).

## The DI-token-collision finding

Checked concretely, per requirement D, before writing `ApproverProfile.ts`:
`tradingCardProfile.register()` registers exactly two tokens —
`TOKENS.COMPONENT_CONTACT_CARD` and `TOKENS.UTIL_OCA_RESOLVER`. Neither is
something the Approver demo needs to touch — its own trigger + inbox is a
`COMPONENT_HOME_HEADER` override, and its rendering goes through the new
`UTIL_TRUST_TASK_DISPLAY_REGISTRY` token (which trading-card never touches).
**So there is no actual collision between today's two profiles.**

Requirement D still asked for "at least a minimal way to choose which is
active for a given e2e run" even without a live collision, since a future
profile easily could collide (the obvious future risk is two profiles both
wanting `COMPONENT_HOME_HEADER`, or both wanting `COMPONENT_CONTACT_CARD` for
a richer per-contact affordance). Built exactly what was asked and no more:
`app/src/demo-profiles/index.ts` exports `selectDemoProfiles(activeProfileId?)`
— unset registers every installed profile (today's default, since today's
pair doesn't collide); set to a profile `id` via `ACTIVE_DEMO_PROFILE`
(`app/.env`, read through `react-native-config`'s `Config`) registers only
that one. `App.tsx` calls
`registerDemoProfiles(bcwContainer, selectDemoProfiles(Config.ACTIVE_DEMO_PROFILE))`.
No picker UI — that is explicitly later work per 2026-09-03-bm.md's own
scope note, and this is the "an env var is fine for now" the task asked for.

One process note: this environment's permission settings deny reading or
editing `app/.env`/`app/.env.sample` directly (a blanket rule, presumably to
avoid a session leaking mediator URLs or other environment-specific values),
so `ACTIVE_DEMO_PROFILE` is not documented with a sample line in
`.env.sample` the way `MEDIATOR_URL` is — `App.tsx`'s own comment and this
document are the documentation for now. Whoever reviews this should add a
commented `# ACTIVE_DEMO_PROFILE=` line to `.env.sample` if they agree that's
where it belongs.

## What was verified, and what was not

**Verified:**

- `yarn typecheck` (root/app) — clean.
- `yarn lint` (root/app) — clean.
- `yarn test` (root, app's jest) — 19/19 suites, 87/87 tests passing,
  including the pre-existing `StarterContainer.test.ts` and
  `TradingCardProfile.test.tsx`, unaffected by this work.
- `cd bifold/packages/core && yarn test` — 182/182 suites, 1667 passing (2
  pre-existing skips, unrelated to this work), including the full
  `ceremony.test.ts` (the contract for the exchange this refactor touched)
  unchanged and passing, plus the two new suites (`registry.test.ts`,
  `ceremonyRegistry.test.ts`) covering: registration/lookup, the
  duplicate-registration guard, orchestration hooks carried through
  unchanged, that a brand-new registered type's request leg reaches
  `handleRequest` and its `#response` leg reaches `handleResponse` (not each
  other), that an unregistered type still falls back to retain-and-log, and
  that the built-in discovery type is itself resolvable through the registry
  and its answer includes a freshly-registered type (proving the discovery
  answer reads the registry, not only the static list).
- `bifold/packages/core`'s own `yarn build` (bob) — needed once, to pick up
  the new exports before the app's TypeScript could see them through the
  portal-resolved package; this is the same step any change to `@bifold/core`'s
  public surface requires and was not itself part of this task's design.
- **The e2e run itself, on two real Android emulators** (`Pixel_8_API_33` +
  `Pixel_8_API_33_b`, both already running via KVM in this environment, with
  a local mediator already up on `:3010` and a debug APK already built) —
  **run for real, five times, and it does not yet pass.** Full honesty on
  what that run found, since three of the five failures were genuine bugs
  this task surfaced and fixed, and the last is an open, unresolved finding:

  1. **Run 1–2: `COMPONENT_HOME_HEADER` never renders in this fork.**
     `screens/Home.tsx` (which resolves that token) is wired via `HomeStack`,
     but `TabStack.tsx`'s `initialRouteName={TabStacks.ContactStack}` and its
     five actual tabs (Contacts/Message/QR/Wallet/Menu) never route to
     `HomeStack` at all — confirmed by grep, not assumed. The e2e hung 30s
     waiting for a button on a screen the app can never reach. **Fixed**: the
     trigger + inbox moved to `TOKENS.COMPONENT_CRED_LIST_FOOTER` (the Wallet
     tab's credential-list footer — reachable, confirmed rendering by a
     subsequent run's own page-source dump showing "Approver demo" / "Request
     access from a contact"). `ApproverProfile.ts`'s own comment records this
     finding in place, per this plan's own repeated lesson (2026-09-04-bm.md:
     "read the code before sizing the work") — this is the fourth instance.
  2. **Run 3: the e2e script itself didn't navigate to the Wallet tab**
     before waiting for the button (an e2e-script bug, not an app bug) —
     fixed (`goToWalletTab` helper, mirroring the trading-card script's own
     "View contacts" overlay dismissal).
  3. **Run 3, second finding, real and app-side: `connections.getAll()`
     picked the mediator's own connection** as the "contact" to ask (it is
     typically the first ready connection), which has no relationship DID on
     file — fixed by excluding `connectionTypes.includes('mediator')`.
  4. **Runs 4–5: unresolved.** After both fixes above, wallet B (the Wallet
     tab, confirmed reached) still shows the "Request access from a contact"
     button rather than a rendered `TrustTaskApprovalCard` after wallet A taps
     it. Diagnostic instrumentation was added and then removed once it
     confirmed the finding: **a bare `console.log` placed as the literal
     first statement of the `TouchableOpacity`'s `onPress` never appears in
     `adb logcat`, on either device, across two runs**, even though Appium's
     own log shows the tap resolving to exactly one accessibility node
     (`resource-id=...ApproverRequestAccess`, `clickable=true`) and issuing
     `ACTION_CLICK` against it — the same mechanism that DID work, in the
     same run, for `ProposalAccept`, `RCardSubmit`, `Wallet` (the tab), and
     every other tap in the onboarding/relationship flow. So the tap
     registers at the OS/accessibility level but the RN `onPress` callback is
     not observed to run. This reads as a touch-dispatch peculiarity specific
     to a `TouchableOpacity` inside a `FlatList`'s `ListFooterComponent`
     (nothing else in this codebase has an *interactive* element registered
     through that token — `TradingCard`, the only prior custom
     `COMPONENT_*` registration, is pure display, no `onPress`), not a
     defect in the registry/dispatch work itself. **This is recorded here
     as open, not silently fixed or hidden**: the round-trip through the
     *engine* (registry dispatch, generic approval scaffold, signing) is
     unit-tested and believed correct; the round-trip through *this specific
     UI trigger, on a real device* is not yet proven. Next step for whoever
     picks this up: reproduce with a plain `Button`/`Pressable` in the same
     footer position, or move the trigger to a genuinely tap-tested location
     (a real screen/button already proven interactive in this fork) to
     isolate whether the `FlatList` footer position is actually the cause.

**Not verified, and said so explicitly rather than left implicit:**

- **No physical-device/hardware-signing path was exercised.** This demo's
  signing rides `signDocumentProof`/`verifyDocumentProof` under a
  software-backed relationship-DID key — the same key material the VRC
  exchange itself already uses on an emulator — not hardware/biometric
  attestation. That is by design (the plan's own Approver scoping never asked
  for hardware-backed signing on this demo; "Passkeys Nobody Has to Store" is
  the idea that owns hardware signing), so nothing here needed
  `yarn e2e:vrc:devices` and none was run.
- **The picker UI** (a home-screen chooser between installed profiles) is
  explicitly deferred, per 2026-09-03-bm.md's own scope note — this document
  does not reopen that.
- **T1** (measuring whether `@bifold/trust-tasks`'s canonicalizer and
  `@openvtc/trust-tasks`'s diverge) was not run as part of this work — it
  remains the "pre-demo-day insurance" 2026-09-03-bm.md already flagged,
  unrelated to R5's own scope.
- **Two JCS canonicalizers still both ship**, unrelated to and unaffected by
  this change (see 2026-09-01-al.md §1) — recorded here only so it is not
  mistaken for something this work touched.
- **The full signed round-trip on a real device is NOT proven** — see the
  five-run e2e account above. What IS proven on-device: the Approver profile
  installs, boots, and renders (both the trigger and, via the generic
  `ITrustTaskDisplayRegistry`, the would-be approval card path) correctly
  inside the real running app, on real emulators, alongside the trading-card
  profile with no observed collision. What is NOT proven on-device: a tap on
  the trigger reaching the JS layer in this specific footer position.
- A stray `artifacts/` directory at the repo root (gitignored, harmless) was
  created by running an e2e script from the wrong working directory during
  this session's debugging; it holds diagnostic dumps from run 2 only and is
  not part of this change.
