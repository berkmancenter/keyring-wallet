# 2026-11-17 (al): member badges, research to plan

Parent plan: [../member-badges-plan.md](../member-badges-plan.md).

## What was concluded

The research (private, `docs/spikes/20261117-member-badges-research.local-al.md`) read upstream at these refs:

- VTI `4abe40a2a`, plus `vtc-service` tags v0.27.0, v0.29.0, v0.30.0 and v0.31.0;
- trust-tasks-tf `4fddc096a`;
- vta-browser-plugin `637be40`;
- openvtc `c6a2bde`.

It found the following:

1. **Badges are a VTC feature: 30 `vtc/badges/*/0.1` draft tasks.**
   - A community badge, once accepted, becomes an Open Badges 3.0 credential, issued and signed by the **community** (VTI aa95c8368, #2501; `vtc-service/src/badges/credential.rs:86-99, 312, 357-375`).
   - Upstream prose in about eight places still says the badge group issues it, but the code is the authority.
2. **The member's agent needs nothing.** `vta-service/` has no badge code; the credential comes on the existing `credential-exchange/issue/0.1` (`vtc-service/src/credentials/delivery.rs:11-23`).
3. **No upstream wallet supports badges.** vta-browser-plugin, openvtc, pnm and cnm have none. Only the VTC's web member portal drives them, signed with a browser key the wallet delegated (`vtc-service/src/trust_tasks/oob_tasks.rs:74-81`).
4. **Holder tasks accept the member's own key** (`badge_tasks.rs:281-306`), so Keyring can send them as the identity it already signs community tasks with.
5. **`wall/show` takes a directory `entryId`** (TT `specs/vtc/badges/wall/show/0.1/payload.schema.json`). That is why the bubble lookup goes through the directory.
6. **Sharing outside publishes a lot, and unshare revokes nothing.** It exposes the membership DID, the badge, the community and the givers' notes (TT `awards/share/0.1/spec.md:202`; `awards/unshare/0.1/spec.md:77-79`). That is why the plan's rule is that nothing leaves the community.

## Decisions, and what they supersede

The research recommended:

- phase 1 = read and accept, behind a Developer switch, off by default;
- the Wallet card in phase 2, bubbles in phase 3;
- starting after the current rooms and SEDI work.

**Alberto, 2026-11-17 (relayed by the coordinator):** "lets also start executing on the members badges please so we can show badges, go on recommended but build in parallel and all together, not off by default, this should go out asap".

That supersedes the recommendation in three ways:

- **All three surfaces are built now, in parallel, and ship together**, instead of in phases.
- **They ship ON**, with a release kill (`remoteOff`) instead of an off-by-default Developer switch. The pattern is `sessionsPerIdentitySwitch.ts` (bifold #1022), and the kill is a one-line OTA.
- **They start now.** SEDI/KERI (b0) still goes first in the review queue.

The rest of the recommendations stand:

- holder side only;
- no sharing outside the community;
- the Wallet card, with the OB context bundled;
- kudos read-only;
- a written rule that badges never reflect vetting;
- a friendly note to upstream about the stale "group issues" text, which goes through Alberto.

## Open, for whoever implements

- **The OB `image` shape** in an issued credential (a URL or data), to be read from `credential.rs` before c0 renders it. The plan's rule is that the app never fetches it by URL.
- **Whether directory `query/0.1` can answer an `entryId` for an author DID.** If it can't, bubbles fall back to no chip. 62 checks before building the lookup.

## Later the same session: room-post chips on hold

62 checked at source (VTI 4abe40a2a, TT 4fddc096a) that the bubble lookup the plan assumed cannot be made:

- directory `query/0.1` returns only `{subject, fields}`, with no entryId (`vtc-service` `directory/read.rs` `query_by_did`; the TT response schema has `additionalProperties: false`);
- `entries/show` by DID needs `vtc.directory.admin` or `vtc.members.manage`;
- `wall/show` takes only an entryId.

The plan's fallback (no chip) applies, so chips are on hold for Alberto. The options are:

- (a) no chips this release (recommended);
- (b) the post carries its author's entry, with a check that the entry's projected DID is the author's, which works only for members who show their DID;
- (c) searching the member list, which is ruled out by upstream's spec and our own rule.

This supersedes the plan's earlier statement that chips ship with the rest.

**Decided, later the same session.** Alberto chose (a), in his words: "a". There are no room-post chips in this release. Badges show in the community's Badges section, on member cards opened from Members, and in the Wallet. He did not take up asking upstream for a member-callable wall-by-DID, so it is not raised.
