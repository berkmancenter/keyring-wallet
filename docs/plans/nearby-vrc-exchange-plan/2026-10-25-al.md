# 2026-10-25 — Security review, UI/UX review, and corrections against `main`

Companion to [`../nearby-vrc-exchange-plan.md`](../nearby-vrc-exchange-plan.md).
It records a security review of the plan (replay especially), the UI/UX lane's
review, and corrections found by reading `main` after keyring-bifold #471 merged.
Each section says what changed in the plan. It is not revised afterwards.

## Decision recorded — Nearby is optional

The product owner agreed that Bluetooth for VRC exchange is optional. The QR code
stays the default, every nearby screen offers it as an explicit button, and the app
never switches to it by itself. Applied in the plan's scope paragraph and §4.

## 1. Security review

The question asked was whether replay, or anything like it, is possible. The plan's
core holds: an ephemeral X25519 exchange with a commit-reveal short code (the
ZRTP/Bluetooth numeric-comparison pattern) defeats a remote man-in-the-middle as long
as people really compare the codes. The gaps were in what sits around that core.

### 1.1 Replay

| Gap | Why it mattered | Change in the plan |
|---|---|---|
| No lifetime on the session or its invitation | A recorded or leaked invitation could be accepted later, from anywhere, and the resulting connection would look like a nearby one | §2.2 item 8: the session ends 10 minutes after confirmation. §2.4: the invitation is single-use (`multiUseInvitation: false`) and expires with the session |
| The host did not check which invitation a `propose` arrived on | Before Phase 2's digest exists, any connection could claim to be the nearby one | §2.4: a nearby `propose` is honoured only on the connection whose `outOfBandId` is the session's invitation, from Phase 1 |
| The signed binding covered only `{context, t, exchangeId}` | A signature could be moved onto a different credential made by the same device key, or reflected as the other role | §2.4: the binding adds `role`, both relationship DIDs, the VRC digest and `issuedAt` |
| `t` was held only in memory | An exchange resumed after the app is killed (`resumeInterruptedExchanges`) would either skip the check or stall | §2.4: `t` is stored keyed by connection |
| iOS App Attest counters | Assertions carry a counter that this phone does not track per key, so a counter gives no freshness here | §2.4 says so; freshness rests on `t` and `issuedAt` |

### 1.2 The AEAD session

The plan had one key `k` for both directions and did not say how nonces are chosen.
With one key, a phone's own sealed message can be reflected back to it and decrypts
correctly. §2.2 item 7 now derives a key per direction (`h2j`, `j2h`), uses a strictly
increasing counter as the nonce, puts `t ‖ message type` in the additional data, and
rejects a repeated or out-of-order counter. §2.2 item 6 adds key confirmation
(`MAC_k("confirm" ‖ role)`) before anything sealed is sent, so a phone never sends an
invitation under a key the other phone has not proved it holds.

The commitment now covers the version and the host key
(`SHA-256("keyring-nearby-v1" ‖ EH ‖ nH)`). With only `nH`, a commitment was not tied
to the session's key or to the protocol version, so it could in principle be carried
into another session or a later version of the protocol.

### 1.3 Rubber-stamping

Identical codes and a **Match** button rely on people really looking. Usability
studies of compare-and-confirm pairing found people often confirm without
comparing, which turns a man-in-the-middle defence into a formality. §2.2 item 5
replaces it with picking: each phone shows its own code, the other phone shows three
choices, and the person picks the one on the other screen, in both directions. A
phone never shows its own code next to its own choices, because then a person could
pick by matching their own screen.

The alternatives were recorded in §2.2's "Rejected" paragraphs: one-sided
confirmation (a man-in-the-middle can send the passive phone a confirmation of its
own), and typing six digits (safer, but slower and harder with motor impairments).

### 1.4 Tracking and identity leakage

The advert was already clean: a random session id, a code tag, and 120 s on the
open screen only. One leak was not covered: a connected central may read the
operating system's GAP **Device Name** characteristic, which often holds a person's
chosen name. §2.3 now requires the GATT surface to expose no name, Phase 0 checks it
on each platform, and §6 lists it as a device proof.

### 1.5 Rate limits

A nearby attacker can start sessions over and over, hoping for one where a person
picks a code without looking (one chance in three per direction), or just to be a
nuisance. §2.2 item 8 caps the host at three sessions per minute, and a wrong pick
ends the session with no retry on the same keys.

### 1.6 Downgrade

The Trust Tasks framework requires a consumer to ignore an unknown `ext` namespace,
and `propose` 0.1 cannot mark an extension critical. So a responder that does not
know `ext.nearby` would silently accept a `propose` without it. That is fine here
because both phones have just run the Bluetooth session and each knows to require
the digest: enforcement is the responder's own policy (§2.4), and a nearby
connection with no digest is refused as `malformedRequest`. Phase 2's tests cover
the missing digest.

### 1.7 What stays open

The relay of a whole phone for a person who is not present remains open by design,
the same residual the locality plan prices as open. Ultra-wideband could later give
the two people a warning, never a claim (§3, last item).

## 2. UI/UX review

The UI/UX lane reviewed §4 against the app as it is on `main`. Its answers:

- **Where Nearby lives:** a third tab in `QRCodeExchangeSlider`, beside "My code" and
  "Scan", hidden where the phone cannot do it.
- **No badge, a layer row.** The contact screen already lists relationship layers.
  "Cards exchanged nearby · {date}" (or the "signed with secure hardware" variant)
  fits there and does not compete with the witness's "Confirmed in person". The
  earlier "Exchanged nearby · no witness" read as a warning about something the person
  did not ask for, so "no witness" is dropped. In-person wording is never used.
- **The code:** grouped digits, read digit by digit, enlargeable; the emoji tag
  always has a text name ("🦊🌵 Fox Cactus").
- **Pick-from-three** (§1.3) was accepted as clearer than Match/Doesn't match, since
  the person is asked to do one thing.
- **Android below 12:** hide Nearby, after checking the share of testers on those
  versions.
- **iOS permission text:** "Keyring uses Bluetooth to find a phone near you when you
  exchange cards or confirm a relationship."
- **The pre-flight sheet** says exactly what goes over the air.
- **Failure states:** "Keep waiting" / "Stop" after the app returns from the
  background; no automatic selection even with one phone listed; "Still looking?" at
  120 s; a cancelled biometric prompt sends nothing; a "can't exchange nearby" message
  for unsupported phones; "Use a QR code instead" always explicit; the app never
  changes the Bluetooth setting.
- **Timers:** the exchange's stall timers start at "Connecting…", never while people
  are still choosing a code.

All of these are in the plan's §4 and §3 status-store row.

## 3. Corrections against `main`

- **#471 added `upgradeRelationship`.** Confirming an existing contact nearby is now
  cheap and useful: no invitation crosses the radio, the phones compare the stored
  relationship DIDs under AEAD, and `ext.nearby` rides the upgrade `propose`. New §2.7,
  §4 ("Confirm nearby" in `RelationshipUpgradeSection`) and Phase 2.
- **The peripheral API is witness-shaped.** `respondToSensor()` serves a single
  witness turn. The host role needs a new, multi-turn API surface. Dependencies table
  and §3.
- **The chunking and retry logic lives in the witness server's central**, not in the
  peripheral. The phone's central re-implements it. §3.
- **The nearby crypto runs once, in JavaScript.** There is no tight radio deadline,
  so native code only moves bytes, and the parity fixture needs Hermes and Node only.
  §3 and Phase 0.
- **Verification goes through `HardwareSignatureVerifier.verifyEvidence`**, the same
  path VRC evidence uses, not a separate public-key check. §2.4 and Phase 2.
- **No hardware key** (Secure Exchanges off, an emulator): the plan did not say. It
  now proceeds and records "no hardware binding", with no hardware wording. §2.4.
- **iOS scanning** cannot filter by a UUID prefix: the joiner scans in the
  foreground with no service filter and filters in the app. §2.3.
- **Keyring-bifold #327 is stale.** It was last pushed 2026-10-07 and now conflicts
  with `main`, while `main`'s `LocalityPreflightModal` still asks for
  `BLUETOOTH_SCAN` and never `BLUETOOTH_CONNECT`. It is rebased or replaced before
  Phase 1. Dependencies table.
- **UWB is exposed to apps now.** `locality-plan.md` §2 says it is not. Apple's
  NearbyInteraction (U1/U2) and Android's `androidx.core.uwb` both range to a peer.
  Neither runs on every phone and neither result is checkable by a third party, so it
  stays out of this plan, noted as a possible hint for later. "Not in this plan".
