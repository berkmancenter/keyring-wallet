# 2026-10-11 — Why the nearby exchange is shaped as a rendezvous, not a locality claim

Companion to [`../nearby-vrc-exchange-plan.md`](../nearby-vrc-exchange-plan.md).
This document records the reasoning behind the plan's first version. It is not
revised afterwards.

## The request

The product owner asked for a VRC exchange over Bluetooth "similar \[to\] how we do
VRC and witness, but now without the witness, which should be easier", and keeping
"the same principles like proximity, security, etc."

## Finding 1 — "proximity without a witness" conflicts with a settled decision, so the plan narrows what it claims

[`locality-plan.md`](../locality-plan.md) §2.1 closes witness-free co-presence: "not a
weaker option; it is not an option". §11 records it as "Not open, recorded so it is
not reopened". The reasoning is in locality companion 2026-08-18-bam, Finding 15:

- the observers are exactly the interested parties;
- so two parties can produce any proximity transcript by agreement;
- hardware attestation only raises that to "two genuine attested apps produced this".

A Bluetooth exchange between two phones is that case precisely. So the plan does not
reopen §2.1. It keeps "proximity" in the sense that matters to the two people: they
reach the right phone, and a code they compare by eye defeats a remote attacker. It
makes no claim to anyone else and emits no `locality*` member.

The plan also uses what §2.1 itself says survives without a witness: "ceremony (live,
simultaneous, challenge-bound) and device (hardware attestation)".

**Superseded:** nothing in this plan. A reader who expects "Confirmed in person" for a
nearby exchange should read this finding.

## Finding 2 — three shapes were considered; the rendezvous comes first

1. **Rendezvous (adopted for Phases 1–2).** BLE replaces the QR code. A code
   confirmed by both people authenticates the BLE session. The invitation travels
   under that session, and the ceremony runs through the mediators as it does today,
   bound back to the BLE session (plan §2.4).
   - **Smallest change:** the ceremony, the evidence, the consent and the carriage are
     all unchanged.
   - **Reuses** the peripheral module that is already proven on devices.
   - **Adds** the authentication a QR code only gets from the physical act of showing
     the screen, and makes it explicit.
2. **Offline carriage (deferred to Phase 3, conditional).** The whole exchange
   travels over GATT, with no network. It is real value where there is no
   connectivity. It costs a new carriage, chunked Trust Task documents, and a contact
   that cannot be messaged until both phones are online. That is a product decision,
   not an engineering default, so it is a question for the product owner.
3. **Phone as witness (rejected).** One phone plays the witness's sensor role for the
   other. It fails twice:
   - It is still two interested parties (Finding 1).
   - The locality plan rules out "phone-as-sensor" because "it inherits
     background-execution restrictions and raises the question of who attests the
     *sensor*" (§5.6).

## Finding 3 — the phone has no BLE central today; that is the main build item

The VRC and trust-tasks code at bifold `95371d9f` has the phone only as a BLE
**peripheral**: it advertises and serves GATT (`react-native-locality-peripheral`).
The only central is the witness server (BlueZ `node-ble`, or noble on macOS). The only
`localityTopology` value is `'witness-anchored'`.

A joiner role must therefore be added, either with `react-native-ble-plx` or as a
central inside the native module. The locality survey (2026-07-20-bam §8.3) set
ble-plx aside only because it lacks peripheral mode; that does not apply to the
joiner. Phase 0 makes the choice on measured numbers.

## Finding 4 — the code is a commit-then-reveal SAS, and it carries no proximity weight

The locality plan keeps short authentication strings (SAS) only as channel
authentication, "**zero locality weight**". It notes that two people on a video call
read codes to each other trivially (§2). The nearby plan uses the SAS for exactly
that: an application-layer, commit-then-reveal code over an unbonded GATT session, as
the July survey specified (§4.4, §8.5).

OS Bluetooth pairing is not used. It would create a persistent bond, and the OS, not
the app, owns its code.

## Finding 5 — existing work to fold in

keyring-bifold #327 (open draft) adds `bluetoothPermissions.ts` with
`BLUETOOTH_ADVERTISE` and `BLUETOOTH_CONNECT`, plus a typed "permission missing"
diagnosis. The joiner role needs `BLUETOOTH_SCAN` as well. The plan declares it with
`neverForLocation`, so Android 12+ does not treat it as location access. Below API 31,
scanning still needs location, a gap the locality plan already records (§10.3).
