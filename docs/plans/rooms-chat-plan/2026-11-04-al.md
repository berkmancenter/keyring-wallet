# Rooms chat plan: reasoning, 2026-11-04 (al)

**Plan:** [`../rooms-chat-plan.md`](../rooms-chat-plan.md).
Everything here comes from reading code and #1027's text. Nothing was run except the cost measurement described in #925.

## Findings and decisions

### 1. The parent

`rich-messaging-plan.md` isn't the parent, though it looks like one. Its non-goals say "Group chat. It belongs to the rooms subtask", and it's about the one-to-one wire format. The group work's home is `openvtc-rooms-plan/rooms_group_messaging_subtask.md`, but its §5.3 event body (`org.openvtc.msg/1`) is a different design: an event inside the seal, not record members. So this is a sibling plan, linked from both. It replaces that subtask's conversation event body for rooms.

### 2. Building before #1027 merges

The decision was to treat the text as good to go and not fall behind, so A and C don't wait for its release.

Why this is safe, as checked: no released agent can seal these members (`room_act.rs` `BODY_MEMBERS` at `vta-service-v0.74.0`) and no room lists them ("No room lists them by default"). So A and C run against no real records until an agent release lands. Getting one wrong costs an OTA, and nothing written depends on it. The exception is the untitled MAY, which every Keyring post relies on; the plan singles it out in §8.

Rejected: waiting for #1027's release. It would delay the adoption clock that rollout step 1 needs, and an older reader is the one thing that shows these records wrong.

### 3. What A includes and leaves out

Rule (1), refusing an unknown member, could look like part of being "reader-safe". It's left to B: refusing changes what's shown, and it needs an allow-list.

A hides a withdrawn message rather than drawing an empty bubble, without waiting for C, since an empty bubble is what "shown wrong" looks like. A rewrite by another member could hide a message this way on a first-time read. The draft accepts that limit for first-time readers, and `createdBy` in D narrows it.

Order is left alone in A. The draft's order needs `createdAt`, which only D brings. Using `writtenAt` alone would let a sender's clock move posts, which our chat never allows.

### 4. Re-reads of #1027 today, and what each changed

- **`894c332f`:** the plan's first reading.
- **`4b977952`:** brought `createdBy`, `browse` 0.4, `read` 0.2, `get` 0.3, the image fields, one-write reaction changes, and ordering by `createdAt`.
- **`757dda98`:** added *Which DID document*. A question I'd been holding, what a reader does with records stored before `bodyStoredAt`, is answered: "it uses the current document, and treats a proof that fails there the same way". The earlier position, that the rotation rule couldn't apply to older records, is superseded: it applies by falling back to the current document, and a failure is the placeholder. Also superseded: assuming the anchor would be `createdAt`. It's `bodyStoredAt`, since an edit writes a new body under what may be a newer key.

### 5. Stage 1 findings that carry into stage 2

- Credo's `WebVhDidResolver` calls `resolveDID` with no `versionTime`, and it maps most failures to `notFound` or `invalidDid`. So stage 2 needs more than `resolveDidDocument`. Read from `@credo-ts/webvh` at the pinned version, not run.
- Only our own 5 s timeout can be told apart as temporary, which is why `document-timeout` exists.
- A verify is synchronous work on the JS thread. Noble builds its tables on the first one, so stage 1 waits 10 s before its first check, leaves 1 s between checks, and doesn't verify bodies over 32 KiB. Stage 2 can't defer the same way, since the rule is "before showing". That's the main unsolved design question in B, and a phone's number decides how hard it is.

**A native verify, considered and not chosen for stage 1:** Askar could verify natively and avoid noble's tables, but it means a different path from the file check, with new key-handling surface, for a count. It's an option for stage 2 if a phone's number is bad.

### 6. What the chat doesn't have

Reading `modules/chat` showed there's no delete-for-everyone (`fold.ts:19-20`), no tap-to-jump from a quote, and no delivery or read receipts. So "withdrawn" in C is new to Keyring, with no chat component to reuse, and the plan's non-goals rest on that code, not on what a chat might be assumed to do.

### 7. What the note line and #900 become

`isNote` stays the single decision, as #923 was built for. The items to flag are untitled notes, which #900 and #923 don't have words for since both print a title, and removed-note markers, whose words stop being accurate once a retraction may be a message or a reaction. Neither blocks #923.

### 8. Found in review of the first draft of the plan

- **A manifest with a new member loses its file on a shipped reader.** `parseFileManifest` refuses any member it doesn't know, so #1027's `width`, `height` and `preview` would turn a file record into a record with no file. Added to A.
- **Three answers, not two.** The first table's "nowhere" for a reaction didn't work with a two-way `isNote`, since `isChatPost` is its negation. A now has one function with three answers.
- **A titled message.** The first table sent `kind: message` to chat even with a title. On an open room that would have lost it, because `leftOut` skips by listing title and can't see `kind`. Until listings carry `kind`, a titled message goes to Notes. Rejected: reading every titled record on open rooms again, which costs a read per note to serve a case the draft says SHOULD NOT arise.
- **From the mocks:** `ReactionBar`'s `selected` holds one value, a placeholder can't use `kind`, Delete for me doesn't fit a room, and an edited note stops moving #923's line once `createdAt` arrives.
- **#1027 left GitHub's draft state** at `757dda98`. It's open for review and not merged, so nothing in the approach changes.
- **The note editor would drop `kind`.** It writes `{title, body}`, so editing another client's record breaks *What a new version keeps*. Writing it only in E would leave the gap open from the day a room holds such a record, which can come before Keyring's E, so A turns Edit off on those records and E lifts that.
- **#1027 merged** as `565f8d32`, a squash. Every file under `specs/` is byte-identical to `40257b38`, and `40257b38` changes no record-format text from `757dda98`, so the plan's reading stands. The specs still say `status: draft`.
- **Reaction limits run on the body as written.** Building slice A showed that `toInertText` removes three of the line terminators the draft forbids, so a check on its output would pass a value the draft refuses.
- **The agent's path.** I'd expected a `trust-tasks-rs` release first, then VTI moving to it, then a tag. That was wrong: VTI vendors spec bundles and implemented `seal` 0.3 directly (VTI #2449), with `trust-tasks-rs` still at 0.37.2. So a crate release isn't a useful signal, and the plan's watch now follows VTI's three stages. #2449's `!` marks Rust API changes only (`FileManifest`, `ProfileEdit`), not anything on the wire.
