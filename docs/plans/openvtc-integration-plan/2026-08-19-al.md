## A. Presentation assembly and the verifier's pairing algorithm land

`outcomeEvidence.ts` (bifold `be7a4ec0`) implements both halves the cred-spec's
Outcome Interpretability section demands:

- **Holder**: `assembleVwcPresentation` signs a VP over the stored VWC and
  attaches the retained initiating/terminal pair, located by the credential's
  own `taskContext`. It throws when either half is missing — the spec says a
  holder MUST include matching evidence, and shipping a hollow bundle would
  misrepresent one. The evidence travels *beside* the VP rather than embedded
  in its JSON-LD: task documents are JCS-secured artifacts with their own
  proofs, and embedding them in an RDF-canonicalized presentation would re-open
  the vocabulary trap closed twice this week (witnessedExchangeContext, §G of
  [2026-08-18-al.md](./2026-08-18-al.md)).
- **Verifier**: `verifyVwcPresentationBundle` runs the pairing checklist and
  returns an `EvidenceVerdict` — never a bare boolean. `credentialValid` and
  `completionEvidenced` are independent axes (a credential can verify perfectly
  and still evidence nothing); `failures` name what broke; `residuals` name
  what the verification deliberately does not settle (witness identity
  legibility, revocation), so no caller mistakes silence for coverage. The
  checks: the initiating document's `id` equals `taskContext` (locates);
  `taskDigestMultibase` reproduces over it (binds — a counterfeit with the
  right id fails here); the terminal's `threadId` equals
  `initiating.threadId ?? initiating.id` (a minted threadId cannot orphan
  evidence, because pairing runs through the initiating document); the
  terminal is a success `#response` — an error response is failure evidence,
  never completion; and the terminal's REQUIRED proof verifies under its
  issuer.

The unit suite exercises each check under its own tamper (counterfeit
initiating bytes with the id kept, minted-threadId pairing, wrong-thread /
error / proofless / bad-proof terminals), with the digest math real and only
the credential crypto mocked.

**Proof**: the ceremony's witnessed branch now self-checks after every
completed session — assemble the bundle from retained evidence, verify it
against a self-minted challenge, log a gateable marker. The witnessed
two-device e2e gates on that marker and passed (run 22, prod mediator,
2026-08-19): both parties completed the ceremony *and* the holder-side
assembly and verifier-side pairing ran end-to-end on real documents.

## B. Three conformance corrections the assembly work forced

Writing the verifier against the spec text exposed three places the shipped
witness path was close-but-not-conformant. All corrected in the same commit,
on both the wallet and witness-server sides:

1. **The task digest excludes the top-level `proof`** (framework 0.3, task
   digest). `taskDigestMultibase` now strips `proof` before JCS. Superseded
   position: the VWC's `taskDigestMultibase` was computed with plain
   `digestMultibase` over the session document as transmitted — which happened
   to match only because the session request is unproofed today. The §A
   proof-invariance test pins the corrected behavior.
2. **Digests compare as decoded bytes, never encoded strings**
   (`digestBytesEqual`, constant-time over the decoded multihash). Superseded
   position: string equality on the multibase form — correct only while both
   sides pick identical base encodings, which the spec does not require.
3. **The terminal of an outcome pair is the *latest* response on the thread.**
   `findOutcomeEvidencePair` sorted ascending and took the first response —
   but a witness session thread carries two (`session#response` challenge,
   then `submit#response`), so the pair returned the challenge as "terminal".
   Undetected until now because nothing consumed the pair; the §A self-check
   is exactly the consumer that catches this class.

## C. Two build-hygiene notes, recorded because they will recur

- The self-check hook reaches `outcomeEvidence` via an inline `require`: a
  static import would cycle (outcomeEvidence imports `getTrustTasksService`
  from ceremony) and a dynamic `import()` re-creates the Metro split-bundle
  failure from §A.3 of [2026-08-18-al.md](./2026-08-18-al.md).
- The delivery-side fire-and-forget (§G's deadlock fix) makes ceremony unit
  tests race the assertion — they now flush the event loop after triggering
  delivery. Any future test asserting on post-consume sends needs the same.

### Finding: the contact's Witnessed badge does not light up under v4

Confirmed on both platforms (screenshots in `e2e/artifacts/shields-missing-*`).
The badge (`ContactDetails` → `getWitnessCredentialsForSubject`) keys on a
stored VWC whose `credentialSubject.id` equals the **peer's** relationship
DID — but the v4 ceremony is per-party: each wallet submits its *own* VRC,
receives a VWC naming its *own* DID as subject, and nothing delivers that VWC
to the peer. The legacy shared-session flow delivered cross-party VWCs, which
is what the badge was built against. The run records this as an observation,
not a failure: the VWCs are correct per spec; what is missing is **VWC
sharing**. Two candidate mechanisms, undecided: the issue leg carrying the
sender's VWC alongside the VRC (cheap, but bloats the issue payload and
duplicates what a presentation proves), or a peer-to-peer application of the
presentation flow (§A) — the holder ships VWC + outcome evidence and the
peer's wallet verifies the bundle before showing the badge, which exercises
the verifier path for real. This is design work for the plan, recorded here
so the badge's silence is not mistaken for a ceremony defect.

Witness-side observation from the same run's logs: VRC proofs still sign
eddsa-rdfc-2022 (`getVrcJsonLdProofOptions`) while all task documents sign
eddsa-jcs-2022 — the Decisions 10–13 proof-set migration remains the pending
unifier.

## F. VWC sharing adopted as subtask step 7 — presentation-based, not issue-leg carriage

The §E gap gets its design: a third relationship task,
`vrc/relationships/witness-share/0.1`, carrying the holder's presentation
bundle (VWC in a signed VP + the retained outcome-evidence pair) to the
counterparty on the exchange thread. Decision and the rejected alternative
are recorded in the step itself (subtask §9 step 7). The deciding argument:
a bare VWC pushed on the issue leg arrives without its outcome evidence —
the exact "verifies as a credential, proves nothing" failure retention
exists to prevent — while the presentation bundle makes the receiving
wallet run `verifyVwcPresentationBundle` for real, so the Witnessed
indicator becomes earned by verification rather than granted on receipt.
Witness-side cross-distribution (the legacy mechanism) is not revived:
holder-controlled disclosure is the cred-spec's model, and it is the
per-party session's point.

Also noted from the M4 timing: of ~86 s consent-to-verified, roughly half
is PickUpV2 poll idle (10 s interval × five-plus inbound hops per side).
Adaptive polling during an active exchange is the obvious lever —
**backlogged deliberately** (Alberto, 2026-08-19); not part of step 7.
