Author: Brendan A. Miller (bam). Changes to
[`../openvtc-integration-plan.md`](../openvtc-integration-plan.md) §4.5 and §4.6,
made while writing the [locality plan](../locality-plan.md), whose own companion

Verified against `dtgwg-cred-spec` PR #18 (open, updated 2026-08-18) and pinned

## 1. §4.5 said JCS was an auth-document concern. It is now a credential one

**What §4.5 said.** Upstream #880 made REST `/auth/` require a DI-signed
`auth/authenticate/0.1` under `eddsa-jcs-2022`; Keyring ships `eddsa-rdfc-2022`;
the JCS variant is "the *simpler* sibling"; bounded new work, scoped to Phase D.
All still true, and all of it about the **task layer**.

**What changed.** [cred-spec #18](https://github.com/trustoverip/dtgwg-cred-spec/pull/18)
— Alberto's, ours, open — proposes for **DTG credentials themselves** that
`proof.type` MUST be `DataIntegrityProof` with the suite named in
`proof.cryptosuite`, and that the RECOMMENDED suite is **`eddsa-jcs-2022`**:

> its JCS (RFC 8785) canonicalization requires no `@context` resolution at
> verification time, so credentials remain verifiable offline (including
> credentials formed in person and synchronized later), and it is the same
> canonicalization this specification uses for `digestMultibase` — a digest and
> a proof over one credential cannot disagree about the credential's canonical
> form.

with `bbs-2023` named as the selective-disclosure path, issued as a **proof set**
beside it because "an `eddsa-jcs-2022` proof cannot yield" an SD base proof.

**Why this belongs in the plan and not only in a tracker.** §4.5 as written
would lead a reader to scope the JCS signer as an auth-only component and be
surprised later. It is now plausibly the signer for everything we issue. The
edit says so, points at where the Keyring-side review lives, and states what is
*not* blocked: `auth/authenticate` needs the JCS signer regardless of how #18
lands, so Phase D's scope is unchanged either way.

**What it does to `CRYPTO_SUITE_FOLLOWUP.md` Decision 3.** That decision chose
`eddsa-rdfc-2022` on 2026-07-14 and recorded the JCS variant as "considered and
rejected", justified as matching "Keyring's DTG spec feedback §3". Our own later
proposal now points the other way, which makes the *justification* superseded by
us rather than overtaken by someone else. I did not flip the decision — nothing
has merged, and #18 says RECOMMENDED, not MUST, so we are conformant either way.
I added a **"Decision 3 under review"** section carrying the direction, a third
argument (below), the reversal criteria, and the cost, with the original decision
text untouched as history.

**The cost, so a reversal is not mistaken for a flag flip:** the suite itself is
cheap (pure-TS JCS already lives in `@bifold/vrc-contexts`, and Decision 5 Option
B already matches on `type` **+** `cryptosuite`, which is exactly the agility #18
asks for), but dual-verify becomes **triple** with no sunset, since stored
credentials are never re-signed. And the `rdf-canonize` patch leaves the
credential path *only* if we never issue SD proof sets — `bbs-2023` is
RDF-canonicalized, so the dependency returns with selective disclosure. Worth
stating because it is the kind of saving that gets booked twice.

## 2. A third argument for JCS that #18 does not make

#18's two arguments are about verification. This one is about **authoring**, and
it came out of building `ref-06p`.

Under RDF-canonicalized suites, credential members whose terms are undefined in
the `@context` are **not secured by the proof** — in two ways, both measured:
JSON-LD safe mode (which the DI signing path uses) refuses to canonicalize at
all, and with safe mode off the members drop to **zero quads** while remaining
visible in the JSON. The credential verifies; the evidence in it was never
signed.

That is a structural penalty on **extensibility**, and DTG credentials are the
extensible kind: `witnessContext` is an open object of three optional strings
that issuers are expected to extend, and the evidence-axes direction adds members
over time. We found it in our own tree — `witnessedExchangeContext.ts` defines
`localityVerification` but none of the members nested inside it, latent only
because the sole locality provider is a null one.

**Offered as a comment on #18, not as a commit to it.** The argument supports a
conclusion the PR already reached, so pushing it into an open review buys nothing
and costs review time; a later revision can fold it in if the editors want it.
Drafted at
[`tsp-reference/ref-06p-locality-binding/PR-CANDIDATE.md`](../../../tsp-reference/ref-06p-locality-binding/PR-CANDIDATE.md),
including a suggested Security Considerations paragraph. **Not posted** — it is
Alberto's PR and the standing rule is that nothing reaches an external repository
without his review.

## 3. §4.6's three open questions are now decided — by us

§4.6 listed three things as open and blocked on nobody: whether VRC and VWC move
to `bbs-2023`, whether the VWC carries `digest` or a commitment, and whether our
session challenge adopts the ZKP task force's canonical transcript.

All three are now decided, in the same session and for one reason: **ZKP
presentation is a requirement, not an aspiration.** The specification we edit
says implementations SHOULD make it the default, and a design that defers it
ends up shipping credential shapes that cannot support it. The decisions are
recorded in `CRYPTO_SUITE_FOLLOWUP.md` (Decisions 10–13) and worked through in
the [locality plan's companion](../locality-plan/2026-08-18-bam.md); the
one-paragraph versions are now in §4.6 itself.

**What changed my own position along the way**, since I argued the opposite
earlier the same day: with selective disclosure out of scope, dropping RDF
canonicalization entirely is clearly right — the legacy compat argument is void
(pre-production, and every VRC/VWC expires in 7 days). With it in scope, RDF
cannot leave, because `bbs-2023` is RDF-canonicalized and is the only path to
member-level disclosure. The distinction that survives is that **"keep RDF for
bbs" is not "keep the legacy suites"**: `Ed25519Signature2018` and
`eddsa-rdfc-2022` issuance still go, along with the negotiation ladder that
exists to serve a fleet we do not have.

The second decision needs its boundary stated precisely, because "commitment
instead of digest" would be wrong as a general claim: cred-spec's
`credentialSubject.digest` is REQUIRED and stays. What becomes a commitment is
the *evidence summary*, following the ZKP TF's witness-seat pattern — commit
over the public parts rather than disclose them. The locality assertion is the
worked example, and the sharpest instance is the device key id, which now stays
on the artifact side entirely.

The third has a locality consequence worth recording: the radio binding commits
to five values rather than a bare nonce, which is the same direction as the
canonical transcript (`witness/session` 0.1 already anticipates being superseded
by one, and the ZKP TF carries "a bare nonce is insufficient" as a failing test).
Shaping it as {canonical transcript fields} + {locality extension} means
ratification adds members rather than forcing a re-cut; the context string is
versioned and `ref-06p` freezes the binding as a fixture so the change is visible
when it happens.
