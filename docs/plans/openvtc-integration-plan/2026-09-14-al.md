### Correction: first contact was a Credo option all along (2026-09-14)

ref-15 finding 1 ("the inviter gets no connection from the invitee's first
v2 message — Credo only looks up, never creates") and ref-17 finding 3 (the
same, on the mediator, called a deployment blocker) described the

DID when the invitation is reusable. Found while wiring the mediator half of
V2 step 4: the mediate-request "refusal" the earlier status predicted never
had to happen.

sentence in the V2 status block, and the plan's reading of ref-15/ref-17
finding 1/3. Both rung READMEs carry the correction inline (the measurement

### The v2 mediator is a second mediation record (2026-09-14)

Design adopted for V2 step 4 and §7.1 rule 2, implemented on the worktree:

- `mediator-server` in v2 mode (`yarn mediator --didcomm-v2`; env
  `MEDIATOR_DIDCOMM_VERSIONS=v1,v2`) sets the first-contact option, uses
  `did:peer:2` for its OOB 2.0 DIDs, and mints a **reusable**
  out-of-band/2.0 invitation beside the v1 legacy one. Its routing DID is
  self-derived from its routing key and its HTTP endpoint
  (`getEffectiveMediatorRoutingDid` falls back to the first endpoint when
  there is no `ws://` one), so no WebSocket transport was added: the wallet
  polls with Pickup 4.0 exactly as it polls v1 with Pickup 2.0. The
  lifecycle script writes both invitations into `app/.env`
  (`MEDIATOR_URL`, `MEDIATOR_V2_URL`), the v2 one blank when v2 is off so a
  stale invitation cannot outlive a restart.
- The wallet, with the developer flag on and `MEDIATOR_V2_URL` baked in,
  provisions Coordinate Mediation 2.0 **once** after agent start
  (`provisionV2Mediation` in `@bifold/core` `trust-tasks/v2Routing.ts`):
  accept the invitation with `getRouting({ useDefaultMediator: false })`
  (ref-17 finding 1 — the v1 default cannot route a `did:peer:2`),
  `provision()`, then `setDefaultMediator(previous)` (ref-17 finding 2 —
  the newest grant would otherwise become the default and move every v1
  invitation's route). The v1 mediator remains `selectedMediator` and the
  default; nothing about existing connections changes. A failure is logged
  and the wallet stays on v1.
- Two pickup loops: the existing Pickup 2.0 loop against v1, then Pickup
  4.0 against the v2 record — in that order, because the credo patch that
  stops every running loop before a v1/v2 start (the anti-stacking guard)
  does not run in the v4 case. `configureMessagePickup` restarts both on
  every foreground resume, so the order is encoded there, not left to
  callers.
- v2 invitations route through the v2 record by id (`getRoutingForV2`),
  unmediated when there is none — never the v1 default. Applied at both
  ends: `createRelationshipInvitation` and `connectFromInvitation`.

Rejected: replacing `selectedMediator` with the v2 invitation (the earlier
§7.1 rule 2). It would have moved a wallet's v1 routing to a mediator that
speaks v1 too, but the point of §7.1 is that no existing connection changes
mediator; two records is what ref-17 measured and it costs one extra poll.

Not done: the witness-server does not enable `didcommVersions: ['v1','v2']`
yet. With v2 on, a bare `createInvitation({ label })` mints a **v2**
invitation (Credo infers v2 when there are no handshake protocols,
attachments or routing) — the witness's two `createInvitation` calls would
change meaning, so that is its own step with its own test pass (the
witnessed variant of V2 step 5).

**B7, first simulator result (2026-09-14): the 0.7 hop could not start an
agent on a device.** Every unit gate was green and the iOS app died at
`agent.initialize()` with `Error during call to 'onInitializeContext' method
in module 'didcomm'`. The cause chain (logged from a new try/catch around
initialize, at info level — on iOS dev builds console.error is captured by

creating key <- CredoError: Could not encode data to utf8 string <- Error:

round-trip), verified in Node against valid, invalid and non-fatal input;
the iOS onboarding probe then completed and the agent initialized. Recorded
in the subtask's V1 section as the fourth breaking change of the hop.
Candidate upstream note: Credo's React Native package could document the
polyfill requirement (or ship a decoder that honours `fatal`).

launched app, its activity paused, and Doze blocked the app UID's network

dozed, which made it look like a network or Wi-Fi problem for two attempts

disabling Doze put the JS load at ~5 s. Neither quirk is a Keyring or Credo

Findings so far, one per attempt:

1. **iOS markers cannot be read after the fact.** The simulator's unified
   log does not persist the app's info-level lines; `log show` minutes
   later returns only the last few seconds (the earlier same-day probe only
   worked because it read within a minute). The harness now starts
   `log stream` into a file at session creation (`startIosLogCapture`) and

   Android is.
2. **The iOS Developer toggle tap did nothing.** The row carries the

   wallet restarted with the flag off (the new diagnostic line
   `[TrustTasks:V2Mediation] not provisioning: flag=off, MEDIATOR_V2_URL=set`
   is what settled it — the build was right, the flag was not). The TSP
   suite is Android-only, so this path had never run on iOS. Fixed by
   making the row's `onPress` toggle the switch. With it, iOS provisioned

3. **Accepting a non-VRC v2 invitation sends nothing.** Both wallets
   accepted the witness's out-of-band/2.0 invitation and navigated to Chat,
   but the VRC connection handler only acts on relationship goal codes, and
   v2 has no handshake — so the witness never learned either wallet
   existed (0/2 participants). The v1 flow never needed a first message
   because DID Exchange itself was one. Fix under test: on any v2 invitation
   we accepted that is not a VRC one, send a trust ping with no response
   requested as the first authenticated message, so the inviter's
   connection materializes and its follow-up (the witness announcement)
   can reach us. Credo's snapshot has no trust-ping 2.0; the v1 ping rides
   the same v1→v2 normaliser that carried issue-credential 2.0 in the
   afternoon run.

4. **The witness leg over v2 works; the ceremony then hit a Credo 0.7
   change, not a v2 one.** With the trust ping as first contact, both
   wallets' connections materialized on the witness, the announcement came
   back over BasicMessage 2.0, the session opened, the challenge arrived
   and the presentation was submitted — all as v2 envelopes — and the
   witness rejected it: `challengeMismatch`. A diagnostic added to the
   witness (it had swallowed the verification error) showed the signature
   verified and the failure to be Credo 0.7's new holder-binding rule,
   "Presentation does not authenticate the credentialSubject of one or
   more included credentials". Keyring's VRC presenter is the credential's
   *issuer*; the subject is the counterparty's relationship DID, so that
   binding never holds by design, on v1 as much as on v2 — the witnessed v1
   suite had simply not been run on the 0.7 snapshot yet (B7's device half),

   wallet's own outcome-evidence self-check too. Fix: the existing core
   patch gains an opt-out, `verifyCredentialSubjectAuthentication: false`

   call sites (witness task sessions, the legacy witness path, the wallet's
   outcome evidence) with the rationale beside each; party membership is
   what those checks rely on. Lesson kept: `yarn patch-commit -s` writes a
   patch containing only the current edit — it replaced the 45 KB core
   patch with a 2.5 KB one. The root mirror still held the full patch; the
   two were concatenated (the new hunks touch files the old ones do not)
   and both copies replaced before reinstalling.

   Side observation, not yet acted on: on the witness leg the wallet's very
   first Trust Task document was refused `wrongRecipient` — the witness
   rotates its DID for reusable v2 invitations (`from_prior`), and the
   wallet had not seen the rotation when it addressed that document to the
   invitation DID. The ceremony that followed used the rotated DID and
   worked. Candidate handling: do not send documents on a freshly accepted
   reusable v2 invitation until the inviter's first message has been
   processed, or have the witness accept the pre-rotation DID as its own.

### Plan added: the TSP envelope over a v2 connection (2026-09-14, night)

Asked whether today's v2 work uses TSP: it does not. `selectCarriage` gives
a v2 connection the DIDComm v2 binding unconditionally, and TSP is only
chosen on v1 connections with the developer flag on. Asked next for a plan
to carry the TSP envelope over v2 connections the way it rides v1; written
as phase V2T and steps T1–T6 in the subtask.

**What Brendan's work already abstracts, and what it does not.** Alberto
recalled that Brendan may have abstracted this part. Checked against bifold
history: Brendan extracted the `Carriage` port (`c3311a37`, 09-01) and built
`TspCarriage`, the TSP ports and `credo-tsp-adapter` behind it (`3b3d8b3f`,
`45769d55`, `11739098`, `908a7805`, 09-02). That port is why V2T is a small
phase: documents never see the transport. It does not make TSP independent
of the DIDComm version underneath, because the adapter and the carriage
still assume v1 peer DIDs (change 1 and change 3 in V2T). The parent plan's
§4.2 / §5.2 envelope-format resolver (`TSPTransport` discovery) is designed,
not built. `vta-carriage_subtask.md` works on a different axis (reaching a
counterparty's VTA delegate, with its own discovery ladder) and does not
cover TSP over v2. Brendan's open plan PR (keyring-wallet #52, embedded VTA)
refers to the carriage port but proposes nothing on this either.

**The finding that sizes the work.** The key mismatch in V2T change 1 is
the substantive one: on a v2 connection Credo publishes a separately
generated X25519 key as the DID's `keyAgreement`, and the adapter's
receiving side would derive a different key from the Ed25519 signing key.
Without that change a TSP envelope over v2 cannot be opened at all, so
"mostly a change to carriage selection", as first described to Alberto, was
too optimistic. The adapter change and the rotation-tolerant sender check
are required alongside the selection change.

**Rejected: a v2-native TSP message by default.** Adding a new message
class up front would be the safe-looking choice, but the C14 run showed
Credo's normaliser carrying attachment-bearing v1 messages over v2, and
keeping one message class keeps one inbound handler on both the wallet and
the witness. The plan keeps the existing class and lets T2 measure whether
the envelope bytes survive; the v2 class is the fallback, not the start.

**T1 exists because of this session's evidence.** Every simulator failure
today came from something the unit gates could not see (the `TextDecoder`
option, the holder-binding rule, iOS automation). The TSP suite has not run
on the snapshot at all, so it runs first, before any V2T change, to keep a
hop regression from being misread as a v2 problem.
