## A. Step 7 lands: witness-share, verified before the badge

`vrc/relationships/witness-share/0.1` (local spec staging,
`witnessShareSpec.ts`; bifold commit on `feat/trust-tasks-integration`)
carries the holder's presentation bundle — VWC in a VP bound to
`{challenge: exchange id, domain: vrc:witness-share}` plus the retained
outcome-evidence pair — to the counterparty on the exchange thread, proof
REQUIRED. The receiver runs the complete Outcome Interpretability pairing
(document proof under the sender's relationship DID, VP under the expected
challenge/domain, credential valid AND completion evidenced, subject = the
sender's relationship DID, `parties` naming both) and only then stores the
VWC and receipts it; every failure is a `trust-task-error` and nothing is
stored. No UI change was needed: `ContactDetails` already keys the
indicator on a stored VWC whose subject is the peer's relationship DID,
which is exactly what a verified share delivers.

Discovery became **symmetric** — the responder now queries at acceptance —
so both sides hold the peer's `supportedTypes`; the share is gated on the
peer advertising the type (bounded wait for an in-flight answer, silent skip
otherwise). A design detail settled in code: a failed self-check of one's
own bundle *withholds* the share rather than shipping what the peer would
refuse.

**Proof.** Unit: six tests — conforming bundle stored and receipted; one's
own VWC bounced back refused; error-typed terminal refused; forged
initiating document refused on the digest; idempotent redelivery; receipt
round-trip. Live: the witnessed simulator e2e (run 32, prod mediator) gates
on four witness-share markers (sent → verified and stored → receipt sent →
receipt matched) **and the Witnessed badge on both contact screens** —
green. The did:peer:4 cross-party concern from §E of
[2026-08-19-al.md](./2026-08-19-al.md) did not materialize: witness
connection DIDs travel in long form, so the terminal document's proof
verifies on a wallet that never met the witness.

## B. What the e2e ladder caught (runs 23–32), recorded because they recur

1. **Retention tags by the BASE type URI.** `TrustTaskDocumentRecord` strips
   the `#response` fragment, so a lookup by `…#response` finds nothing, and
   an issuer-only idempotence check on `trust-task-discovery` matches one's
   own *answer* to the peer's query — the responder concluded it had already
   queried and never learned the peer's types (run 24). Both lookups now
   match on the document's own `type`. Rule for future legs: query the base
   URI, filter on `document.type`.
2. **A response schema must carry no fragment-bearing `$id`.** ajv throws on
   `"$id": "…#response"`, which made every receipt consume die silently;
   the package's own response schemas carry no `$id` — mirror that exactly.
   The receipt handler now warns on any non-handled outcome.
3. **Harness navigation, two shapes.** On one platform the Contacts row
   opens the chat (details sit behind `ContactMenu → View Contact`); on the
   other it opens Contact Details directly. `openContactDetail` detects
   which. And `ContactDetails` declares its testIDs *bare* (no
   `com.ariesbifold:id/` prefix) — the shields assert now checks raw ids
   too; the text fallback failed on iOS because the header renders
   uppercased.
4. **Infra flakes, named so they are not mistaken for regressions**: the
   witness agent init hung under a load average of 13 (run 27); one wallet
   missed the witness connection twice (runs 26, 30) — the known
   intermittent iOS no-send shape.

### Finding: the R-Card's legacy trigger can starve while the task exchange succeeds

Run 31: every trust-task leg completed in ~6 s on both sides, yet iOS showed
the contact as "Unknown …KdkPszTd". Android had logged *"Peer RCE version
unknown yet — deferring issuance"* and never resumed: the resume depends on
the peer's `vrc:relationshipDid … rceVersion` basic-message announcement,
of which there was no trace — while android had learned the version from
the accepted *proposal* instead. The R-Card (still on the legacy
issue-credential leg, and the source of the display name) therefore never
went out. **Hardening — applied the same day** (bifold, `fix: the accepted
relationship exchange also triggers the R-Card`): the ceremony calls
`issueRCardForAcceptedExchange` from both the responder's acceptance and the
proposer's consumption of it; `issueRCardCredential`'s per-connection lock
makes whichever trigger runs second a no-op (run 33: the announcement path
offered first, the acceptance trigger logged and stood down). The contact's
name no longer depends on a basic message that can be lost. Superseded
position, same day: "backlog, out of step 7's scope" — it was half a day and
a demo-visible bug.

## E. The two debts retired: one plumbing, one pipeline

Both hygiene debts recorded on 08-18/19 closed today, proven by the witnessed
sim e2e (runs 36–37) and then by the attended device run the same evening
(Samsung + iPhone: hardware-attestation evidence present, every marker set,
*Witnessed + Secure Exchange* on both phones):

1. **`@bifold/trust-tasks`** — a new, platform-neutral package holds the
   Trust Task plumbing the wallet (React Native) and the witness-server
   (Node) both run: document proofs and digests, the binding-0.2 carriage
   message, and the §7.2 payload validator. The two deliberate duplicates are
   gone; `@bifold/core` re-exports from it under its old module paths (so
   imports and `jest.mock` sites are unchanged) and the witness imports it
   directly. First attempt put it under `@bifold/vrc-shared/trust-tasks`
   and was **reversed the same afternoon**: that package's README says
   "server side — NOT for the mobile app", its root modules use `fs`/`path`/
   `process`, and stretching it with a second entry would have left a
   foot-gun for the next contributor. The new package's tsconfig compiles
   with no ambient Node types, so a stray Node import fails the build — the
   contract is enforced, not just written. App-side, a new `@bifold/*`
   package needs the four wiring entries now recorded in the root
   `CLAUDE.md` (portal, app dependency, Metro `packageDirs`, and the
   dev-source list) — Metro resolves files only inside its watch folders,
   which is what the red "Unable to resolve module" screens on both
   simulators were.
2. **The witness runs the real `@openvtc/trust-tasks` runtime.** The local
   `framework.ts` pipeline is deleted; `WitnessTaskSessions` consumes through
   `consumeInbound` with the published `witness/session` and `submit` specs
   (payload schema validation included), `StaticTransport` identity
   cross-check, and the spec's proof policy — the same pipeline the wallet
   uses, so conformance cannot drift between the two sides. Loading detail
   worth keeping: the package is ESM-only with an `import`-condition-only
   exports map, so `require()` fails (`ERR_PACKAGE_PATH_NOT_EXPORTED`) even
   on Node 20.19's `require(esm)`; a CommonJS service must use dynamic
   `import()`, and because TypeScript with `module: commonjs` rewrites a
   literal `import()` into `require()`, the call goes through a
   `Function('return import(…)')` trampoline (the standard idiom), with
   types resolved through a tsconfig `paths` map. Credo's ESM worked under
   `require` all along only because its bare-string export counts as
   `default` — which is why nobody had noticed the trap.
