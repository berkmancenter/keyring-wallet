## 1 — Duplicate v2 message-pickup loop

Fixed in `app/src/hooks/useBCAgentSetup.ts`'s `provisionV2MediationIfConfigured`:
it now checks `findV2MediationRecord` *before* calling `provisionV2Mediation`,
and only calls `startV2MessagePickup` when this call is the one that newly
provisioned the record. `configureMessagePickup` (called earlier in the same
setup, unconditionally) already starts the v4 loop for a record that
pre-exists from an earlier launch — the bug was calling `startV2MessagePickup`
a second time on top of that, and `startV2MessagePickup`'s Pickup 4.0 start
has no anti-stacking guard (unlike the patched v1/v2 start).

Test: `app/src/hooks/useBCAgentSetup.test.ts` (new), exporting
`provisionV2MediationIfConfigured` for direct testing rather than exercising
the whole hook. Five cases, including the exact regression ("does NOT start a
second pickup loop when the v2 record already existed").

## 3 — DIDComm v2 developer toggle can diverge from the agent's real capability

**Judgment call:** the finding named `app/src/screens/Developer.tsx` as the
location, but the fix landed in `bifold/packages/core/src/modules/vrc/vrc-manager.ts`'s
`createRelationshipInvitation` instead — that is where the divergence is
actually checked and actionable (the toggle screen already carries an
accurate comment that a restart is needed; it was never wrong on its own
terms). `createRelationshipInvitation` now reads the agent's own
`agent.modules.didcomm.config.isSupported('v2')` alongside the live
`isDidCommV2Enabled()` flag, and falls back to a v1 invitation with a logged
warning when they disagree, instead of minting a v2 invitation the agent
was never actually constructed to process.

Test: `bifold/packages/core/src/modules/vrc/__tests__/unit/createRelationshipInvitationDidCommV2Gate.test.ts`
(new) — flag-on-agent-supports (mints v2), flag-on-agent-does-not-support
(falls back to v1, warns), flag-off (v1 regardless).

## 4 — `identityFromDid`'s keyAgreement fallback throws for did:key / did:peer:0

Fixed in `bifold/packages/credo-tsp-adapter/src/identity.ts`: the keyAgreement
lookup no longer falls back to `agreementJwk.legacyKeyId` when no DID-record
key mapping exists for the keyAgreement verification method. That fallback
made sense for the *signing* key lookup a few lines above (a real, pre-
credo-0.6 storage convention for migrated records) but never applied to
keyAgreement — did:key and did:peer:0 publish a keyAgreement method that is
*derived* from the signing key (Edwards→Montgomery), with no independent
Askar storage at all, so the fallback looked up a name Askar never wrote
anything under. Removing it makes the code fall through to
`identityFromEd25519Key`, the correct derivation path, unconditionally when
no real separate key is registered.

Test: extended the existing `identityFromDid.test.ts`'s did:key case (which
previously only checked `.publicKey` and `.sign()` — never `.agree()`, so it
never reached the bug) to call `.agree()` against a peer key and check the
result against `keyAgreementFromEd25519Key`'s own computation directly.

## 5 — `checkV2ThreadCorrelation` false-rejects a conforming producer

Fixed in `bifold/packages/trust-tasks/src/v2Binding.ts`: reads the raw
`message.thread?.threadId` (the `~thread.thid` header as it actually arrived
on the wire) instead of `message.threadId`, a Credo getter that defaults to
the message's own `@id` whenever `thid` is absent. The binding's own rule is
that a missing member is never compared — reading the getter meant "thid was
never set" and "thid was set to something equal to my own id" were
indistinguishable, and the former was being treated as the latter, i.e. as a
mismatch, whenever the document's `threadId` happened to differ from the
message's `@id` (routine, since those are different identifier spaces by
design).

Test: rewrote `checkV2ThreadCorrelation`'s test block in
`bifold/packages/core/src/modules/trust-tasks/__tests__/didCommV2Carriage.test.ts`
to build real `TrustTaskEnvelopeV2Message` instances via the file's existing
`inboundInstance` helper instead of plain object literals shaped to the old
signature — a literal can't distinguish getter-vs-raw-field and is exactly
how the original bug shipped with tests green. Added the specific regression
case (no `~thread` on the wire at all, message `@id` deliberately different
from the document's `threadId`, must still resolve `ok`).

## 6 — Security: DIDComm v2 first contact bound `theirDid` from an unauthenticated plaintext claim

The deepest fix in this set, and the one to read carefully rather than take
on trust.

**What was there:** `ensureV2ConnectionForFirstContact`
(`@bifold/trust-tasks`'s `v2Binding.ts`) minted a connection record with
`theirDid: contact.from`, where `contact.from` came from the inbound
message's plaintext `from` header (or the same unauthenticated `senderDid`
as a fallback) — a claim, not something the envelope's own cryptography
attested to. DIDComm v2 first contact has no handshake, so nothing else in
the path checked it either.

**The fix:** `senderKeyBelongsToClaimedDid` (new, in the same file) resolves
the claimed `from` DID's own document and checks whether the key that
*actually* authenticated the envelope — `ctx.senderKey`, Credo's own unpack
result, never read from a header — appears among that document's
`keyAgreement` verification methods. `ensureV2ConnectionForFirstContact`
now calls this before minting anything, and refuses (returns `undefined`,
which the two call sites — `DidCommV2Carriage.ts` and
`WitnessTaskSessions.ts` — already treat as "no connection", i.e. the
document is dropped) on any DID-resolution failure or key mismatch. `senderKey`
had to be threaded from both call sites into `V2FirstContact`, since it
previously stopped at the carriage layer.

**What this closes:** an authenticated-but-unrelated sender can no longer
have a connection minted under an identity it does not control, on either
the wallet or the witness-server (both share this function).

**What this does NOT close, honestly:**
- It trusts DID resolution itself — a compromised or spoofed resolver for
  the claimed DID would still pass. That is a pre-existing, general trust
  assumption of the whole DID stack, not something this fix could reach
  without redesigning DID resolution.
- It is a point-in-time check with no freshness/replay guard: a key that
  legitimately belonged to the claimed DID at some point but has since been
  rotated out would still pass if the DID document briefly re-published it,
  or if a resolver cache is stale. No timestamp binding was added.
- Established connections were never affected by this bug in the first
  place (`receive()` in `DidCommV2Carriage.ts` already used
  `connection.theirDid` — the connection's own authenticated DID — not the
  plaintext claim, once a connection exists). The fix is scoped to first
  contact, which is where the gap actually was.

Test coverage is split across two layers deliberately:
- `bifold/packages/credo-tsp-adapter/__tests__/senderKeyBelongsToClaimedDid.test.ts`
  (new) — the pure function against a real resolved did:peer:2-shaped
  document with real (Askar-free) key material: verified match, unrelated
  key refused, unresolvable DID fails closed, no senderKey fails closed.
  Lives in `credo-tsp-adapter` rather than `trust-tasks` because
  `trust-tasks` has no test infrastructure of its own (platform-neutral,
  shared with the witness-server, tested only through its consumers) and
  `credo-tsp-adapter` already has the real-DID-resolution fixtures this
  needs.
- `bifold/packages/core/src/modules/trust-tasks/__tests__/didCommV2Carriage.test.ts`
  (extended) — the full carriage-level integration: a new security test
  proves a first-contact message plaintext-claiming to be a known peer, but
  authenticated by a different key, is refused end to end (no connection
  minted, no document handed to the inbound handler). The two pre-existing
  first-contact tests were updated to supply a `senderKey` that genuinely
  matches the claimed peer's resolved document, since they now exercise a
  real check rather than an unconditional pass.

## 7 — Security: hardware attestation evidence can be paired with a chain that doesn't certify the signing key

Fixed in `bifold/packages/core/src/hardware-signing/evidence.ts`: both
guards (`getOrFetchAttestation`'s "held" branch and its fetch branch) read
`!held.publicKey || held.publicKey !== publicKey` — was
`held.publicKey && held.publicKey !== publicKey` (`attestation.publicKey`
for the fetch branch), which short-circuited past the mismatch check
entirely whenever the reported key was empty or absent, treating "the
platform told us nothing" as "it matches ours". Both now fail closed:
an empty/missing reported key is refused exactly like a real mismatch,
never cached under the requested key.

Test: new `bifold/packages/core/src/hardware-signing/evidence.test.ts`,
covering the empty-string case on both guards (refused) alongside the
genuine-match case on both (still accepted, so the fix isn't a blanket
regression). Two *pre-existing* test fixtures elsewhere had baked in the old
(buggy) behavior as their expectation — `__tests__/hardware-signing/hardware-signing-service.test.ts`'s
`givenAvailableAttestation()` helper and `__tests__/modules/vrc/EvidenceBuilder.test.ts`'s
two raw `mockGetHardwareKeyAttestation` fixtures mocked a "successful"
attestation with no `publicKey` field at all, which only ever passed
*because* of the bug (the missing key was silently treated as a match).
Both were corrected to include the real signing key's public key, which is
what an actual native attestation response carries — this is the same
blind spot the vulnerability itself had, now closed in the fixtures too,
not just the production guard.

**Environment note, not a code finding:** this worktree needed a real
`bifold` workspace `yarn install` and several `yarn build` runs
(`react-native-attestation`, `oca`, `vrc-contexts`, `vrc-shared`,
`verifier`, `remote-logs`, `trust-tasks`) before any of the above would even
resolve the pinned credo-ts version or discover test files — the checkout
this worktree started from had stale hoisted `@credo-ts/*` copies and
several unbuilt `@bifold/*` packages. One further subtlety cost real time to
find: `app`'s `jest.config.js` maps several `@bifold/*` scopes (`core`,
`oca`, `verifier`, `react-hooks`, `credo-tsp-adapter`) straight to this
worktree's own `bifold/` source, but `app/node_modules` itself was a plain
symlink to a *different* checkout's `node_modules` — so a source file
resolved into this worktree's `bifold/` tree that then required a sibling
`@bifold/*` package (e.g. `evidence.ts` requiring
`@bifold/react-native-attestation`) resolved that sibling through this
worktree's own `bifold` workspace node_modules, a **different physical
directory** than the one `app/jestSetup.js`'s global `jest.mock(...)` calls
resolved from. Same package, two unrelated resolved paths, so the mock
never applied to the one App actually needed — every test that transitively
imported this chain failed with `TurboModuleRegistry.getEnforcing(...):
'Attestation' could not be found`, which looked exactly like a code
regression until traced to the split. Fixed by rebuilding `app/node_modules/@bifold`
as real per-package symlinks into this worktree's own `bifold/packages/*`
instead of inheriting the other checkout's. None of this needed a change to
any tracked file — it is worktree-local `node_modules` layout only.
