## Decision: user-facing value first, ecosystem cross-check second

Both items are real, both are open. Choosing between them:

- **`ref-07`'s reference-adapter fixture parity** proves the port-based
  adapter produces byte-identical output to the raw-key reference
  implementation — a correctness/parity check with no surface a person
  outside this codebase would ever see or verify.
- **The wallet answering `credential-exchange/query`** is the first piece of
  this whole step-4 line of work reachable from the actual app: a real
  consent prompt, a real presentation, receivable and demoable by anyone —
  not a Node script proving the protocol against a `vta-service` nobody but
  this session has run.

Reprioritized the latter first. Not a scope cut — `ref-07`'s item remains on
the roadmap, tracked here and in `trust_tasks_subtask.md` §9 step 4, and
worth doing; it's simply no longer ahead of the thing with a user-visible
payoff, now that it's understood not to be gating anything.

## Built: `credential-exchange/query` → consent → `credential-exchange/present`

Happy path only — `credential-exchange/pending/{list,approve,deny}` (defer
for later approval) is explicitly out of scope for this slice, not
foreclosed.

`ceremony.ts` gains a handler in the same dispatch table `propose`/`issue`/
`witnessShare` already ride (`setupTrustTasksInbound`), following
`handleInboundPropose`'s exact shape:

1. `TrustTasksService.consume()` against `credential-exchange/query/0.1`'s
   `SPEC` (no proof required, no `#response` variant — the spec's own
   payload doc says the answer is a separate task).
2. The DCQL query is checked against the wallet's stored credentials via
   Credo's `DcqlService.getCredentialsForRequest(agentContext, dcqlQuery)`,
   resolved directly from the dependency container — the SAME primitive
   `modules/openid/resolverProof.tsx`'s holder-side OID4VP path already
   uses, but called with the bare DCQL query object rather than through a
   full OID4VP authorization-request envelope, because this Trust Task
   carries no such envelope (`ref-08-credential-exchange/run.mjs`'s own
   `minimalDcqlQuery` confirms the wire shape: `dcql_query` is the raw DCQL
   object, "carried verbatim"). Checked BEFORE prompting, not after — an
   unsatisfiable query surfaces no prompt at all, so the user is never shown
   a Share button that can't do anything.
3. Only if satisfiable, a new store (`credentialExchangeStore.ts`) surfaces
   a consent prompt — a sibling to `witnessStatusStore.ts`'s
   `vrcFlowStore.proposalPrompts`, but keyed by the QUERY DOCUMENT's own id
   rather than by `connectionId`: a wallet can plausibly hold prompts from
   more than one verifier connection at once, where a relationship proposal
   cannot (one connection, at most one open proposal).
4. `CredentialExchangeQueryModal.tsx` — a near-literal copy of
   `RelationshipProposalModal.tsx`'s bottom-sheet pattern (same modal
   primitives, same subscribe-to-store-events shape), showing the verifier's
   stated `purpose`. Mounted in `RootStack.tsx` beside
   `RelationshipProposalModal`.
5. On Share, `respondToCredentialExchangeQuery` re-checks the match (a
   credential present when the prompt was shown may be gone by the time it's
   answered), builds a challenge-bound VP via `buildChallengeBoundVp` (now
   exported — it already existed, built for the witness ceremony's own VP;
   reused verbatim rather than re-implemented) with `challenge: <the query's
   nonce>` and `domain: <the verifier's connection DID>` — the spec's own
   payload doc for `credential-exchange/present` says a JSON *object*
   `vp_token` is exactly "a W3C Data-Integrity VP whose proof carries the
   same nonce and domain," which is precisely what this construction already
   produces; no need for Credo's OID4VP/DCQL presentation-building pipeline,
   which is built for a different wire shape this exchange doesn't use.
   Signs the `credential-exchange/present` document itself with the
   wallet's own connection DID (`connection.did`) as controller —
   `signDocumentProof` needs no relationship-DID-specific behavior to do
   this; it resolves whatever DID it's given.
6. On Decline, nothing is sent — there is no error/response variant for
   `credential-exchange/query`.

`credentialExchangeQuery.TYPE_URI` was added to `SUPPORTED_TASK_TYPES` (the
wallet's `trust-task-discovery` advertisement) alongside `propose`/`issue`/
`witnessShare`.

### Not verified — written, unrun, same posture as this branch's own precedent

`e2e/run-credential-exchange-query.js` (`yarn e2e:credential-exchange-query`)
drives two Android wallets through an ordinary VRC exchange (so the holder
has a real, stored credential to be queried for), then a minimal verifier
agent connects and sends the query, asserting the app's consent prompt
appears and a valid `present` comes back. **Not run against a real device or
emulator** — no Android hardware was available when this was written, the
same posture `2026-09-02-bam.md` recorded for `yarn e2e:vrc:tsp` before a
later session confirmed it live. Treat this as unverified until it's
actually run, not as evidence the flow works on-device.

The verifier itself (`e2e/lib/verifier.js`) is new infrastructure, not a
full `vta-service`: a raw, disposable `@credo-ts/node` Agent (Askar-backed,
HTTP transport through a cloudflared tunnel, mirroring `e2e/lib/witness.js`'s
already-proven reachability pattern) that speaks binding 0.2's
`TrustTaskMessage` directly — modeled on
[`ref-06v1-didcomm-v1-binding`](../../../tsp-reference/ref-06v1-didcomm-v1-binding/)'s
`makeAgent` (two Credo agents speaking the binding, already proven) and
`witness-server/src/trustTasks/WitnessTaskSessions.ts`'s
`registerMessageHandler` shape (already proven). A full `vta-service` binary
is unnecessary here: `credential-exchange/query` is just a Trust Task
document over an authenticated DIDComm connection, same as every other Trust
Task in this codebase — the DID-auth/REST/ACL machinery `tsp-reference/ref-08`
exercises belongs to `vta-service`'s own admin surface, not to the spec.

**A real packaging constraint worth flagging, not just an untested detail**:
`e2e/` is deliberately outside the yarn workspaces (root `CLAUDE.md`), so it
has no ordinary way to depend on `@bifold/trust-tasks` (workspace-only) or on
the exact *patched* `@credo-ts/*` versions bifold's own install resolves
(`.yarn/patches/` — hand-rolling with unpatched versions risks silently
hitting a bug this project already spent sessions fixing elsewhere).
`verifier.js` resolves these by relative path into `bifold/node_modules`/
`bifold/packages/trust-tasks/build` instead of adding them as `e2e/package.json`
dependencies — confirmed these specific paths resolve (`node -e` smoke
checks against each package's own `exports` field, not assumed) before
relying on them, but this is otherwise unexercised: the agent has never
actually been started, connected, or sent a message.
