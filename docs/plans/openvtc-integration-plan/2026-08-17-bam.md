## A1. We were citing the framework a minor behind what our pin contains

The pinned `SPEC.md` header table reads `Document version 0.3`; its Appendix B
changelog documents 0.4, and 0.4 is what the file actually contains — the
`ceremony` member (§4.11), authorization-distinct-from-proof (§7.2 item 10),
`trust-task-ok` (§8.6), the task digest (§4.9.3).

This is not cosmetic. [[DTG-CRED]] cites "framework 0.4" against the *same
bytes*, so a reader holding both documents saw a version gap that does not
exist, and would reasonably have concluded that one of the two was building
against something unavailable. `[[TT-SPEC]]` now states the label to use and why
the header disagrees. The sibling subtask carries the same wart in its own
header, noted there as "the editor has confirmed this is stale" — that note is
now out of date in the other direction and should be reconciled when that
document is next touched.

## A2. There are two digests, and one hash helper cannot serve both

§2.2's retry rule was corrected when the subplan was written, but the digest
question was left open. The framework computes two different digests over a Trust Task
document, and states the distinction rather than leaving it to be inferred:

- **Document identity** (§7.2 item 11, §8.4) asks *which serialization arrived*.
  Two documents sharing an `id` are the same document "when their serializations
  are identical under [RFC 8785] canonicalization", so a `proof` re-signed over
  identical content makes a **different** document — the `idConflict` case.
- **The task digest** (§4.9.3) asks *what the document says*, and is computed
  with the top-level `proof` **removed**: "the same statement signed, unsigned,
  or re-signed is one document with one task digest."

The spec is explicit that these are not interchangeable — *"this is not the
document identity of §7.2 item 11 … the two answer different questions and are
deliberately computed differently"* — and names a third computation that is
neither (`trust-ceremony-receipt`'s step digest, over the document *including*
its `proof`). A client that writes one hash helper and reuses it gets at least
one of the three wrong, silently, in a way that only shows up as a failed
pairing months later.

## A3. The DIDComm v2 binding moved to 0.2 without moving the envelope type

`binding/didcomm/0.2` is in our pin. The envelope type is deliberately
unchanged — "additive, and a `MINOR` increment accordingly: the envelope type is
unchanged, so a `0.1` consumer recognises a `0.2` producer's messages and vice
versa" — so §2.1's transport table was correct and stays correct.

Two things 0.2 adds do bind us. `thid`/`pthid` are now **mapped** to
`threadId`/`parentThreadId` rather than ignored (0.1 "left `thid` and the
framework's `threadId` free to disagree with nothing detecting it"), with the
comparison engaging only when both are present. And on `identityMismatch` the
consumer **MUST** route its error to the transport-authenticated sender and
**MUST NOT** route to the contested in-band `issuer` — which is the rule a
naive "reply to `issuer`" implementation gets wrong by default, and precisely
the case where the in-band member is what is in dispute.

**Recorded alongside it, and this is the part worth keeping:** the framework's
DIDComm **v1** binding answers the same question in the *opposite* way. It
cannot represent a `urn:uuid:` correlator (Credo enforces RFC 0008's id shape),
so its 0.2 rule is that an unrepresentable correlator is **omitted, never
rewritten** — "a rewritten correlator contradicts the in-band member and draws a
guaranteed `malformedRequest`" ([#238](https://github.com/trustoverip/dtgwg-trust-tasks-tf/pull/238)).
Keyring runs both bindings, because the parent plan requires DIDComm v1
coexistence for the legacy VRC/witness stack, and PNM mints exactly the ids v1
cannot carry. So **one shared thread-correlation helper is a trap**: v2 maps and
errors on disagreement, v1 drops what the transport cannot carry, and neither
may edit the value. This is only visible when both bindings are held in view at
once — which is this plan's position and neither binding spec's.

## A4. Outcome evidence is a pair, and we were specifying half of it

The largest correction, and the one that reached the parent.
[cred-spec #18](https://github.com/trustoverip/dtgwg-cred-spec/pull/18) took the
`taskDigestMultibase` work (merged from Mickens-Lab#5 late on 08-17, after the
subplan was written) and redefined matching outcome evidence as **the
exchange's initiating document together with a terminal document**, paired as:

```
terminal.threadId == (initiating.threadId ?? initiating.id)
```

The indirection through the initiating document is deliberate, and it is what we
had wrong: §4.9 lets an initiator mint a fresh `threadId`, so pairing a terminal
document directly against the credential's `taskContext` would orphan legitimate
evidence. The PR says so — "pairing runs through the initiating document
precisely so that an initiator exercising §4.9's freedom … does not orphan
legitimate outcome evidence."

**Superseded:** parent §8.1 specified persisting "the ceremony's `#response`
document with its proof" and indexing "by the identifier the credential's
`taskContext` carries". A holder that did exactly that **cannot complete the
pairing** whenever the initiator minted its own `threadId` — which is permitted
and which we cannot control from the holder side. The requirement now reads:
keep both documents; index on the initiating document's `id`; and verify by
recomputing `taskDigestMultibase` over the retained initiating document rather
than by comparing `id`s, because "`id` equality … locates a candidate document;
only the digest match confirms it is *the* document."

Worth stating plainly because it is easy to read as bookkeeping: this is a
requirement generated by **our own contribution**. The digest algorithm is ours
(§4.9.3, co-authored as #236; `taskDigestMultibase` as Mickens-Lab#5). A
specification whose only implementation does not satisfy it is worse for us than
one we never wrote, which is why it is now costed at a phase rather than left in
the parent's uncosted list alone.

## A5. Framework 0.4 landed rules a consent surface would otherwise get wrong

All inside our pin, all normative, all bearing on P1. Recorded in §4.5:

- **Task control (§12)** — a pending consent prompt can now be withdrawn
  in-band. A phone that renders a prompt and never handles a control document
  asks a human to decide something that no longer matters, and then accepts the
  decision. Rollback is never offered; suspension **MUST NOT** resume after
  `expiresAt`.
- **Authority re-evaluated before each irreversible effect (§7.2 item 12)** —
  approval is a *window* with live revocation semantics, not a moment. Note
  `expiresAt` is deliberately excluded from item 12, so the consent card's
  countdown reads `payload.expiresAt`, never the envelope's.
- **Authorization is distinct from identity and proof (§7.2 item 10)** — the
  inference *valid proof + recognized issuer + correct recipient → authorized*
  is named as "the same confused-deputy vector", "most dangerous where the
  *producer* is an agent that can prove its identity but holds no authority to
  act." Consequence for us: `task-consent`'s model, where a verified assertion
  *is* the authorization, is now an explicit per-specification declaration and
  **not a default a consent surface may assume**.
- **The `ceremony` member (§4.11)** — rides on the document rather than in
  `payload`, is covered by `proof`, and confers no authority. A witnessed VRC
  exchange is exactly such a flow, so this is the framework mechanism the
  sibling subplan's Layer C composes on rather than inventing.

## A6. Edge-binding verification and selective disclosure cannot coexist in one presentation

A selectively-disclosed VRC cannot satisfy `digestMultibase` verification — the
digest is over the full canonical form — so the two are "mutually exclusive in
one presentation". Deriving a selective disclosure at all requires a `bbs-2023`
**base proof**, which an `eddsa-jcs-2022` proof cannot yield, so an issuer
needing both must issue a **proof set**; and because `bbs-2023` uses RDF
canonicalization, the offline-verification argument for `eddsa-jcs-2022` does
not extend to the ZKP path.

The trade was taken on review of the staged PR earlier the same day, on two
grounds recorded there: the privacy story leans on the ZKP constructions rather
than per-field disclosure, and DTG credentials are "small, atomic and meant to
be composed". It is in the plan as standing rationale rather than in this
document alone because **it cannot be retrofitted** — issuing a proof set is a
decision made at issuance, and an implementer who needs selective disclosure has
to know before the credential exists.

## A7. Two internal inconsistencies in the subplan as first written

Both are the ordinary hazard of a correction sweep applied section by section:
a rule fixed in one place and left standing in another.

- **P3's acceptance criteria still said "a fresh envelope id is minted per
  attempt … including on fallback"** — the exact instruction §2.2 had been
  corrected, three sections earlier, to forbid. Under §7.2 item 11 a genuine
  retry re-sends the document unchanged; re-minting turns one request into two
  documents and causes the duplicate effect the rule exists to prevent.
- **§9 carried a dangling `Q7` reference** pointing at a question never written.
  The reference was reaching for "do we build P5 against cred-spec #12 while it
  is open?", which is a real decision, so it was written rather than the
  reference deleted. Issue #11's challenge to the whole `taskContext` dependency
  became Q8.

# Part B — The four scope gaps

Found by reading the finished subplan against what it is supposed to deliver: a
VRC exchangeable between Keyring and the CLI, a phone that handles approval
requests, and the rest of the user-facing PNM/CNM surface. Gaps 2 and 3 were
confirmed as in-scope by Brendan before being written up; gap 1's resolution
was authorized as "even if it means contributing work on other repos".

## B1. Neither CLI has a headless relationship surface — which is the real blocker

**Superseded position:** Q1 framed the choice as "`openvtc` or `pnm`, and adding
`relationships` to `pnm-cli` is a larger and different project". The framing was
right about `pnm-cli` and missed the constraint that actually bites.

`openvtc` declares exactly two subcommands — `setup` and `health`
(`openvtc/src/cli.rs:36-44`). Everything else is a ratatui TUI driven through
`state_handler/relationship_actions.rs` (2124 lines). So the three-phase
handshake cannot be scripted from a terminal **in either CLI**, and an automated
Keyring↔CLI interop test has no counterparty it can drive. Hand-driving a TUI
produces a demo but not evidence, and the ladder's whole discipline is that a
rung is re-runnable.

The resolution is cheaper than the problem suggests, because the coupling is not
where it looks: **`openvtc-core` is UI-free** — no `ratatui`/`crossterm` in its
`Cargo.toml` — and holds the entire protocol behind a public API
(`generate_profiles`, `create_send_message_accepted`,
`create_send_message_rejected`, `VrcRequest::create_message`, the
`Relationships`/`Vrcs` stores). Headless subcommands are a thin dispatcher over
code that already runs without a terminal.

So the decision: **extend `openvtc`, not `pnm-cli`.** Extending `pnm-cli` means
porting a protocol into a crate that has never seen it; extending `openvtc`
exposes an implementation that already works. Recorded in the plan as standing
rationale rather than deleted, because "add `relationships` to `pnm-cli`" is the
obvious-looking move for anyone reading the demo's phrasing ("Keyring PNM ↔ CLI
PNM"), and the reason it is wrong is a fact about where the code lives.

This is now P4's prerequisite and parent §7 row 11. It is the first phase whose
*evidence* is gated on review in someone else's repo — noted in §7 as a
scheduling risk, with the mitigation being to open the PR early and keep the
rung runnable against a local branch meanwhile.

## B2. Backup/restore and mnemonic export are in scope — and the docs said backup didn't exist

**Superseded:** P3 excluded backup/restore and `vta/seeds/*` as "server-operator
surface". Brendan's call was that a personal agent whose state cannot be
recovered from the device that manages it is not a personal agent. Both are in.

Three findings shaped how they land.

**The backup slice is documented as unbuilt and is in fact built.** The design
note states *"Status: spec only — no implementation yet"* and the SDK says the
handlers "land in follow-on commits per the rollout plan". Both are stale:
`vta-service/src/trust_tasks/backup.rs` implements all five and
`trust_tasks/mod.rs:968-976` registers every one. Taken at their word, these
comments would have removed backup from the plan on the grounds that there was
nothing to call. This is the **fourth** measured instance of upstream doc drift
(§4.4) and the first that drifts *downward* — documentation understating what
shipped, which is the more dangerous direction because it reads as a reason not
to build.

**Bulk bytes leave the envelope, and the transport invariant leaves with them**
(new §4.8). Trust-task envelopes are capped at 1MB, so the bytes move over
`GET`/`POST /backup/blob/{bundle_id}`, **deliberately REST-only** — "bulk bytes
are wrong on top of a JSON envelope". This is the one place in the plan where
"the same document over any transport" stops being true, so P3's acceptance
criteria now carry an explicit exception. Three further constraints are each a
way to lose a backup silently: one-shot tokens expiring on first read and on a
5-minute TTL (a backgrounded mobile download cannot be resumed); v1 buffers the
full backup in memory, which is a real ceiling on a phone and is why the
criterion names a measured limit; and the `.vtabak` format is Argon2id +
AES-256-GCM and is *not ours to vary*, since a wallet that re-wraps the bundle
produces a file the operator's CLI cannot restore.

**Seeds export the VTA's seed, not the phone's.** `vta/seeds/export-mnemonic/1.0`
"operates on the seed identifier, not an individual key". A wallet screen
labelled "your recovery phrase" over this task tells the user something false —
Keyring's own Askar store has nothing to do with this family. `seeds/rotate` is
deliberately still excluded: an operator action with no recovery path if it
half-completes.

The exclusion list was also given its criterion, since it had none:
**"would a person administering their own VTA from their own phone need it?"**,
not "is it privileged?". Several in-scope items need admin or super-admin. The
Rego editor and seed rotation stay out because both are ways to lock yourself
out of your own VTA with no recovery path, and neither becomes safer on a small
screen.

## B3. P6 spans two services, and `cnm-cli` is not the membership surface

**Superseded:** P6's only acceptance criterion was "a community admin can review
and decide a pending join request" — scoped to the one operation with *no*
upstream precedent, and silent on the surface that does exist.

The correction is a fact about where membership lives. `cnm community
{list,use,add,remove,status,ping}` manages *which communities this client talks
to* — local configuration. Nothing in `cnm-cli`'s 13 subcommands decides a join
request. The membership operations are in `vtc-client`, against the **VTC**:
`list_join_requests`, `approve_join`, `reject_join`, `list_members`,
`remove_member`, `update_member_extensions` (`vtc-client/src/lib.rs:279-436`).

So a Keyring CNM is **not a port of `cnm-cli`**; it is the VTA surface P3 already
built, re-scoped, plus a VTC client P5 already stood up. That also means the
tokens do not interchange — the VTC issues its own JWT with `aud: "VTC"` and
cross-audience tokens are rejected — so P6's criteria include a test for it,
because the failure is a `401` whose cause is not obvious from the message.

§1 previously read as though CNM never touches the VTC, which is true of
`cnm-cli` and false of what a community admin actually wants; it now says so
directly, since that composition is P6's whole cost.

## B4. Approvals management had no phase, and cannot answer its most natural question

P1 *answers* consent and step-up requests; nothing covered configuring approver
sets or reading which task types demand approval. Now P3 item 4, read-only
first — showing the rules needs no super-admin, writing them does.

The finding worth recording is what **cannot** be built at Cypress:
`policy/evaluate/0.3` is deliberately not served, because its `input` schema
still marks `site` — a vault-flow origin — as required, inherited from before
0.3 generalised the family to any Trust Task. The SDK states the objection
plainly: *"There is no honest `site` for 'would `acl/grant` need approval here',
and inventing one means fabricating a member of a security decision's input to
satisfy a validator."*

So no client — CLI or wallet — can dry-run "would this task need approval?", and
the plan requires the UI not to pretend otherwise. Upstream already records this
as a wart wanting a follow-up, which makes it an invited contribution: parent §7
row 12. A wallet is the context where that question is most natural to ask,
which makes us the right implementer to press it.

# Part C — Q9, recommended and flagged

**The question:** what does Keyring offer when it holds super-admin on a VTA the
user does not own?

**Superseded, and it was this document's own first position:** §4.7 initially
said the distinction "has to be a runtime check on the session's own
claims". That cannot work. **Ownership is not on the wire.** The claims carry
the *tier*; they say nothing about the holder's relationship to the deployment,
so "my own agent" and "someone else's agent where I happen to be super-admin"
are indistinguishable from the session alone. Any design assuming otherwise
fails at the first shared VTA.

**Recommended, adopted provisionally:** capability follows the claim; consequence
additionally follows a **local declaration** made once at enrolment, defaulting
to "somebody else's". Reads follow the claim alone. Discloses and writes —
backup export, restore, mnemonic export, approvals-write — require the claim
*and* the declaration. Where the claim is present without the declaration, state
the absence rather than hiding it, because a super-admin who knows they hold the
role and finds no screen reads that as a bug and works around it.

The reasoning, because the conclusion is cheap to re-derive wrongly: this is a
**presentation** decision, not access control. Getting it wrong cannot cause a
breach — the VTA refuses what the session may not do. What it can cause is
someone casually restoring a backup over infrastructure other people depend on,
and that risk is a property of the deployment, which only the user knows. So the
input must come from them, once, with the safe default.

**Rejected: inferring ownership** — from being the first enrolled DID, from
holding super-admin, from having performed setup. Every signal is true of a
legitimate co-administrator on a shared VTA, so each one silently promotes
exactly the case the gate exists for.

**Flagged for review at three triggers**, rather than "later": before P3's
backup and approvals screens are designed (the declaration sits in P2's
enrolment flow, so the cost rises sharply once both are built); when Q3 is
answered, because if users enrol with a VTA *we* operate then "not personally
owned" becomes the **default** rather than the edge case, and a design tuned for
personal agents would be gating the common path; and on first contact with a
real multi-administrator VTA, since the shared case is currently hypothetical.

# Part D — delivery phasing, and the cred-spec #5/#18 review

A separate review the same day covered three things: Alberto's Rev 6–11
commits, cred-spec #5/#18 against Geoff's inline review, and an audit of the
plan against the four-stage phasing we had discussed verbally. Its findings,
re-verified against the sources here rather than taken on trust, and applied:

## D1. The plan's own revision metadata was wrong

The header read **Rev 8** while the disposition table ran through Rev 11 — and
the table's last four rows were out of date order (08-17, 08-17, 08-16, 08-15).
Both fixed; the header now reads Rev 12 and the table sorts ascending. Trivial
to fix, and worth noting only because a plan that misreports its own revision
undermines the disposition index's entire purpose, which is telling a reader
which review drove the text in front of them.

## D2. The four-stage phasing was nowhere stated, and two axes were being conflated

**Superseded framing:** the plan supported the phasing directionally — v1 first,
recast before carriage swap, PNM last — but never stated it as an ordered list,
so it lived only in conversation. Worse, the document already contained a
*different* phasing (§6's Phase A–E ladder) and drew no line between them, so the
two read as one confused sequence.

They are different axes and now say so, in a new **§5.4**: §6 is a **validation
ladder** answering "does this mechanism work", ordered for cheap learning; §5.4
is the **delivery order** answering "what does Keyring ship next", ordered by
dependency. The five stages are stated with their carriage, their operation
layer, and their status.

The framing correction that made this tractable: read literally, "TSP over
DIDComm v1/v2" does not map onto the design at all, because TSP and DIDComm v2
are *parallel* envelope formats here, not stacked. With **Trust Tasks** as the
subject, every stage maps — the operation layer stays fixed while the carriage
moves, which is exactly §2.3's byte-identity property.

## D3. Stage 3 was argued away on a premise that no longer holds

**Superseded position:** the plan had a reasoned argument for skipping a
DIDComm-v2 hop for the VRC/witness exchange and swapping straight to TSP —
running Trust Tasks over v2 would mean standing up `vti-didcomm-js` as a second
transport stack *for that hop alone*, whereas the TSP swap is free because
`tsp-core`'s Carriage port is Credo-version-independent.

That was sound when PNM sat after the ladder. It stopped being sound earlier the
same day: **P1 of the PNM subplan stands up exactly that stack** for the approver
flow, and **P4 already runs a peer-to-peer VRC exchange over it** against
`openvtc`'s bespoke types. The stack is not marginal cost for one hop; it is
infrastructure two PNM phases already require.

So stage 3 is a carriage swap on a proven stack. And it is where the exchange
becomes real, because **it is the only Trust-Task carriage with a live peer
today** — TSP has no counterparty for this exchange until `vta-service` ships
TSP enabled, which it does not at Cypress. Skipping stage 3 does not reach stage
4 sooner; it only waits.

Recorded at §5.4 with the caveat that the stages fix *dependency*, not release:
stage 3 may be exercised as a rung and held behind a flag if stage 4 lands close
behind.

## D4. A merged upstream spec cites a member no published schema defines

`witness/session/submit/0.1` is merged and in our pin, and normatively requires
the delivered VWC to carry `taskDigestMultibase` — while saying plainly that the
member's schema "belongs to DTG Core Credentials", where it lands only when #18
merges. The sequencing risk was flagged on #236 and the merge went ahead anyway.

Now recorded as **parent §8.2**, in the plan rather than only in a tracker,
because we are the party who can close it: #18 is ours and its blocking review
is answered. That makes reviewing #5/#18 a higher priority than its queue
position suggests — it resolves a gap in someone else's shipped specification,
not only our own.

## D5. The correction this forced to Part A's conclusion

Reading that spec directly corrected A4. §4.6 of the PNM subplan hedged the
pairing rule as "the shape we are driving, not ratified text", because #18 is
open — and parent §8.1 inherited the same implication.

**That is wrong for the case Keyring actually has.** The witness specification
already states the holder's duty normatively, in our pin:

> A holder later presenting that VWC as proof the witnessing occurred **MUST**
> retain this `#response` **and the `witness/session` document that opened the
> session**, and ship both with the presentation.

#18 supplies the credential-side *schema*; the *retention obligation* exists
now. So the §8.1 work is not contingent on #18 and must not be scheduled as
though it were — the two proceed independently. Both documents corrected.

Reading the same spec also surfaced two verifier checks the general rule leaves
to the task specification, now in §4.6: the evidence's `issuer` is the witness
that issued the VWC, and the presented credential's own digest equals the
evidence's `vwcDigestMultibase` — so a VWC is verified against the response that
delivered it, not merely against the session it names.

## D6. Closed by the day's other work

The audit found PNM "named but not sequenced — closer to a roadmap entry than a
planned phase". That was true of the plan as it stood: `pnm_cnm_subtask.md`
landed later the same day with P0–P6 and per-phase acceptance criteria.
Roadmap row 5 now says so rather than continuing to read as an unscoped entry.

## D7. Left open, not resolved here

**`taskContext` placement.** Geoff observed that the reference run stored
`taskContext` inside `credentialSubject` while the spec puts it at the credential
top level, and the resolution was to move the *implementation* to match the
spec. That is a real wire-shape choice rather than a nit, and it was resolved in
the direction that changes running code. Recorded rather than adopted silently:
nothing in the plan depends on revisiting it, but the time to reopen it is
before #18 merges.
