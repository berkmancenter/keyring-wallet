## `yarn e2e:vrc:tsp` verified — a real Askar bug, not an environment gap

Running the spec for the first time surfaced a genuine crypto bug, not the
"just needs a device" gap the prior entry assumed. `credo-tsp-adapter`'s
`keyAgreementFromEd25519Key`'s `agree()` passed a peer's public key straight
through to Askar's native `Key.fromPublicBytes`, which rejected it as
"Invalid key data" on every real inbound envelope — HPKE-Auth open failed
100% of the time, silently, at the FFI boundary.

**Root cause**: `Buffer.prototype.slice()` — unlike
`Uint8Array.prototype.slice()` — returns a **view** into the original
backing `ArrayBuffer`, not a copy. The peer's 32-byte public key arrived as
exactly such a view (measured: `byteOffset=3865` into a 3969-byte buffer —
the entire wire message), and Askar's native binding, which reads the
underlying `ArrayBuffer` across the JSI boundary rather than respecting the
JS-level `byteOffset`/`length` window, received the whole 3969-byte message
instead of the 32-byte key. Root-caused by streaming adb logcat on a live
run and adding temporary instrumentation at each step of the send/receive
path — confirmed the raw key bytes matched between sender and receiver
before finding the mismatch was in the runtime object's `byteOffset`, not
its content.

**Fixed** with a defensive `Uint8Array.from(...)` copy at the FFI boundary,
regardless of what the caller hands in. Verified: `yarn e2e:vrc:tsp` now
passes clean end to end, including the Developer-toggle navigation this
entry's predecessor could not verify.

## The user's question: "Why isn't our witness also speaking TSP?"

Asked directly after the clean `e2e:vrc:tsp` pass, before any witnessed-flow
work started. This is a real architecture question against this plan's own
stated position, not a rhetorical one — worth answering precisely rather
than assumed.

**What the plan currently says** (§4.2, unchanged until this entry):
*"Convergence of the legacy stack (VRC-over-TSP, witness ops as Trust
Tasks) remains a deliberate later phase."* Read at face value, this framed
witness-over-TSP as intentionally out of scope for now, and the prior
entry's wallet-to-wallet `TspCarriage` work as a self-contained slice that
didn't touch the witness.

**That framing doesn't survive contact with how carriage selection actually
works.** `sendTrustTaskDocument` (`ceremony.ts`) auto-selects carriage from
the wallet's own `isTspCarriageEnabled()` flag — it does not, and cannot,
know whether the *witness* on the other end can read a TSP envelope. So the
moment a wallet has the TSP dev-flag on, **every** Trust Task document it
sends goes out TSP-wrapped, including its witness session-request — whether
or not `WitnessTaskSessions.ts` (the witness's own handler) was built to
expect one. The witness was not: it registered only for the plain
`TrustTaskMessage` the DIDComm-v1 binding uses. The two capabilities
(wallet-to-wallet TSP carriage, witness-server TSP support) are not
independent slices that can ship in either order behind the same flag —
turning on the wallet's flag silently breaks the witness ceremony the
instant it's on, with no error, just a timeout, because the request never
arrives in a shape the witness's handler is listening for.

**Instruction received**: implement witness-side TSP support now, ahead of
§4.2's stated later-phase ordering — "We are moving away from the legacy
design." Recorded here rather than silently overriding the plan's own text,
per this directory's rule that a changed position needs a companion, not
just a diff.

### Scope-correction within this same investigation

A first research pass (forked sub-agent) concluded the wallet's witness
session-request/submit still rode the LEGACY
`agent.modules.didcomm.basicMessages.sendMessage` path
(`witnessed-vrc-manager.ts`), and that migrating the wallet onto the
Trust-Task dialect would be the bulk of the remaining work. **This was
wrong** — caught by direct evidence from a live run's device logcat, not
assumed correct because a sub-agent produced it. The wallet's v4+ ceremony
(`ceremony.ts`'s `runWitnessSession`, wired via `witnessCeremony.ts`)
already sends witness session-requests via the Trust-Task dialect
(`sendTrustTaskDocument`, type `https://trusttasks.org/spec/witness/
session/0.1`) as of the 2026-08-20 recast (Rev 15) —
`witnessed-vrc-manager.ts`'s legacy path only serves v1–v3 (non-Trust-Task)
peers and was correctly not in the code path exercised here
(`shouldUseWitness = useWitnessing && witnessConnected && !v4Pair` — v4Pair
is true, so it defers to the new path). The actual, narrower bug is exactly
the carriage-selection point above: same Trust-Task dialect, wrong
envelope.

## Fixed: `WitnessTaskSessions.ts` now speaks both carriages

`bifold/packages/witness-server/src/trustTasks/WitnessTaskSessions.ts` now
registers a **second** `DidCommMessageHandlerRegistry` handler, for
`TspEnvelopeMessage`, alongside the existing `TrustTaskMessage` one. Both
route to the same `handleDocument`, now taking a `carriage: 'didcomm-v1' |
'tsp'` parameter, and reply on whichever carriage the request arrived on —
mirroring `TspCarriage.ts`'s own send/receive pattern exactly
(`identityFromDid` + `createCredoVidResolver` + `tsp.pack`/`unpack`).

Supporting moves:

- **`TspEnvelopeMessage` relocated** from `@bifold/core` to
  `@bifold/trust-tasks` (`packages/trust-tasks/src/TspEnvelopeMessage.ts`)
  — mirrors `TrustTaskMessage`'s existing location, which lives there
  specifically so `witness-server` (a plain Node process) never needs to
  depend on the whole RN `@bifold/core` package. A thin re-export shim
  stays at the old core-relative path so `TspCarriage.ts` and its test
  needed zero changes.
- **`@bifold/credo-tsp-adapter` added as a `witness-server` dependency**
  (it had none before) for `identityFromDid`/`createCredoVidResolver`. The
  witness's own `did:peer:0` identity shape needs no new fallback logic —
  it's the same shape `identityFromDid` already handles for wallet DIDs.
- **`.yarn/patches/@openvtc-vti-tsp-js-*` extended**: the patch already
  fixed a Hermes `TextDecoder({fatal:true})` crash; it now also adds a
  `"require": "./dist/index.js"` export condition, needed because
  `witness-server` loads the package via `ts-node`/plain Node `require()`,
  not Metro's ESM-aware resolver the RN side uses. Bifold-only — the outer
  repo's separate copy of this patch doesn't need it, since `witness-server`
  only ever runs from inside `bifold/`.

**Known pre-existing gap, not caused by this change**: `witness-server`'s
own `yarn test` has one failing suite, `WitnessService.test.ts` — plain
jest (unlike `@bifold/core`'s RN-preset jest config) can't do the
`require(esm)` interop trick that fixes this for real Node/`ts-node`, and
hits a raw `SyntaxError` parsing `@openvtc/vti-tsp-js`'s ESM dist through
`@bifold/trust-tasks`'s barrel export. Confirmed pre-existing by diffing
against the file's original content — the `TrustTaskMessage` import chain
that trips it already existed before this session touched the file. Fix
(not done here): a `transformIgnorePatterns` override in `witness-server`'s
jest config, the same way `@bifold/core`'s config already allowlists this
package.

## Verified: full attended two-physical-device pass, both carriages

New e2e spec, `yarn e2e:vrc:witnessed:tsp:android-only`
(`e2e/run-vrc-exchange-witnessed-tsp-android-only-devices.js`), mirrors the
existing witnessed-flow script with `useTspCarriage: true` (a new option
threaded through `runWitnessedExchange` in
`e2e/lib/witnessedExchangeFlow.js`). Getting a clean pass took several
attended runs and surfaced three more real bugs, all found live and fixed
before the run that finally passed:

1. **Metro cache staleness**: running `yarn install` in `bifold/` while
   Metro was already serving killed a run outright (`Unable to resolve
   module ./message/envelope.js` — the file existed on disk, Metro's cache
   didn't know). Fix going forward: always restart Metro with
   `--reset-cache` after a bifold-side install, not only when something
   looks wrong.
2. **`restartApp`'s fixed 5s sleep raced a slow cold JS boot.** The restart
   right after `enableTspCarriage` (a heavier, freshly-cache-reset bundle)
   sometimes took longer than 5s on a real device; `unlockIfLocked`'s
   instant existence check ran before the PIN screen had mounted, silently
   missing it. Fixed: `existsTestId(driver, "EnterPIN", 15000)` — a real
   wait, not a delay.
3. **The developer-mode "tap Version 11 times" gesture assumed every tap
   lands.** `useDeveloperMode`'s counter (`bifold/packages/core/src/hooks/
   developer-mode.ts`) has no time-window reset, so any 11 taps that land
   trip it — but a raw `.click()` loop with no verification silently drops
   an occasional tap on a real device under load, the same flake class
   `tapTestIdReliable` exists elsewhere in this harness to absorb. Seen
   live: **both** phones in the same run needed 12 taps, not 11. Fixed:
   the loop now overshoots (up to 20 attempts) and polls for the Developer
   screen after each tap, so a dropped tap costs a few extra clicks instead
   of failing the run.
4. A real Android notification pulling the status-bar shade down over the
   app mid-run can cover it entirely (observed: a "QR Code" tap failure
   whose page-source dump showed only status-bar content, no app UI).
   Fixed defensively: `collapseNotificationShadeIfOpen` runs before opening
   the QR sheet.

With all four fixed, `yarn e2e:vrc:witnessed:tsp:android-only` passed clean
on two physical Android devices (`R5CN70Q6PDP`, `R5CY83SM4ST`): witness
sessions opened and VWCs issued over the TSP-enveloped carriage in **both**
directions, hardware-attestation evidence present, the full witness-share
chain (shared → verified → stored → receipted) confirmed, both contacts
showing Witnessed in their respective Contacts lists.

Also switched the emulator scripts to run **windowed by default** (a
developer can watch a run live), with `E2E_HEADLESS=1` to opt back into
headless for CI-style unattended runs — documented in `e2e/README.md`
rather than left as personal context, per the user's explicit correction
that this is a project convention, not something to carry only in an
agent's own memory.

## What this supersedes

**§4.2's "Convergence of the legacy stack (VRC-over-TSP, witness ops as
Trust Tasks) remains a deliberate later phase"** no longer describes
current status accurately for either half. As of `2026-09-02` (the prior
entry) wallet-to-wallet Trust Task documents can carry a real TSP envelope
over the existing DIDComm-v1 connection, dev-flag-gated; as of this entry
the witness itself accepts the same documents over that carriage too, and
both are live-proven end to end on real devices. **What is still true and
unchanged**: this is dev-flag-gated experimental capability, not the
default production posture — DIDComm-v1 binding 0.2 remains what a fresh
install actually uses, and no ecosystem counterparty (`vta-service`,
`openvtc` CLI, another implementer) exists for any of this yet, exactly as
[`2026-09-02-bam.md`](./2026-09-02-bam.md)'s "what this unlocks" section
already established. The plan's §4.2 line and `trust_tasks_subtask.md` §9
step 5 are updated in the same commit as this entry to say so.
