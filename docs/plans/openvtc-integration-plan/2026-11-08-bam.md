### A finding the report did not make

`digestBytesEqual` (`@bifold/trust-tasks`, `documentProof.ts`) already existed and its comment says it compares `z` and `u` spellings. It **could not decode `u…`**: credo's `MultiBaseEncoder` has no decoder for the base64url multibase prefixes (`MultiBaseEncoder.decode('u…')` throws "No decoder found for multibase prefix 'u'"; `encode(…, 'base64url')` throws "Unsupported encoding"), and the function's `catch` turned that into `false`. Switching the session compares to `digestBytesEqual` alone would have changed nothing for the peer's digests. The decoder now handles `u` and `U` itself. Existing callers (`witnessCeremony`, `outcomeEvidence`, `vtiVetting`) get the fix too; their behaviour for `z` digests is unchanged.

## Part II — What changed (bifold `interop-weekend`, commit `654378891`)

1. **Digests compared as decoded bytes** in `sharedConnect.ts` (invitee) and `sharedConnectInviterCeremony.ts` (inviter): the stated digest on an inbound issue and the digest on a receipt. The receipt we send echoes the **sender's own spelling** of the digest once it is proven equal, so a peer that still compares strings finds its digest in it. A different digest in any spelling is still refused.
2. **A received credential that cannot be stored is said aloud.** The store call is wrapped: the exception is logged (`name: message`), the exchange is refused with `credential could not be stored`, and **no receipt is sent**, because a receipt says the credential is held. Before, the handler threw out with nothing logged.
3. **`digestBytesEqual` decodes base64url** (`u`, `U`; padded or not) without `Buffer`, since `@bifold/trust-tasks` must stay platform-neutral.

Tests: `documentProof.test.ts` (new `digestBytesEqual` block: spellings equal, different digests unequal, undecodable input is `false` and not a throw) and `sharedConnectSession.test.ts` (accepts a respelled stated digest and echoes it; completes on a respelled receipt; still refuses a different digest; a store failure logs, refuses, sends no receipt and ends `refused`). 41 tests across those two and `sharedConnectInviter.test.ts` pass. The wider `sharedConnect*` set was run once under load and passed apart from suites that only failed to load under contention; they pass when run alone. **Not run:** the full bifold suite; anything against Anton's CLI; anything on a device.

**Supersedes:** nothing in the plan. The inviter ceremony has no test for the respelled digest or the store failure; only the invitee session does.

## Part III — Not done, and why

- **Acknowledgement of a frame whose handler threw.** The drain in `VtiMediatorTransport.handleDelivery` leaves a frame queued on purpose ("what the queue is for"); `tspFrameUnopenable.test.ts` records the rule that only a *lasting* reason acknowledges a frame. A retry cap would drop a good frame on a transient error. The observed loop was caused by the store failure, which no longer throws. **Revisit only if it recurs** with the new logging. Unverified on a device.
- **Contact litter.** Cleaning up after a failed encounter means deleting a connection record that other flows may share. Needs a decision on what is safe to remove (an encounter that ended without any credential exchanged, and whose connection nothing else references), not a code change made in a hurry.
- **A name for the other side.** Two routes, both in their report: Keyring reads `_label` behind its developer flag, or the acceptance carries `ext: {"org.real-life.rltp": {"name": …}}`. Their group decides on `_label`. Lean: read the `ext` name, since it needs no developer flag, but that is not decided and nothing was built.
- **Which RLTP profile member the W3C store refuses.** Unknown until the new log line fires on a real run. Candidates (theirs): the third `@context`, the extra `credentialSubject` members, the fourth `type`, the `did:key` issuer. A run with their default credential, then one with `--plain-vrc`, narrows it. If it is the store and not Keyring's code, the credential may need to be stored in a form Credo accepts while `receivedVrcJson` keeps the signed original.

## Part IV — Operational findings from getting a dev build onto the phone

These cost real time and are recorded so they are not rediscovered.

1. **Side-by-side install.** The phone carries the store build (`asml.bkc.harvard.wallet`, versionCode 278). A plain debug build (versionCode 4, same id) fails with `INSTALL_FAILED_VERSION_DOWNGRADE`; the only remedy would uninstall the store app and wipe its data. `-PkeyringPushTest` (already in `app/android/app/build.gradle`) installs as `asml.bkc.harvard.wallet.pushtest` and `google-services.json` already carries that client. Used as `./gradlew assembleDebug --write-locks -PkeyringPushTest`.
2. **A desktop build has no `app/.env`.** `remote` does not sync gitignored files and `react-native-config` bakes `.env` into `BuildConfig` at build time, so the first APK had no `MEDIATOR_URL` and the app showed "There is no mediator to pickup messages from" although the mediator was healthy. The desktop mirror now has `app/.env`; `BuildConfig.java` containing `MEDIATOR_URL` is the check.
3. **`remote --pull` can report done on a bad copy.** The first pull finished with the right byte size and the wrong SHA-256 (`rsync --inplace` preallocates). Compare `sha256sum` before `adb install`. A checksum re-sync (`rsync -c --inplace`) repaired it; later rebuilds sync as a delta.
4. **A long-lived Metro can hold a stale file map.** One that had run 9 days returned `Unable to resolve module …/passGeometry` for a file that exists; the app sat on its splash screen. Restart with `--reset-cache`.
5. **The desktop mirror's `bifold/node_modules` is stale** (Oct 1) and `yarn install` in `bifold/` there fails on a `three@0.183.2` checksum mismatch (`three` is only a `witness-server` dependency). The checksum was not overridden. Bifold jest was therefore run on the laptop, after `yarn --cwd bifold/packages/dtg-vocab build`, with `systemd-run --user --scope -p MemoryMax=3G -p CPUQuota=200% nice` and `--maxWorkers=2`. Unbounded runs earlier in the day starved the machine.
