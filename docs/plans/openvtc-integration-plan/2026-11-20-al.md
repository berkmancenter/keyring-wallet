## Fixture

A locally built Affinidi mediator at affinidi-tdk-rs `c0a69f1e` (2026-10-03),
the last commit before the mediator moved to its own repository (#949), 20
commits after the deployed `55580615` (mediator 0.33.1). Default features, its
own Redis with persistence off, a `did:peer:2` naming `http://127.0.0.1`. This
is a **declared deviation**: the results below are plumbing and design
evidence, not the migration plan's M2 evidence, which needs a re-run on the
deployed version.

## Findings

### F1. Credo's v2 mediation client has nothing to talk to

The mediator's advertised protocols are pinned in source with no
Coordinate Mediation entry, deliberately (`discover_features.rs`,
`ADVERTISED_PROTOCOLS`, test `coordinate_mediation_is_not_advertised`, issue
#755). Live, it disclosed `discover-features/2.0`, `routing/2.0`,
`trust-ping/2.0`, `out-of-band/2.0`, `messagepickup/3.0`,
`atm/1.0/authenticate`, `report-problem/2.0`. Credo sends
`message-pickup/4.0`.

**Supersedes:** §7's row "Wallet ↔ wallet, v2: Keyring's Credo mediator in v2
mode", and the second-mediation-record design (`v2Routing.ts`, a Pickup 4.0
loop beside Pickup 2.0) as the route to the target mediator. That design still
describes the development Credo mediator; it does not reach the Affinidi one.

### F2. Two Credo wallets work through it the ref-18 way

The app's v2 agent configuration, each wallet signed in with its own
Credo-held `did:peer:2` over ATM, forwards addressed by DID: the first message
creates the inviter's connection, replies flow (10–16 ms live), and a message
held for an offline wallet arrives after reconnect and a Pickup 3.0
`delivery-request`. 7 rows passed.

### F3. A socket per contact does not scale; one mailbox per phone works

The mediator keeps one account and one live socket per DID, newest wins. The
design in §7.2 (mailbox DID signed in once; pairwise contact DIDs naming it;
Credo wraps for the mailbox key, the `did`-scheme transport forwards to the
mailbox the peer's contact DID names) passed 6 rows with three wallets: three
pairs, all six directions live on the right connections, no contact DID ever
signed in, every inbound frame a forward for the mailbox key, and an offline
wallet collecting from two senders on reconnect.

Two details the run settled:

- Credo follows contact DID → mailbox DID → mediator itself (its `did:peer`
  endpoint resolution), so the endpoint it hands the transport is the
  **mediator's** DID, and the forward it builds names the mailbox key as a
  **`did:key`**. Neither is an account at the mediator; addressing the outer
  forward to either strands the message. The mailbox DID comes from the peer's
  contact DID document.
- Credo's v2 invitation create reads `ourDid`, not `invitationDid`; the latter
  is only checked against `routing`.

### F4. Linkability, and the decision

Every contact DID names the phone's one mailbox DID, so two contacts who
compare documents can tell they reach the same phone; in v1 they cannot, since
the routing key there is the shared mediator's. The mediator learns nothing
new: it sees mailbox DIDs only. Alternatives: a socket per contact (F3 rules it
out) or a mailbox per group of contacts. **Decided 2026-11-20 (product owner):
one mailbox per phone, the trade-off accepted**, built so per-group mailboxes
stay possible.

### F5. No push wake

While a wallet was offline the mediator called nobody: a local webhook sink
recorded 0 calls (its control call recorded). Redis keyspace notifications do
fire when it stores (`RECEIVE_Q:xadd`, `SEND_Q`, `PEER_Q`, `MSG`), the premise
of the migration plan's D2 option W5 — a lead, not a design, until run against
a real gateway path.

### F6. Discover Features spelling

The mediator reads a query only as `{"feature_type": "Protocol"}`; the
specification's `{"feature-type": "protocol"}` gets an empty `disclose`.
Recorded upstream-facing as VTI-44. No effect on Keyring today.

### F7. DIDComm v1 mediation exists in the mediator, opt-in

`src/messages/v1_mediation.rs` (Coordinate Mediation 1.0, Message Pickup 2.0)
is present at `55580615` and `c0a69f1e`, behind the `didcomm-v1` cargo
feature and a configuration switch that defaults to disabled. Whether one
mediator could serve both versions is to be measured on a build of the
deployed commit with that feature; nothing here depends on it.
