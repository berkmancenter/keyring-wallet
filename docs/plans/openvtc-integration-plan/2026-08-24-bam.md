# Part I — the mediator delivery regression

Re-verification session on `feat/trust-tasks-integration` (main repo tip
`dc8ed99`, bifold pinned at `cbee4057`) ahead of merging further work: a plain
`yarn e2e:vrc:android-only` run (two `Pixel_8_API_33` emulators, Linux host, no
Xcode) surfaced a new, reproducible connect failure distinct from anything in
`docs/spikes/e2e-vrc-connect-findings.md` (2026-08-18) or this file's
2026-08-18/2026-08-20 entries — those are judged already fixed (see below);
this is a fresh regression or a previously-unobserved failure mode.

## Symptom

Wallet B pastes wallet A's relationship invitation and sends
`didexchange/1.1/request` through the shared production mediator
(`credo-mediator.asml.berkmancenter.org`). The wallet's own 60s "connecting"
watchdog (`FLOW_TIMEOUT_MS_NON_WITNESSED`, `chat-messages.tsx`) fires and shows
the timeout UI — the on-screen error a live observer sees. From the Android
side's logcat: the HTTP POST completes normally ("No response received." —
credo's normal log line for a body-less ack, not itself an error), but
Alice's mediator mailbox (`messagepickup/2.0/status` → `message_count`) stays
at **0** for the full test window (minutes), i.e. the message never reached
the recipient's queue at all. **Reproduced 3/3** independent runs, alternating
which side's contact assertion times out first (`Bob Baker` missing on one
run, `Alice Anderson` on another) — so the connecting side isn't fixed, only
whichever side's 120s `assertVrcReceived` timeout is checked first by the
harness.

## What was ruled out

1. **Not the two known-and-fixed transport bugs.** Both `2026-08-18`
   remedies — `RetryingHttpOutboundTransport` (`app/src/hooks/useBCAgentSetup.ts`,
   commit `b6b5eaf`) and `PickUpV2` polling replacing live mode
   (`bc-agent-modules.ts`) — are confirmed present at `dc8ed99` (`b6b5eaf` is
   an ancestor of HEAD). The bug reproduces anyway.
2. **Not the mediator's HTTP response status being swallowed.** Hypothesis:
   `DidCommHttpOutboundTransport.sendMessage` (`@credo-ts/didcomm`) never
   checks `response.ok` — a non-2xx with an empty/unparseable body falls
   into the same "No response received." branch as a normal successful
   forward ack, so a mediator error could be silently treated as success
   (this is upstream issue 4 in the spike doc's "worth reporting" list).
   **Tested and disproven**: patched the installed
   `@credo-ts/didcomm` build (`.yarn/patches/@credo-ts-didcomm-npm-0.6.3-b3cbe5f2a8.patch`)
   to throw `Mediator responded with HTTP ${status}` on `!response.ok`, so
   the existing `RetryingHttpOutboundTransport` wrapper would retry on a
   fresh connection. Re-ran the suite: same failure, and the new throw
   **never fired** — the mediator returns 2xx on every send in this failure
   mode. The patch was reverted (see `git log` — no trace left; the working
   tree is clean). Not a case for the upstream ask to be *wrong*, just not
   the cause of *this* symptom.
3. **Not the mediator server, and not this machine's general network path.**
   `curl` to the mediator's base URL: fast, consistent 404s (expected — POST-only
   endpoint), no drops across 3 attempts. More importantly: the host-side
   probe `tsp-reference/ref-06v1d-carrier` (`npm run start:mediated`) — two
   plain Node.js Credo 0.6.3 agents, **not** React Native, run from this same
   machine against this same production mediator — **passed cleanly**:
   mediation granted both sides, connection established, store-and-forward +
   pickup both green. This is the same probe the spike doc used on 2026-08-15
   to confirm the mediator; it still passes today. The mediator and the core
   DIDComm connection/pickup protocol logic in `@credo-ts/*` are not broken.

## Where this leaves it

The failure is localized to something the **React Native / Android runtime**
does differently from the passing Node.js probe on the exact same protocol
path. The one confirmed difference in the transport stack:
`@credo-ts/react-native`'s `agentDependencies.fetch` is `global.fetch` — RN's
own networking implementation (OkHttp-backed on Android) — not Node's
fetch/undici, which is what the passing host probe used. Nothing here proves
RN's fetch is the fault; it is simply the one asymmetry identified between a
passing path and a failing one, and it's an entirely different code path than
the credo-ts transport code the two known 2026-08-18 fixes and the new patch
attempt all target — none of those touch `global.fetch` itself.

**A data point, held loosely**: the very first run of this session
(before the branch mixup documented in the session transcript was caught and
corrected) accidentally ran this exact test against `bam/locality`'s pinned
bifold commit (`0ebd6f867`, a descendant of `cbee4057` via
`d75cf7ce merge: feat/trust-tasks-integration`) and passed cleanly, same
mediator, same emulators. `git log cbee4057..0ebd6f8673d9c32f7f83d854c37b46509eb4c74c`
in bifold shows only locality/BLE-peripheral commits in that range — nothing
that obviously touches connection or transport code — so this is **not**
strong bisection evidence on its own (could be a real fix hiding in an
unrelated-looking commit, could be one-run luck). Not chased further this
session; flagged so a future bisect knows the range and the caveat.

## Suggested next steps (needs decision / access, not yet done)

1. **Instrument, don't guess.** A dev-only diagnostic build that logs
   `response.status`, all response headers, and timing for every
   `DidCommHttpOutboundTransport.sendMessage` call (not just when the body is
   non-empty) would show directly whether the mediator's *response* differs
   between the RN send and the Node probe's send, or whether the divergence
   is entirely server-side after an identical-looking 2xx.
2. **Mediator server-side logs for a reproduced failure's exact window**,
   correlated by the request's `@id`/threadId (captured in the wallet's own
   logcat — e.g. thread `298e9fa6-c5e6-41b7-aed6-1dcca75f22c1` from one of
   this session's failed runs). Would show whether the mediator received and
   parsed the envelope at all, and if so why it didn't queue it for the
   recipient key. This is the fastest way to settle client-side vs.
   server-side, and needs infra access this session didn't have.
3. **Byte-level comparison**: capture the actual POST body the RN app sends
   (e.g. a temporary local proxy the emulator is configured to use, or
   logging the exact JSON `payload`/headers `DidCommHttpOutboundTransport`
   constructs) against what the Node probe sends for the equivalent message
   type, looking for a structural difference (header casing, content-length,
   an RN-`fetch` body-serialization quirk) the mediator might parse
   differently.
4. Re-run `yarn e2e:vrc:android-only` a few more times to firm up the
   failure rate (3/3 so far is already a strong signal, but more data would
   rule out "returns to green on its own" before spending time on 1-3).

## Resolution: root-caused with mediator server-side access (same day)

Brendan granted SSH access to the mediator host (`asml-identity`,
`/home/bam-asml-main/didcomm-mediator-credo`) to tail the `credo-mediator`
container's own debug logs live against a reproduced failure. This settles
the open question above — **superseding the "localized to RN's fetch"
paragraph**, which was a reasonable read of the client-side-only evidence but
was not the cause.

**Correlated a failing run end to end:** captured the mediator's docker logs
(`docker logs -f -t credo-mediator`) while re-running
`yarn e2e:vrc:android-only` (4th reproduction, still 100%). Cross-referenced
by timestamp and by the wallet's own logcat (`threadId`/`@id` on the
`didexchange/1.1/request`) against the mediator's log:

1. Alice's `coordinate-mediation/1.0/keylist-update` for her connection's
   recipient key (`did:key:z6MksLhS6YkGNvooFHSbF9cqSYkd2xX3NfuKwB6cGrkynEYC`)
   is received and answered `result: 'success'`.
2. Bob's `routing/1.0/forward` envelope (`to: 'DtSPWJVq3PKL8nbtZaezbTCdDPFBxneyFABgSanxs1kp'`)
   arrives at the mediator and is logged received. **Verified by direct
   base58/multicodec decode (`@multiformats/base-x`, cross-checked against a
   hand-rolled decoder) that `to` is exactly the correctly-derived raw verkey
   for Alice's recipient key above** — the wallet's key encoding is correct,
   not a client-side bug.
3. **Nothing else is ever logged for that forward — not even at DEBUG
   level, across the entire multi-minute run.** Read the mediator's actual
   installed source (`@credo-ts/core@0.5.19`, inside the running container)
   to find out why:
   - `MediationRepository.getSingleByRecipientKey` would throw
     `RecordNotFoundError` on a lookup miss, and `Dispatcher.dispatch`'s
     catch block explicitly calls `this.logger.error(...)` on any handler
     exception — confirmed present in the source. Since **zero ERROR/WARN
     lines exist anywhere in the captured log**, the mediation-record lookup
     is not the failure; it succeeds.
   - `MediatorService.processForwardMessage` calls
     `messagePickupApi.queueMessage(...)` inside a `switch
     (messageForwardingStrategy)` with cases for `QueueOnly`,
     `QueueAndLiveModeDelivery`, `DirectDelivery` — **no `default` case**.
     `queueMessage()` itself starts with `this.logger.debug('Queuing
     message...')`. **That line never appears in the log either** (same DEBUG
     level as everything else that *does* appear constantly), meaning the
     switch falls through with the message forwarding strategy matching none
     of the three cases — a **silent no-op**: no error, no queue, no
     delivery, ever.
4. **Why the strategy doesn't match `DirectDelivery` (the config default):**
   the *default* import is `DidCommMessageForwardingStrategy` from
   `@credo-ts/didcomm` — but the running container has **no
   `@credo-ts/didcomm` package at all** (`/app/node_modules/@credo-ts/`
   contains only `askar`, `core`, `node`). The running image was built
   **before** the repo's own `3a5ea51 chore: update repo to 0.6 alpha, add
   redis and dynamodb to mediator (#55)` migration — confirmed:
   `git merge-base --is-ancestor 3a5ea51 d9ff9cb` (the running image's tag,
   which is a commit sha — `d9ff9cb "Security upgrades"`) is **false**. The
   mediator repo's checked-out `HEAD` (`375518d`, many commits past the 0.6
   migration) has moved on to the same `@credo-ts/didcomm`-based architecture
   the wallet uses (credo-ts 0.6.3) — **the source has been fixed; the
   deployed container was never rebuilt from it.**

**Root cause: an operational drift, not a wallet or protocol bug.** The
production mediator container (`ghcr.io/openwallet-foundation/didcomm-mediator-credo/mediator:d9ff9cb`,
built 2026-07-27, "Up 5 days" at diagnosis time) predates the mediator repo's
own credo-ts 0.6 migration. Running pre-0.6 `@credo-ts/core` code against a
0.6.3 wallet, the two sides still speak compatible wire-level DIDComm (OOB,
didexchange, keylist-update all worked correctly), but the *old* mediator's
forward-handling code path silently drops every forwarded message because
its message-forwarding-strategy config resolution — built for a
`@credo-ts/didcomm` type that doesn't exist in this build — never resolves to
a value the `switch` recognizes.

**Fix is operational, not a code change here:** rebuild and redeploy
`credo-mediator` from current `HEAD` (or any commit ≥ `3a5ea51`) on the
mediator host. Nothing in `keyring-wallet` or `bifold` needs to change for
this specific failure.

## Second layer: the new image's default forwarding strategy doesn't fit this wallet

Redeployed `credo-mediator` on `375518d` (Brendan's explicit go-ahead;
`.env` also updated with the renamed `ASKAR__STORE_ID`/`ASKAR__STORE_KEY`,
straight values-copied from the old `WALLET_NAME`/`WALLET_KEY` — same wallet
identity, confirmed via `.env.example`'s documented rename, not a data
migration). First re-run: real progress (Bob's `didexchange/1.1/request`
now reaches Alice — the item above is genuinely fixed) but still failed,
alternating which side's contact assertion timed out — a **new, second**
issue, not evidence the first diagnosis was wrong.

Traced with the same live mediator-log correlation: Bob's request reached
Alice and she auto-accepted and sent back a `didexchange/1.1/response`
through the mediator — but Bob's log never shows receiving it. The new
image's `messagePickup.forwardingStrategy` **defaults to `DirectDelivery`**
(confirmed in `apps/mediator/src/config.ts`), which sends a forwarded
message only if the recipient currently has a live return-routing session
open — no fallback to queuing if not. This wallet deliberately runs
**`PickUpV2` batch polling, not live mode** (the `b6b5eaf` fix from
2026-08-18, still present at HEAD, exists *specifically* to avoid a
persistent live socket that can die silently). A polling client's
return-routing session is only open for the moment of each poll — `DirectDelivery`
against it is a coin flip on timing, which matches exactly what was
observed (worked once, by luck; failed the next hop).

**Fix:** `.env.example` documents the alternative —
`MESSAGE_PICKUP__FORWARDING_STRATEGY=QueueOnly`, which always queues
regardless of session state, and the next poll always finds it. Added to
`.env`, redeployed. **Result: `yarn e2e:vrc:android-only` passed clean —
both contacts visible, all trust-task ceremony markers present, no
timeout.** Both mediator fixes (image `375518d` + `MESSAGE_PICKUP__FORWARDING_STRATEGY=QueueOnly`)
are live in production as of this session.

# Part II — exchange durability: a persisted state machine instead of timeouts

## The question

Can the VRC and witnessed-VRC exchanges be converted off wall-clock timeouts
and off the assumption that both apps stay open and foregrounded, onto state
that is persisted and advanced as messages are sent and received — so an
exchange survives delivery flakiness, delays, and an app being closed and
reopened?

**Finding: yes, and the trust-task recast already built most of the
substrate.** The work is predominantly moving continuations out of the
JavaScript stack and into storage that already exists, not inventing new
persistence. This part is a **proposal, not an adopted design** — nothing here
is written into [`trust_tasks_subtask.md`](./trust_tasks_subtask.md) yet, and
§4 below names one question that needs a decision before it can be.

Scope note: this is a durability investigation, not a review of Part I's
transport fixes. It reads on the *same* symptom class from the other side —
Part I fixed why messages were lost; this asks what the wallet does when a
message is merely *late*, which the mediator fixes do not address.

## 1. Where the exchange's state actually lives

Every piece of in-flight exchange state that is not a Credo record or a
retained Trust Task document is a module-level `Map` that dies with the JS
context — i.e. with a reload, a crash, or an agent restart.

**Legacy flow** (`bifold/packages/core/src/modules/vrc/vrc-manager.ts`):

| State | Where | What loss costs |
|---|---|---|
| `pendingWitnessedVrcs` | `:973` | The built VRC and its verification method, awaiting `session-challenge`. On loss the challenge arrives and hits `'Received session-challenge but no pending VRCs found'` (`:1126`) — this side dies silently while the peer waits out its own timeout |
| `pendingVrcIssuanceAfterWitness` | `:994` | The prepared credential **including the hardware-attestation evidence the user already authorized with a biometric**. Loss means a stall or a second biometric prompt for work already done |
| `sessionChallengeTimeouts` | `:150` | A 90 s wall clock (`:47`) that makes a *protocol* decision: on expiry it calls `autoFallbackWithoutWitness` (`:1751`–`:1758`), silently downgrading a witnessed exchange to an unwitnessed one |
| `vrcFlowStore` / `witnessStatusStore` | `witnessStatusStore.ts` | In-memory `EventEmitter`s. `VrcFlowError` carries `onRetry` / `onProceedWithout` **closures** (`:52`–`:55`), which cannot be persisted in any form |

**Trust-task flow** (`bifold/packages/core/src/modules/trust-tasks/`):

| State | Where | What loss costs |
|---|---|---|
| `pendingProposals` | `ceremony.ts:511` | A received `propose` awaiting user consent. The *document* is persisted; the awaiting-consent fact is not. On loss the consent modal never returns and the exchange stalls permanently, with no error sent to either party |
| `pendingWitnessResponses` | `witnessCeremony.ts:49` | The whole witness session (open → challenge → submit → VWC) is one `async` function whose continuation is a live stack frame plus a 60 s timer (`:65`–`:74`, `:105`). A reload anywhere inside it loses everything; the VWC arrives later, `resolveWitnessResponse` returns false, and the document is retained but never acted on — the log line already exists at `ceremony.ts:399` |
| discovery-answer poll | `ceremony.ts:974`–`:977` | Six 5 s polls waiting for a peer's discovery answer before the witness-share is either sent or silently skipped |

The common shape: **the decision to give up is made by elapsed time, and the
information needed to resume is held only in a stack frame.** Those two
properties together are what makes delay indistinguishable from failure.

## 2. What the recast already gave us

The trust-task work did the structurally hard part, which is why the estimate
here is modest:

- **Every exchange already has a durable identity and a durable log.** The
  `propose` document id is the exchange thread; witness sessions nest under it
  via `parentThreadId` (`witnessCeremony.ts:113`–`:122`); every document is
  retained verbatim in `TrustTaskDocumentRepository`, tagged
  `exchangeId / typeUri / role / connectionId`
  (`services/TrustTaskDocumentRecord.ts:58`–`:70`). The subtask plan already
  states the intent — the thread is *"a durable artifact to be retained, not a
  transient routing device"*, and *"the exchange becomes reconstructable from
  the thread"* ([`trust_tasks_subtask.md`](./trust_tasks_subtask.md) §5).
- **Idempotence is already implemented as a query against that log**, not as a
  flag: `deliverVrcViaTrustTaskForExchange` checks prior issues before
  delivering (`ceremony.ts:648`–`:653`), and the witness-share does the same
  (`ceremony.ts:991`). That is exactly the property a resumable machine needs,
  already in place and already exercised.
- **The trust-task witness session is per-party, not a two-party rendezvous**
  (`WitnessTaskSessions.ts` opens a session from one wallet's `parties`
  payload). This removes the deepest cause of the legacy 90 s timeout: the
  counterparty no longer has to be online at the same moment.
- Credo persists its own protocol state, so a persisted exchange record is
  idiomatic to the stack rather than a foreign concept.

The consequence worth carrying forward: **most of the states are already a
fold over documents that are being persisted today.** A
`deriveExchangeState(agent, exchangeId)` projection over
`TrustTaskDocumentRepository` yields
`proposed → accepted → witness-session-open → witness-submitted → witnessed →
vrc-delivered → receipt-received → share-sent/received → complete` with no new
record at all. Only three facts are not on the wire and therefore need genuinely
new storage: the prepared credential plus its biometric evidence, the
awaiting-consent flag, and a last-error for the UI.

## 3. The proposed design

1. **A `RelationshipExchangeRecord`** (Credo `BaseRecord`, tagged by
   `exchangeId` and `connectionId`) holding the state enum, `updatedAt`,
   `lastError`, and the three non-wire facts above. Everything else is derived
   from the document log, so state and evidence cannot drift apart.
2. **One `advanceExchange(agent, exchangeId)` step function.** Read state, do
   the next thing, persist, return. Every inbound handler becomes *retain
   document → advance*. No `await` on a promise that a later inbound message
   resolves — which also removes the hazard the code already works around with
   fire-and-forget `void` calls and an explicit deadlock comment
   (`ceremony.ts:1193`–`:1198`).
3. **Timers become UI hints, never protocol decisions.** The 90 s timeout stops
   choosing "unwitnessed"; the state stays `witness-requested`, the overlay says
   so, and the *user* may choose to proceed. A witness that answers late is
   still handled correctly.
4. **A reconciliation sweep** on agent init and on foreground: load every
   non-terminal exchange and `advance` it. This is the piece that delivers
   "closed and reopened" — messages that arrived while the app was dead are
   sitting in the mediator queue and land on the next pickup.
5. **Error closures become a discriminated action enum**
   (`{action: 'retry-witness-submit', exchangeId}`) resolved against persisted
   state, so a dialog can be rebuilt after a restart instead of being lost with
   its callbacks.

## 4. What a wallet-side state machine does not fix

Four constraints, stated because each one can quietly invalidate the benefit:

- **The witness is as ephemeral as the wallet was.** Its sessions are in-memory
  `Map`s with TTLs — `pendingSessionRequests` at 3 minutes
  (`witness-server/src/WitnessService.ts:427`), `activeSessions` at the
  configured expiry (`:2156`), trust-task `sessions` at 10 minutes
  (`trustTasks/WitnessTaskSessions.ts:67`, `:77`) — and all of them are lost on
  a witness restart. Wallet-side durability past ~10 minutes buys nothing until
  the witness persists sessions (it already has `PersistentJsonStore` and a
  Redis-backed `CredentialRegistry`, so there is a home for them) and its TTLs
  are lengthened or removed.
- **"Survives the app being closed" means "resumes correctly on next open",
  not "completes while closed."** Message pickup is stopped on background
  (`bifold/packages/core/src/contexts/activity.tsx:79`) and the wallet locks on
  inactivity. Real background progress needs push or background fetch, and
  neither can run a biometric. The machine should therefore treat a biometric
  as a **checkpoint it parks at** (`awaiting-user-biometric`), never as
  something a resume path attempts unattended.
- **The legacy flow should not be retrofitted.** Its witnessed path requires
  both wallets inside the witness's 3-minute pairing window
  (`WitnessService.ts:427`) — not fixable without changing that protocol, and
  the v4 dialect already fixed it structurally. Build the machine on the
  trust-task dialect, which `vrc-manager.ts:1825`–`:1831` already stands the
  legacy witness flow down for, and let the legacy path keep its timeouts.
- **Open question, needs a decision: resumability versus challenge freshness.**
  An indefinitely resumable witness session weakens exactly the property the
  challenge exists to provide. The proposed resolution is *resumable but
  re-challengeable* — on resume, request a fresh challenge on the existing
  session thread rather than replaying a stale one — but that is a change to
  the witness-session leg's shape, so it is a specification question for the
  `witness/session` family, not a local implementation choice. **Blocked on
  that call**; the rest of the design does not depend on it and can proceed.

## 5. A defect found on the way (independent of any of the above)

`contexts/activity.tsx:98` restarts pickup on foreground as
`initiateMessagePickup()` with **no strategy argument**. Credo then falls back
to the configured value —
`DidCommMediatorPickupStrategy.Implicit` (`app/src/utils/bc-agent-modules.ts:130`)
— confirmed by reading the installed build: `initiateMessagePickup` resolves
`pickupStrategy ?? await this.getPickupStrategyForMediator(mediatorRecord)`
(`@credo-ts/didcomm/build/modules/routing/DidCommMediationRecipientApi.mjs:134`).
Startup explicitly passes `PickUpV2` (`app/src/hooks/useBCAgentSetup.ts:67`–`:72`);
the resume path does not.

So **after a single background-and-return, the wallet spends the rest of its
session on Implicit live mode** — the path this repo's own comment
(`useBCAgentSetup.ts:59`–`:66`) documents as silently lossy, and the same live
-versus-polling mismatch Part I ran into from the mediator's side. It is a
one-line fix, it is worth making independently of the state-machine work, and
it is plausibly a contributor to flakiness attributed to the exchange logic.

**Not yet fixed or measured** — identified by reading, not by a reproduction;
no e2e run has been done against it. The e2e suite backgrounds nothing, so it
would not currently catch this.

## 6. Proposed phasing

Each phase is independently shippable, ordered by value per unit of risk.

1. **Fix the pickup-strategy regression** (§5), and persist the two facts whose
   loss costs the user a biometric or a permanent stall: `pendingProposals` and
   the prepared-credential/evidence pair.
   *Done when:* a proposal awaiting consent survives an app restart and the
   modal returns; a witnessed exchange interrupted after the biometric resumes
   without prompting a second time; foreground resume logs
   `Starting explicit pickup … using v2`.
2. **Add `deriveExchangeState` and `advanceExchange`**, and convert the witness
   ceremony from an awaited stack to persisted steps.
   *Done when:* `pendingWitnessResponses` and its 60 s timer are gone; a VWC
   delivered after a reload is consumed rather than logged at
   `ceremony.ts:399`; the ceremony unit tests cover resume-from-each-state.
3. **Reconciliation sweep on init and foreground**; convert error closures to
   action enums.
   *Done when:* an exchange killed at any leg completes after a restart with no
   user action beyond unlocking; `WITNESS_BACKGROUND_TIMEOUT_MS` no longer
   selects a fallback, only UI copy.
4. **Witness-side session persistence**, TTL review, and (pending §4's open
   question) re-challenge on resume.
   *Done when:* a witness restart mid-ceremony does not fail the exchange; an
   attended two-device run with one wallet backgrounded for >10 minutes
   mid-exchange completes witnessed, with hardware attestation intact.

## 7. Related

Parent: [`trust_tasks_subtask.md`](./trust_tasks_subtask.md) §4 ("Two threads")
and §5 (the thread as a durable artifact) — this part proposes cashing in the
durability that section already asserts. Part I above is the transport-side
counterpart on the same symptom class.
