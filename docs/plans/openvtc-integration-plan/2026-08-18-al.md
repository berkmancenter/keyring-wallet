## A. The e2e:vrc path is green on the production mediator — five defects deep

The two-device suite (`Pixel_6_API_33` + iPhone 17 simulator, prod
`credo-mediator.asml.berkmancenter.org`) went from unable-to-connect to green
with the Trust Task exchange asserted, through five distinct defects. Full
diagnosis chain with evidence: `docs/spikes/e2e-vrc-connect-findings.md`.
Summary of what was concluded:

1. **iOS stale keep-alive sockets** — the mediator side drops idle TCP after
   ~45–50 s; NSURLSession reuses the dead socket and never retries POSTs.
   Fixed app-side (`RetryingHttpOutboundTransport`). An earlier h3/QUIC theory
   was disproven and is recorded as a red herring.
2. **Live-mode pickup loses messages** — the PickUpV2 live-mode websocket dies
   silently (credo's reconnect only fires on close events) and the mediator
   live-pushes into the dead socket without requeueing. Superseded position:
   live mode (adopted in the Phase-4-lite work) is withdrawn in favor of
   PickUpV2 polling (10 s) — the batch protocol's request/ack semantics mean
   nothing is lost and dead sockets self-heal per tick.
3. **Dev-bundle dynamic import** — `import('../trust-tasks/ceremony')`
   compiles under Metro to a split-bundle fetch that fails at runtime in dev
   builds, so the propose had never actually executed before 2026-08-18.
   Inline lazy `require()` keeps the module-cycle break in-bundle.
4. **relationshipDid race** — with the propose actually running, the
   basic-message issuance trigger could look up `myRelationshipDid` ~25 ms
   before its creation landed and silently abort one issuance leg. Fixed with
   a bounded lookup retry. Standing hazard recorded:
   `getOrCreateRelationshipDid` is find-then-create and not concurrency-safe —
   parallel calls can mint divergent DIDs for one counterparty.
5. **Intermittent iOS no-send (OPEN)** — 2 of 7 runs: iOS as invitee creates
   the connection record and opens chat, but no didexchange request ever
   reaches the wire (zero CFNetwork attempts). Silent because credo's accept
   observes record state while the send runs in background, and iOS surfaces
   only error-level JS logs. Android as sender is clean (roles-flipped
   control). Blocked on adding iOS-side JS observability, not on anyone.

## B. §9 step 6 has started, sliced: propose + issue live in Keyring

Two capability-gated slices landed on `feat/trust-tasks-integration`
(bifold `006eea9`→`e8f7410e` lineage), both e2e-proven same day:

- **Propose** (first slice): `vrc/relationships/propose/0.1` + `#response`
  over the binding-0.2 carriage, deterministic proposer (lower connection
  DID), gated on the legacy `rceVersion` announcement at **v4** — the
  `trust-task-discovery` replacement the step ultimately wants is not built
  yet. Both dialects write the same `RelationshipDidRepository` state.
  Measured: ~650 ms round trip, interleaved with legacy issuance at zero
  wall-clock cost.
- **Issue** (second slice, shadow): each side delivers its signed VRC as
  `vrc/relationships/issue/0.1` on the exchange thread; receiver verifies
  party bindings against the accepted proposal, receipts with
  `vrcDigestMultibase` recomputed over the credential as accepted; refusals
  and pipeline rejections return as `trust-task-error` on the connection.
  **Shadow means** the legacy issue-credential 2.0 leg remains the storage
  authority — the task proves and receipts delivery; flipping authority is a
  later slice.
- **Proof production pulled forward from milestone 3**: the staged spec
  declares the issue request proof REQUIRED and the 0.9 runtime rejects a
  proofless document regardless of policy, so shipping the leg at all
  required a real signer. `documentProof.ts` signs
  DataIntegrityProof/eddsa-jcs-2022 with the sender's relationship DID via
  the KMS (key id from the DidRecord key mapping, legacy fingerprint id as
  fallback — `publicJwk.keyId` alone throws for these keys). Verification
  remains `acceptUnverified` until milestone 3 wires the verifier; the
  proofs are real, so nothing re-ships then.
- **The e2e suite now gates on the ceremony**: `run-vrc-exchange.js` requires
  a propose marker plus "issue sent" / "issue receipt sent" /
  "issue receipt matched" from run-scoped logcat before PASS. This gate
  caught its first real defect (the keyId resolution) on its first run — a
  failure invisible in the UI, since the legacy leg still completes.

Evidence for both slices (payloads, proofs, timeline):
`docs/spikes/trust-task-propose-evidence.md`.

## C. Plan corrections applied to `trust_tasks_subtask.md` §4 Layer A

The Layer A table and declarations were written 2026-08-05, before the
specification drafting (staged as Mickens-Lab#3, reviewed in the 08-11/08-15
documents) settled the final shapes. Implementing against the published
`0.9.x` bindings surfaced the drift; the plan now states the staged spec's
positions. Superseded positions, recorded here:

- **Receipt = `IssuedCredential` from `credentials/_shared/0.1`** →
  superseded by the **recomputed-digest receipt** (`vrcDigestMultibase` over
  the RFC 8785 canonicalization of the credential *as stored*). The spec's
  own rationale drove this: both directions share one `threadId` and a
  `#response` carries no `inResponseTo`, so only a recomputed digest can say
  *which* delivery a receipt answers — a copied identifier attests nothing.
- **Payload member `vc`** → **`vrc`** (and the digest member beside it).
- **`proof: RECOMMENDED` on issue** → **request REQUIRED / response
  OPTIONAL**: the delivery is retained-and-relied-upon (the §4.7.1
  condition), and the envelope proof attributes the delivery itself on a
  relayed path; the receipt is consumed inside the exchange under authcrypt.
- **Error codes `subjectMismatch` / `unsupportedFormat`** → a single
  **`notAccepted`** ("does not match the accepted proposal, or arrives
  outside an accepted exchange") — the accepted proposal is the
  authorization evidence, so every refusal is the same statement.

## D. Hardening round, same evening: the verifier lands, plus two guards

Second working block of the day (the morning's sections stand; this extends
them per the one-file-per-author-per-session rule):

- **The eddsa-jcs-2022 verifier replaced `acceptUnverified` on the issue
  legs** — the milestone-3 item the module comment promised. Attribution
  semantics chosen: the proof must verify under the sender's relationship
  DID *as the accepted proposal established it* (an expected-controller
  check), so a valid signature under any other key fails; a delivery outside
  an accepted exchange still refuses `notAccepted` rather than
  `proofInvalid`, because the accepted proposal is the authorization
  evidence and that is the more accurate statement. Verified live: run 8's
  receipts only issue after pipeline consumption under the verify policy, so
  both directions' wire proofs passed real cryptographic verification.
  Propose legs stay on the service default — their proofs are OPTIONAL and
  unsigned, and at propose time the would-be controller is exactly what the
  document delivers.
- **A didexchange watchdog for the intermittent iOS no-send** (finding A5):
  after any invitation accept, bifold checks connection progress at 12 s and
  30 s and logs at ERROR level — deliberately, since error is the only JS
  log level that reaches the iOS system log — turning the silent failure
  into a diagnosable breadcrumb. Silent on healthy runs.
- **`getOrCreateRelationshipDid` serialized** — concurrent callers share one
  in-flight creation per counterparty DID, closing the divergent-DID hazard
  section A recorded, with a regression test exercising the race window.

Six new unit tests (five real-crypto verifier cases, one `proofInvalid`
pipeline case) plus the three-case concurrency suite; 200 tests green across
the trust-tasks and vrc modules; e2e run 8 green with the ceremony-marker
gate.

## E. Third working block: the authority flip lands, consent moves to the proposal

Decision taken this block (the fork the flip could not proceed without):
**the user's consent is accepting the RELATIONSHIP PROPOSAL, not each
credential**. Adopted over the alternative (keeping a per-credential accept
fed from the task) because it is the design §4 argues for — `shouldIssue`
as a stated, answered field — and it removes the double-ask. The UX: the
non-proposer's wallet shows a bottom-sheet ("X wants to form a relationship
with you", Accept/Decline); the proposer's user consented by creating or
accepting the invitation. Old peers keep the legacy flow untouched.

What landed, e2e-proven (run 9: consent prompt tapped on iOS, exchange
propose→stored receipts in ~5.5 s, both contacts visible, marker gate green
including the new "issue stored"):

- Inbound proposals are consent-gated: nothing answers until the user does;
  a decline is a `trust-task-error` with `vrc/relationships/propose:declined`
  (the spec forbids `accept: false`).
- On acceptance each side builds its VRC (shared preparation, hardware
  attestation evidence included), signs it standalone via the registered
  DataIntegrityProof suite, and delivers it as the proof-bearing issue leg.
- The receiver verifies document proof, credential proof, and party bindings,
  then STORES from the task (digest-deduplicated) and receipts — the task is
  now the storage authority.
- The legacy VRC offer is suppressed for v4 pairs (`v4 pair — VRC rides the
  trust-task issue leg; issuing RCard only`); the RCard still travels the
  legacy leg and auto-accepts, so contact naming is unchanged.
- The old credential-Done shadow trigger was removed as dead code; the flow
  overlay reuses the existing offer-sent/offer-received completion semantics,
  so the chat progress/timeout UI needed no surgery.

Superseded position (mine, from block D's framing): the flip as "a later
slice, after a separate consent-UX design round". Alberto took the consent
decision in-session, and the shadow-mode language in section B's issue-leg
description no longer describes the code.
