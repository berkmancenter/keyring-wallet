## Correction: the "Node reference-adapter fixtures" item is blocked, not unstarted

The prior entry (and `trust_tasks_subtask.md` §9 step 4, before this commit)
described the one remaining "done when" item — "the same fixtures pass in
Node against the reference adapter" — as a standalone piece of unstarted
work, parallel to the round trip just closed. Checking the parent plan
(`openvtc-integration-plan.md`) before picking it up: it isn't standalone.
**"The reference adapter" is `ref-07-credo-adapter`'s raw-key implementation**
(§4.4, Phase D) — extracting the `SigningKey`/`KeyAgreement`/`VidResolver`
ports from the Phase A–B cores and keeping a raw-key implementation of them as
the reference adapter, so the same fixture suite can run against it and
against `credo-tsp-adapter` (Askar-backed). That rung has an explicit 2–3
week estimate in the plan and, per step 1's finding this branch already
established, **no `tsp-core` package or port set exists anywhere in this
codebase yet** — there is no reference adapter to run fixtures against.

So this item was never "the next thing to build inside step 4" — it's a
downstream consequence of Phase D landing, tracked here because step 4's
interop evidence is meant to feed it once it does. Building a standalone
"reference adapter" scoped only to credential-exchange, ahead of and separate
from `ref-07`'s actual port extraction, would create exactly the "duplicated
task spine" / premature-abstraction problem step 1's A1 resolution avoided
for the carriage — a second, narrower port set that `ref-07` would then have
to reconcile or discard.

## Naming collision worth flagging, not fixing here

The parent plan's ladder reserves `ref-08-rn-hello` for a Phase E rung ("The
ref-00 + ref-03 cores imported unchanged into a dev screen in the app"). The
credential-exchange conformance work from the last several sessions used the
directory name `tsp-reference/ref-08-credential-exchange` instead — a real
numbering collision between the plan's table and what's on disk, not just a
coincidence of two different "08"s. It doesn't cause any functional problem
(different directories, different purposes, the credential-exchange rung
fits the same "exercises upstream, stays portable" category as ref-00–06 per
§Phase-C's own classification) but the next rung actually built under this
family should account for it — either renumber the credential-exchange
directory or skip `ref-08` in the plan's own table when Phase E starts, so
`rn-hello` doesn't collide on disk with a script that already exists under
that name. Left alone here; not blocking anything, and renumbering an
existing, referenced-elsewhere directory is not this entry's call to make
unilaterally.
