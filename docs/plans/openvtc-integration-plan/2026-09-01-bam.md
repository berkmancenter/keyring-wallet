# 2026-09-01 — Brendan and the agent

Follow-up to the 2026-08-24 mediator regression entry (`2026-08-24-bam.md`) on
`feat/trust-tasks-integration`: that entry root-caused and fixed the shared
production mediator's forwarding strategy (`QueueOnly`) for the *wallet-to-wallet*
path. It did not cover the witness-server, which turned out to have the
matching half of the same class of bug, unfixed, the whole time.

## Finding

`yarn e2e:vrc:witnessed:android-only` (two physical Android phones, attended)
failed 4/4 identically at `witness.waitForParticipants` — *"only 0/2
participant(s) connected"*. Root cause: the witness-server's mediation-recipient
config used `MediatorPickupStrategy.Implicit` — push-only, issues no pickup
requests — against the same `QueueOnly` mediator the 08-24 fix targeted, which
only queues and never pushes. The witness could send (mediation request,
`keylist-update`, locality heartbeats) but received nothing, ever, with no
error on either side. The wallet was moved onto explicit `PickUpV2` polling on
2026-08-18 (`bc-agent-modules.ts`) specifically to fit this same mediator's
`QueueOnly` behavior; the witness-server was never given the equivalent.

Full diagnosis chain, the A/B evidence proving it (including that mediator
mode itself is not the problem — a fresh wallet with the pull strategy fixed
passed cleanly through the same mediator), and the "why did this look
machine-specific" mechanism (a value persisted on a wallet's MediationRecord
outranks module config) are in `docs/spikes/e2e-vrc-connect-findings.md`
("fourth failure layer") — not duplicated here.

## Decision: DIRECT is the primary architecture; MEDIATOR is a supported,
now-tested fallback

Both matter, for different reasons, and both are now proven working on real
devices (see below):

- **DIRECT** (the witness's own HTTP endpoint, tunneled for e2e) is lower
  latency for the live ceremony — direct HTTP is synchronous; a mediated hop
  costs up to a full `mediatorPollingInterval` each way — and keeps the
  witness's traffic off the same shared mediator that already sees the two
  wallets' own relationship, which matters for a system whose purpose is
  attesting relationships. This is the recommended default.
- **MEDIATOR** avoids the operational cost of a witness needing a stable,
  publicly reachable endpoint (TLS, DNS, uptime) — real for an operator who
  can't or won't expose a public port — and is a legitimate disaster-recovery
  lever if a witness's direct endpoint has an outage: flipping to mediator
  mode is one env var, not a cancelled event. That lever was dead the whole
  time this bug existed; a fallback nobody tests is worse than no fallback.

## Applied

- `startMediatorMessagePickup` / `assertSupportedMediatorPickupStrategy` in
  `@bifold/vrc-shared` (`src/mediation.ts`) — passes the pickup strategy
  explicitly wherever a credo agent talks to a mediator, bypassing both module
  config and any value persisted on the wallet's MediationRecord. Wired into
  the witness-server, `vrc-reference/BaseAgent.ts`, `core/utils/agent.ts`, and
  the app's foreground-resume path (`core/contexts/activity.tsx`, which was
  separately leaking a duplicate polling loop on every resume — caught by the
  same fix). A repo-wide static-analysis guard
  (`mediatorPickupStrategy.guard.test.ts`, in both bifold and `app/`) fails the
  build if any file declares an unreceivable strategy or omits an explicit one
  on `initiateMessagePickup()`, so this class of bug can't reappear silently.
- `e2e/lib/witness.js` no longer lets a developer's local, gitignored
  `bifold/packages/witness-server/.env` decide the witnessed e2e's transport —
  `MEDIATOR_INVITATION_URL` is passed explicitly by the harness (this was the
  mechanism behind "works on my machine, not on Brendan's": Alberto's
  `.env` has it commented out, so his witness only ever ran DIRECT and never
  touched the broken path) — and the witness's own startup banner is read back
  and asserted against what was requested.
- **`yarn e2e:vrc:witnessed:android-only:mediator`** — a new, dedicated variant
  that deliberately runs the witness in MEDIATOR mode (reusing `app/.env`'s own
  `MEDIATOR_URL`, so it's a real test against production infrastructure), so
  the fallback gets exercised on demand instead of only when someone remembers
  to set an env var by hand. This is the direct fix for how the bug survived —
  nothing had run this path before.

**Confirmed on device (2026-09-01):** both `yarn e2e:vrc:witnessed:android-only`
(DIRECT) and the new `:mediator` variant passed on the same two physical
Android phones against the same production mediator — first run after the fix,
both transports. Full run detail in the spike doc.

## Still open

- No `mediatorPollingInterval` set for the witness (credo's 5s default now
  applies, where previously it polled not at all — new behavior, not a
  regression, but worth measuring against the wallet's tuned 1s cadence).
- No periodic/CI job runs the `:mediator` variant automatically — manual, on
  demand, for now.

## What this supersedes

Nothing in the plan's prior text claimed the witness-server's mediator support
was tested or working — it was simply never mentioned. This entry is the first
record of the witness's transport architecture as a decision rather than an
unstated default.

## Trust Tasks over DIDComm v1 — review A1 resolved in code

New branches, `feat/trust-tasks-over-didcomm-v1` (both the app repo and the
bifold submodule), forked from `fix/mediator-pickup-strategy` above rather
than from `main` — the mediator pickup-strategy fix is a precondition for
running the witnessed e2e at all, so this work needed it underneath. Verified
before branching: every commit on `feat/trust-tasks-integration` not already
on `main` is an ancestor of the pickup-strategy branch, in both repos (bifold:
43/45, the 2 missing being unrelated credential-list UI fixes; app: 52/52) —
so the recast (subtask §9 steps 5–7) and this fix are not actually diverged
work, just unmerged.

### Finding

`trust_tasks_subtask.md` §9 step 1 ("resolve review A1 — `tsp-core`'s
dependency direction") had stood open since the subtask was written, carried
in every status note as "outside this milestone... TSP-side." That framing
turned out to be wrong: A1's disposition in `2026-08-05-bam.md` — "✅ Applied
— §5.2 wires `TT --> CARRIAGE`, `WIRE` implements it" — was a **plan-level**
resolution only. Nothing in `feat/trust-tasks-integration`'s code enacted it.
`ceremony.ts`'s `sendTrustTaskDocument` and `setupTrustTasksInbound` called
Credo's `DidCommMessageSender` / `DidCommMessageHandlerRegistry` directly,
inline — exactly the "recast carries its own model" fallback §8.1 said would
need "rethinking" if A1 went unresolved. It didn't get rethought; steps 5–7
were simply built on top of it, and it worked, because there was no TSP wire
package yet to create the coupling A1 warns about. That's also why the step's
literal "done when" (task model compiles with the TSP wire package absent
from its dependency graph) was already vacuously true and not a useful signal
to keep chasing.

### Decision

Don't build the `tsp-core`/`credo-tsp-adapter` package split §5.2 describes.
`@bifold/trust-tasks` already plays `tsp-core`'s role for the one carriage
that exists; a second, separate package now would be the duplicated task
spine §8.1 warns against, not a fix for anything. Instead: extract the
`Carriage` port in place — a zero-dependency interface
(`{ send(document, peer), onDocument(handler) }`) in `@bifold/trust-tasks`,
and move the existing Credo-specific send/receive logic behind it
(`DidCommV1Carriage`, `packages/core`) rather than leaving it inline in
`ceremony.ts`. This is the smallest change that makes the dependency
direction `TT --> CARRIAGE <-- WIRE` real for the carriage that exists today,
so a future TSP carriage (or DIDComm v2) implements the same port without
touching the task model or any of its callers.

Deliberately left alone: `documentProof.ts` (digests, `eddsa-jcs-2022`
sign/verify) still takes an `Agent` and calls Credo's KMS and DID resolution
directly. That's a real, separate coupling — the `SigningKey`/`VidResolver`
ports §5.2 also names — but it's §4.3's territory (crypto custody, already
"RESOLVED PATH" there) and a different, larger, riskier change (8 call sites
across two packages doing real signing/verification, versus this step's one
send path). Scoping A1 to the carriage only kept this change reviewable and
low-risk; §4.3's ports remain undone in code and should not be assumed closed
by this entry.

### Applied

- `packages/trust-tasks/src/carriage.ts` — the `Carriage`, `CarriagePeer`,
  `CarriageDocumentHandler` types. No imports.
- `packages/core/src/modules/trust-tasks/module/DidCommV1Carriage.ts` —
  `createDidCommV1Carriage(agent)`, wrapping the same
  `DidCommMessageSender`/`DidCommOutboundMessageContext`/
  `DidCommMessageHandlerRegistry` calls `ceremony.ts` used to make inline.
- `ceremony.ts` — `sendTrustTaskDocument` and `setupTrustTasksInbound` now
  delegate to the port; their own signatures are unchanged, so none of their
  callers (the app's `useBCAgentSetup.ts`, or the eight in-module call sites)
  needed edits.

**Verified, not just typechecked:** the module's existing test suite —
`ceremony.test.ts`, `ceremonyIssue.test.ts`, `witnessCeremony.test.ts`,
`witnessShare.test.ts`, `outcomeEvidence.test.ts`, `documentProof.test.ts`,
`trustTasks.test.ts` — passes unchanged (7 suites, 64 tests); those tests mock
`DidCommMessageSender`/`DidCommMessageHandlerRegistry` at the DI-container
level, which the relocated code still resolves the same way, so the fakes
needed no changes either. `@bifold/trust-tasks` and `@bifold/core` typecheck
clean (after building sibling packages the fresh worktree hadn't built yet —
that step surfaced one pre-existing `witness-server` type error, in
`WitnessService.ts`, last touched by `b9112b12` on `fix/mediator-pickup-strategy`
itself; unrelated to this change and not fixed here).

### Still open

- The `SigningKey`/`VidResolver` half of §5.2's port set, in `documentProof.ts`
  — not attempted here, see Decision above.
- No second carriage exists yet to prove the port against (the two-adapter
  rule §4.4/§5.2 use for the crypto ports has no equivalent here until TSP or
  DIDComm v2 carriage work starts) — this entry proves the port compiles and
  is load-bearing for one implementation, not that it's sufficient for a
  second.

### What this supersedes

`trust_tasks_subtask.md` §9's repeated status-note framing of step 1 as
"TSP-side" / "outside this milestone" — it was DIDComm-v1-side work the whole
time, just undone. The plan's step-1 section is updated in the same commit as

## Dual-accept gap (§7.2/§7.3, step 6) — unit-evidenced, not device-evidenced

Same branch (`feat/trust-tasks-over-didcomm-v1`). §9 step 6 recorded the
dual-send path as "true by construction... not yet evidenced against an
actual v3 build." Checked what's actually achievable without a device: the
basic-message handler that speaks the legacy dialect
(`vrc-manager.ts`'s `setupVrcConnectionHandler`) had **zero direct unit
coverage** before this — every existing trust-tasks test mocks `vrc-manager`
out entirely, and the handler itself is a large inline event-listener
closure, not a small testable function. Both the giant-handler shape and the
"needs a real old build" requirement rule out closing this gap in full here.

### Decision

Don't attempt to unit-test the whole handler (high mocking cost, low
confidence, wrong tool for "evidenced against a v3 build" anyway). Extract
the one piece that's both small and precisely what's in question — the
legacy announcement parser and the version it hands to the capability gate —
and test that directly against real wire-format strings, chained into the
real gate (`maybeOpenRelationshipExchange`, already unit-tested in isolation
via `ceremony.test.ts`'s "a v3 peer never receives a Trust Task message", but
never previously fed a value that came from parsing an actual message
string). This closes as much of the gap as static evidence can: it proves the
production regex correctly derives version N for every RCE generation
(1 through today's `RCE_PROTOCOL_VERSION`), and that a real v1–v3 string run
through it is provably rejected by the dialect gate.

**What this does not prove**, and nothing short of a real old build can:
that an actual older compiled app, on a device, still completes the full
legacy credential exchange when paired with a current wallet. That remains
open, same as before this entry — recorded here so it isn't mistaken for
closed.

### Applied

- `vrc-manager.ts`: extracted `parseLegacyRelationshipAnnouncement(content)`
  (new, exported, pure) from the basic-message handler's inline regex
  parsing; the handler now calls it instead of duplicating the two regexes.
  No behavior change — same patterns, same malformed-input handling.
- `vrc/__tests__/unit/legacyRelationshipAnnouncement.test.ts` (new): 12
  tests — every RCE version 1–5 round-trips, the no-suffix-defaults-to-1
  case, two rejection cases (no marker; marker present but malformed), and
  three cases chaining a parsed v1/v2/v3 announcement into
  `maybeOpenRelationshipExchange`, asserting zero Trust Task messages sent.

**Verified:** the new suite passes (12/12); the full trust-tasks + vrc unit
suites still pass unchanged (17 suites, 217 tests); `@bifold/core` typechecks
clean.

### Still open

- Real device/build evidence for the dual-send path — unchanged from before
  this entry, see "what this does not prove" above.
- The other two items §9's status note lists outside this milestone (step 4
  against a live `vta-service`; the proof-set migration, parked) — untouched
  here.

### What this supersedes

Nothing — this is additive evidence on top of an unchanged "true by
construction" position, not a reversal of it.

## Step 4 (credential-exchange against a live VTA) — unblocked, then started

Same branch. §9 step 4 ("Adopt `credential-exchange/{query,present,
pending/*}`... against `vta-service`") had been blocked from the start on
"needs a running VTA to test against" — nothing in this codebase could stand
one up. The user pointed at `firstperson.dev/#downloads`, which turned out to
publish real, current-release binaries (`vta`, `pnm`, `mediator`,
`did-hosting-daemon`, `vtc`, `openvtc` — codenamed "Dogwood"), with a
documented non-interactive setup mode (`vta setup --from`, per
`docs/02-vta/non-interactive-setup.md` in `OpenVTC/verifiable-trust-
infrastructure`) that a live-device tutorial hadn't needed to mention.

### Decision: an ephemeral VTA, same shape as the witness fixture

`e2e/lib/vta.js` (new) provisions a disposable `vta`: two cloudflared quick
tunnels (one for a minimal static file server hosting the minted `did:webvh`
log, one for the VTA's own REST port), `vta setup --from` a generated TOML,
an offline-minted admin `did:key` (`vta create-did-key --admin`), the daemon
started and health-checked through its tunnel. Same reasoning as
`startWitness`: a fresh identity every run is right for a test fixture, wrong
for anything meant to persist — did:webvh's identifier is derived from its
hosting domain, and a free quick tunnel's hostname is random per run, so the
VTA this mints is never reconnectable once torn down. Verified repeatedly
end to end against the real binary (v0.23.3): provisions, `did:webvh`
resolves through the tunnel, `/health` reports ok, and `pnm health`
(a completely independent client) confirms DID resolution + REST reachability
+ a valid auth token.

One real bug found and fixed along the way, unrelated to the VTA work itself:
building the full workspace to get sibling packages in place surfaced that
`@bifold/vrc-shared`'s `MediatedAgentLike.initiateMessagePickup` declared its
params required while credo's real API declares them optional with a nominal
enum type — sound for neither direction of TS's structural check, and
breaking `witness-server`'s `yarn build` (silently, since its test suite runs
`isolatedModules` and never type-checks this file). Confirmed via an isolated
repro before fixing: matching the real API's *optionality*, not the value
type, is what makes the assignment sound. This also blocks
`staging-witness.yaml`'s deploy job, which runs this same `tsc` step via
`docker compose up --build`.

### Applied

- `e2e/lib/vta.js`, `e2e/README.md` (new section) — the fixture above.
- `e2e/lib/witness.js`: exported `assertPortFree` (already implemented, just
  unexported) so `vta.js` reuses it instead of duplicating the port-freeness
  check.
- `@bifold/vrc-shared/src/mediation.ts`: `MediatedAgentLike`'s
  `initiateMessagePickup` params made optional (see bug above). No behavior
  change — the one caller always passes both arguments.

### Step 4 itself: started, not finished

Against that live VTA,
[`tsp-reference/ref-08-credential-exchange`](../../../tsp-reference/ref-08-credential-exchange/)
proves the DID-auth handshake (`POST /auth/challenge` → holder
`eddsa-jcs-2022`-signed `auth/authenticate/0.1` → `POST /auth/`) round-trips
against the real `vta-service`, using a hand-rolled implementation of the same
algorithm `@bifold/trust-tasks`'s `documentProof.ts` already implements —
cross-checked against `vta-sdk/src/trust_task_sign.rs`'s Rust construction
line by line first, not assumed compatible. That succeeding is itself evidence
Keyring's own signer is real-ecosystem-interoperable, not just internally
self-consistent.

Two findings that reshape what "done" requires here, both from reading the
live dispatch table rather than guessing:

1. **Every REST caller needs an ACL role before anything else applies** —
   `POST /auth/challenge` 403s an unregistered DID (`vta import-did --did …
   --role initiator` fixes it). The "verifier the holder hasn't pre-trusted"
   language in `vta-sdk`'s own module docs is a *second*, finer-grained tier
   (auto-answer vs. defer) layered on top of ACL membership, not a
   description of who may reach `/auth/` at all.
2. **`credential-exchange/query` isn't in the REST dispatch table in this
   build.** Tried both `/0.1` (the SDK's own constant) and `/1.0` (the version
   the `pending-*` handlers' doc comments use) — both `422 unsupportedType`.
   Confirmed directly against `vta-service/src/trust_tasks/mod.rs`'s
   dispatch-table macro invocation: only `PENDING_LIST` / `PENDING_APPROVE` /
   `PENDING_DENY` are registered there. `QUERY` only exists on the
   DIDComm/TSP messaging inbound path (`vta-service/src/messaging/`), which a
   REST-only VTA (`[messaging] kind = "skip"`, `e2e/lib/vta.js`'s default)
   never enables.

### Still open

- The admin side (`pending-list`/`approve`/`deny`) is confirmed reachable
  over REST (dispatch-table cross-check) but not yet exercised — nothing was

- The Node reference-adapter fixtures the parent step's "done when" also

## Step 4 continued — the query round-trip, over a real mediator

Same day, same branch, later session. Pushed past the "messaging-enabled VTA
needed" blocker the entry above left open.

### Applied

- A local `did:peer` mediator, stood up by hand (`mediator-setup
  --non-interactive --did-method peer --admin generate`, a locally-run
  `redis`, a second cloudflared tunnel, then a **regeneration** with
  `--public-url` set to the tunnel — needed so the did:peer's own service
  entry, not just `mediator.toml`'s `local_endpoints`, carries the real URL;
  the first attempt without it left the mediator warning "no local_endpoints
  configured" and produced a did:peer with no service segment at all).
  `mediator-setup` also writes `atm-functions.lua` to the wrong relative
  location for what it configures in `mediator.toml` — copied by hand each
  time; a real (if minor) tool bug, not user error, worth upstreaming.
- `startVta({ mediatorDid })` (already a parameter `e2e/lib/vta.js` supported,
  just unexercised until now) against that mediator: `vta setup --from` came
  up with `[messaging] kind = "existing"`, logged "DIDComm messaging started"
  / "connected to mediator", and both `curl .../health` and an independent
  `pnm health` confirmed it — mediator resolves and trust-pings, VTA DIDComm
  trust-pings, `Mode: DIDComm + REST`.
- `tsp-reference/ref-08-credential-exchange/run-messaging.mjs` (new) —
  `@openvtc/vti-didcomm-js`'s `connectVtaViaMediator`/`sendAndWait`, not a
  hand-rolled DIDComm encryption layer (unlike `run.mjs`'s Data-Integrity
  proof, which deliberately hand-mirrors the Rust construction to prove
  Keyring's own signer independently — there's no equivalent reason to
  reimplement ECDH-1PU here; using the real ecosystem's own client is the
  more direct proof for this half). Needs Node's `ws` for `WebSocketImpl`
  (the package is browser-first and has no global `WebSocket` fallback on
  Node 20).

### Findings

1. **The messaging path bypasses REST auth entirely.** No `/auth/challenge`
   step — `vti-didcomm-js`'s own docs: "the inner authcrypt envelope is
   self-authenticating and the VTA ACL-checks the `from` DID." Still needs
   *an* ACL role on the VTA (granted `initiator`, same as the REST verifier),
   but the identity is a **native X25519** `did:key` (`z6LS...`), not the
   Ed25519 one REST auth used — DIDComm key agreement needs X25519 directly
   and the library takes the keypair as a plain argument rather than deriving
   one from an Ed25519 DID.
2. **The query works, and answers `not-found`, not deferred.** Sent a DCQL
   query for a credential type this VTA holds none of. Expected (from
   `vta-sdk`'s own docs on the untrusted-verifier path) a deferral pending
   admin approval; got a `report-problem/2.0`,
   `code: "e.p.msg.not-found"`, `comment: "no held credential satisfies the
   verifier's query"` instead — correct behavior, and a real distinction: a
   fast-path refusal when nothing held could *ever* match, checked before
   deferral logic runs, is a different code path than "might be answerable,
   ask a human." `trust_tasks_subtask.md`'s "Done when" for this step
   presumed defer-always; that's now known to be wrong for this case.

### Still open

- A held credential matching the query, to reach the defer/pending-list/
  approve/present half — nothing here proves that path yet, only that
  `not-found` is correct when nothing could match.
- The Node reference-adapter fixtures the parent step's "done when" also
  requires.

### `e2e/lib/mediator.js` — the recipe above, scripted

Built right after this entry, same session. Mirrors `vta.js`'s shape exactly
(`startMediator()`: tunnel, non-interactive `mediator-setup` with
`--public-url` set from the start — no two-pass regenerate needed once the
tunnel exists before generation — the `conf/atm-functions.lua` copy, editing
`local_endpoints` into the generated `mediator.toml`, spawn, readiness poll).
One real bug found while porting the by-hand steps into a script:
`mediator-setup`'s relative-path outputs (`atm-functions.lua`, `mediator-
build.toml`, `admin-monitor.json`) are written relative to its own **process
cwd**, not relative to `--config`'s path — invisible when driving it by hand
from an already-`cd`'d shell, but silent (`ENOENT` on the lua-file copy) when
spawned from a different cwd. Fixed by passing `cwd: dir` to the `spawn` call.
Verified: `startMediator()` alone, twice, clean; paired with `startVta({
mediatorDid })` once, clean, before hitting transient cloudflared-tunnel
timing noise on further rapid back-to-back runs (same class of flakiness
already noted for `vta.js`'s tunnel wait) — not a code defect, not chased
further.

## Step 4 finished — the defer/pending-list/pending-approve/present path, proven

Same day, same branch, later session. Closes the "still open" item both
entries above left: a held credential, deferred presentation, and a real
`vp_token` out the other end.

### Applied

`tsp-reference/ref-08-credential-exchange/run-pending.mjs` (new) — brings up
its own disposable mediator + messaging-enabled VTA
(`e2e/lib/mediator.js`/`vta.js`) and runs the whole chain in one script:

1. Mints a Data-Integrity (`eddsa-jcs-2022`) W3C VC and stores it via
   `POST vault/credentials/receive/0.1` **over REST** — not `pnm cred-vault
   receive`, which was the first path considered and abandoned: the task URI
   is in the REST dispatch table (`vta-service/src/trust_tasks/mod.rs`), and
   `Role::Initiator` already carries `VaultWrite`/`CredentialWrite`
   (`vti-common/src/acl/mod.rs`), so the same REST auth handshake `run.mjs`
   already proved (challenge → authenticate → bearer) is sufficient — no need
   to stand up `pnm`'s local config/keyring plumbing at all.
2. Queries it from a fresh, not-pre-trusted verifier over DIDComm-via-mediator
   (`run-messaging.mjs`'s `connectVtaViaMediator`/`sendAndWait`), with the DCQL
   query changed from the prior entry's `dc+sd-jwt`/`vct_values` shape to
   `format: "ldp_vc"` / `meta.type_values: ["MembershipCredential"]` — the
   mapping `vta-service/src/operations/credential_exchange.rs`'s
   `dcql_format()` defines for `CredentialFormat::EddsaJcs2022`.
3. Reads the deferral back and approves it as a fresh `admin`-role identity,
   over REST (`credential-exchange/pending/list/0.1`,
   `.../pending/approve/0.1` — also both in the REST dispatch table, note the
   SDK's actual wire spelling is `pending/{list,approve}/0.1`, not the
   `pending-list/1.0` form `vta-service`'s own doc comments use elsewhere).

Two real, non-obvious constraints found by running it against 400s rather than
by reading docs, each fixed once identified:

- **The credential's `credentialSubject.id` must be a did:key the VTA itself
  manages** (a `KeyRecord` derived from its own seed), not merely a valid
  did:key. `resolve_holder_keys` (`vta-service/src/operations/holder_keys.rs`)
  looks up the subject's private key to sign the holder-bound presentation and
  404s ("holder subject `...` is not a did:key" / not found) for anything
  else — an externally-generated did:key (or the VTA's own did:webvh service
  identity, tried first) doesn't qualify. Fixed by minting the subject with
  `vta create-did-key --context vta` (no `--admin`) during the same paused-
  daemon window as the ACL grants — added as `createDidKey()` in
  `e2e/lib/vta.js`, alongside a new `importDid()` for the ACL-grant half and
  `pauseDaemon()`/`resumeDaemon()` on `startVta`'s return value so the daemon
  can be stopped for these offline, store-exclusive commands and restarted
  without tearing down its tunnels or state (`startVta` itself unchanged in
  behavior — same options, same return fields plus these four additions).
- **A DCQL credential query's `claims` must name at least one path.** Omitting
  it (`vta-sdk`'s own semantics: "the credential as a whole is requested") is
  valid for *matching*, but leaves the matched disclosure set empty, and
  `vta-vault/src/consent.rs`'s consent-record builder refuses to authorize an
  empty reveal set (default-deny: "consent claims must be non-empty") —
  `pending-approve` 400s even though `pending-list` showed the deferral fine.
  Fixed by adding `claims: [{ path: ["type"] }]` to the query.

**Verified — the full round trip, three clean runs:** `receive` → 200,
`query` → deferred (`report-problem/2.0`, `e.p.msg.bad-request`, "presentation
requires holder consent... an out-of-band approval is needed"), `pending/list`
→ 200 with the deferral, `pending/approve` → 200 with a real `vp_token` (a
holder-bound `VerifiablePresentation`, `eddsa-jcs-2022` proof, the VC embedded
in `verifiableCredential`). Every run's mediator + VTA + tunnels torn down
clean afterward, confirmed via `ps` — nothing left running.

### A second near-miss with backgrounded forks — a sharper lesson than the last one

The prior entry's near-miss lesson ("resume via `SendMessage`, never call
`Agent` again") was followed correctly this time, and it wasn't enough. A
background fork given this exact task died mid-run to an org rate limit with
nothing written; a retry got partway (receive/query/pending-list working, the
`credentialSubject`-must-be-did:key bug not yet found) and then reported
completion with a non-answer ("I'll wait for the completion notification") —
twice, across two `SendMessage` resumes, with no further progress either time
and no processes or files changed between them. Rather than keep resuming it,
the orchestrating session read its diff directly, ran the script by hand to
see the actual live failure, diagnosed and fixed the two bugs above itself —
and the fork, still alive, was independently mid-edit on the *same* fix at the
same time: it added its own `createDidKey` to `e2e/lib/vta.js` while the
orchestrator's edit was landing, producing two conflicting declarations of the
same export before anyone noticed. Caught by an on-disk-changed warning on the
next edit, not by anything either side flagged proactively. Resolved with
`TaskStop` (the fork's last recorded action: "Now update `run-pending.mjs` to
mint and use a VTA-managed did:key as the credential subject" — it would have
collided a second time, in the file the orchestrator was about to fix next),
then manually reconciling the duplicate.

**The sharper lesson:** a fork that stops reporting usable progress after
being resumed is not necessarily idle — it can still be alive and mutating
files. `SendMessage`-resuming it is the correct way to *ask* it something, but
if the plan is to *also* take over and edit the same files directly, stop it
first (`TaskStop`) rather than proceeding in parallel on the assumption that a
content-free reply means it's done or stuck. This is a different failure mode
from the previous entry's ("don't call `Agent` again to check on a fork") —
that one was about which tool re-attaches to a fork; this one is about not
editing alongside one that's still attached, however it got that way.
