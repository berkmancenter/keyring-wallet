# Part B — the binding, implemented: two rungs, one break, one PR

## B-1. What was proven

Two rungs, both green, both pinned to `fbe196a` + `@credo-ts/*` 0.6.3 (the
app's exact Credo):

- [`ref-06v1-didcomm-v1-binding`](../../../tsp-reference/ref-06v1-didcomm-v1-binding/)
  (12 checks): the binding's basic-message built with Credo's own classes
  matches a fixture **emitted by the upstream reference crate** field-for-field
  on everything normative; live agent-to-agent carriage over real v1 authcrypt
  delivers the document byte-identically; `theirDid` supplies the §4.8.1
  transport-authenticated sender.
- [`ref-06v1b-mediated`](../../../tsp-reference/ref-06v1b-mediated/)
  (7 checks): the identical carriage through the **production Keyring
  mediator** — mediator-routed invitation, handshake across the mediator,
  store-and-forward, implicit pickup. The mediator is transparent to the
  binding: today's wallet-to-wallet topology carries Trust Tasks unchanged.

## B-2. The break, and why it is spec-shaped

Credo validates every `~thread` field against RFC 0008's id shape
(`MessageIdRegExp = /[-_./a-zA-Z0-9]{8,64}/` in `BaseDidCommMessage`) and
refuses to pack a message whose `thid` is a `urn:uuid:` URI — the id form
every framework example uses. The refusal is client-side, before the envelope
exists: reproduced identically with and without the mediator (both rungs
assert it as a named check, so a future Credo that lifts the constraint turns
the check red and we notice). Since Credo enforces and the reference stack
does not, the collision lives in the **binding's mapping layer**, and the fix
belongs there — not in Credo, not in the framework's id format.

Five smaller findings (producer API is content-only; stored records drop the
attachment; decorator asymmetry both directions; `@type` equivalence is
load-bearing; askar-shared single-instance hazards) are catalogued in the
rung's [`UPSTREAM-FEEDBACK.md`](../../../tsp-reference/ref-06v1-didcomm-v1-binding/UPSTREAM-FEEDBACK.md).

# Part C — recorded so they don't vanish (deferred deliberately)

1. **DTG credential digests vs DataIntegrityProof.** The framework editor
   reports the cred-spec's `"sha256:…"` digest form conflicts with VC DIP and
   has aligned the DTG Rust library, making the spec text the outlier; he asks
   for the spec edit "ASAP… prior to GDC and LF events". Belongs on the
   subtask §11 owed-edits list; intersects the VWC digest-vs-commitment
   question (plan §4.6), so the edit must not foreclose that decision.
2. **Approvals/step-up integration.** Upstream retired step-up floors into a
   single DTTE-based approval chain (VTI #914, breaking; `[auth.step_up]`
   configs will fail to boot on the next VTA release — our ref-05 recipe is
   clean), and the editor's headline ask for Keyring is the device approval
   flow. No plan section owns this; it needs one.
3. **Pin advance boundary = Cypress RC-1.** Upstream is mid-realignment (the
   `VTI-Cypress-RC-0` tag was *moved*; the editor asked that new versions not
   be tested until an RC-1 re-tag). All pins stay; the ladder re-runs bottom-up
   at RC-1.
