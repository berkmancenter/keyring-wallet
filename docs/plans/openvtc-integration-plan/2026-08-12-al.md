# Compatibility evidence: the recast is the same ceremony at its core

*2026-08-12 · Alberto · one working session; evidence in
[`tsp-reference/ref-06w2-compat`](../../../tsp-reference/ref-06w2-compat/)*

## The question, and the calibration

Before the appendix specs go anywhere near upstream, the obvious objection —
"you are changing a shipping protocol" — deserved evidence rather than
argument. Calibration set at the outset: **Keyring is pre-production, so
backward compatibility needs to be *signaled as viable*, not built out** —
the levers proven, not productionized.

## What ref-06w2 proved (13 checks, against the real compiled witness core)

The rung imports the **production functions** from
`bifold/packages/witness-server/dist` — not copies — and establishes:

1. **Shared core.** The same submission expressed as today's
   `submit-presentation` JSON and as a `witness/session/submit` document,
   fed to the real `buildWitnessCredentialJson`, yields **byte-identical
   VWCs** (volatile members stripped), digests included. The recast changes
   the dance, not the ceremony.
2. **Lossless translation, honest delta.** A pure old⇄new translator
   round-trips the three session messages exactly onto ref-06w's document
   shapes; the five legacy concepts with *no* task home yet (witness
   preference, `reportingDid`, the announce, verify-credential, the bespoke
   error codes) are enumerated in frozen fixtures rather than glossed.
3. **Mixed-dialect coexistence.** One witness, one session state machine:
   one party ran the entire legacy dance while the other ran the entire
   task dance — one challenge served both, each received its per-direction
   VWC in its own dialect, and the dialects never leaked.

Three migration levers now have runnable backing: **B** — the legacy
handshake's own `vrc:rceVersion` ordinal gates the new dance (`4` = speaks
Trust Tasks; zero new messages); **C** — the legacy `witnessContext.sessionId`
and the ceremony identifier (`taskContext`) are one value, so the identifier
spaces converge and old records can be retrofitted; **witness-as-compat-point**
— the dual-stack witness serves both fleets, and we own its deployment.

**Lever D stays an open design question for the PR #3 review:** whether VWC
delivery remains on Credo's `issue-credential` protocol with the
`submit#response` carrying a reference+digest as the evidence artifact, or
moves wholly into the response as the rung and drafts currently have it. The
split-delivery variant may be the better permanent design, not only a
transitional one.

Also confirmed in passing, with the production code itself: today's digest is
`sha256:`+hex over JCS — so the cred-spec `digestMultibase` change
([Mickens-Lab/dtgwg-cred-spec#2](https://github.com/Mickens-Lab/dtgwg-cred-spec/pull/2))
is encoding-only for Keyring; the canonicalization survives untouched. And
today's VWCs carry no `taskContext` at all — the recast is what makes
Outcome Interpretability satisfiable, not a rearrangement of something that
already worked.
