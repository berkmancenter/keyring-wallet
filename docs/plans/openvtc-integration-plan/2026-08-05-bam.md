## 1. `tsp-core`'s internal dependency direction may be backwards

**Evidence.** §5.2's module diagram wires the core as:

```
TT ("trust-task model · canonical schemas · validation · Type-URI dispatch · threading")
  --> WIRE ("envelope orchestration · vti-tsp-js pack/unpack · CESR demux · noble HPKE-Auth backend")
  --> IFACE (ports: SigningKey · KeyAgreement · VidResolver)
```

The trust-task model depends on TSP envelope orchestration.

**Why this is a problem.** It inverts the property the rest of the plan rests on. §2.3: "Trust Tasks are the *operation layer* that rides any transport… everything we build at the task layer is transport-portable by construction." SPEC §1.1 goal 1 makes the same claim normatively — a task document "makes no assumption about the protocol that delivers it."

With `TT --> WIRE`, using the trust-task model over any non-TSP carriage drags in HPKE, CESR, and the noble crypto backend. That directly affects three things this plan wants:

- **DIDComm v1 carriage** (the legacy VRC/witness stack, §7.6) needs the task model and none of the wire layer.
- **The REST leg** in the TSP > DIDComm > REST ladder (§1.2, §4.2) likewise.
- **§5.3's stated goal** that `tsp-core` "has zero Credo/Askar/RN imports so the same code runs in Node… and RN" is about *dependencies*, and this coupling adds the heaviest one to the layer that least needs it.

**Proposed adjustment.** Split the two boxes and re-point the arrow:

```
TT (trust-task model) --> CARRIAGE (interface: send/receive a document + transport-derived identity)
WIRE (TSP envelope orchestration) --implements--> CARRIAGE
```

This is a diagram-and-interface change now; after Phase D it is a refactor of the package everything else depends on.

**Secondary benefit.** It lets the §7.6 recast consume `tsp-core`'s task model over a DIDComm-v1 carriage rather than building a second spine — making the VRC/witness work an *early second consumer* that validates the abstraction. That is the same two-implementations logic already applied to adapters (§4.4, "the same fixture suite runs against every adapter") and to bindings (§7.9).

## 2. §7.9's binding commitment may not be achievable as written

**Evidence.** Three statements that collide:

1. §7.9 commits to "**Second implementation of `binding/didcomm/0.1`** (the Credo trust-task client, Phase D/E)", with "Interop evidence to dtgwg-trust-tasks-tf" as the deliverable.
2. Phase D / ref-07 restates it: "scope the Credo client for the existing draft `binding/didcomm/0.1`".
3. §3 states: "**DIDComm**: v1 only (Credo has no v2)."

And the binding itself is unambiguous — `bindings/didcomm/0.1/spec.md` front matter reads:

> `title: DIDComm v2.1 transport binding`
> `summary: Carries Trust Task documents inside DIDComm v2.1 authcrypt envelopes; the verified sender_kid maps to the framework's transport-authenticated party identity.`

It mandates authcrypt JWE and rejects plaintext, anoncrypt, and signed-only envelopes. §9 of the plan already records "authcrypt-mandatory" — the v2.1 constraint is the part not yet captured.

**Two readings, and they need different fixes.**

- *Loose phrasing.* The v2 envelope actually comes from `@openvtc/vti-didcomm-js`, consistent with §3: "Keyring↔VTA therefore uses OpenVTC's JS libraries beside Credo, never through it." If so, the roadmap entry should name that library rather than Credo — the interop claim rests on which implementation speaks the binding.
- *Literal.* If the intent is genuinely a Credo-native implementation of `binding/didcomm/0.1`, it is not reachable on Credo 0.6.3, and the contribution should be re-scoped before it is offered upstream.

**Proposed adjustment.** Pin down which reading applies and reword §7.9 accordingly.

**Related opportunity.** Either way, there is no registry binding for **DIDComm v1**. A private `didcomm-v1-basicmessage` binding — Trust Task document as the JSON body of a basic message, connection `theirDid` as the transport-authenticated sender for the SPEC §4.8.1 cross-check — is what would let the legacy stack speak trust tasks at all. Every Credo-based wallet in the ecosystem has this same gap, so it is plausibly a more reusable contribution than a second implementation of an existing binding. Detail in the companion doc §6.

## 3. "Clean cutover, no dual-accept" has no mobile-side answer

**Evidence.** §1.2: "the canonical-task migration is a **clean cutover** (old URIs are being deleted, no dual-accept)." ref-06 reinforces it: "canonical `trusttasks.org/spec/` URIs… **never** deprecated `vta/*` 1.0 shapes."

**Why this is a problem.** That norm is workable for a server and a browser extension, both of which can be updated in lockstep. It is not workable for a phone app: old versions persist in the wild for months, app-store review adds latency, and native code has no OTA path. A clean cutover upstream becomes a hard break for every un-updated install.

§4.2 addresses coexistence carefully and explicitly — but only for **envelope formats**. There is no equivalent position for **task versions**, and the two problems are independent: an app can be perfectly capable of TSP and still be bricked by a Type URI that was deleted.

Notably, the framework permits what we need. SPEC §5.2 makes forward-minor compatibility a SHOULD, and consumers may accept multiple versions concurrently; §5.4's expand-then-contract sequence ("update receivers first") is written for exactly this. Nothing obliges us to mirror upstream's cutover discipline in the client.

**Proposed adjustment.** Add a task-layer coexistence subsection alongside §4.2, stating at minimum:

- Keyring consumers accept **N and N−1** of any task version we emit, for at least one release cycle.
- Type URI churn upstream is absorbed by the client, never propagated as a hard break.
- Where we are the producer, we follow SPEC §5.4 receiver-before-sender ordering.

This also sets the tolerance for how aggressively the reference ladder can track upstream `main`.

## 4. §8's non-negotiables contradict §7.6

**Evidence.** §8: "**Non-negotiable at every level**: VRC module tests stay green; **witness flow untouched**; `e2e:vrc:devices` remains the attestation proof; legacy DIDComm v1 stack fully supported throughout."

§7.6, in the same document: "**Witnessed-exchange Trust Task spec** (+ CODEOWNERS for our namespace) | Private authority → dtgwg-trust-tasks-tf PR". Line 233 schedules it: "witnessed-exchange as a Trust Task (private authority → registry PR)". Demo milestone 3 depends on it.

Recasting the witness ceremony as Trust Tasks necessarily touches the witness flow.

**Proposed adjustment.** Scope the non-negotiable to the workstream it was written for — e.g. "witness flow untouched *by the TSP transport work*; changes to it are gated on §7.6 and on `e2e:vrc:devices` staying green." The intent is almost certainly this already; as written it is a constraint the plan's own roadmap violates.

## 5. VWC outcome-evidence retention is real work, costed nowhere

**Evidence.** DTG Core Credentials §Outcome Interpretability is normative: a verifier **MUST NOT** read a `taskContext`-bearing credential as proof its ceremony completed unless matching outcome evidence is present and verified, and the **holder MUST include that evidence with the presentation**. Discovery and retrieval are explicitly out of scope of that specification, so evidence the holder does not ship is evidence that does not exist.

**Why this is a problem.** Keyring is the holder. Our VWCs are standalone credentials today and the witness ceremony's messages are transient, so we cannot currently present a VWC as proof a witnessing occurred — the one thing a witnessed exchange exists to demonstrate. Closing it needs persistence, indexing by `taskContext`, presentation assembly, and a retention policy.

**Proposed adjustment.** This has been surfaced as plan §8.1, but §8.1 itself records that it is "not currently costed in any phase of §6." It should be costed into a phase — it is storage, presentation and policy work in the wallet's credential store, not `tsp-core` work, so it does not follow the `tsp-core` packages. **Demo milestone 3 depends on it**, and the failure mode is silent: the VWCs verify perfectly well as credentials and simply fail to prove completion.

## 6. §7.6's route and timing were stale in two places — applied

**Evidence.** Roadmap item 6 described the route as "private authority → dtgwg-trust-tasks-tf PR", and the ecosystem-phase line placed the work "after the ladder". Both are now wrong: DTG Core Credentials makes a qualifying specification a normative dependency of the VWC, and the framework editor has invited the specification as a joint appendix ([#173](https://github.com/trustoverip/dtgwg-trust-tasks-tf/issues/173#issuecomment-5189686547)). Spec authoring belongs in parallel with Phases A–C; implementation at D/E.

**Status: applied.** Both locations corrected. Recorded here so the change is traceable rather than silent, and because it moves work *earlier* in the plan — which affects Phase A–C capacity, not just wording.

## Confirmed synergies (no adjustment needed)

Recorded so the companion doc's dependencies on this plan are visible:

- **§7.6 is the companion doc.** That doc supplies the concrete slugs, party declarations, `bearer: true` for `witness/announce` (SPEC §4.8.3 — a broadcast attestation with no intended audience), and the mapping of the current kebab-case `error` codes onto framework-standard ones with `retryable` / `retryAfter`.
- **§4.5's `eddsa-jcs-2022` signer is reusable for task `proof`.** Most VRC-layer documents won't need one — DIDComm authcrypt authenticates the sender, so SPEC §4.7.1 permits `proof: OPTIONAL` — but `witness/announce` is a bearer broadcast and should carry a proof. Phase D covers it.
- **The recast is a prerequisite for "VRC-over-TSP," not a competitor.** Line 233 lists both in the ecosystem phase without ordering them. The relationship handshake cannot ride TSP while it is a regex inside a chat message (`vrc-manager.ts:2180`, parsed at `:1410-1424`). Once A and B are task documents, changing carriage is a transport swap by §2.3's byte-identity property. **Recast must precede VRC-over-TSP**; worth making explicit.
- **§8's claim that "our witness session messages are already Trust-Task-shaped" holds up.** `session-request` → `session-challenge` maps onto SPEC §4.4.1's `#request`/`#response` fragment convention almost exactly; `threadId` replaces the current ad-hoc correlation.
- **The `taskContext`-on-VWCs thread (demo brainstorm, "Witness governance under remote connection") lands in `witness/session/submit`'s payload** — ceremony / device / locality / domain become declared evidence axes rather than implied ones, which is what makes remote-witnessed and co-present-witnessed distinct honest claims.

## Sequencing implication for §7.6

The companion doc originally recommended doing the witness recast first, on the grounds that it is self-contained and we control both ends. Reviewed against this plan, that is right only if it does **not** mean building a spine `tsp-core` will later replace. Revised ordering:

1. **Resolve Finding 1** — cheap now, expensive after Phase D.
2. **`didcomm-v1-basicmessage` binding alongside Phase D**, once the ports exist.
3. **Adopt `credential-exchange/{query,present,pending/*}`** — the **presentation** half only — over that binding, against `vta-service`. Sequenced first among the implementation work because it needs **no spec authorship** and has a genuinely **live counterparty** (`vta-service/src/trust_tasks/credential_exchange.rs` implements the deferral path), so a failure is unambiguous — and because running it *is* the second-implementation interop evidence §7.9 and §4.4 both want.
4. **Author the `vrc/*` and `witness/*` specs** — starts in parallel from the beginning (document work, long registry lead time). **Gate on freezing, not on starting:** hold the final shape until the framework editor's PR from [#173](https://github.com/trustoverip/dtgwg-trust-tasks-tf/issues/173#issuecomment-5189686547) lands, since it changes what a qualifying specification must declare.
5. **Implement the witness recast on `tsp-core`'s task model** at Phase D/E, including **outcome-evidence retention** (§8.1 of this plan).
6. **Relationship handshake + capability discovery** — `trust-task-discovery` (SPEC §11) replaces the ordinal `rceVersion` ladder currently gating `counterpartySpeaksVc20` / `counterpartySpeaksDi` (`vrc-manager.ts:379`, `:394`).

> **Revised 2026-08-05, second pass.** An earlier version of this list had spec authoring at step 2 and left `credential-exchange/*` adoption as a standalone decision at the end, "orthogonal to this workstream." That rested on treating Credo's existing protocol set as a fixed constraint; under the premise that **we are updating Credo to support these flows rather than fitting them to Credo**, adoption is neither orthogonal nor expensive.
>
> **Third pass.** `credential-exchange/*` then had to be **split**. The registry carries two credential-delivery idioms: DTG credentials travel as a signed VC in the payload (`vtc/members/vmc` → `{ vc }`, with a `credentials/_shared/0.1` receipt), while `credential-exchange/*` wraps OID4VCI objects (`credential_response` — snake_case, carried verbatim from a foreign spec). **Every DTG credential in OpenVTC uses the first idiom; none uses the second.** Upstream status differs too: the presentation legs are implemented in `vta-service`, the issuance legs are not ("handlers … land in later Phase 3 slices"). So the issuance half is dropped and the presentation half keeps the validator role. Companion doc §9.1 and §9.4 carry the evidence.
>
> Standing lesson for this workstream: **"align with OpenVTC" and "adopt registry-published specs" are not the same instruction.** The registry serves several worlds at once; picking a family by publication status rather than by idiom is how we drift while believing we are converging.
