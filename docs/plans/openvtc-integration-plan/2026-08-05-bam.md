# Part A — Findings against the integration plan

## A1. `tsp-core`'s dependency direction is backwards

**Evidence.** §5.2's module diagram wired the core as `TT --> WIRE --> IFACE`:
the trust-task model depending on TSP envelope orchestration.

**Why this is a problem.** It inverts the property the rest of the plan rests on.
§2.3: "Trust Tasks are the *operation layer* that rides any transport… everything
we build at the task layer is transport-portable by construction." SPEC §1.1 goal
1 says the same normatively — a task document "makes no assumption about the
protocol that delivers it."

With `TT --> WIRE`, using the task model over any non-TSP carriage drags in HPKE,
CESR and the noble crypto backend. That hits three things the plan wants: the
DIDComm v1 carriage the legacy VRC/witness stack uses (§7.6); the REST leg of the
TSP > DIDComm > REST ladder; and §5.3's stated goal that `tsp-core` carry no
heavy dependencies so the same code runs in Node and RN.

**Adjustment.** `TT --> CARRIAGE` (send/receive a document plus
transport-authenticated identity), with `WIRE` implementing that port. A
diagram-and-interface change now; after Phase D, a refactor of the package
everything depends on.

**Secondary benefit.** It lets the §7.6 recast consume `tsp-core`'s task model
over a DIDComm-v1 carriage instead of standing up a second task spine — making
that work an early second consumer validating the abstraction, the same
two-implementations logic already applied to adapters (§4.4) and bindings (§7.9).

## A2. §7.9's binding commitment is not achievable as written

**Evidence.** Three statements collided: §7.9 committed to a "second
implementation of `binding/didcomm/0.1` (the Credo trust-task client)"; ref-07
restated it; and §3 says "**DIDComm**: v1 only (Credo has no v2)." The binding's
own front matter reads `title: DIDComm v2.1 transport binding`, mandating
authcrypt JWE.

**Adjustment.** Re-scope to a **DIDComm-v1 basic-message binding we author**.
Where the v2.1 binding is exercised it is via `@openvtc/vti-didcomm-js` beside
Credo, and that is what any second-implementation claim must name.

**The larger opportunity.** No registry binding covers DIDComm v1 at all, so no
Aries-lineage wallet can carry Trust Tasks today. The identity mapping is clean —
the connection's `theirDid` is the transport-authenticated sender for SPEC
§4.8.1 — which makes a v1 binding more reusable than a second implementation of
an existing one.

## A3. "Clean cutover, no dual-accept" has no mobile-side answer

**Evidence.** §1.2 records the upstream norm — "old URIs are being deleted, no
dual-accept" — and we watched it happen: **54 of the 74 `spec.md` files** in
`verifiable-trust-infrastructure/trust-tasks/` are `status: retired`, re-minted
under new URIs and renumbered downward on the way.

**Why this is a problem.** That cadence works for a server and a browser
extension, which update in lockstep. It does not survive an app-store release
cycle: old versions persist for months and native code has no OTA path. §4.2
addressed coexistence carefully — but only for *envelope formats*. The two
problems are independent; an app can be fully TSP-capable and still be bricked by
a deleted Type URI.

**Adjustment.** A task-layer coexistence policy (new §4.2a): accept **N and N−1**
of any task version we emit for at least one release cycle, absorb upstream churn
in the client, follow SPEC §5.4 receiver-before-sender ordering where we are the
producer. The framework permits all of this — §5.2 makes forward-minor
compatibility a SHOULD — so it costs no upstream negotiation. It does mean
conformance fixtures must cover N−1.

## A4. §8's non-negotiables contradict §7.6

**Evidence.** §8 listed "witness flow untouched" as non-negotiable at every
level, while §7.6 of the same document committed to recasting the witness
ceremony as Trust Tasks, and demo milestone 3 depends on that recast.

**Adjustment.** Scope the non-negotiable to the workstream it was written for:
untouched *by the TSP transport work*, with changes gated on §7.6 and on
`e2e:vrc:devices` staying green.

## A5. VWC outcome-evidence retention is real work, costed nowhere

**Evidence.** DTG Core Credentials §Outcome Interpretability is normative: a
verifier **MUST NOT** read a `taskContext`-bearing credential as proof its
ceremony completed unless matching outcome evidence is present and verified, and
the **holder MUST include that evidence with the presentation**. Discovery and
retrieval are out of scope of that specification — evidence the holder does not
ship is evidence that does not exist.

**Why this is a problem.** Keyring is the holder, and retains nothing. See Part B
decision 4 for what the design requires.

**Adjustment.** Surfaced as plan §8.1, but §8.1 itself records that it is "not
currently costed in any phase of §6." It should be costed into a phase. It is
storage, presentation and policy work in the wallet's credential store — not
`tsp-core` work — so it does not follow the `tsp-core` packages. **Demo milestone
3 depends on it**, and the failure mode is silent: the VWCs verify perfectly well
as credentials and simply fail to prove completion.

## A6. §7.6's route and timing were stale in two places

**Evidence.** Roadmap item 6 described the route as "private authority →
dtgwg-trust-tasks-tf PR", and the ecosystem-phase note placed the work "after the
ladder". Both are wrong: DTG Core Credentials makes a qualifying Trust Task
specification a *normative dependency* of the VWC — we cannot conformantly issue
VWCs without one — and the framework editor has **invited** the specification as
a joint appendix ([#173](https://github.com/trustoverip/dtgwg-trust-tasks-tf/issues/173#issuecomment-5189686547)).

**Adjustment.** Authoring runs parallel with Phases A–C; implementation lands at
D/E. Recorded rather than silently fixed because it moves work *earlier*, which
affects Phase A–C capacity and not only wording.

# Part B — Design decisions for the Trust Tasks subtask

## B1. The witness ceremony is its own thread, nested in the relationship exchange

**Decided.** `witness/session` opens a thread of its own. That document's `id` is
the ceremony thread's identifier and the value VWCs carry as `taskContext`. Its
payload carries `exchangeThreadId` linking back to the relationship exchange.

**Supersedes.** One thread for the whole exchange, opened by
`vrc/relationship/propose`, with the ceremony as legs within it.

**Why.** Two sections of the plan disagreed once `taskContext` was anchored on a
document `id` rather than a `threadId`. DTG Core Credentials defines
`taskContext` as naming the exchange "in which the witnessing occurred", and
Outcome Interpretability wants evidence *that* exchange terminated. A
`propose#response` proves the relationship exchange concluded and says nothing
about whether a witness observed it; only `witness/session/submit#response`
attests the witnessing. Anchoring on the outer thread would have verifiers
collect evidence of the wrong event — and it would verify cleanly, which is the
failure mode worth designing against.

**Consequence we own.** The framework defines no parent-thread member — no
`pthid` equivalent, and `threadId` is a flat correlator with no nesting semantics
— so the link between the threads lives in our payload.

## B2. Credential delivery follows the DTG idiom, not OID4VCI

**Decided.** VRC and RCard delivery uses `vrc/relationship/issue` — the signed
credential in the payload, receipts from `credentials/_shared/0.1`, matching
`vtc/members/vmc`. Presentation adopts
`credential-exchange/{query,present,pending/*}`. The issuance legs
`credential-exchange/{offer,request,issue}` are not used.

**Supersedes.** Adopting `credential-exchange/*` as a single family, sequenced
first as a "pipeline validator" because it needed no spec authorship and had a
live counterparty.

**Why.** Both halves were wrong. The registry carries two credential-delivery
idioms — the DTG one (signed VC in the payload) and the OID4VCI one
(`credential_response`, snake_case, carried verbatim from a foreign spec) — and
every DTG credential in OpenVTC uses the first. And the live counterparty exists
only for the presentation legs: `vta-service` implements `query` and
`pending/{list,approve,deny}`, while the issuance handlers "land in later Phase 3
slices."

**The general form of the mistake**, worth keeping in view: *"align with OpenVTC"
and "adopt registry-published specs" are not the same instruction.* The registry
serves several worlds at once. Choosing a family by publication status rather
than by idiom is how we drift while believing we are converging.

## B3. Credo is not the constraint — `vrc/relationship/issue` exists

**Decided.** The task family expresses the exchange we want; the Credo layer
follows it.

**Supersedes.** Omitting a delivery task because Credo's `issue-credential` v2
already delivers; and the "B1" staging tier that would have kept Credo delivering
while recasting only the negotiation around it.

**Why.** Both rested on treating Credo's current protocol set as fixed. We are
moving to a new foundation and updating Credo to support these flows. That
staging tier was a hedge against Credo being immovable; without the hedge it is a
correlation layer between the trust-task thread and Credo's protocol that we
would build and then delete. Its one durable idea — `trust-task-discovery`
replacing the ordinal `rceVersion` ladder — survives in layer A.

## B4. The VWC is specified; we design only the ceremony it binds to

**Decided.** `witness/session` and `witness/session/submit` each declare
`proof: REQUIRED` and define a `#response`, satisfying the qualifying profile.
Outcome-evidence retention is new implementation work. The RCard does not ride
`vrc/relationship/issue`.

**Supersedes.** A Layer C task table giving `witness/session/submit` no
`#response` and leaving `proof` unstated; an RCard sharing
`vrc/relationship/issue` with the `type` array discriminating; and calling the
membership flow "the VMC triple".

**Why.** Read as authoritative rather than inferred from implementations, DTG
Core Credentials settles all three. VRC, VMC and VWC are sibling `DTGCredential`
subtypes sharing one Base Structure, so naming tasks after a credential implied a
distinction the taxonomy denies. The r-card is a verifiable data structure
awaiting its own specification — its `type` array lacks `DTGCredential` and fails
Base Structure; our own code already called it "a separate exchanged VDS". And a
VWC **MUST** bind to its exchange via `taskContext`, which requires a qualifying
specification: one declaring `proof` REQUIRED on its response variants and
defining a `#response`.

**Retention** follows from Outcome Interpretability, and is finding A5 above: a
holder presenting a `taskContext`-bearing credential as proof of completion must
ship matching outcome evidence, and we retain nothing today.

## B5. `taskContext` anchors on the initiating document's `id`

**Decided.** Anchor on `id`, and treat the `trust-task-error` branch as
diagnostic rather than verifier-facing outcome evidence.

**Supersedes.** Anchoring on `threadId` (as DTG Core Credentials currently
states), and asserting that our error responses "MUST also carry `proof`" under
the qualifying rules.

**Why.** From the framework editor on
[#173](https://github.com/trustoverip/dtgwg-trust-tasks-tf/issues/173#issuecomment-5189686547):
`threadId` carries no normative validation semantics and its uniqueness is
unenforceable by a stateless consumer, while `id` already carries a normative
global-uniqueness obligation on a mandatory member. And the proof requirement is
resolved from the specification named by the document's `type` — an error
response's `type` is `trust-task-error`'s own URI, a different specification
declaring `proofRequirement: RECOMMENDED`, which nothing lets a task
specification strengthen. A retained error also names neither the originating
Type URI nor `id`, so a third party cannot tell what it terminated.

**Owed as a result.** Three edits to DTG Core Credentials, where we hold the pen
— tracked in the subtask plan §11.

## B6. Sequencing, gated on the parent plan's `tsp-core` shape

**Decided.**

1. **Resolve A1** — cheap now, expensive after Phase D.
2. **`didcomm-v1-basicmessage` binding**, Phase D, once the ports exist.
3. **Adopt `credential-exchange/{query,present,pending/*}`** over that binding
   against `vta-service` — the presentation half only. First among the
   implementation work because it needs no spec authorship and has a genuinely
   live counterparty, so a failure is unambiguously ours. Running it *is* the
   second-implementation interop evidence §7.9 and §4.4 both want.
4. **Author the `vrc/*` and `witness/*` specs** — starts in parallel from the
   beginning. **Gate on freezing, not on starting:** hold the final shape until
   the framework editor's PR from #173 lands, since it changes what a qualifying
   specification must declare.
5. **Implement the witness recast** on `tsp-core`'s task model, including
   outcome-evidence retention.
6. **Relationship handshake and capability discovery**, with
   `trust-task-discovery` replacing the `rceVersion` ladder.

**Supersedes.** Doing the witness recast first because it is self-contained.

**Why.** That is right only if it does not mean building a task spine `tsp-core`
will later replace — which is why A1 is a precondition rather than a suggestion.
Per-step acceptance criteria are in the subtask plan §9.

## Confirmed synergies (no adjustment needed)

- **§4.5's `eddsa-jcs-2022` signer is reusable for task `proof`.** Most VRC-layer
  documents need none — DIDComm authcrypt authenticates the sender, so SPEC
  §4.7.1 permits `proof: OPTIONAL` — but `witness/announce` is a bearer broadcast
  and should carry one. Phase D covers it.
- **The recast is a prerequisite for "VRC-over-TSP," not a competitor.** The
  ecosystem phase listed both without ordering them. The relationship handshake
  cannot ride TSP while it is a regex inside a chat message
  (`vrc-manager.ts:2180`, parsed at `:1410-1424`). Once the exchange is task
  documents, changing carriage is a transport swap by §2.3's byte-identity
  property.
- **§8's claim that "our witness session messages are already Trust-Task-shaped"
  holds up.** `session-request` → `session-challenge` maps onto SPEC §4.4.1's
  `#request`/`#response` convention almost exactly.
- **The `taskContext`-on-VWCs thread** (demo brainstorm, "Witness governance
  under remote connection") lands in `witness/session/submit`'s payload —
  ceremony / device / locality / domain as declared evidence axes rather than
  implied ones, which is what makes remote-witnessed and co-present-witnessed
  distinct honest claims.

## Open questions

1. **A2** — which reading of §7.9 was intended: loose phrasing for
   `vti-didcomm-js`, or a literal Credo-native implementation?
2. **Namespace** — largely answered. The framework editor invited the
   specification as a **joint appendix**, so neither a private authority nor an
   unsolicited registry PR. Residual: slug placement within that appendix, and
   whether a CODEOWNERS entry still makes sense once the work is co-authored.
3. **Is `witness-server` the only counterparty for the witness protocol**, or do
   `openvtc` / `vta-browser-plugin` speak it? Determines whether §7.6 is a
   two-codebase change or an ecosystem migration.
4. **Does the task-layer coexistence policy (A3) need upstream buy-in**, or is it
   purely a client-side stance?

## Earlier position, recorded for completeness

The first pass rated layer B a poor fit on the assumption that
`credential-exchange/*` requires an HTTPS OID4VCI issuer endpoint. It does not —
the family carries OID4VCI *objects* inside Trust Task payloads,
`credential-exchange/issue` accepts a W3C Data-Integrity VC, and the wallet
already registers `OpenId4VcModule` with holder-side OID4VCI and DCQL selection.
That correction opened the question B2 then settled on idiom grounds.
