### The attestation bug the strict badge check found (2026-09-15)

The TSP run on the same two devices passed every marker, but one contact
screen was missing **Secure Exchange** — and the run did not care, because
the shield assertion only logged what it found. Making it strict
(`requireSecureExchange`, and `requireLocality` for the locality variant)
turned the badge into a result instead of a note, and the first strict run
failed on the iPhone's contact for Bob with `Evidence public key does not
match leaf certificate public key`.

**What the iPad's log showed.** Three App Attest keys in one run:

1. `14:51:37` — the attestation prefetch calls `attestKey` on the keychain's
   key id and Apple rejects it (`DCError 2`; the id survives a reinstall, the
   key does not). The native code clears the id and generates key **B**,
   attests it, and caches B's chain — but the JS layer stores that chain
   under the public key it *asked* about, key **A**'s.
2. `14:52:24` — the user authenticates and **B** signs.
3. `14:52:28` — evidence assembly looks up B's chain, misses (the cache holds
   it under A), calls `attestKey` again, and that call clears B and generates
   **C**. The evidence then carried **B's signature with C's certificate
   chain**, which every verifier correctly rejects.

So the bug was not in signing or in TSP or v2 at all: evidence assembly could
destroy the key whose signature it was assembling evidence for. It needed two
things to go wrong together (a cache keyed by the wrong key, and a fetch with
the side effect of replacing the key), which is why it showed on one contact,
on one device, and only after a reinstall.

**The fix.**

- A new native read, `getCachedHardwareKeyAttestation`, returns the chain the
  device already holds for the current key — no Apple call, no key mutation.
  (Android's KeyStore chain is already a local read, so it delegates to
  `getKeyAttestation`.)
- After a signature exists, `HardwareEvidenceBuilder` tries that held chain
  first. The key that signed is known-valid, so the chain it holds is the
  right one, and nothing can replace the key behind the signature's back.
- A chain is **never** paired with a public key it does not certify: when the
  attested key differs from the signing key, the evidence goes out without a
  chain (honest: "no attestation") instead of with a mismatched one.
- A chain fetched for a replacement key is cached under *that* key, so the
  next signature — which will use it — gets a hit rather than a re-fetch.
- The native attest path clears the cached public key and chain whenever it
  clears or replaces the key, so a cached chain can no longer outlive its key.

Four regression tests replay the iPad's sequence (held chain used without a
fetch; mismatched chain never attached; no fetch after signing when the held
chain belongs to a replaced key; a prefetched chain cached under the
replacement key).

**Result — TSP over DIDComm v2, witnessed, strict badges, iPhone + iPad:
green.** Both contacts show **Secure Exchange + Verified**. The device logs
show the new path doing its work: the key is still replaced during the
prefetch ("Attestation was issued for a different key than requested"), the
chain is cached under the replacement, and evidence assembly after signing
reports `Attestation: cached (2 certs)` with no Apple call — every
verification `chain=YES, sig=YES, pubkey=YES, errors=0`.

**Two harness fixes this needed.** A debug build on a device loads its JS from
metro whenever metro is reachable, and after a source change the first bundle
takes ~30–55 s. An app relaunched mid-run (the DIDComm v2 and TSP toggles both
require one — the agent fixes its DIDComm versions at construction) sat on its
splash past the 45 s the post-restart unlock waited, on both devices at once.
The runners now build metro's bundle before the sessions start, the unlock
waits 120 s as a backstop, and metro's output is saved to
`e2e/artifacts/metro-*.log` instead of being discarded.

**Result — the same run with locality required: green.** Witness policy
`required`, both devices advertising over Bluetooth to the Mac's adapter, the
pre-flight sheet accepted on each. Both contacts show all three shields:
**Secure Exchange + Verified (Witnessed) + In-Person**. Neither device logged
a single `Evidence public key does not match leaf certificate public key`, and
every hardware-evidence verification on both sides reported `chain=YES,
sig=YES, pubkey=YES, errors=0`.

That is the full badge set on physical hardware, over TSP envelopes carried on
DIDComm v2 connections, with Coordinate Mediation 2.0 on both wallets — the
thing none of the simulator suites can prove.

**Result — DIDComm v1 on the same two devices, strict badges: green.** The
