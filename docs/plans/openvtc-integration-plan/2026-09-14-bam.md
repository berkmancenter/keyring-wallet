## What was asked, and why the first framing was wrong

The initial ask: investigate the sibling `verifiable-trust-infrastructure`
repo's VTA functionality and plan (1) a TypeScript version that passes the
same automated tests, (2) hooks to keep it aligned with upstream
automatically, (3) which repo it should live in. Read literally, that's "port
`vta-service` to TS and run it as a server we control."

A clarifying question surfaced the actual goal: **Keyring should be able to
operate without any external/hosted VTA at all** — the phone custodies its own
keys already; what it lacks is ACL evaluation and Trust Task dispatch, which
today only exist server-side. Wake-up is a "blank" push notification that
triggers a DIDComm/TSP fetch; the real content arrives in the fetched message,
not the push payload. The subtask document is written against this corrected
framing, not the literal one.

Two forked investigations (Rust VTA internals + Keyring's existing
push/mediator machinery) established the facts the subtask cites: the Rust
VTA's Trust Task logic isn't a separable dispatch core (task-by-task scoping
required); ACL is the one cleanly-factored exception
(`vti_common::acl`); the wake pattern needed already exists upstream as
`binding/push/0.1` + `vta-mobile-core::push`; `did:webvh` self-hosting is
avoidable via `did:peer`; and, on the Keyring side, push registration and iOS
background-mode entitlement exist but nothing consumes them — no background
message handler, no background-execution mechanism, mediator pickup is
foreground-only.

## Why this isn't already covered by `pnm_cnm_subtask.md`

That document ports `@openvtc/pnm-core` to React Native (its §3.2, "Strategy
C") — a real, already-decided, already-detailed plan. But `pnm-core` is a
**client of a remote VTA**: it holds "an authenticated session with a VTA" and
drives `~79 spec/vta/*` ops against one. Nothing in it embeds VTA-side custody
or ACL or dispatch on the phone; it assumes the VTA is elsewhere by
construction. The subtask's §1/§4.5 state this explicitly, including the one
real overlap: VTC (community) membership architecturally requires a real
hosted VTA+VTC pair no matter what the embedded document builds.

**`docs/plans/openvtc-integration-plan/vta-carriage_subtask.md`** — this one
required real integration, not just a citation update. It independently
established (its §2) that fully decentralized relationship negotiation —
no VTA of any kind — is already Keyring's shipping behavior, and it names and
uses the VTA's own policy-evaluation vocabulary (its [[DTTE]]/[[VTA-OVERVIEW]]
references: "signing oracle with policy," task-consent + approvals, a Policy
Decision Point with a default-deny-with-notify disposition) for exactly the
capability class this subtask is trying to bring on-device. Rewrote the
embedded-VTA subtask's §1 and §4.3/§4.4 to: (a) state plainly that decentralized
negotiation itself is not new work — only the *policy-evaluation* layer is;
(b) adopt PDP/DTTE terminology throughout instead of parallel invented terms
for the same concept; (c) add an open question about whether this document's
on-device PDP and that sibling's VTA-side PDP should ever be one

**Two claims corrected because the world moved, not because they were wrong
when written:** `bifold/packages/credo-tsp-adapter` is now a real, shipped
