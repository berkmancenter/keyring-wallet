## 1. The question that started this

A VRC exchange between two people, each running a PNM against their own VTA —
does the task travel VTA-to-VTA? Working through it live surfaced a real design
gap, not a documentation gap:

1. First pass found `openvtc`'s `KeyBackend::Vta` mode — the PNM fetches its
   own key from its VTA via `GET /keys/{key_id}/secret` and then runs the
   whole DIDComm relationship protocol itself. Concluded (wrongly) that this
   was *the* VTA model.
2. Corrected against `docs/01-concepts/architecture.md`'s own words: a VTA is
   "a signing oracle with policy... private key material never leaves the
   VTA's process." `KeyBackend::Vta` key-export is real but is a *different*,
   also-legitimate pattern (`docs/02-vta/integration-guide.md`) for a service
   that needs to run its own independent process — not the general model.
3. The general model — DTTE/approvals (`task-consent.md`, `approvals.md`) —
   genuinely is "always on, acts on saved policy while my PNM sleeps,
   escalates to me only when a rule requires it." That part of the intuition
   was right and is real, documented infrastructure.
4. But nothing wires a VRC/witness exchange onto it. `trust_tasks_subtask.md`
   §8.5 already found upstream's own relationship exchange (`openvtc`)
   predates Trust Tasks and was never migrated, unlike the sibling VMC flow
   which was. No VTA anywhere — Keyring's or upstream's — has ever run a
   peer-to-peer relationship or witness ceremony through its own always-on
   Trust-Task dispatcher. This is real, unbuilt work.

Three parallel research forks then established: the VTA's ACL has no
stranger-carve-out today, but `vtc-service`'s VIC (Verifiable Invitation
Credential) verification is the right precedent (authenticate from the
document's own proof, not ACL membership); `witness-server` is already a
working, always-on, cold-contact-open precedent (`autoAcceptConnections:
true`, gated at the message-type level, no ACL at all); `trust_tasks_subtask.md`'s
wire design is topology-agnostic by construction — `propose#response` already
carries only `{ relationshipDid, accepted }`, no credential, so nothing in the
wire shape blocks retargeting it at a VTA; and `openvtc`'s Persona/VTA
identities are always architecturally distinct, with no daemon mode, so
`openvtc` itself is not a vehicle for the VTA-mediated path.

## 2. The design decision from the first draft — and the flaw in it

**First draft's split:** `vrc/relationship/propose` (negotiation, no
credential) becomes VTA-eligible. `vrc/relationship/issue` and the witness
ceremony (`witness/session`/`submit`) stay PNM-to-PNM, justified by a single
claim: witnessing requires physical co-presence per
[`../locality-plan.md`](../locality-plan.md), so a VTA "cannot stand at the
meetup."

**The flaw, caught on review:** that justification conflates three separate
things under one "always PNM" rule, and only one of them is actually a hard
constraint.

1. **Witnessing is not inherently physical.** `trust_tasks_subtask.md` §5
   already states this: *"An unwitnessed exchange is the outer thread alone —
   `propose` → `issue`, with the ceremony block simply absent. Witnessing is
   additive, never a precondition."* `witness-server` itself has no locality
   requirement in its protocol — session/challenge/submit run over plain
   DIDComm. Locality (BLE co-presence evidence) is `locality-plan.md`'s
   *addition* on top of the witness ceremony, layered in as `ext` payload on
   already-existing documents — it does not redefine what witnessing is.
2. **`issue` has no physical-presence requirement in any case** — witnessed,
   unwitnessed, local, or remote. The real reason to keep it PNM-bound is a
   *different* argument entirely: avoiding a second, independently-audited
   implementation of DTG-credential logic (JCS canonicalization,
   `eddsa-jcs-2022` proof construction, VP assembly) inside `vta-service`.
   That is a legitimate engineering-cost argument, but it is a **custody
   choice**, not a **physical constraint**, and the first draft borrowed
   locality's hardness to make a softer argument sound settled.
3. The same custody question, not a physical one, applies to
   **VP-signing in a *remote* (non-local) witness ceremony** — signing
   `submit-presentation` requires the credential-bearing key regardless of
   whether the parties are in the same room.

## 3. The corrected model: three axes, not one rule

| Axis | Nature | What it forces |
|---|---|---|
| Negotiation (`propose`) | No physical or custody constraint | Unaffected — VTA-eligible as designed |
| **Locality** (optional) | Hard physical constraint, **only when engaged** | When used: that specific ceremony **must** run PNM-to-PNM — BLE radio and a human body are not things a VTA has. When not used: no constraint from this axis at all |
| **Credential custody** (`issue`, and VP-signing in *any* witness ceremony) | Engineering/duplication-avoidance choice | Defaults to PNM (avoid a second credential-issuance stack), but is a revisitable decision, not a wall |

Locality forces PNM-to-PNM when chosen — that is now a confirmed, unconditional
axiom, not a design preference. But it only governs *that* ceremony. It says
nothing about the (likely more common) unwitnessed or remotely-witnessed case,
where `issue` staying PNM-bound is a deliberate default for a stated
engineering reason, not a physical necessity.

**What this opens up, named and deliberately deferred rather than built or
foreclosed:** once custody is separated from locality, a real third tier
exists for the non-local case — full autonomy, negotiation *and* issuance,
for a pre-authorized class of counterparty, no human ever woken. Building
that into `vta-service` would be exactly the duplication rejected above. VTI
already has the right shape for it without touching `vta-service`, though:
the existing `ai-agent`/Service-consumer pattern
(`docs/02-vta/personal-ai-agents.md`) — a separately-registered, always-on
agent holding its own VTA-issued key, under a least-privilege capability
grant. A user wanting full autonomy for non-local relationships could run one
of these; the VTA's handoff on an accepted `propose` would go to that
registered agent instead of the human's phone. Not v1 scope, but the handoff
mechanism (§6 of the subplan) is worded generally enough not to require
rework if this gets built later.

## 4. What this supersedes

Supersedes the first draft's blanket "witnessing/issuance is always PNM
because locality" framing. The negotiation/custody split itself survives
unchanged — only its justification and scope are corrected. Nothing in
`pnm_cnm_subtask.md` or `trust_tasks_subtask.md` needs to change beyond what
the first pass already added; the fix is entirely within the new subplan.
