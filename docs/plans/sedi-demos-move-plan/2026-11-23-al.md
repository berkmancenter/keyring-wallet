## Summary

<!-- plan-part: human -->

> **Human part: for people deciding and reviewing.** What was concluded and what it
> asks for. The findings below are authoritative; if the two disagree, the findings win.

Alberto widened the plan's scope in review. Keyring keeps `did:webs` so it can work with VTC communities whose DID is a `did:webs`: joining, signing in and being vetted. It no longer supports the guardianship flow, trusted approvers ("Who approves") or their Developer options rows. The state office's server side is already scaled down.

What that changes in the plan:

- **D2 is reversed.** `chain.ts`, `controller.ts`, `keriEvents.ts` and `rootKel.ts` leave with the demo, and the KERI holder plan is parked.
- **D6 removes trusted approvers.**
- **D7 keeps "Confirm it's you"**, minus the SEDI umbrella kill. This is open for Alberto's confirmation.

The trace shows two things.

- **None of the three journeys needs the demo.** Join, sign-in and vetting work without it.
- **All three load trusted-approver code** through one file, the agent client `vtaAgent.ts`. That code runs on every inbound agent message.

Two risks follow, and the plan adds a step or a test for each:

- **The trusted-approver rules live on the agent, not the phone.** A tester who still has approvers when the code goes could not join a community again, and could not remove the rule. The plan empties every set first (S0b).
- **The link and inbound paths change.** The guardian-card link check runs first on every link, and the inbound handler sits on every journey. The plan writes two tests on `main` before anything is deleted (S2, S2b), and runs the full device gate on the removal branch, hidden vetting included (S7).

## Findings

### 1. The scope is the demo, the guardianship flow and trusted approvers

- **Concluded:** plan Scope, Overview, §1, D2, D6, D7.
- **Evidence:** the product decision of 2026-11-23 (Alberto, in review): keep `did:webs` for VTC communities; drop the guardianship flow "and the rest"; consider removing the Developer options parts and the "Who approves" screen. The state office's server side is already scaled down, so the demo cannot run end to end; this supports R1's archive recommendation.
- **Supersedes:** the scope "the SEDI demo only, with trusted approvers and Confirm it's you kept as non-SEDI features" (the inventory's finding 3 and plan §2.4 before this review).

### 2. Join, sign-in and vetting reach the removal set, but need none of it

- **Concluded:** plan §2.6.
- **Evidence:**
  - **How it was traced:** an import graph over core, its tests and the app. It follows static imports, `import()`, `require` and `jest.mock`, and drops type-only edges. No `require` outside tests uses a computed path.
  - **The two runtime hooks:** `vtiLinks.ts:126` calls `isGuardianCardLink` on every link, before every other classification. Every journey goes through `vtaAgent.ts:42-43`, which imports `afterStepDown` and `foreignApproval`.
  - **The join screen:** `VtiJoin.tsx:1056` renders `ApproverWaitNote`. It shows nothing while the switch is off.
  - **`did:webs` resolution:** it needs only `parseWebsDid` and `getArtifact`. `resolve.ts` imports `kel.ts`, the CESR reader and `document.ts`, which is why those stay.
  - **Clean of the removal set:** `oobSignIn.ts`, `triggerLink.ts`, `joinLink.ts`, `VtiMediatorTransport.ts`, `VtaClient.ts` and `packages/trust-tasks`.
- **Supersedes:** the inventory's finding 1, that `WebsDidResolver` is "the only non-demo runtime import of `modules/sedi`". That is still true of `modules/sedi`. It misses the runtime paths into trusted-approver code, which was outside the inventory's scope.

### 3. `resolveWebs` has no product caller

- **Concluded:** plan §2.1, D1, R9.
- **Evidence:**
  - **Its only callers:** `rootKel.ts:25`, `designatedAliases.ts:72` and `webs/guardian.ts:46`, all demo.
  - **What sign-in actually does:** `WebsDidResolver.ts` calls `getArtifact` for `did.json` and hands the document to Credo. So `did:webs` sign-in does not verify the KEL, today or after the move.
- **Supersedes:** the reading of D1 that removing the gate keeps the verifier "live". It keeps it callable, with no caller.

### 4. Trusted-approver rules outlive the code that answers them

- **Concluded:** plan §2.7, D6, S0b, R7.
- **Evidence:**
  - **What the set holds:** `module/trustedApprovers.ts:41-63` puts `vta/webvh/dids/create/1.0` to `1.2` (a community join mints a persona), `acl/grant/*` and `policy/upsert/*` in the `keyring-trusted-approvers` set on the person's VTA.
  - **The approver's side:** the approver's phone lists a relayed request only through `approvedAgentOf` (`foreignApproval.ts:61-64`, behind the switch), which the removal deletes.
  - **The asker's side:** deleting the set is itself `policy/upsert`, which the set holds.
- **Supersedes:** nothing written; the plan did not cover trusted approvers.

### 5. Corrections to plan §2.3, §2.4 and S4

- **Store and container:** `store.tsx` has five demo fields, not three. The plan missed `enableStateVerifiedApprovers` and `enableTrustTestState` (`:49-58`, `:93-94`, `:204-205`). `container-imp.ts` has five loads and five setters (`:398-402`, `:437-451`, `:506-511`).
- **Test ids, not locale keys:** `SetUpSediDemo` and `TurnOffSediDemo` are test ids that tests assert are absent (`DeveloperDemoRowTap.test.tsx:113`, `DeveloperStateVerifiedRows.test.tsx:211`).
- **Missing app locale keys:** `HoldK0RevokedTestCard`, `HoldK0RevokedOmittedCard`, `BecomeK0TestWard`, `Demos`, `DemoStateHost`, `DemoStateHostHint`, `DemoStateHostInvalid`, `PasteDemoStateHost`, `EnableStateVerifiedApprovers` and `EnableTrustTestState` (`app/src/localization/en/index.ts:207-232`).
- **`resolveWebs`' gate:** it reads only `isStateVerifiedApproversEnabled`, not `trustedApproversFlag`. The app also reads the umbrella kill, at `Developer.tsx:1325` and `:1341`.
- **`trustTestStateFlag.ts`:** plainly demo. It adds the K0 root and needs both approver switches.
- **Wrongly classified as SEDI tests:** `confirmItsYouScreens` has no guardian parts; its SEDI ties are the umbrella rows `:25`, `:69` and `:76`. `DeveloperConfirmItsYouRow` is a "Confirm it's you" test, not a SEDI one.
- **Tests the plan missed that load the umbrella:** `confirmChatCard`, `confirmSheetJustTheBox`, `enforcementCheckCard` and `messageWakeNavigation`.
- **`ceremonyRegistry.test.ts`:** it has a guardian-evidence block at `:252-300`.
- **Shared string:** `Approver.UnnamedContact` is used outside the feature in seven places, so it needs a new home before the `Approver` block goes.

### 6. "Confirm it's you" is separable either way

- **Concluded:** plan §2.8, D7.
- **Evidence:** it imports nothing from the demo or from trusted approvers. Its only SEDI tie is the umbrella clause at `confirmItsYouFlag.ts:19` and `:40`. Nothing in join, sign-in, vetting, rooms, polls, badges or sessions uses it. It is on by default, so removing it takes a visible feature from testers: the contact page's "Confirm with" row, the chat action and cards, and the incoming "Is this you?" sheet.
- **Recommendation:** keep it, and treat it as a product question for Alberto, not a SEDI one.
