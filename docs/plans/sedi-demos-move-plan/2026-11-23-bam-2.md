## Findings

### 1. Everything removed from `main` is preserved on `sedi-demos` (applied)

- **Requirement (Brendan):** the demo, guardianship, trusted approvers and all their Developer options rows move to `sedi-demos`; nothing is simply dropped.
- **Plan before:** S0 already cut `sedi-demos` from `main`, so the code was preserved in effect, but the plan did not say that Developer rows, store fields, locale keys and test ids were part of what is kept, nor that S0 precedes every removal, nor what archiving means.
- **Now:** stated in Scope, §1 Goal, §4 Target and S0; R1 says an archived branch is preserved but unmaintained and builds only against the `main` commit it was cut from.

### 2. Joining `sedi-vtc` is proved after the removal (applied)

- **Requirement (Brendan):** confirm Keyring can join `https://sedi-vtc.openvti.net/` (KERI and `did:webs` based) once the work is done.
- **Evidence class:** the VTC is third-party, so the proof is field evidence under the `vti-lab-and-field` skill, not lab evidence.
- **Now:** S7b, after S7's gate, on a Test build of the exact commit that lands on `main`, fresh install and update in place; run with trusted approvers never set and on an agent S0b cleared. It proves the happy path of resolution, join and sign-in and that removing `takeForeignReply` handling broke no inbound reply; it cannot prove refusal paths, revocation or KEL verification (R9). S7 and S8 wait for it, or for a dated "VTC unreachable" record, which blocks merge unless the owner waives it. R10 closes only if the VTC offers vetting and it is run. An Overview table row was added.
- **Open:** whether `sedi-vtc` offers vetting is not known until S7b.

### 3. Step-order bug: S2 and S2b could not pass before S3 (applied)

- **Evidence:** S2's and S2b's "done when" required root `yarn typecheck`, but `Developer.tsx`, `container-imp.ts` and `store.tsx` import what S2 deletes (`stateVerifiedApproversFlag`, `sediDemoSide` and so on) and what S2b deletes, and those edits were in S3, after S2b.
- **Chosen fix:** move the app-side source edits into S2 (demo rows, loads, fields, locale keys) and S2b (trusted-approver row, practice request, the empty "Demos" header, load, field, locale key). Each commit then typechecks and passes root `yarn test` alone. S3 keeps its number and becomes the `e2e/` testids, the `link.js` comment and the clock-row check.
- **Rejected:** merging S2, S2b and S3 into one landing branch with per-commit checks on core only. It keeps the commits unable to pass on their own and renumbers every cross-reference.

### 8. The inbound-reply guard cannot be fully behaviour-only (applied)

Writing the S2b guard test (BAM, same day) showed that the only ask the phone makes whose reply arrives through the inbound path is the foreign-approver decision; the phone's own agent's replies return through the session. So "a reply to an ask the phone made resolves that ask" is trusted-approvers behaviour and cannot pass after S2b. The plan now says the unsolicited-message group must pass unchanged and the foreign-decision group is deleted with the feature (S2b, R8).

Implementing S1 showed that removing the `resolveWebs` gate leaves `switchedOff` as a refusal reason nothing can produce, with two handlers: `webs/guardian.ts` (it fell back to the presented KEL copy when resolution was switched off) and `webs/designatedAliases.ts` (it answered `unreachable`), plus a test row in `designatedAliases.test.ts` that would fail. S1 now removes the reason, both handlers and that row, and updates the stale "behind the state-verified approvers switch" comments and README line. `websResolver.test.ts` also read the `k0-utah-v2` fixture (`PROVENANCE.json`, `kel-sam.cesr`), which S4 deletes (D2); it now uses the AIDs and the `deb` KEL already in `webs-k0-root/`.
