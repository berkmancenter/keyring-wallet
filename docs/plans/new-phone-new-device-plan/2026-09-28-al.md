# 2026-09-28: why this plan, and the PNM-parity gap list

Parent: [new-phone-new-device-plan.md](../new-phone-new-device-plan.md).

## Part 1: reasoning

**The direction.** Keyring acts as the person's own agent manager (a PNM), and the persona's keys stay in the agent (#4, #10). Both come into release 226.

**What upstream does.** Read at the `external/` pins: openvtc `ed13d29`, VTI `ed672fff`, vta-browser-plugin `43e2cc7`, vta-mobile-agent-ios `035dd65`.

- **Recovery re-authorises; it doesn't recover keys.**
  - The admin credential is "an authorisation grant, not an identity" (openvtc `docs/design/vta-authoritative-state.md:88-104`).
  - A new install gets its own ACL entry (:133-155).
  - The openvtc backup stores VTA key ids, never private keys (`openvtc-core/src/config/secured_config.rs:702-704`).
- **Old devices.** Revoke, disable and wipe are offered, not preselected, with last-seen times (design D17, :635-655). The VTA refuses a disabled or wiped device (`vta-service/src/auth/backend.rs:225-239`).
- **Key custody.** Exporting a key is a capability separate from signing, because an exported key outlives withdrawn authority (`vti-common/src/acl/mod.rs:143-159`).
  - openvtc fetches persona keys into memory only (`openvtc-core/src/config/keys.rs:204-213`).
  - The browser plugin never exports; it signs through `vault/sign-trust-task` (`packages/core/src/vault/task-signer.ts:1-12`).
- **Decryption can't be delegated.** A holder "has to hold that DID's private keys to decrypt … It cannot delegate that per-frame" (`vta-sdk/src/trust_tasks.rs:288-294`). No task on the lab's VTI (`63d4c0ca`) or on VTI main decrypts or agrees a key on a persona's behalf. So the key-agreement key stays on the phone, in memory only.
- **Keyring today** borrows both persona keys and persists them (`VtaClient.ts:1047-1050`, `borrowKey` → `keys/export-secret`).

**Positions taken.**

- **Signing uses `keys/sign/0.1` rather than `vault/sign-trust-task/0.2`.** Keyring's proofs include credentials and vetting statements, not only trust-task documents, and `keys/sign` covers all of them through the existing signer seam.
- **Key-agreement keys are held in memory per session.** This is the openvtc model and follows from the missing decrypt task.
- **Signing keys are locked down** (non-exportable) once signing moves to the agent.
- **Rotation after a lost phone is offered only when the agent is new enough.** VTI `83492acf` or later keeps method ids.
- **No new recovery channel in this release.** A recovery approver named in advance is upstream's E1/D23 and isn't built there.

**Rejected.** Copying keys to the new phone: revoking the old phone would then not remove its copies, and every copy is one more place to steal a key from.

## Part 1b: the UX review, same session

The UI/UX lane's review (PR #226) changed four things, all adopted:
- **One removal action.** "Remove this phone" is revoke plus wipe. `device/disable` is dropped from the UI because it's irreversible at VTI `63d4c0ca` (`operations/device.rs:334-360`: it sets `disabledAt`, and no task clears it).
- **Part F added.** It warns once per newly live sibling device, following openvtc (`devices.rs` `sibling_warning`, `device_presence.rs:156-176`).
- **The device key is this-device-only,** so a restored backup links as a new device. Only the device key gets this treatment, not the whole wallet store: making the store device-only would make every local record unreadable after a restore. How our key store holds the device key is to be confirmed before implementation.
- **The post-link offer sits on the new phone,** with equal Keep and Remove choices. The default device name is dated rather than a model string. Offline signing is disabled, not queued.

### Biggest gaps

1. **Signing through the agent** (C of this plan).
2. **Devices, and a new phone as a new device** (A, B, D), and rebuilding a new phone from the agent.
3. **Step-up and approval rules.**
4. **Data the agent keeps:** cards (a branch today), profile, relationships.
5. **Identity hygiene:** persona delete, context delete with a preview, agent-name claim, key list.

### Upstream dependencies

- No remote key-agreement or decrypt task, which blocks the second half of #4.
- The vault refuses proof-set cards (VTI-44 (e)).
- The persona store needs a `persona-holder` grant that no role carries.
- Whether rotation keeps method ids on the Farm depends on the Farm's VTI commit, which isn't published.
