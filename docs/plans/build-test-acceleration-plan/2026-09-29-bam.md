### 1.2 Caching

- **Present:** `quality.yml` caches `.yarn/cache` (`enableGlobalCache: false` makes that work). `test-builds.yml` and `staging.yaml` cache Pods by `Podfile.lock`. `staging.yaml` enables `setup-java cache: gradle`, then deletes `~/.gradle/caches` before building.
- **Absent:**
  - A yarn cache in the build workflows, and a cache of `bifold/.yarn/cache` anywhere.
  - Gradle: deliberately wiped at `test-builds.yml` (`rm -rf ~/.gradle/caches ~/.gradle/daemon`). The comment says a restored cache left library codegen folders missing.
  - DerivedData, ccache and Metro caches. Metro's is explicitly reset (`--reset-cache`) in both `test-builds.yml` and `staging.yaml`.
  - Any remote build cache, EAS, Turborepo, Nx or sccache.

### 1.3 Install path

- **Every install rebuilds bifold.** The root `preinstall` runs `scripts/ensure-bifold-ready.js` on every `yarn install`, and it runs `yarn build` in bifold unconditionally. It skips bifold's own install only when `bifold/node_modules` exists.
- **The rebuild is never incremental.** Most packages' `build` scripts run `clean` (rimraf) first, then `tsc` or `bob build`; `witness-server` and `mediator-server` run plain `tsc`. Core's bob build emits three targets: commonjs, module and typescript.
- **Measured double build in one CI job:**
  - The explicit "Build bifold packages" step finished with `Done in 52s`.
  - The root `yarn install` then ran preinstall and rebuilt everything (`Done in 56s`).
  - Quality jobs pay for the bifold install and build inside their ~230 s "Install dependencies", once per job.
- `fix-portal-symlinks.js` and the patches (10 yarn `patch:` entries across the root and `app` `package.json`, 12 files in `.yarn/patches`, 5 patch-package patches) cost little.

### 1.4 Native configuration

- **Android** (`app/android/gradle.properties`, `app/android/app/build.gradle`):
  - `reactNativeArchitectures=armeabi-v7a,arm64-v8a,x86,x86_64`, and `abiFilters` for all four are hard-coded in `defaultConfig`.
  - `newArchEnabled=true`, `hermesEnabled=true`. Gradle 8.14.3, NDK 27.1, CMake 3.22.1.
  - `org.gradle.daemon=false`, `org.gradle.parallel` commented out, no configuration cache. `org.gradle.logging.level=info` is verbose enough that the Actions log viewer truncates before the build finishes.
  - `org.gradle.caching=true`, but the cache directory is deleted each CI run. jvmargs are 6g, while CI overrides `GRADLE_OPTS` to 2g.
  - **Configuration and dependency resolution took about 5 min** (log timestamps from "Welcome to Gradle" to "Selected primary task"), all downloaded cold.
  - CI runs `npx react-native bundle --reset-cache` by hand, and the `react {}` block is at defaults. So `createBundleReleaseJsAndAssets` probably bundles a second time (inferred).
  - `test-builds.yml` builds `bundleRelease assembleRelease` but uploads only the APK.
  - The debug-only override `reactNativeDebugArchitectures` exists in `build.gradle` but is undocumented. `yarn android` uses `--active-arch-only`, but the e2e README's plain `./gradlew assembleDebug` builds all four ABIs.
- **iOS** (`app/ios/Podfile`):
  - 146 pods (239 `PODS` entries in `Podfile.lock`, counting subspecs), `use_expo_modules!`, Firebase with modular headers. Hermes uses the prebuilt pod.
  - **React Native core compiles from source.** `RCT_USE_PREBUILT_RNCORE` and `RCT_USE_RN_DEP` are not set anywhere, and there is no `React-Core-prebuilt` or `ReactNativeDependencies` in `Podfile.lock`. No ccache.
  - CI builds are Release with the bundle embedded, using an uncached `-derivedDataPath`.

### 1.5 The JS-only path that already exists but is not wired in

- `scripts/ci/js-only.mjs` decides, from git objects alone, whether a change can ship as a new bundle inside an existing native build. It uses two guards: a per-file allowlist and a fingerprint of every native input, including the `.env` that `react-native-config` bakes into native code. Any doubt answers *full*.
- `scripts/ci/js-swap.sh` performs the swap in about 2 min.
- No workflow calls either script. `test-builds.yml` also computes its own `native` fingerprint and uses it only for the manifest.
- B1 in the plan wires these in rather than writing anything new.

### 2.4 Setup floor vs work

- **An empty test file takes 5.8 s** (core, warm, one worker; the test itself shows 3934 ms).
  - The cause is `bifold/packages/core/jestSetupAfterEnv.js`: its `beforeEach` calls `require('./src/hooks/notifications')` in every test file. That pulls in `@credo-ts/core`, `@credo-ts/didcomm`, the openid module and `@bifold/verifier`.
  - The comment there ("Module may not be loaded yet") is wrong: the require itself is what loads the module.
  - Without that file the empty test takes 1.9 s. Without any setup file it takes 0.41 s, so `jestSetup.js` (react-native, gesture-handler, bifoldLogger) accounts for about 1.5 s.
- **Proof the setup line is removable.** A temporary config that drops only `jestSetupAfterEnv.js` passes all 3183 tests. Warm wall went from **181 s to 149 s** and CPU from **1141 s to 817 s (−28%)**. This is what U1 is based on.
- **Transform cost (cold minus warm):** core 99 s wall and 555 CPU-s; app 121 s wall.
  - The core cache holds **6071 transformed modules against about 885 first-party files** (570 src + 315 tests), so about 5,000 come from `node_modules`.
  - `@credo-ts` is 1722 files and 40 MB of ESM-only `.mjs` that has to be converted to CommonJS. `react-native` is 740 files, all through the full RN babel preset.
  - When the cache is cold, all six workers transform the same modules at once: app's first six files each took about 122 s.
- **Test bodies vs loading:**
  - Core: time inside tests is 37% of summed file time, and about 90 s of that is idle real-timer waiting.
  - App: time inside tests is **2.5%** (2 s of 82 s); the rest is module loading.
- **Sharding:** `--shard=1/4` works (79 files listed).
- **`--changedSince=HEAD~5`** selects 193 of 315 core files (61%). This is the evidence for rejecting it as a lever.
- **swc/esbuild** is safe for `node_modules`: credo's build is already compiled, there are no decorators to lower, and `emitDecoratorMetadata` is off in `bifold/tsconfig.json`. First-party source still needs babel for `react-native-reanimated/plugin` and the module-resolver aliases. That is why U4 transforms `node_modules` only.
- **180 of 315 core files** never import `@testing-library/react-native`, which is the population for U5's `node` project. 85 files import `@credo-ts` directly.

### 2.5 Expected outcome

- U1 + U3 + U5 on a warm cache should take core from about 180 s to roughly 50–60 s.
- Adding U2 (CI cache) and U6 (four shards) gets CI close to 10× from today's cold 280 s (core) and 141 s (app).
- U4's gain, estimated at 3–5× on the transform phase, is **not measured**.

## 3. E2e

### 3.1 Orchestration

- **Structure:** there is no test framework. Each scenario is a plain node + webdriverio `run-*.js` script, one linear test, so every scenario pays the whole setup again.
- **Appium:** each run spawns its own server (`e2e/lib/driver.js`) and stops it at the end.
- **Sessions are created one after the other, on purpose.** Booting in parallel was starving the host's CPU.
- **Fresh install every time:**
  - `appium:fullReset: true` on both platforms, plus `enforceAppInstall` on iOS (`e2e/lib/config.js`), so the app is uninstalled at the start and again at the end.
  - `E2E_KEEP_APP` / `E2E_KEEP_STATE` allow chaining runs on one install, but the standard runners don't use them.
- **Per-session setup:**
  - Android: `adb logcat -c`, `adb reverse` for Metro, `activateApp`.
  - iOS: a simctl camera grant, then terminate, sleep 3 s, activate, sleep 3 s — 6 s fixed.
  - WebDriverAgent is prebuilt and reused when present.
- **Onboarding runs through the UI every time.** `completeOnboarding` (`e2e/lib/flows.js`) walks the tutorial, PIN, PIN re-entry, biometry, wallet name and R-Card form, with a 5-min budget plus 120 s after the R-Card submit.
  - It checks for screens in a fixed order with a 2 s timeout each, so a screen late in the order pays up to 6 × 2 s of misses first.
  - Every miss also runs two more lookups (the locality pre-flight sheet and the sibling notice) inside `waitForTestId`. One transcript shows about 466 lookups per key.
- **Two-device coordination:** onboarding, VRC assertions and log-marker checks run in parallel via `Promise.all`. Invitation, paste and the witness connect run in sequence, A then B (`e2e/lib/witnessedExchangeFlow.js`).
- **Witnessed runs:**
  - Metro is warmed first (a cold bundle is *measured* at 54 s).
  - A cloudflared tunnel starts, with a fixed 5 s wait after its URL appears (`e2e/lib/witness.js`).
  - The witness runs via `ts-node --transpile-only` with a 180 s readiness budget.
  - `enableHardwareAttestation` is a PIN-gated settings round trip. `enableDidCommV2` and `enableTspCarriage` each restart the app.
- **Mediator:** the wallet's pickup poll is 1 s (`app/src/utils/bc-agent-modules.ts`, `mediatorPollingInterval`). Its comment records device-log measurements of 10 s polling → ~41 s exchange and 2 s → 16–19 s, and gives ~10–12 s at 1 s as a target, not a measurement.

### 3.3 Numbers that exist

- **`yarn e2e:vrc`: about 7 min** on an emulator plus a simulator (`UPGRADE_PROGRESS.md`). Another `UPGRADE_PROGRESS.md` entry records about 9–10 min and attributes it to slow mediator pickup polling. Both figures predate the 1 s polling change.
- **The protocol exchange: about 10–12 s** at 1 s polling. This is the target the code comment projects from the 2026-08-26 device-log measurements at 10 s and 2 s; the 1 s figure itself is not measured there. Hardware attestation adds about 2 s. **The exchange is about 3% of a 7-min run.**
- **Session start with `fullReset`:** about 17–19 s per physical Android phone, one phone after the other, and about 6 s per emulator (*measured* from run transcripts).
- **Run start to witness and tunnel ready:** about 18 s.
- **A stuck onboarding loop:** one physical-device run spent 3.5 min in it (3,240 `findElements` calls) without ever reaching Contacts. The loop can spin for its full budget.
- **Other reports:**
  - An isolated script cut a debugging loop from about 10 min to under 1 min (`docs/E2E_REAL_DEVICE_FLAKINESS.md`).
  - An iPhone WebDriverAgent rebuild once took a run from 20 to 45 min.
  - `docs/RELEASE_GATE.md` targets a ~20-min smoke.
- **CI runs no e2e.** `quality.yml` only parse-checks the e2e files.
- **There is no per-step timing data yet.** `appium.log` has no timestamps, there is no JUnit output, and few transcripts exist, most of them failures. This is why E1 comes first.

### 3.4 Parallelism and state reuse today

- **Not present:**
  - test-level parallelism or device sharding;
  - emulator snapshots, `simctl clone`, or adb backup/restore;
  - a test hook to seed an onboarded wallet. Deep links exist but only for invitations, and the Developer screen toggles don't skip onboarding;
  - any setting that turns animations off. `waitForIdleTimeout` is already 100 ms.
- **Present:**
  - `E2E_KEEP_APP` / `E2E_KEEP_STATE`;
  - `docs/RELEASE_GATE.md`'s persona-reuse *policy*;
  - `e2e/read-vetter-state.mjs`;
  - `scripts/ci/js-swap.sh`.
- **Debug-build dependency:** the harness reads the invitation URL from `__DEV__`-only hidden text, which ties it to debug builds loading JS from Metro. E5 exists to remove this.
- **Key derivation:**
  - The PIN hash is Argon2id with 32 MiB memory and 2 passes (`bifold/packages/core/src/utils/crypto.ts`), probably under 0.5 s (inferred).
  - The Askar store is opened with no explicit key-derivation method, so it likely uses Askar's default on every unlock and restart. Inferred, not measured.

### 3.5 What needs real devices

- **Only real devices can prove:** Secure Enclave and StrongBox attestation, the real biometric prompt, and BLE locality (which also needs a host Bluetooth adapter).
- **Everything else can be proven headless.** That covers protocol logic: DIDComm v1/v2 and TSP carriage, Trust Task markers, the witness ceremony and VWC issuance, mediator fallback and store migration.
- **But today's Node tests don't cover the wallet's own code:**
  - `vrc-reference` runs headless credo agents with its own Alice/Bob code;
  - `witness-server` has 20 test files;
  - `tsp-reference/` rungs run protocol slices;
  - core's VRC tests (53 files under `__tests__/modules/vrc` and `src/modules/vrc`) use mocks.

  None runs the wallet's `core/src/modules/vrc` or trust-task code against real agents. That gap is the reason for §6 of the plan.

### 3.6 Ranked e2e sinks

1. **UI onboarding on a fresh install, every run: roughly 1–2 min per device.** It can spin to its 5-min budget. *Inferred from code, with one transcript as support.*
2. **Per-scenario Appium, install and service startup.** *Measured* at 17–19 s per physical session, 6 s per emulator session and ~18 s for tunnel and witness, all serial.
3. **Poll granularity and fixed settles: tens of seconds per run.** *Inferred.*
4. **App restarts for protocol toggles: about 15–30 s each per device.** *Inferred.*
5. **Serial steps that could overlap.** *Inferred.*
6. **Debug build loading JS from Metro (54 s cold bundle, *measured*), and possibly store key derivation on every open.** *Inferred.*
7. **The actual exchange: 10–12 s.** *Projected* in the code comment, not measured at 1 s. Not the bottleneck.

### 3.7 Hardware alone does not deliver 10× per run

- Warm snapshots and pre-installed builds give about 1.5–2× per run.
- Sharding scenarios across N pairs gives about 10× suite throughput.
- A single flow getting 10× faster needs the test-side work: E1–E5.

This is why the plan orders the software phases before any purchase.

## 4. Biometrics — what the code requires

### 4.1 Where prompts happen

- **Wallet unlock.** This is the in-app PIN, which the harness already types. Optional biometric unlock uses the keychain with `ACCESS_CONTROL.BIOMETRY_ANY` (`bifold/packages/core/src/services/keychain.ts`). The Trust Task owner-confirm uses `BIOMETRY_ANY_OR_DEVICE_PASSCODE` (`core/src/modules/trust-tasks/module/ownerConfirm.ts`), so the passcode is allowed there too.
- **Credo secure-environment key management** runs with `biometricsBacked: false` (`app/src/utils/bc-agent-modules.ts`, `core/src/utils/agent.ts`), so it never prompts.
- **Android attestation key** (`bifold/packages/react-native-attestation/android/src/main/java/com/attestation/AttestationModule.kt`):
  - `setUserAuthenticationRequired(true)`, and `setUserAuthenticationParameters(300, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)` on both the StrongBox and the TEE-fallback builders.
  - `setInvalidatedByBiometricEnrollment(true)`. `setUnlockedDeviceRequired` is not used.
  - The prompt allows `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`, or `DEVICE_CREDENTIAL` alone in passcode mode.
  - Signing tries `initSign` silently first and prompts only on `UserNotAuthenticatedException`.
  - The locality peripheral module mirrors this.
- **iOS** (`bifold/packages/react-native-attestation/ios/Attestation.mm`):
  - App Attest keys have no access control. The gate is app policy only: `evaluatePolicy:LAPolicyDeviceOwnerAuthentication`, which permits a passcode fallback.
  - A 300 s reuse window, scoped to the process ID and stored in `NSUserDefaults`, skips the prompt. The file's own comment says the gate is policy-only.
  - `authenticationMethod` in the evidence is whatever `LAContext.biometryType` reports, read before the prompt, so a passcode fallback on a Face ID phone still records `FaceID`. `LocalityPeripheral.swift` gates with the same `.deviceOwnerAuthentication` policy and honours the same 300 s record, but reports no method of its own.

### 4.2 What the verifier checks

- **Verification runs on the peer wallet** (`core/src/hardware-signing/verify.ts`). For VRC evidence the witness-server records only whether it was present (`hardwareAttestationIncluded` in `WitnessService.ts`); the only signature it verifies is the locality transcript's (`src/trustTasks/locality.ts`, `appAttest.ts`).
- **Android:** the native parser reads `USER_AUTH_TYPE` (tag 504) and `AUTH_TIMEOUT` (505), but not `noAuthRequired` (503) or `trustedUserPresenceRequired`. `verify.ts` passes the parsed values through, and `valid` never depends on them. `CredentialOffer.tsx` displays the method. This is gap 1 in the plan's §9.
- **iOS:** the evidence contains no user-presence proof at all. This is gap 2.

### 4.3 The harness today

- `handleBiometricConfirmIfPresent` taps the in-app Confirm, prints an OPERATOR banner and sleeps 5 s.
- `acceptSystemAlertIfPresent` deliberately never touches the OS prompt.
- `e2e/README.md` describes roughly 2 attended prompts per phone.
- Nothing calls `mobile: sendBiometricMatch` or `adb emu finger`.

### 4.4 Options evaluated

| Option | Reliability | Preserves the proof? | Disposition |
|---|---|---|---|
| Emulator/simulator injection (`adb emu finger touch`, `mobile: enrollBiometric` + `sendBiometricMatch`) | High | No hardware attestation at all | Prompt-UX checks only |
| Android: keyguard PIN over adb, then silent `initSign` | Expected high; to be confirmed by the plan's Q1 | Yes for key properties; no biometric match | **Adopted** (A1) |
| Android: type the PIN into the prompt's "Use PIN" screen via adb or UiAutomator2 | Unverified. `FLAG_SECURE` blocks screenshots, not input | Same as above | Fallback for A1 |
| iOS: WDA drives the LocalAuthentication passcode sheet | Not possible on physical devices (out-of-process UI) | — | Rejected |
| iOS: compile-time e2e-only bypass of `evaluatePolicy` | High | Yes for everything a verifier checks. Loses only the app-side LocalAuthentication gate | **Adopted** (A2), with the Release-binary check and verifier rejection (A3) |
| Robotic tapper plus fingerprint replica (Touch ID; Pixel under-display sensors) | Low to medium, costly | Yes | Rejected |
| Face ID automation | Not realistic | — | Rejected |

The split follows from the table: unattended nightly runs use A1 and A2, and a short attended release gate proves the real prompt and method.

### 5.4 Keeping phones on the charger

- **Pixel:** "Limit to 80%" exists on the 6a and later. Bypass charging (the phone runs on wall power while the battery idles) exists on the Pixel 8 and 9 series from Android 15 QPR1. The a-series is unconfirmed, which is the plan's open question Q5.
- **iPhone:** a hard 80% limit exists on the iPhone 15 and later, including the 16e and 17e. The SE 3, 13 and 14 only have Optimized Battery Charging, which is unreliable on a phone that's always plugged in. Those need a smart plug on a charge cycle, or the risk accepted.
- **Supervise iPhones with Apple Configurator** to suppress update prompts, keep the screen awake and restore quickly. Keep an "enable UI Automation" re-toggle in the runbook (XCTDaemon Code=41 after a re-plug).
- **Budget** one battery or device replacement per phone per two years, about $100 each.

### 6.3 Self-run AWS

- **EC2 Mac** is a dedicated host billed per second with a **24-hour minimum allocation**, a condition of Apple's macOS licence. There is no spot pricing. Savings Plans cut up to 44% on a 3-year term.

  | Instance | On-demand, us-east-1 |
  |---|---|
  | `mac2-m2.metal` | $0.878/hr |
  | `mac2-m2pro.metal` | $1.56/hr |
  | `mac-m4.metal` | $1.23/hr — about **$898/month, $10.8k/yr** always on |

  Real iPhones can't be attached to EC2 Mac.
- **Linux KVM:**
  - Since 2026-02-16, nested virtualization works on *virtual* C8i/M8i/R8i instances at no extra cost, so bare metal is no longer needed.
  - `c8i.4xlarge` (16 vCPU / 32 GB) is $0.750/hr on-demand or $0.373/hr spot.
  - `c7i.metal-24xl` (96 vCPU) is $4.284/hr on-demand, $1.138 spot or $2.834 on a 1-year RI.
  - **Density estimate:** a headless emulator needs about 2–4 vCPU and 2–4 GB. A 16-vCPU host runs one pair comfortably; a 96-vCPU host runs roughly 20–30 emulators.
- **Real devices on AWS** means Device Farm private devices (§6.1).

### 6.4 Self-run GCP

- Nested virtualization works on N2/C3 at no extra charge.
  - `n2-standard-16`: $0.777/hr, spot $0.466.
  - `c3-standard-22`: $1.11/hr, spot from about $0.12/hr.
- **GCP has no macOS offering**, so the iOS leg has to go elsewhere.
- **Real devices on GCP** means Firebase Test Lab, which cannot coordinate a pair.

### 6.5 Scale-to-zero and pre-warmed images

- **Scaling to zero:** actions-runner-controller on EKS or GKE (the EKS control plane is about $73/month), or a per-job spot launcher. GitHub charged no self-hosted platform fee as of 2026-09-28.
- **Android:** bake an image with the SDK, the system image and the AVDs. Save a quick-boot snapshot with the app installed and a persona onboarded, and boot with `-snapshot <name> -no-snapshot-save`. That removes about 60–120 s of boot, install and onboarding per emulator.
- **iOS:** keep simulators booted on a persistent Mac, `xcrun simctl clone` from a golden simulator for each run, and cache the prebuilt WDA.
- **The recurring cost:** images and snapshots must be rebuilt whenever the app build, the emulator image or Xcode changes. This is the main ongoing cost of the self-run option.
