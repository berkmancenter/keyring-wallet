# 2026-10-11 — the mediator already reports undelivered messages; build steps for 241

Parent: [`../peer-message-notifications-plan.md`](../peer-message-notifications-plan.md).

Written by the push lane after the product owner raised peer-message notifications to a top item
for release 241 (relayed by the coordinator). Read from source; nothing measured yet.

## Findings

**F1. The production mediator already has a webhook for queued, undelivered messages.** The Keyring
mediator is the OpenWallet Foundation's `didcomm-mediator-credo`, deployed at `375518d` (the
08-24 companion of the integration plan records the redeploy). GitHub's compare shows `375518d`
identical to the repository's `main`, which includes "feat: didcomm push notifications module
(#85)" (2025-12-23). With `pushNotifications.webhookUrl` set, the mediator posts
`{connectionId, fcmToken}` "for all messages that are queued and could not be delivered directly"
(README, Push Notifications; `apps/mediator/src/push-notifications/sendNotification.ts`). The
token is what the phone registered with Aries RFC 0734 `set-device-info`
(`packages/push-notifications`, `@credo-ts/didcomm-push-notifications`, built for Credo 0.6.x).

**F2. The gateway accepts a wake over HTTPS from any allowed trigger.** `push/wake/0.2` on
`POST /trust-tasks`, authenticated by an `eddsa-jcs-2022` document proof from the trigger's
operational key (vti-push-gateway `0856939` README, API and Authentication).

## Positions superseded

The 2026-10-10 draft had the mediator sign and send `push/wake` itself, which needed mediator code,
a mediator DID the gateway resolves, and a DIDComm v2 or TSP client (its step 3, "Keyring (the
mediator is ours)"). F1 replaces that: the mediator only needs its existing webhook configured,
and the phone registers its wake handle as the device token. The wake is then sent by the gateway
itself (a new Keyring patch, 0003), as a trigger the phone's agent allowed, so no new DID, key or
service is introduced. A separate relay service was considered and set aside: it would duplicate
the gateway's handle store, identity, senders and rate limits.

The draft's step 1 (per-wake collapse ids through a field on the trigger's request) becomes a rule
inside patch 0003: wakes from a trigger other than the handle's controller agent get their own
`keyring-msg-…` collapse id. The prefix also lets the tap route to Messages, which the draft's step
4 needed and could not do from a contentless wake.
