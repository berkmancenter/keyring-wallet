# 2026-10-10 — first draft: findings and the four options

Parent: [`../peer-message-notifications-plan.md`](../peer-message-notifications-plan.md).

Written by the push lane at the product owner's request (relayed by the coordinator, 2026-10-10).
Read from code and configuration only; nothing here was measured on a device for this draft.

## Findings

**F1. Peer messages never reach either person's agent.** Bifold's chat is DIDComm basic messages
over the connection a VRC exchange creates (`packages/core/src/hooks/chat-messages.tsx`). The
carriage is the integration plan's §7 row 1 (DIDComm v1 via Credo, "existing connections"), and
it delivers through the recipient's mediator, the production Keyring mediator
(`credo-mediator.asml.berkmancenter.org`; integration plan row `ref-06v1b-mediated` calls it "the
production Keyring mediator"). No agent is on the path.

**F2. The gateway already expects a mediator as a trigger.** vti-push-gateway `e542a9d7`
`README.md`:110 lists `push/wake/0.2` as sent by "trigger (mediator/VTA)"; :212 shows an
allowlist with a mediator DID and a VTA DID. The agent builds the allowlist from its own DID and
the device's `suggestedTriggers` (vta-service `operations/device.rs` `set_wake_device`, the
doc comment calls the suggested trigger "typically its mediator"). Keyring sends no
`suggestedTriggers` (wallet `app/src/push/pushWake.ts`), and the Keyring mediator has no wake code.

**F3. The silent later wakes in the 242 test are the shared collapse identifier.** Keyring's
gateway patch 0001 (`04d7330`) uses one configured collapse id for `apns-collapse-id`, the APNs
`thread-id`, the FCM `collapse_key` and the FCM `notification.tag` (`src/sender.rs:86-89`, `:189`);
production configures `keyring-wake` (infra `variables.tf` `alert_collapse_id` default). A later
wake replaces the shown notification. The test (MR3C-MY4H): first wake seen and tapped, four
later ones silent. Not yet reproduced on purpose: step 1 of the plan starts with that repro.

**F4. Only a person's own agent rings their phone today, and only for its own requests.**
VTI-Q47's reading (VTI pin `ed672fff`): `consent_request.rs:168,248` → `step_up.rs:1014`
`push_to_device` → `:1060-1061` `trigger_gateway_wake`. VTI-Q52 records that another person can
ring someone's phone only by holding administrator rights on that person's agent.

**F5. Decision #39 (2026-09-29) stands in the way of named notifications.** No notification
service extension; visible alerts with one fixed localisation key. The push plan's §2 also rules
out a key usable while the wallet is locked ("the second way into the wallet that this design
rules out").

## Options considered

| Option | What the person sees | Cost | Disposition |
|---|---|---|---|
| **A. Content in the push** (sender name or text in the APNs/FCM payload) | Named, per-message | Apple, Google and the gateway read who wrote and what. Contradicts the contentless wake (`binding/push/0.1`) and the push plan's premise | Rejected: privacy, by construction |
| **B. Notification extension fetches and decrypts** (iPhone service extension; Android background handler) | Named, per-message | Reverses #39; needs a key usable while locked (push plan §2); a second iOS target and signing profile; a fetch inside the extension's time limit that can fail | Not recommended now; the only route to named text, so left as a product-owner decision |
| **C. The recipient's mediator rings** (contentless, per message while the phone is away, rate-limited) | "A message is waiting" per message (or per interval in a burst) | Mediator work (ours), a per-wake collapse id at the gateway (our patch, a redeploy), the phone handing the mediator its handle | **Recommended** |
| **D. The recipient's agent rings** (the sender sends a notice to the recipient's agent) | Same as C | A second message per message; an agent task non-administrators cannot call today (VTI-Q52); the sender learns which agent serves the recipient; upstream work | Not for messages while they travel phone to phone; the right path once messages reach the agent (plan §5) |

## Why C over D

The component that should ring is the one that knows a message is waiting. Today that is the
mediator (F1). D makes the agent ring for something it never sees, by adding a parallel notice
from the sender. That is more traffic, more metadata, and an upstream dependency. When the
integration plan moves peer messages to the agents, the agent becomes that component, and D (via
VTI-Q52's hook) replaces C.

## What this draft does not settle

- The message-versus-approval text question and the rate-limit interval (plan §6).
- Whether the gateway accepts the Keyring mediator's DID as a trigger without change (plan §6,
  open question; answered by step 3's first send).
- The repro of F3, which step 1 does before any gateway change. The backlog row "every wake
  shows its own notification" is that step; it is not built until the repro confirms the cause.
