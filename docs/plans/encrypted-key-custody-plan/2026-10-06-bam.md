## Bottom line

**Recommended: a 2-of-3 threshold signing setup on two independent, inexpensive
providers, with an offline recovery share.** Details in section 9.

- Two online signers at different providers (different admins, accounts and
  billing) each hold one key share; the third share is kept offline by the owner.
  No machine ever holds a whole key, and the signers sign without the owner online.
- Each signer independently enforces policy (verifier allowlists, limits, delays,
  alerts). Policy changes require the owner's signature.
- The online quorum holds a limited-authority key certified by an offline root.
- Storage is an AEAD-encrypted dictionary with PRF labels and padded blobs. SSE is
  not needed for a small store looked up by exact ID.
- Estimated cost: about $12-50/mo for the two signers.
- Optional upgrade: move one signer to a confidential VM (Azure first, 0% premium),
  see section 7.

Accepted risks: signing operators see their own usage, and if both providers are
compromised or collude the key is exposed. The design's strength depends on the
two providers being genuinely independent.

Check first, because either could change the design: whether the target credential
ecosystems require hardware-bound holder keys, and whether the signatures must be
ES256 (which needs threshold ECDSA, not FROST). See section 5.

## 1. Goal

A cloud service that holds and uses private keys, used primarily for verifiable
credentials, such that:

- An admin of the cloud infrastructure cannot see or use the keys.
- Someone monitoring the server and the network connection cannot correlate
  particular keys with particular uses.
- Signing can happen without the owner's client being online.
- Running everything inside a TEE is too expensive, so it must work without one
  (or with TEEs only as an optional layer).

## 2. Background: encrypted key-value stores with search

The relevant field is searchable symmetric encryption (SSE) and, more broadly,
structured encryption. There is no scheme with full search and zero leakage.
Every scheme trades functionality and performance against leakage.

### Approaches

1. **SSE.** Encrypted inverted index. The client sends a PRF token per keyword;
   the server follows it and returns encrypted records. Supports exact keyword
   and boolean queries. Dynamic variants need forward and backward privacy
   (Sophos, Diana, Janus). Leaks search pattern, access pattern and result
   volume. Deployed in practice (e.g. MongoDB Queryable Encryption).
2. **Property-preserving encryption** (deterministic, order-preserving,
   order-revealing). Cheap and works with ordinary DB indexes, but leaks
   properties of the values themselves and is broken by inference attacks
   (Naveed, Kamara, Wright 2015). Avoid unless values are high-entropy and the
   attacker is weak.
3. **Structured encryption / encrypted dictionaries.** Generalizes SSE. For a
   pure KV store the core primitive is an encrypted dictionary: PRF-derived
   label, AEAD-encrypted value, padded.
4. **ORAM.** Hides access patterns at O(log n) or worse bandwidth per access.
5. **TEEs.** Rich queries and low leakage, at the price of trusting a hardware
   vendor and exposure to side channels.
6. **PIR / FHE / functional encryption.** PIR hides which record you fetched and
   is practical for modest KV tables. FHE is still too slow for general use.

### Leakage levels (worst to best)

| Level | Server learns | Examples |
|---|---|---|
| L4 | Equality, order or frequency of the values | Deterministic encryption, OPE/ORE |
| L3 | Search pattern, access pattern, volume | Static SSE, dynamic SSE without forward privacy |
| L2 | As L3, but updates unlinkable to old queries; often volume-padded | Modern dynamic SSE |
| L1 | Only that an access happened, plus size and timing | ORAM, PIR |
| L0 | Total size and sync times | Download the encrypted blob and search on the client |

### Expressiveness (weakest to strongest)

Exact key lookup; keyword to record set; boolean; range; substring and fuzzy;
arbitrary computation.

### Cost comparison

| Approach | Bandwidth per query | Server compute | Client state |
|---|---|---|---|
| DET / OPE | about 1x | Native DB index | None |
| SSE | about 1x results plus token | Index lookup | Small |
| ORAM | O(log n) blocks or more | Moderate | Position map or recursion |
| PIR | Small query, server touches all data | Heavy (linear scan) | None |
| Enclaves | about 1x | Native | Attestation |
| FHE | Large ciphertexts | Very heavy | Keys |
| Client-side search | Index size, amortized by caching | None | Whole index |

### Orthogonal concerns

Integrity and freshness (most schemes assume an honest-but-curious server),
updates, multi-user key sharing, volume leakage, and metadata outside the
scheme (timing, sizes, IPs).

## 3. How this applies here

The key store is small (tens to thousands of keys) and looked up by exact ID.

- **SSE is not the main tool.** An AEAD-encrypted dictionary with PRF-derived
  labels covers exact lookup. SSE is only worth adding for server-side tag
  queries; otherwise keep a tag index as another encrypted blob on the client.
- **Hiding which key is used is an access-pattern problem.** SSE leaks access
  patterns by design. For a small vault the right tools are fetching the whole
  vault or PIR.
- **Storing keys and using keys are separate problems.** Storage is tractable
  with the dictionary design. Use without a TEE is the hard part.

### Storage design

- Master secret on a device or token under the owner's control. Derive
  `K_label` and `K_enc` with HKDF using separate contexts.
- `label = PRF(K_label, key_id || epoch)`
- `blob = AEAD(K_enc, record, AD = label || version)`, padded to fixed buckets.
- Server stores `label -> blob` only. Admin sees opaque labels, fixed-size
  blobs and the record count (which can be padded with decoys).

### Hiding usage from a storage-side observer

| Option | Hides | Cost |
|---|---|---|
| Fetch and decrypt whole vault or shard | Everything about which key was used | Bandwidth proportional to vault size; fine up to MBs |
| PIR over labels | Which record, even from the server | Linear pass on the server |
| Epoch-rotating labels | Long-term linkage of a label to a purpose | Re-labeling per epoch; repeats within an epoch stay linkable |
| Dummy queries and batching | Weak statistical hiding | Cheap, mitigation only |

### Network observer

TLS 1.3 with ECH; fixed-shape, padded requests to one endpoint; scheduled or
constant-rate sync; hide the source IP with OHTTP, Tor or a mixnet. Residual
risk: a global observer correlating timing at both ends.

### Integrity and freshness

Signed, versioned Merkle root or monotonic counter held by the client or in a
transparency log. Bind each blob to its label and version via AEAD associated
data. Check monotonic versions to detect rollback.

## 4. Autonomous signing without a TEE

If one server can sign alone with no client and no TEE, whoever administers
that server can also sign or extract the key. Encryption at rest does not help,
because the key must be usable at signing time. The way out is to make sure no
single administrative domain can sign alone.

### Recommended architecture: independent threshold signers

- Generate the key with DKG (or split once on a trusted device) so it is never
  whole in one place afterward.
- 2-of-3 shares:

| Share | Where | Role |
|---|---|---|
| A | Signer 1, provider X | Online, signs |
| B | Signer 2, provider Y (different cloud, admins, account, billing) | Online, signs |
| C | Owner, cold (hardware token or paper) | Offline: recovery, re-sharing, policy changes |

- A and B sign together without the owner. A single admin sees one useless
  share. An attacker must compromise both providers.
- This only helps if A and B are genuinely independent. Two accounts at one
  company, or two VMs managed by one admin, buy almost nothing.

### Authorization and policy

Each signer independently enforces policy, so compromising one does not bypass it:

- allowlists, per-key rate and amount limits, time delays on sensitive
  operations, out-of-band alerts;
- policy changes require a signature from the owner (tied to share C or a
  separate admin key), so a compromised admin cannot loosen rules;
- scoped, revocable credentials for callers;
- anomaly alerts.

### Keep the root out of the online path

The online quorum should hold a delegated, limited-authority key certified by an
offline root, not the most valuable key. Use per-purpose derived keys so one
compromise does not spread. Verify that derivation is supported for the chosen
threshold scheme.

### Additional hardening

- Proactive share refresh (re-randomize shares, same public key).
- Append-only, third-party-held log of signing requests (stands in for
  attestation, which is unavailable without a TEE).
- Monotonic counters and nonces for rollback and replay protection.
- Optional: confidential VM or cloud KMS/HSM layered on top.

### What cannot be hidden

Signing operators learn usage for their own sessions. Autonomous signing and
hiding usage from the signers are incompatible.

| Observer | Learns usage? | Mitigation |
|---|---|---|
| Network observer | Largely no | TLS, ECH, padding, OHTTP/Tor |
| Storage-only admin | No | Encrypted dictionary |
| One signing operator | Partly (its own sessions) | Sign hashes or blinded messages where possible; per-purpose keys |
| Both signers colluding | Yes, and can sign | The core assumption |

## 5. Verifiable-credential specifics

### Issuer keys vs holder keys

- **Holder keys** sign presentations and prove possession (e.g. the SD-JWT
  key-binding JWT). Low volume; a verifier nonce and audience are bound into
  every signature.
- **Issuer keys** sign the credentials. Higher volume; a compromise lets an
  attacker forge credentials for everyone issued to.

### What this changes

1. **Structured payloads make policy meaningful.** Signers can parse audience,
   nonce and disclosed claims, and enforce verifier allowlists, per-credential
   rules, rate limits, and approval for new verifiers.
2. **Holder signing may not need full autonomy.** Presentations usually happen
   while the owner is interacting with a verifier. Pre-approved verifiers can be
   signed autonomously; new or sensitive verifiers can require a one-tap
   approval from a held device. Issuer signing is the case that truly needs
   autonomy.
3. **Unlinkability is a real concern.** One holder key or DID everywhere lets
   colluding verifiers correlate activity. Options: per-verifier or
   per-relationship derived keys (pairwise DIDs, `did:key` per relationship);
   batch issuance of single-use credentials; BBS+ proofs (threshold BBS is still
   research-grade). The signing quorum still sees which verifier.
4. **Keys can be rotated.** DID-document keys (`did:web`, `did:webvh`, not static
   `did:key`) can be rotated, which makes share refresh and re-sharing easier
   and limits the damage of a compromise.
5. **Issuer delegation fits cleanly.** Keep the DID's controlling key offline.
   Publish a short-lived online signing key as an `assertionMethod`. On
   compromise, rotate it in the DID document and revoke through a status list.

### Constraints to check early

- **Curve and scheme decide the threshold protocol.**
  - Ed25519/EdDSA: FROST works, and the output is an ordinary signature.
  - P-256/ES256 (common in SD-JWT VC, OpenID4VC, mdoc): FROST(P-256) produces
    Schnorr signatures, not ECDSA, so ES256 verifiers will reject them. A
    threshold ECDSA protocol is needed; fewer libraries, slower, more complex.
  - secp256k1: threshold ECDSA or Schnorr both available.
  - RSA: awkward and rarely supported.
- **Some ecosystems require hardware-bound holder keys** (e.g. EU digital
  identity wallets, ISO mdoc device authentication). A cloud threshold signer
  may not be accepted there regardless of the cryptography.

## 7. What a confidential VM adds, and how

A confidential VM (CVM) hardens one signer against the host it runs on: the
hypervisor, the provider's operators, and anyone with host-level access. It does
not change who can compromise the guest from the inside.

Without a CVM, the provider's admin or anyone who compromises the hypervisor can
read the signer's RAM and recover its share. With one, they cannot (barring
hardware flaws).

### Mechanisms

- **Memory encryption.** The CPU encrypts the VM's RAM with a per-VM key held in
  the processor, so the hypervisor, host OS and DMA-capable devices see
  ciphertext (AMD SEV-SNP, Intel TDX).
- **Integrity protection.** SEV-SNP and TDX stop the host from remapping,
  replaying or tampering with guest memory pages. Older SEV without SNP lacked
  this and was open to several attacks.
- **Register and state protection** when the VM exits to the hypervisor.
- **Remote attestation.** The CPU signs a report containing the VM's launch
  measurement (firmware, kernel, often an initial image hash). A remote party
  verifies the signature chain back to the CPU vendor and checks that the
  measurement matches the expected software.
- **Attestation-gated secrets.** The decryption key for a share is released only
  to a VM whose measurement checks out, so the share is never in plaintext
  anywhere the host can reach, and is never provisioned to a modified image.

### What it adds to this design

1. Protects a signer's share from its own provider's admin. This is the main gain.
2. Gives a verifiable software identity for that signer, which supports the
   "verifiable" goal and partly replaces the audit log's role for it.
3. Defends against host-initiated memory snapshots, cold-boot and live-migration
   attacks.
4. Adds a second barrier on top of the threshold split: an attacker must
   compromise the other signer and also break or bypass the CVM.

### What it does not give

- Protection from bugs inside the guest. If the signer software or its OS is
  exploited, the CVM protects nothing.
- Protection from the guest's own admin. Anyone with a login to the VM can read
  its memory, so close that access: no SSH, immutable image, measured boot.
- Immunity to hardware attacks. SEV-SNP and TDX have had published side-channel,
  fault-injection and physical attacks. Threat models generally exclude a
  determined attacker with physical access to the hardware.
- Independence. Two CVMs under one admin are still one failure domain.
- Hiding usage from the signer's operator. The service still processes requests,
  and the host still sees network metadata and timing.
- A trust-free root. You now trust the CPU vendor (AMD or Intel) and the
  attestation chain, and in some clouds the provider's attestation service too.
- Freshness. Attestation proves what is running now; it does not stop the host
  from rolling back stored state, so the monotonic counters are still needed.

### Practical notes

- Attestation is only useful if you verify it yourself, against measurements you
  computed from a build you control. Trusting the provider's "attested" label
  gives little.
- Without a custom measured image, the measurement may cover only firmware, which
  proves less. Check what the chosen cloud actually measures.
- Attestation support differs by cloud; Azure and GCP details were not verified
  (see section 6 caveats).
- Some clouds restrict instance types and regions (e.g. AWS SEV-SNP).

### Does it earn its cost here?

Probably not for the first version. The threshold split already means one
provider's admin sees only a useless share. A CVM becomes worthwhile if a
provider-level attacker is a real concern, or if a verifiable software identity
for a signer is wanted. The cheapest way in is one signer on Azure, where the
premium is 0% (section 6).

## 8. Hardened Kubernetes

"Hardened Kubernetes" covers several things:

| Category | Examples | Effect |
|---|---|---|
| Hardened/immutable node OS | Talos Linux, Bottlerocket, Flatcar | Read-only root, no SSH, API-driven management |
| Policy and supply chain | Kyverno, OPA Gatekeeper, Sigstore/cosign, admission control | Signed images only; pod security standards; default-deny networking |
| Workload identity | SPIFFE/SPIRE | Short-lived verifiable identity per workload |
| Sandboxed runtimes | gVisor, Kata Containers | Stronger container isolation |
| Confidential Containers | CoCo, Edgeless Constellation, confidential node pools | Pods in a confidential VM; secrets released after attestation |

**Helps with:** tampering and drift (signed images, immutable nodes), network
exposure, auditability, repeatable operations.

**Does not solve:** the admin-reads-memory problem (only a TEE underneath does);
independence (one cluster is one admin domain, and threshold signing needs
separate operators); complexity and attack surface (a large surface for a tiny
service).

**Cost:** managed control planes can add a fixed fee (from memory, roughly $70+/mo
per cluster on EKS, free or cheap tiers on GKE and AKS; unverified), plus at least
one worker node per cluster. Two independent clusters can easily cost more than
two plain VPSes.

**Fit:** a reasonable substrate for each signer, and the likely route to adding
TEEs later via confidential containers on confidential node pools. Not needed for
the minimum viable version.

## 9. Recommendation

Build a 2-of-3 threshold signing setup on two cheap, independent providers, with
an offline recovery share, signer-enforced policy and a client-signed audit log.

1. Keys: FROST (Ed25519/Schnorr) or threshold ECDSA, depending on curve. No
   machine holds a whole key. Shares A and B on independent budget VPSes; C
   offline.
2. Policy: each signer enforces allowlists, caps, delays and alerts; policy
   changes require the owner's signature.
3. Limited-authority online key: delegated or session key certified by an offline
   root (for VCs, an `assertionMethod` key in a rotatable DID document).
4. Storage: AEAD dictionary with PRF labels and padded blobs; proactive share
   refresh.
5. Integrity: signed, versioned state with monotonic counters, plus a
   third-party-held append-only log of signing requests.
6. Network metadata: TLS with ECH, fixed-shape padded requests, OHTTP or Tor
   where it matters.
7. For holder keys: pre-approved verifiers signed autonomously, new verifiers
   approved from a held device; per-verifier derived keys for unlinkability.

Estimated cost: about $12-50/mo for the two signers.

### Why not the alternatives

- SSE and search: not needed for a small, exact-lookup store.
- ORAM/PIR on the signers: a signer necessarily learns which key it signs with.
- A single confidential VM: still a single point of failure.
- Client-side-only signing: strongest for secrecy but conflicts with the
  offline-client requirement (partly relaxed for holder keys, see section 5).

### Upgrade path

1. Move one signer to a hyperscaler confidential VM (Azure first, no premium):
   about $75-100/mo total.
2. Both signers confidential: about $125-150/mo, only if a provider-level
   attacker on both sides is a real concern.
3. Add a third online signer (2-of-3 online, C still offline) if availability or
   collusion resistance matters more.
4. Adopt Kubernetes or confidential containers only if growth or a TEE decision
   makes them worthwhile.

### Accepted residual risks

- Signing operators learn usage patterns for their own sessions.
- If both providers are compromised or collude, the key is exposed; only policy
  and delegation limits cap the damage.
- If the two providers are not genuinely independent, most of the security case
  disappears. This is the biggest practical risk.
- A global observer correlating timing at both ends is only partly mitigated.

## 10. Open questions

1. Holder keys, issuer keys, or both?
2. Credential formats and signature algorithms (SD-JWT VC, JSON-LD VC, mdoc,
   BBS)? Specifically ES256 vs EdDSA.
3. Do the target verifiers or ecosystems require hardware-bound holder keys?
4. Is the owner present at presentation time, and can new verifiers be approved
   from a phone?
5. Identifier method (`did:web`, `did:key`, other) and how easily keys rotate.
6. Which two providers will host the signers, and where does share C live?
7. Does this build on the existing `keyring-wallet` work under `seas/`?
