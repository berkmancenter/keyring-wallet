# 2026-10-11 — first draft: findings

Parent: [`../community-admission-plan.md`](../community-admission-plan.md).

Written by the push lane at the product owner's request (decision #5, relayed by the coordinator).
His brief, in substance: people must visit a community's landing page to join; from a phone it
should be possible to show a QR code ("my communities"), and to admit people from Keyring; analyse
only the basics, and analyse the CNM upstream for what to reuse, with the same trust tasks; basic
and simple is better.

Read from code only, at VTI `49f5f1be` (the `external/` pin, tag VTI-Eucalyptus) and Keyring
`main`. Nothing was run against a VTC for this draft.

## Findings

**F1. `cnm` has no join-request commands.** Its subcommands (`cnm-cli/src/main.rs:146` onward) are
setup, community, health, auth, config, keys, contexts, acl, auth-credential, backup, audit,
vetting, access, member, consent, actions, git, did-log, bootstrap, did-templates. The only join
traces are the `joinRequests` topic in `actions watch` (`actions_watch.rs:31,53`) and reading the
join manifest for vetting (`vetting/mod.rs:38`). The pnm/cnm subtask recorded the same absence
(§2.5) at an older pin; it still holds.

**F2. The console's join decisions are three trust tasks.** `vtc/join-requests/list/0.1`,
`show/0.1` and `decide/0.1` (`routes/join_requests/decide.rs`: "one payload decides a pending
request either way … Supersedes the former `/approve` + `/reject` pair"). Approval atomically
writes the member's ACL row and record and issues the membership and role credentials; a
redelivered decision is answered from the recorded response; a re-decision is refused
`notPending`.

**F3. A moderator may decide.** Test `a_moderator_may_decide_and_may_not_edit_the_profile`
(`trust_tasks/mod.rs:7488`) signs the decision with a scoped administrator and expects success.
The live topic table gives `join-requests/list` to "any administrator"
(`admin_events/mod.rs:452`).

**F4. `vtc/admin/invites/*` is not member invitation.** It mints a single-use install URL for a new
**administrator**, writes an unrestricted Admin row, and needs the inviter's passkey gesture and
another unrestricted administrator's consent (`trust_tasks/admin_tasks.rs:13-14`;
`routes/admin/invites.rs` header). Easy to mistake for "invite a member" by its name.

**F5. Keyring already reads community codes, and can already build one.** The scanner classifies
a bare community `did:webvh` (what upstream pages draw) and Keyring's own
`keyring://community?d=…&n=…` link (`vtiLinks.ts`; `vtiCommunityLink.ts:51-59`).
`buildCommunityLink` exists and is called by nothing today. Keyring also already sends
`join-requests/manifest` and `submit` (`joinWire.ts:25-26`).

**F6. The tab bar is full.** Six tabs (`TabStack.tsx`: Contacts, Messages, Connect, Credentials,
My Agent, Settings). Communities already have a screen each inside My Agent (`VtiCommunity`,
`MyAgentStack.tsx:73`).

**F7. No wake for a join request.** The VTC signals only its console's stream; VTI-Q47 asks for the
agent path.

## Options weighed for the UI

- **A tab.** Rejected for the basics: a seventh tab, mostly empty for most people (F6).
- **Reshuffling the menu.** Rejected: it moves things people use for a feature few will.
- **The community screen (adopted).** Invite for every member (no rights needed: an invitation is
  not an admission, the community's policy decides at submit); Requests to join only where the
  phone holds an administrator row; a badge on My Agent.

## Positions this draft takes that a reviewer may want to challenge

- **Granting the phone's identity a moderator row is a console step**, not a phone feature. It is
  rare and consequential, and the console already has the review screens for it.
- **No CNM code is ported.** The reuse is the task contracts the console already calls.
- **Which code the QR carries** is left to phase 1 (landing URL versus bare DID), because it
  depends on whether the landing page links into Keyring's Join flow.
