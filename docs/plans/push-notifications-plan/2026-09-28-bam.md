### F1. The wallet does not lock "shortly after backgrounding"

§2 says the wallet "locks itself shortly after the app goes to the background.
So the generic text is the usual case, not a fallback".

- The lock is a timeout, default 5 minutes
  (`bifold/packages/core/src/constants.ts:81`, `defaultAutoLockTime = 5`;
  `contexts/store.tsx:60`), configurable by the person.
- It is evaluated only when the app returns to the foreground
  (`bifold/packages/core/src/contexts/activity.tsx:88-95`, `lockOutUser(
  LockoutReason.Timeout)` on `background -> active`). On backgrounding the
  handler clears the inactivity timer (`:77`), so nothing locks the wallet
  while the process sleeps.
- So a phone woken by a push inside the first 5 minutes is not "locked" by any
  state the app holds, and a killed app has no state at all. "Unlocked +
  background" is the common case for a person who just switched away, which is
  the opposite of the plan's statement.

**Fix.** Rewrite §2 so the branch is on a defined predicate, not on the word
"locked". Define it as: the wallet is *usable in the background* only if a
process is alive with an open agent and the last background transition was
within the auto-lock window; everything else (process dead, window elapsed,
agent not open) gets the generic text. State that the person's auto-lock
setting (`autoLockTime`, `0` meaning never) changes how often the named path
is possible. Add a step, before 1.6, that names the source of that predicate
(a module-level flag set by `activity.tsx` on the background transition, with
a timestamp) and its acceptance test.

### F2. Registration has no local anchor, and two register verbs coexist

Step 1.5 has the phone send `push/register`; §1 says the agent sends
`push/wake`. The plan does not say to whom the phone sends `push/register`,
over which transport, or how it relates to the device registration that
already exists.

- The wallet already registers as a device of the person's agent through the
  Trust Task `device/register/0.1`
  (`bifold/packages/core/src/modules/trust-tasks/module/vtaDevices.ts:31,178`).
  The plan's "Relation" section says this plan "starts after that has
  shipped", but the plan's own message is a second, different register.
- `docs/VTI_UPSTREAM_FINDINGS.md:1809` records upstream's answer to our design
  question: "extend `device/register`, `push/wake`, `task-consent/*` or
  `confirm/request` before drafting anything new". The plan does not say
  whether the wake handle rides an extension of `device/register`, or whether
  `push/register` goes straight to the gateway.
- The gateway receives DIDComm v2 through the shared VTI mediator (§1). The
  wallet's mailbox is the Credo DIDComm v1 mediator (§5.2). The plan never
  states which transport the phone uses to reach the gateway, so an
  implementer has to choose between a v2 client in the wallet and the
  gateway's HTTPS endpoint (§1, last paragraph).
- The opaque handle: who derives it (gateway or phone), and what binds it to
  the person's agent DID, are not stated. "The agent never sees the platform
  token" (§1) depends on this.

**Fix.** Add a §4.1 sub-step 1.5a that records, with citations to the pinned
gateway README, four decisions: the receiver of the register message; the
transport (name the HTTPS endpoint if that is the answer, since it needs no v2
stack in the wallet); the message shapes; and the handle derivation. If the
answer includes a new client in `bifold/`, say so: it is a submodule change
(sign-off as the last trailer line, per the root `CLAUDE.md`), and a new
`@bifold/*` package needs the four wiring entries listed there. Also record
whether the handle travels back to the agent inside a `device/register`
extension, per the upstream answer at `:1809`. Cross-check the wake-up
binding cited at `docs/VTI_UPSTREAM_FINDINGS.md:866`.

### F3. Background execution is not designed

Step 1.6 has four device cases, but nothing in the plan says what code runs
when a push arrives.

- `app/App.tsx:47` and `:50` register empty handlers for background and
  foreground messages ("Do nothing with push notifications received...").
  The named path (fetch the request and name it) needs a handler that opens
  an agent, and the plan does not say whether that is possible headless.
- Message pickup is stopped on backgrounding
  (`bifold/packages/core/src/contexts/activity.tsx:77-83`) and restarted on
  foreground (`:88-113`; `app/src/hooks/useBCAgentSetup.ts:403-420`). A woken
  process that only fetches once has to start its own bounded pickup and stop
  it again.
- `app/ios/AriesBifold/Info.plist:123-127` already declares
  `remote-notification`, but iOS gives a silent handler about 30 seconds, and
  Android limits high-priority FCM messages that do not show a notification
  (the plan cites this in §7 for Phase 3 only).

**Fix.** Add an explicit decision before 1.6: either (a) the background
handler never opens the agent, and the named path is dropped from the
background case (it reduces to "unlocked and foregrounded", where no push is
sent anyway), or (b) it runs a bounded fetch, with a stated time budget,
failure behaviour (fall back to the generic text), and the pickup start/stop
sequence. Option (a) is the smaller design and removes F1's predicate; say
which one the plan picks and why, since the choice decides what 1.6 tests.

### F4. iOS signing and entitlement steps are incomplete

- `app/ios/AriesBifold/AriesBifold.entitlements` has no `aps-environment`
  (only associated domains and App Attest). Step 1.3 covers it.
- Step 1.3 lists "the Remote notification background mode" as work, but
  `Info.plist:123-127` already has `remote-notification`. It also carries
  `audio` and `voip`; neither is used by push, and `voip` implies PushKit
  obligations that App Review checks. Reword the step to "confirm
  `remote-notification`; review the unused modes".
- Step 2.2 adds a notification service extension with "its own app ID and
  signing profile" but does not list what that costs: a new Xcode target and
  bundle ID (`asml.bkc.harvard.wallet.<ext>`), an App ID with push, a profile,
  a Podfile target entry so the extension links without the app's pods, and a
  second `BUILD_PROVISION_PROFILE_BASE64`-style secret in
  `.github/workflows/staging.yaml` (`:74,:110,:820` show one profile today).
  `docs/plans/release-flow-plan.md` says the flow is unchanged; the plan
  should say what it adds there and mark it as a dependency, since the
  release flow's signing step handles one profile.

**Fix.** Expand 1.3 and 2.2 with those items as acceptance lines, and add to
§8 a dependency on the release-flow signing step accepting two profiles.

### F5. The test app ID is not buildable as described

§6 sets `asml.bkc.harvard.wallet.pushtest` "with a matching Android
application ID". Neither project has a switch for that.

- iOS: the bundle ID is a literal in both configurations
  (`app/ios/AriesBifold.xcodeproj/project.pbxproj:687,730`); there is no
  scheme or xcconfig for a second ID.
- Android: `applicationId "asml.bkc.harvard.wallet"` is literal
  (`app/android/app/build.gradle:116`) and there are no `productFlavors`.
  `google-services.json` names the single package `asml.bkc.harvard.wallet`
  (`:12`); a second package needs its own client entry, and iOS needs a
  `GoogleService-Info.plist`, which does not exist in the tree.

**Fix.** Add a step 1.0 that creates the test variant without changing the
release configuration: an Xcode configuration/scheme with its own bundle ID,
an Android `productFlavor` (or a Gradle property override), a second
`google-services.json` and a `GoogleService-Info.plist` selected per variant,
and the isolation rule of §6 as its acceptance test (release build output
unchanged, byte for byte, in its bundle ID and Firebase project).

### F6. The inherited push removal is wider than step 1.2

Step 1.2 removes `PushNotificationsHelper.ts`. The dormant code is spread
further:

- `app/src/hooks/useBCAgentSetup.ts:34-35,364-366,378` and
  `app/container-imp.ts:43-44,255-256` carry commented references.
- `pushNotificationsFcm` is not registered in `app/src/utils/bc-agent-modules.ts`,
  yet the helper calls `agent.modules.pushNotificationsFcm.setDeviceInfo`
  (`PushNotificationsHelper.ts:194`); the code cannot work as it stands.
- Storage keys `UserDeniedPushNotifications` and `DeviceToken`
  (`app/src/store.tsx:122-123`), the `usePushNotifications` preference
  (`bifold/packages/core/src/contexts/store.tsx:48`, reducer
  `reducers/store.ts:53,300`), and the bifold screen
  `screens/TogglePushNotifications.tsx` (its Settings entry is commented out at
  `Settings.tsx:269`) all remain. Those are in the submodule.
- `@react-native-firebase/messaging` is imported and active in `app/App.tsx`,
  so removal is not the whole story: the no-op handlers there are the
  starting point for step 1.6.

**Fix.** List these in 1.2 and split by repo: the `app/` deletions, and the
submodule cleanup as its own commit (sign-off trailer last). Acceptance: a
repo-wide search for `PushNotificationsHelper`, `pushNotificationsFcm`,
`DeviceToken` and `usePushNotifications` finds no live code, and
`yarn lint`, root `yarn typecheck` and `cd app && TZ=GMT yarn jest` pass.

### F7. Firebase dependency and New Architecture compatibility are unverified

- `@react-native-firebase/{app,messaging}` are `~21.14.0`
  (`app/package.json:81-82`), while Android pins `firebase-bom:26.8.0`
  (`app/android/app/build.gradle:205`), a much older BoM than that release
  line expects.
- `newArchEnabled=true` (`app/android/gradle.properties:45`); compatibility of
  the messaging module on RN 0.81 with the new architecture is not checked
  anywhere.
- The Podfile carries `modular_headers` for four Firebase pods
  (`app/ios/Podfile:65-68`); the extension target in F4 has to build against
  the same setup.
- The committed config names BC Government's project, `bc-wallet-mobile`
  (`app/android/app/google-services.json:4`). Step 1.1 replaces it, but the
  replacement file is committed too; say which values are safe to commit.

**Fix.** Make 1.1's "done when" include: the BoM and the RNFirebase version
resolve to a compatible pair (record the pair), and a foreground plus
background message is received on a New Architecture Android build.

### F8. Privacy claims omit timing metadata and stale tokens

§1 says Apple and Google "learn only that a Keyring push went to this phone at
this time". That is accurate for content, and the plan should name what the
gateway and the platforms still see: the timing correlates with the agent's
activity; an empty push has no `collapse-id`/`thread-id`, so repeated wakes
are not deduplicated by the platform; and a token refreshed or revoked while
the phone is offline leaves the gateway waking a dead token. §8 covers "no
unregister" but not token *refresh* while the phone cannot reach the gateway,
nor the case where a revoked phone is already wiped and so cannot "drop its
token" (step 1.5's revoke path assumes the app is running).

**Fix.** Add to §8: timing is observable to the gateway, APNs and FCM; wakes
set `apns-collapse-id` and the FCM `collapse_key` (bounded by the FCM numbers
in §7); and on revoke the agent-side stop is authoritative, with the app-side
drop treated as best effort. Add an acceptance line to 1.5: a token refreshed
while offline is re-registered on next launch.

### F9. Step 1.7 cannot check the simulator claim

§6 says the simulator/emulator claim "hasn't been measured on the project's
machines yet: step 1.7's first run checks it". Step 1.7's acceptance is the
gateway's test sender, "with no Apple or Google keys", which by definition
does not reach APNs or FCM.

**Fix.** Move the check to a step that has keys and a test build: 1.3/1.4, with
acceptance "a sandbox push reaches an iOS simulator and an Android emulator
with Google Play services". Keep 1.7 for the image build.

## Requested testing requirements

The PR description and the plan itself specify tests: per-step acceptance
criteria, and §6's split between simulator/emulator automation and real
phones. The plan does not tie them to the repo's runners. Gaps:

- Step 1.6's four device cases and step 2.2's force-quit case are attended.
  Name the runner: `yarn e2e:vrc:devices` is the only path that proves
  hardware paths, and its attended mode is where iOS force-quit runs. Without
  a named runner, the iPhone criterion cannot be reproduced later.
- §6's automated tier (simulator, emulator) has no runner. Say whether it
  lives under `e2e/` or is a script of the gateway stack, and state the memory
  limits on the shared machine before choosing emulators.
- The gates every step ends on should be stated once: `cd app && TZ=GMT yarn
  jest`, root `yarn typecheck`, `yarn lint`.

## Test coverage

The change is code (token handling, wake handling, removal), so coverage
matters. The plan lists no unit tests. It should require:

- token register, refresh and clear (including refresh while offline, F8);
- the background branching from F1/F3 (predicate true, predicate false,
  process just started, auto-lock disabled);
- the generic-versus-named choice, including a fetch failure falling back to
  the generic text;
- removal of the BC code (F6): a test or search gate that fails if
  `pushNotificationsFcm` reappears;
- gateway-side tests for the Phase 2 patch (payload holds only fixed text and
  flags, step 2.1) and for the rate-limit settings (§5.1);
- a failure-mode matrix for wake delivery: permission denied, token missing,
  gateway unreachable, handle unknown, stale token, app force-quit, device
  wiped.
