# 2026-09-29: the gateway brings its own mediator

Parent: [`../push-notifications-plan.md`](../push-notifications-plan.md)

The server package relied on a DIDComm v2 mediator it did not contain: in
testing, the VTI lab's; in production, "the shared VTI mediator". While the
handover for the engineer who will run it was being written, two things made
that untenable:
- the lab mediator runs on a developer's machine behind a tunnel;
- the hosted VTI stack, the intended shared mediator, was wiped on 2026-09-29.

A handover that tells an engineer to use a mediator nobody can give them is not
self-contained. This companion records the choice of what the package bundles
instead, and why it is not Keyring's own mediator.

## Part 1: Findings

### F1. The gateway can only use an Affinidi-style mediator

The gateway doesn't speak generic DIDComm to its mediator. Its transport is
Affinidi's messaging service crate:
- `affinidi-messaging-didcomm-service` (vti-push-gateway `e542a9d7`,
  `src/didcomm.rs:22-31`, started at `:75-111`) connects, logs in and collects
  messages.
- The same connection carries TSP: "the mediator allows one websocket per DID,
  so the service multiplexes both protocols off it" (`src/didcomm.rs:18-21`).

What that client needs from the mediator is Affinidi's own API:
- a login endpoint, `/authenticate/challenge` and a JWT session (affinidi-tdk-rs
  `affinidi-messaging-mediator/docs/acls.md` §2). The lab mediator's DID
  document advertises it as an `Authentication` service at
  `/mediator/v1/authenticate`;
- live delivery over one WebSocket per DID;
- TSP on that same socket.

### F2. Keyring's Credo mediator can't be that mediator, even on DIDComm v2

The proposal considered was to move Keyring's mailbox to DIDComm v2, as the app
already did, and let the gateway use it.
- The Credo build the app ships, `@credo-ts/didcomm` `0.7.1-pr-2704`, serves the
  standard mediation and pickup protocols (`message-pickup/protocol/` has
  `v1`, `v2` and `v4`).
- It has no login endpoint and no TSP: its build contains no `/authenticate`
  route and no `TSPTransport`.
- So the gateway couldn't log in to it, or collect from it, whatever DIDComm
  version it spoke.

Making Credo serve the gateway would mean rebuilding Affinidi's login, session,
live-delivery and TSP behaviour inside Credo, then keeping that copy in step
with every Affinidi release. An interoperability suite would mostly be testing
the copy.

### F3. The mediator the lab runs is buildable, and is the one already proven

- The lab's mediator is Affinidi's `affinidi-messaging-mediator` v0.33.1:
  commit `55580615`, the `affinidi-messaging-mediator-v0.33.1` tag. The
  gateway's device test (2026-09-29, 5 of 5 wakes delivered to a real iPhone)
  ran through it.
- Upstream publishes images (`ghcr.io/affinidi/messaging-mediator`), but the
  newest tag is `v0.26.5` (read from the registry on 2026-09-29), seven minor
  versions behind.
- Upstream's own `docker/mediator.Dockerfile` builds any commit.

### F4. Cross-mediator delivery is a documented feature, with settings on both ends

With a bundled mediator, the agents that wake the gateway sit on *other*
mediators. Affinidi documents this as federation
(`docs/multi-mediator.md`):
- the agent's mediator relays the message to the gateway's mediator's
  `/inbound`, anonymously;
- the receiving mediator must accept that relay
  (`enable_inter_mediator_relay`, or an ACL default granting `SEND_FORWARDED`);
- the sending mediator must relay outward: `external_forwarding`, and an ACL
  default granting `RECEIVE_FORWARDED` to the next hop.

The gateway's replies to `push/provision` travel the other way, so the agents'
mediators must also accept inbound relays. The lab mediator does both today
(`global_acl_default = "ALLOW_ALL"`), but only for agents on the same mediator
has it been exercised.

## Part 2: Decisions

| # | Decision | Status |
| --- | --- | --- |
| D12 | The package bundles its own DIDComm v2 mediator: Affinidi's `affinidi-messaging-mediator` at v0.33.1 (`55580615`), built from source with upstream's Dockerfile recipe, with Redis, behind the same Caddy on a second hostname. It serves only the gateway. **Supersedes** D2's "the gateway uses the shared DIDComm v2 mediator" for production; the lab mediator remains the test mediator until the bundled one is proven | Decided |
| D13 | Keyring's mailbox, the Credo mediator the app's `MEDIATOR_URL` names, is unchanged. Phones never talk to the bundled mediator, so the VRC, witness and every other app flow are untouched. Two mediators run: the mailbox for phones, the bundled one for the gateway | Decided |
| D14 | Only the gateway can hold a session on the bundled mediator. Its ACLs are the lab's (`ALLOW_ALL`), but Caddy refuses its login endpoint from public addresses. Inside the stack the mediator's hostname resolves to Caddy through a network alias, so the gateway logs in from a private address | Decided; the lab proof confirms it |
| D15 | The mediator's own identity is a self-contained `did:peer:2`, created by upstream's `mediator-setup` with no VTA. The gateway's identity is still issued by a VTA (§5.3) | Decided |
| D16 | Moving Keyring's mailbox to DIDComm v2 (Credo, as the app already is) is worthwhile but separate. It doesn't help push (F2). It carries its own migration risk (F3 of the 2026-09-28 companion) and is not bundled with push | Later |

## Part 3: What must be proven before a server deploy

The package builds and boots in CI. None of the following has run yet:

1. **Cross-mediator wake, in the lab.** The bundled stack runs on the Mac with
   its own tunnel hostname. The push-test agent, whose mediator is the lab's,
   provisions and wakes the gateway through it, and the iPhone shows the
   notification with the app in the background and after a force-quit. This is
   F4's untested path, and the one production depends on.
2. **Only the gateway can log in.** From outside, `/mediator/v1/authenticate`
   is refused. The gateway still logs in through the alias.
3. **No open relay.** A stranger's anonymous relay addressed to a DID that is
   not the gateway is not forwarded onward. If it is, the relay settings are
   tightened before any deploy.
4. **The agents' production mediator relays.** Whichever mediator hosts the
   production agents must relay out, and accept the gateway's replies back
   (F4). That is checked against its configuration once it is known; the hosted
   stack is being rebuilt.

After these, the production test of the handover (a real iPhone and a real
Android phone against the deployed server) is what makes it production-ready.
