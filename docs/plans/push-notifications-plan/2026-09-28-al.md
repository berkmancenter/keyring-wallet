# 2026-09-28 — review of the first draft, and the decisions it led to

Parent: [`../push-notifications-plan.md`](../push-notifications-plan.md)

The first draft (2026-09-26) was written outside the repository, as a planning
document and a draft Compose package (`deploy/keyring-messaging/`, local
commit `8cc19c6`, not pushed). This companion records:
- the review of that draft;
- the decisions taken on 2026-09-28;
- the draft positions they replace.

The plan in this directory is the result.

## Part 1 — Findings

### F1. Silent pushes alone can't carry approvals on iPhone

The draft shipped Phase 1 (silent background push) on both platforms, and
added the visible push later as Phase 2.

- Apple limits background notifications: "don't try to send more than two or
  three per hour". Also: "If something force quits or kills the app, the
  system discards the held notification"
  ([*Pushing background updates to your App*](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)).
- For an approval that a person is waiting on, that is the main path, not an
  edge case.

**Concluded:** iPhone ships Phases 1 and 2 together; Android ships on Phase 1.
**Supersedes:** Phase 1 first on both platforms, Phase 2 after Phase 1 works on
real phones.

### F2. Agents couldn't reach the drafted gateway

The draft package bundled Keyring's Credo mediator, which is DIDComm v1. But
the gateway receives `push/*` over DIDComm v2, through a mediator it connects
out to (vti-push-gateway `33bc8052`, `README.md`, "DIDComm transport
(preferred)"; `src/identity.rs`, whose identity file names a `mediator` DID).
Nothing in the package could be that mediator.

**Concluded:** the gateway uses the shared VTI DIDComm v2 mediator, and its
`push-gateway` identity's `URL` is that mediator's DID. The gateway needs no
public inbound port for DIDComm.

### F3. Bundling the mailbox swap made the rollout riskier

The draft package also replaced the mediator that Keyring's `MEDIATOR_URL`
points at.
- Existing installs don't follow a changed `MEDIATOR_URL`.
- Parity with the running mediator (image source, Askar storage type, settings)
  was unverified. The package README says so under "Unknowns and unverified".

**Concluded:** the package ships the gateway and Caddy only. The mailbox
migration is separate work.

### F4. "Simulators cannot receive these pushes" was wrong

The Xcode 14 release notes say: "Simulator now supports remote notifications
in iOS 16 when running in macOS 13 on Mac computers with Apple silicon or T2
processors". They also say it uses the APNs sandbox, and supports notification
service extensions. Android emulators with Google Play services receive FCM.

**Concluded:** automate register → wake → notify on a simulator and an emulator,
and keep real phones for force-quit, Low Power Mode and the release build.
This hasn't been measured on the project's machines yet.

### F5. The inherited push path should be removed, not revived

On `main` at `fa5c70e`:
- `app/src/utils/PushNotificationsHelper.ts` is present but commented out in
  `useBCAgentSetup.ts` and `container-imp.ts`. It registers the FCM token with
  the mediator (Credo's mediator push module).
- `app/android/app/google-services.json` still names `bc-wallet-mobile`.
- `app/ios/AriesBifold/AriesBifold.entitlements` has no `aps-environment`.

**Concluded:** Phase 1 removes the helper, so there is one push path and the
token never goes to the mediator.

### F6. The gateway's per-IP rate limit is global behind a proxy

The gateway limits HTTP requests per peer IP (default 10 a second, burst 40).
Behind Caddy every device shares Caddy's IP.

**Concluded:** the package raises `GATEWAY_HTTP_PER_SEC` and `_BURST`.

### F7. The gateway has no unregister verb

The API at `33bc8052` is `push/register`, `push/provision` and `push/wake`
(`README.md`, "API"). A revoked phone's handle and token remain in the store.

**Concluded:** recorded as a limit in the plan (§8). On revoke, the agent stops
waking the handle and the app drops its token.

### F8. The draft's two cost figures disagreed, and neither fitted

The draft's planning document said $4–17 a month for separate hosting. Its
colleague-facing copy said $15–35.
- The first assumed only the gateway.
- The second assumed Postgres, the Credo mediator and an on-host Rust build.

After F2 and F3 the server runs only the gateway and Caddy, and the image is
built on CI.

**Concluded:** $0 on an existing server, or $12 a month on a separate 2 GB,
1 vCPU server
([DigitalOcean Basic](https://www.digitalocean.com/pricing/droplets), checked
2026-09-28). A 1 GB server ($6) would probably do, but that's unmeasured.

## Part 2 — Decisions of 2026-09-28

| # | Decision | Taken |
| --- | --- | --- |
| D1 | For now, run the gateway locally. Where it runs after the local test is left to the collaborator who offered hosting, as an open question in the plan (§5.4) | Decided; hosting open |
| D2 | The gateway uses the shared DIDComm v2 mediator. The hosted stack's DID creation was failing (HTTP 502), so testing uses the local lab's mediator | Decided |
| D3 | iPhone ships Phases 1 and 2 together (F1) | Decided |
| D4 | No mailbox swap in the first rollout (F3) | Decided |
| D5 | The project lead creates the credentials (APNs key, Keyring Firebase project, test app ID and its profile) and shares them privately | Decided |

**Isolation rule, adopted with D1–D5.** Push work stays apart from other
workstreams until it passes on a test build, on a real device if needed. That
means:
- a separate app ID (`asml.bkc.harvard.wallet.pushtest`) and Android
  application ID;
- the release app ID, its signing profile and the committed
  `google-services.json` unchanged until then;
- a dedicated test VTA in the lab, so no agent used elsewhere takes part.

**Sequencing.** Execution starts after the current release ships, and after
the local lab has moved to upstream main.
