# 2026-09-28 — review of the first draft, and the decisions it led to

Parent: [`../push-notifications-plan.md`](../push-notifications-plan.md)

The first draft (2026-09-26) was written outside the repository, as a planning
document and a draft Compose package (`deploy/keyring-messaging/`, local
commit `8cc19c6`, not pushed). This companion records:
- the review of that draft;
- the decisions taken on 2026-09-28;
- the draft positions they replace.

The plan in this directory is the result.

## Part 1 — Findings

### F1. Silent pushes alone can't carry approvals on iPhone

The draft shipped Phase 1 (silent background push) on both platforms, and
added the visible push later as Phase 2.

- Apple limits background notifications: "don't try to send more than two or
  three per hour". Also: "If something force quits or kills the app, the
  system discards the held notification"
  ([*Pushing background updates to your App*](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)).
- For an approval that a person is waiting on, that is the main path, not an
  edge case.

**Concluded:** iPhone ships Phases 1 and 2 together; Android ships on Phase 1.
**Supersedes:** Phase 1 first on both platforms, Phase 2 after Phase 1 works on
real phones.

### F2. Agents couldn't reach the drafted gateway

The draft package bundled Keyring's Credo mediator, which is DIDComm v1. But
the gateway receives `push/*` over DIDComm v2, through a mediator it connects
out to (vti-push-gateway `33bc8052`, `README.md`, "DIDComm transport
(preferred)"; `src/identity.rs`, whose identity file names a `mediator` DID).
Nothing in the package could be that mediator.

**Concluded:** the gateway uses the shared VTI DIDComm v2 mediator, and its
`push-gateway` identity's `URL` is that mediator's DID. The gateway needs no
public inbound port for DIDComm.

### F3. Bundling the mailbox swap made the rollout riskier

The draft package also replaced the mediator that Keyring's `MEDIATOR_URL`
points at.
- Existing installs don't follow a changed `MEDIATOR_URL`.
- Parity with the running mediator (image source, Askar storage type, settings)
  was unverified. The package README says so under "Unknowns and unverified".

**Concluded:** the package ships the gateway and Caddy only. The mailbox
migration is separate work.

### F4. "Simulators cannot receive these pushes" was wrong

The Xcode 14 release notes say: "Simulator now supports remote notifications
in iOS 16 when running in macOS 13 on Mac computers with Apple silicon or T2
processors". They also say it uses the APNs sandbox, and supports notification
service extensions. Android emulators with Google Play services receive FCM.

**Concluded:** automate register → wake → notify on a simulator and an emulator,
and keep real phones for force-quit, Low Power Mode and the release build.
This hasn't been measured on the project's machines yet.

### F5. The inherited push path should be removed, not revived

On `main` at `fa5c70e`:
- `app/src/utils/PushNotificationsHelper.ts` is present but commented out in
  `useBCAgentSetup.ts` and `container-imp.ts`. It registers the FCM token with
  the mediator (Credo's mediator push module).
- `app/android/app/google-services.json` still names `bc-wallet-mobile`.
- `app/ios/AriesBifold/AriesBifold.entitlements` has no `aps-environment`.

**Concluded:** Phase 1 removes the helper, so there is one push path and the
token never goes to the mediator.

### F6. The gateway's per-IP rate limit is global behind a proxy

The gateway limits HTTP requests per peer IP (default 10 a second, burst 40).
Behind Caddy every device shares Caddy's IP.

**Concluded:** the package raises `GATEWAY_HTTP_PER_SEC` and `_BURST`.

### F7. The gateway has no unregister verb

The API at `33bc8052` is `push/register`, `push/provision` and `push/wake`
(`README.md`, "API"). A revoked phone's handle and token remain in the store.

**Concluded:** recorded as a limit in the plan (§8). On revoke, the agent stops
waking the handle and the app drops its token.

### F8. The draft's two cost figures disagreed, and neither fitted

The draft's planning document said $4–17 a month for separate hosting. Its
colleague-facing copy said $15–35.
- The first assumed only the gateway.
- The second assumed Postgres, the Credo mediator and an on-host Rust build.

After F2 and F3 the server runs only the gateway and Caddy, and the image is
built on CI.

**Concluded:** $0 on an existing server, or $12 a month on a separate 2 GB,
1 vCPU server
([DigitalOcean Basic](https://www.digitalocean.com/pricing/droplets), checked
2026-09-28). A 1 GB server ($6) would probably do, but that's unmeasured.

**Isolation rule, adopted with D1–D5.** Push work stays apart from other
workstreams until it passes on a test build, on a real device if needed. That
means:
- a separate app ID (`asml.bkc.harvard.wallet.pushtest`) and Android
  application ID;
- the release app ID, its signing profile and the committed
  `google-services.json` unchanged until then;
- a dedicated test VTA in the lab, so no agent used elsewhere takes part.

**Sequencing.** Execution starts after the current release ships, and after
the local lab has moved to upstream main.

## Part 3 — Response to the 2026-09-28 review

[`2026-09-28-bam.md`](./2026-09-28-bam.md) reviewed the plan against the code it
lands in. Its plan edits (F1, F3–F10, and the testing and coverage asks) were
adopted as written. This part records the answers to its two open questions,
and the corrections found while answering them.

### R1. F2, the register path: two existing tasks, HTTPS to the gateway

**Concluded:**
1. The phone sends `push/register/0.2` to the gateway over HTTPS.
2. The gateway makes the handle.
3. The phone conveys the handle to its agent with `device/set-wake/0.2`, not
   inside a `device/register` extension.
4. The agent sends the signed `push/provision`.

The plan's §4.4 records this with citations. Evidence:
- **Upstream documents this exact path** (VTI `2240aa7e`,
  `docs/05-design-notes/mobile-agent-architecture.md:550-561`). `set-wake`
  already exists, so this is the "extend before drafting anything new" route
  upstream asked for (`docs/VTI_UPSTREAM_FINDINGS.md:1809`), with nothing
  drafted.
- **The gateway makes the handle from 32 random bytes** (vti-push-gateway
  `e542a9d7`, `src/api.rs:178-182, 384, 403`), so nothing about the token or the
  person is derivable from it.
- **HTTPS, over DIDComm or TSP.** Registration is the one anonymous task, and
  only HTTPS rate-limits anonymous registration per source (gateway
  `README.md`, "Who can spend the record"). It also needs no v2 or TSP client
  in the wallet for this step.
- **`0.2` over `0.1`.** The VTA marks `device/set-wake/0.1` deprecated, "will
  be removed in a future release", and the `0.2` bump changed no values (VTI
  `vta-sdk/src/trust_tasks.rs:212-219`).
- **The bifold change is small.** `vtaDevices.ts` has no `set-wake` (bifold
  `b8768fd3`, `:30-34`), and step 1.5a adds it. The HTTPS client is
  gateway-specific and lives in `app/`.

### R2. F3, the background handler: option (a)

**Decided on 2026-09-28:** (a). The background handler never opens the agent,
and the notification text is always generic. The review's own plan edit
already wrote this into §2. Option (b), a bounded fetch, was rejected: the
notification text would depend on a fetch that can fail inside the operating
system's background budget, and the review's F1 showed that no lock predicate
is available to a background handler anyway.

### R3. The gateway pin moves from `33bc8052` to `e542a9d7`

The first draft pinned `33bc8052` as "the commit before" gateway PR #32, on the
ground that agents did not yet sign their gateway calls. That no longer holds:
- PR #32 merged on 2026-09-26. Gateway main authorises `push/provision` and
  `push/wake` only by a document proof (`README.md`, "Authentication").
- VTI `2240aa7e` signs exactly that way (`vta-service/src/trust_tasks/step_up.rs`,
  `trigger_gateway_wake`; `trust_tasks/device.rs`, `provision_gateway`).

A `33bc8052` gateway would refuse the lab's agents. **Supersedes:** the
"pin before PR #32" position in the plan's §8.

Gateway main also brings two requirements the draft didn't have:
- **`GATEWAY_ALLOWED_CONTROLLERS`.** Registration names only listed agents,
  matched as exact DIDs (`src/controllers.rs:1-15`). That makes "which agents a
  shared gateway serves" a production decision, recorded as not decided in §5.4.
- **A `TSPTransport` service on the gateway's DID** (`README.md`, "TSP and
  DIDComm transports").

### R4. Unregister is a Keyring requirement, and partly unverified

The gateway has no unregister task, and VTI's `device/disable` and
`device/wipe` don't clear a device's wake channel
(`vta-service/src/operations/device.rs:342-436`); only `set-wake` does
(`:471`). So the plan makes removal Keyring's job:
- a phone being removed clears its own channel before it unlinks;
- removing another device gets a test (§6.1), and becomes an upstream finding
  if the agent still wakes it.

### R5. `binding/push/0.1` is implemented by running the gateway

The gateway's README introduces it as the implementation of
[`binding/push/0.1`](https://trusttasks.org/binding/push/0.1) (line 4). That
closes the review's F10 question in the plan's "Relation to other work".

## Part 4 — How push ships, decided later on 2026-09-28

### D6. Push ships in the next release, built in and off

**Decided:** push goes into release 227, and is off for testers. Under the
local-testing rule (D1) no build carries a push gateway except the push-test
variant, so a tester's build supplies no push configuration: no prompt, no
switch, no registration.

### D7. Reuse bifold's push framework instead of removing it

**Decided:** reuse. Mapping bifold's push code for step 1.2's removal showed it
is not BC plumbing but a generic framework the app configures:
- `enablePushNotifications?: { status, setup, toggle }` (`types/config.ts`);
- an onboarding permission screen (`screens/PushNotifications.tsx`);
- a Settings switch (`screens/TogglePushNotifications.tsx`).

Both screens stay hidden without the configuration. So Keyring supplies it,
only when a build names a gateway, and bifold's change shrinks to re-enabling
the Settings entry.

**Supersedes:** step 1.2's bifold half and its acceptance line ("a repo-wide
search for … `usePushNotifications` finds no live code"), which came from the
2026-09-28 review's F6. The app half of 1.2 stands: the BC helper fed the
mediator's FCM module, the path §1 rules out.

### D8. No local-notification library in the first build

**Decided:** the first build carries registration, the Settings switch and
logging wake handlers, but not the display. Showing the generic notification
needs a local-notification library, a new native dependency, which was not
added to a build already in its final release checks. A push-test build
therefore registers and receives wakes, which get logged, and shows no
notification until the library follows.

### D9. The push-test variant is switched at build time

**Concluded:** a build script and a Gradle property, not an Xcode configuration
and scheme or a Gradle flavor. The review's F5 suggested those, but a new
configuration needs new Pods configurations, and a flavor renames the Gradle
tasks the release pipeline runs. The acceptance test is F5's own: the variant
installs beside the release app, and a build without the switches is
unchanged. The iOS script edits the tracked project file for one build, so it
restores it on every exit and signal. That was tested with a stub `xcodebuild`
(INT, TERM, a failed build), each leaving the file clean.

Two consequences:
- The pushtest App ID and profile grant push only, so the iOS variant has no App
  Attest and no universal links.
- The same `-PkeyringPushTest` switch must not reach a release pipeline.
