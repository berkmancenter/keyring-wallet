## What was decided

Alberto decided on 2026-09-25:

- **Against the openvtc TUI itself**, the program maintainers run, not a
  stand-in built on its library.

    versions.

## A third defect that agreed with itself

On 2026-09-25 a maintainer ran the openvtc TUI as vetter against Keyring 223 as
applicant. The card was verified, which confirms keyring-bifold#108. The TUI
said the statement was signed and sent, but Keyring stayed on "the vetter is
checking". The phone's log shows the `credential-exchange/issue/0.1` message
unpacked, and then nothing.

The cause was ours:

- A statement names the card it attests by `cardDigestMultibase`, which is
  DTG Credentials' `digestMultibase`: JCS of the card without its top-level
  `proof` (dtg-credentials 0.9.1 `digest_multibase_json`, lib.rs:534, called
  from vta-sdk `vetting/card.rs:322`, at VTI `a96fe02f`).
- Keyring hashed the card with its proof, as applicant and as vetter.
- Keyring↔Keyring therefore agreed. Keyring's applicant refused every openvtc
  statement at the digest check without a word, and Keyring's statements fail
  vta-sdk `check_against_card`. Measured with `card-verify verify-statement`:
  `Binding("cardDigestMultibase")`.
- Fixed in keyring-bifold#116.

It is the same shape as #108 and #148. A value is computed from our reading of
the spec, and the only proof is Keyring agreeing with Keyring. After #108 the
card was checked against `verify_card`, but not the digest a statement carries,
and not the round trip.

## Why conformance vectors come first, in every PR

All three defects were a single value, hashed or read in a way both Keyring
sides shared. Each is decidable without a device, a Farm, or another person:
run upstream's function on Keyring's output, and Keyring's function on
upstream's output. So the cheapest layer catches the whole class, and it runs
on every PR rather than at the gate.

The upstream side is a small cargo binary on the pinned vta-sdk and
dtg-credentials (`scripts/openvtc/card-verify`, keyring-wallet#146 and #162).
The rule each vector follows is Alberto's standing rule for VTI work: read
openvtc and the VTA plugin at the pinned clones first, and cite file:line.

## Why the TUI, when the 2026-09-24 plan ruled it out

The 2026-09-24 position was that a pseudo-terminal breaks on redraws, and that
a screen-scrape is weak evidence. Both still hold, and the design answers them
rather than avoiding the TUI:

- **A bot does not remove the risk; it moves it.** Much of the maintainer's
  path lives in the TUI crate, not in openvtc-core. Examples: the attest
  action composes `statement_draft`, `record_statement` and
  `credential_delivery` in `openvtc/src/state_handler/vetting_actions.rs`, and
  the ticket form and paste handling live there too. A bot would re-implement
  those, and its reading could agree with ours while the TUI does something
  else: the defect this plan exists to catch.
- **The screen is not the only evidence.** Assertions read openvtc's log and
  persisted state as well, and the community's records. openvtc refuses some
  things silently (VTI-Q24), so its screen alone proves nothing.
- **Screen assertions use the TUI's own strings**, cited by file:line. A
  string that changes upstream fails the run loudly at a pin advance, rather
  than passing on stale text.
- **Fallbacks are named.** A step that cannot be driven through the TUI uses
  openvtc-core, and the run report lists each one.
- **Two versions**, because maintainers run upstream `main` and we pin a
  commit. A difference between the two is itself a finding.

## What this leaves open

- **A second Farm agent** with a DID host for the TUI as applicant (Phase 2):
  `keyring-runner-openvtc`, §9 decision 1.
- The invitation-only community, where the drift run lives, and whether the
  TUI driver goes upstream: §9 decisions 2–4.
- **Not decided here:** Keyring's own VRC and VWC digests
  (`vrcDigestMultibase`, `vwcDigestMultibase`) also include the proof. They are
  read only by Keyring and our witness-server, never by VTI. Whether to align
  them with DTG now, or when a second implementation reads them, is a separate
  question for Alberto.

## Afternoon: both directions run, what they found, and the pin

**Results on the lab at the Farm's versions** (VTA 0.42.0, VTC 0.11.58,
mediator 0.29.4; openvtc `ed13d29`). Reports are kept under
`~/vti-stack/openvtc-harness-lab*/runs/` for the release PR.

- **Phase 1** (the TUI vets a Keyring applicant): a build without
  keyring-bifold#116 is red at "statement accepted", as expected, which is
  the maintainers' report reproduced. With #116 it is green on Android (twice, before
  and after the lab upgrade) and on the iOS simulator.
- **Phase 2** (a Keyring vetter, the TUI applies) found Keyring's defects,
  which is what it was for:
  1. openvtc refused Keyring's acceptance: the eligibility presentation used
     Keyring's own desk id as its `nonce` and signed for `assertionMethod`,
     where the spec and vta-sdk require the request document's id and
     `authentication`. Fixed by keyring-bifold#125.
  2. openvtc ignored Keyring's statement: Keyring wrapped
     `credential-exchange/issue` in a signed Trust Task document, while the
     VTC and openvtc send the bare `{ credential_response: { credential } }`
     body. Fixed by keyring-bifold#130.

  With both, Phase 2 is green on Android: the TUI applicant became a member
  in the community's own list.
- **An upstream defect** surfaced as openvtc's advisory eligibility line:
  vta-sdk cannot verify a credential signed with a proof set, and a
  hybrid-keyed VTC signs every grant with two proofs (VTI-44). We left the
  grant intact rather than strip its post-quantum proof.

**Why these defects had lived.** It was the third time Keyring's producer and
Keyring's own consumer agreed with each other and not with upstream. Only the
card, the statement and four vectors were judged by upstream code in CI. The
answer is keyring-wallet `docs/VTI_CONFORMANCE_INVENTORY.md`: every document
Keyring produces or accepts, its upstream judge, and the PR that puts that
judge in CI (keyring-bifold #125, #128, #130; keyring-wallet #173, #176). A
new document type isn't done until it has a row there with an upstream check.

**The pin is `ed13d29`, and `177a218` is not a gate.** This plan had pinned
`177a218` and asked for runs "at both openvtc versions". `177a218` cannot
create a persona against VTA 0.42.0. Its vta-sdk 0.42.1 does not read the
agent's answer to `vta/contexts/get` for a not-yet-existing sub-context (a
422) as NotFound, so persona creation aborts (openvtc-core
`config/community_context.rs` ~:296-303). Measured twice on the lab,
12:19Z and 12:21Z. Without a persona, `177a218` can be neither applicant
nor vetter, so it cannot run either phase against the stack the Farm runs. A
build that can't run against the current stack says nothing about Keyring.
The gate is the pinned build (keyring-wallet#177 pins `ed13d29`), and the
nightly drift run against upstream `main` catches the next change.

**Harness lessons, recorded where they apply:**
- A TUI whose persona listener fails to come up keeps running deaf, so the
  runner relaunches it until the listener is up (VTI-Q29).
- A join's credentials are applied only when the join page is left, so the
  join step asserts the stored membership.
- A lab failure at a network step gets one rerun before it counts, and
  device runs never overlap a heavy build or an emulator boot. One Phase 2
  run was void from an ANR under a load average of 44.
- Each openvtc build gets profiles it created itself: a build reading
  another build's Keychain item waits on a macOS prompt.
