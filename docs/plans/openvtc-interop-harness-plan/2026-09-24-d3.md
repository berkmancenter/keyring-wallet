# 2026-09-24 — why the interop harness, and what was ruled out (d3)

Parent: [openvtc-interop-harness-plan.md](../openvtc-interop-harness-plan.md).

## What happened

On 2026-09-24 two Keyring defects reached testers although every Keyring
gate was green.

1. **The card commitment.** A Keyring 219 applicant sent its Vetting Card to
   an openvtc vetter five times, and the vetter's desk stayed on "waiting for
   their card". Keyring hashed `provenance` into the identity commitment and
   sorted with `localeCompare`. The spec and the VTI SDK hash `{ type, value }`
   in code point order (`vta-sdk/src/vetting/card.rs`, VTI `a96fe02f`).
   Keyring's own vetters copy the commitment from the card and never
   recompute it, so Keyring-to-Keyring runs always passed. openvtc logs the
   refusal as a warning and answers nothing (VTI-Q24), so the failure was
   silent on both screens. Fixed in keyring-bifold#108.
2. **"You're a member."** The "I was invited" screen showed membership for any
   answer that was not an error. `keyring-test-vtc` publishes a vetting
   criterion, and on VTI that makes vetting mandatory for everyone (VTI-Q25).
   So every invitation join since the runners stopped changing the criteria
   (#127) was deferred, while `run-vti-invite.js` passed on the screen, the
   219 gate's run included. Found by reading `join-list deferred` through the
   admin API. The harness half is fixed in keyring-wallet#148.

In both cases the screen or our own implementation vouched for itself. What
found them was the other implementation (an openvtc vetter) and the
community's records.

## What was concluded

- **Interop with upstream's reference implementations becomes a standing
  release-candidate gate**, on Alberto's request relayed by keyring-wallet-45.
  It is not a one-off test.
- **Assertions read truth from the other party and the community.** The
  screen is compared against them, never trusted alone. The pattern already
  exists in `e2e/lib/joinOutcome.js`.
- **openvtc is pinned** like VTI, so a red run can be attributed.
- **card-verify (Phase 0)** stays as the cheap first layer, because it would
  have caught defect 1 in seconds. Measured: a card from the old code is
  refused with *"identity commitment does not recompute from the card"*; the
  fixed card is accepted.

## Options considered and ruled out

- **Driving the openvtc TUI** (a pseudo-terminal and keystrokes). Ruled out:
  ratatui redraws make it brittle, and the result would be a screen-scrape,
  which is the same kind of evidence that let defect 2 through.
  openvtc-core's own `tests/vetting_e2e.rs` shows the whole ceremony runs
  without the TUI, so a bot on openvtc-core is the TUI's engine without its
  face.
- **A CLI bot, one process per step.** Ruled out: the vetting book keeps
  session state in memory between steps (the challenge, the match code, the
  session id). Restarting the process per step either loses that state or
  re-reads it from disk in a way the TUI never does, which tests something
  other than openvtc.
- **Capturing a card from a Release e2e run** for card-verify. Ruled out:
  the card exists only in the app's encrypted store and travels end-to-end
  encrypted. Capturing it would need an export path in the shipped app. The
  producer test runs the shipping `sendCard` with only the key store and
  resolver stubbed.
- **Running it on every PR.** Ruled out for cost and contention: Farm
  resources, the compile slot and community criteria are shared by all
  sessions on one Mac. It runs at the release-candidate gate and nightly.
- **Seeding vetters by admin approval.** Not possible on VTI: `decide`
  refuses a deferred request (`409 notPending`), and an invitation join on a
  vetting community is always deferred. Hence the invitation-only test
  community in the plan's §6.

## Measurements behind the plan (2026-09-24)

- openvtc `177a218` builds against vta-sdk 0.42.1 and trust-tasks-rs 0.21.3
  (its `Cargo.toml` and `Cargo.lock`). Our VTI pin is `a96fe02f`, which is
  vta-sdk 0.46.0.
- pnm's config directory is `dirs::config_dir()/pnm`, and `PNM_HOME` is never
  read (VTI `pnm-cli/src/config.rs`, `a96fe02f`). On macOS that is
  `~/Library/Application Support/pnm`. A second session's `pnm` call dropped
  keyring-wallet-92's gate session at about 20:21Z ("replaced by a newer
  connection").
- card-verify's build reused the VTI clone's warm `target/` and took about
  2 minutes. `external/openvtc/target` is 3.8 GB at `177a218`.

## Later the same session: the invitation-only community

keyring-wallet-45's review of the first draft pointed to an existing
resource. Farm Full Stack #22, `keyring-vetting` (VTC `keyring-vetting-vtc`),
is unused, and its admin is not yet claimed. Claiming it by passkey and
setting its criteria to invitation only is cheaper than creating a community.
The plan's §6 and decision 2 now recommend it. The first draft left the
choice open between a second Full Stack and a second community on an existing
stack. Both remain as alternatives, but neither reuses what already exists.
