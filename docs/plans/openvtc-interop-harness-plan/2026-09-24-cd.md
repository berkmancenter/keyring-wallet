# 2026-09-24 — pnm calls: serialize per slug, don't isolate by HOME

Author: the Prague/VTI session (cd), 2026-09-24. Revises §6 *Machine rules* of
[the plan](../openvtc-interop-harness-plan.md). The measurement it corrects is
in [2026-09-24-d3.md](./2026-09-24-d3.md), *Measurements behind the plan*.

## What §6 said, and why it was wrong

§6 planned to give each runner its own `HOME` for pnm calls, and to ask
upstream to honour `PNM_HOME` or a `--config-dir`, so that sessions stopped
sharing "one admin identity per runner". That treats the shared config
directory as the cause. It isn't:

- **The identity is not in the config directory.** pnm stores a runner's
  admin session in the OS credential store: the macOS login keychain, service
  `pnm-cli`, account `vta:<slug>` (VTI `a96fe02f`:
  `vta-sdk/src/session/backends/keyring.rs`, `pnm-cli/src/config.rs`
  `vta_keyring_key`). `config.toml` holds only the profile list. On this Mac,
  `farm-runner-prague`, `-uiux` and `-nohost` each have their own keychain
  entry.
- **A different `HOME` moves the profile list, not the key.** Measured: with
  `HOME` pointed at an empty directory, `pnm vta list` lists nothing. The
  keychain entry stays where it is, keyed by the slug. So a per-runner `HOME`
  either breaks pnm (it can't find the profile) or, with the profile copied
  in, reaches the same key: the same DID.
- **Separate runners were never sharing an identity.** Each slug is its own
  DID already. At 20:21Z, 92's retry commit `088d1ec` records "another
  client connected with the same pnm identity": a second call on the gate's
  own slug.
- **The mediator drops one of two sockets per DID, on purpose.** VTI
  `vta-sdk/src/acl_setup.rs`: "one socket per DID; a second is evicted as
  `duplicate-channel`". affinidi-messaging-mediator 0.26.0 closes the
  incumbent (*replaced by a newer connection*) or, with its duel damper,
  refuses the newcomer (*this DID already has a live connection*), and says
  that only the client can know why a second session exists.
- **`PNM_HOME` was never a pnm variable.** No commit in VTI's history
  mentions it. Our scripts have passed it since the local stack was built,
  and it has isolated nothing.

## What replaces it

Only one pnm call per slug may run at a time, across every session on the Mac.
`scripts/openvtc/pnm-locked` (keyring-wallet#154) takes a per-slug `flock`
and execs pnm, which holds the lock until it exits. The harness helpers and
`farm-health.sh` use it. Calls on different slugs never wait for each other,
so the bot's runner and a gate's runner stay independent.

Options set aside:

- **A second admin DID per consumer** (the gate, the health check, the bot,
  each on its own ACL entry of the same runner). This gives real isolation,
  but it means more ACL entries to create and remove on the Farm, and a slug
  per consumer. Worth revisiting only if waiting on the lock becomes a real
  cost; today pnm calls take seconds.
- **`--transport rest`** for read-only calls. A REST call authenticates with
  a token instead of holding a mediator socket, so it may avoid the eviction.
  It is not measured against the Farm runners, and pnm treats it as a
  recovery path, so we don't depend on it.
- **An upstream ask.** Not filed: the one-socket rule is deliberate and
  documented, and pnm's error already names it.
