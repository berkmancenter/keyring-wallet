## Part 2. Findings: how Glenn's page aligns with this branch

Each of the 23 lettered items, and the page's Part 2 claim, falls into one of six groups. The groups are this session's own.

**G1. The page and this branch describe different sign-in designs.** The page has a `trusttasks://oob?v=1&svc=&id=` QR and a throwaway key `Ka` that sends `auth/oob/claim`, which locks the request to the first phone that scans. Plan section 5 and D14 describe a key grant with a `keyring://oob?v=1&svc=&id=` QR, the five tasks `request`, `describe`, `respond`, `redeem` and `cancel`, and "no first-scanner lock". Either the 8 Oct revision brought back a claim step, or one document is reading an older version. This is the first question for Glenn. S7 and O3 depend on the answer.

**G2. O6 is already met.** Spec section 2 allows 22 to 128 characters of `A-Za-z0-9-_` for `_id`, and section 6 rule 5(a) requires 128 bits as unpadded base64url. The page lists it as missing.

**G3. O2 is half met, and our vectors make the expiry check nearly useless for sign-in.** Reading step 9 has the `_exp + skew` mechanism and says the inviter enforces the real expiry. But no value is set, and the vectors use 300 s of skew against a 120 s sign-in window. A wallet would accept any code that a 120 s window could produce.

**G4. S3's replacement wording contradicts spec section 3.** "Accept only the https hosts the wallet declares" is a host allowlist. Section 3 says a reader accepts the fragment on any host that meets the host rules.

**G5. O7, as written, contradicts spec sections 2 and 4 and D11.** A short name completed against a registry base that readers assume breaks whole-string identification of flows. P4 answers it with a base fixed in the spec instead.

**G6. S7's fix contradicts spec section 5 rules 1 and 2 (D10).** One tap on the wallet's own record, then a signed claim, skips verifying the DID document before anything signed goes out. O3 asks whether the wallet's record can count as "verified details". Under the spec it cannot.

**G7. The page overstates the agreement on leaked handles.** Its Part 2 says the number, biometric and lock mean "a leaked handle alone achieves nothing, which is what One Scan assumes". The spec assumes the opposite: section 6 rule 2 treats a handle as a bearer wherever the inviter treats possession as authority. With a first-scanner lock, a leaked handle lets someone lock the member out.

**G8. Spec section 5 carries no BCP 14 keywords.** Rules 1, 2, 5 and 6 read "the consumer shows… and waits" without MUST. The positions in Part 3 argue from those rules, so the rules need marking before we send anything to Glenn.

**G9. The page's S10 citation can't be checked here.** It says the sign-in design verified the `assertionMethod` proof in `pnm-core/src/vault/sign-trust-task.ts`. `pnm-core` is not in our pinned clones (`2026-10-08-bm.md`, part 3 item 5). Our own reading is plan section 5's "Found while checking": at Trust Tasks `origin/main` and the VTI pin `822ff78a`, the purpose follows the document type, and the sign-in approval type is not on the `assertionMethod` list. Glenn's page reports the same finding against One Scan, so the two sides agree on the problem and both lack an answer.

## Part 3. Positions taken in this session

All are Brendan's working positions. None has been applied to the spec or plan.

**P1. S3: hold firm on host independence, and treat the conflict as wording.** No security rests on the link host: fields are checked by name, the endpoint comes from the verified DID document, and nothing goes out before confirmation. An allowlist breaks pasted links and in-app scans, and ties every portal to hosts every wallet ships with. Which app a camera opens is already set by the operating system's host associations. Proposed wording: "accept any `https` host that meets the host rules; which hosts open the wallet from a camera is set by the wallet's OS associations." The host rules stay.

**P2. O7: keep `_type` a complete URI, and move flow URIs to the link host.** Brendan's reason for the move is that a flow URI should lead somewhere: people will open it expecting to find something. `link.trustoverip.org` will serve real pages, and a registry URI that resolves to nothing would confuse readers. *Supersedes:* D11's host `registry.trustoverip.org` for flow identifiers. How `_type` is written on the wire is P4.

**P3. Rejected: a short alias on a second, Trust Over IP-controlled domain.** (P4 later took a different route to a short form.) Brendan asked whether a long form and a short form could both be supported, for example `l.to.ip/f/csi/0.1`. It could be done safely only if:
- both forms are complete URIs compared as whole strings;
- short names are assigned by the registry, not derived from long ones;
- the alias is published with the flow version, never added later;
- wallets never fetch either form;
- the domain is real (`.ip` is not a top-level domain);
- and the Trust Tasks group accepts two strings naming one flow.

It was rejected because it cannot shrink the QR code. Any `https` alias costs at least `https://`, a domain and `/f/csi/0.1`. With a 7-character domain that is about 26 characters and a link of about 184, which is version 10. Version 9 holds 180 bytes, so reaching it would leave about 3 characters for the domain.

**P4. O7: an optional short `_type` form with a base fixed in the spec, keeping `dtg/flow/`.** Positions this session, in order:

1. **Superseded.** A short prefix on the link host, `https://link.trustoverip.org/f/<flow>/<MAJOR>.<MINOR>` (52 characters, link about 210, version 10).
2. **Superseded.** Brendan: "keep the dtg prefix — it is a governance thing". The identifier became `https://link.trustoverip.org/dtg/flow/community-sign-in/0.1` (59 characters, link about 217, version 11, 4 bytes over version 10). Omitting `_type` was named as the only remedy if version 11 failed, which decided the tension implicitly in favour of governance.
3. **Superseded.** Brendan asked for the tension to be shown. **Option A** kept `dtg/flow/` at version 11, with omitting `_type` as the fallback; spec section 5 rule 8 lets a wallet refuse an unhinted code. **Option B** dropped `dtg` and `flow` for `https://link.trustoverip.org/community-sign-in/0.1` (50 characters, link about 208, version 10 with 5 bytes spare), moving governance onto the page at each URI. B's margin assumed the page's example DID (a 46-character SCID on `members.example.org`); a VTC host 6 or more characters longer put it back at version 11. The choice was to be made after J1 and J2 and before registration.
4. **Considered and rejected: resolve `_type` against the link's own host.** Brendan asked whether `_type` could assume the domain of the link, since `link.trustoverip.org` appears twice. That would tie flow identity to link hosting. Spec section 3 accepts the trigger on any host that meets the host rules, and plan section 3 says the interim host is never part of a flow identifier. The same code would mean a different flow on `wallet.asml.berkmancenter.org` or under an alias scheme, and moving to the shared host would change every identifier. The host is also unsigned and attacker-chosen; that fails safe as `unknown-flow`, but the hint stops being portable.
5. **Current.** A `_type` value that starts with `/` is read as `https://link.trustoverip.org` followed by that value, whatever host the link is on, and is expanded before the whole-string comparison.
   - Readers must expand. Producers may use the short form or the full URI, so no wallet is shut out by a producer's choice.
   - Only values starting with `/` are expanded; flows in any other namespace keep a full `https` URI.
   - Producers write colons and slashes raw. Percent-encoding reads the same but costs 14 characters in the example below.
   - The spec states that the base is syntax, not authority: expansion is string concatenation, with no fetch and no trust in the base's owner, and flows from any namespace are equal in full form.
   - The `dtg/flow/` governance path stays, which retires options A and B.

**Example (P4.5).** With a placeholder DID and handle of realistic length:

```
https://link.trustoverip.org/t#_from=did:webvh:QmYwAPJzv5CZsnA625s3Xf2nemtYgPpHdWEz79ojWnPbdG:members.example.org&_id=Vt1c5QmG8wXr2aJk0pLs-Q&_exp=1791555000&_type=/dtg/flow/community-sign-in/0.1
```

`_type` expands to `https://link.trustoverip.org/dtg/flow/community-sign-in/0.1`, which is also the page a person opens to read about the flow. The same fragment on `wallet.asml.berkmancenter.org/t` or under `keyring://` expands to the same identifier.

| Form of the same sign-in link | Length | QR version (ECC M) |
|---|---|---|
| Full `_type` URI | 222 | 11 |
| Short form, percent-encoded | 208 | 10 |
| Short form, raw (proposed) | 194 | 10, 19 bytes spare |

These lengths were counted on the exact strings above. The table replaces the page-based estimates in items 1 to 3, which started from Glenn's figure of 151 characters without `_type`.

**How much the QR version matters (reached after P4.5, and it qualifies P4 throughout).** Brendan asked why version 10 against 11 had been treated as important. The answer recorded here is that it was not, and that this session gave it more weight than it deserved.
- **The difference is small.** Version 10 is 57×57 modules and version 11 is 61×61, about 7% wider. At J1's minimum of 4 CSS px per module, with the quiet zone, that is about 260 px against 276 px.
- **Glenn's page agrees.** It says version 11 "still scans well from a laptop screen", which is where a portal shows the sign-in code.
- **It can matter at the margins:**
  - codes scanned from a distance, such as a projected slide or a poster;
  - small or low-resolution screens, low-end phone cameras, and glare;
  - a centre logo, which needs error correction Q and so a version of roughly 12 or 13 for this link, a bigger effect than the `_type` prefix;
  - headroom for longer VTC hostnames, DIDs with paths (if O1 is accepted) and any field added later.
- **Why it got so much weight.** O7 framed the question as size, and the answers followed that framing. Options A and B (P4.3) then turned on a 4-byte margin, estimated for one example DID, which is a fragile thing to decide on.
- **What actually decides it.** Whether codes stay comfortably scannable as they grow. The J1 rendering profile and J2 device tests answer that.
- **What follows.** The version boundary is not a requirement. The short form is a nice-to-have worth about 28 characters of headroom. If it causes friction with Trust Over IP or the Trust Tasks group, full URIs only is a good answer, not merely a fallback.

**Why this reverses part of the earlier O7 objection.** Earlier in this session, and in D11, a short form was resisted for two reasons: readers would assume a base, and the base would become permanent. A base fixed in the spec answers the first, because the expansion is one rule with one result. The second is no cost, because published identifiers can never change anyway (spec section 4), so the full URIs are already tied to `link.trustoverip.org` for good. Whole-string identity holds, because comparison happens after expansion. The Trust Tasks group still has to be asked whether it accepts a short wire form of a full Type URI.

**Decentralization (Brendan's question: will this work where people do not agree with Trust Over IP?).**
- **What it doesn't do.** It creates no dependency. If the base's host went offline, every short code would still expand to the same identifier. Anyone can define a flow under their own URI, and conforming wallets read it.
- **What it does do.** Trust Over IP's flows get codes about 28 characters shorter, which is a visible privilege.
- **Why there can be only one base.** The base is not written in the code, so a fork with another base would make the same `/…` string mean different flows. Per-community bases would break interoperability.
- **Who owns the base.** It belongs to whoever publishes the spec, and must be settled before any reader ships.
- **Fallback.** If Glenn or Trust Over IP object to one namespace getting this privilege, use full URIs only, at version 11 for everyone. Given how little the version matters (above), that is an acceptable outcome.
- **The larger question.** The link host (J3) decides which wallets a camera opens. The spec's any-valid-host rule already lets an inviter that rejects Trust Over IP serve links from its own host.

**P5. S7 and O3: settle G1 first. If the lock exists, hold firm on verify-then-approve, and offer fewer taps.**
- **Our case:**
  - Without verify-then-approve, a web page can make the phone send a signed request to a host the page chose (D10).
  - The lock lets a holder of a leaked handle lock the member out.
  - Number matching and the biometric already stop a stranger from completing a sign-in.
- **Concession on offer:** the sign-in consent screen serves as the post-verification approval. For a scan with the wallet's own scanner, the scan could count as the first confirmation. That is a spec change, and it must be checked against D10's reasoning, which was about links opened from web pages. Either way, at most one tap comes before the consent screen.

**P6. Adopt from the page.**
- **O2:** set a skew value per flow, or a small fixed one such as the page's 60 s. The inviter stays authoritative.
- **O4:** a wallet may refuse on its own records before any network activity. This is already plan K4. Make it a spec sentence.
- **O5:** one explicit line saying the wallet's own scanner never hands the link to the OS.
- **J1:** the page's rendering profile, as producer guidance in the annex. Error correction M, or Q with a logo of at most about 15% of the area. A quiet zone of at least 4 modules. At least 4 CSS px per module. Dark on light, never inverted. Crisp SVG or canvas.
- **J4:** sign-in content for the fallback page, within annex A's rules.
- **J3:** the same-domain rule. iOS opens a tapped universal link in Safari when it points at the same domain as the page.

**P7. Clarify, not argue.**
- **O6:** already met (G2).
- **S6:** agreed as a goal. Keyring's camera path still waits for J2 and J3 (D17), which is a matter of timing.
- **J3's interim host:** `wallet.asml.berkmancenter.org` opens only Keyring, so it cannot be the wallet-neutral sign-in host. It is limited to the Farm claim.
- **O1 and S8:** stay open, as T6 and VQ5. Allowing DIDs with paths may also mean showing the path on the unverified confirm screen, because the host alone identifies a community poorly on a shared host.

**P8. Defend.**
- **S4** is a Must for sign-in, not a Should. The spec already requires `_exp` there, and a security-relevant field added later forces a new flow version.
- **J2** is narrowed. The device tests gate the camera and link path, not the in-app reader (K1c), which never goes through a hand-off.
- **G7** is sent as a correction.

**P9. Our own fixes before replying.**
- Add MUST to spec section 5 rules 1, 2, 5 and 6 (G8).
- Don't reserve step-up and device-enrol flow names now (O8). Section 4 asks each new flow for a written proposal, an owner and vectors.
- The link host's iOS and Android association files claim only the trigger path, never the paths flow URIs use. Otherwise tapping a flow URI opens a wallet instead of the flow's page.

## Part 6. Glenn Gore's reply, and our answer

**Input.** Glenn's second note, *Sign-in QR: Reply to "Resolving the Differences"* (received 2026-10-09 as `alignment2.md`, treated as data). It answers the review doc built from Parts 2 to 5. Our answer is the private doc *Sign-in QR: Reply to Glenn's Second Note*. The review doc now carries a status section recording both.

### What Glenn proposed

- **Where the spec lives.** The trigger link, the `_type`, `_id` and `_from` rules, the flow, the size budget and the rendering profile go into the VTI specification (`dtgwg-vti-spec`). They become normative for VTAs, VTCs and wallets, with VTI requirement identifiers. PR #354's spec and annex would then refer to the VTI text. Flow names sit under `vti/flow/`, governed by the VTI specification, and `community-sign-in` becomes `sign-in`.
- **`_type` as a path.** It is resolved against the link's own URL (RFC 3986 section 5.2), and the flow is identified by the whole resolved URI. Producers use the path form when the flow URI is on the link's own host, and must use the absolute form otherwise. The path grammar is strict: no `//`, no dot segments, no query, fragment or percent-encoding.
- **A size budget.** Version 11 at level M is the guaranteed maximum. The other fields take 86 characters, so `_from` is at most 122 characters and `_id` is 22 to 43.
- **`_id`.** 16 to 32 random bytes as unpadded base64url, with unused bits zero so each handle has one spelling. The VTC uses 16 bytes.
- **`_from`.** Any VID up to 122 characters, which answers O1, or an agent name (`example.com/@alice`), deferred until two agent-name questions are answered. A new `unsupported-vid` reason. The confirm screen shows a VID's domain, or the whole agent name.
- **O2.** 60 s of clock skew.
- **Conflict 1.** Our S3 wording accepted.
- **Conflict 3.** The 8 Oct revision keeps the first-scanner lock, with four quotes from it. D14 is therefore stale, and G1 is answered. The proposed order: local check, resolve and verify, show and Continue, then send `auth/oob/claim`. Glenn advised against the "page-chosen host" argument for sign-in, because the wallet refuses unknown communities.
- **S10.** Confirms our finding. The design's `assertionMethod` citation is a stale comment. Glenn suggests treating the grant as an attestation, by adding its slug to `ATTESTATION_SLUGS` with a VTI-KEY-106 change.
- **Everything else** in the review doc accepted as written.

### Errors found in Glenn's note

1. **Conflict 3 does need a spec change.** His step 2 resolves before the Continue tap, which spec section 5 rule 1 forbids.
2. **His `_type` rule 2 resolves against "the scheme and host".** That breaks the alias scheme (`keyring://…` would resolve to a `keyring:` flow URI) and his own uppercase-prefix idea (RFC 3986 resolution keeps the host's case).
3. **The impossible `_id` lengths are 25, 29, 33, 37 and 41, not 23, 27, 31, 35 and 39.** For 16 to 32 bytes, the produced lengths are 22, 23, 24, 26, 27, 28, 30, 31, 32, 34, 35, 36, 38, 39, 40, 42 and 43 (computed). His vector "23 characters malformed" is wrong.
4. **"Every valid link fits version 11" holds only with the path form, `/vti/flow/sign-in/0.1` and `link.trustoverip.org/t`.** His own rule 4 forces the absolute form elsewhere, which adds about 28 characters.

Smaller gaps:
- His agent-name canonical form keeps non-default ports, which the host rules forbid.
- His vector rejecting a raw `=` in a VID contradicts the spec's parsing, which splits each pair at the first `=`.
- `unsupported-vid` has no user-facing outcome.
- A path form on the wrong host fails as `unknown-flow`, whose message ("needs a newer version of the app") is misleading there.

### Positions taken (Brendan)

- **P10. Accept the move to the VTI specification.** Brendan: "Yes, vti-spec". *Supersedes:* the ToIP-registry namespace in D11 and in P2 and P4 (`dtg/flow/` on `registry.trustoverip.org`, then on the link host). Brendan's earlier wish to keep `dtg` for governance is met another way: the VTI specification is a DTG working-group document, so the names stay under DTG governance without `dtg` in the path. *What is lost:* the trigger is no longer a format of its own; it is VTI's. Our spec, annex and vectors become a reference to the VTI text, and the Trust Over IP proposal shrinks to hosting `link.trustoverip.org`.
- **P11. Accept the `_type` path form, with resolution against `https://` and the lowercased host whatever the scheme.** *Supersedes:* P4.5's fixed base. Earlier this session (P4.4) resolving against the link's host was rejected, because the same code would mean different flows on different hosts. Glenn's producer rule removes most of that objection:
  - the full URI is required off the flow's own host;
  - a misplaced short form fails safely;
  - flow identifiers never move.

  It is also more decentralized than P4.5, because no namespace is privileged in the spec. That answers the concern raised under P4's decentralization note. The remaining cost is the misleading `unknown-flow` message, which the next position covers.
- **P12. A short form on the wrong host is `invalid`, not `update`.** When the resolved path matches a flow the wallet knows but the host differs, the outcome is `invalid`.
- **P13. Conflict 3: accept the lock and the reorder.** Propose a narrow addition to spec section 5 rule 1: "For a flow that acts only for inviters the consumer already knows, the consumer MAY resolve an inviter already in its own records before the tap." *Supersedes:* P5's case that rested on D10's page-chosen-host argument. For sign-in that argument does not apply, as Glenn says. The verify-then-approve order stands on consent, and on the claim locking the request.
- **P14. Accept the size budget for `sign-in` only,** stated per flow, with the conditions in error 4.
- **P15. `unsupported-vid` maps to `update`; agent-name domains follow the host rules; producers encode `&`, `=`, `#` and `%`, and readers accept a raw `=`.**
- **P16. Accept 60 s skew, J1, the extra J2 conditions, no logo on sign-in codes (or only with an agent name), the whole agent name on the confirm screen, and separate later flows.**

### What we found in the cap, and the positions taken

- **P17. The cap binds producers; readers keep the 1,536 code-point limit.**
  - A reader cap of 251 lets an appended parameter make a valid link unusable. For example, a mail system's `?utm_…` on a 240-character link takes it near 280.
  - That breaks the promise S3 was settled on (spec section 3: the query is never read, so an appended parameter "changes nothing").
  - Proposed wording: "A producer MUST NOT emit a link longer than 251 bytes. A reader rejects a link only above the general limit of 1,536 code points (`too-long`)."
  - One cap and derived field caps are accepted. Only where the cap is enforced moves.
- **P18. The cap counts UTF-8 bytes.**
  - "Every character in a valid link is ASCII" is false under current rules: a reader ignores unknown parameters whatever their value, and a vector accepts a non-ASCII space inside an ignored value.
  - QR byte mode counts UTF-8 bytes. Counting bytes changes no vector.
  - Forbidding raw non-ASCII was the alternative. It was not chosen, because it changes that vector and adds a rule.
- **P19. The cap is measured on the `https` form.** `keyring://` is two characters longer than `https://`, so counting under a wallet's own scheme would reject a 250-byte link. With P17 the cap is a producer rule, and producers emit the `https` form.
