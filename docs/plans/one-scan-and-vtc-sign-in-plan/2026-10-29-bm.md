## Part 1. Corrections

**C1. Supersedes N7 (the VCALM bridge). The bridge does not sit in the flow definition.** N7 said a VCALM page could show a trigger link for a flow whose first request is DIDComm. That is not how VCALM bridges to DIDComm.
- VCALM (W3C Working Draft, section 3.7) has a QR code carry an opaque `https` interaction URL with `?iuv=1`. The wallet fetches it and receives a `protocols` map. Its `didcomm` entry "should be the Out-of-Band (OOB) Invitation URL for the exchange". VCALM also defines `interaction:` and `web+interaction:` scheme prefixes (section 3.7.3).
- The bridge therefore depends on fetching the scanned URL. A trigger link must not cause a fetch by reference (VTI-LNK-072), keeps its handle in the fragment, has no `iuv`, and its host serves an HTML page (VTI-LNK-091).
- Position now: a trigger link is not a VCALM interaction URL and does not use VCALM's route to DIDComm. A flow with a DIDComm first request can still start a DIDComm exchange, but that does not make trigger links part of VCALM. The two meet side by side: in one wallet, where a VCALM interaction URL is `not-ours` and passes on (VTI-LNK-020, -021), or as two codes on one page.
- Verified this session against the published draft text (`iuv=1`, the `didcomm` entry, the scheme section). Not verified: any VCALM rule that allows or forbids protocol identifiers beyond its table; no VCALM implementation was tried.
- The reply drafted on 2026-10-28 for the contributor said the bridge sits in the flow definition. It is not to be posted as written.

**C2. Supersedes the third option of N6 (one code with `?_oob=` in the query and the trigger parameters in the fragment). It is blocked by the chapter, not only constrained.**
- A minimal `_oob` query for the chapter's example `did:webvh` is about 269 bytes, so the combined link is about 453 bytes against the 251-byte cap at QR level M (VTI-LNK-081).
- An `_oobid` form fits (about 228 bytes) but makes a DIDComm reader fetch, which VTI-LNK-072 rules out.
- The figures are arithmetic with an illustrative goal code, not measurements. "About twice as long" holds: a minimal OOB link is about 376 bytes against about 184 for the trigger link.
- The assumption behind the option, that a DIDComm reader reads only the query, holds for Credo (read from source, not run): it parses with `query-string` `parseUrl`, which strips the fragment. DIDComm itself says nothing about fragments.
- Position now: two codes on one page, or a DIDComm service in the contact's DID document. Both stay deferred.

**C3. Corrects N5's reliance on VTI-LNK-041.** N5 used it to show that a reader fetches nothing from the link host. The requirement only says a path-form flow is resolved against `https` and the link's host and compared as a whole string. That a reader makes no fetch is the result of VTI-LNK-072 and of the reader's own design, not of VTI-LNK-041. N5's conclusion stands; its citation is narrowed.

## Part 2. New findings

**F1. A Credo-based scanner treats a trigger link as a short URL.** Credo's `parseInvitationShortUrl` treats any URL without `_oob`, `oob`, `c_i` or `d_m` as a short URL and issues a GET. A Credo-only scanner given a trigger link fetches the link host's page, without the fragment, and then errors. Nothing is spent, but that wallet shows its own error and not a helpful message. Read from the pinned `@credo-ts/didcomm` (0.7.1-pr-2704) source; our yarn patch does not touch OOB parsing.

**F2. "Connects before reading the goal" is confirmed in code.** With default options a v2 invitation goes `receiveInvitation`, `acceptInvitation`, `acceptOutOfBandInvitation`, which creates a connection record. `goal_code` is not consulted. The annex said this "read from code"; it is now checked at the pinned version.

**F3. The chapter has moved since the merge.** `spec/07a-links.md` on `main` has four later commits: VTI-LNK-106 and 107 (the same-device click on the portal, 2026-10-20), VTI-LNK-104 (2026-10-20), and the `did:scid:vh:1` additions (2026-10-22). Citations in the design note are against current `main` (`a85dc840`), and every requirement ID it cites was checked to exist and say what is claimed. Our spec and vectors have not been re-read against these four commits.

**F4. The `auth/oob/*` name is still used.** The plan accepted renaming `sign-in` away from `oob` (S9). The chapter and upstream code still say `auth/oob/*`. The design note says the name is not DIDComm out-of-band.

## Part 3. Sources and their authority

- **The VTI specification chapter is authoritative.** The 8 October sign-in design (a downloaded file and a shared artifact, one document) may be outdated and was set aside where it disagrees. It uses `trusttasks://oob?v=1&svc=&id=` with parameters in the query, rejects unknown parameters and versions with `v=1`. The chapter requires `https` and no custom scheme from producers (VTI-LNK-010, -013), parameters only in the fragment and the query never read, unknown names ignored (VTI-LNK-011), and versions in `_type`. Nothing from that document is in the design note.
- **The draft design note** is `/srv/dev/scratch/2026-10-29-bm-trigger-link-design-notes.md`, proposed upstream as `docs/05-design-notes/trigger-link-design.md`. It is written in that repo's voice and carries no Keyring-internal references. Not submitted.
