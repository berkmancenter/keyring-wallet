## Part 1. Decisions and what each superseded

**D1. One plan for A and B (F1).** They share a precondition (the phone manages the member's VTA), a key rule, one scanner and one set of parsing rules; two plans would each carry half of each and drift. The Farm evaluation companion records an evaluation, not a design, and was left unchanged.

**D2. B's custody rule, scoped (F2, F16).** B says no DID key leaves the VTA. Keyring's manager key is a device key, kept apart from personas (`VtiIdentityStore.ts:26`, `:57`), but `VtaClient.borrowKey` copies persona keys into memory today. The rule is therefore scoped to the sign-in module and persona keys rather than stated as a fact about Keyring. When B was revised to the key grant (D14) the VTA signs the approval itself, which meets the rule directly. Keyring still has a second, separate login: the Farm's SIOPv2 `id_token` from a phone-held Ed25519 key. *Superseded:* the reading of B's sentence as a statement about Keyring today.

**D3. `did:webvh` resolution already exists (F3, F14 M2).** `RetryingWebVhDidResolver` is registered (`utils/agent.ts:164`) and the shipped claim resolves the slot's DID for its mediator (`vtaAgent.ts:1272`, `resolveVtaMediator`). What is unproven is a real Farm log on each supported device with a tampered log rejected. *Superseded:* the parent plan's "resolution does not exist in the wallet" (left for its own edit).

**D4. `keyring://vta/enrol` stays, lab-only; U1 is withdrawn as a Farm ask (F4, F14 M8).** It carries a proof of the key and a code both screens compare, which suits an operator who grants by hand and is used by the lab page and tests. The Farm builds one claim payload instead.

**D5. The wire rules live in a shared spec (F7, F8).** The Farm, a portal and Keyring all read the links. The format went through three shapes on the way to D6, each superseded: (a) every new host rejects unknown parameters (F5), dropped because one added parameter would break every installed app; (b) a bespoke `keyring://<flow>?v=&…&crit=` envelope with IGNORABLE and CRITICAL parameters (F7), dropped because `crit` copied JOSE's `crit` without JOSE's signature, so it was advisory, and because a scheme of our own is one more format; (c) a DIDComm v2.1 out-of-band invitation carrying a Trust Task document as an attachment, with a `goal_code` registry and a by-reference `_oobid` form (F8), dropped by D6.

**D6. The QR is a one-way trigger, not a task (F12).** It names a contact DID, a handle, an optional expiry and an optional flow hint, grants nothing, and the wallet takes the endpoint from the inviter's DID document. *Superseded and why:* the attachment container, because `bindings/didcomm/0.2` says a plaintext or anoncrypt arrival "MUST NOT enter the framework pipeline" and Credo dispatches attachments by `@type`, which a Trust Task document lacks (read, not run); the `goal_code` registry, because it named the flow twice and was not namespaced; the by-reference fetch, because a GET is made by link previews and scanners and spent the handle; F11's lean toward a new `link` binding carrying a Trust Task document, because a trigger has no document to carry; the "scanner-only" rule for sign-in (F5), because a camera delivers a link as a link and refusing links does nothing against a relay; and the claim that proof of possession protects a leaked handle, because in a pool claim the claimant picks its own key.

**D7. Claim authorisation: A hardened now, Phase 2 open (F10, F12, F13 WP2, F17).** Three options were set out: A, the single-use bearer handle (the Farm's callback today); B, a claim code on another channel (the `vtc/install/claim/start/0.3` pattern, OpenID4VCI `tx_code`); C, no secret in the QR, the phone's signed claim makes the slot pending and the person confirms a key-derived code on the Farm page. Brendan's working position: v1 is A, hardened (spent on the POST, never on a GET; device authentication at claim; the `acl/list` sole-super-administrator check after the swap); Phase 2 candidates are C, then B if C is impractical, with A plus B's code as the fallback. *Superseded:* "no option chosen" (F10, F12). C cannot ship before the Farm's frozen QR moves.

**D8. Transport from the verified DID document, by the wallet's preference (F13, F15).** The presenting screen is usually not the endpoint. *Superseded:* "the first supported service in document order", because it lets the document steer the wallet and no ranking rule among services was found in DID Core or upstream; and the advisory `tp` transport hint (F13), cut in F15 because it had no defined effect. Endpoint-looking members in the text are ignored, never used (F14 M5).

**D9. Container: a plain `https` link with four `_` names and standard decoding (F13 WP3, F15 D1).** *Superseded:* "no lean" between this and the out-of-band invitation (F12), and the "never percent-decode" grammar, because `URLSearchParams` and `urlencode` encode colons and slashes and a reader refusing `%` refuses standard output. The out-of-band invitation is recorded as an alternative (spec annex E).

**D10. Confirm before any network activity, normative (F15 D2).** Without it a web page could make the phone fetch from a host the page chose and send a signed request. The first screen shows only the contact's host, labelled unverified; the person approves again after verification. *Superseded:* resolving and sending straight after reading the text.

**D11. Flow identifiers (F9, F13 WP7, F15 D3, F18 D3, F19).** Four positions in turn: `trusttasks.org` with an accepted-authority set and dual emission (F9, F13), dropped because the framework forbids a private specification from claiming `trusttasks.org` and the migration machinery was for a move nobody planned; private identifiers under `wallet.asml.berkmancenter.org` (F15), dropped because a wallet's own host should not be in a shared identifier; a proposed Trust Over IP prefix, `https://registry.trustoverip.org/dtg/flow/`, with the sign-in slug derived from B's task family (F18); and finally slugs that name the flow, `vta-claim` and `community-sign-in` (F19), because B's task names are a third party's and may change, a flow may use several tasks, and B's family name contains `oob`, which is also DIDComm's out-of-band term. The prefix not being ours knowingly misses the framework's "SHOULD sit in a namespace the publisher controls" until Trust Over IP answers. Brendan chose this over an interim prefix we control.

**D12. A slim normative core (F15 D4).** The spec carried about 100 lines of real contract in about 490; the rest moved to an annex. The handle travels as the framework's `parentThreadId` (mapped to DIDComm `pthid`) instead of a task-defined member, and `trust-task-discovery` answers "which tasks do you support" when there is no hint. *Superseded:* the display `goal` string and the `tp` hint (cut).

**D13. Claim relay is a recorded risk (F15 D5).** Reported by a review, not verified: a claim code relayed from the attacker's own Farm account. Recorded with the mitigation (show the signed issuer and account before the claim) in the Phase 2 design and asked of the Farm. Withholding `vta-claim` from the spec was considered and declined.

**D14. B is a key grant (F16).** B's authors replaced their SIOPv2 design (`auth/challenge`, an `id_token` minted through `vault/proxy-login`, `auth/cross-device/*`, a `keyring://vtc-login?v=1&vtc=&lid=` QR and a first-scanner lock) with five tasks, a browser-held key and a VTA-signed approval through `vault/sign-trust-task/0.2`. Adopted as the plan's description of B; K4 rewritten around it. *Superseded:* every earlier description of B as SIOPv2, the first-scanner lock and the `crossDeviceClaim*` term. Recommendations to the authors: emit the trigger link, tolerate unknown parameters, carry the expiry, state the DID method, rename the family without `oob`, cite what the pinned trees contain, and say which VTA capability the approval needs.

**D15. No reader for B's custom-scheme QR (F17).** A legacy reader for `keyring://oob?…` (15 vectors) was added in F16 in case B shipped first, then removed: the portal can emit the trigger link from the start, and a custom scheme neither opens from a camera nor stays private to one app.

**D16. One shared link host and the fragment (F18 D1, D2).** One link opens any of several wallets only if one host lists them all; a shared custom scheme is indeterminate (RFC 8252 section 8.1). Proposed host `link.trustoverip.org`, a dedicated subdomain rather than the registry's host. The trigger moved from the query to the fragment so the host never receives it; a reserved name only in the query is `query-form`. *Superseded:* "no link-domain option chosen" (F11), and the query link with a no-log rule (F15). The fragment's survival through camera hand-offs is unverified and is the main risk to this decision.

**D17. Working positions (F13, F14, F15; Brendan, for discussion).** The first release bundles the QR fix, the host-check fix and log redaction, and K0 ships alone if the others slip. Device authentication at claim, passcode as fallback. Sign-in is not scanner-only; number matching, the signed requester screen and a biometric now, proximity later. Admin-side revocation of login identities does not block. The first releases use the in-app scanner only, with Keyring's own host as the interim link host. No "Open Keyring" button on the Farm page in the first release (F14 H2): the legacy QR from a link is `wrong-channel`, an `https` button opens nothing until a build declares the host, and a custom-scheme button on a spendable callback is forbidden. Login registration failing after `connected` is retried idempotently while the progress credential is valid.

**D18. The spec is general; Farm and Keyring specifics leave it (this pass).** The spec core now names no Farm, VTC or wallet: the Farm's legacy QR moved to the annex as one consumer's other handler (spec annex F), with its vectors in a separate `legacyVectors` list; `keyring://` became "an alias scheme the consumer registers"; Keyring-specific out-of-scope link lists and code notes moved to the plan; Farm domains in the vectors became `example.com` fixtures. *Superseded:* the core's section 8 (legacy) and its `scan-only` outcome, and the claim that sections 1 to 9 named no Keyring internals while section 3 named `keyring://`.

**D19. Design fixes found in this pass (spec).**

- **Draft status, not MAJOR 0, allows a breaking MINOR.** The framework's rule is "a breaking change to a `draft` artifact MAY be released as a `MINOR` increment". The spec tied it to MAJOR 0; it now ties it to the flow's status, and the vectors' flows carry `status`. Behaviour for both proposed flows is unchanged.
- **Host labels are letters, digits and hyphens.** The host rules gave label lengths but no character set, so `link_host.example.org` or `-link.example.org` passed. Labels are now LDH, not starting or ending with a hyphen. This tightens, never loosens, a security rule.
- **Selection says which services are candidates.** A service whose endpoint is not `https`, has userinfo or fails the host rules is not a candidate; the vectors already expected this and the core now says it.
- **The producer rule said "exactly the four reserved names".** `_exp` and `_type` are optional. It now says `_from` and `_id`, and the other two where used, each once.
- **The reader's whitespace rule is exact:** any code point U+0000 to U+0020 or U+007F.
- **Length is counted in code points**, and the query is defined as text after the first `?` that comes before the first `#`.
