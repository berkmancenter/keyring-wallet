## F2 — B's key-custody rule does not describe today's phone

B's first principle is *"No DID private key leaves the VTA. Keyring holds only its enrolled device key"*, and B's Keyring section says Keyring *"must have no code that signs an `id_token` on the phone"* and *"hold any DID private key"*.

Checked: the **manager key** is a device key, stored as its own record kind (`VtiManagerIdentity`, `VtiIdentityStore.ts:26`), minted as a temporary `did:key` and swapped onto a phone-minted DID (`VtaClient.ts:1135`). It is not a persona key and is not derived from one. That half of B holds.

The other half does not. `VtaClient.borrowKey` (`VtaClient.ts:1683`) fetches a persona's **private** signing and key-agreement keys over `keys/export-secret/0.1` and imports them into an in-memory KMS backend (`vtaKeys.ts`, whose header says Keyring does "exactly this"; `VtiPersona.kmsKeyIds`). They are never persisted and are refetched each session, but they do leave the VTA, and `vtiAgent.ts` signs vetting statements with the borrowed signing key.

**Conclusion.** B's rule is adopted **scoped to the login flow**, and the plan says so rather than restating B's absolute. A reader who took B's sentence as a statement about Keyring today would conclude the phone holds no persona key, and would be wrong. Open: whether the persona key the VTC checks in an `id_token` (its `authentication` key) is one the phone already borrows (plan §11 V2).

## F5 — Decisions made in drafting the scheme

- **Parsing rules per flow, not for the router as a whole.** The router also carries `vetting-ticket:`, bare DIDs, `keyring://vti/…`, `keyring://vta/…` and a JSON shape; "reject other schemes" cannot apply to them. The shared rules bind the two new hosts only, and the existing links are untouched. Retrofitting strictness onto them was considered and rejected: `parseEnrolmentLink` deliberately ignores trailing parameters today.
- **`vtc-login` is scanner-only in v1.** The app's own convention says every QR has a link twin. B's controls (number matching, the portal's own origin, the claimed-state notice in the browser) assume the code is on a different screen. A link opened from the phone's own browser or a chat message is B's T2 (out-of-band QR) with no portal to match against, and a deep link held while the wallet is locked (`deep-links-while-locked.test.tsx`) outlives a 120 s login. This departs from the convention on purpose; recorded as an open question (plan §11 B4).
- **Parser bounds** (`lid` 22–128 base64url characters, `cb` ≤ 2,048) are mine, not either design's, and are marked as proposed in the plan.
- **Terminology.** "Claim" means a parked slot (A), a pending login (B's `auth/cross-device/claim`, a name we do not own) and a credential statement. Screens use "Set up your agent" and "Sign in"; code uses `vtaClaim*` and `crossDeviceClaim*`.
- **Biometric at the claim** is recommended and left open: today `confirmHostOffer` checks only for a screen lock, while every later owner act prompts (`confirmOwner`).

## F7 — The wire rules move to a shared spec; CRITICAL/IGNORABLE replaces blanket reject-unknown

**Superseded in part by F8** (the bespoke envelope, `v`, `crit` and the flow registry). Kept as written: it is the reasoning Keyring held at the time.

Written the same day, after F5. The two new links are read by the Farm and a VTC portal as well as by Keyring, so their rules cannot live only in a Keyring plan. They now live in [`../../specs/keyring-qr-and-links.md`](../../specs/keyring-qr-and-links.md) (DRAFT, with vectors), and the plan points to it.

**Supersedes F5's first bullet's consequence and plan §4 rule 3.** The plan said the two new hosts reject any unknown parameter. Rejecting every unknown parameter means a Farm that adds one optional parameter breaks every installed app, so the parties could never evolve a link independently. Replaced by: `v` is a major; within a major only optional parameters are added; each is IGNORABLE or CRITICAL; a CRITICAL extension is named in a reserved `crit` list in the link itself, so an old reader that has never heard of the parameter still sees the warning; unknown IGNORABLE parameters are ignored; unknown CRITICAL ones, unknown flows and unknown majors give an "update the app" screen. Repeated parameters still always reject. Rejecting unknown keys stays for version 0 (the legacy JSON), where `parseAgentHostQr` requires exactly `vta_did` and `callback_url` (verified 2026-10-08).

**Also changed.** Plan §4 rule 2 said an unknown host token is passed to the existing classifier. That conflicts with "never fall back silently", so only slash-bearing hosts (`vta/enrol`, `vti/community`) go to the classifier; an unregistered single-token host is the update outcome. `cb` is capped at 512 characters, not 2,048 (the plan's figure could not fit a QR next to the rest of the link, whose cap is 1,024).

**Found while checking.** `allowedHostOf` accepts `https://.ic3.dev/…` (its `endsWith('.ic3.dev')` test passes on an empty label) and a URL with a fragment. Neither is exploitable as far as read, since the host still ends in an allowed name, but the spec refuses both and K1 aligns the code.

**Verification.** A throwaway reader written from the spec's grammar and evaluation order was run over all vectors in the scratchpad and agreed on every one; that proves the vectors and the spec are consistent, not that Keyring's parsers pass them. The 1,024 and 512 caps and the 256-character DID cap are proposals. The QR capacity figure in the spec is from memory and not checked.

## F8 — One standard container: the DIDComm out-of-band invitation replaces the bespoke envelope

**Superseded in part by F12** (the Trust Task attachment, the `goal_code` registry, by-reference fetch and the claim-secret reading). Kept as written: it is the reasoning Keyring held when it was written.

Same day, later. Brendan's direction: be transport agnostic like Trust Tasks, and use standards as much as possible. The research behind it (DIDComm v2.1 out-of-band, TSP, RFC 8252, OID4VCI/VP, RFC 8628, CTAP hybrid, the VSC and Trust Tasks identifier rules) was read from the documents and the pinned clones on 2026-10-08.

**Concluded.** Both flows are one DIDComm v2.1 out-of-band invitation (`https://didcomm.org/out-of-band/2.0/invitation`; `id`, `from`, `body{goal_code, goal, accept}`, `attachments`). `goal_code` names the flow (registry: `vta-claim`, `vtc-login`). Delivery is an `https` link `?_oob=<base64url>` or `?_oobid=<id>` fetched by plain GET; `keyring://` is an alias carrying the same host, path and query. The attachment is a Trust Task document in a plaintext envelope (`https://trusttasks.org/binding/didcomm/0.1/envelope`, `TrustTaskEnvelopeV2Message.ts:40`). Transport comes from the `from` DID's document, never from the text. Versioning comes from the Trust Task type URI (`MAJOR.MINOR`, framework 0.5 s5.2): MINOR additive, higher MINOR accepted with unknown members ignored, unknown MAJOR refused with `unsupportedVersion`. The wire rules are in `docs/specs/keyring-qr-and-links.md`; the plan's §4 states how Keyring applies them.

**Supersedes.**

- **The bespoke envelope** `keyring://<flow>?v=<major>&…&crit=…`, its `v` major, its IGNORABLE/CRITICAL parameter marking with a reserved `crit` list, and the flow registry as the way to name a flow (F7; spec revision 0 as first drafted). Why it was proposed: the Farm and a portal needed to evolve a link without stranding installed apps, and no standard was known that did it. Why it moved: the out-of-band invitation, the attachment and the Trust Task version rules already do each job, so a scheme of our own would be one more format every scanner learns; `goal_code` is the flow registry; DIDComm's "attachments in order of preference, one chosen" is the extension and fallback mechanism that `crit` approximated. `crit` mirrored JOSE's `crit` (RFC 7515 s4.1.11), which is protected by the signature; ours was unsigned, so it was advisory against an active attacker. The sibling `cierge-pair://v1?…` custom scheme in `vta-mobile-agent-ios` was precedent for custom schemes, and also for the risk of many bespoke ones.
- **Position 1 (QR shape).** Keyring's position was that the QR keeps `{vta_did, callback_url}`, also offered as `keyring://vta-claim`, the Farm enforcing expiry and single use, a field added only when the wallet needs to see it, the format versioned, and the Farm building one payload. The "one payload" and "the Farm enforces single use and expiry" parts stand. The shape does not: the payload is the out-of-band invitation, and the legacy JSON is accepted until a sunset the owners set.
- **Position 2 (callback allow-list).** Keyring's position was that callbacks are on Farm domains only (`ic3.dev`, `firstperson.dev`), partners issue links that land on a Farm callback, and any widening reads a signed, fetched configuration. The callback is gone from the QR: the endpoint comes from the claim service's DID document, and the allow-list now applies to `from`'s DID domain and to any `_oobid` host. The "signed, fetched configuration if ever widened" part stands. Positions 3 to 10 are unchanged.

**Evidence and what is unverified.**

- **`from` for a pooled claim.** A parked slot runs nothing, so it cannot serve a DID document or be an inviter; the inviter is the Farm's always-on claim service, and the slot's DID is a subject in the attachment. This is an inference: no Farm design is in `external/` (grep for `vtafarm`, `parked`, `claim` found only unrelated uses).
- **The carrier.** Binding `didcomm/0.2` mandates authcrypt; an invitation has nobody to encrypt to, so the attachment is a plaintext envelope outside the binding's transport rules, and its document is unauthenticated unless it carries a `proof`. Whether the Trust Tasks group accepts that is open. Framework s4.8.2 and s4.8.3 make a document audience-bound (`recipient`) unless its spec declares itself bearer; a claim handle is not intrinsically audience-free, so the claim task must be audience-bound to the claim service.
- **The task types do not exist.** The claim task has no spec. The login-claim name `auth/cross-device/claim/0.1` is from proposal B and is in no pinned clone. Their authority is **an open question**: a private spec "MUST NOT" be served from `trusttasks.org` and "SHOULD use an HTTPS authority the publisher controls" (framework s6.5); whether `trusttasks.org` or `registry.trustoverip.org` would host them is unverified.
- **Draft versions break.** A task at MAJOR 0 is draft, and framework s5.2 lets a breaking change ship as a MINOR; the spec therefore has a MAJOR 0 consumer accept only the MINORs it implements. A strict-match consumer is allowed (the framework's non-normative paragraph calls exact-URI routing conformant).
- **Identifier rules** (framework s6.1, s6.4; VSC governance s2.1, s2.3, s3): kebab-case slug, version last, exact byte comparison, a published identifier never edited, reserved subtrees and fragments. The identifier-research note in the scratchpad contained only its source list when this was written, so these were read from the sources directly. The VSC registry has no entry in `PINS.json` (read at head `eb29484`); the Trust Tasks clone is at the pin `bdae1cf9`.
- **A secret in a QR.** DIDComm says "no private information may be passed in the message" and "should not be passed via URL or QR code". A claim handle is a secret. The spec states the mitigations as requirements on the Farm (single-use `_oobid` fetched once, short expiry, proof of possession by the phone's key, single use, revocation) and records the risk as open for the Farm owners rather than hiding it. OpenID4VCI 1.0's pre-authorised code with a `tx_code` second factor is the standards' own pattern for this. Whoever scans first still wins.
- **`vtc-login`.** No standard defines it. RFC 8628 s3.3.1 (`verification_uri_complete` "designed for non-textual transmission") is the model for a short-lived code on another screen; FIDO CTAP 2.2 s11.5 (hybrid transport, a Bluetooth proximity requirement so a remote site cannot make a person scan its code) is the strongest precedent for the same-device and remote-QR risk, and its mitigation is cryptographic where ours is a policy rule. The cross-device BCP is cited by OpenID4VP 1.0 as `draft-ietf-oauth-cross-device-security`; a datatracker summary said RFC 10027 / BCP 247 (August 2026), from a summariser, **unverified**.
- **TSP.** No invitation format: the specification calls out-of-band introduction "out of scope" and uses a QR only in "a TSP message can be printed". `vti-tsp-js` has no OOBI helper; the ToIP Rust SDK was not in `external/` and was not checked. A TSP-based inviter is an open question.
- **`accept`.** DIDComm's `accept` names media-type profiles and cannot say "reply over HTTPS" or "over TSP"; the DID document's service list (`DIDCommMessaging`, `TrustTaskHTTPS`) decides instead. That is custom.
- **RFC 8252.** s7.1 asks a private-use scheme to be a reverse domain name (`keyring` is not) and s7.2 says a claimed `https` URI "SHOULD" be preferred, so `https` is primary and `keyring://` an alias.
- **Does Keyring ingest v2 `_oob` links?** `vtiLinks.ts` has no `https` or `_oob` classification (only the comment at `:103`). `helpers.ts:1156-1186` passes a v2 `_oob` link to Credo as an ordinary connection invitation (`:1163`, `:1169`, `:1179`; called at `:1349`); nothing dispatches on `goal_code`. Attachment-only handling in Credo and `_oobid` were not checked.
- **`allowedHostOf`** (`agentHostConnection.ts:121-126`), evaluated in a scratchpad with the same regex and logic: it accepts `https://.ic3.dev/x`, `https://a..ic3.dev/x`, `https://ic3.dev/x#frag` and a NUL in the path; it rejects userinfo, a port, `evilic3.dev`, `ic3.dev.example` and a bare `#frag`. A follow-up code fix is recommended (K1 in the plan); no code was changed. This corrects F7's statement that "neither is exploitable as far as read" only in scope: the host still ends in an allowed name, as F7 said, and the control-character case was found now.
- **Off-pin clones.** `verifiable-trust-infrastructure` is at `187ad9cd`, not the pin `822ff78a` (the pin object is absent from the clone); `openvtc` is at `ed13d29`, its pin `8991f9c` is not an ancestor of head; `affinidi-tdk-rs` and `dtgwg-cred-spec` differ from their pins and were not used. Nothing was advanced.
- **Vectors.** Rewritten for the new container (124 cases). A throwaway reference reader written from the spec's reading order, in the scratchpad and not the repository, agrees with every vector. **That shows the vectors and the spec text are consistent; it does not test Keyring's parsers**, which do not exist for the new links.

**Applied.** The shared spec and vectors are rewritten, and the plan's §4, §5, §7 (positions 1 and 2), §8, §10, §11, §12 and §13 are aligned. Not applied: any change to `vtiLinks.ts`, `agentHostConnection.ts` or `own_agent_subtask.md` (its U1 pointer stays as it is).

## F9 — Authority for the task types, and what upstream tasks can be reused

**Restored 2026-10-08 (BM).** The plan and the spec cited an F9 and an F10 that this companion did not contain (an adversarial review found the gap). They are reconstructed here from the plan, the spec and the appendix of the same day; the original wording is not recoverable, and the reasoning below is what those documents already rest on.

**Authority.** The two task types (`vta-claim`, and the login pairing `auth/cross-device/claim`) are new, so they need a home in the identifier space. Framework s6.1 gives `https://trusttasks.org/spec/<slug>/<MAJOR.MINOR>` as the public-registry form; s6.5 forbids a private specification from claiming `trusttasks.org`. Brendan's position: this work lives under Trust Over IP unless there is a compelling reason against, and he can have the types added (he is an editor). What was read: the registry repository README says it is "Developed under the Trust Over IP Foundation (ToIP) Decentralized Trust Graph Working Group (DTGWG)", which is a statement about the repository and not about who controls the domain. The VSC registry was checked and is not the home: its `GOVERNANCE.md` s1 and s5 scope it to credential predicates and exclude anything "meaningful only inside one exchange (that is a trust task artifact, not a statement)", and a claim or a login is a flow. (Later the same day, F12 turns the authority into a configured **set** with transition rules.)

**Reuse.** Every candidate upstream task was read at `dtgwg-trust-tasks-tf@7b6bb488` and judged as is, profile, or new type. None is a drop-in: `vtc/invitations/deliver/0.1` binds its code to a subject DID known up front (a pool claim's is not); `vtc/install/claim/{start,finish}/0.3` is VTC-specific and its token must name an admin DID; `auth/step-up/*` binds an approver; `auth/authenticate/0.3` fits the VTA-proxied sign-in leg. ## F10 — Claim authorisation: why it was left open as two options

**Restored 2026-10-08 (BM)**, as F9. The question: DIDComm says "no private information may be passed in the message" and that such a message "should not be passed via URL or QR code", while a one-scan claim needs something that makes the scanner the owner, once. Two options were set out in the spec, with pros, cons, requirements and residual risk, and neither was chosen: **A**, a single-use handle fetched once by `_oobid`, with proof of possession by the phone's key at the claim; **B**, no secret in the QR and a separately delivered claim code and/or step-up approval (the `vtc/install/claim` pattern), possibly a proximity check (CTAP hybrid). They were not known to dominate: A is one scan but moves a bearer value through a retrieval endpoint; B keeps the QR clean and costs a second step and channel. OpenID4VCI's `tx_code` (a pre-authorized code with a second factor) is the standards' own combination of the two, so "A with B's code" was named as a fallback. **Superseded by F12**: the first draft's claim that proof of possession protects a leaked handle was wrong, the by-reference fetch spent the handle on a GET, and a third option (C) dominates both.

## F11 — Two further asks: trust tasks in the link itself (D1), and opening from a generic camera (D2)

**Superseded in part by F12** (D1 is replaced by T1 and Option 2 is a recorded alternative; the by-reference resolver of D2 is gone). The camera and domain findings stand. Kept as written.

Same day, later. Brendan asked (A) whether Trust Tasks could be encoded directly in the QR or link, treating a URL as one more binding, and (B) that a generic camera app open the right app like any other link, with `keyring://` demoted. Both are recorded as **open decisions for the team**, not adopted positions. The spec's sections 2.1 to 2.4, 6.4 and 12.1 and the plan's D1 and D2 carry them; this entry holds the reasoning.

**D1, what was concluded.** Two options, set side by side in the spec (6.4): Option 1, the current out-of-band invitation wrapping a plaintext Trust Task attachment; Option 2, a bare Trust Task document on a new link binding (by value, or by reference plus a digest), optionally wrapped. **Lean: Option 2 with the optional wrapper, unreviewed**, because it names the flow once (the Type URI) instead of twice (`goal_code` and `type`, kept equal by section 3 step 15), roughly halves the symbol (measured, below), avoids the connection Credo makes to `from` on a v2 invitation, and fits the framework's own idea of a binding (`SPEC.md` s9 lists "paper"). Against it: a binding the Trust Tasks group has not seen, no DIDComm scanner reads it unless wrapped, an unsigned by-value document has no attributable issuer, and it does not remove Q6. This does not supersede F8: F8's container remains the specified one until the team decides.

**Evidence, with status.**

- Binding naming and shape: `SPEC.md` s9.3 (`https://trusttasks.org/binding/<slug>/<MAJOR.MINOR>`, `bindings/<slug>/<MAJOR.MINOR>/spec.md`, private forms, a Type URI never rooted at `/binding/`), s9.1 (what a binding specifies; lifecycle mapping is a MUST), s9.1.1 (silence is not permission to omit `proof`; a binding with no end-to-end guarantee "SHOULD say so plainly"). Section list and front matter from `bindings/didcomm/0.2/spec.md` and `bindings/https/0.3/spec.md`; `tsp/0.1` has the same spine. All at `dtgwg-trust-tasks-tf@7b6bb488`. **Verified** (read at `origin/main`).
- Bearer and audience: s4.8.2 (`recipient` required with `proof` unless a bearer specification; replay rationale), s4.8.3 (bearer only if "the audience-free property is intrinsic"), and the privacy section's sentence that bearer status "governs audience, not distribution". **Verified.** The inference drawn is mine: a QR is distributed to anyone, which is a different fact from a task being audience-free, so both tasks stay audience-bound.
- Upstream precedent: `specs/vtc/invitations/deliver/0.1/spec.md`. Its response carries an OID4VCI offer "small enough for a QR code"; the QR holds that offer and not a Trust Task. **Verified**; it is a precedent for a small key-redeemable offer, not for a Trust Task in a URL. An exhaustive search for any task or binding that puts a Trust Task in a URL was not made (**unverified**).
- Sizes: the case `valid-claim-oob` is 870 characters; with `recipient` and `expiresAt` added and an illustrative payload, Option 1 by value is 983 characters (QR version 22/25/31 at L/M/Q), a bare document by value 434 (14/16/19), a bare document by reference and digest about 91 (4/5/7), `_oobid` 66 (4/5/6). Computed with the Python `qrcode` package, byte mode; version-to-module-count and the version-40 capacities are from memory (**unverified**); a `proof`'s added size was not measured; real-device scan reliability was not measured.
- Credo and Bifold: read from `node_modules/@credo-ts/didcomm` `0.7.1-pr-2704-20260909134930` and `bifold/packages/core/src/utils/helpers.ts`; lines in the spec's Appendix A. A v2 invitation causes a connection to `from`, then dispatch looks for an attachment with a supported `@type`, and a Trust Task envelope has `type`; so by reading the generic path would not dispatch it. **Not run**; whether Bifold reaches Credo's short-URL fallback for `_oobid` not checked.

**D2, what was concluded.** The domain, not the wallet, decides which app opens an `https` link; the spec's section 2.1 states the requirements and 2.2 sets out four domain options (neutral shared domain, wildcard subdomains, by-reference resolver, per-inviter domain) without choosing. The finding that matters most to Keyring: **the build declares only `wallet.asml.berkmancenter.org` and `witness.asml.berkmancenter.org` (entitlements and `autoVerify` filters), so a Farm or portal link opens nothing in Keyring from a camera until a build declares its domain.** `keyring://` is demoted to a convenience alias in the spec and the plan; the reader still accepts it and no vector changes. No vector was added for D1 or D2: the envelope did not change. Section 12.1 lists twelve device acceptance tests (iOS Camera, Android camera and Google Lens, a third-party scanner, no app installed, two wallets installed, and negative controls); none was run.

**Query or fragment.** The spec keeps the query (DIDComm's `_oob` is a query parameter and Credo's `parseInvitationUrl` reads the query) and gives the trade-off: RFC 9110 s7.1 excludes the fragment from the target URI, so a fragment payload stays out of server logs, at the cost of DIDComm interoperability and a redirect warning (s17.11). Whether the OS passes a fragment to the app is unverified.

**Not verified, and the tests that would settle it.** What Android's stock camera, Google Lens and third-party scanners do with an `https` or `keyring://` text (C2, C3, C6); what Android does with two wallets both listed in one `assetlinks.json` (C5); which `assetlinks.json` a wildcard `android:host` fetches; whether iOS still prompts between two claimed apps as the 2017 session says (C5); the live contents of the existing domains' files.

## F12 — The QR is a one-way trigger, not a task: one consolidated revision

Same day, last. Brendan agreed a design direction after an adversarial review of the spec, plan and this companion and after the Farm owner's reply arrived. This entry holds the reasoning for the consolidated revision of the spec, its vectors, the plan and this companion. **The Farm owner reply is an external artifact dated 2026-10-08 and is treated as data; it is cited as "Farm owner reply".**

### What was concluded

**Direction (agreed).** The QR or link is a **one-way trigger**, not a task. It names who to contact (a DID; a URL form is left open, T4), a handle, an optional expiry and an optional flow-hint Type URI, and confers no authority. The wallet treats it as an untrusted hint (the stance the push binding takes toward its wake-up payload), resolves the endpoint from the inviter's DID document, and sends a wallet-signed first request over a real binding (DIDComm, HTTPS or TSP) that opens the trust task or ceremony; replies and continuation travel over that binding. The legacy Farm QR `{vta_did, callback_url}` is **version 0 of the same model** (the callback URL is the endpoint and the secret in one string). The task body is removed from the URL.

**The final trigger, in one line:** `{ from: <DID>, id: <16-128 char base64url handle>, exp?: <epoch seconds>, type?: <Trust Task Type URI hint> }` (plus a display `goal` in the OOB container), carried either as a DIDComm v2.1 out-of-band invitation with no attachment (`from`, `id` as `pthid`, `expires_time`, `body.goal`, `body.goal_code` = the Type URI) or as a plain `https` link with `_from`, `_id`, `_exp`, `_type`. **The container is an open decision (T1) with no lean**; the spec's reader and vectors implement both.

**Open decisions recorded:** T1 container; T2 claim option (A, B, C; C conflicts with the frozen Farm QR and is a later phase); T3 link domains; T4 contact as URL; T5 first request when no hint is given; T6 limits (proposals). Plus the Trust Tasks questions for the expert.

**The word "trigger" is an unconfirmed working term.** Searched at `dtgwg-trust-tasks-tf@7b6bb488`: no task document defines "trigger" as a term. The only uses are the push binding's *Trigger* role (decides when to wake a device; its payload is an "untrusted hint") and `vtc/admin/events/event/0.1` ("A hint is a trigger to re-read"). VTI's "ceremonies" documents use "trigger" for an authenticated actor in a different, server-side policy pipeline. Brendan will ask the Trust Tasks expert for the exact term and source. The spec and plan say so at the top.

### What it supersedes

- **F8's container: an OOB invitation wrapping a plaintext Trust Task document in an attachment, with a `goal_code` registry (`vta-claim`, `vtc-login`).** Why it moved: (1) binding `didcomm/0.2` says a plaintext or anoncrypt arrival "MUST NOT enter the framework pipeline", so an envelope in an attachment invites a conformant handler to reject it (the cause of Q6); (2) Credo accepts an attachment-only v2 invitation at connection level and then fails "Invalid message type" because the attachment carries `type` and not `@type` (read from code, not run); (3) the task body in a URL needs no binding once the text is a pointer; (4) `goal_code` duplicated the task type and was un-namespaced, so the flow was named twice and the bare codes could collide with other ecosystems'. The container now carries no attachment, and the flow is named once, by a Type URI hint.
- **F11's D1 (Option 1 vs Option 2).** The lean toward Option 2 (a new `link` transport binding carrying a bare Trust Task document by value or by reference and digest) is withdrawn: a trigger carries no document, so there is nothing for a binding to carry, and a new binding needs Trust Tasks group acceptance for a gain (one name for the flow) that the hint already gives. **Option 2 is kept as a recorded alternative**, with the essentials of the withdrawn spec section 6.4 preserved here because the spec files are not committed: a binding published through the registry is `https://trusttasks.org/binding/<slug>/<MAJOR.MINOR>` at `bindings/<slug>/<MAJOR.MINOR>/spec.md` (framework s9.3; private forms use the path or URN shapes and MUST NOT claim `trusttasks.org`; a Type URI is never rooted at `/binding/`); its shape follows `bindings/didcomm/0.2` and `bindings/https/0.3` (front matter, Abstract, Status, Binding URI, Document carriage, Identity mapping, Error mapping with Lifecycle mapping, Proof interaction, Transport security profile, Versioning, References; s9.1 makes lifecycle mapping a MUST); request direction only (no reply, so "error and response delivery" says there is none); identity mapping populates neither `issuer` nor `recipient`; carriage by value (`?_tt=<base64url document>`, placeholder name, never `_oob`) or by reference plus a digest of the exact bytes (DIDComm's attachment `links` form likewise needs a `hash`); a transport security profile that says plainly nothing authenticates the producer (s9.1.1: silence is not permission to omit `proof`); audience-bound, not bearer, because a QR is distributed to anyone and bearer status "governs audience, not distribution" (s4.8.2, s4.8.3, privacy section); measured sizes in F11. D1 is replaced by T1.
- **F11's D2 (four domain options).** The by-reference resolver option goes with the by-reference fetch. Three options remain (T3), and the first release needs only option P with the Farm's two allow-listed domains.
- **F5's second bullet and the spec's "scanner only" rule for the login flow.** A stock camera delivers the link to the app as a link, so scanner-only contradicted the generic-camera requirement, and it did nothing against a relay (RFC 8628 section 5.4); calling it a control was wrong. Replaced by relay mitigations (inviter-signed requester screen, number matching, short expiry, biometric, later proximity).
- **The spec's section 8.1 claim that proof of possession means a leaked handle alone cannot claim.** False: in a pool claim the phone's key is unknown in advance, so an attacker signs with their own key. The spec now says handle-only is bearer. Option A's single use is spent on the signed claim, never on a GET.
- **The plan's phase list** (K1 to K4, sequencing) is replaced by Phases 0 to 2 and a Later list (below).
- **Spec "every offer MUST carry `expiresAt`".** That sentence applied to a Trust Task offer, which no longer exists. The trigger's `exp` is optional in general and **required per flow** (`vta-claim`, login), and the reader and vectors now check it.

### WP1 — one small hardening release (K0 + K1a + K1b)

Maps to Phase 0; no decision ID. K1a and K1b are code PRs and are not made by this change.

- **Pros.** The Farm's QR is frozen until K0 ships, so K0 is the only item with an outside party waiting on it. K1a (`allowedHostOf`, `agentHostConnection.ts:121-126`, accepts `https://.ic3.dev/x`, `https://a..ic3.dev/x`, a fragment after a path and a control character; appendix E) and K1b (`TabStack.tsx:146` logs every deep link in full, and the logger can be remote) are small, touch the same area, and are the two defects found while reading the claim path. ### WP2 — claim token, staged (T2, F2, B3)

v1: the Farm's HMAC callback, hardened. Phase 2: Option C. Option B only if C proves impractical.

- **Why not C first.** C changes what the QR means and conflicts with the frozen QR; it cannot ship before K0 and needs the Farm to build a challenge endpoint, a pending-claim state and a confirmation UI. **Pros of the staging:** the hardening is ours and ships without the Farm; the Farm's current QR keeps working; nothing is spent on a GET (the Farm owner reply: the callback is a POST target, single-use per DID, idempotent 24 hours for the same `admin_did`). **Cons:** v1 is still a bearer: whoever uses an unused callback first nominates the administrator, and proof of possession does not change that (spec 8.1). The biometric at claim narrows the damage (the person at the phone must authenticate) and does not remove it; a leaked callback used on the attacker's own phone is authenticated by the attacker.
- **Hardening parts.** (a) Single use spent on the claim POST and never on a GET: a Farm requirement, already how the callback behaves per the Farm owner reply. (b) Biometric or OS local authentication at the claim: `confirmOwner` already reads a Keychain item stored with `BIOMETRY_ANY_OR_DEVICE_PASSCODE` (read from `ownerConfirm.ts`), so the passcode fallback is built in. The cost is one more tap on a path sold as one scan. (c) The sole-super-administrator check by `acl/list` after the key swap (`VtaClient.listAcl`, `:1284`): it catches a slot that was claimed by someone else first, since the Farm's grant kind is only an assertion.
- **B.** A second factor on another channel (`vtc/install/claim/start/0.3`; OpenID4VCI `tx_code`). **Pros:** a real second factor; precedent in upstream. **Cons:** a second channel and a Farm build; a code shown on the same screen as the QR is no second factor.
- **Recommendation.** The staged path as accepted. If the Farm will not build C, take A with B's code rather than A alone (spec 7, "if C is rejected").

### WP3 — trigger container (T1)

- **Y: a plain `https` URL with a fixed query (`_from`, `_id`, `_exp`, `_type`, optional `_tp`), proposed to the Trust Tasks task force as a profile.** **Pros:** smallest (about 150 to 250 characters, so a lower-density QR that scans more easily; scan reliability itself is unverifiable from documents, test C11); trivial to parse strictly; no DIDComm side effect. **Cons:** not a standard until the task force adopts it; a second format every scanner learns; five names someone must govern; the names are placeholders.
- **X: a DIDComm v2.1 out-of-band invitation with no attachment.** **Pros:** a published container; Credo and DIDComm scanners parse it; `from`, `id`, `expires_time` already exist. **Cons, verified or read from code:** (1) on receipt Credo saves a receiver out-of-band record and creates a connection, with a `did:peer:2` of its own for a v2 invitation, before looking at the goal (`DidCommOutOfBandApi.receiveInvitation`, `DidCommConnectionsApi.acceptOutOfBandInvitation` with handshake protocol `None`, `createPeerDidForV2OOB`; read from `node_modules`, not run), so the Keyring router must intercept it first; (2) the base64url JSON is verbose (about 400 to 550 characters) and needs strict JSON with duplicate-member detection; (3) `goal_code` is not namespaced as DIDComm asks: "goal codes defined outside of this spec MUST use Reverse Domain Name Notation" (DIDComm v2.1, Goal Codes, read in the saved text), and a Type URI is not that form. The earlier note that DIDComm tooling "may not expect a URI there" is replaced by this sentence.
- **Legacy `{vta_did, callback_url}`.** Stays version 0 (the contact is `vta_did`, the callback is the endpoint and the secret in one string).
- **Recommendation.** Y, proposed as a profile, with X as the alternative if the task force prefers a standard container. The deciding facts are the DIDComm side effect and the goal-code rule, both checked above; the Trust Tasks view on a profile is still needed.

### WP4 — login is not scanner-only; biometric at claim and at every approval (B3, B4)

- **Pros.** Allowing camera links keeps the generic-camera requirement; a link refused by Keyring would do nothing against a relay (RFC 8628 section 5.4). The mitigations are the ones RFC 10027 section 6.1 lists (short-lived code, number matching as request binding, user authentication) plus an inviter-signed requester screen.
- **Cons.** Without proximity a relay attacker who gets a victim to scan and approve a code still succeeds if the victim does not read the screen; number matching and the signed screen depend on the person noticing. Proximity is the stronger control: RFC 10027 section 6.1.1 says proximity-enforced flows "are more resistant to CDCP attacks", and CTAP 2.2 hybrid fixes a BLE advertisement. Keyring has no proximity transport, so it is a later version.
- **Recommendation.** As accepted: no scanner-only rule now; proximity scheduled with K4's later versions.

### WP5 — admin-side revocation of login identities does not block (F5)

- **Pros.** The Farm's login identity is separate from the VTA's admin key, which the Farm owner reply says is permanent once accepted with no recovery, so a Farm-side revoke of the login identity would not restore anything about the VTA. Self-service deletion exists. Not blocking keeps Phase 1 moving. **Cons.** A lost or stolen phone's login identity stays valid at the Farm until the person deletes it from another device, which needs one; an operator cannot revoke it.
- **Recommendation.** As accepted, and ask the Farm for admin revoke in the same conversation as the re-registration path (WP8a), so both are one request.

### Transport: why it is agreed from the inviter's DID document (new spec section 6.2.1; T7)

**Rationale.**

1. **The presenting screen is usually not the endpoint.** A Farm or portal web page draws the code; the service that answers is elsewhere. So the trigger names an inviter DID and the DID document says how to reach the service.
2. **The wallet chooses by its own preference** among the services it implements. DIDComm's `accept` cannot do this job: it is "an array of media types in the order of preference for sending a message to the endpoint", an attribute of one DIDComm service (verified in the saved DIDComm text). DIDComm also says the order of endpoints inside one `DIDCommMessaging` service "SHOULD indicate the DID Document owner's preference", which ranks endpoints within a service and not one service against another. **How DID Core or the upstream Trust Tasks documents rank several services in one document is not verified** (I read the https binding's section 6.2, which says to match on `type` and not `id`, and found no ranking rule), so the wallet's preference decides rather than document order. **Option not taken:** "first supported service in document order" (the previous spec rule): it lets the inviter's document steer a wallet toward a binding the wallet ranks lower for its own reasons, and the order of a JSON array is not something DID Core assigns meaning to (unverified).
3. **A defined no-common-transport outcome**, shown as "This service can't be reached from your wallet.", sending nothing. **Why:** without a named outcome a wallet falls back to something it was not told to use (the generic connection handler, an endpoint from the text), which is exactly what the rule against text-supplied endpoints exists to prevent. It is a fifth UI message, not a reason that tells an attacker which field failed: it arises after the trigger is accepted, from a document the inviter published.
4. **Same binding for the request and the reply**, so the exchange cannot be split across a binding the wallet did not choose.
5. **An advisory transport hint** (`tp`) lets an inviter that prefers one binding say so, without gaining any power: it orders choices, never adds a candidate, never makes an endpoint acceptable, and a wallet may ignore it. **Pros:** an inviter whose HTTPS service is cheaper than its DIDComm one can say so. **Cons:** a fifth name to govern (Y), and a hint nobody honours is noise; hence advisory and T7 left open on whether it may break ties.
6. **An endpoint is never taken from the trigger**, except the allow-listed legacy Farm callback (version 0). Stated as a conformance rule so a reader cannot be built to trust a text-supplied endpoint. (First written as "rejected unless it is in the DID document"; the final review, M5, showed that needs a rule for recognising an endpoint member, so an appended parameter could abort an exchange. Such members are now only ignored.)
7. **The DID document must be verifiable** (the `did:webvh` log), because the transport choice and the endpoint both come from it; an unverified document would make the document, not the text, the unauthenticated hint.
8. **Out of scope, recorded as a future profile.** The device-to-device case, where the QR holder is the endpoint and there is no server (for example the mutual-attestation ceremony anchors, "a scanned code ... a compared short authentication string", `7b6bb488`), cannot use a DID-document lookup: ISO/IEC 18013-5 device engagement lists the retrieval methods in the QR (unverified, paywalled) and CTAP 2.2 hybrid fixes a BLE advertisement plus a tunnel and puts the routing data in the QR (verified, section 11.5.1). That profile would need a `transports` list in the trigger and a proximity check. Not defined, so nothing in this version is a basis for it.

**Evidence.** `TrustTaskHTTPS` and its matching rule and `https:` endpoint form: `bindings/https/0.2` and `0.3` section 6.2 (verified at `origin/main`). `DIDCommMessaging`: named by the `0.3` text as the type the DIDComm binding resolves. `TSPTransport`: **not** a verified service type; the TSP binding resolves a VID "through TSP's own mechanism" and the `tsp/0.1` text names no DID-document service type, so the spec reserves the name and defines no behaviour for it. The v2 accept-side behaviour of Credo is read from code, not run.

### C. Reasoning chains for the design decisions

**Why a DIDComm out-of-band invitation is the container.** The direction was to be transport-agnostic like Trust Tasks and to use standards as far as possible. (1) The bespoke `keyring://<flow>?v=&crit=` envelope (F7) meant every scanner learns another format; the upstream sibling `cierge-pair://` in `vta-mobile-agent-ios` shows the cost of many bespoke schemes. (2) OpenID4VCI/VP have a Credential Offer and a request by value or reference (`credential_offer`/`credential_offer_uri`, `request_uri`), but they are issuance and presentation protocols; a pool claim and a login pairing are neither, and the upstream VTC already uses the OID4VCI offer for invitations, so a second use would blur which it is. (3) TSP has no invitation format at all (its text puts out-of-band introduction out of scope). (4) The DIDComm v2.1 OOB invitation is generic: `from` is a DID whose document says how to reach the inviter, so the wire is not in the text; `goal_code` names a flow; `attachments` carry a Trust Task document; the URL form has a by-value and a by-reference variant; and Keyring already routes v1 OOB through Credo. Costs accepted: `accept` cannot say "reply over HTTPS", the spec gives no QR byte limit, and its privacy guidance conflicts with a bearer secret (F10). Sources: DIDComm v2.1 (above), TSP Rev 3, OID4VCI 1.0 s4.1.

**Why `goal_code` plus Trust Task type IRI versioning.** DIDComm makes `goal_code` optional and "self-attested", so the profile requires it and uses it as the flow registry; it selects behaviour and proves nothing. Rather than invent a link version and a critical-parameter list, the version comes from the Trust Task Type URI `<authority>/spec/<slug>/<MAJOR.MINOR>` (framework s5.2, s6.1): MINOR additive, an unknown MAJOR refused with `unsupportedVersion`, MAJOR 0 a draft whose MINOR may break. Exact string comparison (s5.2 non-normative paragraph) keeps the reader trivial, and a private form or a different authority is simply a different task. Sources: DIDComm "Out Of Band Messages"; `SPEC.md` s5.2, s6.1.

**Why the Farm's claim-service DID is `from`.** `from` is "REQUIRED for OOB usage" and is the DID later interactions use. A parked slot is not running, so it cannot serve a DID document or answer; the Farm's always-on claim service can. The slot's DID is therefore a subject in the attachment. This is an **inference**: no Farm design was available. It also gives the consumer an allow-list point (the `from` domain) in place of the old callback-URL list, and removes the endpoint from the text (the endpoint comes from the DID document's service entry). Sources: DIDComm "from"; the legacy format's callback model (`agentHostConnection.ts` header).

**Why `https` is primary.** DIDComm wants the URL to "return human readable instructions when loaded in a browser", which needs an https page. RFC 8252 s7.2 says a claimed `https` URI "SHOULD" be preferred because the operating system establishes which app receives it; s7.1 asks a private-use scheme to be a reverse domain name, and `keyring` is not, and another app can register it. So `keyring://` is only an alias carrying the same host, path and query, and nothing safe depends on the alias reaching only Keyring. Sources: RFC 8252 s7.1, s7.2 (<https://www.rfc-editor.org/rfc/rfc8252>); DIDComm.

**Why `crit` was dropped.** The bespoke link had a reserved `crit` list so an old reader would reject a critical extension it did not know, copying RFC 7515 s4.1.11 ("If any of the listed extension Header Parameters are not understood ... then the JWS is invalid"). In JOSE `crit` is inside the signed header, so an attacker cannot strip it; our link was unsigned, so `crit` was advisory against an active attacker. The invitation already has the mechanisms it approximated: attachments are "in order of preference" with one chosen, an unknown MAJOR is refused by the Trust Task rule, and an unknown `goal_code` is the update outcome. Sources: RFC 7515 s4.1.11 (<https://www.rfc-editor.org/rfc/rfc7515>); F7, F8.

**Why `vta/enrol` stays lab-only.** The enrolment offer carries an EdDSA proof of the submitted key and a code that both screens derive and compare before an operator grants (`bifold/packages/trust-tasks/src/enrolment/offer.ts`); the Farm claim has neither. That is the right shape for a self-hosted or lab operator who grants by hand. It is in use by the lab enrolment page and its tests, `vtiLinks.ts`, `TabStack.tsx` and the deep-link tests. It has no `_oob`/`_oobid` parameter, so it is `not-ours` in the spec and unchanged. What was retired is U1 as a request to the Farm, so the Farm builds one payload. Sources: this checkout; `own_agent_subtask.md` U1; F4.

**Why `https` by reference (`_oobid`) is allow-listed.** It is the one place a text makes the phone contact a host. The check is applied before the GET, with no redirects, on a host list that is configuration and not part of any link. `allowedHostOf` has defects (section E), so the host check is a K1 follow-up.

**Why the claim-authorisation decision is open.** See F10.
