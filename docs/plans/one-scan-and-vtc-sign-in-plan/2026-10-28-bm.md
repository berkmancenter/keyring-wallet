# 2026-10-28 — BM

Companion to [`../one-scan-and-vtc-sign-in-plan.md`](../one-scan-and-vtc-sign-in-plan.md) and to the spec [`docs/specs/keyring-qr-and-links.md`](../../specs/keyring-qr-and-links.md). It follows [`2026-10-10-bm.md`](./2026-10-10-bm.md). One working session.

**What this session settled.** A contributor on the VTI specification thread asked whether the trigger link design considered DIDComm's `_oob` query parameter and its `_oobid` short form, which would let a VCALM QR code bridge to DIDComm out-of-band; a second question asked whether the answer means a trigger link is always a new kind of QR code that no existing DIDComm scanner supports. The answers are recorded here. The spec, the annex and the plan were not changed: nothing below is a requirement, and the rules these positions explain are already in the spec.

The chapter is `spec/07a-links.md`, requirements VTI-LNK-001 to 124. The merged chapter says nothing about `_oob` or `_oobid`, or about why the link is not DIDComm.** A search of the chapter for `oob`, `didcomm` and `vcalm` finds only: the scope statement that the format can carry "DIDComm, OpenID or anything else", the allowance for flows that are not Trust Tasks "such as a DIDComm or OpenID exchange", and the `data-oob-*` attributes of the sign-in page. VCALM is not mentioned.

**F3. Our own notes cover part of it.**
- The annex (section E, "Alternatives not taken") rejects a DIDComm v2.1 out-of-band invitation and its `_oobid` by-reference form, on mechanical grounds. Section D gives the reasons for the fragment and for no fetch.
- The first companion (`2026-10-08-bm.md`, D5) records that an earlier shape was a DIDComm OOB invitation carrying a Trust Task attachment with a `goal_code` registry and `_oobid`, superseded by D6.
- Not recorded anywhere before this file: the cost that existing DIDComm-only scanners will not act on a trigger link, and what mitigates it; the Trust Spanning Protocol reasoning; what survives an outage of each host; a DIDComm fallback and why it is deferred; the VCALM bridge.

**F4. `STRUCTURE.md` in the vti-spec repo is that repo's decision record.** It is working-group material, not rendered, and carries one status line for the links chapter and no decision about the link format. We did not add to it.

## Part 2. Positions

**N1. A trigger link is a new kind of code, on purpose.** It is an `https` URL with its parameters in the fragment. A scanner that understands only DIDComm `_oob` links does not act on it. We accept that cost for the reasons in N2 and N3.

**N2. The main reason is transport neutrality.** The link names whom to contact and which flow to start; each flow states its own first request. The transport comes from the contact's verified DID document, never from the link (VTI-LNK-053). This is the same direction as the rest of our work, which builds on the Trust Spanning Protocol so the stack does not depend on one transport (see the OpenVTC integration plan). A link that is a DIDComm artifact would make Trust Task, OpenID and every other flow second-class. DIDComm still fits: a flow can state a DIDComm first request.

**N3. The mechanical reasons are secondary, and apply to `_oob` as a link encoding.**
- `_oob` is in the query, which the link host, a CDN and a preview fetch receive. Parameters in the fragment are not sent (VTI-LNK-010, -011).
- `_oobid` needs an HTTP GET. A preview or mail scanner could make it, and a trigger link MUST NOT cause a fetch by reference (VTI-LNK-072).
- Credo may create a connection before it reads the goal (read from code, annex E).
- The encoding is about twice as long, and a link is capped at 251 bytes at QR level M and 177 at level Q (VTI-LNK-081).
- DIDComm says no private information should be passed by URL or QR code, and a handle is spendable.

**N4. The cost is softened three ways.**
- A plain `https` link opens in any camera or browser, and the link host's page (VTI-LNK-091) tells a person with no wallet what to do.
- Coexistence in one wallet: a text with no reserved name in the fragment is `not-ours`, and the reader passes it unchanged to its other handlers (VTI-LNK-020, -021). A wallet registers trigger links beside DIDComm OOB, and the scanner picks by inspection.
- The link can start a DIDComm exchange (N2).

**N5. What happens when a host is down.**
- *The link host:* mostly survivable. The reader parses the link locally and resolves a flow by string (VTI-LNK-041), so it fetches nothing from that host. The wallet's own scanner, pasting and an alias scheme still work. The no-wallet landing page does not, and the camera hand-off may not. The chapter itself says the camera path is not verified on real devices.
- *The inviter's DNS or site:* not survivable, by design. The reader resolves the contact's DID document afresh for each exchange and sends nothing if it cannot verify it (VTI-LNK-052, -053). Route B's did-configuration fetch fails closed with `domain-not-linked` (VTI-LNK-123). The link format adds no single point of failure beyond the inviter's own infrastructure.

**N6. A DIDComm fallback for readers that only understand `_oob` is possible and is deferred.** Three ways, in the order we would try them:
- *Two codes on one page* (a trigger-link QR beside a DIDComm QR). No spec change.
- *A DIDComm service in the contact's DID document.* A reader that understands trigger links already picks a binding it supports (VTI-LNK-053). This is a fallback for the exchange, not for the scan.
- *One code with `?_oob=` in the query and the trigger parameters in the fragment.* Trigger readers ignore the query (VTI-LNK-011). It stays a separate optional extension profile outside the core format. It needs: no spendable handle in the fallback, because the query is visible to the host; a separate code if it does not fit the byte cap; and trigger-first precedence in a reader that supports both. A DIDComm-only reader would also do less with it than a trigger reader, because it does not know the flow.

We offered to work through it with the asker if they think it important.

**N7. The VCALM bridge is not evaluated.** The asker's point is that VCALM's existing affordances bridge a QR code to DIDComm OOB through `_oob` and `_oobid`. Our reply says the bridge sits in the flow definition: a VCALM page shows a trigger link for a flow whose first request is DIDComm. We have not read the VCALM section they linked (`#interaction-protocols-response`), so we do not claim it works and asked what the bridge needs.

**N8. Notes live here, not in the spec or annex.** Everything above is rationale, a cost or a deferred option. The spec holds the rules (`not-ours`, resolve afresh, fail closed) and does not need them restated. The annex is unchanged. The cost of keeping them out of the chapter is that the people asking read the merged vti-spec chapter and cannot see our branch, so a question like this one is answered by linking to this file until the chapter carries a rationale of its own. We are not proposing that chapter change now.

## Part 3. Not verified

- Coexistence in one scanner is what the chapter specifies. No phone has been tested (annex C, tests not run).
- How current DIDComm scanners treat an `https` URL that also has a fragment is not checked. N6's third option assumes they read only the query.
- The camera hand-off during a link-host outage depends on how each operating system caches association files; not checked.
- The Trust Spanning Protocol framing in N2 is taken from the integration plan's stance that TSP is the transport; its wording was not re-read this session.
- The VCALM section was not read (N7).
