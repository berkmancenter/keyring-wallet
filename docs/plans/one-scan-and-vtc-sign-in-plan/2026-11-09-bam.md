## Part 1. Positions applied or withdrawn

**A1. Supersedes the "differs from the VTI draft" notes (spec section 5 rules 4 and 7, the status line, plan section 1.2 and 1.3).** Those notes recorded a change this branch proposed on PR 58: that the Trust Task first request be scoped to VTI's flows, with the fresh-key rule general. The chapter was merged with exactly that split. VTI-LNK-054 now binds every flow in the registry to a Trust Task first request signed by a fresh Ed25519 `did:key`, with the handle as `parentThreadId`, and VTI-LNK-057 holds the general rule that a first request is signed by a key made for the exchange unless the flow defines an identifier the person chooses. The notes are deleted from the spec and plan because they now describe nothing. Spec section 8.1 cites 054 for the Trust Task first request and 057 for the general rule. Applied.

**A2. Supersedes the "may connect before reading the goal" claim (annex E, the Trust Over IP proposal).** [`2026-10-29-bm.md`](./2026-10-29-bm.md) F2 already withdrew it: it was read from a pull-request build of Credo (`0.7.1-pr-2704`) carrying a Keyring-local patch. The design note's statement is the supportable one: `goal_code` is optional and "a self-attested code the receiver may want to display to the user or use in automatically deciding what to do", and neither released Credo (0.7.4, 0.6.3) reads a DIDComm v2 invitation. The annex and the proposal now say only that, and agree with each other. Applied; F2 had left the spec files unchanged.

**A3. Where this branch stands against `dtgwg-vti-spec` issue 86.** PR 354 predates issue 86, which is open and proposes a person-to-person shared-connect flow, a per-flow size budget and a registry entry. Its outcomes are pending. Position: this branch specifies no shared-connect flow, no `inv` field and no `_label` field; the single 251 and 177 byte budget (VTI-LNK-081) is expected to become a budget per flow; the 300 second expiry rule stays scoped to the flows that state it; and the fresh `did:key` rule stays scoped to the registry's flows, with a shared-connect flow's need for an identifier the person already uses left open. Rejected alternative: stating the fresh-key rule for all flows. VTI-LNK-057 already allows a flow to define an identifier the person chooses, and issue 86 has not said whether its flow does.

**A4. Terms.** "Trigger link" is the normative term. "One-scan" is informal shorthand. `keyring://vti/invitation` is not a trigger link. "Consumer" in this branch is the chapter's "reader". Spec section 8.1 no longer calls the invitation the exchange that `parentThreadId` names: the exchange is the pending one the handle names. The plan's rename ask for the `auth/oob` family (`auth/handoff`) is our proposal and the name is unchanged upstream, where the design note's "Not to be confused: `auth/oob`" section says it is not DIDComm's out-of-band protocol.
