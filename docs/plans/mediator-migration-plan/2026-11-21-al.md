# 2026-11-21 — M3 drafted: Keyring's own Affinidi mediator as the wallet mailbox

*Companion to [`m3_affinidi_mailbox_subtask.md`](./m3_affinidi_mailbox_subtask.md). Parent: the mediator migration
plan on branch `docs/mediator-migration-plan` at `8a75531b`.*

## Decisions taken before this draft (product owner, 2026-11-20 and 21)

- The wallet-to-wallet v2 route is one mailbox per phone at an Affinidi mediator; contacts who compare notes can tell
  they reach the same phone, and that is accepted.
- The mailbox is hosted on **Keyring's own Affinidi mediator**, not the VTA Farm's shared one, which refuses public
  sign-in and is not Keyring's to load. The app's mailbox setting stays blank until it is up.
- **Testers first:** the mailbox opens only with the Developer switch on; the build after load is measured opens it
  for everyone and drops the switch.

## Findings

### F1. The deployed mediator lacks the Redis-resubscribe fix; `c0a69f1e` has it

`affinidi-tdk-rs` `878301bd` (2026-10-02, "Redis streaming resubscribes after a Redis restart") is not an ancestor of
the deployed `55580615` and is an ancestor of `c0a69f1e` (checked with `git merge-base --is-ancestor` in the pinned
clone). `c0a69f1e` is also the build the local lab ran on 2026-11-20 (two- and three-wallet rows, store-and-forward,
the wake gap). So the draft names it as the mailbox image, rather than the deployed version.

### F2. The parent plan's D1 ACL bullet cites the upstream sample, not the deployment

D1 says the default `global_acl_default="DENY_ALL,…"` "doesn't grant `RECEIVE_FORWARDED`", citing the upstream
sample's line numbers. The deployed `mediator.toml:92` already grants `RECEIVE_FORWARDED` (and `LOCAL`,
`SEND_MESSAGES`, `RECEIVE_MESSAGES`). What keeps phones out of the deployed mediator is `explicit_allow` (no account,
no sign-in) and Caddy's 403 on public `/authenticate`. The subtask plan's §3.3 is written from the deployment.

### F3. Why a separate instance

Opening sign-in is a posture change for the gateway's mediator, whose comments are explicit that no stranger can hold
a session there (`Caddyfile:22-28`, `mediator.toml:22-25`). And the gateway's VM is an e2-small shared by four
services in 2 GB; phone mail would put the push path's memory behind the mailbox's queue. The parent's extension notes
and its 2026-10-25 review both leaned the same way. The one-VM option stays written down with its conditions.

### F4. The wake lead is a lead

Measured locally on 2026-11-20: storing for an offline wallet fires `RECEIVE_Q:xadd` keyspace events on the
mediator's own Redis, and the mediator itself calls nothing. That makes W5 buildable, not proven: it has not met the
real gateway path, and it reads Redis key names that are internal to the mediator. The subtask plan therefore lists
W4 and W1 beside it, and makes S6's three checks, against the real gateway, the gate.

### F5. DIDComm v1 is an opt-in build feature

`src/messages/v1_mediation.rs` (Coordinate Mediation 1.0, Pickup 2.0) is present at `55580615` and `c0a69f1e`,
behind the `didcomm-v1` cargo feature and a configuration switch defaulting off. The deployed image is built with
`--features tsp,secrets-aws`, so it does not serve v1. The build features live in this repository
(`deploy/keyring-messaging/mediator/Dockerfile`), not the infra repository, which only pins this repository's
`deploy/keyring-messaging/` by `package_ref`.

### F6. Monitoring and the runbook

Nothing probes the deployed mediator, and its update runbook has never been run (infra `docs/operations.md:160-181`;
`docs/gateway-operator-guide.md:1767-1769`). The mailbox host cannot inherit either as-is, so the subtask plan specifies
its own checks and treats its first deploy as the runbook's first run.

### F7. Rollback after the tester build is M4-shaped

Only the mailbox's own outbound transport (bifold `walletMailbox.ts`, the `did` scheme) carries a send to a contact
made through the mailbox, and it is registered only when a mailbox opens (bifold `7dd8bf0de`). So with the switch off
or the mediator setting blank, those contacts cannot be sent to, and their incoming mail waits at the mediator. The
parent's M3 rollback row rests on "no shipped app uses it yet", which stops being true at S7. The subtask plan
therefore takes the parent's M4 standard for rollback after S7 (no silent loss; "waiting for the new message
service"), adds S6b to build and test that display before S7, and keeps the mailbox host up after a rollback while
testers hold such contacts.

### F8. Refusal at the hard cap is open, not known

The parent's M3b row asks for refusal versus drop to be defined at the hard cap, with a tested refusal path and a
user-visible sender error. The first draft of the subtask plan stated refusal as fact; it is now S5b, measured.
