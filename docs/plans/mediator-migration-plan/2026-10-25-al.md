# 2026-10-25 — Response to the extension review, rollback, and the infrastructure blocker (al)

**Plan:** [`../mediator-migration-plan.md`](../mediator-migration-plan.md).
**Answers:** the 2026-10-21 review of this PR. That review is the extension commit `7d35fe49`, its notes in [`2026-10-21-bam-extension-notes.md`](./2026-10-21-bam-extension-notes.md), the PR comment, and a review marked "commented".

## 1. The extension phases are accepted

The extension phases M0a–M5b (§5.1) and their notes (E1–E16) are accepted as written. On the four points the review asked to be looked at most closely:

1. **The witness server's dependence on the Credo mediator** (M2a). Agreed. It is a real gap the draft missed: the witness in mediator mode uses Coordinate Mediation plus Pickup 2.0, which the Affinidi mediator does not offer. M2a's "verify the deployed mode, then choose an Affinidi or v2 path, or direct HTTPS" is the right order. Retiring Credo (M5) also stays gated on "no witness uses Credo" (M5a).
2. **Existing contacts at M5** (M4a, M5a). Agreed. Contacts that stay on v1 until re-invited must never be lost silently. The in-app migration flow, the dated notice and the measured "no v1 traffic" gate are what make M5 safe.
3. **Rollback and custody for M1** (M1a, M2c). Agreed. This companion goes further and supplies the per-phase rollback table M2c asks for, now §5.2. See part 2.
4. **Mailbox placement** (M3a). Still open; M2c decides it. The leaning here is a **separate mediator instance** rather than the gateway VM, for three reasons:
   - an outage of the phone mailbox should not also stop approvals and wakes;
   - the gateway VM already carries the push gateway and its Redis;
   - the Credo mediator on the current host has been memory-limited and restarted under load recently, which shows how much a mailbox's load varies.

   The decision stays with M2c, recorded with a date.

## 2. Why the plan now has a rollback section (§5.2)

**What the draft had.** It had rollback pieces:

- M1's "rollback (DNS back) is tested";
- M4a's remote flag or Credo fallback;
- M5's "after a release cycle with no rollback";
- M5b's backup retention.

**What was missing.** No single place said:

- what **triggers** a rollback;
- **who** may start one;
- what happens to **messages caught mid-switch**;
- that **after M5 there is no way back** except restoring backups.

**What §5.2 adds:**

- **Triggers:**
  - the privacy control failing;
  - the positive wake check failing for more than 10% of wakes in an hour;
  - a lost message between two online test phones;
  - restarts or errors above the pre-switch baseline;
  - tester reports above the pre-switch baseline within 24 hours.
- **Decision rights:** the infrastructure maintainer for infra-only phases, the product owner for app phases. Each rollback is recorded the same day.
- **Rules that keep rollback possible:**
  - the old side is frozen, never destroyed, until the rollback window ends;
  - cut over at a measured low point of queue depth;
  - the old side is drained, never discarded;
  - each rollback is rehearsed before the forward switch.
- **A per-phase table:** how to roll back, what can be lost, the rollback window, and whether it is rehearsed. M4 now states what happens to contacts made on v2 during M4 if the new mailbox is down: their messages wait there and the app shows them as waiting, rather than losing them silently.

The thresholds (10%, 5 minutes, 24 hours) are starting values, to be confirmed at M2c.

## 3. Why the migration is blocked on the infrastructure deployment (§6)

**The change.** No phase of this plan starts until the managed infrastructure's wallet-host and short-link change is deployed. That is infrastructure repository #20, merged 2026-10-24.

**Why it is not deployed yet.** Its apply, the VM sync and the DNS change can only be done by the infrastructure maintainer.

**Why the migration waits for it:**

- **One change at a time.** Both changes run on the same managed infrastructure, are carried out by the same maintainer, and include a DNS cut-over. Running them one at a time keeps each change's rollback simple, and keeps any fault attributable to one change.
- **A dependency.** Short links and the wallet host are part of how invitations reach new phones. The migration's own tests (M2's QR and share-link invite) depend on them working.

**Supersedes:** the draft's §6, which listed only M1's scheduling against the infrastructure maintainer.

## 4. Why the new mediator's service order is checked (M3d)

**Concluded:** before phones move, check the order in which the new mediator lists its services. If WebSocket comes first or is the only transport, measure a large pickup frame on both platforms.

**Evidence,** from the rich messaging plan's Step 0 measurement (`rich-messaging-plan/2026-10-25-al.md` §9):

- **Pickup:** the wallet uses PickUp v2 polling. Credo sets a transport priority only for implicit pickup, and the app sets none, so a phone uses the mediator's services in their listed order.
- **Today:** the Credo mediator lists HTTPS first, so pickup and sending go over HTTPS. A ten-photo pickup arrives as one 6.2 MB HTTP response, measured.
- **On a new mediator:** a mediator that lists WSS first, or serves only WebSocket, moves both to WebSocket with no app change. A pickup frame of several MB then reaches the phone's WebSocket client (OkHttp on Android, SocketRocket on iOS), which has not been tested at that size.

**Where it sits:** an extension phase in M3, before M4, beside the other checks that must pass before phones move.

## 5. Why a `MEDIATOR_URL` change waits for the single-flight agent start (§6)

**The race,** READ at wallet `origin/main` 1efd90b0, bifold 37877716:

1. When the stored mediator can't be used, agent start logs "Stored mediator can't be used (…); using this build's mediator and resetting the stored one" and dispatches `RESET_MEDIATORS` (`app/src/hooks/useBCAgentSetup.ts:297–299`). It can't be used when it is missing, unreadable, retired, or not offered, meaning not the build's `MEDIATOR_URL` and not one the person added (`app/src/utils/mediatorPreference.ts:80`).
2. The reset writes `selectedMediator` and `availableMediators` (bifold `contexts/reducers/store.ts:798`). Those are dependencies of `initializeAgent` (`useBCAgentSetup.ts:384`), so `initializeAgent` is rebuilt mid-start.
3. bifold `navigators/OnboardingStack.tsx:104–106` builds Splash as a `useCallback` over `initializeAgent`. The navigator remounts it, and the fresh Splash's `initializing` guard (`app/src/screens/Splash.tsx:74,85`) is false, so it starts the agent again.

**Seen on a device.** A lab Release build with no `MEDIATOR_URL`, where the mediator is "missing" on every start, never opened. At its first agent start it began three starts within 120 ms on one Askar store. Some failed with `no such table: config`, and the starts looped until Android's low-memory killer killed the app, about 16 s in. In the two kept logs:

- every failure fell in the store's creation, the first second or so;
- every later open succeeded, while up to 13 other starts were in flight.

That build loops because it resets on every start. A store build resets once.

**Who it reaches:**

- **A fresh store install: not reached.** `selectedMediator` starts as the build's own `MEDIATOR_URL` (bifold `contexts/store.tsx:62`). A 271 Android store build on a fresh emulator logged one start.
- **Phones whose stored mediator was retired or unreadable: reached today.**
- **Every existing phone at a store build that changes `MEDIATOR_URL`: reached once, on its first start after the change** (INFERRED; not yet seen on a device). That is one extra concurrent start, not a loop:
  - It opens an existing store, which the lab logs show succeeding.
  - It provisions mediation at the same time as the first start, the path 833e759 (2026-09-14) recovered from after it bricked fresh wallets. The credo patch's recovery (now in the 0.7.1 patch, guarded by `mediatorPickupStrategy.guard.test.ts`) makes it a 15 s wait plus a one-time retry today, not a brick.

**What this plan takes from it.** Wallet #631 makes agent start single-flight: a call made while a start is in flight waits for it, so the path is closed by construction rather than by recovery. The start in flight already uses the build's mediator (`mediatorPreference.ts:104`, `useBCAgentSetup.ts:301`), so joining it is correct. M4 changes the mailbox config, so it doesn't ship without #631 and a device check of the upgrade path (§6). Nothing in the plan is superseded.

## 6. The Credo mediator's memory growth is a native leak in Askar's JavaScript wrapper

**Question.** The testers' Credo mediator grows by about 40–80 KB of RSS per inbound message, is flat when idle, and passed 1 GiB against a 768 MB V8 heap cap. The WebSocket `socketIds` patch (credo-ts fbb6517d) changed nothing. Why, and what fixes it?

**Facts about the running service** (READ, live state 2026-10-25 16:10–16:43Z, read-only):

- Image `ghcr.io/openwallet-foundation/didcomm-mediator-credo/mediator:375518d`, digest `sha256:4e0cbbd2…7976`, Node 22.21.1, Debian 12, glibc 2.36.
- Credo `@credo-ts/{core,node,askar,didcomm}` 0.6.0; `@openwallet-foundation/askar-nodejs` and `askar-shared` 0.4.3.
- Askar runs on its default **SQLite** inside the container. Only the pickup queue is Postgres, with one idle connection and no pile-up.
- File handles (~30) and threads (~18–20) are flat. Only 2 sockets are open, so traffic is HTTP polls, which is why the WS patch could not help.
- Transparent huge pages are `always` on the host. AnonHugePages was 305–356 MB of 441–500 MB anonymous memory.
- jemalloc ships in the image but is not loaded: `LD_PRELOAD`, `MALLOC_CONF` and `MALLOC_ARENA_MAX` are empty, and `/proc/1/maps` has no jemalloc mapping.
- Growth: RssAnon +59 MB in about 33 minutes, over roughly 1,300 inbound messages (about 45 KB each), 97% of them `messagepickup/2.0/status-request`.

**Finding 1 — the cause: `Scan` never frees its native result lists** (READ):

- In askar-shared 0.4.3, `Scan.forEachRow` takes a native `EntryList` from each `scanNext` and frees only the scan handle (`build/store/Scan.js:44-57`).
- On the Rust side, `askar_scan_next` allocates the list with `Arc::into_raw` (askar `src/ffi/store.rs:667` @ v0.4.6). Only `askar_entry_list_free` releases it; `askar_scan_free` does not (`store.rs:687-698`).
- No `FinalizationRegistry` exists anywhere in askar-shared or askar-nodejs. `Session.fetch` and `fetchAll` do free their lists (`build/store/Session.js:35, :54`), so only queries leak.
- Credo 0.6.0's `AskarStorageService.findByQuery` is exactly this `Scan.fetchAll` (`packages/askar/src/storage/AskarStorageService.ts:185`). Every query therefore keeps its whole decrypted result set (values, tags, names) in native memory for the life of the process.
- **Unfixed upstream:**
  - identical code in askar-shared 0.6.1 (latest stable) and 0.7.0-alpha-20261023221824;
  - Credo 0.7.1 still calls `new Scan` in `findByQuery`.
    An image or Credo upgrade does not fix it.

**Finding 2 — a smaller leak: C strings.** Askar's string getters (`askar_entry_list_get_name`, `get_tags`, `askar_key_get_algorithm`, JWK getters) allocate `CString`s, and the 0.4.3 Node wrapper has no `askar_string_free` binding. This is READ in source and has not been measured separately.

**Finding 3 — an amplifier, not the cause.** glibc malloc on a host with huge pages set to `always` keeps freed native memory resident. In 02's samples, AnonHugePages rises in steps behind RssAnon rather than driving it (READ, 16:28→16:43Z).

**Measurement** (MEASURED on the MacBook, askar-nodejs/askar-shared 0.4.3 on SQLite, Node 20). The metric is native memory = RSS − V8 heapTotal, with a full GC at start and end. Script: `scan-leak.mjs`, quoted in the PR description.

| Case                                                         | Native memory                    | Kept per query        |
| ------------------------------------------------------------ | -------------------------------- | --------------------- |
| Leaky `Scan`, one 3 KB record, 20,000 queries                | 92.1 → 183.1 MiB, linear         | about 5.2 KiB         |
| `session.fetchAll`, same record                              | 83.8 → 102.3 MiB, decelerating   | about 1 KiB, settling |
| Leaky `Scan`, one 100 KB record, 3,000 queries               | 212 → 327 → 441 MiB              | about 121 KiB         |
| `Scan` with each list freed, 100 KB, 9,000 queries (control) | 95.5 → 100.4 → 101.3 → 104.6 MiB | flat                  |

A caveat on the harness: askar-nodejs 0.4.3's ffi-napi binding crashed or hung at random on macOS with Node 20 (`Napi::Error`, or exit 13 under forced GC), in leaky and freed modes alike. Only completed runs are reported. That is a further reason to move the mediator to askar-nodejs 0.6.x (koffi) eventually.

**Per message** (INFERRED from code; an instrumented count is in progress on a local mediator). An inbound status-request runs roughly 6–10 `findByQuery` calls:

- unpack finds our DID by recipient key (`DidCommEnvelopeService.ts:317`);
- the connection lookup by keys runs two DID lookups and one or two connection lookups (`DidCommMessageReceiver.ts:224`, `DidCommConnectionService.ts:823-854`);
- packing the reply resolves DIDs again.

At 3–8 KB records that is about 30–100 KB per message, which matches production.

**The app has the same leak** (READ; a device measurement is booked):

- The wallet resolves askar-shared 0.6.0 and askar-react-native 0.6.0, with the same `Scan.js`.
- The React Native binding returns an `EntryListHandle` to JS as a bare pointer string (`cpp/turboModuleUtility.cpp:211-216`), with no destructor or finalizer.
- An open Keyring polls about once a second and runs findByQuery on each round trip, so it should accumulate native memory continuously while open (INFERRED: order of tens of MB an hour).

**Fix options, ranked by cost and risk:**

1. **Free each list in `Scan.forEachRow`.** This is a try/finally around the row loop that calls `list.handle.free()`. Proven locally (the table's control).
   - _Mediator:_ a read-only bind-mounted `Scan.js`, the same way as the existing three patches, with no rebuild. It still needs proof inside the production image before it is applied.
   - _App:_ a `.yarn/patches` patch of askar-shared 0.6.0 (wallet branch `fix/askar-scan-free-entry-list`). `tier.mjs` classes it **store** by policy, since dependency patches need a native fingerprint check. An equivalent startup shim in bifold source, replacing `Scan.prototype.forEachRow`, would be OTA-tier.
   - _Upstream:_ a PR to askar-wrapper-javascript; drafted, not posted.
2. **jemalloc through `LD_PRELOAD` plus `MALLOC_CONF=background_thread:true,metadata_thp:auto`,** as the upstream README recommends (mediator PR #67). It reduces fragmentation under huge pages but does not stop the leak. A config change and a restart.
3. **Slower polling (wallet #635).** It cuts the fuel by about 60–80% in both the mediator and the app, but fixes neither.
4. **An image or Credo upgrade does not help:** the bug is in every Askar wrapper release.

**What this means for the migration.** The Affinidi mediator removes Credo and Askar from the mailbox, so the mediator half of this leak ends at M5. The app half does not: it runs in every Keyring phone whatever the mediator, so it needs its own fix independent of this plan. Until M5, the mediator patch with jemalloc is the bridge. Nothing in the plan is superseded.
