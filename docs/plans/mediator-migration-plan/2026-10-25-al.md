## 1. The extension phases are accepted

The extension phases M0a–M5b (§5.1) and their notes (E1–E16) are accepted as written. On the four points the review asked to be looked at most closely:

1. **The witness server's dependence on the Credo mediator** (M2a). Agreed. It is a real gap the draft missed: the witness in mediator mode uses Coordinate Mediation plus Pickup 2.0, which the Affinidi mediator does not offer. M2a's "verify the deployed mode, then choose an Affinidi or v2 path, or direct HTTPS" is the right order. Retiring Credo (M5) also stays gated on "no witness uses Credo" (M5a).
2. **Existing contacts at M5** (M4a, M5a). Agreed. Contacts that stay on v1 until re-invited must never be lost silently. The in-app migration flow, the dated notice and the measured "no v1 traffic" gate are what make M5 safe.
3. **Rollback and custody for M1** (M1a, M2c). Agreed. This companion goes further and supplies the per-phase rollback table M2c asks for, now §5.2. See part 2.
4. **Mailbox placement** (M3a). Still open; M2c decides it. The leaning here is a **separate mediator instance** rather than the gateway VM, for three reasons:

   - an outage of the phone mailbox should not also stop approvals and wakes;
   - the gateway VM already carries the push gateway and its Redis;
   - the Credo mediator on the current host has been memory-limited and restarted under load recently, which shows how much a mailbox's load varies.

   The decision stays with M2c, recorded with a date.

## 2. Why the plan now has a rollback section (§5.2)

**What the draft had.** It had rollback pieces:

- M1's "rollback (DNS back) is tested";
- M4a's remote flag or Credo fallback;
- M5's "after a release cycle with no rollback";
- M5b's backup retention.

**What was missing.** No single place said:

- what **triggers** a rollback;
- **who** may start one;
- what happens to **messages caught mid-switch**;
- that **after M5 there is no way back** except restoring backups.

**What §5.2 adds:**

- **Triggers:**
  - the privacy control failing;
  - the positive wake check failing for more than 10% of wakes in an hour;
  - a lost message between two online test phones;
  - restarts or errors above the pre-switch baseline;
  - tester reports above the pre-switch baseline within 24 hours.
- **Decision rights:** the infrastructure maintainer for infra-only phases, the product owner for app phases. Each rollback is recorded the same day.
- **Rules that keep rollback possible:**
  - the old side is frozen, never destroyed, until the rollback window ends;
  - cut over at a measured low point of queue depth;
  - the old side is drained, never discarded;
  - each rollback is rehearsed before the forward switch.
- **A per-phase table:** how to roll back, what can be lost, the rollback window, and whether it is rehearsed. M4 now states what happens to contacts made on v2 during M4 if the new mailbox is down: their messages wait there and the app shows them as waiting, rather than losing them silently.

The thresholds (10%, 5 minutes, 24 hours) are starting values, to be confirmed at M2c.

## 3. Why the migration is blocked on the infrastructure deployment (§6)

**The change.** No phase of this plan starts until the managed infrastructure's wallet-host and short-link change is deployed. That is infrastructure repository #20, merged 2026-10-24.

**Why it is not deployed yet.** Its apply, the VM sync and the DNS change can only be done by the infrastructure maintainer.

**Why the migration waits for it:**

- **One change at a time.** Both changes run on the same managed infrastructure, are carried out by the same maintainer, and include a DNS cut-over. Running them one at a time keeps each change's rollback simple, and keeps any fault attributable to one change.
- **A dependency.** Short links and the wallet host are part of how invitations reach new phones. The migration's own tests (M2's QR and share-link invite) depend on them working.

**Supersedes:** the draft's §6, which listed only M1's scheduling against the infrastructure maintainer.

## 4. Why the new mediator's service order is checked (M3d)

**Concluded:** before phones move, check the order in which the new mediator lists its services. If WebSocket comes first or is the only transport, measure a large pickup frame on both platforms.

**Evidence,** from the rich messaging plan's Step 0 measurement (`rich-messaging-plan/2026-10-25-al.md` §9):

- **Pickup:** the wallet uses PickUp v2 polling. Credo sets a transport priority only for implicit pickup, and the app sets none, so a phone uses the mediator's services in their listed order.
- **Today:** the Credo mediator lists HTTPS first, so pickup and sending go over HTTPS. A ten-photo pickup arrives as one 6.2 MB HTTP response, measured.
- **On a new mediator:** a mediator that lists WSS first, or serves only WebSocket, moves both to WebSocket with no app change. A pickup frame of several MB then reaches the phone's WebSocket client (OkHttp on Android, SocketRocket on iOS), which has not been tested at that size.

**Where it sits:** an extension phase in M3, before M4, beside the other checks that must pass before phones move.

## 5. Why a `MEDIATOR_URL` change waits for the single-flight agent start (§6)

**The race,** READ at wallet `origin/main` 1efd90b0, bifold 37877716:

1. When the stored mediator can't be used, agent start logs "Stored mediator can't be used (…); using this build's mediator and resetting the stored one" and dispatches `RESET_MEDIATORS` (`app/src/hooks/useBCAgentSetup.ts:297–299`). It can't be used when it is missing, unreadable, retired, or not offered, meaning not the build's `MEDIATOR_URL` and not one the person added (`app/src/utils/mediatorPreference.ts:80`).
2. The reset writes `selectedMediator` and `availableMediators` (bifold `contexts/reducers/store.ts:798`). Those are dependencies of `initializeAgent` (`useBCAgentSetup.ts:384`), so `initializeAgent` is rebuilt mid-start.
3. bifold `navigators/OnboardingStack.tsx:104–106` builds Splash as a `useCallback` over `initializeAgent`. The navigator remounts it, and the fresh Splash's `initializing` guard (`app/src/screens/Splash.tsx:74,85`) is false, so it starts the agent again.

**Seen on a device.** A lab Release build with no `MEDIATOR_URL`, where the mediator is "missing" on every start, never opened. At its first agent start it began three starts within 120 ms on one Askar store. Some failed with `no such table: config`, and the starts looped until Android's low-memory killer killed the app, about 16 s in. In the two kept logs:

- every failure fell in the store's creation, the first second or so;
- every later open succeeded, while up to 13 other starts were in flight.

That build loops because it resets on every start. A store build resets once.

**Who it reaches:**

- **A fresh store install: not reached.** `selectedMediator` starts as the build's own `MEDIATOR_URL` (bifold `contexts/store.tsx:62`). A 271 Android store build on a fresh emulator logged one start.
- **Phones whose stored mediator was retired or unreadable: reached today.**
- **Every existing phone at a store build that changes `MEDIATOR_URL`: reached once, on its first start after the change** (INFERRED; not yet seen on a device). That is one extra concurrent start, not a loop:
  - It opens an existing store, which the lab logs show succeeding.
  - It provisions mediation at the same time as the first start, the path 833e759 (2026-09-14) recovered from after it bricked fresh wallets. The credo patch's recovery (now in the 0.7.1 patch, guarded by `mediatorPickupStrategy.guard.test.ts`) makes it a 15 s wait plus a one-time retry today, not a brick.

**What this plan takes from it.** Wallet #631 makes agent start single-flight: a call made while a start is in flight waits for it, so the path is closed by construction rather than by recovery. The start in flight already uses the build's mediator (`mediatorPreference.ts:104`, `useBCAgentSetup.ts:301`), so joining it is correct. M4 changes the mailbox config, so it doesn't ship without #631 and a device check of the upgrade path (§6). Nothing in the plan is superseded.

## 6. The Credo mediator's memory growth is a native leak in Askar's JavaScript wrapper

**Question.** The testers' Credo mediator grows by about 40–80 KB of RSS per inbound message, is flat when idle, and passed 1 GiB against a 768 MB V8 heap cap. The WebSocket `socketIds` patch (credo-ts fbb6517d) changed nothing. Why, and what fixes it?

**Facts about the running service** (READ, live state 2026-10-25 16:10–16:43Z, read-only):

- Image `ghcr.io/openwallet-foundation/didcomm-mediator-credo/mediator:375518d`, digest `sha256:4e0cbbd2…7976`, Node 22.21.1, Debian 12, glibc 2.36.
- Credo `@credo-ts/{core,node,askar,didcomm}` 0.6.0; `@openwallet-foundation/askar-nodejs` and `askar-shared` 0.4.3.
- Askar runs on its default **SQLite** inside the container. Only the pickup queue is Postgres, with one idle connection and no pile-up.
- File handles (~30) and threads (~18–20) are flat. Only 2 sockets are open, so traffic is HTTP polls, which is why the WS patch could not help.
- Transparent huge pages are `always` on the host. AnonHugePages was 305–356 MB of 441–500 MB anonymous memory.
- jemalloc ships in the image but is not loaded: `LD_PRELOAD`, `MALLOC_CONF` and `MALLOC_ARENA_MAX` are empty, and `/proc/1/maps` has no jemalloc mapping.
- Growth: RssAnon +59 MB in about 33 minutes, over roughly 1,300 inbound messages (about 45 KB each), 97% of them `messagepickup/2.0/status-request`.

**Finding 1 — the cause: `Scan` never frees its native result lists** (READ):

- In askar-shared 0.4.3, `Scan.forEachRow` takes a native `EntryList` from each `scanNext` and frees only the scan handle (`build/store/Scan.js:44-57`).
- On the Rust side, `askar_scan_next` allocates the list with `Arc::into_raw` (askar `src/ffi/store.rs:667` @ v0.4.6). Only `askar_entry_list_free` releases it; `askar_scan_free` does not (`store.rs:687-698`).
- No `FinalizationRegistry` exists anywhere in askar-shared or askar-nodejs. `Session.fetch` and `fetchAll` do free their lists (`build/store/Session.js:35, :54`), so only queries leak.
- Credo 0.6.0's `AskarStorageService.findByQuery` is exactly this `Scan.fetchAll` (`packages/askar/src/storage/AskarStorageService.ts:185`). Every query therefore keeps its whole decrypted result set (values, tags, names) in native memory for the life of the process.
- **Unfixed upstream:**
  - identical code in askar-shared 0.6.1 (latest stable) and 0.7.0-alpha-20261023221824;
  - Credo 0.7.1 still calls `new Scan` in `findByQuery`.
    An image or Credo upgrade does not fix it.

**Finding 2 — a smaller leak: C strings.** Askar's string getters (`askar_entry_list_get_name`, `get_tags`, `askar_key_get_algorithm`, JWK getters) allocate `CString`s, and the 0.4.3 Node wrapper has no `askar_string_free` binding. This is READ in source and has not been measured separately.

**Finding 3 — an amplifier, not the cause.** glibc malloc on a host with huge pages set to `always` keeps freed native memory resident. In 02's samples, AnonHugePages rises in steps behind RssAnon rather than driving it (READ, 16:28→16:43Z).

**Measurement** (MEASURED on the MacBook, askar-nodejs/askar-shared 0.4.3 on SQLite, Node 20). The metric is native memory = RSS − V8 heapTotal, with a full GC at start and end. The script and raw results are kept with the research notes and can be attached on request.

| Case                                                         | Native memory                    | Kept per query        |
| ------------------------------------------------------------ | -------------------------------- | --------------------- |
| Leaky `Scan`, one 3 KB record, 20,000 queries                | 92.1 → 183.1 MiB, linear         | about 5.2 KiB         |
| `session.fetchAll`, same record                              | 83.8 → 102.3 MiB, decelerating   | about 1 KiB, settling |
| Leaky `Scan`, one 100 KB record, 3,000 queries               | 212 → 327 → 441 MiB              | about 121 KiB         |
| `Scan` with each list freed, 100 KB, 9,000 queries (control) | 95.5 → 100.4 → 101.3 → 104.6 MiB | flat                  |

A caveat on the harness: askar-nodejs 0.4.3's ffi-napi binding crashed or hung at random on macOS with Node 20 (`Napi::Error`, or exit 13 under forced GC), in leaky and freed modes alike. Only completed runs are reported. That is a further reason to move the mediator to askar-nodejs 0.6.x (koffi) eventually.

**Per message** (MEASURED on a local mediator with the same libraries: Credo 0.6.0, askar 0.4.3 on SQLite, and the Postgres pickup queue; part 7's harness). Every inbound message runs exactly **4.0** `findByQuery` calls, in every mode tried (1 s and 5 s polls, live delivery, 1,000 messages). An earlier reading of the code estimated 6–10; the count supersedes it. Native growth there was about 45–63 KiB per inbound request, about 11–16 KiB per query on real DID and connection records. That matches production's 40–80 KB.

**The fix, run in that mediator** (MEASURED 2026-10-25 17:17–17:38Z; Node 20 on macOS, while production runs Node 22 on Linux). Each run polled every 250 ms for 10 minutes (about 2,250 requests), then sent 300 messages.

| Run               | Native memory, minute 1 → minute 10 | Per request  | 300 messages                    |
| ----------------- | ----------------------------------- | ------------ | ------------------------------- |
| Unpatched         | 116.2 → 193.8 MiB, linear           | about 35 KiB | 300/300 delivered, 0 duplicates |
| `Scan.js` patched | 99.4 → 130.7 MiB, still linear      | about 14 KiB | 300/300 delivered, 0 duplicates |

So the patch is safe: the round trip with acknowledgement works, and every message reached the right recipient, so no wrong connection record was returned. It removes about 60% of the growth, but it is **not flat**. A second leak remains, most likely the C strings (finding 2), which are not yet measured. Scaled to production (INFERRED), 140–200 MiB/h would become roughly 55–80 MiB/h.

**The fix in production** (MEASURED by the gateway lane, read-only, 2026-10-25 19:42:43–20:43:09Z).

- The mediator has run the bind-mounted `Scan.js` with jemalloc since 18:43Z. The process was 1–2 hours old during this window.
- Traffic in that hour: 7,814 inbound messages from 19 senders. 7,432 were status requests, 15 onboardings and about 100 deliveries.
- Growth over the hour:

| Metric        | Patched, 19:42–20:43Z                 | Unpatched, 12–16Z    |
| ------------- | ------------------------------------- | -------------------- |
| RssAnon       | +122.4 MB, about 15.7 KB per message  | 40–80 KB per message |
| cgroup memory | +133.5 MiB, about 17.5 KB per message |                      |
| Threads       | 24, flat since 19:43Z                 |                      |
| File handles  | 33, flat since 19:43Z                 |                      |

- **The patch works in production.** Per-message growth fell by roughly 60–80%. That agrees with the 60% measured locally, and the patched rate is close to the local 14 KiB per request.
- **What remains.** 4.0 queries per message at about 4 KiB each would give roughly the 15.7 KB that is left, which is consistent with the C-string leak (finding 2). INFERRED, not yet measured separately.
- **Huge pages still grow.** AnonHugePages rose by 133 MB in the hour, even with `metadata_thp:auto`.
  - That option covers jemalloc's metadata only. With the host's transparent huge pages set to `always`, jemalloc's arenas are still eligible for huge pages (INFERRED).
  - Two changes would stop that: `thp:never` in `MALLOC_CONF`, which the jemalloc in the image must support, or setting the host to `madvise`.
  - Either one is a production configuration change, so it waits for Alberto's go and is applied by the gateway lane.
- **One more hour is owed** from an older process, to confirm the rate holds.

**The app has the same leak** (READ; a device measurement is booked):

- The wallet resolves askar-shared 0.6.0 and askar-react-native 0.6.0, with the same `Scan.js`.
- The React Native binding returns an `EntryListHandle` to JS as a bare pointer string (`cpp/turboModuleUtility.cpp:211-216`), with no destructor or finalizer.
- An open Keyring polls about once a second and runs findByQuery on each round trip, so it should accumulate native memory continuously while open (INFERRED: order of tens of MB an hour).

**Fix options, ranked by cost and risk:**

1. **Free each list in `Scan.forEachRow`.** This is a try/finally around the row loop that calls `list.handle.free()`. Proven safe in a same-library mediator; it cuts growth by about 60% but does not end it (above).
   - _Mediator:_ a read-only bind-mounted `Scan.js`, the same way as the existing three patches, with no rebuild. It still needs proof inside the production image before it is applied.
   - _App:_ a `.yarn/patches` patch of askar-shared 0.6.0 (wallet branch `fix/askar-scan-free-entry-list`). `tier.mjs` classes it **store** by policy, since dependency patches need a native fingerprint check. An equivalent startup shim in bifold source, replacing `Scan.prototype.forEachRow`, would be OTA-tier.
   - _Upstream:_ a PR to askar-wrapper-javascript; drafted, not posted.
2. **jemalloc through `LD_PRELOAD` plus `MALLOC_CONF=background_thread:true,metadata_thp:auto`,** as the upstream README recommends (mediator PR #67). It reduces fragmentation under huge pages but does not stop the leak. A config change and a restart.
3. **Slower polling (wallet #635).** It cuts the fuel by about 60–80% in both the mediator and the app, but fixes neither.
4. **An image or Credo upgrade does not help:** the bug is in every Askar wrapper release.

**What this means for the migration.** The Affinidi mediator removes Credo and Askar from the mailbox, so the mediator half of this leak ends at M5. The app half does not: it runs in every Keyring phone whatever the mediator, so it needs its own fix independent of this plan. Until M5, the mediator patch with jemalloc is the bridge. Nothing in the plan is superseded.

## 7. Live WebSocket pickup instead of polling, on the Credo mediator's Postgres queue

**Question.** Should the wallet pick up over a live WebSocket (`PickUpV2LiveMode`) instead of polling (`PickUpV2`, every 1 s today, 5 s idle in #635)? Live mode was dropped twice before, for lost messages and dead sockets. Does that still hold, what does each mode cost the mediator and the phone, and what would a switch take?

**History** (READ, wallet and bifold history):

- 2026-07-07, `dc944fd`: the wallet adopts `PickUpV2LiveMode`.
- 2026-08-18, `b6b5eafd`: back to polling (10 s). A live socket on Android died without a close event, the mediator pushed a didexchange request into it, and the message was gone (`docs/spikes/e2e-vrc-connect-findings.md:56-83`). The mediator then ran the pre-0.6 image `d9ff9cb` on Credo's built-in queue. Stated condition for coming back: "once the mediator requeues unacked live deliveries" (`app/src/hooks/useBCAgentSetup.ts:79-86`).
- 2026-08-24 and 08-26: the image moves to `375518d` (`QueueOnly`, §2 of the 08-24 companion in the OpenVTC plan), and the pickup queue moves to Postgres. Commit `87f8048` says the Postgres queue serves "polling clients only".
- 2026-08-31, `9ee0dd1` and bifold `b9112b12`: `Implicit` receives nothing from this mediator; every agent pulls explicitly, guarded by `mediatorPickupStrategy.guard.test.ts`.
- 2026-09-13, `467a6ea`: the credo patch stops a running loop before starting another, in the `PickUpV1`/`PickUpV2` branch only.

**Finding 1 — the Postgres queue already requeues unacked live pushes** (READ, `packages/transport-queue-postgres/src/TransportQueuePostgres.ts` @ `375518d`; Credo 0.6.0 and 0.7.1 builds):

- A push to a live session marks the row `sending` and leaves it in the table (`addMessage`, :262-320). Only the phone's `messages-received` deletes it (`removeMessages`, :344-373).
- When the live session ends, every `sending` row of that connection goes back to `pending` (`LiveSessionRemoved` → `checkQueueMessages`, :92-106 and :429-452).
- The session ends when the server sees the socket close (Credo's WS inbound removes the transport session on `close`), and also when the phone reconnects: `saveLiveSession` removes the connection's old session first (`DidCommMessagePickupSessionService`).
- So the 08-18 condition is met on the Postgres queue. The `87f8048` note is wrong for `PickUpV2LiveMode`: the queue pushes to any live session. It is right for `Implicit`, which never opens one.

**Finding 2 — polling has the lost-message hole, not live mode** (READ and MEASURED):

- A poll also marks rows `sending` (`takeFromQueue`, :138-205). If the response never arrives, nothing resets them: a polling connection has no live session to end, and the next poll reads only `pending` rows.
- Production shows this today: 3 rows of one connection sat in `sending` from 2026-10-14 (a pickup never acked). The 7-day cleanup added on 10-25 now deletes such rows, which turns them into losses.
- MEASURED locally: one lost delivery response (4,814 B) left 3 messages in `sending`. None arrived in the next 30 s, while later messages arrived normally.

**Finding 3 — live mode recovers from every socket failure but one** (MEASURED, 6 scenarios below). The exception: when a socket goes half-open and the app then returns to the foreground, today's restart (`stopMessagePickup` + `initiateMessagePickup`) reuses the dead socket. Credo's transport table still holds it as open. The restart throws `Timeout has occurred`, and nothing arrives (0/10). Closing the socket first, then restarting, delivered all 10 in about 70 ms.

**Setup** (local only, nothing in production touched):

- A stand-in mediator from the same libraries as production: Credo 0.6.0, askar-nodejs/askar-shared 0.4.3 on SQLite, `@credo-ts/didcomm-transport-queue-postgres` 0.0.2-alpha-20251223125919 on an embedded Postgres, `QueueAndLiveModeDelivery`, HTTP and WS on one port.
- Two agents on the app's Credo 0.7.1-pr-2704. The phone's WebSocket class could be made half-open (open, nothing flows, no close event) or closed abruptly. Its `fetch` could lose a delivery response or the ack after it.
- The scripts are in the study's scratch folder, not in the repo.

| Scenario (live unless noted)                                | Delivered | Duplicates | Notes                                          |
| ----------------------------------------------------------- | --------- | ---------- | ---------------------------------------------- |
| 10-message burst                                            | 10/10     | 0          | p50 112 ms                                     |
| Socket closed abruptly after 10 of 30                       | 30/30     | 0          | Credo reconnects on its own                    |
| Server closes the socket                                    | 10/10     | 0          | reconnect in about 250 ms                      |
| Half-open for 15 s with 10 pushed, then the socket closes   | 10/10     | 0          | 6 runs; rows sat in `sending` until the close  |
| Half-open, then the app's foreground restart                | 0/10      | 0          | restart reuses the dead socket and times out   |
| Same, socket closed before the restart                      | 10/10     | 0          | about 70 ms                                    |
| No socket for 5 min, 20 sent, then resume                   | 20/20     | 0          | all within 109 ms of resume                    |
| Polling, a delivery response lost                           | 0/3       | 0          | rows stay in `sending`                         |
| Polling, the server resets `sending` → `pending` after it   | 3/3       | 0          | next poll                                      |
| Polling, the ack after a delivery lost, then the same reset | 3/3       | 3          | the phone had them; the reset sends them again |

After each live scenario, 3 more messages still arrived live, at 45–57 ms.

**Load on the mediator** (MEASURED, one fresh mediator per mode; idle 10 min, then 1,000 messages; native = RSS − V8 heapTotal, minute 1 → 10):

| Mode     | Phone requests, idle | Native growth, idle | Per inbound request | 1,000 messages: inbound, native | p50 latency in the burst |
| -------- | -------------------- | ------------------- | ------------------- | ------------------------------- | ------------------------ |
| Poll 1 s | 614 in 10 min        | +39.9 MiB           | about 63 KiB        | 1,216 requests, +59 MiB         | 0.9 s                    |
| Poll 5 s | 131 in 10 min        | +9.6 MiB            | about 45 KiB        | 1,205 requests, +64 MiB         | 4.6 s                    |
| Live     | 0 after setup        | +4.9 MiB            | about 46 KiB        | 2,003 requests, +163 MiB        | 7.5 s                    |

- Idle growth counts every inbound request, including the sender's own 5 s polls (about 120 in 10 min), which is all the live run had.
- Every inbound message ran exactly 4 `findByQuery` calls in every mode, idle and under load. This is the Askar `Scan` leak of part 6, so mediator memory follows the request count.
- An idle live phone costs the mediator nothing. A polling phone costs 3,600 requests an hour at 1 s and 720 at 5 s, about 200 MiB and 30 MiB of native growth an hour each (inferred from the rates above).
- Live costs about 2 requests per received message (the push, and an ack per message), against about 1.2 when polled in batches of 10. It is still cheaper whenever a phone receives fewer than about 1,800 messages an hour (vs 1 s) or 360 an hour (vs 5 s).
- In a burst of 1,000, live was slower (p50 7.5 s), because each message is pushed and acked one at a time. In ordinary traffic it was the fastest by far: p50 45–112 ms, against about half the poll interval.

**The phone** (MEASURED bytes; READ for the platform; battery INFERRED):

- Idle traffic per hour: about 6.9 MB at 1 s polling (about 1.9 KB per round trip), about 1.5 MB at 5 s, and close to nothing live after setup.
- During the 1,000 messages, live moved about 4.1 MB against 1.75 MB polled. The per-message acks go out as separate HTTPS requests, because the mediator lists HTTPS before WSS. Sending them on the socket would be a later saving.
- React Native's WebSocket can send a ping (`ping()`, SocketRocket on iOS, OkHttp on Android), but never reports the pong to JavaScript. On Android, OkHttp runs with no read timeout and no ping interval (RN 0.81.5 `WebSocketModule.kt:83-86`). So the app cannot see a half-open socket except through a round trip of its own.
- Credo reconnects only on a close event, with a backoff that doubles from 100 ms and has **no ceiling** by default (`maximumMediatorReconnectionIntervalMs` = infinity).
- Battery, INFERRED: polling every 1–5 s keeps the cellular radio from ever going idle (its tail is several seconds). An idle socket with a check every minute lets it sleep in between.
- Not testable here: iOS suspension, Android Doze, and a Wi-Fi ↔ cellular switch. These need two phones.

**Ranked recommendation:**

1. **Live mode with a liveness backstop (recommended).** What it takes:
   - `PickUpV2LiveMode` in `configureMessagePickup` (`useBCAgentSetup.ts:100-103`) and in bifold `contexts/activity.tsx:157`.
   - On every return to the foreground, and every 60 s while open: a status round trip with a short timeout (`messagePickup.pickupMessages` with `awaitCompletion`). On a timeout or an error, close the mediator socket, through a socket-tracking `WebSocketClass` in the agent dependencies, then restart pickup. This is the fix measured above.
   - Extend the credo patch's stop-before-start to the live-mode branch. Two foreground handlers (the app's and bifold's `ActivityProvider`) would otherwise stack reconnect monitors, as they stacked polling loops on 09-13.
   - Set `maximumMediatorReconnectionIntervalMs` (about 30 s).
   - Update `mediatorPickupStrategy.guard.test.ts`.
   - Keep a switch back to `PickUpV2`.
   - The mediator must stay on the Postgres queue. Live mode depends on its reset; the built-in queue is what lost the 08-18 message.
   - **Shipping: a store build, not OTA.** The patch change moves `yarn.lock`, which `tier.mjs` classes as store, and a change of transport belongs in a store build anyway. Before testers: a two-phone device run covering background, foreground, a network switch and a mediator restart.
2. **Polling at 5 s (#635), as the step before 1.** Already decided as the first OTA after 272. It cuts the mediator's fuel by about 80% against 1 s, but keeps the lost-response hole.
3. **Live mode without a backstop: rejected.** A half-open socket followed by a return to the foreground leaves the phone deaf until TCP gives up on its side.

`Implicit` is not a candidate under any of these: it opens no live session, so this queue never pushes to it.

**Independent of the choice: a server-side reset of stranded rows.** It closes the polling hole for every phone now, with no app change:

- Run it every 5 minutes. Each run saves the ids it finds in `sending`, and the next run resets to `pending` only ids that are still there: `UPDATE queued_message SET state = 'pending' WHERE state = 'sending' AND id = ANY($prev)`. A row is reset after 5–10 minutes stuck.
- Two sweeps, because the table records only `created_at`, not when a row was taken. An age filter on `created_at` would reset a message queued hours ago whose delivery is in flight right now.
- A late ack is safe: `removeMessages` deletes by id whatever the state.
- The cost is a duplicate when only the ack was lost (measured above). The chat module drops an exact repeat (`inbound.ts:68`, `'duplicate'`), so a repeated chat event is harmless. Other protocols may log a state error.
- It is applied on the mediator host like the 7-day cleanup, with the same go-ahead.

**Supersedes:**

- The 2026-08-18 position that live mode loses messages. That was true of the pre-0.6 image's built-in queue and is not true of the Postgres queue. The code comment at `useBCAgentSetup.ts:79-86` goes with any switch.
- `87f8048`'s note that the Postgres queue serves polling clients only.

What 08-18 found that still holds: a socket can die without a close event. The backstop in option 1 exists for that.
