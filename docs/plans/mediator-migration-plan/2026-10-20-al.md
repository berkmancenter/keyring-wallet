# 2026-10-20: findings behind the first draft of the mediator migration plan

Parent: [`../mediator-migration-plan.md`](../mediator-migration-plan.md).

## F1. Message wakes needed a mediator patch; "no mediator code change" did not hold

`peer-message-notifications-plan.md` §4 expected that nothing needed "a VTI, Credo or mediator code change". On the deployed Credo mediator (`375518d`) that turned out not to hold:
- **No webhooks at all without Firebase.** `build/config/pushNotificationLoader.js:8` returns early unless Firebase is configured, so a webhook-only setup never subscribes to queued messages. Upstream `main` `8617ac6` has the same line.
- **Posts for every connection.** `build/push-notifications/sendNotification.js:13` posts for every connection, with or without a device token.

Two one-line fixes were bind-mounted read-only on 2026-10-20, with backups kept and the rollback recorded in the infra repo's operations notes.
- **Result:** 28 webhook posts for exactly the two push-enabled connections of a two-iPhone test, which became 6 delivered wakes under the 30 s cap, with 0 errors.
- **Not yet run:** the deliberate privacy control (a message to a connection without a handle).

## F2. The Affinidi mediator has no push hook

Read at `555806151b30` and `a1611baa`: there is no webhook, FCM, APNs or RFC 0734 device-info code anywhere.
- **Config:** `mediator.toml`'s sections are `[secrets]`, `[server]`, `[database]`, `[security]`, `[streaming]`, `[did_resolver]`, `[limits]`, `[processors.forwarding]`, `[processors.message_expiry_cleanup]` and `[processors.session_expiry_cleanup]`. There are no push keys.
- **Hook points:** the only ones are the store (`src/messages/store.rs:23,333`; `MediatorBuilder::store`, `src/builder.rs:298`) and the lossy traffic monitor (`src/monitor.rs`).
- **Newer fix missing from the deployed build:** `a1611baa` adds a Redis-resubscribe fix (`878301bd`). Without it, a Redis restart silently stops live delivery until the mediator restarts. That affects the gateway VM's mediator today.

## F3. The decision: Affinidi for Keyring ↔ Keyring, superseding the DIDComm v2 subtask's mapping

`didcomm_v2_subtask.md` §7 maps "Wallet ↔ wallet, v2" onto Keyring's Credo mediator in v2 mode, and keeps Affinidi for wallet ↔ VTA. On 2026-10-20 the product owner decided on the Affinidi mediator for Keyring ↔ Keyring too, retiring the Credo mediator because of its downtime. The infrastructure maintainer had asked for the legacy host and its services to be retired rather than reinvested in.

This supersedes the subtask's v2 wallet ↔ wallet row; this PR marks that row superseded and points here. The Credo-v2 option stays in the plan as standing rationale (why it isn't chosen).

The product owner also accepted the order: move the Credo mediator as-is first (M1), then Affinidi as its own evidence step and store build.

## F4. Wake options without new mediator code

Asked whether new code is the only way, the session recorded five options (D2 W1–W5):
- **W1:** an upstream hook from Affinidi.
- **W2:** the sender rings through the gateway's existing trigger allowlist. Unverified: does `set_wake_device` accept contact DIDs as triggers?
- **W3:** the recipient's agent rings. Needs VTI-Q52.
- **W4:** our own store decorator.
- **W5:** a Redis sidecar.

The traffic monitor was rejected as lossy. Proposed: ask for W1 now, verify W2 in M2, and build W4 only as the fallback.

## F5. M1 "as-is" must carry the wake setup

A literal "as-is" move drops message wakes. They depend on state outside the image: `PUSH_NOTIFICATIONS__WEBHOOK_URL` in the env, and the two fixes. M1 lists both, and its exit check includes the push-sender log line, the positive wake test and the privacy control.

## F6. Two banner effects, only one of them gateway-side

**The in-app toast** a tester saw after tapping a message notification comes from bifold `InAppMessageNotifier.tsx:76-104`, not from the gateway.
- It toasts every received basic message unless that chat is open (:81).
- A wake tap opens the contact screen, not the chat, so the message picked up a second later gets toasted.
- The app fix is to route the tap to that chat (the toast's own `onPress` target, :97-101). That is app work, outside this plan.

**OS notifications stacking** is the separate, gateway-side effect.
- Each message wake carries its own collapse id (`keyring-msg-<uuid>`, patch 0003).
- One exchange left 4 wakes on one phone and 2 on the other, about 1 minute apart. They were fed by bursts of queued DIDComm messages (the message plus acks and receipts) under the 30 s cap.
- The plan adopts a stable per-handle collapse id for message wakes (§4.1).

## F7. OTA can't carry a mailbox move

- **A store-tier change in every respect:** new mailbox config is a react-native-config value, and mediation setup (`useBCAgentSetup.ts`) is a migration path in `scripts/release/tier.mjs`.
- **Main is already store-tier:** a dry-run publish on 2026-10-20 showed main since build 264 to be store-tier (a `yarn.lock` change, and a flag in the OTA server's code).
- **So:** M4 and M5 are store builds, and OTA only carries JS follow-ups after them.
