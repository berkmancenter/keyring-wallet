## 1. What exists in Keyring today

- **Text only.** `Chat.tsx:160` sends `basicMessages.sendMessage(connectionId, messages[0].text)`. In the Credo `0.7.1-pr-2704` build on `origin/main`, the API sends BasicMessage 2.0 only when the module, the agent and the connection are all v2 (`DidCommBasicMessagesApi.mjs:37-47`); otherwise 1.0. Neither class has attachments: v1 has `content` and `sent_time`, v2 has `content`, `createdTime`, `lang` and `parentThreadId`.
- **Credo's base class does carry attachments.** `DidCommMessage` applies `AttachmentDecorated` to every message, so `~attach` would survive the wire on a BasicMessage. But the BasicMessage handler and `DidCommBasicMessageRecord` drop it. Using it means patching Credo and still breaking every non-Keyring peer.
- **VRC code already smuggles JSON through BasicMessage `content`** (`witnessed-vrc-manager.ts:102,234`, `vrc-manager.ts:2645`, `vrc-biometric.ts:114`, `WitnessConnectionProvider.tsx:519`). To keep that out of the chat, `chat-messages.tsx:677-743` hides any content that parses as JSON with a `type` (except `reporting-did-registration`), and `useUnreadMessages.ts:8-28` excludes it from the unread count. **Conclusion:** a JSON-in-content chat protocol would collide with this filter, so the plan uses a real message type.
- **Precedent for a custom type with attachments:** `TrustTaskMessage` (JSON attachment `trust-task`) and `TspEnvelopeMessage` (base64 attachment), registered in `TrustTasksModule.ts:46-53`, with v1, v2 and TSP carriers. The plan's `chat/1.0` copies this.
- **Libraries:** see the plan §3. `react-native-video ~6.16.1` is in `app/package.json` and `Podfile.lock`, but no source file imports it. No emoji picker, GIF, fast-image or audio library is present.
- **Rooms:** no rooms or group chat code on `main`. `origin/main` has `docs/plans/openvtc-rooms-plan/rooms_group_messaging_subtask.md`, which designs messages, reactions, edits, redactions and a chunked encrypted blob layer for **group** rooms (§5.3–5.5, §8 there).

## 2. What the protocols allow

### 2.1 Transport

| Layer | Arbitrary bytes? | Size limit | Evidence |
|---|---|---|---|
| DIDComm v1 | Yes, through `~attach` (`data.base64`, `data.json`, `data.links` + `sha256`) | none in the spec | Aries RFC 0017 |
| DIDComm v2 | Yes, through top-level `attachments[]` | none in the spec | DIDComm Messaging v2.1 "Attachments" |
| TSP | Yes, the payload is opaque `Vec<u8>` | ~48 MiB (`MAX_FIELD_SIZE = 3 * (1 << 24)`) | `affinidi-tsp/src/message/wire.rs:41`, `direct.rs:102` |
| Credo mediator (HTTP in) | — | 5 MB request body | `@credo-ts/node/.../DidCommHttpInboundTransport.mjs:19` |
| Credo mediator (WS in) | — | 100 MiB (`ws` default `maxPayload`) | `ws/lib/websocket-server.js:74` |
| Affinidi mediator | — | **1 MiB `message_size`**, enforced at ingress; 10 MiB HTTP/WS frames; 20 attachments | `affinidi-messaging-mediator/src/common/config/limits.rs` defaults; `deploy/keyring-messaging/mediator/mediator.toml:117-134` |

**Conclusion:** the protocols carry media. The mediator cap is what forces media out of band. Under 1 MiB, with base64 applied twice (attachment, then JWE), the usable raw payload is about 500–560 KiB before JSON and forward overhead. That is why the plan's inline threshold is 256 KiB.

### 2.2 Existing chat standards

- **Basic Message 1.0 (RFC 0095)** and **2.0 (didcomm.org)** both list attachments and emoji responses as out of scope.
- **Media Sharing 1.0** (didcomm.org `media-sharing/1.0`): `share-media` with `items[]`, each referring to an attachment with `links`, `ciphering { algorithm: "aes-256-cbc", parameters: { key, iv, tag } }` and `metadata { preview, blurhash, duration, … }`, plus `request-media`. This is the closest existing standard, but it was **not adopted verbatim**: AES-CBC with an optional tag is not an AEAD, it defines no content hash (you have to borrow RFC 0017's `sha256`), its spec text and examples disagree on the media-type field name, and it has no reactions. The plan takes its ideas (encrypted link + key + preview, re-request) and uses AES-GCM and a mandatory ciphertext digest.
- **Trust Tasks `chat/message 0.1`** (`external/dtgwg-trust-tasks-tf/specs/chat/`): "a conversational message between an AI agent and a messaging-platform bridge, signed by its author and hash-linked to the previous message." Attachments are by reference (`AttachmentRef { id, mediaType, filename, sizeBytes, digest }`) with no key and no URL, and there is no reaction, edit or delete. **Rejected for person-to-person chat**, because the per-message signature and hash chain exist for audit and make delete costly by design. Its `AttachmentRef` field names informed the plan's descriptor.
- **Trust Tasks `rooms/*`**: MLS-keyed data rooms. VTC Trust Task bodies are capped at 64 KiB (rooms plan §5). This is the upstream answer for groups.

### 2.3 Reactions

No reactions protocol exists on didcomm.org or in the Aries RFCs. Prior art from other messengers:
- **Signal:** `DataMessage.Reaction { emoji, remove, targetAuthorAci, targetSentTimestamp }`.
- **Matrix:** an `m.reaction` event with `m.relates_to { rel_type: "m.annotation", event_id, key: "<emoji>" }`; removal is a redaction of the reaction event.
- **Rooms subtask §5.4:** a `reaction` event, with removal as a `redaction` of the reaction, aggregated on the client.

The plan follows the Matrix/rooms model (target by event id, remove by redaction), with Signal's one-reaction-per-person rule.

### 2.4 How the big messengers move media

All three encrypt on the device with a fresh per-file key, upload ciphertext to a CDN, and send the key and a hash inside the end-to-end-encrypted message:
- **Signal:** `AttachmentPointer` with a 64-byte key (AES-256-CBC + HMAC-SHA256), the ciphertext SHA-256 `digest`, padding to size buckets, and 30-day CDN retention.
- **WhatsApp:** a 32-byte `mediaKey` expanded by HKDF into an AES-CBC key, IV and HMAC key, with the SHA-256 of both plaintext and ciphertext (WhatsApp Security Whitepaper).
- **Matrix:** `EncryptedFile { url, key (JWK, AES-CTR-256), iv, hashes.sha256 }`.

None of them needs MLS for one-to-one chat. The pairwise DIDComm/TSP encryption plays the role of their session encryption.

## 3. Decisions taken in this session's first pass (proposed; items 3, 4 and 6 superseded by Part 2)

1. **A Keyring chat message type, not JSON in BasicMessage and not a Credo patch.** Evidence: §1 (display filter, record drops attachments, peer interop).
2. **Event body shaped like the rooms profile `org.openvtc.msg/1`.** One vocabulary for one-to-one and group chat. The room-only fields (`via`, record-key checks, `sig` inside the seal, padding buckets) are omitted because the pairwise envelope already authenticates the sender.
3. **Inline ≤ 256 KiB, otherwise an encrypted blob link; the hard cap is 100 MB.** Designed against the Affinidi 1 MiB cap (§2.1), not today's 5 MB. To be measured in Phase 0.
4. **AES-256-GCM through Credo's KMS** (`A256GCM` is in `supportedEncryptionAlgsForKey`, `@credo-ts/core/build/modules/kms/jwk/alg/encryption.d.mts:6`), chunked at 4 MiB to match the rooms blob layer. No new crypto library. The fallback, if streaming through Askar is too slow, is a thin native module over CryptoKit / `javax.crypto`.
5. **Our own emoji picker** built from Unicode `emoji-test.txt` at build time. **No third-party GIF search** (privacy, and an API key in the shipped app).
6. **Video playback is an open decision (D3).** The recommendation is to use `react-native-video`, which is already linked, over writing a native player.

## 4. Options considered and not taken

1. **Patch Credo's BasicMessage to keep `~attach`.** Keyring-only behaviour on a standard type: other peers would silently drop the media, and we would carry the patch through every Credo upgrade (the 0.7 move is in progress).
2. **JSON envelope inside BasicMessage `content`.** Collides with the existing hide-JSON filter, shows raw JSON on every non-Keyring peer, and cannot be indexed by event type.
3. **Everything inline, no blob store.** Fails at 1 MiB for any real photo or video, and large base64 strings on the JS thread freeze the UI.
4. **Pairwise fan-out for group chat.** Rejected in favour of the rooms work: no shared group key, no membership changes, and an N× upload cost per message.
5. **Adopting Trust Tasks `chat/message 0.1`.** See §2.2.

# Part 2 — Later the same session: no hosting, minimum scope

## 5. The constraint that moved

The project ruled out any design that makes Keyring host media: no storage cost and no legal obligations around user content. Two follow-ups came with that: could a user's own VTA hold their media instead, and could the plan be cut to the minimum that makes chat clearly better?

**This supersedes**, from Part 1 §3:
- item 3: the encrypted-blob store for anything over 256 KiB, and the 100 MB cap;
- item 4: AES-256-GCM per-file keys and 4 MiB chunking. Without out-of-band bytes, the DIDComm envelope already encrypts inline media;
- item 6: the video-playback decision, since video is out of scope.

It also supersedes the first-pass plan's phases 3–5 (blob store, large media, video playback, edits/deletes/voice notes) and its decisions D2 (where the blob store runs) and D3 (video player).

## 6. Can a VTA host a user's media? (pin VTI `49f5f1be`, verified)

**Not today.**

| VTA storage | Fit for chat media? | Evidence |
|---|---|---|
| app-state | No. JSON only, 64 KiB per record (`MAX_VALUE_BYTES = 65_536`), and no blob member by design | `vta-service/src/operations/app_state.rs:93`; `docs/05-design-notes/appstate-store.md:237-242` ("1.0 has no blob member at all … keeps a consumer from quietly treating `value` as a blob store") |
| Backup bundles | No. Super-admin only, delivered only to whoever created the bundle; a whole-node backup, not a file store | `docs/01-concepts/architecture.md:201-203`; `dtgwg-trust-tasks-tf/specs/backup/get-chunk/0.1/spec.md:82` |
| Vaults (secrets, credentials, agent memory) | No. Small records, 1 MiB REST body limit | `vta-service/src/routes/mod.rs:84` |
| Generic blob/file/S3 store | Does not exist | `rooms_s3_storage_subtask.md:21` (`origin/main`) |

**Peer access** is the second blocker. No grant is scoped to a peer and there is no share link. The only way to let another wallet read is an admin ACL entry on a whole context, which also grants write, since "a namespace in 1.0 is collision avoidance, **not** a trust boundary" (`appstate-store.md:327-331`). The backup `stream` bearer token is backup-only and super-admin.

**Coverage:** not every Keyring user has a VTA. The Farm path is "optional and additive" (`keyring-on-the-vta-farm.md:9` on `origin/main`), and the rooms plan's no-VTA mode is undecided (`openvtc-rooms-plan.md:98`).

**Data rooms** are no way around this. Rooms are hosted by a VTC or `room-host`, "not part of the VTA, on purpose" (`docs/02-vta/data-rooms.md:35,493`), with body caps of 64 KiB on a VTC and about 2 MB on `room-host`. Their blob layer is a Keyring draft that needs an upstream spec.

**Moving cost and legal duty to an operator.** That would shift both to whoever runs the VTA or room host. No pinned source records any Farm terms on hosting media, so it would be a question for the operator, and is not assumed here.

**What would make it possible, upstream:** an app-state `blobRef` (left open as a MINOR addition) plus a peer-scoped read grant or capability link, or the rooms `blobs/*` family. Both are owned by the VTI and Trust Tasks maintainers. Recorded in plan §8 as the future path.

## 7. Decisions in Part 2 (proposed)

1. **Scope cut to four items:** the chat message type, reactions and replies, our own emoji picker, and inline photos/GIFs up to 256 KiB. Each needs no new infrastructure. Steps 1 and 2 can ship without Step 3.
2. **Inline media gets no per-file encryption.** It travels inside the encrypted envelope, the same protection text has. The attachment descriptor uses RFC 0017 `data.base64`, so a later link variant with a `cipher` field is an additive change.
3. **Photos are compressed to fit**: 1600 px on the long edge, and JPEG quality stepped down from 0.8 until the photo fits, which also strips EXIF. GIFs are sent as they are, or refused if over the limit.
4. **The mediator's queue is accepted as transit** for compressed photos. It already holds every text message as ciphertext for up to 7 days. Recorded as decision D2 in the plan rather than assumed.
5. **Splitting large media across many messages is rejected.** It makes the mediator a file store by the back door, hits the Affinidi queue caps (200 soft, 1,000 hard per DID), and costs every pickup.

## 8. Before the PR: queue effect and ownership

- **Mediator queue.** The point came up in review that 256 KiB of inline media also flows through the mediator and wake paths. The queue gates count messages, not bytes (`mediator.toml:127-131`), so photos reach them no sooner than text does. What changes is bytes held per recipient: up to ~256 MiB at the 1,000-message hard cap. The plan now states this in §4.4, adds it to Step 0's measurement, and makes D2 conditional on the mediator operator accepting the measured worst case. Before this, D2 treated the photo case as identical to text.
- **Ownership.** The wake and notification files (`messageWake.ts`, `InAppMessageNotifier.tsx`, `activeChatTracker.ts`) belong to the message-notifications work (bifold #452, #462). The plan says changes there are coordinated with it.
- **Mediator migration** is cited as wallet PR #530, which is still in review: Affinidi for Keyring↔Keyring, M1 → M5, no date yet.
- **Boundary with the community messaging plan** (a draft, not yet in a PR). That plan's one-to-one section had proposed dedicated DIDComm types shaped after Affinidi Meeting Place's `meeting-place-chat/1.0`, with receipts, reactions and typing first and media deferred. Its author agreed to align on this plan's `org.openvtc.msg/1`-shaped events instead, so that room chat later inherits one vocabulary, with Meeting Place handled as a mapping. Result: this plan owns one-to-one chat, and the community plan keeps rooms, directory introductions and the group-chat decision. Two things were adopted from it: Step 0 also records how a current wallet handles an unknown message type, and non-content events must not ring the phone. The second is owned by the peer-message-notifications work.
