# 2026-10-27 — D2 and Step 3: what shipped, and what is on record (al)

**Plan:** [`../rich-messaging-plan.md`](../rich-messaging-plan.md).
**Why this exists:** Step 3 (inline photos) shipped in store build 272. On `main`, D2 still gates Step 3 on the mediator operator's acceptance, and nothing on `main` records that acceptance. This file records what shipped, what records exist, and what is missing. It decides nothing new.

## 1. What D2 required

On `main`:
- **§7, D2:** *"Is it acceptable for compressed photos to pass through the mediator's encrypted queue, as text already does?"* Recommendation: *"Yes, once the mediator operator accepts the measured worst case"*. It blocks Step 3.
- **§7, "Blocked on":** *"The worst-case queue size for photos (D2) — The mediator operator — Step 3 does not ship until the measured worst case is accepted"*.
- **§4.4:** *"Step 0 measures the storage each queued photo takes on both mediators (disk on Credo, memory on Affinidi), and the mediator operator signs off on the worst case before Step 3 ships (D2)."*
- **Step 0's "Done when":** a dated companion records both ceilings, the per-photo queue memory on both mediators, the unknown-type behaviour, and §4.4's 256 KiB confirmed or replaced.
- **`2026-10-25-al.md`, header:** *"D2 waiting for the mediator operator"*.

## 2. What shipped, and when

**Concluded:** inline photos shipped first in store build 272. All six keyring-bifold PRs merged on 2026-10-25:

| PR | What it does |
|---|---|
| #577 | checks a received inline image against its bytes. Caps are 256 KiB, 4096 px a side and 16 MP |
| #581 | writes a received or sent photo to its chat's media folder |
| #584 | receives a photo in a chat message. A `message` event with an attachment may be up to about 415 KiB of JSON |
| #588 | fits a picked photo to one message. It sends exactly 256 KiB and refuses one byte more before sending |
| #591 | shows the photo in its bubble, and full screen on tap |
| #592 | sends a photo from the composer, by camera or from the library |

keyring-wallet #637 pinned bifold at `8923a375` (#592's merge), merged 2026-10-25. The tag `staging-v0.2.0-272` is on wallet `2df81844`, whose bifold pin contains all six merges. `staging-v0.2.0-271` contains none of them.

None of the six PR descriptions mentions D2, the mediator operator or queue size. #588 cites one measurement: the Credo mediator's 5 MB HTTP body limit drops an oversize message with no error to the sender.

## 3. What is on record about D2 and Step 0

**On `main`** (`2026-10-25-al.md`):
- **§4, item 3:** about 470 KB of Postgres disk per queued photo on the Credo mediator, and about 466 KB of Redis memory on the Affinidi mediator. It does not say how these figures were obtained.
- **§5:** Step 0's unknown-type behaviour, from a code trace.
- **§7:** since 2026-10-25, the production Credo mediator deletes queued messages older than 7 days. It has no queue quota.

**In two open keyring-wallet PRs, not merged,** both opened on 2026-10-25, each extending `2026-10-25-al.md`:
- **#632, opened before any of the six photo PRs merged,** *"record D2 as accepted for the Credo mediator"*. It adds §9 to `2026-10-25-al.md`. That section reads *"D2 is accepted (al, 2026-10-25)"*. The figures it accepts:
  - up to about 470 KB of Credo disk per queued photo;
  - for at most 7 days, under the daily cleanup;
  - at a 256 KiB cap.

  Its conditions:
  - it covers the Credo mediator as it runs since 2026-10-25, with the cleanup and a fix for WebSocket sockets the mediator left open;
  - it does not cover the Affinidi mediator, which is decided when the mediator migration carries Keyring↔Keyring chat;
  - the client never overlaps pickups and caps the batch size while photos are queued.

  It also updates §4.4 and §7 and removes D2 from "Blocked on".
- **#633, opened shortly after #632,** *"Step 0's measured attachment ceiling on the Credo path"*. It used a local Credo mediator running the app's Credo version and two agents picking up by PickUp v2 polling. No production mediator was used. It records:
  - 2,112 KiB raw is delivered and 2,176 KiB is not;
  - a message on the wire is about 2.37 times its raw attachment;
  - the mediator's 5 MB inbound HTTP body limit refuses anything larger, and the sender gets no error;
  - ten queued 256 KiB photos came back in one pickup response of 6,227,799 bytes, and all ten arrived.

  It confirms 256 KiB on this path. It leaves the Affinidi ceiling derived, to be measured with the chat-over-v2 item.

Both PRs add a section numbered §9 to the same companion, so whichever merges second needs its section renumbered.

## 4. What is not on record

- **On `main`, any record that D2 was accepted:** by whom, when, or on what figures. The only such record is #632, which is unmerged.
- **That the acceptance came from the mediator operator, as D2 requires.** #632 attributes it to the initials `al`. Neither #632 nor the plan says that this was the mediator operator's acceptance.
- **A measured storage figure per queued photo, on either mediator.** The 470 KB and 466 KB figures come with no stated method. #633 measured bytes on the wire and in a pickup response, not a stored queue row. Step 0's "per-photo queue memory on both mediators" is therefore not met, on `main` or in the open PRs.
- **Step 0's ceilings on `main`.** They are only in #633. The Affinidi ceiling and pickup batch are derived, not measured, in any record.
- **D2 for the Affinidi mediator.** It is undecided, by #632's own scope.
- **The mediator queue under real photo traffic since build 272.** No record of it is in the plan, its companions or the six PRs.
