## Part 1 — The ten review points

### 1. Who may redact

**Concluded:** a `reaction` or `redaction` is valid only when the receiver can check the sender's authorship of the target. Unknown targets that expire from the held buffer, targets from another connection, and wrong-author events are all ignored. The sender is the connection's authenticated DIDComm sender, never a field in the event.

**Plan:** §4.2 "Authorization"; Step 1's wrong-author and other-connection tests.

**Supersedes:** the earlier text, which defined redaction without saying who may redact.

### 2. Image bytes at rest

**Concluded.**
- **iOS:**
  - Store media under `Library/Application Support/chat-media/<connectionId>/`, not `Documents`, which iOS backs up by default (Apple File System Programming Guide).
  - Create the folder with `NSURLIsExcludedFromBackupKey`.
  - Write files with the protection class `NSFileProtectionCompleteUnlessOpen` (class B in Apple Platform Security, "Data protection classes"). A closed file is unreadable until the next unlock, while background pickup can still write a new photo while the phone is locked.
- **Android:** store media under `filesDir/chat-media/<connectionId>/` (app-private, credential-encrypted storage), excluded from both cloud backup and device-to-device transfer through `android:dataExtractionRules` (Android "Back up user data with Auto Backup").
- **Files are named by `eventId`,** never by the peer's `filename`.

**Evidence.**
- **The app-wide default class is left alone.** Making it `Complete` would break background message pickup, which must open the wallet store while the phone is locked. Developer reports show class A files becoming unwritable about 10 s after lock while backgrounded (Apple Developer Forums 95757). Apple DTS also notes the app-wide entitlement only applies to newly created containers (Forums 18118).
- **No new native code.** `react-native-fs` 2.20 already accepts `NSFileProtectionKey` on `writeFile`, `mkdir`, `moveFile` and `copyFile`, and `NSURLIsExcludedFromBackupKey` on `mkdir` (`RNFSManager.m`). Its `FileProtectionKeys` constant is undefined at runtime, so the string value is passed.
- **Precedent.** Signal-iOS uses the same combination of data protection and backup exclusion (`OWSFileSystem.swift`).

**Considered and not taken now:** encrypting each file with a key held in the wallet's Askar store. Credo 0.7's KMS supports symmetric keys, so it would need no native code. But rendering would then go through in-memory data URIs, which Android decodes at full resolution. The cost and the memory risk outweigh the gain, unless the threat model grows to include forensic extraction from a phone unlocked since boot. That can be revisited without a protocol change.

**Plan:** §5 "Media files on disk"; Step 3's per-platform check.

**Supersedes:** "Image bytes are written to a file under the app's documents directory".

### 3. Receiver-side image safety

**Concluded:**
- **Read dimensions from the header first.** The receiver reads them in JavaScript from the image header before writing or rendering anything:
  - PNG: IHDR;
  - GIF: the logical screen descriptor plus a frame count;
  - JPEG: the SOF markers;
  - WebP: the `VP8`, `VP8L` and `VP8X` chunks.
- **Reject oversized images.** Images over 4096 px on a side or 16 megapixels are rejected, as are GIFs over a frames-by-area budget.
- **Check the descriptor against the bytes.** The descriptor's `byteCount`, `width`, `height` and `mediaType` must match the bytes.
- **Accepted formats.** JPEG, PNG, GIF and WebP only. HEIC is dropped from the accepted types.
- **GIF metadata.** GIFs are forwarded as-is, so their metadata travels with them, and the send sheet says so.

**Evidence.**
- **Why not `Image.getSize`.** React Native documents that it may need to load or download the image first, so it is no guard.
- **Why the JavaScript cap is still needed.** The platform decoders downscale to the view size: iOS through `CGImageSourceCreateThumbnailAtIndex`, Android through Fresco's automatic downsampling. Neither has a hard maximum decode size.
- **Why HEIC can go.** `expo-image-manipulator` outputs only JPEG, PNG and WebP, so no Keyring sender produces HEIC.

**Plan:** §4.3; §5 "Safety"; Step 3's mismatch and oversize tests.

**Supersedes:** the magic-byte-only check, and the list that included HEIC.

### 6. Reaction ordering and held events

**Concluded:**
- **Ordering.** Events are ordered per sender by ULID `eventId`, with later winning per sender and target. `clientTs` is display-only.
- **The held buffer** is capped at 200 events per connection, with a 7-day expiry per event, matching the mediator's retention.

**Plan:** §4.2; Step 1's reverse-batch and buffer tests.

**Supersedes:** "Ordering follows local receive order", and the previously unbounded buffer.

### 7. Emoji on Hermes and on older phones

**Concluded:**
- **Validate by exact membership.** A reaction is checked against the generated set of fully-qualified entries, after a length cap and after normalising minimally-qualified forms (for example "❤" to "❤️").
- **Filter by what the phone can draw.** The picker hides entries newer than the operating system can draw, using an OS-version table keyed on `Platform.Version`.
- **Fallback.** A valid reaction the device cannot draw still shows as a chip, labelled with its CLDR name.

**Evidence.**
- **Hermes, tested on the VM shipped for React Native 0.81.5:**
  - `Intl.Segmenter` is undefined;
  - a RegExp with the `v` flag throws "Invalid flags";
  - `\p{Extended_Pictographic}` works, but matches single code points only, so it cannot validate a sequence.

  Hermes's own `IntlAPIs.md` and `RegExp.md` agree.
- **The data file.** `emoji-test.txt` carries each entry's emoji version (for example `E15.0`); the latest is version 18.0.
- **Older Android.** It cannot update its emoji font (Android emoji2 guide). AndroidX `emoji2` 1.3.0 is already on the classpath through AppCompat, and may render newer emoji on some devices; that is to be checked on an Android 11 emulator in Step 2.

**Plan:** §5 "Emoji picker" and "Emoji validation"; Step 2.

**Supersedes:** "exactly one grapheme cluster".

### 8. Fallback freshness and delivery

**Concluded:**
- **Re-query rule.** The capability answer is re-queried when it is missing, when it was recorded by an older app version, or when it is more than 7 days old. It is also re-queried before anything is dropped because of an "unsupported" answer more than 24 hours old.
- **Photos to offline peers.** A photo to a peer that stays offline past the mediator's 7-day expiry is dropped there without the sender knowing. That matches text today. It is accepted for this plan and stated in §4.5, with delivered receipts named as the later fix.

**Plan:** §4.5.

Step 1 adds the wrong-author redaction (point 1).

## Part 2 — Message history and disappearing messages

### 2.1 What exists in Keyring

- **No user-facing delete** for a message or a chat, and no retention setting. Bifold calls no BasicMessage delete anywhere in `packages/core/src`.
- **The only deletion is removing a contact** (`modules/vrc/hooks/useDeleteContact.ts`). It removes the contact's credentials, connection and relationship record. Credo's connection delete removes only the connection and its routing, so the contact's BasicMessages stay in the store.
- **Previews.** The in-app toast shows an 80-character text preview (`components/InAppMessageNotifier.tsx`). The push itself carries no content.
- **Screenshot blocking.** `react-native-screenguard` is wired through `hooks/screen-capture.ts`, and off by default.

### 2.2 How other messengers do it

- **Signal:**
  - The disappearing setting "applies to all parties of a conversation". Each recipient's "clock starts ticking for each recipient once they've read their copy". The feature is "not for situations where your contact is your adversary" (Signal blog, 2016-10-11).
  - A default timer for new conversations was added in 2021.
  - On the wire, every `DataMessage` carries `expireTimer` and `expireTimerVersion`, the latter to resolve races (`SignalService.proto`).
  - **Local history** has "Keep messages" (Forever, 1 year, 6 months, 30 days) and a conversation length limit.
- **WhatsApp:**
  - Timers of 24 hours, 7 days or 90 days, counted from send, with an optional default timer for new chats.
  - Changing the timer affects new messages only.
  - "Keep in chat" is controlled by the sender, and view-once media is a separate per-send choice.
- **Telegram secret chats:** the timer starts when the message is displayed on the recipient's screen, and screenshot alerts are best effort.
- **Matrix:** room retention (`m.room.retention`, MSC1763) is a server-side policy that the Synapse server implements experimentally; it is not in the spec. Per-event self-destruct (MSC2228) is an unmerged draft.
- **DIDComm** has no disappearing-message standard. The v2 `expires_time` header governs delivery and processing, not deletion. On the Affinidi mediator, v2 queue expiry is the earlier of the client's `expires_time` and the server TTL. The v1 path always uses the TTL, which is 7 days in this deployment (`mediator.toml`).
- **VTI rooms:** `retentionDays` is a whole-room lifecycle, not per-message expiry (`docs/02-vta/data-rooms.md`).

### 2.3 Decisions taken in the plan

1. **Ship the local controls first:** Delete for me, Clear chat, Keep messages, and removing a contact also removing its chat. They need no protocol change, and they fix the existing gap where removing a contact leaves its messages behind.
2. **Disappearing messages as a `timer` event plus a per-message `expiresIn`,** following Signal's wire shape. A missed timer change then cannot leave the two phones disagreeing about a message, and races resolve by `version`.
3. **Signal's clock rule:** the sender's copy at send, the recipient's at first display (D4). Nothing disappears unread.
4. **Do not shorten the mediator queue** (D5). Shortening it gives WhatsApp's semantics, dropping undelivered messages, rather than Signal's. And the v1 path cannot shorten it anyway.
5. **Require `chat/1.0` on both sides.** A plain BasicMessage carries no timer, so an older peer cannot honour one.
6. **No previews in chats with a timer,** so a notification cannot outlive the message.
7. **Honest wording:** the setting says that people can still screenshot or copy messages. Blocking screenshots in timed chats is possible with the existing `react-native-screenguard`, but is not promised.

### 2.4 Not taken

- **View-once media:** a separate feature with its own semantics. It can be a later attachment flag.
- **Delete for everyone:** already a named later type in §4.2.
- **A default timer for new chats:** easy to add once per-chat timers exist. It is left until the per-chat version is in use.
