# 2026-10-25 — Design changes made while building Step 1, chat over DIDComm v1 only, the capability notice, and mediator corrections (al)

**Plan:** [`../rich-messaging-plan.md`](../rich-messaging-plan.md).
**Context:** the plan is being built for store build 272, with D1, D3, D4 and D5 decided as recommended and D2 waiting for the mediator operator. The first code is bifold #525 (B1), the chat protocol skeleton. Code facts below are from bifold `main` `d7d89ed3`.

## 1. Capability: the announced RCE version, not Discover Features

**Concluded:** a contact's support for `keyring/chat/1.0` is read from the RCE protocol version it announces in the relationship handshake (`vrc:rceVersion:<n>`, stored as `counterpartyRceVersion` on its `RelationshipDidRecord`). **Version 6 means "speaks chat".**

**Evidence:**
- **Keyring has no Discover Features exchange.** No DIDComm Discover Features call exists anywhere in bifold core or the app. The "discovery" in `ceremony.ts` is the Trust Task `trust-task-discovery` document exchange.
- **The announced version is the existing mechanism.** VRC issuance decides what a contact can verify the same way (`counterpartyRceVersionAtLeast` in `vrc-manager.ts`; `RCE_PROTOCOL_VERSION` is 5 today), and the Trust Task dialect is gated the same way (`TRUST_TASKS_MIN_RCE_VERSION = 4`).

**When 6 is announced.** B1 defines `CHAT_MIN_RCE_VERSION = 6` but leaves `RCE_PROTOCOL_VERSION` at 5. The announcement moves to 6 in the PR that shows chat events in the timeline. Until then, no contact sends chat events to a build that cannot display them.

**What this changes elsewhere.** Existing contacts never re-announce:
- the relationship handshake is sent once per relationship;
- re-sending it is not safe, because receiving it calls `maybeOpenRelationshipExchange`, which would restart the relationship exchange.

So a build that first announces 6 must tell existing contacts separately, with a one-time chat-capability notice that never touches the exchange. Its exact form (a chat event type of its own, or another existing message) is decided in the Step 1 sending PR, before anything depends on it.

**Supersedes:** §4.5's "Each wallet advertises `keyring/chat/1.0` through Discover Features …" and its re-query rules.

## 2. One message class for both DIDComm versions, with the event as a member

**Concluded:**
- **One class, `ChatEventMessage`, serves DIDComm v1 and v2.** Over v1 the event rides as the message's `event` member. Over v2 it is `body.event`, and Credo spreads `body` back onto the same property on receipt.
- **The event is one level down,** so its own `type` and `eventId` never collide with the DIDComm message's `type` and `id`.
- **Inbound is limited to authenticated events on an existing connection.** The sender is always the connection the event arrived on.

**Evidence:**
- **Credo's own precedent.** Credo's BasicMessage 2.0 class works this way over both envelopes (`DidCommBasicMessageV2.toV2Plaintext()`).
- **Why two classes would need two type URIs.** Credo matches an inbound message to a class by type alone (`DidCommMessageHandlerRegistry.getMessageClassForMessageType`). The Trust Task pattern of one class per DIDComm version exists because its binding spec defines a different type for each; this protocol has no such spec.

**Supersedes:** §4.1's "carries a chat event as a JSON attachment with id `chat-event`" and "A DIDComm v2 class mirrors it".

## 3. Chat over DIDComm v1 only; v2 is a later item

**Concluded,** with the product owner's agreement the same day: Step 1 is built and proven over DIDComm v1. A contact on a v2 connection counts as not supporting chat and gets plain BasicMessages. Chat over v2 is a separate item after Step 1.

**Evidence:**
- **v2 and TSP can deliver with no authenticated sender.** Over v1, Credo finds a connection only from the sender and recipient keys, so a connection always comes with a sender key. Over v2 (and TSP), it can find one from the `from` and `to` DIDs alone, so an anoncrypted message arrives with a connection and no sender key. The chat handler drops those as `no-authenticated-sender` (bifold `modules/chat/inbound.ts`, from #525), because the sender of an event must be the connection it arrived on.
- **Sending over v2 would have walked into that drop.** B2's `sendEvent` uses `DidCommMessageSender`, which sends in the connection's own DIDComm version. So B2 (bifold #530) makes `counterpartySpeaksChat` false on a v2 connection, with a test that pairs v1 → yes and v2 → no on otherwise identical input. The reviewer confirmed that `didcommVersion` is a real field on the connection record in the Credo build bifold resolves, so the check is not a no-op. A legacy record with no `didcommVersion` reads as v1.
- **No cost today.** v2 is off by default: a developer setting turns it on (`setDidCommV2Enabled` in `trust-tasks/ceremony.ts`), so every tester's contacts are v1.

**The deadline this creates.** The mediator migration plan's M4 (wallet #530) turns v2 on by default for new contacts. From then on, a new contact would get only plain messages. So chat over v2 must land before M4; the plan's blocked-on table now says so. The v2 item decides how a v2 chat event proves its sender (authcrypt required, or another binding to the connection) and has its own two-device run.

**Supersedes:** Step 1's "It runs once over DIDComm v1 and once over DIDComm v2", and the Step 1 bullet naming the Discover Features advertisement and §4.5's re-query rule. Section 1 above already superseded those for the capability check. Step 0's unknown-type measurement is now framed as what the capability notice must guard against.

## 4. Mediator facts corrected from the Step 3 research

The Step 3 and D2 research reported four things the plan had wrong or too broad:

1. **"At most 7 days in the queue" is true on Affinidi only.** The current production Credo mediator has **no expiry and no queue caps**: rows from 2026-08-26 are still queued, and three have been stuck in `sending` since 2026-10-14 (upstream credo mediator issue #103). §4.4, §4.5, §4.6, D2 and D5 now say so.
2. **Affinidi's 200/1000 per recipient.** 200 is the enforced default. 1,000 is only the ceiling to which an account's limit can be raised. §4.4's bytes-held figure now uses 200 (about 50 MiB per recipient), noting 1,000 as the raised case.
3. **"Per-photo queue memory".** It is disk on Credo (Postgres JSONB, about 470 KB per queued photo) and memory on Affinidi (Redis, with no `maxmemory` set in `deploy/keyring-messaging`, about 466 KB per queued photo). Step 0 now measures "storage" on both.
4. **The EXIF acceptance check.** It cannot be a unit test: Jest runs the manipulator's mock (bifold `__mocks__/@expo/expo-image-manipulator.js`). Step 3 now requires a simulator or device run that reads the real output. The native code does re-encode without EXIF (iOS `UIImage` to `jpegData`; Android `Bitmap.compress` with no `ExifInterface`), so the run is expected to pass.

**Also added to §5 from the same research:**
- reuse gifted-chat's `MessageImage` for the viewer;
- pick GIFs with `quality: 1`;
- resize very large photos first, since Android decodes at full size;
- never overlap message pickups, and cap the batch size while photos are queued.

**Forward shape, settled later the same session.** Keyring-to-Keyring chat on Affinidi uses a JSON forward, so the ceiling is about 430 KiB raw, and 256 KiB fits with room to spare.
- **Credo's own v2 routing** wraps the inner message as a JSON attachment (`media_type: application/didcomm-encrypted+json`, `data.json`), in `@credo-ts/didcomm` 0.7.1-pr-2704 `build/envelope/DidCommV2Envelope.mjs`.
- **The wallet's VTI mediator transport** does the same (`VtiMediatorTransport.ts` `forward()`).
- **No JWS layer** is involved, since Credo PR #2704 has no signed-send path. If a later phase routes this traffic through another packer, re-check.

**Pickup batches are larger than the plan said.** The mediator returns queued messages as base64 attachments of a pickup `delivery`, so a queued photo is about 830 KB in the batch, and ten are about 8.3 MB. The plan's earlier "about 4.5 MiB on the wire" for ten is superseded. This is why §5 caps the batch size while photos are queued.

## 5. Step 0: what a build without chat does with a chat event

**Concluded:** a build without chat neither shows nor stores the event. It answers with a generic problem report, the answer dies quietly on the sender, and nothing loops.

**Evidence,** traced in `@credo-ts/didcomm` 0.7.1-pr-2704 (the version the wallet resolves; the wallet's patch does not touch these files):
1. **The receiver.** `DidCommMessageReceiver` falls back to the plain `DidCommMessage` class for an unknown type, so validation passes.
2. **The dispatcher.** `DidCommDispatcher`'s default middleware finds no handler and no `fallbackMessageHandler`, and throws `DidCommProblemReportError` ("… The message type is not supported", `MessageParseFailure`).
3. **The reply.** With a connection present, the dispatcher sends a `https://didcomm.org/notification/1.0/problem-report` back on that connection, with `pthid` set to the message's `@id`.
4. **No fallback anywhere.** Neither bifold (at the wallet's pinned commit, nor on `main`) nor the app registers a fallback handler or a handler middleware.
5. **The sender.** No Credo module registers a handler for the generic `notification/1.0` problem report (no `supportedMessages` lists `DidCommProblemReportMessage`). So the sender's dispatcher fails to handle it too, and its own guard stops the reply: `DidCommDispatcher.mjs` line 51 throws "Not sending problem report in response to problem report" when the inbound message is a generic problem report. This happens before line 54 (threading by `threadId` when both are of the same protocol) is reached. The result is one logged error and no loop.
   - **The guard is ours, not the peer's.** It runs in the sending phone's Credo, so the no-loop property doesn't depend on how the other phone behaves.
   - Once Step 1 registers its own handler for this problem report (section 6), the report never reaches that path. The handler returns nothing, so there is still no reply.

**Not yet seen on a device.** This is a code trace. Two things are confirmed in Step 1's two-device run (a build with chat and one without):
- that the older phone shows nothing;
- whether a backgrounded phone shows a wake banner for the notice or the problem report. The mediator wakes a phone for any queued message, and the banner's text comes from the push gateway.

**Superseded:** Step 0 framed this as deciding "how much the fallback leans on Discover Features being current". The capability check no longer uses Discover Features (section 1), so the finding now shapes the capability notice instead (section 6).

## 6. The capability notice

**Concluded:** the notice's form, settled before anything depends on it. Plan §4.5 states it:
- **The message.** A message of its own, `https://keyring.berkmancenter.org/chat/1.0/capability` with `rceVersion`. Receiving one raises the stored version, never lowers it, and never opens a relationship exchange.
- **When it's sent.** Lazily: when a chat is first opened with a contact stored below 6, plus answer-once. Not as a sweep of every contact at startup.
- **Problem reports.** A handler for the generic problem report acts only on messages this phone sent, matched because each chat event's `@id` is its `eventId`.

**Why each choice:**
- **A message of its own, not the handshake re-sent.** Receiving the handshake calls `maybeOpenRelationshipExchange`.
- **Not a BasicMessage.** Older builds would show it.
- **Not a Trust Task.** Trust Tasks carry relationship operations with their own discovery and error vocabulary, and a capability bump is not one.
- **Lazy, not a startup sweep.** Section 5 shows that every notice to an older build costs a queued message, possibly an empty wake, and a problem report back. A sweep would wake every contact a person has; lazy sending limits it to the chats people actually open.
- **Answer-once.** Without it, a contact who never opens the chat would never learn that the other phone upgraded.
- **Reading problem reports.** Without that, a contact that went back to an older build would silently lose chat events. With it, text falls back to a BasicMessage within one round trip.
- **Matched on the connection it arrived on.** The handler queries the arriving connection's sent events, then matches `pthid`. Matching against every stored `eventId` would let a peer cite an id it learned in another chat and have it treated as a failure there. The same discipline applies to the deletions in Step 4: bound by connection first, then match the id.
- **The `@id` is the `eventId`.** A ULID matches Credo's message id pattern (`[-_./a-zA-Z0-9]{8,64}`). Using it means the problem report's `pthid` finds the stored event directly, with no new field on `ChatEventRecord`.

**Where it is built:** Step 1, in the PR that announces 6 (bifold `modules/chat/notice.ts`), after the timeline that shows chat events (plan §4.5, "When a build announces 6").

## 7. The Credo mediator now drops queued messages after 7 days

**Concluded:** "at most 7 days in the queue" now holds on both mediators. Section 4, item 1 said the Credo mediator had no expiry; that is superseded.

**Evidence:**
- **The change.** Since 2026-10-25 the production Credo mediator runs a daily cleanup that deletes queued messages older than 7 days.
- **Its first run** removed 22 old rows. That included the three stuck in `sending` since 2026-10-14 (upstream credo mediator issue #103).

**What it changes in the plan:** §4.4, §4.5 ("Delivery to an offline peer"), §4.6, D2 and D5 now say 7 days on either mediator.

**Still true:**
- The Credo mediator has no queue quota, per connection or in total. Affinidi's enforced default is 200 messages per recipient.
- A queued photo costs disk on Credo (Postgres) and memory on Affinidi (Redis).
- An undelivered message dropped after 7 days is not reported to the sender, on either mediator.

## 8. Step 4: bounds on what a peer can set, and the received clock's backstop

*A separate working session (the Step 4 history and disappearing-messages work), the same day.*

**Concluded:**
- **A floor of 1 hour.** A received `timer` under 1 hour (other than 0) is refused (`bad-timer`), and the chat keeps its setting. A received message with a shorter `expiresIn` is kept, its `expiresIn` raised to 1 hour.
- **A `version` cap of 1,000,000.** A timer event above it is refused, and a phone refuses to send a change past it.
- **The recipient's clock** starts at first display, with a backstop at the seen time; a message neither shown nor seen is never deleted by its timer.

**Why the floor:** a buggy or hostile peer could set a 1-second timer, and a message would vanish as the chat opens. 1 hour is the smallest choice the setting offers.

**Why raise a short message rather than refuse it:** refusing drops the person's text while their phone shows it sent, which is the worst failure this feature has. Raising it keeps the text and still prevents vanish-on-open. Only a buggy or hostile sender can produce such a message, since our phones never send under the floor, so keeping it slightly longer than asked is the right trade. A timer change, by contrast, is refused: nothing is lost, because the chat keeps its current setting. (Refusing messages too was proposed first and set aside for this reason.)

**Why cap the version:** `timer.version` was the one wire field with no upper bound. One event at `Number.MAX_SAFE_INTEGER` saturates the count (2^53 + 1 is 2^53), after which every change ties on version and falls to the `eventId` tie-break. Both phones still agree, but the versioning is retired. Found in review.

**Why the backstop, and what it costs:**
- **Why:** a lost display report would otherwise leave a timed message that never disappears, with neither person told.
- **The cost:** the seen stamp is set when the chat is open with the message unread, which can precede its row being on screen. So a received message disappears no later than `expiresIn` after it is first on screen, possibly earlier, never later.
- **Wording:** "after you first see them" is never an overclaim. Dropping the backstop would make it one, through a lost report.
- **Narrowing it:** the seen stamp is restricted to a focused chat in an app in the foreground (bifold #571), which narrows the early case to a message scrolled past in an open chat.

**Code:** the floor, the version cap and the backstop are in the H4b PR (the expiry sweep), which follows bifold #570; #570 itself has the timer, stamping at send and the start at first display, but not these bounds.

## 9. Step 0: the attachment ceiling on the Credo path, measured

**Concluded:** §4.4's 256 KiB is confirmed for photos over DIDComm v1 through the Credo mediator, the path of this plan's first release. The Affinidi ceiling stays derived until the chat-over-v2 item.

**How it was measured.**
- **The setup:** a local Credo mediator (bifold `packages/mediator-server`, Credo 0.7.1-pr-2704, the app's version, HTTP inbound) with two Node agents mediated through it, picking up by PickUp v2 polling as the wallet does.
- **The payload:** each message carried N raw bytes base64-encoded in its body, standing in for an inline attachment.
- **The ladder:** 64 KiB to 4 MiB, then 2,112 to 2,496 KiB in 64 KiB steps.
- **The batch:** ten 256 KiB messages queued while the recipient was not collecting, then one pickup.
- No production mediator was used.

**Results.**

| Measurement | Result |
|---|---|
| Largest raw attachment delivered | 2,112 KiB (2,176 KiB is not delivered) |
| Bytes on the wire for 2,112 KiB raw | 5,128,203 (about 2.37 times raw: base64 in the message, then two JWE layers) |
| What refuses larger | The mediator's inbound HTTP body limit, `express.text({ limit: "5mb" })` = 5,242,880 bytes (`PayloadTooLargeError: request entity too large`) |
| Sender's view of a refused message | No error; the message looks sent |
| Ten 256 KiB photos in one pickup | One response of 6,227,799 bytes (about 623 KB each), all ten delivered |

**Why the local result stands for production.**
- **Same limit:** the production Credo mediator runs `@credo-ts/node` 0.6.0. Its `DidCommHttpInboundTransport` sets the same `"5mb"` text limit, and its WebSocket server the same `ws` default frame limit (100 MiB, incoming frames only).
- **Same path:** the wallet starts pickup with PickUp v2 polling (`app/src/hooks/useBCAgentSetup.ts`). Credo sets a transport priority only for implicit pickup (`DidCommMediationRecipientApi.sendMessage`), and the app sets none. So a phone uses the mediator's services in their listed order, and production lists HTTPS before WSS.
- So sends to a contact and pickups both go over HTTPS, the path measured.

**Where the WebSocket question comes back:** a different mediator. If a new mediator's invitation lists WSS before HTTPS, or it serves only WebSocket (as the Affinidi mediator may), then pickup and sends move to WebSocket with no app change. A pickup frame of several MB then reaches the phone's WebSocket client, which is untested on Android and iOS. The mediator migration plan carries this as a prerequisite: check the new mediator's service order, and if WebSocket comes first or is the only transport, measure a large pickup frame on both platforms before moving phones.

**What it changes.**
- §4.4 states the measured ceiling and the silent refusal in place of "an estimate until Step 0 measures it".
- §4.4 gains the measured Credo pickup batch.
- The earlier 830 KB and 8.3 MB figures in §4.4 are kept: they describe the Affinidi mediator's pickup, not the Credo one measured here.

**Still derived:** the Affinidi ceiling (about 430 KiB, from `message_size` = 1 MiB with a JSON forward) and its pickup batch. Both are measured with the chat-over-v2 item, before the mediator migration's M4, since chat reaches that mediator only over v2.

**Superseded:** Step 0's "both ceilings". For this release, Step 0 is done with the Credo ceiling measured and the Affinidi one carried by the chat-over-v2 item.
