# The agent serves `vta/pcs/*` — measured, not read

**2026-10-15, al.** Companion to
[`keyring_implementation_subtask.md`](./keyring_implementation_subtask.md) §0.
What this records: the first live confirmation that a real agent serves the
hidden-vetting task family, how the question had to change before it could be
answered safely, and four defects found in our own code on the way.

## The answer

`servesPcs` returned **true**, from Keyring's own client against the real
agent. The Developer screen's log, pulled off the device with
`uiautomator dump` rather than transcribed:

```
[VTA-PROBE] connected as did:peer:2.Vz6MknLjmwyvw6qko…idCI6ImRtIn0
[PCS-PROBE] servesPcs true
[VTA-PROBE] whoami roles=application scopes=ctx:vta
[VTA-PROBE] contexts 1 vta
[VTA-PROBE] servers 1 control
[VTA-PROBE] failed permission denied: forbidden…t capability
```

**Heads.** Agent `did:webvh:QmWj8ssa2BZAcLZzMTfLXHXWbkHUkY8ibMsG89otkEMue8:dids.ic3.dev:hidden-vet-vta`,
VTARest `https://vta-hidden-vet.ic3.dev`. Phone
`did:peer:2.Vz6MknLjmwyvw6qko2A6SQntLo3Q7HzhCXRVDuzTZL5zN3Y2c…`, granted role
`application`, contexts `vta`, **no capabilities**. bifold `25b2d6ba`; wallet
worktree at `1f022308`; Android debug build; emulator `Hidden_Vet_API_33`
(see "Where the identity lives").

**What it establishes:** the agent implements the family, and Keyring can ask.

**What it does not:** nothing about the applicant flow. Every one of the five
`vta/pcs/*` calls gates on `Capability::PcsApplicant`, which this phone does not
hold. The trailing `permission denied … does not carry the KeyMint capability`
is the *pre-existing* manager probe continuing into `mintPersona` →
`webvh/dids/create`, which an `application` role cannot do. Expected, and
unrelated to hidden vetting.

**The agent has no version to read.** `GET /health` answers
`{"status":"ok"}` and nothing else; `/version`, `/api/version` and
`/health/version` are empty. The probe's answer *is* the version evidence, and
a better one than a string — see [[vta-version-string-lags]].

## Why the question had to change

The probe originally dispatched `applications/show` with an id no agent can
hold and read the refusal: `notFound` ⇒ serves it, `unsupportedType` ⇒ does
not. Then a capability refusal was added to the "serves it" side, on the
grounds that `handle_applications_show` checks the capability **before** it
looks anything up (`vta-service/src/trust_tasks/pcs.rs:203-213`), so reaching
that check proves the handler exists.

**That reasoning is true at 0.60 and unsafe as a rule.** The Policy Decision
Point gate runs *before* dispatch, and with `policy.enforcement` on a denial
for an unknown type is also `permissionDenied`
(`policy_gate.rs:141` at vta-service-v0.56.0), as is a policy-store read
failure, which fails closed with "policy evaluation unavailable" (`:132`). A
pre-0.60 agent can therefore refuse that way for a task it has never heard of,
and reading that as "serves it" would offer hidden vetting on an agent that
cannot do it. Enforcement is on in some of our deployments, so this is live.

**So the client now asks instead of inferring.** `trust-task-discovery/0.1`
answers from the dispatch table itself (`discovery.rs` passes
`dispatched_uris()`), its handler takes no capability check, and it separates
"does not implement" from "will not let you" — which no refusal can do. The
probe remains only as a fallback, where `permissionDenied` is inconclusive.

Two consequences worth keeping:

- **the narrowest grant is enough.** The answer above came back on an
  `application` entry with no capabilities, which is why `initiator` did not
  have to be created while that question is still open;
- **nothing else is dispatched when discovery answers**, so the version
  question cannot wake an approver through a gated task — the concern behind
  §0.1's "nothing is asked until the user taps".

A discovery query must send **no patterns**. A responder matches a pattern
against a task's *slug*, not its Type URI (`vti-common/src/trust_task/discovery.rs:51-59`
slugs first), so a URI-shaped pattern matches nothing and the empty answer
reads as "does not serve it" — for every agent. An empty list is now
inconclusive, never a no.

## Four defects in our own code, found on the way

1. **Capabilities read from the wrong member.** An entry's wire `scopes` is its
   *context* list; the narrowing rides `ext["org.openvtc.capabilities"]`. The
   check could never have matched a correctly granted entry.
2. **Empty contexts read as unrestricted** — true only for an admin. For any
   other role an empty list means no access at all, so a phone that can reach
   nothing was reported ready to apply. The dangerous direction.
3. **The refusal mapping above**, which would have claimed support falsely on
   an older agent.
4. **The discovery pattern**, which would have denied support universally.

The first two passed 25 tests because the fake ACL made the same mistake as
the parser: it put the capability in `scopes`. A fake that agrees with the code
proves only that they agree. The ACL documents those tests use are now
validated against the registry's own `acl/_shared` 0.1 and 0.2 schemas and then
run through the real parser, so the wire shape and the parse are each checked
by something that is not the other.

**The capability question now goes to `whoami`,** not the access list:
`auth/whoami/0.1` needs only a session — `acl/list` requires manage authority,
which a least-privileged phone does not have — and it answers `capabilities`
already resolved as the role's derived set intersected with the entry's
narrowing (`effective_capabilities`, `vti-common/src/acl/mod.rs:362`), plus
`scopes` as `ctx:<id>`. The run above confirms the shape in the field:
`roles=application scopes=ctx:vta`, exactly the grant that was made.

## The drift guard had never run

The vendored-schema check resolved `external/` relative to the bifold package,
where it never exists, and skipped per-file on anything missing upstream — so
it had never executed anywhere and would have passed vacuously if it had. It
now resolves the clone from the outer checkout (with a `TRUST_TASKS_REGISTRY`
override), compares each fixture against the commit its own `PROVENANCE.sha`
names, read from the object store, and **fails** on a file that commit lacks.

That matters because the `vta/pcs/*` fixtures are **off the shared pin** by
design: the pin is `7b6bb488` and those specs first exist at `15b91d1f`, so
this workstream cannot be graded against it. The pin was deliberately not moved
— it feeds spec-watch and conformance for everything else.

## Where the identity lives

The granted DID is in the wallet store of the app installed on
**`Hidden_Vet_API_33`**, an AVD cloned from the gate's shared
`Pixel_6_API_33` precisely so gate legs cannot wipe it. The copy was booted and
confirmed to recall the same 287-character DID before the gate's AVD was reset.
`ensureManagerIdentity()` recalls rather than mints, so the ACL entry stays
usable for 242 as long as that AVD's data survives.

**Two ways to lose it, both learned the hard way today:** booting with
`-no-snapshot-save` and then killing the emulator discards the session's disk
writes — that destroyed one granted identity outright; and any Appium session
with `noReset: false` clears app data at session start, which is why the
keep-state path exists. Save a snapshot explicitly before shutting down.

## Reproducing the probe

Nothing of this is committed: the hook and the driver were removed with the
worktree, deliberately, so a dev-only call cannot ship. The hook was seven
lines in `app/src/screens/Developer.tsx`, immediately after the existing
manager probe's `client.connect()`:

```ts
const serves = await client.servesPcs()
mark('[PCS-PROBE] servesPcs', serves === undefined ? 'undefined (inconclusive)' : String(serves))
```

The driver was an e2e script modelled on `run-vta-enrol.js`, with the
enrolment step replaced by a pause: it onboards, prints the minted DID, and
holds the session open until the ACL entry exists. That shape matters — the
first attempt split the work across two runs and lost the identity in the gap.

What a repeat needs: a mediator running (the app cannot finish onboarding
without one, and `react-native-config` bakes `MEDIATOR_URL` into the APK, so a
new invitation means a rebuild), Metro as its own process (`yarn android`
starts it as a child of the build and takes it down when the build exits), and
`ANDROID_AVD` naming the AVD actually booted.
