## 1. What upstream built

```
Attribute pool   agent-scoped   one value, held once
      ↑ referenced by
Face (Profile)   agent-scoped   ordered entries: ref | pinned | override | inline
      ↑ bound by
Binding          context-scoped face ↔ persona DID; pushes a materialised copy down
Local face       context-scoped inline-only; cannot reference the pool
```

It lives **on the VTA**, not the phone. Merged so far: slots, so a face can say
which entry is its name (#1605); pins honoured and purgeable (#1606); a
per-binding label that stops the holder's private face name crossing into a
context (#1597); the correlation index seeing values faces carry (#1594). Still
a proposal in the design note: `face/compose` and `attribute/promote` (§5.3),
manifest criteria that ask for attributes (§5.2), `FaceReach` (§5.4), and the
agent minting the persona DID itself when a face is worn (§9.7).

## 2. Where it agrees with our decision, and where it does not

**It agrees on the harm.** Brendan's reason for 1:1 — a profile linked to two
personas lets one edit silently change what both present, bridging correlation
scopes the person chose to keep apart — is the same harm upstream's design
exists to prevent.

**It disagrees on the mechanism.** Upstream deliberately allows one face to be
worn in several contexts ("edit once, everywhere is right for most
counterparties", §9.1) and protects the person three other ways:

1. **Local by default.** The recommended authoring path composes a face inside
   the context, from values typed there; nothing enters the pool, so no
   cross-context link exists until the person makes one.
2. **Sharing is an explicit, one-way act** (`attribute/promote`), and the UI
   must say "this value becomes reusable across faces".
3. **A correlation index** reports the same value presented by two personas in
   two contexts — including values typed separately into two local faces, the
   case a structural 1:1 rule cannot see at all.

A 1:1 constraint on our side would forbid something upstream allows on purpose,
while leaving uncovered the correlation upstream's index catches.

**It also moves the store.** Our profile is an `RCardTemplate` in the phone's
Credo wallet, used for wallet-to-wallet relationship credentials. Upstream's
face is on the VTA, used for what a community sees. They are not two copies of
one thing: they serve different counterparties through different stores.

## 3. Proposal

1. **Do not build `linkedPersonaDid` as specified yet.** Hold it until the
   mapping below is agreed, because building it first would bake the stricter
   rule into our data model.
2. **Keep the R-Card profile as the phone-side identity for Keyring↔Keyring
   relationships**, which is what it is today and what it is good at.
3. **For communities, use the VTA face as the store of record**, authored from
   the context as upstream recommends: when a person joins, the vetting screen's
   "Your face" step writes a context-local face (`persona/local/profile/put`,
   the legal name in a slot) rather than keeping the name on the phone. That is
   also the guide's disclosure model for the Vetting Card (VTI-Q6), so the
   deviation our reports have been declaring goes away with it.
4. **Keep Brendan's safety intent as a UX default rather than a constraint**:
   Keyring composes local faces unless the person explicitly chooses to reuse
   one, and shows upstream's correlation findings when they do.
5. **An R-Card profile may seed a face** — "use my Work profile's name here" —
   as a copy into a local face, never as a live link, so editing the R-Card
   profile never silently changes what a community sees.

## 4. Open, and not ours alone

- **Capability.** `PersonaHolder` is additive and granted by super-admin only.
  Our manager holds `admin` (VTI-23). Whether a phone manager should hold
  `PersonaHolder`, and who grants it, is a question for upstream before step 3
  can run.
- **Timing.** §5.2 (manifest asks for attributes) and §5.3 (compose/promote) are
  proposed, not merged. Step 3 can start on `persona/local/*`, which exists;
  the smoother flow waits on those.
- **Plan owners.** This companion proposes; it does not supersede
  [`2026-09-18-bam.md`](./2026-09-18-bam.md)'s decision. If adopted, the plan's
  §3 and §4.1 change with a companion recording it.
