## The VTA architecture question is resolved, not open

The parent workstream's own §2.4 ("Keys — and an open decision on who the member is",
`community_vetting_subtask.md`) reads as unresolved, but it has been answered on
`feat/prague-farm-membership`: `d5d526c6e feat(trust-tasks): the phone as manager of its
own VTA (architecture B)`, and a substantial amount of code built on that choice since. A
persona is concretely:

```ts
interface VtiPersona {
  communityDid: string
  vtaDid: string
  did: string                 // a did:webvh
  contextId: string
  vtaKeyIds: { signing: string; keyAgreement: string }
  kmsKeyIds?: { signing?: string; keyAgreement?: string }
  label?: string
  createdAt: string
}
```

(`bifold/packages/core/src/modules/trust-tasks/module/VtiIdentityStore.ts`, that branch.)
One persona per community, minted by `VtaClient.ensurePersona()` with no user-facing
naming step at all — `label` defaults to `keyring-<timestamp>` — and no connection to any
Profile data today. Storage is Credo generic records tagged `keyring/vti-identity`,
entirely separate from `rCardCredential.ts`'s `W3cCredentialRepository` use.

## r-card, persona, and VPC are formally defined, and related, in dtgwg-cred-spec

Read directly against `origin/main` (26 commits ahead of the pin, `b89f389` → `994a3d6`,
dated 2026-08-12 to present) rather than the stale pin, since this question needed current
text. Restored the pinned clone to `b89f389` afterward.

- **r-card**: *"A [VDS] containing a combination of human-readable and machine-readable
  data describing the publisher... typically exchanged in conjunction with VRCs... As a
  VDS, an r-card may be encapsulated in a standard VC... One use of r-cards is to serve as
  a modern, self-updating version of a vCard. The open standard specification for r-cards
  will be a deliverable of the DTGWG."* (`spec/terms-definitions/relationship_card.md`).
  The last sentence matters: our jCard shape isn't behind a published r-card schema —
  none exists yet, so there's nothing external to be out of conformance with.
- **persona**: *"an identifier the holder deliberately uses across a set of counterparties
  they choose, so as to be recognized as the same party by that set and by no one
  else... Membership in a VTC does not require a persona — a member who declares
  `pairwise` toward the community has none."* (`spec/terms-definitions/persona.md`). This
  corrects a framing I gave earlier in conversation, that personas exist to *stay*
  uncorrelated across communities — that's `pairwise`, a persona's opposite. A persona is
  the deliberate, opt-in mechanism for being recognized consistently by a chosen set of
  counterparties.
- **VPC**: *"A DTG annotation credential that enables one party to a DTG edge relationship
  to assert a persona to the counterparty... Asserting a persona is how an individual
  controls intentional correlation deliberately, rather than acquiring it as a side effect
  of reusing an identifier."* (`spec/terms-definitions/verifiable_persona_credential.md`).
  A VRC is a DTG edge credential (`verifiable_relationship_credential.md`), so a VPC
  riding a VRC is the spec's own mechanism for "let this relationship counterparty
  recognize me as this persona." Real and spec-sanctioned, but unbuilt anywhere in this
  codebase — grepped `feat/prague-farm-membership`'s trust-tasks module for
  `VPC`/`verifiable persona`, no real hits (only an unrelated test variable name that
  happens to contain the letters "VP").

## The Vetting Card is an r-card subtype in name, not yet in shape

`vtiVetting.ts`'s card (`feat/prague-farm-membership`) is typed
`['VerifiableDataStructure', 'RelationshipCard', 'VettingCard']` — declaring the same base
type our own issued R-Card credential does (`['VerifiableCredential', 'RelationshipCard']`,
`rCardCredential.ts`). Its actual shape is a flat, generic `{type, value, provenance}[]`
claims array plus session fields (`audience`, `challenge`, `domain`, `commitmentSalt`,
`identityCommitment`) — not jCard — and none of its fields are declared in any shared
JSON-LD context: `RCARD_CONTEXT_DOCUMENT`
(`bifold/packages/vrc-contexts/src/relationshipContext.ts`) declares exactly one property,
`card`, which `VettingCard` doesn't carry.

Both shapes are legitimate for their job, not a bug in either: jCard fits "hand a
counterparty your whole contact card once," a fixed, external, named-property vocabulary
(RFC 7095/6350). The claims array fits "assert exactly what this community's manifest
requires right now" — `application.requiredClaims = vetting?.requiredClaims ?? ['name.legal']`
is fetched from the community at runtime, not fixed by the client — with per-claim
provenance (`selfAsserted` today; the ceremony's later steps mark a claim
`documentVerified`) and a set-level commitment (`identityCommitment`), none of which a
fixed jCard property list expresses. Since no r-card schema is published (above), neither
implementation is behind a spec; they just don't share one today despite sharing a type
tag. That is why the decision below is about sharing *values*, not merging the two shapes.

## Decision: an optional, enforced 1:1 profile↔persona link

Settled in conversation, for user safety and clarity, explicitly stated as such: a profile
may link to at most one persona DID, and a persona to at most one profile — enforced in
both directions. **Rejected: any looser cardinality** (one profile powering several
personas, or several profiles claiming one persona). The reasoning is a safety property,
not a preference — a persona exists specifically to bound *who* gets to correlate a
holder across contexts (its `directed` scope, above); a profile linked to two personas
would let an edit made for one silently affect the other, bridging two correlation scopes
a user chose to keep apart. Applied to the plan's §3 and §4.1 (`linkedPersonaDid` field
and its uniqueness check).

Also settled: the credential-alignment work this surfaced (the vetting ceremony's own
already-described reciprocal-VMC step, `community_vetting_subtask.md`'s own step 11, not
yet sent by `vtiJoin.ts` though the reference server already accepts it) is scoped
narrowly to *this repo's client catching up to what the ecosystem's own fixed stack
already provides*, in service of the vetting demo already in progress — not a general
initiative to advance the VTI Rust stack, which is upstream's own and not ours to move
forward.
