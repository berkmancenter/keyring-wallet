## The VTA architecture question is resolved, not open

The parent workstream's own §2.4 ("Keys — and an open decision on who the member is",
`community_vetting_subtask.md`) reads as unresolved, but it has been answered on
`feat/prague-farm-membership`: `d5d526c6e feat(trust-tasks): the phone as manager of its
own VTA (architecture B)`, and a substantial amount of code built on that choice since. A
persona is concretely:

```ts
interface VtiPersona {
  communityDid: string
  vtaDid: string
  did: string                 // a did:webvh
  contextId: string
  vtaKeyIds: { signing: string; keyAgreement: string }
  kmsKeyIds?: { signing?: string; keyAgreement?: string }
  label?: string
  createdAt: string
}
```

(`bifold/packages/core/src/modules/trust-tasks/module/VtiIdentityStore.ts`, that branch.)
One persona per community, minted by `VtaClient.ensurePersona()` with no user-facing
naming step at all — `label` defaults to `keyring-<timestamp>` — and no connection to any
Profile data today. Storage is Credo generic records tagged `keyring/vti-identity`,
entirely separate from `rCardCredential.ts`'s `W3cCredentialRepository` use.

**This is a snapshot, not a live reference.** `feat/prague-farm-membership` is someone
else's active, in-review branch — this session watched three branches in this same repo

## r-card, persona, and VPC are formally defined, and related, in dtgwg-cred-spec

Read directly against `origin/main` (26 commits ahead of the pin, `b89f389` → `994a3d6`,
dated 2026-08-12 to present) rather than the stale pin, since this question needed current
text. Restored the pinned clone to `b89f389` afterward.

- **r-card**: *"A [VDS] containing a combination of human-readable and machine-readable
  data describing the publisher... typically exchanged in conjunction with VRCs... As a
  VDS, an r-card may be encapsulated in a standard VC... One use of r-cards is to serve as
  a modern, self-updating version of a vCard. The open standard specification for r-cards
  will be a deliverable of the DTGWG."* (`spec/terms-definitions/relationship_card.md`).
  The last sentence matters: our jCard shape isn't behind a published r-card schema —
  none exists yet, so there's nothing external to be out of conformance with.
- **persona**: *"an identifier the holder deliberately uses across a set of counterparties
  they choose, so as to be recognized as the same party by that set and by no one
  else... Membership in a VTC does not require a persona — a member who declares
  `pairwise` toward the community has none."* (`spec/terms-definitions/persona.md`). This
  corrects a framing I gave earlier in conversation, that personas exist to *stay*
  uncorrelated across communities — that's `pairwise`, a persona's opposite. A persona is
  the deliberate, opt-in mechanism for being recognized consistently by a chosen set of
  counterparties.
- **VPC**: *"A DTG annotation credential that enables one party to a DTG edge relationship
  to assert a persona to the counterparty... Asserting a persona is how an individual
  controls intentional correlation deliberately, rather than acquiring it as a side effect
  of reusing an identifier."* (`spec/terms-definitions/verifiable_persona_credential.md`).
  A VRC is a DTG edge credential (`verifiable_relationship_credential.md`), so a VPC
  riding a VRC is the spec's own mechanism for "let this relationship counterparty
  recognize me as this persona." Real and spec-sanctioned, but unbuilt anywhere in this
  codebase — grepped `feat/prague-farm-membership`'s trust-tasks module for
  `VPC`/`verifiable persona`, no real hits (only an unrelated test variable name that
  happens to contain the letters "VP").

## The Vetting Card is an r-card subtype in name, not yet in shape

`vtiVetting.ts`'s card (`feat/prague-farm-membership`) is typed
`['VerifiableDataStructure', 'RelationshipCard', 'VettingCard']` — declaring the same base
type our own issued R-Card credential does (`['VerifiableCredential', 'RelationshipCard']`,
`rCardCredential.ts`). Its actual shape is a flat, generic `{type, value, provenance}[]`
claims array plus session fields (`audience`, `challenge`, `domain`, `commitmentSalt`,
`identityCommitment`) — not jCard — and none of its fields are declared in any shared
JSON-LD context: `RCARD_CONTEXT_DOCUMENT`
(`bifold/packages/vrc-contexts/src/relationshipContext.ts`) declares exactly one property,
`card`, which `VettingCard` doesn't carry.

Both shapes are legitimate for their job, not a bug in either: jCard fits "hand a
counterparty your whole contact card once," a fixed, external, named-property vocabulary
(RFC 7095/6350). The claims array fits "assert exactly what this community's manifest
requires right now" — `application.requiredClaims = vetting?.requiredClaims ?? ['name.legal']`
is fetched from the community at runtime, not fixed by the client — with per-claim
provenance (`selfAsserted` today; the ceremony's later steps mark a claim
`documentVerified`) and a set-level commitment (`identityCommitment`), none of which a
fixed jCard property list expresses. Since no r-card schema is published (above), neither
implementation is behind a spec; they just don't share one today despite sharing a type
tag. That is why the decision below is about sharing *values*, not merging the two shapes.

## Decision: an optional, enforced 1:1 profile↔persona link

Settled in conversation, for user safety and clarity, explicitly stated as such: a profile
may link to at most one persona DID, and a persona to at most one profile — enforced in
both directions. **Rejected: any looser cardinality** (one profile powering several
personas, or several profiles claiming one persona). The reasoning is a safety property,
not a preference — a persona exists specifically to bound *who* gets to correlate a
holder across contexts (its `directed` scope, above); a profile linked to two personas
would let an edit made for one silently affect the other, bridging two correlation scopes
a user chose to keep apart. Applied to the plan's §3 and §4.1 (`linkedPersonaDid` field
and its uniqueness check).

Also settled: the credential-alignment work this surfaced (the vetting ceremony's own
already-described reciprocal-VMC step, `community_vetting_subtask.md`'s own step 11, not
yet sent by `vtiJoin.ts` though the reference server already accepts it) is scoped
narrowly to *this repo's client catching up to what the ecosystem's own fixed stack
already provides*, in service of the vetting demo already in progress — not a general
initiative to advance the VTI Rust stack, which is upstream's own and not ours to move
forward.

## Entry point reconsidered: a Settings row is not where users look for "edit me"

A later session the same day, starting Phase 1 implementation. §4.2 as drafted specified
a plain Settings row, following the `Screens.ChangePIN` pattern exactly. Before wiring
that up, checked whether Keyring's existing tab chrome offered a more natural home —
users expect to find "edit my own info" behind something that looks like *them*, not a
row among toggles.

A fork surveyed the current bottom tab bar (`TabStack.tsx`) and header idioms
(`ContactStack.tsx`'s `headerRight`, `IconButton`/`WitnessHeaderButton`). Findings: the
tab bar already has six peer tabs (Contacts, Messages, QR, Wallet, MyAgent, Settings) —
Settings is not buried behind a hamburger, it is already one tap away. No avatar/profile
affordance exists anywhere in the app's main chrome today. No prior plan document
considered or rejected a header- or tab-level placement for this — genuinely open.

Considered three shapes, in conversation with the user:

- **A — plain Settings row (§4.2 as drafted).** Zero navigation changes, but
  underweights "edit my own profile" relative to how prominent it feels in comparable
  apps (WhatsApp, Telegram, Signal all surface it as the first thing you see, not a row
  among many).
- **B — an additional header button** elsewhere (e.g. on the Contacts landing screen),
  reusing the `IconButton`/`WitnessHeaderButton` idiom, *in addition to* a Settings row.
  Rejected: adds a profile affordance to a screen (Contacts) that has nothing else to do
  with the user's own profile, and creates two disconnected entry points to maintain.
- **C — rename the existing Settings tab to "Profile" and put a profile card (avatar/
  name, tap to edit) as the first thing on that screen, with the existing settings
  sections unchanged below it.** This is the WhatsApp/Telegram/Signal pattern: the tab is
  already a peer bottom-tab destination (per the survey above), so this is a relabel plus
  a reorder, not a new navigator or a new tab slot.

**Decided: C.** It gets the "tap something that looks like me" affordance the user
described without adding a seventh tab or a second, disconnected entry point. Concretely:
only the *user-facing label* changes (the `Screens.Settings` translation string, used
identically by the tab bar, the stack header, and the two existing hamburger-style
`accessibilityLabel`s in `SettingsMenu.tsx`/`HistoryMenu.tsx` — all four call sites read
that one key, so retranslating it relabels all of them together) — the internal
`Screens.Settings` / `Stacks.SettingStack` / `SettingStack.tsx` identifiers are unchanged,
since the screen still *is* the settings screen, now fronted by a profile card. The tab
icon also changes, from the generic hamburger/menu glyph to an account/person glyph, to
match the new label. This supersedes §4.2's "Entry point" paragraph as drafted.

**Deferred, not designed:** using the user's own live R-Card photo as the tab icon
(rather than a generic account glyph) — a nice-to-have that needs the tab bar to read
`useRCardCredential()` and handle the loading/no-photo states, out of scope for landing
Phase 1's edit capability.

## e2e safety check on the Settings→Profile relabel

The user asked, mid-implementation, whether relabeling the tab would break any e2e test
that navigates to Settings. Checked by reading, not running (no built binaries/emulators
in this session) — `e2e/lib/flows.js` is the only e2e code that reaches Settings, at two
call sites (the Secure-Exchanges-toggle flow and the developer-mode flow), both via
`tapTestId(driver, "Settings", ...)`. `tapTestId`/`waitForTestId` (`e2e/lib/driver.js`)
resolve elements strictly by React Native `testID`, never by visible text or
`accessibilityLabel` — confirmed by reading `waitForTestId`'s implementation, and by
grepping `e2e/` for any text- or accessibility-label-based lookup of "Settings" (none
found).

This is exactly why `TabStack.tsx`'s `tabBarTestID: testIdWithKey('Settings')` was
deliberately left unchanged above, while only the *visible* label (via the
`Screens.Settings` translation) and the tab icon changed — the relabel is invisible to
`tapTestId`-based navigation by construction, not by luck. If a future change ever
renames that testID (e.g. to `'Profile'`, for consistency with the new label), both
`e2e/lib/flows.js` call sites need updating in the same change, and this file's "no
e2e reference to the old label text" finding should be re-verified against `e2e/`'s
state at that time — it was correct as of this session's read, not a standing guarantee.

**Not done:** actually running `yarn e2e:vrc` or any other e2e suite against this
change — the check above is static (reading the driver/flow code), not an executed
regression test.

## Phase 2 implementation session: resolving the active profile without Redux access

A later session the same day, implementing Phase 2 (§5.2 of the plan). §4.1's data
model gives `loadRCardTemplate(agent, profileId)` a required-looking `profileId`, but
two real call sites — `buildRCardCredential` and `buildLegacyIssuerObject`
(`vrc-manager.ts`) — only ever have `agent` in scope, deep inside DIDComm
connection-event handling with no React tree and no access to `useStore()`. Neither
call site changed in this implementation (per §4.3's "zero change to the automatic
offer machinery beyond the query key"), which meant something *other* than
`RCardState.activeProfileId` had to answer "which profile is active" from `agent`
alone.

**Decided: a Credo tag, `active: 'true'|'false'`, on every `RCardTemplate` record,
written and read entirely within `rCardCredential.ts`.** `loadRCardTemplate(agent)`
(no `profileId`) queries by that tag; `loadRCardTemplate(agent, profileId)` queries by
`templateId` instead. `setActiveRCardProfile(agent, profileId)` is the single place
that ever writes it — it sets the target `true` and every other `RCardTemplate` record
`false` in the same call, so "at most one active" is enforced by construction rather
than assumed. `RCardState.activeProfileId` is kept in sync by dispatching
`R_CARD_ACTIVE_PROFILE_SET` whenever `setActiveRCardProfile` succeeds, but it is a
mirror for the UI layer's convenience, not the source of truth — a distinction this
plan's earlier text didn't draw, since it hadn't yet hit the concrete call sites that
make the distinction load-bearing.

*Rejected: giving `buildRCardCredential`/`buildLegacyIssuerObject` an explicit
`profileId` parameter*, threaded down from wherever the DIDComm event handler that
calls them originates. Traced that call chain (`issueRCardCredential` ← a
connection-state event ← the DIDComm event bus) and found no point on it that has, or
should acquire, a dependency on the app's Redux store — that machinery is agent-scoped
by design, matching how every *other* piece of state it touches (relationship DIDs,
peer capability flags) is already resolved from `agent`/Credo alone, not passed in from
React. Adding a Redux dependency there would be the actual scope violation, not the
tag.

**Other decisions made without new plan text, applied directly to the plan's §4.3
rather than left only here, since an implementer reading the plan alone needs them:**
the Settings profile card now opens `Screens.MyProfiles` instead of `EditRCard`
directly (a single profile card had one obvious destination; multiple profiles do
not), and `EditRCard` takes an optional `profileId` route param — given, edit that
profile; omitted, create a new one — rather than a separate create screen, since the
form itself (§4.2's `RCardForm`) is already shared.

**Test coverage limit, noted rather than papered over:** the connect-time switcher's
unit tests (`QRScanner.test.tsx`) prove the picker calls `setActive` with the right id,
and that mounting fresh with either profile active produces an invitation — they do
NOT prove that switching live, on an already-mounted screen, regenerates the
invitation end-to-end. Driving that through a real store dispatch inside `act()`
reproducibly threw `TypeError: reducer is not a function` deep in
`react-test-renderer`'s `useReducer` internals, in this file's fake-timer setup,
for reasons not root-caused (see the feedback filed this session on that failure
mode). The plan's own §5.2 step 5 already designates `yarn e2e:vrc` as the
verification method for exactly this behavior, so the gap is left to that, not forced
into a fragile unit test.
