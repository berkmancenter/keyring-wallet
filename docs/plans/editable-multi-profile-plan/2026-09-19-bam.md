# 2026-09-19 — BAM

Design decision for two related feature requests that came in after the R-Card
photo-crop work this session, both scoped against this plan's §4.3 storage
question. Parent: [`editable-multi-profile-plan.md`](../editable-multi-profile-plan.md).

## What was decided: shared-profile *visibility*, not *binding*

§4.3 already anticipated this connection-keyed storage question and deliberately
deferred one specific capability under it — **a true per-connection profile
binding**, where a contact would keep being offered a specific profile on future
exchanges even after the user's active profile changed (§7's still-open item).
That capability remains undesigned; nothing below builds it.

What was actually requested, and built, is narrower: **show, on a contact's own
detail page, which of the user's profiles was shared with them** — a read-only
display feature, not a change to which profile future exchanges offer. The two
are easy to conflate because they touch the same record; they are not the same
feature, and this note exists so a future reader doesn't assume this closed
§7's open item.

**Live lookup, not a frozen snapshot** — the user's explicit call, and the reason
this isn't a simpler "record it once and print it" feature. If the profile is
later renamed, the contact page shows the *current* label, not what it was at
share time. Only once the profile is **deleted** does the page fall back to a
label snapshot taken at share time. This mirrors §4.3's existing "most recent
wins, not a history" rule for `RelationshipDidRecord` — one row per relationship,
updated in place.

## Where it lives

Two fields added to `RelationshipDidRecord`
(`bifold/packages/core/src/modules/vrc/types/RelationshipDidRecord.ts`):

- `sharedProfileId?: string` — the live key. `ContactDetails.tsx` resolves it
  against `useRCardCredential().profiles` at render time, the same live list the
  "My Profiles" screen already reads.
- `sharedProfileLabel?: string` — the fallback-only snapshot, used solely when
  `sharedProfileId` no longer resolves (profile deleted). Never preferred over
  the live value.

`sharedProfileId` is also a queryable tag (`getTags()`), which is what makes the
second feature possible without a new query mechanism.

Written from `issueRCardCredential`
(`bifold/packages/core/src/modules/vrc/vrc-manager.ts`), immediately after a
successful `offerCredential` call, via a second `loadRCardTemplate(agent)` call
(cheap — same pattern already used elsewhere in this file for the active
profile) and a new `RelationshipDidRepository.updateSharedProfile()`. Recording
is best-effort: a failure there is logged and swallowed rather than surfaced,
since by that point the credential offer has already gone out and there is
nothing to roll back.

## The second feature this unlocks: warn before deleting a shared profile

`MyProfiles.tsx`'s delete action had no pre-delete confirmation at all in the
normal case. Since `sharedProfileId` is now a tag, "how many contacts currently
have this profile recorded as shared" is a single indexed query
(`RelationshipDidRepository.countBySharedProfileId`), which is what makes a
delete-time warning cheap to add. If the count is zero, delete proceeds exactly
as before (the user didn't ask for a blanket confirmation, only one gated on
actual impact). If it's nonzero, a new `ModalUsage.ProfileDeleteWithContacts`
case on the existing `CommonRemoveModal` component asks to confirm, naming the
count, before calling through to `remove()`.

This does **not** attempt to fix up affected contacts' `sharedProfileId` on
delete (e.g., clearing it, or re-pointing it) — the live-lookup design above
already handles a deleted profile gracefully (falls back to the label
snapshot), so there's nothing to clean up.

## Status

Implemented and tested (unit tests on `RelationshipDidRecord`,
`RelationshipDidRepository`, `issueRCardCredential`'s recording behavior,
`ContactDetails`'s live/fallback display, `MyProfiles`'s warn-then-confirm
flow, and `CommonRemoveModal`'s new usage). Not yet verified on-device — see
`/srv/dev/scratch/2026-09-19-bam-rcard-photo-and-profile-contact-tracking.md`
for that session's device state and the on-device verification this still
