# 2026-10-24 — Sending an edited card to contacts who already hold the old one (al)

**Plan:** [`../editable-multi-profile-plan.md`](../editable-multi-profile-plan.md).
**Read at:** wallet `main` `fa53c341` and bifold `main` `f133052d`.
**Status:** proposal only. It adds a later item to §7, and changes nothing the plan has shipped.

## 1. The question

If a user edits their card, or edits a profile that some contacts already received, does the contact's phone ever see the change?

## 2. Today: no, by design

**The plan says so.** §1 and §4.2: "Existing contacts who already hold an issued R-Card from before an edit or a profile switch keep exactly what they were issued — re-issuing is required for them to see a change". This semantics is inherited from `rcard-profile-picture-plan.md` §3.6.

**The code agrees.**
- **Sent once per connection.** `issueRCardCredential` (`packages/core/src/modules/vrc/vrc-manager.ts`) sends the card once, guarded by an in-memory per-connection lock (`connectionRCardOffers`).
- **Not resent on upgrade.** Upgrading a relationship in place (bifold #471) deliberately does not resend the card.
- **The first exchange cannot simply run again.** The automatic first exchange must stay once per connection, because restart recovery depends on it.

## 3. What already exists that an update would build on

- **The receiver accepts any card on an existing connection.** The credential-state handler in `vrc-manager.ts` auto-accepts every `RelationshipCard` offer it receives. It does not check that the card is the first one on that connection.
- **The receiver shows the newest card.** When a phone holds more than one card from the same relationship DID, `utils/rcardDisplayUtils.ts` picks the most recent by `validFrom` / `issuanceDate`.
- **The sender knows which profile each contact got.** The 2026-09-19 companion added `sharedProfileId` and `sharedProfileLabel` to `RelationshipDidRecord`. `sharedProfileId` is a queryable tag, so "every contact who holds the Work profile" is one indexed query.

So a fresh card sent over an existing connection would very likely be accepted and shown already. That conclusion is from reading the code and has not been run.

## 4. Proposed design

**Sending side.**
1. **Offer to share the edit.** After a profile is edited, offer to send the update: "Share this update with the 12 contacts who have your Work card?". Never send silently.
   - The list comes from the `sharedProfileId` query.
   - The user can deselect contacts.
   - "Not now" leaves contacts on the old card, as today.
2. **Use a separate update path.** It sends a fresh card over each chosen existing connection. It does not reuse the first-exchange lock, and it leaves that lock untouched, because restart recovery depends on it.
3. **Record which version each contact holds.** Store a version or timestamp of the card each contact holds on `RelationshipDidRecord`, beside `sharedProfileId`. That lets the app show "3 contacts still have an older version" and avoid repeat sends.

**Receiving side.**

4. **A visible notice, not silent replacement.** The phone shows "Alex updated their card", and **See what changed** compares the new card with the one it replaces, field by field (name, email, organisation, photo). The new card is what the contact list shows, as it is today. The notice is what makes the change visible.

   This matters for safety as well as convenience. Because any new card is accepted automatically, a contact could otherwise rename themselves to resemble someone else without the user noticing.
5. **No exchange overlay.** An update does not show the "exchanging contact cards" overlay that a first exchange uses (`vrcFlowStore.markRcardReceivePending`).
6. **The older card stays.** It is kept in storage, so "See what changed" has something to compare against. Pruning older copies is a later decision.

## 5. Edge cases

- **Contacts on app versions before the RCard format** cannot receive it (`counterpartySpeaksVc20`). They keep the old card, and the sender's list says so.
- **Offline contacts** receive the update through the mediator when they next connect.
- **Duplicate rows for one person** (IN-354): each relationship is separate, so each gets its own update. The planned "Same person? Merge" work does not change that.
- **A deleted profile** sends nothing. Contacts keep the last card they received, which matches the existing "share-time label snapshot" fallback (2026-09-19 companion).

## 6. Size and testing

**Size, an estimate.** About one to two weeks:
- the update action with its prompt and contact list;
- the version field;
- the receiver notice with "See what changed";
- unit tests, and one two-phone run.

No protocol change is needed: it is the same `RelationshipCard` credential the first exchange already sends.

**Testing.** Two-phone features have passed CI and review and still not worked on devices. So this needs a run where one phone edits and sends, and the other phone shows the notice and the new card. Unit tests alone are not enough. The cases to cover:
- a contact who already holds the old card;
- a contact on an older app version;
- an offline contact who reconnects later;
- "See what changed" showing exactly the fields that differ.
