## Part 0 — How to implement any of this: carefully, cheapest and most valuable first

The gate and the CI pipelines work today, and releases depend on them. Every step taken from this plan follows these rules.

1. **Do not break what works.** A step changes one thing at a time and can be reverted on its own. Required checks, store builds and the release gate keep behaving exactly as they do now until the step has been proved.
2. **Cheapest and most valuable first.** Start with the steps that cost little, carry little risk and save the most time, and measure each one before starting the next. Bigger or riskier steps (a new harness tier, retiring device runs, new hardware) come last, and only when the earlier numbers justify them.
3. **Measure before and after.** Every PR records the baseline it starts from and the number it produced: job minutes, gate minutes, flake rate. A step that does not move its number is reverted or rethought, not stacked upon.
4. **Prove on the test path before the release path.** Build and caching changes go to `test-builds.yml` first and run green across several runs before anything similar touches a store or release workflow. Pushing to the `staging` branch is never used to try anything, because a push there ships its code to every tester. This has happened once already.
5. **No coverage lost.** A check moves to a cheaper layer only when the cheaper layer runs the same code (the plan's own principle 1). A device run retires only under the team's existing two-release rule (Part 3).
6. **Respect shared machines.** Heavy runs (Jest, builds, gate legs) take a slot on the shared Macs, one heavy job at a time. Each step that adds caches, snapshots or build trees states its disk use and how it is cleaned up.

## Part 3 — Conflicts with decisions already made

- **B7 (staging builds stop waiting on tests): drop it, or move it to the release-flow plan.** The `staging` branch is being retired, and a push to it ships to every tester. The measured saving is also small: about 5–6 minutes of about 51.
- **E6 (parallel device pairs) and Tier 3 (emulator e2e on every PR):** these work only for hermetic suites. Two lanes on one Farm runner collide on its access list and rate limit. That was decided on 2026-10-14, and it is why each Farm-backed lane needs its own runner and why the gate's halves run one after the other.
- **T4.1 and §4.7, retiring device runs:** the existing rule is that a device row leaves the per-release gate **two releases** after its Jest twin lands, and then stays nightly (2026-10-14 companion, decision 5). Rule 6's "three CI passes" should become that. T4.1 should also say that the core journeys never retire from the per-release gate:
  - vetting, including hidden vetting;
  - joining;
  - agent link;
  - the mediator;
  - sign-in.
- **E5 (make the invitation readable in e2e builds):** exposing the invitation in release test builds was **rejected on 2026-10-15**. The release-build alternative is the share-link path (`run-pair-ios.mjs`, the `pair-ios` leg), whose iOS clipboard read is still open (#605). The companion's row calling E5 "compatible" is incorrect.

  The gate lane rates E5 as the single most valuable item, because the gate has no Release-build exchange evidence today. **Whether to reopen that decision belongs to the product owner.**
- **P2 (an in-app contract screen in test builds):** this sits close to the same 10-15 rejection. The precedent the other way is `E2EClockRows`, shown in test builds only. The plan should say why P2 is acceptable where that rejection applied.
- **§8 Tier 3 cost:** about USD 5k, against the stated budget of USD 50 now and up to USD 400 later. Tier 2 (emulators on hosted runners) already runs for free in `gate-smoke.yml` and `gate-ci.yml`.

## Part 4 — What the plan misses

1. **The release gate's time is not in the VRC family.** No `run-vrc-exchange*` runner is in the gate today, and `e2e:vrc` cannot run on Release builds. So the Node tier (T2) and the VRC retirements (T4) take **zero minutes** off the gate as it runs.

   The gate's time is Farm-backed onboarding and linking (36%) plus the serial Farm turn. The levers for that are already in the subtask and still owed:
   - item 6, merging relaunch into update;
   - item 7, the shared linked phone;
   - phase 3, lanes on separate runner VTAs.
2. **The harness is the main source of red legs** (8 of 13), and the automatic verdict mislabels them. A corrected verdict step should come before any ledger-driven policy. New harness code is proved before a gate relies on it: `dry --golden`, the gate's tests in CI, and build identity.
3. **Build identity on every device.** A device left on the previous build gave a false pass (fixed in #596). Every canary, snapshot or "frozen artifact" run checks each device's bundle hash against the candidate.
4. **Two-phone features need a two-phone run on the Release build.** A feature with a mocked pipeline passed CI and review but did nothing on devices; a two-simulator run caught it. The Node harness (T2) must drive the real Trust Task pipeline, and retirement must keep a two-phone Release run.
5. **Native changes need a compile check.** Native-path PRs get test builds (`test-builds.yml` path filters, #572, #602). B2–B4 and A2 change native configuration and must wait for those checks by name. B1 must not bypass them.
6. **Shared machines.** On two release candidates, most Android legs broke within seconds on the memory swap guard. The rule is one heavy job at a time, `--maxWorkers=2` for Jest, and the gate on the mini first.
7. **Disk.** An iOS Release simulator build is about 8.4 GB, and a debug build of both platforms is about 16 GB. The mini has a 256 GB disk and was at 16.8 GB free today. U2, B2, B4 and E2 each need a disk budget and a cleanup rule.
8. **The emulator cannot complete Android sign-in.** The user-verification prompt is biometric-only, and the emulator's fingerprint token reads as expired (`e2e/gate/gate.sh`, the comment above `LEGS_ANDROID`). A1 reaches the attestation key only. §9's "simulated biometrics … reliable" should be corrected.
9. **Farm and mediator behaviour:**
   - one mediator connection per identity;
   - rate limits shared per runner;
   - root health probes answered by the CDN while the origin is down, so probe `did.jsonl` and `pnm health` instead;
   - upstream VTI binaries pinned to release or nightly tags, never to VTI `main`.

   All 4 environment reds were Farm or mediator. The subtask's mediator round-trip row (item 16) is unbuilt.
10. **Duplicate package copies.** Two copies of a package break `instanceof` and singletons, and this has happened three times. T2.2's new Node bindings need single-copy mapping in Jest and Metro (core `jest.config.js`, `app/metro.config.js`).
11. **Tests must be found by CI, not listed.** A hand-kept list let 34 harness tests run nowhere until #586. T0.3's `runners.tsv` should be generated rather than hand-kept, and a Node harness in a new package needs its own CI job, or it will run nowhere. Fourteen harness tests still run nowhere (`scripts/ci/tests-need-install.json`).
12. **The TUI driver.** The openvtc TUI leg is red on every run because of its 3-second read. Subtask §8 already says to wait on state; it is not done yet.
