# 2026-11-24 — The memory binding is the VTA's: a fixed set per agent (rev 4)

Companion to [`../agent-connect-plan.md`](../agent-connect-plan.md). Not revised afterwards.

## Summary
<!-- plan-part: human -->

> **Human part: for people deciding and reviewing.** What was concluded and what it
> asks for. The findings below are authoritative; if the two disagree, the findings win.

The product owner decided on 2026-11-24 that a language model must never be the thing that decides whether a memory is honoured. Revision 3 let the owner pick, per room, which of an agent's memories it uses there, and trusted the agent's plugin to keep to the pick. That is withdrawn. An agent is now **bound, on the VTA's own access entry for it, to a fixed set of memories** chosen when it is connected. The VTA already refuses any memory that is not on the entry, on every call, whatever a room says; nothing in a room or in the model can change that. If the owner wants a college's room to see "Education" and a clinic's room to see "Healthcare", they connect two agents, one for each, and the room's screen offers "Connect another agent". The room offer still lists the agent's memories, but only as information.

The question of whether Keyring can create the memories at all was checked in the VTA's code. A context at the top level needs an unrestricted administrator. The owner's phone is one by design on their own VTA, so Keyring can create memories directly. The product owner later stated that Keyring always connects as an unrestricted administrator (plan §1.5, finding 14); an `auth/whoami` check at connect time ends the connect with a clear failure if a session is not one. A one-time parent context made by a super-admin was considered and is not built. Both give an agent exactly the same binding; the difference is who else could reach the memories (the finding below).

The same pass settled the smaller gaps. Deleting a memory purges what it remembered, and the VTA's own warning does not count those items, so Keyring counts them and asks. Wiping what an agent remembered is a loop Keyring runs and can safely re-run. Memory is text up to 64 KiB an item, not files, with no quota, no expiry and no encryption of its own, and the screens say only that. Ids are opaque and random (`keyring-memory-k7m2q9x4tb`), with the owner's label in the context's `name`, so no topic sits in ACL entries, audit rows or logs. The three decisions left to the owner were all made on 2026-11-24: direct creation after the whoami check, an opaque random id, and widening behind a biometric approval naming every room.

Six asks go upstream as VTI-Q39 to VTI-Q44, and VTI-Q37 (a room-scoped binding) becomes a convenience. A later pass the same day found that memory is encrypted only when the VTA holds a storage key (not in standard mode) and that nothing bounds how much an agent can write; the screens claim no encryption (finding 10). The kit mockups were redrawn and four added; the UI/UX canvas frames that carry the old design are listed in finding 11.

### 1. The binding is the ACL entry (D31); D29's per-room half is withdrawn

- **Concluded:** an agent's memory set M is fixed on its entry's `act` at connect, as exact context paths; rooms add only the persona's context (§3.3); a different set is a different agent identity; the room offer's `contexts` is informational; changing M is an owner act in Keyring (narrow with one confirmation, widen with the biometric decision, naming every room it applies to); reconcile shows any other context on the entry as drift with "Restore". Plan §3.15 (rewritten), §3.2 step 1, §3.3, §3.6 steps 3 to 5, §3.7, §3.9, §3.11, §6, §7 step 7, §9 threat 11, D29 (replaced), D31, D11, D22.
- **Old:** the owner picked per room which memories the agent used; Keyring sent the list in the offer; the plugin "kept to" it; the copy said the VTA could not enforce it; one agent per room was offered as the enforced form (rev 3, [`2026-11-23-al.md`](./2026-11-23-al.md) finding 3 and 4).
- **Why:** what the plugin keeps is a request to software driven by a model that reads room text, so a prompt injection or a plain model mistake decides whether a memory is used. The VTA decides on every call: memory tasks need the memory capability and `require_context` for the memory's context (`trust_tasks/memory.rs:89-90`), `act` covers a context and its subtree and nothing else (`vti-common/src/auth/extractor.rs:407`, VTI-CTX-017), and the decision is derived from the entry alone (VTI-ACL-001). Rev 3 already knew the enforced form was one entry per distinct set; it called it a workaround. It is now the design.
- **What it keeps:** top-level memories granted by exact path; the persona-context widening of §3.3 (still shown); the room add flow, the composer's "+", the VDC, revoke by `deviceId`; the `act` narrowing semantics ("a later narrowing binds the next request", §2.1).
- **What it costs:** more agents (two did:keys, entries, VDCs and plugin sessions for two sets), and P is shared: adding an agent to a room still adds the persona's context and the memory capabilities apply to it (§3.3, VTI-Q29). A **prompt-injected agent can read and overwrite its whole bound set from any room it is in**; the boundary is the set, so a memory not to be exposed to room text is kept out of the set of an agent that is in that room (§9 threat 11).
- **Residual:** one identity cannot have different sets per room (VTI-Q37, now a convenience); a widened or restored entry is judged at the next request, so there is a window after widening only for requests already in flight; drift is detected at reconcile (app start, list, details), not instantly (VTI-Q34's lack of a push signal applies).

### 2. The blocker: who can create a memory

*Read with finding 14: the unrestricted-administrator assumption (plan §1.5) replaced option B and the "otherwise" wording below; the connect ends with a clear failure for a session that is not one, and the parent route is not built.*

- **What the code says.** `create_context` runs `ensure_may_create_context` (admin role, or the additive `context-create` capability; `operations/contexts.rs:67-84`), then for `parent = None` `auth.require_super_admin()` (`:125-126`); `require_super_admin` is admin with an unrestricted scope (`vti-common/src/auth/extractor.rs:393,551`; `act_scope_for`: an admin with no contexts is `All`, `vti-common/src/acl/mod.rs:746-752`). A sub-context needs `require_context(parent)` and an existing parent, answered `create:parentNotFound` either way (`:127-146`). Spec: VTI-CTX-020, "Creating a root context MUST require unrestricted act authority." `context-create` is additive, granted only by a super-admin, and reaches only sub-contexts (`acl/mod.rs:405-428`, appendix line 247). Renaming a display `name` is super-admin only (`:231-238`); an id has no rename and a context's derivation base is fixed at create (VTI-CTX-021).
- **What session Keyring has.** `VtaClient.grantAdmin` writes an admin entry "that names no scopes (unrestricted)", and says only a super-admin may create one (`bifold/packages/core/src/modules/trust-tasks/module/VtaClient.ts:2444-2475`); `addBackupDevice` (`vtaAgent.ts:2735-2790`) uses it, so a phone that works as designed is a super-admin of its own VTA. `VtaClient.createContext(id, name)` and `listContexts` already exist (`VtaClient.ts:2649-2656`) and nothing calls them; the phone's persona context is `keyring` (`PERSONA_CONTEXT_ID`, `:409`), made elsewhere (the comment at `:2805-2810` says the phone makes no context itself). `vtaAgent.ts` (`approvalRules`) reads `me.scopes` and `me.contexts` to tell a `scoped` session, so a scoped phone is a state the code expects. **Not verified:** that every linked phone is unrestricted on a live VTA (a Farm VTA, a phone added by another administrator). The plan asks `auth/whoami` and records it in step 0.1(p).
- **So:** the owner's session can create top-level contexts **when it is a super-admin**, which is the designed state. If not, it cannot, and nothing Keyring can do from that session changes that.

**Options, recommendation first. DECIDED by the owner on 2026-11-24 (plan §11 Q2, D32): option A; option B stays a documented fallback only, not built; step 0.1(p) still measures the phone's session live.**

| Option | Pros | Cons |
|---|---|---|
| **A (recommended). Create top-level memories from the owner's own session when `auth/whoami` shows an unrestricted administrator; the documented fallback is B** | The phone is a super-admin by design, so no provisioning step and no new code path; no common ancestor, so no entry anywhere can reach several memories by naming one id; a delete is isolated; ids stay one simple segment | Not available to a phone that is scoped; memory ids sit in the VTA's root namespace beside the operator's own contexts (the prefix and owner segment mitigate, `Conflict` decides) |
| B. A Keyring-owned parent `keyring-memory` made once by a super-admin; memories `keyring-memory/<random>` made by a session scoped to it; agents granted each child by exact path | Keyring can run with a scoped session; one tidy parent in listings; a context policy on the parent also binds every child (a child cannot widen what an ancestor allows, `vta-support/src/contexts.rs` `effective_context_policy`) | A one-time super-admin step with no screen yet; **any entry that names the parent reaches every memory** (including a scoped administrator Keyring runs as, and a mistaken grant, which reconcile must catch); deleting the parent deletes every memory (`NotEmpty` counts sub-contexts, so `force` is needed, but one tap away); depth two |
| C. A `context-create` provisioner entry for a second Keyring identity | Least privilege for the creator | Granting it is super-admin only, so it still needs the one-time step; reaches sub-contexts only, so it is B with a second identity |
| D. Change the VTA (VTI-Q39) | Removes the dependency on a super-admin | Not needed while the phone is one; upstream's decision and time |

**Sub-context versus top level, truthfully.** Against an *agent*, the two are identical when the agent's `act` names the exact child path: `act` covers that path and its own subtree only, and VTI-CTX-017 extends authority down, never up or sideways, so a sibling or the parent is out of reach (`ActScope::covers`, segment-aware, VTI-CTX-016; `keyring` does not cover `keyring-memory`). The isolation difference is **who else** reaches the memories: under a parent, every holder of the parent, reaches all of them; at the top level only unrestricted administrators and entries naming the exact context do. Neither is safe under the **persona's** context (`keyring`): every agent added to a room holds it (§3.3), so a memory beneath it is read by all of them, which is why memories are never put there. A sub-context also costs a counter and derivation base per context like any context (`allocate_context_index`), and nests its base under the parent (VTI-CTX-022), which is irrelevant to memory but not free.

### 3. The memory id is opaque (D35, decided 2026-11-24)

- **Decided by the owner:** a memory's context id is `keyring-memory-<random>`, `<random>` being 10 lowercase base32 characters (50 bits) from the phone's secure random generator, for example `keyring-memory-k7m2q9x4tb`. The id is never derived from the name, a slug or the owner's DID, is never typed or shown to the owner, never used for room attribution, never shown to room members and never parsed for a decision; a collision on create is a fresh draw (no suffix scheme); the owner's label is the context's `name`. This replaces D33.
- **Why:** an id lives for good in ACL entries, audit rows, session token claims and logs, and cannot be renamed. A topic in it (`healthcare`, `divorce-lawyer`) would be recorded in all of them. A hash of a name is recomputable from a dictionary (`sha256("healthcare")`), and a hash of the owner's DID only links one owner's memories to each other. Random keeps the topic out.
- **Considered and rejected (in the order they were proposed):** a readable owner segment (`keyring-memory-alice-7k2q-education`: a real or pseudonymous label in every id, and a topic slug); a two-word handle plus a hash (a word list and a "readable owner" no reader needs, since the id is never shown to room members and owners see the `name`); an owner hash of 6 or 8 base32 characters (6 is grindable by a co-tenant in about 10^9 hashes; either only links memories, and Keyring talks to its owner's own VTA, where every memory has one owner); a readable slug of the name with `-2`, a reserved-word list and a 32-character cap (topic exposure again). An owner hash or segment stays a **deferred option, only if a VTA ever has several owners.**
- **Verified (read-only, VTI `4e5861d95`):** the shape is a valid single segment: 1 to 64 characters of lowercase letters, digits and hyphens, no leading or trailing hyphen (`vta-support/src/contexts.rs:255-275`; stricter than Appendix D, which also allows `.` and `_`); `keyring-memory-` plus 10 is 25 characters, and lowercase base32 (`a-z`, `2-7`) is within the alphabet. Depth is 1 against a limit of 8 (`vta-sdk/src/context_path.rs:29`). `name` is 1 to 256 characters and `description` at most 1,024 in the create and update schemas (`vti-specs-vta/trust-tasks/vta/contexts/create/1.0` and `update/1.0`); "two contexts may share a name"; `update` of `name` is super-admin only (`operations/contexts.rs:231-238`); `list_contexts` returns a context to a caller that reaches it (`:216-229`). Ids cannot be renamed. The VTA does not enforce the id format.
- **Honest limits:** the opaque id keeps the topic out of audit rows, token claims and logs, and no more. The display `name` is plaintext in the context record and every unrestricted administrator (or one that reaches the context) who lists contexts sees it; the number of memories and which agent holds which id stay visible; in plain mode memory contents are plaintext anyway (finding 10).
- **`name` handling.** Decided for now: store the owner's label in `name`. *Pros:* survives the loss of the phone and is available on another device; no new format. *Cons:* administrators see the topic. Deferred alternatives, with pros and cons: **(1) phone-only name.** *Pros:* nothing on the VTA names the topic. *Cons:* lost with the phone, not shared across devices, a memory with only an opaque id on a restored phone. **(2) A name sealed to the owner's key, stored in `description` (at most 1,024 characters) or `name` (256).** *Pros:* survives phone loss; administrators see ciphertext. *Cons:* a sealing format and a key to keep; the VTA's own tools show ciphertext to the owner. **(3) An upstream private label** (VTI-Q45, deferred, registered, not requested now).
- **Labels:** the ACL entry label is free text, mutable, up to 256 characters (`VtaClient.ts:538`), read by every administrator: it carries the agent's name and nothing about what it remembers.
- **Option B's ids** (the documented fallback, not built) are `keyring-memory/<random>`.

### 4. Memory lifecycle (gap b)

- **Delete memory.** `delete_context` purges items (`purge_context_rows` → `memory::purge_context`, `:1487`) but the count that decides `force` and the preview omit them (`NotEmpty` at `:578`, the `holds` build at `:998-1004`, the gate at `:1009`). A context holding only items counts as empty and deletes without `force`; an agent on it needs `force` only for the ACL entry, and the deletion also removes or narrows entries that name the context. So the UI confirms explicitly with Keyring's own item count and the list of bound agents, and sends `force: true` only after it. P1 with a memory screen; until then `pnm`. VTI-Q40.
- **Also delete what it remembered.** Client-side, with `memory-read` and `memory-write` on the memory's context (the owner's administrator session holds both through its role): `vta/memory/list/0.3` (no values, every page) then `vta/memory/delete/0.3` per key; not atomic; re-runnable; complete only when a final listing is empty. Tombstones keep keys for 30 days by default (`app_state.rs:120`), so a wiped memory's keys stay listable; deleting the context purges them. Copy: "erases what it remembered", never "no trace". P2 (step 7.18, re-tiered in finding 17). VTI-Q43.

### 5. Limits and claims (gaps c, d, e)

- **Quota and lifetime:** none found beyond the per-request limits; see finding 10 for the evidence and the consequence. Upstream asks VTI-Q41. Interim: a client-side count when the details open (never a timer), a warning above 1,000 items (Keyring's tunable), plugin guidance and a per-session write cap.
- **Values:** UTF-8 text, at most 65,536 bytes (`app_state.rs:94`, `MemoryValue`), keys 1 to 512 bytes, no NUL (`:155`); no binary. Files: a short note about the file, or a room's file feature. VTI-Q42.
- **No encryption claim.** Superseded by finding 10, which read the mechanism: encryption depends on the VTA's mode. The screens say memory is text on the person's own VTA, that its protection depends on how the VTA is set up, and that it is not a place for secrets. A key is itself content (`MemoryKey`'s own text).

### 6. Phantom contexts, collisions and cost (gaps f, g)

- Create first, list back and compare the `name`, then grant; `Conflict` is "name taken", never "reuse" (`operations/contexts.rs:` the exists check before `store_new_context`). The VTA also refuses a grant naming a context that does not exist (`operations/acl.rs:204-229`, create `:943`, update `:1205`), so a typo leaves no dangling grant; the remaining risk is naming a different existing context, which the name comparison and "never build an id from a typed string" close.
- Cost: each context takes an index and a derivation base; no documented limit found; memories are few and meaningful, at depth 1 (2 under B).

### 10. Encryption and quota: findings and consequences

Added the same day, after a research pass whose key claims were re-read in the VTA at `4e5861d95`.

- **Encryption, old versus new.** *Old (finding 5, first draft):* "no memory-specific encryption at rest was found; whether a deployment encrypts its store was not read." *New:* memory values are AES-256-GCM per keyspace, with the keyspace and key as associated data (`vti-common/src/store/encryption.rs`), applied to the memory keyspace through `apply_encryption` (`vta-service/src/server.rs:597-602,650`), **but only when the VTA holds a storage key**. In standard (plain) mode there is none and the store is plaintext (`main.rs:2672`); hardened mode derives it from the master seed (`main.rs:2544-2558`), real protection only with a keyring, KMS or vault seed backend, and the VTA warns when the seed is a plaintext file in the data directory (`main.rs:2622-2640`); a TEE derives it inside the enclave and the host sees ciphertext. Key names stay plaintext for prefix scans (the crate's CLAUDE.md; not re-read in code). Not re-read, from the research: backups containing memory are password-encrypted (Argon2id and AES-GCM) in every mode, and audit rows hold an HMAC commitment of the key, never a value. The VTA's documents say "not a secret store" and never say plain mode is plaintext.
- **Can Keyring read the mode?** The value exists in code (`restore.rs:30-35`: plain, hardened, tee) and is written into backup manifests, but no read-only task, `whoami` or status field returning it was found (a search, not a proof). So Keyring cannot display it today. Registered as VTI-Q44 (ledger AC-31).
- **Consequence for the plan.** §3.15 and the §6 copy rules: never "encrypted", "private" or "safe"; say text on the person's own VTA, protection depends on how the VTA is set up, not for secrets; show the mode when it becomes readable. §9 threat 14 (plaintext store in standard mode).
- **Quota, old versus new.** *Old:* "no quota found; asks VTI-Q41." *New:* the limits are per request only: value 64 KiB, key 512 bytes, `put-many` 64 writes or 768 KiB, `get-many` 256 keys or 512 KiB (`operations/app_state.rs:94-112`). No per-context, per-principal or global cap and no `ttl`. The context policy's `quotas` count operations a day and are called only from `operations/keys/sign.rs:193` and `trust_tasks/vault.rs:1588`, never memory. The operation budget (VTI-TRN-029) is a rate, 100 operations a second per client by default (`trust_tasks/operation_budget.rs:10`), not a total. At the cap and the default rate that is about 6.4 MB a second (100 × 64 KiB: an upper bound by arithmetic, not measured; the weight of `put-many` against the budget was not read). A compromised or prompt-injected agent with `memory-write` can fill the VTA's store (§9 threat 13).
- **Upstream shape (VTI-Q41, extended):** optional `max_items` and `max_bytes` in `ContextPolicy`; per-context counters updated in the same write batch as `put` and `delete`; a `quotaExceeded` error; a server-wide default cap; a heavier `put-many` weight; an optional `ttl`.
- **Interim, Keyring-side:** item count and last change shown in the details (counted once on opening, never on a timer), a warning above 1,000 items (tunable, no VTI precedent), a rise noted between openings, value-size and per-session guidance in the plugin as a convenience, Revoke as the stop, "Also delete what it remembered" (P2, step 7.18) as the clean-up.
- **Residual risks:** a runaway agent can fill the disk before the owner opens the details; the count is a poll, not a limit; a plaintext-mode VTA's memory is readable by anyone with its disk; the mode cannot be displayed until upstream exposes it.
- **Decision (recommendation first):** state nothing about encryption in copy, and show the VTA's mode once readable. *Pros:* no false assurance; costs nothing. *Cons:* the owner on a hardened or TEE VTA is not told their memory is encrypted. Alternative: claim "encrypted" when the mode is hardened or TEE (needs Q44 and a trustworthy read of the seed backend, so not before Q44).
