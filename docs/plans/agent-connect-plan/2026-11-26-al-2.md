Step 7.5 is Keyring's side of pairing an agent: the `auth/oob` ceremony with the purpose `deviceEnrol`, and the P0 fallback. Before building it, its acceptance line was read against what can run today.
- **No VTA serves `auth/oob`.** Step 7.1 measured all three versions in use, 0.79.0, 0.84.0 and 0.87.0, and each refuses it as `unsupportedType`.
- **The only text that defines `deviceEnrol` is a draft:** trustoverip/dtgwg-trust-tasks-tf #1386, not yet accepted (ledger AC-36).

So `deviceEnrol` can be built only against a fake service that follows the draft, which the step itself already calls for. The fallback's Keyring side can run against a real lab VTA, but only with an agent side, and the plugin (step 7.6) does not exist yet.

This companion records one **forced correction**, five **proposals**, and one proposal withdrawn after review (finding 3). The plan's text in the same pull request is the proposed text; merging it accepts it.

**Two of the proposals are design decisions for Brendan.** Each comes with its pros, cons and a recommendation:
- **Finding 2:** which DID Keyring identifies as on the `deviceEnrol` path. We recommend the phone's own administrator DID.
- **Finding 7:** the draft's `aclScope` carries exactly one context, while an agent may be bound to several memories (D31). We recommend granting the first memory and adding the rest with `acl/update` 0.3, and asking upstream to allow a list.

Finding 3 first proposed four digits on the `deviceEnrol` path. The review showed that answers a question Brendan has already decided (§11 Q8: ask for four, ship two until VTI answers), so it is withdrawn. The number stays as #1035 aligned it.

### 2. PROPOSAL, a decision: which DID Keyring identifies as on the `deviceEnrol` path

- **Old (§7.5, within the item):** "`prove` with a signed `identify` from the owner's administrator DID, `grant` with `aclScope`".
- **Proposed (§7.5):** "`prove` 0.4 carrying `identify` 0.2 whose `issuer` is the phone's administrator DID (the DID on the VTA's ACL as its administrator, signed on the phone with its own key for `authentication`), `grant` 0.4 with `aclScope` (signed the same way for `assertionMethod`, after the phone's user verification)".
- **What the draft says:** `identify` 0.2: "The wallet builds it unsigned with the chosen DID as `issuer`, and the member's VTA signs it with `vault/sign-trust-task` for `authentication`". Then: "For `deviceEnrol`, the service checks that the issuer administers the VTA". The grant is signed the same way, for `assertionMethod`, after a user-verification decision.
- **What Keyring has:** the DID it administers the VTA as is the phone's own DID ("The phone's own DID, enrolled on that VTA's ACL", `VtiIdentityStore.ts`). The phone holds that key; the VTA does not. Sign-in identifies as a persona, whose key the VTA holds in its vault.
- **Option A, the phone's administrator DID, signed on the phone (recommended):**
  - **Pros:** it is the DID the draft's check asks for, one that "administers the VTA", which a persona is not. No vault entry is needed. The VTA, which is the service here, would otherwise be signing its own administrator's statement to itself.
  - **Cons:** it departs from sign-in's pattern, where the VTA signs. The draft's sentence "the member's VTA signs it" does not fit a DID whose key is on the phone, so the draft needs a line for this case.
- **Option B, a persona, signed by the VTA through `vault/sign-trust-task`, as sign-in does:**
  - **Pros:** it reuses sign-in's code path unchanged.
  - **Cons:** a persona is not on the VTA's ACL as its administrator, so the draft's check would refuse it. The code would be the same, but the meaning would be wrong.
- **Recommendation:** option A, and ask the draft's author for a sentence allowing the administrator DID to sign with its own key for `deviceEnrol`. Asking upstream is Brendan's call.
- **Plan sections touched:** §7.5.

### 3. WITHDRAWN: the number's length stays as #1035 aligned it

- **First proposed here:** that §7.2's number follow the `MatchNumber` of the served `auth/oob` version per purpose, four for `deviceEnrol` under draft #1386's `_shared` 0.2.
- **Why it is withdrawn:** the review of this pull request showed three problems.
  - **It answers a decided question differently.** §11 Q8 records Brendan's decision of 2026-11-25: ask VTI for four, and "ships two if VTI declines". The status line calls Q8 decided as an ask.
  - **It would leave the plan contradicting itself** in five places that still say two until four is accepted: §3.2, D8, §3.10, the accessibility note and §6's copy.
  - **The citation is circular.** The draft's four is our own ask, A12, filed on Brendan's yes (ledger AC-36). D8's rule is "the `auth/oob` specification's" length, and until the draft is accepted that length is two.
- **What stands instead:** §7.2's line is unchanged from #1035. §7.5's line says the length is §7.2's, and that the fake service accepts two digits on `deviceEnrol` although the draft's `MatchNumber` asks four. That is a stated difference from the draft, not a claim about it. Step 7.2's `MATCH_NUMBER_DIGITS = 2` stays correct as cleared.
- **For later:** if VTI accepts four, the constant becomes four. If a second purpose ever needs another length, a table by purpose and version, as the review suggested, replaces the constant.
- **Plan sections touched:** none in §7.2; §7.5's number clause.

### 4. PROPOSAL: the `deviceEnrol` path is built against draft #1386 behind one seam, and says nothing is proven against a real service

- **Old (§7.5):** "until VTI serves `deviceEnrol` (ledger AC-36), the fallback pairs against the lab VTA and the `deviceEnrol` path runs against a fake `auth/oob` service in jest; once served, the full ceremony runs on the lab".
- **Proposed (§7.5):** "the `deviceEnrol` path runs in jest against a fake `auth/oob` service behind one seam, its requests and answers checked against the draft's own schemas, every one of them and every test named as draft; nothing in this step is proven against a real `auth/oob` service, and the step says so." And: "Once a VTA serves `deviceEnrol`, the full ceremony runs on the lab; that is not part of this step's exit."
- **Pros:** the fake cannot drift from the draft unnoticed. A changed draft is one file. No reader takes a green as proof against a real service.
- **Cons:** the schemas being vendored are a draft's. When #1386 changes, the fixtures and the fake change with it.
- **Recommendation:** accept. The alternative is to build nothing on this path until VTI serves it, which leaves 7.6's plugin nothing to pair with.
- **Plan sections touched:** §7.5.

- **Proposed (§7.5):** "The fallback's Keyring side (the grant for `K_t`, then the entry read back from the VTA by subject and `deviceId`, step 7.4) runs in jest against fakes held to the `acl` and `device/list` schemas, and then on the lab against a VTA at the version the Farm runs, with step 7.1's rung playing the agent (`K_t` authenticates, `device/register`, `acl/swap-key`), run by the test lane."

- **Cons:** a rung playing the agent is not the plugin. Step 7.12 still proves the two together.

### 6. PROPOSAL, for §7.7: the VDC is signed through `issueVdc`

- **Old (§7.7):** the acceptance line says nothing about how the VDC is signed.

### 7. PROPOSAL, a decision: the draft's `aclScope` carries one context, an agent may hold several memories

- **Old (§7.5):** "the `aclScope` sent is exactly the owner's choice (memories as `act` contexts, the capabilities, purposes and expiry of §3.3, the name, consumer kind `aiAgent`)".
- **Proposed (§7.5):** "on both paths the entry ends at exactly the owner's choice (memories as `act` contexts, the capabilities, purposes and expiry of §3.3, the name, consumer kind `aiAgent`), and it never holds a context the owner did not choose. The fallback's `acl/grant` 0.3 writes every chosen memory at once. The draft's `aclScope` carries exactly one context, so on the `deviceEnrol` path with more than one memory chosen the grant names the first, and the rest are added with one `acl/update` 0.3 once the entry is confirmed (§7.4). That widening is computed from the entry as read back from the VTA, never from the set intended, so it is safe to re-send. If it fails, the pairing still completes: the agent is connected with the memories its entry holds, its details say which chosen memories it does not yet have, with "Try again", and Keyring retries at the next reconcile". Revised after the review of this pull request, which asked for three things: the end state asserted on both paths and the intermediate state only on the `deviceEnrol` path; the widening computed from the entry as read back (the rule `AgentAccessChange.act.from` carries), which makes it safe to re-send, unlike the narrowing of step 7.4; and what the owner sees if the widening fails.
- **Evidence:** draft #1386, `_shared/0.2/oob.schema.json`, `AclScope.contexts`: `"minItems": 1, "maxItems": 1`, "Exactly one in this version; never `all`". D31 binds an agent to a fixed set of any number of memories (§3.15). `acl/grant` 0.3, which the fallback uses, takes any number.
- **Option A, grant the first memory, then add the rest with `acl/update` 0.3 once the entry is confirmed (recommended):**
  - **Pros:** the owner's full choice is honoured on both paths. Adding contexts is a widening, which `acl/update` 0.3 accepts (finding 9 of 2026-11-25-al-2). The entry holds fewer contexts than chosen for a moment, never more.
  - **Cons:** two writes where one was planned. If the second fails, the agent holds only its first memory until a retry, which must re-read the entry (step 7.4).
- **Option B, ask upstream to let `aclScope.contexts` be a list:**
  - **Pros:** one signed grant states the whole scope, so the audit record matches the entry.
  - **Cons:** it waits on the draft's authors. It is an ask of VTI, Brendan's to make.
- **Option C, allow one memory on the `deviceEnrol` path:**
  - **Pros:** the simplest code.
  - **Cons:** it contradicts D31, and the two paths would bind agents differently.
- **If the widening fails, two options:**
  - **Complete with a visible gap (recommended).** The agent is connected with the memories its entry holds. Its details say which chosen memories it does not yet have, with "Try again", and Keyring retries at the next reconcile. The retry finishes the widening the owner approved at Approve for this pairing, bounded to exactly that set, so it is not a "Change memories" widening, which D34 gates behind the biometric as a new choice. It adds only memories still in the owner's current choice, so a memory removed in the meantime is not re-added: narrow at 10:00, and a reconcile at 10:05 does not bring the removed memory back. The review of this pull request asked for this bound. **Pros:** the owner keeps a working agent, the gap is never silent, and the retry is safe. **Cons:** for a while the agent has less than the owner chose.
  - **Fail the pairing and remove the entry.** **Pros:** an agent is either exactly as chosen or not connected at all. **Cons:** one flaky network call throws away a whole confirmed pairing, and the owner starts again.
- **Recommendation:** A now, and B as an ask on #1386. Once B is accepted, A becomes a single grant. If the widening fails, complete with a visible gap.
- **Plan sections touched:** §7.5.
