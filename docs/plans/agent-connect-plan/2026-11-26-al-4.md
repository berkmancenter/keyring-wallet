# 2026-11-26 — Step 7.1 item 0.3, the notification checks: how a Claude Code session hears a message, measured

Companion to [`../agent-connect-plan.md`](../agent-connect-plan.md). Not revised afterwards.

## Summary

Item 0.3 of the plan's step 7.1 asks how the agent's Claude Code session is told that the owner wrote to it. On 2026-11-26 a Claude Code session working for the owner measured each lettered check on the Claude Code installed on the owner's Mac, 2.1.332, signed in with the owner's own claude.ai account. It used throwaway folders and a throwaway plugin, and changed none of the owner's settings, hooks or plugins. The probes are in `tsp-reference/ref-25-agent-pairing/notify/`.

**What works as the plan says.**
- A channel wakes a session that is sitting idle. The event was answered about a second after it was sent. Without the development flag the same event is dropped with no error.
- The fallback works: Claude watches the plugin's inbox with the Monitor tool, gets each new line while idle, and re-arms the watch when it runs out.
- The plugin's hook blocks every tool except `reply` while it handles a stranger's text, in auto mode, with the memory tools pre-allowed, and even when Claude is told the text is the owner's. A message from the owner that arrives during that turn is held back and delivered as a turn of its own.
- An `asyncRewake` hook can also wake an idle session. The plan does not rely on it.

**What the plan had wrong.**
- **A channel does not work in a background session**, whether started with `claude --bg` or sent there with `/background`. The plan's first product tier counted on it. It now says that a background session hears the owner only through the Monitor fallback, which was measured to work there. An interactive session is unchanged.
- **The `reply` tool must be loaded up front.** Claude Code holds a server's tools back until Claude searches for them. The hook has to block that search on a stranger's turn, so the plugin marks `reply` to be always loaded. Without this, the first event was answered in plain text instead of through `reply`.

**The minimum version is now known.** Channels arrived in Claude Code 2.1.80. They need a claude.ai login or an API key from Anthropic's Console; the key works from 2.1.128. They are off on the cloud providers. In Team and Enterprise organisations an Owner has to switch them on. Only 2.1.332 with an individual login was run.

**Still open.** The hook check in the mode that skips every permission prompt was not run, because this session's own safety check refused to start that mode; it is the owner's to run. Whether the plugin's Rust server can be the channel server is still the maintainers' question (§11 Q6), with one new constraint from the documentation: it must not use the newest MCP protocol revision, or it is not registered as a channel. Nothing here is filed upstream.

## Findings

**Sources.** Claude Code 2.1.332 (`claude --version`), signed in with claude.ai on an individual plan with no organisation. Model `haiku` (Haiku 5.5), to keep the runs cheap; the default permission mode of these sessions was auto. Channel servers on `@modelcontextprotocol/sdk` 1.32.2 (it negotiates `2025-11-25`), Node 20.19.2, macOS. Documentation read on 2026-11-26: `code.claude.com/docs/en/channels.md`, `channels-reference.md`, `hooks.md`, `mcp.md`, `plugins-reference.md`, `cli-reference.md`, and the public `CHANGELOG.md` of `anthropics/claude-code` at its 2.1.332 entry. The probes, their README and the recorded values: `tsp-reference/ref-25-agent-pairing/notify/`, `fixtures/notify-2026-11-26.json`. Times are UTC, from the probe servers' logs and the session transcripts.

**Isolation, and what it still touched.** Every session ran in a throwaway folder outside the repository, from `cleanenv.sh` (no parent `CLAUDE_*` variables; started from inside another session, a session is marked a child and saves no transcript), with `--setting-sources project,local`. Nothing was installed. The sessions used the owner's claude.ai login, wrote transcripts under `~/.claude/projects/`, recorded each throwaway folder as trusted in `~/.claude.json`, and three background jobs left rows under `~/.claude/jobs/` until they were removed with `claude rm`.

### 1. (a) A channel wakes an idle session

- **Measured.** Run a2: `claude --ax-screen-reader --setting-sources project,local --dangerously-load-development-channels server:probe`, with the trust prompt and the development-channel warning answered, then left idle with no prompt typed. The startup screen shows "Channels (experimental) messages from server:probe inject directly in this session". After 49 s idle, one POST: pushed 16:46:18.467, in the transcript as a user entry with origin `{kind: "channel", server: "probe"}` at 16:46:18.512 (`<channel source="probe" n="1">…</channel>`), answered at 16:46:19.651. A second event 54 s later was answered through the `reply` tool (16:47:16.664).
- **Control.** Run a3, the same session without the flag: the event pushed at 16:48:27.662 resolved on the server with no error, and no turn followed. The documentation says so ("Claude Code drops the events silently and returns no error to your server").
- **Found on the way.**
  - `server:<name>` names a server from the project's `.mcp.json`. The same server given with `--mcp-config` is reported "no MCP server configured with that name" (run a1).
  - A server's tools are deferred behind `ToolSearch`. The first event was answered as text, without `reply`, and for the second the model ran `ToolSearch` before calling it. A tool marked `_meta["anthropic/alwaysLoad"]: true` loads up front (`mcp.md`); with it, run f3's model called `reply` with no search.
- **Plan sections touched:** §2.3 item 6 (measured), §3.12 (the channel bullet, the Phase 0 paragraph), the Overview row for 0.3.

### 2. (b) A development channel does not register in a background session

- **Measured, three ways.**
  - b1: `claude --bg … --dangerously-load-development-channels server:probe "<prompt>"` crashed before start ("entries must be tagged"). The flag is variadic and takes the prompt as an entry. A prompt must follow `--`.
  - b2: the same with `-- "<prompt>"`. The session started and the probe server connected (16:50:11.697), but no development-channel warning and no channel notice appeared. The event pushed at 16:51:06.770 never reached the transcript.
  - b3: interactive with the flag, the warning accepted, one turn, then `/background`. The session moved, and the probe server was restarted and connected (16:52:51.198). The event pushed at 16:53:25.090 never reached it.
  - In b2 and b3 the job's `respawnFlags` (`~/.claude/jobs/<id>/state.json`) do not carry the channel flag.
- **Control: the probe would have seen a delivery.**
  - b4: `claude --bg` with the flag, then `claude attach` to approve the project's server, which connected at 17:27:42.496. The event was pushed at 17:28:08.501 by that same server instance (pid 9613).
  - A message typed into the same session at 17:28:34 was recorded in its transcript and answered at 17:28:35. That transcript holds no channel entry and no `PONG-B4`, and the server logged no `reply`.
  - So in the same session the probe saw a turn arrive after the push, and the channel event was not among them.
  - The positive case for the probe's method is run a2 (finding 1), the same server and the same push, interactive.
- **Reading.** This fits the documentation: "Run the development flag in an interactive session, where Claude Code can show the confirmation prompt." A background session never shows that prompt. Whether an allowlisted plugin given with `--channels` registers in a background session was not run: it would mean installing an official plugin into the owner's own configuration.
- **Design change.** A background session hears the owner only through the `inbox` and Monitor fallback, which works there (finding 5). An interactive session uses the channel as before. The headless daemon (P2, step 7.19) is unchanged.
- **Supersedes** the Overview row "A channel … works with a background session" and §2.3 item 6's open question about `claude --bg`.
- **Plan sections touched:** §2.3 item 6, §3.12 (the channel's limits, the Phase 0 paragraph), D13, the Overview row for 0.3, step 0.3's acceptance line.

### 3. (c) The minimum version and the authentication

- **From the changelog.**
  - 2.1.80: "Added `--channels` (research preview) — allow MCP servers to push messages into your session."
  - 2.1.81: permission relay.
  - 2.1.105: "Fixed inbound channel notifications being silently dropped after the first message for Team/Enterprise users."
  - 2.1.128: "`--channels` now works with console (API key) authentication."
  - 2.1.234: permission requests go only to servers registered as channels. For the plan, which never declares permission relay, this is not a floor.
  - So the minimum is 2.1.80, and 2.1.128 for a Console API key.
- **From the documentation.**
  - Channels "require Anthropic authentication through claude.ai or a Console API key, and are not available on Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry".
  - "Pro, Max, and Ultra users without an organization skip these checks entirely."
  - On claude.ai Team and Enterprise, channels are blocked until an Owner enables `channelsEnabled`.
  - On the Console with managed settings, they are blocked until `channelsEnabled` is set.
  - `--dangerously-load-development-channels` skips only the allowlist; `channelsEnabled` still applies.
- **Measured:** 2.1.332 with an individual claude.ai login delivers (finding 1).
- **Not run:** a Console API key (a secret, the owner's), a Team or Enterprise organisation, any other version.
- **Plan sections touched:** §2.3 item 6, §3.12 ("The login requirement and the minimum Claude Code version are not on the page read").

### 4. (d) `asyncRewake` wakes an idle prompt

- **Measured.** Run d1, a `SessionStart` hook with `asyncRewake: true` and `timeout: 120`, which sleeps 45 s and exits 2. The hook started at 16:54:41. The last turn ended at 16:54:49.984, and the hook exited at 16:55:26. Its stderr arrived at 16:55:26.369 as a task notification headed "Stop hook feedback", its text labelled `Stop hook blocking error from command "SessionStart:startup"`. It was answered at 16:55:28.321.
- **Reading.** One wake per hook run, under the hook's own timeout (600 s by default on most events, `hooks.md`). A third path would have to restart itself from another hook event, and its text arrives under a misleading label. It stays recorded, not relied on, as step 0.3's gating says.
- **Plan sections touched:** §2.3 item 6, D13 (its rejected alternative said "`asyncRewake` unverified").

### 5. (e) The Monitor fallback, with a re-arm, also in a background session

- **Measured, interactive (run e1).**
  - A project skill tells Claude to arm `Monitor` on `./inbox.sh --follow` (a `tail -n 0 -F` on a file) with `timeout_ms` 60000, to log each line, and to re-arm the watch on its expiry notice.
  - Armed at 16:56:36.749. A line written at 16:57:16 reached the idle session at 16:57:16.664.
  - The expiry notice came at 16:57:39.696 ("[Monitor expired after 1m with 1 event delivered. Re-arm it if you still need the watch.]"), and the watch was re-armed at 16:57:41.166.
  - A line written at 16:58:22 arrived at 16:58:23.204.
- **Measured, background (run e2).** `claude --bg --setting-sources project,local -- "/inbox"`: a line written to the background session was acknowledged, the watch expired and was re-armed (17:00:08), and a line written after the re-arm was acknowledged.
- **What it showed beyond the plan.**
  - **The default is 5 minutes, not 30.** `timeout_ms` defaults to 300000 and is capped at 1800000 (the tool's own schema). The skill must ask for 1800000 to get the 30 minutes the plan names.
  - **Framing.** A line arrives as `<task-notification><summary>Monitor event: "<description>"</summary><event>LINE</event></task-notification>`. That is a generic tool notification, not a `<channel>` tag, so the plugin's own wrapping and truncation of each line stand as the plan says.
  - **The re-arm gap.** It was about 1.5 s between the expiry notice and the new watch. A watch that starts at the end of the stream (`tail -n 0`) misses a line written in that gap, so `inbox --follow` must resume from the plugin's durable cursor (§3.12 `inbox`), never from "now".
  - **A WebSocket source.** `Monitor` also takes a `ws` source, one event per text frame. It is an alternative to a shell command, not measured.
- **Plan sections touched:** §3.12 (the fallback bullet), §2.3 item 6, the Overview row for 0.3.

### 6. (f) The plugin's `PreToolUse` gate and the `Stop` hold-back

- **The probe.**
  - A throwaway plugin, `probeplug`, loaded with `--plugin-dir` and its channel with `--dangerously-load-development-channels plugin:probeplug@inline`.
  - Its `hooks/hooks.json` wires `PreToolUse` (matcher `*`) to `gate.sh`, which denies every tool but `mcp__plugin_probeplug_probe__reply` while the turn-trust marker reads `other`, and `Stop` to `stop.sh`, which clears the marker.
  - Its channel holds owner events while the marker is set and sends them once it is cleared.
  - The project pre-allows `mcp__vtamcp__*` (a stand-in for `vta-mcp` with a `memory_get` tool), the plugin's tools, `Bash`, `Write`, `Edit` and `WebFetch`. The session ran in auto mode.
- **Measured, the gate (run f3).** To make the model try the tools, the marker was set to `other` while the event was labelled as the owner's (`POST /inject`): what a successful injection looks like, with only the hook in its way. Every attempt was denied:
  - `ToolSearch` (17:09:38) and `Bash` (17:09:39);
  - `Write` (17:11:13);
  - the pre-allowed `mcp__vtamcp__memory_get` (17:11:42), after it had been loaded on an owner turn so that the tool itself was called;
  - `ToolSearch` for `WebFetch` (17:12:13).
  - `reply` passed every time. No side effect occurred: no `pwned.log`, no `other.txt`, no call in `vtamcp.log`.
  - The model did not try the `Agent` tool after the earlier denials, so a subagent's tool calls were not observed.
  - Run f5 repeated the Bash case with the committed copy in `notify/plugin/`: denied (17:17:47), `reply` passed, and `Stop` cleared the marker.
- **Measured, the hold-back (run f2).**
  - A third party's request was pushed at 17:08:07.063, setting the marker, and an owner event two seconds later was held (17:08:09.087).
  - `Stop` ran at 17:08:10 and the held event went out at 17:08:11.050, as its own turn, where `Bash` passed (17:08:12).
  - The turn never mixed the two. In this run the model declined the third party's request by itself, so f2 tested the hold-back and not the gate.
- **What it showed beyond the plan.**
  - The gate must also deny `ToolSearch`, since a deferred tool is otherwise one search away. So the plugin's `reply` carries `_meta["anthropic/alwaysLoad"]: true`, without which the model cannot reach `reply` on a stranger's turn.
  - A `--plugin-dir` plugin's id is `<name>@inline` (`cli-reference.md`). Its channel delivers although the startup notice says "plugin not installed". An installed plugin is `plugin:<name>@<marketplace>`, as the plan says.
- **Not run.**
  - `bypassPermissions` (`--dangerously-skip-permissions`): this session's own permission classifier refused to start it, and that refusal was respected. The plan's sentence "A hook decision does not depend on the permission mode" is measured for auto mode with tools pre-allowed only. The offline test `notify.test.mjs` shows `gate.sh` itself ignores the mode, but not that Claude Code calls it in that mode. The owner can run it (the probe's README, item f).
  - A subagent's tool calls (above).
- **D23's condition is met** for what it names, auto mode with pre-allowed tools. P1's "Answers other people" switch can be offered, with the `bypassPermissions` run recorded as not done.
- **Plan sections touched:** §2.3 item 13, §3.13 (the Conditional), D23, the Overview row for (f).

### 7. The channel server and the MCP protocol revision (documentation, bears on §11 Q6(c))

- **Read.** `mcp.md`, "Push messages with channels": "On the v2 runtime, a channel server that negotiates MCP protocol revision 2026-07-28 can't deliver channel messages, so Claude Code doesn't register it as a channel." Claude Code asks stdio servers for that revision by default (changelog 2.1.292), and `MCP_PROTOCOL_NEGOTIATION=legacy` keeps every server on the earlier handshake.
- **Consequence.** Whatever serves the plugin's channel, `vta-agent-memory`'s Rust server or a second server, must answer with a revision before `2026-07-28`. The TypeScript SDK 1.32.2 used here does. Which revision the Rust server's MCP library offers is for the maintainers to check (§11 Q6(c)).
- **Plan sections touched:** §11 Q6(c), §3.12 (the "Open (§11 Q6)" sentence).

## What was not checked

- A Console API key, a Team or Enterprise organisation, and any Claude Code version but 2.1.332 (finding 3).
- `bypassPermissions` for the gate, and a subagent's tool calls (finding 6).
- An allowlisted channel given with `--channels` in a background session (finding 2).
- Events sent to a busy session without the hold-back: the channels reference says they "are delivered together on the next turn", and that was not reproduced here.
- A session idle for hours rather than minutes. Linux and Windows.
- `vta-agent-memory`'s Rust server as the channel server (§11 Q6).
