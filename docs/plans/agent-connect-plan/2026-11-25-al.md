### 4. A run of the suite as Keyring would run it

- **Concluded:** the suite works with Keyring's own code. A program with three parties on a mediator (a toy provider behind the suite's own TSP consumer, an agent on the suite's TypeScript libraries, and Keyring signing with `packages/trust-tasks/src/documentProof.ts` and reading the consent request as `consentCheck.ts` does) ran the lane's whole session: a held `hcp/grants/request`, a `task-consent/request` carrying the 6.1.6 checklist, Keyring's decision, the grant, a query, a memory added by Keyring, the grant list, the audit, the disclosure summary, revoke, the notice twice with one `noticeId`, and the refused query after it. 31 of 37 checks came out as expected. Every payload was valid against the suite's schema and, where HCP has one, against HCP's own.
- **Evidence:** `tsp-reference/ref-21-hcp-over-trust-tasks/` on the review branch, with its frozen report. Keyring's eddsa-jcs-2022 recipe also reproduces the suite demo's proof byte for byte (the review's `notes/signing-formats.md`).
- **What it does not prove:** the real VTA (`vta-hcp` does not exist); Keyring's real transport (the run used the suite's TSP library for every party, which writes TSP 0.1); Keyring's key store, screens or biometric.
- **Two things were Keyring's own and are fixed on branches of their own:** the consent check refused a `task-consent/request` typed with a `#request` fragment, which the framework says a consumer accepts (`fix/consent-request-type-forms`); and `VtaClient.sendTask` returned a held reply's payload as the task's result (`fix/vta-held-reply-and-retry-fields`). Neither is met with the VTA as built.

### 5. What the review found that the lane's steps depend on

Each is being raised where it belongs (the suite's pull requests, or VTI #2823). They are listed here because steps 7.27 to 7.30 rest on them.

- **Governance requests require an access token; the VTI design gives Keyring none in V0.** Every Management Client request schema in the suite lists `accessToken` as required and is closed. VTI #2823 §4.4 has Keyring authenticate governance tasks as the administrator DID with a document proof and no token until V1. The VTA validates a payload against its schema before anything else, so the V0 request is refused `malformedRequest`; the run reproduced that. Step 7.27's revoke, new memory and the poll of `disclosures/summary` depend on which side moves. The HCP companion's finding 12 ("D2, Keyring's authentication to the VTA") records the no-token divergence without the schema conflict.
- **The suite tells a client to check the provider against its HCP discovery document.** 27 of the 28 specs do; HCP's discovery schema needs at least one `conformsTo` entry and one binding, and the VTI design publishes none in V0 and no `conformsTo` in V1. An agent client that follows the suite to the letter cannot send a token to that VTA. The lane's CLI (track B) should not be built to make that check until the suite says what a carriage-only provider publishes.
- **A decline is the same `permissionDenied` as any refusal, and an abandoned hold is asked again.** Step 7.27's acceptance has a decline case (VTI's A3 does too); the agent cannot tell a decline from an unknown subject, by the suite's design, and the framework text on the suite's branch says a decision is not reported that way. After a hold the provider gives up on, the next resubmission on that thread is a new request to the person: with a 300-second hold and resubmissions every few seconds, Keyring is asked again.
- **Nothing ties the consent request to the held request.** `task-consent/request` 0.1 has no payload member for the held request's `threadId`, and Keyring accepts the request "only for the VID and `threadId` it scanned" (VTI #2823 §5.2; the HCP companion's finding 6). The framework's `parentThreadId` is the standard carrier. Work package C1 needs the answer.
- **The suite's TypeScript TSP library writes TSP 0.1 and does not read 1.0.** The VTA at the pin reads 1.0 only. A CLI built on that library does not reach the VTA over TSP. Run, not read: `ref-21`'s `probe:tsp-version`.
- **VTI's error for a revoked grant differs from the suite's.** The design says `scope-denied`; the suite sends `hcp:invalidToken`, which is what the client must read as a revocation.
- **Plan sections touched:** none yet. Each becomes a plan change when its owner answers.

### 6. What does not carry over from the access-list path to HCP

- **Concluded:** an agent on the VTA's client library cannot run the lane's connect as that library stands, whatever repository the agent lives in.
- **Evidence, read at `f7b78e29d` and not run:**
  - `vta-sdk` gives every document a fresh `id` and sets no `threadId` (`vta-sdk/src/client/mod.rs:4203-4213`, `build_task_document`), and `vta-mcp`'s `vta_call` takes only `operation` and `payload` (`vta-mcp/src/server.rs:174-182`). A held `hcp/grants/request` must be resubmitted on its thread; a request on a new thread is a new request and a new prompt on the phone.
  - `vta-sdk` returns any reply payload without `code` and `message` as a result (`client/mod.rs:2492-2510`), so a `trust-task-next-step` reaches the caller as the answer.
  - `vta_call` passes the payload the model wrote and returns the reply payload to the model. Every `hcp/*` request but two carries `accessToken` in its payload, and `hcp/grants/request` returns it. HCP 10.5 (:2757): "The access token MUST NOT enter the model's context, and MUST NOT be returned as tool content".
  - `vta-mcp` has no inbound path, so it cannot acknowledge `hcp/grants/revoked`. Both designs already put that receive loop in the agent client (the HCP companion's B4; VTI's plan).
- **Not verified:** `vta-agent-memory` at `80047d95` (D45) was not read for this. Whether it shares these three behaviours depends on whether it uses `vta-sdk`'s `dispatch_trust_task`; that is the first thing to check under Q12.
- **Supersedes:** nothing. D40's "the plugin reuses `vta-mcp` for every operation on the VTA" holds for the access-list path; it does not extend to `hcp/*` without the three changes above.
- **Plan sections touched:** §11, Q12.

### 7. Two questions opened

- **Q11, one identity or two.** The VTI design admits an HCP client only when the access list refuses the sender ("**No ACL entry.** Its authority is the grant", #2823 `hcp.md:113`), and at `f7b78e29d` a sender with an entry is admitted on that standing before any other hook runs. This plan's agent holds an entry, which rooms and `vta/memory/*` need. C12 (step 7.29) merges the two connect paths. Three things follow whichever way it goes: `acl/swap-key` moves only the entry, so the grant, its token, its hold and its notice address stay with the old key (the suite binds all of them to the issuer's VID); disconnect has to send both `acl/revoke` and `hcp/grants/revoke`; and the `AgentConnection` record (plan §3.11) stores no `grantId`.
- **Q12, where the agent side holds the token and the thread.** From finding 6.
- **Plan sections touched:** §11 (Q11, Q12 and its lead), the status line, and the review index (row 9).
