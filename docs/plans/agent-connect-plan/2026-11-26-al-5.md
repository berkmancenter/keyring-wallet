### 4. PROPOSAL, a decision: how the plugin knows a chat document is from the owner's `chatDid` (L5)

§3.12's gate accepts chat "only from `chatDid`", which needs an authenticated sender. **`vta-sdk` 0.94.0 does not give one.** `DIDCommSession::receive_next` returns the unpacked message, and its doc says its `from` "is the plaintext header and is **not** authenticated: do not authorise on it. Establish who composed the document from its own Data Integrity proof (`InboundMessage::verify`)" (`src/didcomm_session.rs:853-855`). The authcrypt sender it could have used is crate-private (`authcrypt_sender_kid`, `:1418`).

| Option | Pros | Cons |
| --- | --- | --- |
| **(a)** Ask VTI to expose the verified authcrypt sender from `receive_next` | The smallest change on our side; trusts the transport, as the plan assumed | Waits on an upstream release; trusts the mediator path's packing rather than the document; no other consumer has asked for it |
| **(b)** The plugin opens messages below `DIDCommSession` (the messaging crate's `ReceivedMessage.sender`) | No upstream change | Duplicates SDK internals the maintainers would have to accept upstream; breaks on any SDK change to its session layer |
| **(c)** Every chat and control document carries a Data Integrity proof by `chatDid`, which the plugin verifies with `InboundMessage::verify` | No upstream change; the SDK's own advice; the proof binds the document itself, so a compromised or wrong mediator cannot forge one; the same check works over TSP | Work in Keyring's step 7.9 (below); a little more weight per message |

**Recommendation: (c). Agreed by relay 2026-11-26, awaiting Brendan's own confirmation before `main`,** with his addition below.

**His addition: a replay rule.** A signed document can be stored and sent again by anyone who saw it, a mediator included; a proof alone does not stop that. So the signed document carries a timestamp, a unique message id and its recipient's DID, and the receiver refuses a stale or repeated one. What it needs decided, proposed here:

- **The signed members.** The Trust Task framework's own document members, which `signDocumentProof` already signs whole (SPEC §6.3): `type`, `id` (a `urn:uuid` v4: a new message gets a new one; a **resend is the same signed document, byte for byte, with its id**, so a document delivered twice, by a mediator's retry or a resend after a timeout, is refused as the duplicate it is), `issuer` (the sender: `chatDid`, or the agent's `K_a`), `recipient` (the receiver's own chat identity), `issuedAt` (in `documentProof.ts`'s `wireTimestamp` form, with no `.000Z`), `payload` (`{ version, …body }`), and `proof`. Agreed with the maintainers of Keyring's step 7.9, who produce them, with their change on resends; the exact members go into the shared vector file below.
- **The recipient check.** `recipient` must equal the receiver's own chat identity: on the plugin's side, the agent's own `did:key` as Keyring addresses its chat (`K_a` after the rotation; which identity the chat uses is §11 Q7(b)); on Keyring's side, `chatDid`. Anything else is refused, so a document meant for another agent of the same owner cannot be replayed to this one.
- **The freshness window, proposed: at most 5 minutes ahead of the receiver's clock, and at most 7 days behind it.**
  - *Why 7 days behind:* the owner may write while the session is off. The message waits in the mediator's queue, whose expiry is 7 days (`message_expiry_seconds` 604800 by default, `message-protection-plan.md:60`), and is delivered when the session starts; a shorter window would refuse it then.
  - *Why 5 minutes ahead:* a phone's and a laptop's clocks differ. Keyring already allows 60 s of skew for a Trust Task proof (`TRUST_TASK_PROOF_CLOCK_SKEW_MS`, `documentProof.ts:504`); a laptop that sleeps drifts more, and 5 minutes bounds how far ahead a document can claim to be without opening much.
  - *Pros:* nothing the owner sent while the agent was off is lost; with the seen-id store below, a replay within the window is still refused by its id.
  - *Cons:* replay protection inside the window rests wholly on the seen-id store, so the store must be durable. A 7-day store holds up to a week of ids, though ids only, no content.
  - *Which way an operator's settings move it, and why both fail safe:* the same row says `delivered_expiry_seconds` is off by default and only shortens the queue's clock once a message is handed over. So the queue keeps a message for at most 7 days unless an operator raises `message_expiry_seconds`. An operator who **lowers** the expiry leaves this window wider than the queue, which costs nothing: the seen-id store holds ids longer than any message can wait. An operator who **raises** it past 7 days makes this window too short, so a genuinely queued document older than 7 days is refused as stale. That is an availability failure, never acceptance of a replay. So the window is not to be widened on the ground that an operator might have changed the setting.
  - *Rejected:* a window of minutes. It would make replay need no store at all, but it refuses every message queued while the session was off, which is the normal case for chat.
- **The seen-id store.** The receiver remembers every id it has accepted for the window plus the skew (7 days and 5 minutes), in an owner-only file beside the inbox cursor. The id is written there **before** the document is acted on, so a restart of the owner process (finding 6) within the window still knows it. Entries past the window are dropped. If the store is missing or unreadable, the receiver refuses anything issued before the store's own creation time: it fails closed on old documents and stays open for new ones.
- **Order for messages that set state** (agreed with step 7.9's maintainers). `settings`, and later `room-offer`, set state, so within the window one is applied only if its `issuedAt` is newer than the last one of its type applied. Otherwise a delayed older `settings` could undo a newer one even with distinct ids. Chat events need no such rule: their order is the chat's.
- **Where each side keeps its seen ids.** The plugin uses the owner-only file above. Keyring uses keyed generic records, as the lockout does, so they survive a restart.
- **Vectors.** The shared vector file of finding 5 gains, for the envelope, a positive example per type and five negative ones: stale, repeated id, wrong recipient, an altered body, and an older `settings` arriving after a newer one. They are generated by an implementation independent of both sides: a small generator committed beside its output with its pinned inputs, so anyone can regenerate them. It signs each proof exactly as eddsa-jcs-2022 hashes the proof configuration, so the file also checks Keyring's own `verifyDocumentProof`. It is marked draft until Brendan's own word.

**What it adds to step 7.9 (agreed with the step's maintainers):**
- Keyring signs every outgoing chat and control document as `chatDid` with `signDocumentProof` (`packages/trust-tasks/src/documentProof.ts`): a `DataIntegrityProof`, cryptosuite `eddsa-jcs-2022` (the one suite Keyring uses), proof purpose `assertionMethod`.
- Keyring verifies the plugin's documents with `verifyDocumentProof` against the agent's `did:key`. That is `K_a`, and after a rotation, the key its entry was read back under.

**On the plugin's side, step 7.6:** the gate verifies the proof and accepts the document only when the verified signer is `chatDid`, never on the `from` header.

- **The heartbeat.** The plugin sends one at session start and every 10 minutes. Keyring shows "Not connected right now" when none has come in 20 minutes or the session is known to have ended. It sits beside step 7.9's "Waiting for your session" after 20 unanswered messages, and does not replace it. 10 minutes keeps mediator traffic low. **Pros:** it gives §6's "Not connected right now" a source, which §3.5 lacks. **Cons:** a new message and a timer; a slept laptop reads as not connected after 20 minutes, which is accurate.

### 6. PROPOSAL, a decision: one process owns the agent's mediator connection

`vta-sdk` 0.94.0 warns that "Two live sessions for the same DID fight on the mediator (`Duplicate WebSocket connection: closing old session …`) and request/response round-trips time out" (`src/didcomm_session.rs:36-38`). As §3.12 lays the plugin out, up to three processes would hold one: the session's MCP server (`serve`, which receives chat), the `SessionStart` hook (`recall`, `hooks/hooks.json`) and the fallback's `inbox --follow`.

| Option | Pros | Cons |
| --- | --- | --- |
| **(a)** `serve` owns the one DIDComm session for `K_a`. It writes accepted events to the core's durable inbox file. `inbox --follow` reads that file, and the hook and other commands reach the VTA without opening a mediator session of their own | One process, the one already alive for the session's whole life; no new IPC; the inbox file is what the fallback needs anyway | A command run with no session open cannot receive chat (P0 needs a session anyway); the hook's path to the VTA must be checked to open no live session (step 7.6, its mediator change) |
| **(b)** A per-user background process owns it, and the others talk to it locally | Survives sessions; it is the P2 daemon's shape | A daemon, a local protocol and its permissions, all in P0 |
| **(c)** Whichever process starts first takes a lock | No new process | Races at start, and a session whose process lost the lock receives nothing |

**Recommendation: (a)** in P0 and P1, with the P2 daemon (§3.12, step 7.19) taking ownership when present. **Agreed by relay 2026-11-26, awaiting Brendan's own confirmation before `main`.**

**In a background session, where no channel registers** ([`2026-11-26-al-4.md`](./2026-11-26-al-4.md), finding 2): the session still starts the plugin's MCP server. Run b3 measured that a session moved to the background with `/background` restarted the server, which connected again, while the channel's events stopped reaching it. So `serve` still owns the connection there. It writes accepted events to the inbox file, and the Monitor fallback follows that file with `inbox --follow`, which was measured to work in a background session (finding 5). The follower resumes from its cursor across the watch's re-arm gap (about 1.5 s, finding 5). Because the move to the background restarts `serve`, the connection is opened again by the new process, and the inbox cursor carries over in the file.

**Not measured:** a session started with `claude --bg` from the outset (run b1 failed on the flag's syntax). That its MCP server starts there too is an inference, to check when the plugin's own front-end is built (its channel and CLI changes).

### 7. PROPOSAL, a decision: what the pairing link's `_scope` carries

Keyring does not read `_scope` today: the link reader lists it under `ignored`, and `pairing.ts:415` holds `TODO(0.1(h))`. The rung `ref-25-agent-pairing` encodes `&_scope=<letters>[~<purpose>.<purpose>]`, with letters `r` memory-read, `w` memory-write, `p` room-present and `o` room-open (`links.mjs`).

**Measured in the rung on 2026-11-26:** a 56-byte `did:key` in `_from`, a 22-character `_id`, a 10-digit `_exp`, the path-form `_type=/vti/flow/agent-connect/0.1`, and host `link.trustoverip.org`. The limit is 251 bytes. Each link read back the same text from its drawn QR code (a software decode, not a camera).

| `_scope` | Bytes | Spare | QR version |
| --- | --- | --- | --- |
| none | 170 | 81 | 9 |
| `rw~personalisation.taskExecution` | 210 | 41 | 10 |
| `rwpo~personalisation.taskExecution` | 212 | 39 | 10 |
| `~personalisation` (purposes, no capabilities) | 194 | 57 | 10 |

**Proposed:**
- `_scope` becomes the contract, in the form above, with the plan's two purposes (`personalisation`, `taskExecution`), never `assist.recall`.
- An agent asking for **no memory capabilities** writes purposes only (`~personalisation`). An agent asking **nothing** omits `_scope`. An empty `_scope` is read as absent, and the phone then shows its own default. The phone never treats the agent as having asked for that default.
- **The link carries no grant expiry.** `_exp` is the link's own lifetime (300 s at most). The grant's expiry is the phone's choice: 4 hours by default, with "Keep it connected" a separate act (D42). This supersedes the "longest expiry, 90 days" ceiling in §3.2, which predates D42 and would refuse "Keep it connected".
- **A limit stated: the link asks for a strict subset of what an ACL entry can hold.** A purpose in the link is a registered name only, by the specification's own pattern `^[a-z][a-zA-Z0-9]{0,63}$` (`acl-entry.schema.json` 0.3, `$defs.Purpose`, its first form, at the registry pin `2a66a0351`). The same schema also allows an absolute IRI as a purpose, but the link cannot carry one: it would not fit (about 60 characters each, by arithmetic, not measured), and `.`, the separator, appears inside IRIs. Before the rung refused one, an IRI was written into the link and read back as several wrong names. The rung's encoder now refuses a purpose that is not a registered name (wallet #1067, with the rows above recorded in `fixtures/links-scopes.json`). Keyring reads no `_scope` yet. What it does check today is stricter than the pattern: it refuses any purpose not in `AGENT_PURPOSES` (`pairing.ts:300`; `personalisation` and `taskExecution`, `pairing.ts:45`). So a further registry purpose, such as `analytics`, needs that constant changed as well as the plan, and a `_scope` reader, once built, refuses a name outside the pattern before that check. Asking for an IRI purpose would need another form, such as an index or a digest.
- **What it costs:** a reader in `pairing.ts` that refuses a purpose outside the pattern; a shared vector file of links beside `handle.json`; the rung stops emitting an empty `_scope` (done in wallet #1067). Keyring shows the agent's ask on Approve as a starting choice the owner can change, and grants what the owner chose.

**Pros:** the owner sees what the agent asked for; it fits with 39 bytes spare at its widest. **Cons:** a second place where scope is spelled, kept in step by the vector file. **Recommendation:** adopt. **Agreed by relay 2026-11-26, awaiting Brendan's own confirmation before `main`.**

### 8. PROPOSAL, following from the plan: where the plugin gets its handle

The plugin cannot derive its own final handle: the `taken` list in `vectors/handle.json`'s rule is the owner's other agents, which only Keyring knows (§3.6).

- **Proposed:** the handle arrives in `settings.handle` (finding 5), in the first `settings` after pairing. It is sent again only if it ever changes. §3.6 fixes the handle at pairing ("does not change if the agent later moves to another key"), so no rename path is promised.
- **Not in the VDC:** that credential keeps to its specification's members.
- **Agreed with the maintainers of Keyring's step 7.9.** This follows from the plan's own rule, so it is not one of the four decisions put to Brendan.
