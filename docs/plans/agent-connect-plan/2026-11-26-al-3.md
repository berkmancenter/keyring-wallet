### 1. ALIGNMENT, §7.2: only a wrong number counts toward the lockout

- **Old (7.2):** "three wrong numbers in 60 minutes lock the flow for 15 minutes, a wrong number while three are still inside the window renews the lock, and the lock survives a restart".
- **Now (7.2):** the same, followed by "cancel, decline and a VTA Keyring does not administer do not count".
- **Evidence:**
  - §3.2 step 5, "Lockout (Keyring's own rule)", counts "Three wrong numbers within 60 minutes", and nothing else. A cancel, a decline and a refused link are not wrong numbers.
  - The code counts only a wrong number: `pairing.ts` calls `lockout.recordWrongNumber()` only when `prove` is refused with `numberMismatch` (`pairing.ts:463`–`464`). It has no other caller outside the tests.
  - A test holds it: "a cancel, a decline and a foreign VTA do not count" (`pairing.test.ts:324`).
- **Why it is written out:** a reader of the old line could count every failed pairing. The plan's rule counts wrong numbers only.
- **Plan sections touched:** §7.2, by #1035. This pull request changes no text for it.

### 2. ALIGNMENT, §7.4: `grantApplication` is `acl/grant` 0.3 with the role `application`

- **Old (7.4):** "`grantApplication` (0.3 shape, `act` contexts, `listed` capabilities, `keys: none`, `purposes`)".
- **Now (7.4):** "`grantApplication` (`acl/grant` 0.3: `role` `application`, `act` contexts, `listed` capabilities, `keys: none`, `purposes`)".
- **Evidence:**
  - §3.3's table gives the entry's `role` as `application`: "The ceiling for an agent … Never `admin`".
  - §2's current state says no method yet "grants role `application`".
  - "0.3 shape" left open which task carries it. Step 7.4's line, in the same pull request, sends the access-list writes at 0.3 only.
- **Plan sections touched:** §7.4, by #1035. This pull request changes no text for it.

### 3. PROPOSAL, §7.2: the handle's vectors file is generated independently and says what it read

- **Old (7.2):** "the handle for fixed vectors (name and `K_a`) is the same on every run and is shared as a vectors file with the plugin (7.15 tests its matching of the same vectors)".
- **Now (7.2):** the same, with the file named and its making stated: "(`connected-agents/vectors/handle.json`, generated by an implementation independent of both, its `derivation` member stating the rules of §3.6 as read; 7.15 tests its matching of the same vectors)".
- **Evidence:** the file exists at that path (step 7.2, #1033). Its `description` says it is "Generated by an implementation independent of either", and its `derivation` member states the slug rule and the suffix rule as read from §3.6.
- **The question:** where the vectors come from. It matters because §3.6 states the rule in prose, and two implementations can read it the same wrong way.

**Option A, generated independently, with the reading written down (the line as merged).**
- **Pros:**
  - Keyring and the plugin are each tested against a third reading of §3.6, so a shared misreading in either shows up as a failed vector.
  - The `derivation` member puts the reading where a reviewer can compare it with §3.6.
- **Cons:** one more thing to keep in step with §3.6. A change to the rule means regenerating the file and updating `derivation`.

**Option B, generated by Keyring's own `handle.ts` and shared with the plugin.**
- **Pros:** nothing extra to keep.
- **Cons:** Keyring's tests then compare Keyring with itself. The plugin would inherit any misreading in Keyring, and the vectors could never show it.

**Recommendation: A.** The point of shared vectors is to catch two implementations agreeing on a wrong answer, and only an independent generator can do that.

- **Plan sections touched:** §7.2, by #1035. This pull request changes no text for it.

### 4. FORCED CORRECTION, §3.2 and §3.3: the fallback's `acl/grant` is 0.3 only

**This is not a proposal.** The old text contradicts §3.3's own table and the specification's schemas. That holds whatever is ruled on step 7.4.

- **Old (§3.2, "The P0 fallback"):** "calls `acl/grant` (newest served version; 0.3 shape) with the entry of §3.3 for `K_t`".
- **Corrected (§3.2):** "calls `acl/grant` 0.3 with the entry of §3.3 for `K_t` (a VTA that serves no 0.3 is refused and never stepped down to, §7.4)".
- **Old (§3.3):** "in the P0 fallback, by Keyring itself in the newest served `acl/grant` (0.3 shape; older shapes only where the VTA serves nothing newer, as `VtaClient` already does)".
- **Corrected (§3.3):** "in the P0 fallback, by Keyring itself with `acl/grant` 0.3 (a VTA that serves no 0.3 is refused and never stepped down to: 0.1 and 0.2 cannot state purposes, §7.4)".
- **Evidence, in order of weight:**
  1. **§3.3's own table**, two paragraphs below the old sentence, gives the entry `purposes` `listed`: `personalisation`, `taskExecution`. An entry without `purposes` is not the entry §3.3 describes.
  2. **The specification at the pin** (`dtgwg-trust-tasks-tf` `2a66a0351`, `specs/acl/_shared/<version>/acl-entry.schema.json`):
     - 0.1 has neither `purposes` nor `capabilities`;
     - 0.2 has `capabilities` but no `purposes`;
     - 0.3 has `purposes` and requires it.

     So no older `acl/grant` can write §3.3's entry. That is a fact about upstream, not a decision of ours.
  3. **§2.6's table**, from step 7.1's measurements, gives `acl/grant` as 0.2 on 0.79.0 and 0.3 on 0.84.0 and 0.87.0, and a VTA serves one version of each `acl` task. On a 0.79.0 VTA there is nothing to step down to that could carry the entry.
  4. **Consistent with step 7.4's line**, which #1035 changed: "the access-list writes are sent at 0.3 only, and a VTA that serves no 0.3 is refused with a clear error and never stepped down to". The correction does not rest on it. Were 7.4 ruled otherwise, (1) and (2) would still forbid the old text.
- **The code:** `VtaClient`'s two agent writes each carry `// version-pinned: an agent's entry is written at acl 0.3 only, since 0.1 and 0.2 cannot state purposes` (`VtaClient.ts:745`, `:760`, step 7.4, #1036).
- **A note on how the old text went wrong.** The old §3.3 sentence ended "as `VtaClient` already does": a plan asserting what our own code does, and wrong about it once step 7.4 pinned the writes. A plan sentence citing code is a claim with no test behind it, so nothing flagged it when the code changed. Such phrases are worth checking whenever the code they name moves.
- **Why the old text survived:** #1035 rewrote step 7.4's line and §3.15 item 4. It did not reach §3.2 and §3.3, which said the same thing in other words. Writing these records turned it up: finding 2 led back to §3.3's table.
- **Plan sections touched:** §3.2 and §3.3, in this pull request.
