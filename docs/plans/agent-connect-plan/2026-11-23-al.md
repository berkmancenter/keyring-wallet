The product owner reviewed the plan again on 2026-11-23 and decided three things, now in the plan as D27 to D29. The agent is a **contact** in Contacts and a conversation in Messages, like a person and messageable like one, drawn so it is never taken for one (plan §3.14). An agent is added to a room from the **"+" next to the message field** as well as from the room's info screen (plan §3.6). And the agent's memory is made of **memories**, the owner's "slices of context": each is one VTA context the owner names ("Education", "Healthcare"), any number are picked when the agent is connected, and for each room the owner picks which of them the agent uses there (plan §3.15).

The third decision rests on what upstream's memory contexts are, read from the pinned clone the same day (finding 3): a context is the VTA's isolation boundary; contexts form a hierarchy in which a parent's holder reaches every child; the memory store is per context, and a key prefix narrows a read without gating anything. Those facts fix the design: memories are **top-level** contexts, granted one by one and never by a parent, and never under a persona's context. They also fix its honest limit: the VTA gates memory on the entry, not on the room, so the per-room choice is a rule the agent's software keeps, the screen says so, one agent per room is the enforced form, and the binding is asked upstream as VTI-Q37 (finding 4).

The owner also asked that every new flow register its upstream gaps in the findings file as sub-findings of its feature, as a standing rule. That is now a checklist item in [`../CLAUDE.md`](../CLAUDE.md) and a "Findings by feature" index in the findings file (finding 5). The mockups were redrawn for D26 to D29 by this lane, since no UI/UX lane was live, and go to the owner as a private artifact first (finding 6). Two questions the owner asked are answered in finding 7: the plan does account for a VDC, and before today the agent was not a contact.

The companion asks the owner for nothing new. It asks upstream, through the findings file, for VTI-Q37.

### 3. What upstream's memory contexts are

- **Concluded:** read at the pin `f7b78e29d` (`external/verifiable-trust-infrastructure`, the pin in `scripts/openvtc/PINS.json`, on 2026-11-23; the 2026-11-20 baseline read `origin/main` `71d524572` because the clone was then on another commit):
  1. **One context is the isolation boundary.** `vta/memory/*` is gated on `require_context(contextId)` and the memory capabilities: "a context-A agent cannot read, write, or delete context-B memory" (`docs/02-vta/personal-ai-agents.md` Step 6). The store lives on the VTA, is versioned (`put/0.2` returns a `version`; `expectedVersion` makes a write conditional), audited and in the VTA's backups.
  2. **Contexts are a hierarchy, and a parent covers its subtree.** A context id is a `/`-separated path of at most 8 segments (`vta-sdk/src/context_path.rs`, `MAX_CONTEXT_DEPTH`); an entry's `act` names contexts "and their subtrees, and only these", and `ActScope::covers` is "segment-aware ancestry … so authority over a parent context covers its whole subtree" (`vta-sdk/src/acl.rs`); a child's policy "can never widen what an ancestor allows" (`vta-support/src/contexts.rs`). So there is a "sliced" shape, sub-contexts, but a slice under a parent is reachable by every holder of the parent.
  3. **Within a context, keys can be sliced by prefix, without a gate.** `vta/memory/list/0.2` takes a `prefix` ("a byte-prefix comparison over the UTF-8 encoding"; agents "SHOULD use `/`-delimited" keys) to "recall one family of items"; `contextId` remains "the isolation boundary" (`vti-specs-vta/trust-tasks/vta/memory/list/0.2.bundle.json`). A prefix narrows a read; it gates nothing.
  4. **Nothing binds a context to a room.** `act` is per entry and holds wherever the entry acts; the room tasks need the persona's context in `act` (plan §2.1); no task or leaf names the contexts a presenter may use in a room.
  5. `vta-agent-memory`, upstream's own memory plugin, runs one `did:key` in one context ("One context per agent (or per domain) — this is the isolation boundary") and speaks only `vta/memory/*` (`docs/02-vta/examples/agent-memory-with-vta-mcp.md`).
- **Evidence:** the files named, at the pin. Not run; step 0.1(o) measures items 2 and 4 on the lab.
- **Supersedes:** the plan's single sentence on hierarchy ("where contexts are hierarchical, their descendants", plan §3.3), which was a hedge; it is now a cited fact in plan §2.1 and §4.
- **Plan sections changed:** §2.1 (a row), §4 (two rows), §7 step 0.1(o).
- **Test impact:** step 0.1(o): an entry naming `a` reads `a/b`; an entry naming `a/b` is refused `a`; a child under the persona's context is readable by a holder of the persona's context; `vta/contexts/create` with a top-level id by Keyring's administrator session, and `vta/contexts/list` returning it with its `name`.

### 4. Memories are top-level slices, picked at connect and per room (D29)

- **Concluded:** a memory is one VTA context the owner names; Keyring creates it top level (`keyring-memory-<slug>`, `name` as typed), never under a persona's context and never under another memory, and grants it by its own path, never a parent's. The owner picks any number at connect ("Memory it can use") and, per room, which of them the agent uses there ("Memory for this room"), on the add and later from the agent's row or details. Keyring grants the **union** on the entry, narrows `act` only when a memory leaves every list, and sends the per-room list in the room offer (`contexts`), which the plugin keeps to while acting on that room's mentions. The copy says "Keyring asks the agent to keep to these in this room. Your VTA cannot enforce it."; the details offer "For your VTA to enforce this, use one agent per room." where an agent has more than one memory. Plan §3.15, D29, D11 amended, §3.2 step 1, §3.3, §3.6 steps 3 to 5, §3.7, §3.11, §6, §7 steps 5 and 7, §8.1, §9 threat (11), §10 item 16.
- **Evidence:** the owner's words: "users can add a slice of context to that data room, or even multiple slices … an 'education' slice of context that involves only things regarding some college … and then add a different slice … for example a healthcare organization"; finding 3 for why top level and why the per-room choice is behavioural.
- **Why top level, in one line each.** Under the persona's context: every agent added to a room of that persona holds that context and so would read every slice (finding 3 item 2; plan §3.3). Under another memory: the parent's holder reads the child, so giving an agent "Education" would give it whatever was filed under it. By key prefix in one context: not gated (finding 3 item 3). One context per agent only (D22's mitigation): rules out the owner's "several slices for one agent", so it stays the recommendation for enforcement and not the limit.
- **Supersedes:** "picking one memory context at connect time" (plan §1.1), "a memory context (one, from the owner's contexts, or 'None')" (plan §3.2 step 1), "At connect the owner picks one context" (plan §3.7), D11 as worded, and `memoryContext` as a single value in plan §3.11. D22's analysis of the persona-context widening stands unchanged: top-level memories are outside that subtree.
- **Plan sections changed:** §1.1, §1.4, §3.2, §3.3, §3.6, §3.7, §3.11, §3.15 (new), §5 D11 and D29, §6, §7 steps 0.1(o), 5 and 7, §8.1, §9, §10 item 16, §11, §12, the overview and status line.
- **Test impact:** the memory pickers; "New memory" (a top-level id and the typed `name`); the greyed ancestor; the `act` union and its narrowing; `rooms[].contexts` and the offer's `contexts`; the plugin's per-room rule with an entry holding two memories and an offer naming one (§7 steps 5 and 7, §8.1).

### 7. Two questions the owner asked, answered

- **Does the plan account for a VDC?** Yes, in plan §3.4: a DTG delegation credential issued by the persona to the agent's lasting key after the rotation, with the agent's signed acceptance, 7 days' validity, re-issued while the entry stands, never presented in rooms, the owner's record only; its signing route is measured in step 0.1(f) (D19). Nothing changed.
- **Once a VDC is made, does it make a contact to talk to?** Before this revision, no: the chat ran over the VTI mediator transport, not a Credo connection, so no contact record existed, and plan §3.5 listed the chat under "AI agents" and in Messages only. Finding 1 makes the agent a contact. The VDC is not what makes it one: the `AgentConnection` record does, once the agent is `active`, and the VDC is what the contact's details and the chat header read the owner from.
- **Plan sections changed:** none beyond finding 1.
