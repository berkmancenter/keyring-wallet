Alberto's session built the reference program the plan's step 7.1 asks for, `tsp-reference/ref-25-agent-pairing`, and ran its mediator half on 2026-11-26. It ran against the same mediator version the production wallet mailbox is pinned to, on a lab that listens on loopback only, first with an open configuration and then with the mailbox's own settings. This covers items 0.1(a), (h), (j) and (q) of the step. It then ran the VTA half on three versions of the VTA, which covers items (b), (c), (d), (f), (l), (o), the first-tier parts of (p) and part of (e).

**What works as the plan says.** A message reaches an agent-style key through the mediator, live and queued. A new key is refused until it switches its own sending on, and is delivered afterwards. An anonymous send is refused. A second connection for one key replaces the first. Both pairing links fit the size limit, with room to spare.

**What changed under the plan, and what it now states.** The plan's three facts below were measured on 2026-11-20 on an older mediator, 0.48.0, and were right for it. The mediator the mailbox runs is 0.53.0, and it behaves differently: its makers changed the first on purpose in 0.52.0 and document it. Nothing here corrects that earlier measurement.

- A message to a key that has never signed in at the mediator is refused. On 0.48.0 the mediator made an account for it and delivered later.
- With the mailbox's settings, a sender must be signed in. The plan said a sender needs no account; that was measured on an open mediator, and it is true there still.
- The queue holds 50 messages from one sender, not 49, and the refusal after it says to retry in 30 seconds.

**What that means for the design.** Each side signs in at the mediator before the other sends to it, and a first send that is refused is retried. Where the agent's mediator is set up as the mailbox is, Keyring's chat key signs in there before its first send. None of this is a defect in the mediator, and nothing is filed upstream for it.

**The VTA half found a version floor.** The VTA version our tooling pins is too old for agent connect: it serves the older access-list tasks, which cannot carry what the plan needs. The version the Farm runs and the version the plan was read from both work, and behave the same on every case. So agent connect needs a VTA at 0.84.0 or later, and Keyring tells a person on an older one before anything is created (finding 7). Grants, memory binding, the memory hierarchy, device registration, key swap and revoke by device all work as the plan says. Removing one memory from an agent is done with a different task than the plan named, and deleting a memory that an agent still holds needs an explicit force. One part of the revoke measurements is not written up here yet.

**The VTA signs the agent's delegation credential as the person's persona.** That was the last open question of the first tier, and it has a plain answer: the VTA has a task for it, the credential comes back exactly as Keyring wrote it with the persona's signature added, and the signature checks out against the persona's published key. An agent cannot use that task to sign as its owner. So Keyring never holds the persona's key, and the fallback the plan kept in reserve is dropped (finding 8).

**It asked Brendan for one decision** (finding 4): where the agent's mediator is not open, how Keyring sends to the agent. An answer arrived the same day, by relay: in the first tier the agent always uses the owner's own mediator, so Keyring's chat key never signs in at a mediator the owner does not control; the question is looked at again in the second tier. The plan's §3.5 is written that way. The answer came through his agent and not yet in his own words, so it awaits his confirmation.

The mailbox's settings: `deploy/keyring-messaging/mailbox/mailbox.toml` on `main` at `9aa6b7215`. The link producer: VTI `f7b78e29d`, `vti-oob-server/src/util.rs`. Era: the lab mediator of 2026-11-26, on loopback, with a Redis of its own emptied at each start.

### 1. A forward never makes an account

- **Measured.** A send to a `did:key` that has not authenticated at the mediator is refused HTTP 403, error 73, `e.p.delivery.refused`, in the open and the mailbox configuration, from a sender with and without a session. The mediator's log gives the reason, "next hop has no account on this mediator". Command: `lab/mediator.sh up open` (or `mailbox`), then `node run.mjs --only never-seen/none,never-seen/session`.
- **Tried to disprove.** The pinned source says the same in a comment (`src/messages/protocols/routing.rs`, `resolve_next_account`: "a forward never creates one, since only authentication (or an admin) admits a DID"), and the changelog lists it as a breaking change of 0.52.0: "A forward never creates an account. A local next hop with no account on this mediator is refused with `73 delivery.refused`; it used to be registered with `global_acl_default`, in either `mediator_acl_mode`." So it is documented behaviour, not a defect, and the row it supersedes was correct for 0.48.0: the mediator changed, the earlier measurement was not wrong.
- **Why it matters most.** Any part of the design that assumed a forward would create the recipient's account no longer holds. The retry of a 403 `e.p.delivery.refused` in §3.5 is the consequence.
- **Supersedes** the plan's §2.4 row "Bob never contacted the mediator before the send: HTTP 200, account created for the recipient, delivered when Bob later authenticated", measured on v0.48.0 on 2026-11-20.
- **Plan sections touched:** §2.4 (the table and "What follows"), §3.2 (the order of authentication, in the self-grant paragraph), §3.5 (sending to the agent), the Overview's first mediator row.

### 2. On the mailbox's settings a sender needs a session

- **Measured.** With the mailbox's settings every POST to `/inbound` that carries no session token is refused HTTP 401 "Missing credentials", whatever the message. With a session and the self-grant the same sends are accepted. Command: `lab/mediator.sh up mailbox`, then `node run.mjs`; the `…/none` rows.
- **Why, from source.** A mediator admits a send with no session only as a relay (`src/common/jwt_auth.rs`, `anonymous_relay_session`): when `enable_inter_mediator_relay` is set or `global_acl_default` grants `SEND_FORWARDED`. The mailbox's default grants `SEND_FORWARDED_CHANGE` and not `SEND_FORWARDED`.
- **Supersedes** §2.4's "Sender … needs no account" as a general statement. It holds on the open configuration.
- **Plan sections touched:** §2.4, §3.5, the Overview's second mediator row, D18's wording, step 0.1(q)'s acceptance.

### 3. The self-grant, the queue and `Retry-After`

- **Measured, mailbox configuration.** A new account's send is refused HTTP 403, error 60, `e.p.authorization.send_forwarded`. After a signed `messaging/account/update/0.1` with `acl.sendForwarded: true`, sent on its own socket, the answer shows the bit on and the next send is delivered. One sender has 50 messages accepted for an offline recipient, and the 51st is refused HTTP 503, error 95, `e.p.limits.queue.peer`, with `Retry-After: 30`. No other refusal measured carries the header (401, the three 403s, 400).
- **Supersedes** §2.4's "49 accepted; the 50th refused", and answers §2.3 items 10 (the self-grant on the mailbox's default) and 11 (`Retry-After` on REST).
- **Plan sections touched:** §2.3 items 10 and 11, §2.4, §3.2 (the failure path's code and the shape of `account/update`), the failure table of §3.10.

### 4. A design consequence that needs Brendan's confirmation

- **Concluded.** Where the agent's mediator is configured as the mailbox is, a send from Keyring with no session there is refused, so the design has to answer it. Three ways: (a) Keyring's `chatDid` authenticates at that mediator and makes the self-grant; (b) the agent always uses the owner's own mediator, where `chatDid` already holds an account; (c) the agent chat uses a mediator that is open. The measurement forces a response, not a particular one.
- **Footprint of (a).** `chatDid` ends up with an account and a self-grant on a mediator the owner does not control.
- **What the plan said.** §3.5: "Keyring needs no account there."
- **What it says now.** §3.5 states (b) for P0: the agent always uses the owner's own mediator, and (a) and (c) are revisited in P1.
- **How the decision arrived.** On 2026-11-26, relayed by the release coordinator from Brendan's agent as his decision: "for P0 the agent always uses the owner's own mediator, so Keyring's chat key never signs in at a third-party mediator. To be revisited in P1." It is recorded as received by relay and awaits the plan owner's own confirmation. An earlier draft of §3.5 in this pull request stated (a); that is superseded by this.
- **Open.** The plan owner's own confirmation. The plan's §11 Q7 (how Keyring learns the agent's mediator) is simpler under (b): the agent's mediator is the owner's.

### 5. The links (step 0.1(h))

- **Measured.** The `auth/oob` link, built as the pinned producer builds it and held to that producer's own test vector, is 108 bytes plus the VTA's DID. The lab VTA's own DID (vta 0.87.0 on localhost, 73 bytes) gives 183 bytes, a version 9 code at level M, recorded in the rung's `fixtures/links-lab-vta.json`. A `did:webvh` of 84 bytes (a 46-character SCID and a 27-character host, the shape of a VTA of the local stack) gives 192 bytes, a version 10 code. The longest DID that fits is 143 bytes. A `did:peer:2` of 504 bytes gives 612 and does not fit. The fallback's `agent-connect` link with a `did:key` is 170 bytes, and 182 with the widest scope.
- **Decided here, as the step asked.** The scope travels in a flow member `_scope`: capabilities as one letter each (`r`, `w`, `p`, `o`), purposes by name after `~`. It costs 8 bytes plus the scope.
- **Concluded.** Item (h) holds for any VTA DID of 143 bytes or less, by construction: 251 bytes is the capacity of a version 11 code at level M, and the link is 108 bytes plus the DID.
- **Not measured.** A phone's camera: "decodes" is a software decode of the drawn code.
- **Plan sections touched:** §3.2 (the link and the fallback), the Overview's link row.

### 6. What step 0.2 records

- **No `VTI-NN` finding.** Nothing measured here is a defect: findings 1 and 2 are documented behaviour of the pinned mediator.
- **The ledger.** The plan's §10 item 11 (VTI-Q36) asked for "a documented per-sender queue cap with `Retry-After`". The pinned mediator documents it (`ERRORS.md`: "Queue-limit refusals (61, 62, 95) include a `Retry-After` header") and the rung measured it. That part of the question is answered; the self-service path on a closed mediator and the refusal at send for a `did:peer` naming another host stay open.

### 7. The VTA half: three versions, and the first 13 cases

- **Fixture.** One VTA on localhost that serves its own `did:webvh`, after upstream's own local recipe (`local-dev/vta-root-webvh-setup.toml`): a plaintext secret backend, no mediator, `VTA_ALLOW_PRIVATE_ENDPOINTS=1`; one seeded administrator, a `did:key` the rung holds. Signed Trust Tasks over the HTTPS binding only. Debug builds from source. No VTC, no DID host, no Farm.
- **Era.** Lab VTAs of 2026-11-26 at three commits of OpenVTC/verifiable-trust-infrastructure: `f7b78e29d` (vta 0.79.0, the commit `scripts/openvtc/PINS.json` pins), `97fda9813` (vta 0.84.0, the tag `vta-service-v0.84.0`, which the Farm's gate VTAs run), `4e5861d95` (vta 0.87.0, the commit the plan's facts were read at). The last two are **not the pin**; they are detached checkouts of the pinned clone, and the pin did not move.
- **Commands.** `lab/vta.sh up <binary> <commit>`, then `node vta-serves.mjs` and `node vta-run.mjs`; recorded in the rung's `fixtures/vta-<version>.json` and `fixtures/vta-cases-<version>.json`.
- **Measured: what each serves.** The table is the plan's §2.6. In short, 0.79.0 serves `acl/grant`, `revoke` and `update` at 0.2 and memory at 0.2; 0.84.0 and 0.87.0 serve them at 0.3, with `acl/list` 0.4 and `vta/memory/get` 0.2. Each serves one version of an `acl` task, not two. None serves `auth/oob`.
- **Measured: the cases.** None can run on 0.79.0. On 0.84.0 and 0.87.0 these 13 are recorded, repeat, and are the same on both: the seeded administrator is unrestricted; a scoped administrator is refused a top-level context; `acl/grant` 0.3 takes kebab-case capability names and requires `purposes`; an entry bound to one memory is refused another (`contextForbidden`); an entry naming a parent reaches its children and not the reverse; registering as `aiAgent` makes `rooms/keys/act` refuse `permissionDenied`; `acl/swap-key` by the entry's own subject, with a `linkProof` signed by the new key, moves the whole entry and its device; revoking the key `device/list` names removes the entry and the device after one swap and after two; a disabled device cannot sign in again.
- **Supersedes.** That the plan's VTA facts hold "at the pin": they hold from the commits they name, all later than the pin. Step 0.1(p) item 5's "`acl/update` removing a memory from `act`": `acl/update` never narrows `act` (`narrowingNotPermitted`); `acl/revoke` 0.3 with `kind: "act"` does, and the `act` it names is what remains. Item 6's unqualified "delete … succeeds without `force`": true of a memory that holds only items; one that an entry names is refused `notEmpty` without it. Item 2's `Conflict` code: the refusal is `taskFailed` with "conflict" in its message. §2.3 items 2, 3 and 4, and §2.1's "whether a disabled device is refused authentication is not measured".
- **Concluded.** Agent connect needs a VTA at 0.84.0 or later. Keyring finds that out from the VTA's own answer (`unsupportedVersion` with its served versions) at the start of a connect, with the `auth/whoami` guard, and says so before anything is created.
- **Plan sections touched:** the "Measured at" paragraph of §2, a new §2.6, §2.1 (the `device/disable` row), §2.3 items 2 to 4, the P0 exit's revoke wording in §7.0, step 0.1's first line and step 0.1(p) items 2, 5 and 6.
- **Not written up here yet.** What a session opened before a revoke or a narrowing may still do. The plan says "under measurement" where that bears.
- **Not for this PR.** Whether `PINS.json`'s VTI pin advances. It is its own decision, recorded by the release coordinator.

### 8. `keys/sign-document` signs the delegation credential as the persona (step 0.1(f))

- **Fixture.** As finding 7, plus a persona made for the case: a context, and a `did:webvh` the VTA mints and holds the keys of (`vta/webvh/dids/create` 1.2, the task Keyring makes a persona with). **Deviation:** it names no `serverId`, so nothing hosts its log. The VTA reads the persona's document from the log it holds, and the rung reads it from the create answer. The agent's entries are the plan's `application` shape (`keys` scope `none`).
- **Era.** Lab VTAs of 2026-11-26: vta 0.84.0 at `97fda9813` and vta 0.87.0 at `4e5861d95`. At the pinned 0.79.0 the task is served, and the case cannot run, because its agent entries need `acl/grant` 0.3.
- **Commands.** `node vta-run.mjs --only f-sign-as-persona`; recorded as the case `f-sign-as-persona` in `fixtures/vta-cases-<version>.json`. One credential each VTA signed is kept in `fixtures/vta-signed-as-persona-<version>.json`, and `npm test` verifies it with no VTA running (`proof.test.mjs`).
- **Measured: it signs.** The administrator sends `keys/sign-document/0.1` with `{ keyId, document }`: `keyId` is the persona's `signingKeyId` (`<persona DID>#key-0`, returned by the create and by `vta/dids/list`), `document` the unsigned grant of §3.4. The answer carries `signerDid` (the persona), the `proof`, and the `document` with the proof added. The proof is a `DataIntegrityProof`, `eddsa-jcs-2022`, purpose `assertionMethod`, by the persona's `#key-0`, and it carries the document's `@context`. Every member of the credential comes back as sent.
- **Measured: it verifies, and the check bites.** The proof verifies with the key the persona's DID document lists for that method. The same check fails after one scope is added to the credential, and with another persona's key.
- **Measured: what it refuses.** Another persona as `issuer`: `keys/sign-document:issuerMismatch`. A `did:key` as `issuer`: `keys/sign-document:failedPrecondition` (the key signs only as the DID whose log it authorizes). No `issuer`: `documentInvalid`. A document that has a proof: `proofPresent`. The persona's key-agreement key: `keyTypeUnsupported`. A key nobody holds: `keys:notFound`. It also signs with `issuer` as an object holding `id`, and under `authentication`.
- **Measured: the agent cannot sign as the persona.** Four agent entries asked for the same signature and each was refused `permissionDenied`: the agent's memory entry; the same with the persona's context added; an entry in the persona's context that lists `sign-document`; and one with every capability an `application` has. The first two lack the capability. The last two hold it and are refused because the persona's key is not among the keys they may use.
- **Measured: the other candidate.** `vta/credentials/issue/0.2` answers with a credential whose issuer is the VTA's own DID, with the one credentials context, types `VerifiableCredential` and the type asked for, and no `issuerScope`. It is not the persona's credential and not the DTG shape.
- **Read, not run.** `vault/sign-trust-task` 0.2 and `credential-exchange/issue` 0.1 are served on all three versions (`vta-serves.mjs`); neither was called.
- **Supersedes.** §2.3 item 5's "which VTA task signs", D19's conditional ("if it has a task ... if not, the VDC is carried in a Trust Task envelope the VTA signs"), the fallback line of step 7.3, and the "VDC signing as the persona" row of the upstream-dependency table. VTI-Q32's first half is answered; its second half (status hosting) stays open.
- **Concluded.** The grant is signed by the VTA, as the persona, with `keys/sign-document/0.1`; the envelope fallback is not needed. Step 7.3's signer is one new `VtaClient` call that sends the unsigned credential with the persona's `signingKeyId`, which Keyring already reads when it makes or lists a persona.
- **Plan sections touched:** §2.3 item 5, §2.6 (the table), §3.4 (the `issuer` row), D19, the upstream-dependency table and step 7.3 in §7, the asks table in §10, and the Overview's test row for the VDC.
- **Not shown.** A persona whose log is hosted, so that a third party resolves it; a status entry; a second implementation's verifier (the check is the rung's own code); the task over DIDComm or TSP.
