### 12. PROPOSAL, agreed by relay 2026-11-26 (own confirmation before `main`), §6 and §7.7: an expired agent is offered "Connect again" and "Remove", not "Extend"

- **Old (§6):** "Extend" for a temporary agent, and the canvas drew it on an "Expired" row too.
- **Measured** (the test lane, VTA 0.84.0, one scratch run):
  - right after expiry the entry is still listed, `acl/update` 0.3 with a new `expiresAt` is accepted, and the agent signs in again;
  - once the VTA's sweeper has run, `acl/update` answers `acl/update:notFound`, and only a new `acl/grant` brings the key back.
- **The sweeper, at `97fda9813`:** `sweep_expired` deletes expired entries (`vta-sweepers/src/acl_sweeper.rs:41`). It runs from the VTA's periodic task (`vta-service/src/server.rs:2167`) every `auth.session_cleanup_interval` seconds, default 600 (`vti-common/src/config.rs:756`), set by the operator.
- **So** an "Expired" row is either still there or gone, and Keyring cannot tell without asking.
- **Unmeasured:** whether the device registration and `deviceId` survive the sweep (is a re-grant the same agent?), and a revoke of an entry already gone.

**Option A, "Connect again" (a new pairing with the name filled in, which replaces the record when it connects) and "Remove"; "Extend" only before expiry (recommended).**
- **Pros:** one behaviour whatever the sweeper has done, and access never comes back without the terminal's number.
- **Cons:** a new pairing even a minute after expiry.

**Option B, "Extend" on an expired row, falling back on `notFound` to a new `acl/grant` of the old key behind Approve and the biometric.**
- **Pros:** one tap.
- **Cons:** access comes back without a fresh pairing, and whether that is the same agent is unmeasured.

**Recommendation: A.** "Remove" on an expired row revokes the entry if the VTA still lists it, and drops the record either way.

### 20. PROPOSAL, agreed by relay 2026-11-27 (own confirmation before `main`), §3.15 and §7.7: a memory create an approval rule can hold

- **The gap:**
  - §3.15 (D32) has Keyring create every memory, and a memoryless agent's own context, with `vta/contexts/create`.
  - The approvals feature offers `vta/contexts/create` as a task the owner can hold for approval (`approvalRules.ts`, `OFFERED_TASKS`), and the approver a rule names may be this phone.
  - A create the phone sends about itself, held for its own approval, would wait on itself. That is why the app had no caller of `createContext`, and a guard test said so (`approvalRules.test.ts`).
  - Neither the plan nor the approvals feature says which wins. CI found the conflict when the memory code (#1068) became the first caller.
- **Built in #1068, as the interim:** the phone's creates are sent with `waitForConsent: false`, the client's own rule for a task the phone sends about itself. A held create is refused at once and the create fails; it never hangs. The guard now pins exactly that: one caller, never waiting.

**Option A, the phone's creates never wait; a held create fails with its own words (recommended).**
- **Proposed words:** "Your VTA asks for approval before a memory is made, so this one wasn't made."
- **Pros:**
  - no deadlock in any configuration;
  - the owner's rule still holds every other creator;
  - this is what #1068 builds.
- **Cons:** an owner who holds context creation cannot make a memory from the phone at all until the rule is lifted.

**Option B, take `vta/contexts/create` off the tasks an owner can hold.**
- **Pros:** "New memory" always works.
- **Cons:** it removes a control the approvals feature offers, for every creator, to fix one caller.

**Option C, wait for consent when the rule's approvers do not include this phone, and refuse at once when they do.**
- **Pros:** an owner whose rule names another approver can still create memories from the phone, after that approval.
- **Cons:** the phone must read the rule's approver set before each create. A wait of minutes would sit inside the connect flow.

- **The words must name the rule, not ask for a retry.** With `waitForConsent: false` the client throws before `onConsentPending` runs, so the approver's wait note (`ApproverWaitNote`) never mounts. That component's own comment warns that a `waitForConsent: false` path makes its claim false. The general failure "Couldn't create the memory. Try again." would then be wrong: trying again fails the same way until the rule changes. So the logic tells a held create apart (its own code, `heldForApproval`), and the screen shows Option A's words, never the retry prompt.

**Recommendation: A for P0, with C as the later refinement if owners ask for it.** The same applies to the empty context Keyring creates for a memoryless agent (§3.3), so with a holding rule such a connect fails with the same words.

- **Plan sections touched:** §3.15, §6 (the words), §7.7.
