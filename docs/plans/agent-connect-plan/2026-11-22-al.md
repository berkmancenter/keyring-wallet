The product owner read the plan on 2026-11-22, after a meeting with its author, and accepted it as the **P0 of a wider vision** the lab has been researching: a person's AI agent that carries its memory, its permissions and its record of what it did with the person, across models, across programs and across communities. It asks the plan's author for two small edits on his branch: the one stale sentence in plan §7, and the status line of each promoted entry in `vti-asks.md`. It asks nobody else for anything.

## Findings and decisions

### 1. The plan is the P0 of a wider vision; what the vision adds is not in this plan

- **Concluded:** the lab's AI research (two rounds, 2026-11-19 to 2026-11-20: a landscape of person-controlled AI, and a brainstorm on models, memory, community rules and the person's screens) describes the whole; this plan is its first buildable piece and is accepted as such. The research is a set of pages and notes, not a plan, and is not linked here because it is not in this repository.
- **What the research covers that the plan does not, by design:** switching the model behind an agent, and what is lost on a switch; where the agent's memory lives and how it moves between programs (the plan uses the VTA's per-context memory and does not read it, plan §3.7); a community's AI rules shown as a card before anything is shared (the plan has a yes/no setting, advisory, plan §3.8); labels for what is proved, seen or only said about an agent, its program and its model; "acting for" another person; a person's own standing terms (MyTerms, P1 in plan §1.1); a hosted or headless agent (P1, plan §3.12). The research's screens (21 frames) drew a connect flow by scanning a code and comparing a short number on both screens; the plan types a four-digit number from the terminal into Keyring and never shows it in Keyring (plan §3.2, D8). The plan's form is kept: it is the decided design, with its reasoning in the author's companion (finding 10 there).
- **Where the two agree:** the agent is a separate program, never the person's VTA, and the screens keep "your agent" for the VTA and "AI agent" for the session (plan §1.4, D20); the agent's authority is the ACL entry and its record of ownership is a delegation credential (plan §3.4); revoke is one action and never promised instant (plan §3.9); the "AI agent" mark on anything the agent writes (plan §3.6); a fixed, model-free reply to strangers (plan §3.13).
- **Framing rule carried over:** Keyring is a research project of the lab, not a product of any state or community; a plan or page describes it so. The plan already does.
- **Supersedes:** nothing in the plan. It supersedes the research's connect-flow mock (compare a number) as a proposal for P0.
- **Plan sections changed:** none.
- **Test impact:** none.

### 2. Mentions are required for the demo; the gap is raised upstream now

- **Concluded:** a person must be able to address their agent in a room by `@`-mention. The plan has it (plan §3.6: the composer inserts `@<handle>`; the plugin matches its own whole handle; a structured `mentions` body member is written only where a room's profile lists it, and no profile can list it today). The product owner's words: "we should if there is a gap upstream add it". So the gap is raised as a question now, instead of waiting for the ledger's promotion rules: VTI-Q26 asks for a registered `mentions` record member and for delivery or a read leaf scoped to the records that mention the presenter.
- **Evidence:** plan §3.6 and §10 items 3 and 4; ledger AC-04. Tried to disprove at the pin: `git grep -i mention -- docs/02-vta/data-rooms.md vti-specs-core/trust-tasks/rooms` in `external/verifiable-trust-infrastructure` at `f7b78e29d` finds nothing; the plan's author found the same at `origin/main` `71d524572`.
- **Supersedes:** the ledger's "not yet raised" for AC-04 (the ledger file itself is not edited here; finding 7).
- **Plan sections changed:** none. P0 keeps the text fallback; mention enforcement stays P1 (plan §1.1).
- **Test impact:** none beyond plan §8.1's mention tests.

### 3. One codebase: a step is one PR here, and one sentence of the plan is stale

- **Concluded:** the plan is implemented in this repository only. keyring-bifold was folded into it at `bifold/` (#960, #970; `origin/main` `7856855ed` carries the fold), so "Steps touching `bifold/packages/*` are paired bifold PRs" (plan §7, first paragraph) no longer holds: a step that changes `bifold/packages/*` is one PR in this repository's stack, with no pin to bump. The process document already says so at the tip of #957's branch (`09935e35f`, [`../CLAUDE.md`](../CLAUDE.md) "Implementing a plan: stacked PRs", "Commits": "one PR here, with no paired PR and no pin to bump"); the plan's branch is based on an older commit of it (`3343e57c`), whose copy still says "paired PR in `keyring-bifold`", so the plan inherits the older wording until it takes the tip. A further move of `bifold/packages/*` to `packages/*` is open as drafts #978 and #979 on the integration branch `feat/one-tree`; until it merges the plan's paths are right, and after it every `bifold/packages/core/...` path in the plan reads `packages/core/...` and the test command in plan §8.1 becomes `cd packages/core && yarn test connected-agents`.
- **Evidence:** PR #970 merged ("fold keyring-bifold into this repository at bifold/"); `git merge-base --is-ancestor 7856855ed origin/docs/agent-connect-plan` fails, so the plan's branch predates the fold; #978 ("move the framework's packages to packages/", draft) and #979 (draft) open on 2026-11-22.
- **Supersedes:** the plan's "paired bifold PRs" sentence. The plan's author is asked to replace it on his branch; this companion does not edit the plan body.
- **Plan sections changed:** §7 (one sentence, owed); §8.1 (the path, when #978 merges).
- **Test impact:** none.

### 8. How the session reaches Keyring, stated in one place

- **Concluded:** the product owner asked which technology connects Claude Code to Keyring. From the plan: **MCP** between the Claude Code session and the plugin (the plugin is an MCP stdio server with a channel and a `reply` tool, plan §3.12) and between the plugin and the person's VTA (`vta-mcp`, as the agent's own key); **DIDComm v2** carrying **Trust Task envelopes** with document proofs, as authcrypt messages inside authcrypt `routing/2.0/forward`s posted to the recipient's mediator, for the pairing messages and for the one-to-one chat (`keyring/chat/1.0`, plan §3.2, §3.5); a **trigger link** shown as a QR for the pairing (plan §3.2); the VTA's own tasks for enrolment, key swap, rooms and memory (`device/register`, `acl/swap-key`, `rooms/keys/present|open|seal`, `vta/memory/*`); a **DTG delegation credential** (VDC) as the owner's record (plan §3.4). Not used: TSP (compiled into the mediator but not measured on this path, plan §2.4), DIDComm v1, the Credo mediator and Credo connections (the chat gets a carrier adapter, plan §7 step 6).
- **Evidence:** plan §2.4, §3.2, §3.5, §3.12.
