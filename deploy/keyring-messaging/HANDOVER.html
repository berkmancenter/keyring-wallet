Keyring push gateway

How to run the service that wakes a person's phone when their agent needs them, without telling Apple or Google anything about why.

Tested on a real iPhone · 2026-09-29 upstream e542a9d7 + patch 0001 no secrets on this page

In the test, a request from the person's agent showed a notification on the phone within about 5 seconds, with the app in the background and after it was force-quit. With the app open it showed nothing, which is the design. The package lives in deploy/keyring-messaging/ of the Keyring wallet repository, with the same text as HANDOVER.md.

1. What the gateway is

Each Keyring user has an agent: a server-side service (a VTA) that acts for them. Sometimes the agent needs the person, for example to approve a request. If the app is closed, the agent can't reach it. The gateway solves that one problem. It's a doorbell.

  • It holds Keyring's Apple and Google push credentials, and the phones' push tokens, each behind a random handle. The agent only ever sees the handle.
  • It sends a push with no content. Apple and Google see that a Keyring push reached a phone at a certain time. The phone shows its own line (“Something is waiting for you in Keyring.”) and gets the actual request from its agent.
  • It doesn't carry messages, hold user data beyond push tokens, or replace Keyring's DIDComm mailbox.
  • Who may use it: a phone registers itself (anonymous, rate-limited) and must name an agent the gateway serves. Only that agent can set who may wake the handle, and only agents on that list can wake it. Both calls are documents signed with the agent's own key; the transport's identity never authorises anything.

2. The image

OpenVTC's vti-push-gateway, pinned at e542a9d77a7369f4f3da01d573107ea155c80691, plus one patch of ours.

Way How
Download the CI build (preferred) The push-gateway-image workflow builds for amd64 and arm64 on GitHub runners, runs the gateway's own test suite with the patch applied, and uploads each image as a run artifact. Nothing goes to a registry. gh run download <run-id> -R berkmancenter/keyring-wallet -n vti-push-gateway-image-amd64, then docker load -i vti-push-gateway.tar. The image is tagged keyring-messaging/vti-push-gateway:<commit>.
Build it yourself docker compose build gateway in the package folder. It checks out the pinned commit and applies gateway/patches/*.patch, and fails if a patch no longer applies. About 4 GB of RAM and several minutes.

Why the patch exists

Upstream sends every wake as a silent background push. On iPhone, Apple throttles those (“don't try to send more than two or three per hour”) and drops them after a force-quit (“If something force quits or kills the app, the system discards the held notification”). An approval can't depend on that.

With GATEWAY_ALERT_LOC_KEY set, the patch sends an interactive wake as a notification the phone's system shows itself: an APNs alert with a loc-key, or an FCM notification with a body_loc_key. Both carry a key, never text. Background wakes stay silent.

The patch is self-contained, with its own tests and README section, and is a candidate for contributing upstream (tracked as CONTRIB-01). The project submits it itself; please don't open anything upstream. Move the pinned commit only together with the agents the gateway serves, because authorisation changed in upstream PR #32.

3. Settings and secrets

Copy .env.example to .env. Secrets are files in ./secrets/, mounted read-only at /run/secrets/gateway/. The gateway runs as uid 10001 and refuses to start if a secret is readable by anyone else: 

sudo chown -R 10001:10001 secrets data/gateway
sudo chmod 700 secrets data/gateway && sudo chmod 600 secrets/*

3.4 The gateway's own identity

The gateway has its own did:webvh. Agents address wake-ups to it, and it collects them from a DIDComm v2 mediator it connects out to, so it needs no inbound port for them. The identity comes from a VTA, made from the VTA's push-gateway template, in three steps:

  1. Request, on the machine that will hold the identity. This stores a one-time seed under pnm's config directory and writes request.json. 
    pnm bootstrap provision-request --template push-gateway \
  --var URL=<the mediator's DID> \
  --var SERVICE_TSP='{"id":"{DID}#tsp","type":"TSPTransport","serviceEndpoint":"<the mediator's DID>"}' \
  --var WEBVH_SERVER=<the DID-hosting server id> \
  --context-hint push-gateway
  2. Approve, by an admin of that VTA. This prints a SHA-256 digest and writes a sealed bundle.armor. 
    pnm --vta <vta> bootstrap provision-integration --request request.json \
  --context push-gateway --create-context
  3. Open it into the identity file with tools/gateway-identity. Back the seed up first. 
    cp <pnm config>/bootstrap-secrets/<bundle-id>.key ./seed-backup.key   # back it up first
cd tools/gateway-identity && cargo build --release
./target/release/gateway-identity --bundle bundle.armor --seed <bundle-id>.key \
  --digest <digest from step 2> --mediator <the mediator's DID> \
  --out ../../secrets/gateway-identity.json
    Then set GATEWAY_IDENTITY_FILE=/run/secrets/gateway/gateway-identity.json.
Don't run pnm bootstrap open on this bundle. For this bundle type it prints a summary, writes nothing, and deletes the one-time seed first, so the gateway's keys are gone and you'd have to start over. No upstream tool writes the gateway's identity file (tracked as VTI-53), which is why tools/gateway-identity exists. It opens the bundle with the VTA SDK's documented open_bundle, keeps the seed, and writes the file with mode 0600.

Mediator account: nothing to create on a mediator that admits new DIDs by default; the gateway registers itself the first time it authenticates. On a mediator that denies unknown DIDs, its admin must allow the gateway's DID.

3.5 Which agents it serves: your decision

GATEWAY_ALLOWED_CONTROLLERS lists the agents whose phones may register. It's required: unset means every registration is refused.

Option Meaning Limits
Exact list of agent DIDs Only those agents' phones can register or be woken. There are no wildcards, by upstream's design Every new person's agent means a configuration change and a restart
* (open) Any agent may register phones A startup warning. Still bounded: 4096 live handles per agent, unprovisioned handles dropped after an hour, and per-sender and per-handle budgets

For the production test the list is just our test agent's DID, which we'll send you. What production needs is open, and it's your call with the project lead.

3.6 Everything else

Setting Value and note
GATEWAY_HOST your public hostname
GATEWAY_HTTP_PER_SEC / _BURST 100 / 400: behind the proxy every phone shares one IP, so the upstream default of 10/s is too low
GATEWAY_DEV_ECHO_SENDER blank in production; when on, wakes are logged and never sent
GATEWAY_METRICS_TOKEN optional bearer token for /metrics, which listens only on the container's loopback
GATEWAY_LOG vti_push_gateway=info,tower_http=info

4. What the host needs

  • Docker with Compose v2.
  • A public HTTPS hostname. Phones register at https://<host>/trust-tasks. The bundled Caddy gets and renews the certificate; it needs a DNS record and ports 80 and 443 open.
  • Outbound access to api.push.apple.com, api.sandbox.push.apple.com, fcm.googleapis.com, oauth2.googleapis.com, the DIDComm v2 mediator, and the did:webvh hosts.
  • A persistent volume for data/gateway. It holds phones' push tokens in clear text, so protect it and its backups like credentials.
  • Backups: the store file (encrypted), secrets/ and .env. To restore, put them back and run docker compose up -d.
  • Health: GET /healthz returns ok. Metrics (Prometheus, container loopback :9300): gateway_register_total, gateway_provision_total and gateway_wake_total{outcome=delivered|transient_failure|token_unregistered|not_allowed}.
  • Logs: docker compose logs gateway. No message content is ever logged, because none passes through.

5. Go-live checklist and production test

The production test

  1. We build the push-test app with your URL and install it on a test iPhone and Android phone.
  2. The phone links to our test agent, whose DID is on your allowlist, and turns notifications on. gateway_register_total and provision_total{outcome="ok"} go up.
  3. We trigger an approval request with the app in the background, then force-quit, then open. Expected: the line in the first two cases, nothing in the third, and wake_total{outcome="delivered"} up each time.

6. Known gaps

  • No unregister. A removed phone's handle and token stay in the store. They can't be used once no agent wakes them, but they are still stored tokens.
  • Disabling or wiping a device at the agent doesn't clear its wake channel (tracked as VTI-Q37). Only the phone clearing its own channel does. The app clears it when it unlinks; a lost phone can't.
  • Timing is visible. The gateway, Apple and Google see when a wake goes out, which correlates with the agent's activity. The content never passes through.
  • The upstream pin moves with the agents (§2).
